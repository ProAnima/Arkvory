# Кластер высокой доступности

Кластер Arkvory продолжает работать, когда отказывает один сервер площадки. Два или три Linux-сервера держат одинаковую копию одного блочного тома. Один сервер **активный** — на нём работает Arkvory. Если он отказывает, менеджер кластера изолирует его (fencing) и запускает Arkvory на другом сервере с теми же данными.

Кластер защищает от потери сервера, диска или сетевого канала внутри одной площадки. От потери всей площадки он не защищает: для этого держите [зеркала](./mirrors) на другой площадке и [резервные копии](./backups) вне кластера.

## Как это работает {#how-it-works}

- **Один том, синхронные копии.** DRBD 9 копирует каждую запись тома на другие серверы до того, как запись завершится (protocol C). На томе лежит вся установка: база данных, хранилище, конфигурация и релизы. Каталог и байты файлов не расходятся.
- **Где работает Arkvory, решает Pacemaker.** Corosync и Pacemaker держат кворум, выбирают активный сервер и запускают по порядку: том, файловую систему, базу данных, `arkvory-replica`, API, worker, агента резервных копий, таймер обновлений и виртуальный IP-адрес. Собственных выборов у Arkvory нет.
- **Fencing обязателен.** Прежде чем другой сервер примет работу, Pacemaker выключает отказавший сервер через устройство питания (IPMI, iDRAC, iLO, Redfish, PDU) или гипервизор. Без fencing два сервера могли бы писать одновременно. Кластер без fencing не запускается.
- **Две копии для каждой подтверждённой записи.** Arkvory отвечает на запись успехом, только когда она лежит минимум в двух полных копиях (см. [Запись](#writes)). Когда копии не хватает, запись останавливается, а чтение продолжается.

| Профиль | Серверы с данными | Свидетель                                                                          | Когда отказывает один сервер с данными                 |
| ------- | ----------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `ha-2`  | 2                 | обязателен: небольшой сервер без данных, на нём `corosync-qnetd` и tiebreaker DRBD | Запись стоит до возврата сервера или решения оператора |
| `ha-3`  | 3                 | не нужен: три сервера решают большинством                                          | Запись продолжается: остаются две копии                |

Рекомендуемый профиль — `ha-3`. `ha-2` дешевле и честно останавливает запись вместо того, чтобы держать данные в одной копии.

Кластер работает с нативными пакетами Linux. Установки на Windows и в Docker Compose остаются отдельными серверами с зеркалами и резервными копиями.

## Запись и копии {#writes}

**Полная копия** — локальный диск активного сервера, если он актуален, и каждый другой сервер с данными, который подключён, реплицирует и актуален. Сервер, который ресинхронизируется, не считается, пока не станет актуальным. У свидетеля нет данных, он не считается никогда.

Каждый запрос, который меняет данные (HTTP API, реестр контейнеров, Git LFS, npm), проверяется дважды:

- **до** выполнения — по копиям за последнюю секунду;
- **после** фиксации и синхронизации данных — по свежему чтению состояния тома.

Когда полных копий меньше, чем нужно записи, клиент получает HTTP 503 с кодом `unavailable`, причиной `replication_degraded` и заголовком `Retry-After`, но никогда не 2xx. Статус задачи завершения загрузки (`GET /api/v1/jobs/{id}`) проверяется так же: по нему клиент узнаёт, что большая загрузка опубликована.

503 после фиксации означает, что операция может лежать только в одной копии. Повторите запрос с тем же `Idempotency-Key`: повтор вернёт уже существующий результат, а его 2xx подтвердит его, как только снова будут две копии.

Чтение, скачивание, консоль, вход и выход, отзыв и пакетный запрос Git LFS работают, пока запись остановлена.

Администратор, вошедший в консоль, видит баннер, пока запись остановлена или действует решение об одной копии.

## Требования {#requirements}

- Два или три сервера с данными с одинаковым дистрибутивом Linux, одной версией пакета Arkvory и диском (или логическим томом) полного размера для тома на каждом. Рассчитывайте на всё хранилище плюс базу данных.
- Для `ha-2` — третий небольшой сервер-свидетель. Диск для данных ему не нужен, Arkvory на нём не работает.
- Сеть между серверами с малой задержкой. Каждая запись ждёт остальные серверы, поэтому задержка добавляется к каждой записи. По возможности используйте выделенный канал.
- DRBD 9 (модуль ядра и `drbd-utils` 9; многие дистрибутивы поставляют старый модуль 8.4, поэтому берите пакеты LINBIT), `pacemaker`, `pcs`, `corosync`, `resource-agents` (в Ubuntu — `resource-agents-base` и `resource-agents-extra`), агенты fencing для вашего оборудования. Для `ha-2`: `corosync-qdevice` на серверах с данными и `corosync-qnetd` на свидетеле.
- Устройство fencing для каждого сервера с данными и учётные данные к нему.
- Свободный IP-адрес в сети серверов. Клиенты подключаются к этому виртуальному адресу.
- TLS-сертификат для виртуального адреса. Храните сертификат и ключ на томе, чтобы каждый сервер находил их по одному пути.

## Сборка кластера {#build}

Команды ниже используют имя ресурса по умолчанию `arkvory`, каталог установки `/opt/proanima-arkvory` и `/dev/vg0/arkvory` как диск под томом. Выполняйте их от root.

1. На каждом сервере с данными распакуйте пакет Arkvory, не устанавливая его. Это добавит файлы и команду `arkvory` и ничего не создаст в `/opt/proanima-arkvory`:

   ```bash
   dpkg --unpack Arkvory-amd64.deb
   ```

2. На одном сервере с данными составьте план. Он запишет ресурс DRBD и команды Pacemaker в каталог для проверки:

   ```bash
   arkvory cluster-plan --cluster ha-2 \
     --nodes node-a=10.0.0.11,node-b=10.0.0.12 --witness witness=10.0.0.13 \
     --disk /dev/vg0/arkvory --fence-agent fence_ipmilan \
     --virtual-ip 10.0.0.100/24 --output /root/arkvory-plan
   ```

   Для `ha-3` перечислите в `--nodes` три сервера и не указывайте `--witness`. Необязательные параметры: `--cluster-resource`, `--drbd-minor` (по умолчанию 0), `--drbd-port` (по умолчанию 7789), `--filesystem` (`xfs` или `ext4`, по умолчанию `xfs`). Имена должны совпадать с именами хостов серверов.

3. Скопируйте `arkvory.res` в `/etc/drbd.d/` на каждый сервер, включая свидетеля. Создайте метаданные на серверах с данными и поднимите ресурс везде:

   ```bash
   drbdadm create-md arkvory   # только серверы с данными
   drbdadm up arkvory          # каждый сервер
   ```

   На свидетеле также выполните `systemctl enable drbd@arkvory.service`, чтобы tiebreaker поднимался после перезапуска.

   План позволяет вернувшейся копии ресинхронизироваться не медленнее 20 МБ/с даже под нагрузкой записи и не быстрее 1 ГБ/с. Задайте `c-min-rate` и `c-max-rate` в секции `disk` под пропускную способность канала репликации.

4. На первом сервере с данными сделайте его основным, создайте файловую систему и смонтируйте её. Для новых пустых дисков сначала пропустите начальную синхронизацию:

   ```bash
   drbdadm new-current-uuid --clear-bitmap arkvory/0
   drbdadm primary arkvory
   mkfs.xfs /dev/drbd0
   mkdir -p /opt/proanima-arkvory && mount /dev/drbd0 /opt/proanima-arkvory
   ```

5. Установите Arkvory на смонтированный том, положите на том файлы TLS и включите режим кластера:

   ```bash
   dpkg --configure proanima-arkvory
   install -d -m 0750 -o root -g arkvory /opt/proanima-arkvory/config/tls
   install -m 0644 tls.crt /opt/proanima-arkvory/config/tls/tls.crt
   install -m 0640 -g arkvory tls.key /opt/proanima-arkvory/config/tls/tls.key
   arkvory configure --root /opt/proanima-arkvory --tls-cert /opt/proanima-arkvory/config/tls/tls.crt --tls-key /opt/proanima-arkvory/config/tls/tls.key --listen-host 0.0.0.0
   arkvory configure --root /opt/proanima-arkvory --cluster ha-2
   ```

   `configure --cluster` проверяет, что каталог установки — смонтированное устройство DRBD, что этот сервер основной и что все копии полные. Команда запускает `arkvory-replica`, включает подтверждение записи только при двух полных копиях и отключает автозапуск служб Arkvory: дальше их запускает Pacemaker. Если шаг не удался, восстанавливается конфигурация отдельного сервера.

6. Остановите Arkvory на первом сервере и освободите том:

   ```bash
   systemctl stop arkvory-update.timer arkvory-backup arkvory-worker arkvory-api arkvory-replica arkvory-database
   umount /opt/proanima-arkvory && drbdadm secondary arkvory
   ```

7. На каждом другом сервере с данными по очереди возьмите том, подготовьте сервер и снова освободите том:

   ```bash
   drbdadm primary arkvory
   mkdir -p /opt/proanima-arkvory && mount /dev/drbd0 /opt/proanima-arkvory
   arkvory cluster-node --root /opt/proanima-arkvory --cluster-resource arkvory
   dpkg --configure proanima-arkvory
   systemctl stop arkvory-update.timer arkvory-backup arkvory-worker arkvory-api arkvory-replica arkvory-database
   umount /opt/proanima-arkvory && drbdadm secondary arkvory
   ```

   `cluster-node` создаёт служебные учётные записи с теми же идентификаторами пользователя и группы, что на первом сервере (файлы на томе принадлежат им), и устанавливает те же службы без автозапуска. Если учётная запись уже есть с другими идентификаторами, команда останавливается и говорит, какие идентификаторы задать.

8. Настройте кластер Corosync через `pcs` на серверах с данными (`pcs host auth`, `pcs cluster setup`, `pcs cluster start --all`). В Debian и Ubuntu сначала выполните `pcs cluster destroy` на каждом сервере с данными: пакеты устанавливают образец конфигурации Corosync, который `pcs` принимает за существующий кластер. Не выполняйте `pcs cluster enable`: изолированный сервер должен возвращаться в кластер, только когда его запускаете вы. Для `ha-2` также аутентифицируйте свидетеля и выполните на нём `pcs qdevice setup model net --enable --start`. В Debian и Ubuntu пакет уже настроил устройство кворума для своей служебной учётной записи: вместо этого выполните там `systemctl enable --now corosync-qnetd`.

9. Откройте `/root/arkvory-plan/pacemaker.sh`. Замените каждый `<agent parameters: …>` параметрами вашего устройства fencing: его адресом, логином, файлом пароля или ключом и розеткой или портом этого сервера. Затем выполните скрипт на одном сервере с данными:

   ```bash
   sh /root/arkvory-plan/pacemaker.sh
   ```

   Скрипт собирает всю конфигурацию в файле и применяет её разом: fencing, политику кворума, ресурс DRBD, группу Arkvory и её ограничения.

10. Проверьте кластер на активном сервере:

    ```bash
    arkvory cluster-check --root /opt/proanima-arkvory
    ```

    Команда проверяет кворум, что fencing включён, что у каждого сервера есть устройство fencing, настройки кворума и fencing в DRBD, что все копии полные и что Arkvory работает ровно на одном сервере. Если проверка не прошла, команда завершается с ошибкой.

11. Один раз докажите fencing: изолируйте каждый резервный сервер и дождитесь его возвращения (см. [Проверка fencing](#fence-test)).

Направьте клиентов и DNS-имя на виртуальный адрес.

## Повседневная работа {#operation}

Выполняйте эти команды от root на активном сервере, где смонтирован том.

| Команда                                                                   | Что делает                                                                                        |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `arkvory cluster-status --root <dir>`                                     | Профиль, роль этого сервера, полные и требуемые копии и решение оператора, если есть, — в JSON    |
| `arkvory cluster-check --root <dir>`                                      | Все проверки здорового кластера; завершается с ошибкой, если одна не прошла                       |
| `arkvory cluster-switchover --root <dir> --to <server>`                   | Плановый перенос Arkvory на другой сервер с данными; отказ, если не все копии полные              |
| `arkvory cluster-fence-test --root <dir> --node <standby>`                | Изолирует резервный сервер, чтобы доказать его устройство fencing; активный сервер не принимается |
| `arkvory cluster-single-copy --root <dir> --until <time> --reason <text>` | Разрешает запись в одну копию до срока; см. [Одна копия](#single-copy)                            |

`pcs status` показывает кластер так, как его видит Pacemaker.

### Плановое переключение {#switchover}

`cluster-switchover` просит Pacemaker перенести группу, ждёт до 5 минут, пока Arkvory заработает на целевом сервере, и затем снимает временное правило размещения. Соединения со старым сервером во время переноса рвутся, клиенты повторяют запросы. Обратно Arkvory сам не переезжает.

### Проверка fencing {#fence-test}

`cluster-fence-test` перезапускает резервный сервер через его устройство fencing. После перезапуска запустите на этом сервере кластер командой `pcs cluster start`. Службы кластера после перезапуска сами не стартуют (шаг 8 из [Сборки кластера](#build)), поэтому изолированный сервер без вас не вернётся.

### Обновления {#updates}

Установите новый пакет на каждый сервер с данными. На резервных серверах пакет только заменяет файлы программы, потому что релиз лежит на томе. На активном сервере пакет применяет релиз: Arkvory просит Pacemaker не трогать группу, останавливает службы, выполняет миграции, запускает службы, ждёт готовности и возвращает группу Pacemaker. Автоматические обновления на активном сервере работают так же.

Не запускайте и не останавливайте службы Arkvory через `systemctl` на сервере кластера: Pacemaker сочтёт это отказом. Для плановой остановки всей службы используйте `pcs resource disable arkvory` и `pcs resource enable arkvory`.

## Отказы {#failures}

| Что произошло                                                          | `ha-2`                                                                                                                | `ha-3`                                                                          |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Отказал резервный сервер                                               | Изолирован. Чтение продолжается, запись получает 503 `replication_degraded`                                           | Изолирован. Чтение и запись продолжаются                                        |
| Отказал активный сервер                                                | Изолирован, Arkvory запускается на другом сервере. Чтение возвращается, запись ждёт вторую копию                      | Изолирован, Arkvory запускается на другом сервере. Чтение и запись возвращаются |
| Разрыв сети между серверами с данными                                  | Свидетель отдаёт кворум одной стороне, другая изолируется. Двух писателей не бывает                                   | Сторона большинства продолжает, другой сервер изолируется                       |
| Отказали два участника из трёх (в ha-2 — сервер с данными и свидетель) | У последнего сервера нет кворума: Arkvory останавливается. Писателя без кворума не бывает. Верните серверы (см. ниже) | Так же для двух серверов с данными                                              |
| Fencing не работает                                                    | Переключения нет. Arkvory остаётся остановленным, пока fencing не пройдёт                                             | Так же                                                                          |

Чтобы вернуть изолированный сервер:

1. Устраните причину и включите сервер.
2. Выполните на нём `pcs cluster start`.
3. Том ресинхронизирует изменённые блоки. Запись возобновится сама, когда снова будут все нужные полные копии; ход показывает `arkvory cluster-status`.

После потери кворума запустите кластер на каждом вернувшемся сервере. Pacemaker снова запустит Arkvory на сервере с самой свежей копией. Сервер, потерявший кворум последним, по пути может быть изолирован ещё раз, потому что не смог остановиться чисто: после его перезапуска снова запустите на нём кластер.

Если fencing не сработал и вы его починили, очистите неудачные попытки на работающем сервере, чтобы Pacemaker попробовал снова: `pcs stonith history cleanup <server>` и `pcs resource cleanup`.

### Одна копия {#single-copy}

Если сервер с данными отсутствует долго (например, меняют диск) и остановка записи обходится дороже риска, оператор может на ограниченное время разрешить запись в одну копию:

```bash
arkvory cluster-single-copy --root /opt/proanima-arkvory --until 2026-10-12T18:00:00Z --reason "замена диска на node-b"
```

- Срок — не дальше 7 дней. Команда работает, только пока копий не хватает.
- Пока решение действует, потеря активного сервера теряет записи, подтверждённые после решения.
- Решение видно в баннере консоли, в метрике `arkvory_replication_required_copies` и в оповещении `ArkvorySingleCopyWrites`.
- Оно заканчивается в срок, по `--off` или само, как только снова все копии полные. Следующая потеря снова останавливает запись.

## Мониторинг {#monitoring}

`GET /health/ready` на активном сервере остаётся 200, пока запись остановлена, чтобы мониторинг не переносил здоровый сервер. Поле `writable` равно `false`, а поле `replication` показывает `copies`, `required` и `singleCopyUntil`; `replication` равно `null`, если копии не удаётся прочитать. У отдельного сервера поля `replication` нет.

| Метрика                                    | Что значит                                                      |
| ------------------------------------------ | --------------------------------------------------------------- |
| `arkvory_replication_copies`               | Полные копии при последней проверке                             |
| `arkvory_replication_required_copies`      | Сколько копий нужно записи: 2, или 1 при решении об одной копии |
| `arkvory_replication_writes_refused_total` | Записи, получившие 503 `replication_degraded`                   |
| `arkvory_replication_check_failures_total` | Неудачные чтения состояния копий                                |

Правила оповещений в `deploy/monitoring/arkvory-alerts.yml` включают `ArkvoryReplicationDegraded`, `ArkvorySingleCopyWrites` и `ArkvoryReplicationCheckFailing`. Следите и за самим кластером: запускайте `arkvory cluster-check` по расписанию и оповещайте по коду выхода или используйте мониторинг вашей установки Pacemaker. См. [Мониторинг](./monitoring).

## Резервные копии {#backups}

Агент резервных копий работает только на активном сервере, в составе группы. Держите хранилище копий вне тома кластера, например на NAS. См. [Резервные копии](./backups).
