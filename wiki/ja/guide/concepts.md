# 基本概念

他のページで使う用語を説明します。各節は短い説明と、詳しい解説へのリンクで構成されています。1 行の定義は[用語集](../reference/glossary)を参照してください。

## インストールとサービス {#installation}

標準的なインストールは 1 台のサーバーで構成されます。1 つの PostgreSQL データベースとともに、3 つの Arkvory サービスを実行します。

| 構成要素                 | 役割                                                                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| API                      | HTTP サーバー。HTTP API、[Web コンソール](./console)、コンテナ、Git LFS、npm のレジストリを提供し、保持処理と物理クリーンアップも実行します。 |
| ワーカー                 | 大容量アップロードの完了処理とミラー同期を行うバックグラウンドジョブ。                                                                        |
| バックアップエージェント | スケジュールに従って保管庫にバックアップします。                                                                                              |
| PostgreSQL               | アーティファクト、パッケージ、リビジョン、アカウント、キー、ジョブのカタログ。                                                                |

ファイルの内容はデータベースではなく、サーバーのローカルディレクトリに保存されます。すべての構成要素は**インストールルート**（Windows では `C:\ProgramData\ProAnima\Arkvory`、Linux では `/opt/proanima-arkvory`）に配置されます。サービスはユーザーのサインインなしで起動し、クラッシュやハングの後に再起動します（[自己修復](../operate/self-healing)）。

単一サーバーのインストールは高可用構成ではありません。サーバーが停止すると、クライアントは待機してから転送を再開します。[インストール方式の選択](../install/index)を参照してください。Linux では、2 台または 3 台のサーバーで[高可用性クラスター](../operate/cluster)を構成できます。

## リポジトリ {#repositories}

**リポジトリ**は、名前の付いたコンテンツ用の領域です。独自のアクセス規則、ストレージポリシー（クォータと保持）、必要に応じてミラー元を持ちます。リポジトリ名は 1～64 文字で、英小文字、数字、`-`、`_` を使用し、英字または数字で始めます。

リポジトリを作成する専用コマンドはありません。グループにその名前へのアクセスを付与するか、サービスアカウントのポリシーに名前を指定すると、リポジトリが存在するようになります。新規インストールには最初のリポジトリ用の `releases` があります。[リポジトリ](../use/repositories)を参照してください。

## アーティファクト {#artifacts}

**アーティファクト**は、保存された 1 つのファイルです。**不変**であり、バイト列が変化することはありません。UUID、名前（最大 240 文字、`/` と `\` は使用不可）、サイズ、SHA-256 チェックサムを持ちます。新しい内容は新しいアーティファクトとなり、古いものを置き換えません。

サーバーが、バイト列が申告されたサイズと SHA-256 に一致することを確認してから、アーティファクトが表示されます。ダウンロードでは同じバイト列と、チェックサムを使った強い `ETag` が返されます。Arkvory の他の要素はすべてアーティファクトに基づきます。パッケージのバージョン、パスのリビジョン、コンテナレイヤー、Git LFS オブジェクトもアーティファクトです。

## アップロード {#uploads}

**アップロード**は、将来作成されるアーティファクトを予約します。ファイル名、サイズ、SHA-256、およびリクエストを安全に繰り返すための `Idempotency-Key` を指定して、**アップロードセッション**を作成します。その後、バイト列を送信します。

- 小～中容量のファイルは 1 回のリクエストで送信します。
- 大容量ファイルは**パート**に分けます。パートサイズはサーバーが選択します。最小は 8 MiB で、非常に大きいファイルでは、パート数が 10,000 を超えないよう倍増させます。1 パートは最大 1 GiB です。各パートに独自の SHA-256 があり、同じパートを再送しても問題ありません。

最後にアップロードを**完了**します。サーバーはファイル全体を確認して公開します。大容量ファイルでは、クライアントが追跡する**完了ジョブ**をワーカーが実行します。SDK とコマンドラインクライアントは 16 GiB 以上でこの方式を選択します。セッションの有効期間は 7 日です。中断したアップロードは、サーバーにあるパートを引き継いで再開できます。管理者が `ARKVORY_MAX_OBJECT_BYTES` で下げない限り、オブジェクトの最大サイズは 10,000 GiB です。

[コマンドラインクライアント](../protocols/cli)と [SDK](../protocols/sdk)がこれらの処理を代行します。[転送](../use/transfers)と[アップロードのリファレンス](../api/reference/uploads)を参照してください。

## パッケージ {#packages}

**パッケージ**は、Arkvory に登録された UPack アーカイブです。識別には**グループ**、**名前**、**SemVer バージョン**を使用します。例は `acme` / `game-server` / `1.4.2` です。グループも識別情報の一部なので、異なるグループで同じ名前を持つパッケージは別のものです。公開したバージョンは変化せず、同じバージョンを異なる内容で公開しようとすると拒否されます。

デプロイエージェントは、正確なバージョン、`^1.4` などの**バージョン範囲**、または**ステージ**上の最新バージョンを指定して取得します。プレリリース版は明示的に指定した場合だけ対象になります。[パッケージ](../use/packages)を参照してください。

## パス指定ファイル {#files-by-path}

**パス指定ファイル**は、`builds/game/1.4/Setup.exe` などのアドレスでアーティファクトを参照します。そのパスに新しいバイト列を保存すると、新しい**リビジョン**（1、2、3…）が作成されます。以前のリビジョンは**履歴**に残り、**復元**できます。復元は、古い内容を持つ新しいリビジョンを追加します。同じバイト列を再度保存しても何も追加されません。

パスは最大 1,024 文字で、区切りに `/` を使います。空のセグメント、`.`、`..`、および `:` は使えません。変更時には期待するリビジョンを指定し、先に別の変更があればサーバーは `409` を返します。まだ存在しないパスには `0` を指定します。[ファイルとパス](../use/files)と[Raw ファイル](../protocols/raw-files)を参照してください。

## ラベル、メタデータ、コレクション、添付ファイル {#annotations}

バイト列を変更せずに、アーティファクトの説明を追加できます。

| 項目         | 規則                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| ラベル       | `nightly`、`tested` などの短いタグを最大 32 個。                                                                                         |
| メタデータ   | テキストフィールドを最大 32 個。キーは最大 64 文字、値は最大 1,024 文字。                                                                |
| コレクション | アーティファクトをまとめる、名前の付いた集合。                                                                                           |
| 添付ファイル | ビルドから同じリポジトリ内の他のアーティファクトへのリンクを最大 32 個。マニフェスト、SBOM、署名、レポートなどのファイルを関連付けます。 |

ラベル、メタデータ、コレクションは、リビジョン管理された 1 つの集合として変更されます。添付ファイルには独自のリビジョンと履歴があります。

## ステージとプロモーション {#stages-and-promotion}

**ステージ**は、`qa`、`release`、`prod` など、ビルドに付ける管理対象の印です。名前には英小文字、数字、`.`、`_`、`-` を使い、最大 32 文字です。アーティファクトには最大 16 個のステージを付けられます。変更には専用権限 `artifact.promote` が必要で、操作者、時刻、コメントが記録されます。

**プロモーション**は、バイト列を再送せずに別のリポジトリへビルドを公開します。`copy` は元を保持し、`move` は元のリポジトリからもビルドを削除します。繰り返すと既存のコピーが返されます。**解決（resolve）**は、ステージとバージョン範囲が指すビルドを特定します。[プロモーション](../use/promotion)を参照してください。

## アカウント、グループ、権限 {#access}

人は**アカウント**を使います。アカウント名は 3～64 文字、パスワードは 12～128 文字です。**管理者**アカウントがアカウントとグループを管理します。アカウントは**グループ**に属し、グループにリポジトリの `read` または `write`（読み取りと書き込み）アクセスを付与します。権限はリクエストごとに再計算されるため、変更は直ちに反映されます。

自動化には**サービスアカウント**を使用します。その**ポリシー**は、リポジトリごとに `upload.create`、`content.read` などの正確な**操作**を列挙し、キーはその範囲を狭めることしかできません。サーバーがすべての操作を確認します。コンソールのボタンを隠すだけでは保護になりません。[アカウントとアクセス](../use/accounts)と[認証](../api/authentication)を参照してください。

## キーとトークン {#keys-and-tokens}

すべてのリクエストに認証情報が必要です。ユーザーが作成する 4 種類と、組み込みの 1 種類があります。

| 認証情報                   | 用途                                            | 有効期間                    |
| -------------------------- | ----------------------------------------------- | --------------------------- |
| コンソールの**セッション** | 名前とパスワードでサインインした人              | 12 時間                     |
| **個人用アクセストークン** | 個人のスクリプトやツール                        | 既定 90 日、最大 365 日     |
| **サービスキー**           | CI/CD とデプロイエージェント                    | 既定 90 日、最大 365 日     |
| **ダウンロードリンク**     | キーを持たない人に 1 つのアーティファクトを渡す | 60 秒～24 時間、既定 1 時間 |
| **回復キー**               | インストール自体                                | 無期限                      |

サービスキーは 1 度だけ発行・表示され、**有効化**して初めて利用できます。**ローテーション**（新しいキーを発行してから古いものを廃止）と、恒久的な**取り消し**ができます。[認証](../api/authentication)を参照してください。

## 所有者と回復キー {#owner-and-recovery-key}

**所有者**は最初のアカウントです。管理者であり、`releases` に `write` アクセスを持つ `arkvory-owners` グループに属します。Windows のグラフィカルインストーラー `Arkvory-Setup-x64.exe` が作成します。Windows PowerShell スクリプト、Linux、Docker では、回復キーを使ってコンソールで作成します。

**回復キー**は、インストーラーがインストールルートの `config/bootstrap-token.txt` に保存する秘密情報です。最初の所有者やアカウントの作成、サービスアカウントとその委任の管理、バックアップの実行、更新の要求に使えます。インストールツールはサーバー上でこれを読み取ります。CI や日常作業用ではありません。サーバーに保管し、コピーしないでください。[インストール方式の選択](../install/index#recovery-key)と[セキュリティ](../operate/security)を参照してください。

## 保持、クォータ、クリーンアップ {#retention}

**ストレージポリシー**はリポジトリごとに設定します。パッケージごと（またはパッケージとチャネルごと）に最新 N ビルドを保持し、ラベルやステージを削除から保護し、削除までの最低経過時間を設け、警告・重大しきい値を持つ**クォータ**を指定できます。管理者が有効にするまでは無効です。アーティファクトはまず論理削除されます。バイト列は**猶予期間**（既定 24 時間）中ディスクに残り、その後バックグラウンドの**物理クリーンアップ**が小さなバッチで空き容量を回復します。サーバーを停止する必要はありません。

サーバーはアップロードが使用できない空きディスクの予備領域も確保します。既定は 1 GiB です。[ストレージ](../operate/storage)を参照してください。

## バックアップ {#backups}

**バックアップエージェント**は、データベースと公開済みコンテンツ全体を、別のディスクまたはネットワーク共有上のフォルダーである**保管庫**にコピーします。1 回分の完全なコピーが**復元ポイント**です。エージェントは各ポイントを検証し、保持規則（既定は日次 7、週次 4、月次 6）を適用します。ポイントを**固定**すると保持処理による削除から保護できます。日次スケジュールは、管理者が [[ui:backupPlan]] で有効にするまで無効です。

復元はサーバー上のコマンドで行います。空のデータベースと空のストレージディレクトリへ書き込みます。[バックアップ](../operate/backups)を参照してください。

## ミラーと読み取りゲートウェイ {#mirrors-and-gateways}

**ミラー**は、別のインストールが最初のインストール、つまり**ソース**を追跡して維持する、読み取り専用のリポジトリコピーです。変更を拒否し、ダウンロードを提供します。ソースが失われた場合、運用担当者がミラーを切り離すと通常のリポジトリになります。切り替えは手動であり、自動フェイルオーバーではありません。[ミラー](../operate/mirrors)を参照してください。

**読み取りゲートウェイ**は、同じストレージを使う追加の API プロセスで、`GET` と `HEAD` だけを処理します。writer とゲートウェイは 1 つのダウンロード帯域予算を共有します。[読み取りゲートウェイ](../operate/read-gateways)を参照してください。
