# クライアントとプロトコル

Arkvoryのストレージとアクセスモデルは1つですが、そこに到達する方法は複数あります。それぞれの方法は、ツールがすでに対応しているクライアントまたはプロトコルです。どの方法でも、データはArkvoryのアーティファクトとして保存されます。そのため、どの方法を使っても、同じ権限、クォータ、SHA-256検証、保持ルール、バックアップ、ミラーが適用されます。

このページでは、Arkvoryと通信するすべての方法について、それぞれの用途と、受け付ける認証情報を説明します。作業に適したツールを選ぶときに使ってください。

## 概要 {#overview}

| 方法                        | アドレス                                       | 用途                                                                                               | 認証情報                                                                           |
| --------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Webコンソール               | `https://arkvory.example/console/`             | ブラウザーでのリポジトリの閲覧、アップロードとダウンロード、ユーザー、キー、バックアップの管理     | ユーザー名とパスワードによるサインイン、またはサービスキー                         |
| `arkvoryctl`コマンドライン  | `/api/v1`                                      | CIスクリプト、再開可能なアップロードとダウンロード、パス指定ファイル、プロモーション、バックアップ | ファイルまたは環境変数から読み込むキー（Bearerとして送信）                         |
| TypeScript SDK              | `/api/v1`                                      | TypeScriptまたはJavaScriptで作る独自のツール（Node.jsまたはブラウザー）                            | コールバックから取得するキー（Bearerとして送信）                                   |
| REST API                    | `/api/v1/...`                                  | 任意の言語での連携                                                                                 | `Authorization: Bearer <key>`のみ                                                  |
| コンテナーレジストリ（OCI） | `/v2/`                                         | Docker、Podman、Buildx、containerd、Helmチャート、ORASアーティファクト                             | キーをパスワードにしたBasic（`docker login`）、またはBearer                        |
| Git LFS                     | `/lfs/<repository>`                            | gitリポジトリの大容量ファイル、UnityとUnreal向けのファイルロック                                   | キーをパスワードにしたBasic（gitの認証情報ヘルパー）、またはBearer                 |
| npmレジストリ               | `/npm/<repository>/`                           | Unity Package Managerのスコープ付きレジストリ、`npm publish`と`npm install`                        | Bearer（`.npmrc`の`_authToken`、`.upmconfig.toml`の`token`）、またはBasicの`_auth` |
| パス指定のRawファイル       | `/api/v1/repositories/<repository>/raw/<path>` | `curl -T`またはPowerShellによる1回のリクエスト                                                     | `Authorization: Bearer <key>`のみ                                                  |

`/v2`、`/lfs`、`/npm`以下のルートは、それぞれのプロトコルの仕様に従います。これらは`/api/v1`のOpenAPIドキュメントには含まれず、エラーはそれぞれのクライアントが期待する形式で返されます。

## 認証情報 {#credentials}

公開されているヘルスチェックを除き、すべてのリクエストに認証情報が必要です。Arkvoryは次の種類を受け付けます。

| 種類                   | 形式               | 入手元                                                                                                                       | 主な用途                                         |
| ---------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 個人用アクセストークン | `pat_...`          | ユーザーがコンソールで作成します。スコープは`read`または`read-write`です。有効期限があります（既定は90日、最大365日）。      | 開発者：ワークステーションでのUnity、git、Docker |
| サービスキー           | `arkvory_...`      | 管理者がサービスアカウント向けに発行します。リポジトリごとに、許可する操作を正確に指定します                                 | CI/CD、デプロイエージェント、ビルドサーバー      |
| ファイルキー           | 任意のシークレット | サーバーのキーファイル（`ARKVORY_KEYS_FILE`）。リポジトリごとに`read`または`write`を指定します。所有者のキーは管理も行えます | インストールの所有者、従来の連携                 |
| セッション             | `dps_...`          | コンソールへのサインイン。12時間有効です                                                                                     | コンソールでの対話的な作業                       |
| ダウンロードリンク     | `?token=`付きのURL | 1つのアーティファクト向けに作成します。有効期間は60秒〜24時間です                                                            | キーを持たない相手に1つのファイルを渡す          |

プロトコルによって違うのは、キーの送り方だけです。

- `/api/v1`、CLI、SDK、Rawファイルは、`Authorization: Bearer <key>`を使います。
- `/v2`、`/lfs`、`/npm`は、HTTP Basicも受け付けます。ユーザー名は検証されません。パスワードがArkvoryのキーです。`docker login`、gitの認証情報ヘルパー、npmの`_auth`は、この方法で認証情報を送信します。
- 読み取り専用の個人用トークンが、データを変更することはありません。ただし、Git LFSのバッチリクエストはダウンロードの場合も`POST`であるため、Git LFSオブジェクトのダウンロードはできます。

トークンとキーの作成方法は、[アカウントとキー](../use/accounts)を参照してください。ヘッダーの詳細は、[認証](../api/authentication)を参照してください。

## どれを使えばよいか {#which-one-should-i-use}

| タスク                                                                             | 推奨される方法                                                       |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| CIからビルドアーティファクトをアップロードし、ネットワーク障害の後に再開する       | [`arkvoryctl upload`](./cli)または[`arkvoryctl put`](./cli)          |
| CIからUPackパッケージを公開する                                                    | [`arkvoryctl packages publish`](./cli)                               |
| 「最新の1.4リリース」をサーバーにデプロイする                                      | [`arkvoryctl packages download --range ^1.4 --stage release`](./cli) |
| 何もインストールせずに、シェルスクリプトから小〜中サイズのファイルをパス指定で置く | `curl -T`またはPowerShellによる[Rawファイル](./raw-files)            |
| コンテナーイメージやHelmチャートを保存する                                         | [コンテナーイメージ](./containers)                                   |
| ゲームのテクスチャ、モデル、レベルをgitホストの外に保管する                        | [Git LFS](./git-lfs)                                                 |
| プロジェクト間でUnityパッケージを共有する                                          | [Unityとnpmのパッケージ](./unity-npm)                                |
| 独自のツールやWebインターフェイスを作る                                            | [TypeScript SDK](./sdk)                                              |
| Python、Go、C#などの言語から連携する                                               | [REST API](../api/index)                                             |
| 全体を確認する、ユーザー、キー、バックアップを管理する                             | [Webコンソール](../guide/console)                                    |

選ぶときの目安は次のとおりです。

- **大容量ファイル（数ギガバイト以上）**：`arkvoryctl`またはSDKを使います。パートに分けてアップロードし、中断後に続行します。単一の`PUT`リクエスト（Rawファイル、Git LFSオブジェクト、npm publish、Dockerのレイヤー）は、失敗すると0バイト目からやり直しになります。
- **ツールがすでにプロトコルに対応している場合**：そのプロトコルを使います。Docker、git、Unityに追加のソフトウェアは不要です。
- **機械が読み取るだけの場合**：読み取り専用のトークン、または読み取り操作だけを持つサービスキーを与えます。

## 共通のルール {#shared-rules}

**HTTPS**：すべてのクライアントでHTTPSを使ってください。CLIとSDKは、ループバック（`localhost`、`127.0.0.1`、`[::1]`）を除き、平文のHTTPを拒否します。Dockerには、信頼された証明書が必要です。gitは、リクエストのたびにキーを送信します。[HTTPS](../install/https)を参照してください。

**同じストレージ**：イメージのレイヤー、Git LFSオブジェクト、npmのtarball、Rawファイルは、すべてアーティファクトです。リポジトリのクォータとインストールの容量に計上され、保存時にSHA-256で検証され、バックアップにも含まれます。

**読み取りゲートウェイとミラー**：読み取りゲートウェイが受け付けるのは、`GET`と`HEAD`だけです。ミラーは、別のインストールにあるリポジトリの読み取り専用コピーです。

| 方法                 | 読み取りゲートウェイでは                 | ミラーでは                                             |
| -------------------- | ---------------------------------------- | ------------------------------------------------------ |
| `/api/v1`、CLI、SDK  | 読み取りのみ                             | 読み取り。変更は拒否されます（`409 mirror_read_only`） |
| コンテナーレジストリ | プル                                     | プル。プッシュは拒否されます                           |
| Git LFS              | 非対応（バッチリクエストが`POST`のため） | クローンとフェッチ。プッシュとロックは拒否されます     |
| npmレジストリ        | インストールと検索                       | インストールと検索。公開は拒否されます                 |
| Rawファイル          | `GET`と`HEAD`                            | `GET`と`HEAD`                                          |

[読み取りゲートウェイ](../operate/read-gateways)と[ミラー](../operate/mirrors)を参照してください。
