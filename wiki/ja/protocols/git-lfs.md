# Git LFS

すべてのArkvoryリポジトリはGit LFSサーバーとして使えます。gitリポジトリ自体は、GitHub、GitLab、Giteaなど、元の場所に置いたままです。Arkvoryに保存するのは、Git LFSが追跡する大きなファイルとファイルのロックだけです。LFSオブジェクトは通常のアーティファクトなので、リポジトリの権限、クォータ、SHA-256の確認、バックアップ、ミラーが適用されます。

## gitリポジトリを設定する {#set-up}

HTTPSのサーバーアドレス（[HTTPS](../install/https)を参照）、`games`などのArkvoryリポジトリ、キー（[アカウントとキー](../use/accounts)を参照）が必要です。

1. リポジトリを使うすべてのマシンにGit LFSをインストールし、ユーザーごとに1回`git lfs install`を実行します。
2. gitリポジトリのルートに`.lfsconfig`ファイルを作成してコミットします。これにより、チーム全体がArkvoryを使います。

```ini
[lfs]
	url = https://arkvory.example/lfs/games
```

3. ファイルのパターンを追跡対象にします。`.gitattributes`が書き込まれるので、これもコミットします。

```bash
git lfs track "*.psd" "*.fbx" "*.wav" "*.uasset" "*.umap"
git add .gitattributes .lfsconfig
```

4. 通常どおりコミットしてプッシュします。最初のリクエストで認証情報を求められます。[サインイン](#sign-in)を参照してください。

リポジトリのLFSアドレスは、常に`https://<host>/lfs/<repository>`です。

すでに別のサーバーのLFSにあるファイルを移すには、まず古いサーバーからすべてのオブジェクトをダウンロードし、次に`lfs.url`を切り替えてアップロードします。

```bash
git lfs fetch --all origin
git config lfs.url https://arkvory.example/lfs/games
git lfs push --all origin
```

## サインイン {#sign-in}

ArkvoryのキーをHTTP Basic認証のパスワードとして渡します。ユーザー名は確認しないため、任意の名前を使えます。Bearerトークンとしてキーを渡すこともできます。

サーバーが初めて`401`を返したとき、Gitは認証情報ヘルパーを通じてユーザー名とパスワードを求めます。ヘルパーがそれらを保存します。WindowsとmacOSではGit Credential Manager、Linuxでは`credential.helper store`または`cache`を使います。

| 利用者             | キー                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 開発者             | 個人用アクセストークン。プッシュとロックにはスコープ`read-write`、クローンとプルだけならスコープ`read`を使います |
| ビルドサーバー、CI | [権限](#permissions)に記載したアクションを持つサービスキー                                                       |

Gitは認証情報をホストごとに保持します。Arkvoryのキーが、GitHubなど、gitリポジトリのホストの認証情報を置き換えることはありません。

認証情報ヘルパーのないCIランナーでは、チェックアウトのローカル設定にキーを入れます。キーはそのワークスペースの`.git/config`だけに保存され、`.lfsconfig`には入りません。

```bash
git config lfs.url "https://ci:${ARKVORY_KEY}@arkvory.example/lfs/games"
```

キーをコミットしたり、ログに出力したりしないでください。ジョブの後にワークスペースを削除してください。

## 日常の作業 {#daily-work}

Git LFSは、他のLFSサーバーと同じように動作します。使用するコマンドは次のとおりです。

| コマンド                                | 動作                                                                                            |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `git push`                              | コミットをプッシュする前に、新しいLFSオブジェクトをArkvoryにアップロードします                  |
| `git clone`、`git pull`、`git checkout` | 作業ツリーに必要なオブジェクトをダウンロードします                                              |
| `git lfs fetch --all`                   | すべてのブランチのオブジェクトをダウンロードします                                              |
| `git lfs ls-files`                      | 追跡中のファイルと短いIDを一覧表示します                                                        |
| `git lfs push --all origin`             | ローカルのすべてのオブジェクトを再度アップロードします。Arkvoryにあるオブジェクトは送信しません |

IDとサイズが同じオブジェクトをArkvoryがすでに持っている場合、再送信しません。中断後にプッシュを繰り返すと、不足しているものだけを送信します。

## ファイルをロックする {#locks}

バイナリアセットはマージできません。ロックは、ある人がファイルを編集中であることをチームに伝えます。ロックはブランチではなくArkvoryリポジトリに属します。

```bash
git lfs lock Content/Maps/Level01.umap
git lfs locks
git lfs unlock Content/Maps/Level01.umap
```

- 同じパスに2回目の`git lfs lock`を実行すると、「already created lock」で失敗し、所有者を表示します。
- 所有者は、ロック作成時のユーザー名またはサービスアカウント名で表示されます。ファイルキーの場合はIDを表示します。
- ロックを解除できるのは所有者だけです。他の人のロックに`git lfs unlock --force`を使うには、そのリポジトリでアクション`artifact.delete`を持つサービスキーが必要です。個人用トークンではロックを強制解除できません。
- ロックのパスはgitリポジトリ内のパスです。最大1024文字で、フォルダーの区切りには`/`を使います。空のセグメント、`.`、`..`、バックスラッシュ、コロンは使えません。
- `git lfs locks`は1ページに100件のロックを表示します。

プッシュ前のチェックを有効にすると、他の人がロックしたファイルへの変更をgitがプッシュしなくなります。設定はサーバーアドレスごとです。

```bash
git config lfs.https://arkvory.example/lfs/games.locksverify true
```

編集前にロックするファイル形式を指定します。Git LFSは、ロックするまでそれらを読み取り専用にします。

```bash
git lfs track --lockable "*.umap" "*.uasset"
```

プッシュ時のロックチェックには書き込みアクセスが必要なため、読み取り専用トークンでは使えません。ロックの一覧には、読み取りアクセスで許可される`git lfs locks`を使ってください。

## UnityとUnrealでの使い方 {#game-engines}

- Unity：テキストアセット（`.unity`、`.prefab`、`.asset`）はgitに保持し、アセットのシリアル化をForce Textに設定します。大きなバイナリはLFSで追跡します。例：`*.png`、`*.psd`、`*.fbx`、`*.wav`、`*.mp4`、`*.exr`。LFSで追跡したテキストファイルも受け付けます。
- Unreal Engine：`*.uasset`、`*.umap`、大きなソースファイルを追跡し、`*.uasset`と`*.umap`をロック可能に指定します。
- LFSのロックコマンドを呼び出すエディター連携は、Git LFSの標準ファイルロックプロトコルを使います。Arkvoryは、`git`と`git-lfs`のコマンドラインクライアントで検証しています。
- 数十ギガバイトに及ぶ、頻繁に変わるビルド出力をLFSに入れないでください。アーティファクトまたは[Rawファイル](./raw-files)として、[`arkvoryctl`](./cli)でアップロードします。LFSオブジェクトは保持ポリシーで削除されないため、永久に残ります。
- Unityプロジェクト間で共有する、大きな再利用可能なコードやツールには、[Unityパッケージ](./unity-npm)が適しています。

## 保存されるもの {#what-is-stored}

- LFSオブジェクトは、Arkvoryリポジトリ内のアーティファクトです。名前と識別子は内容のSHA-256（LFSの`oid`）で、ラベル`lfs`が付きます。コンソールの[[ui:catalog]]で確認できます。
- Arkvoryはオブジェクトの受信中にサイズとSHA-256を検証します。`oid`と一致しなければ、アップロードは`422`で失敗し、何も保存しません。
- オブジェクトはリポジトリに属します。2つのArkvoryリポジトリは、同じファイルでもそれぞれのコピーを保持します。
- サーバーは、どのコミットがオブジェクトをまだ必要としているかを把握できないため、保持ポリシーはLFSオブジェクトを削除しません。LFSオブジェクトを削除するコマンドはありません。アセットの全履歴を収容できるようにリポジトリのクォータを計画してください。
- ロックはデータベースの行です。バックアップに含まれます。

## 権限 {#permissions}

個人用トークンとファイルキーには、リポジトリへの読み取りまたは書き込みアクセスが付与されます。サービスキーには、個別のアクションが付与されます。

| 操作                                     | サービスキーのアクション | 個人用トークンまたはファイルキー                 |
| ---------------------------------------- | ------------------------ | ------------------------------------------------ |
| ダウンロード（`clone`、`fetch`、`pull`） | `content.read`           | 読み取りアクセス                                 |
| アップロード（`push`）                   | `upload.create`          | 書き込みアクセス、トークンのスコープ`read-write` |
| ロックの一覧                             | `artifact.list`          | 読み取りアクセス                                 |
| 自分のロックの作成、検証、解除           | `upload.create`          | 書き込みアクセス、トークンのスコープ`read-write` |
| 他の人のロックの解除（`--force`）        | `artifact.delete`        | 不可                                             |

プッシュとプルを行うCIジョブには、`content.read`、`upload.create`、`artifact.list`が必要です。プッシュだけが許可されたキーでも、オブジェクトが存在することは分かるため、二重にアップロードしません。

ダウンロード一覧のリクエストは`POST`ですが、読み取り専用の個人用トークンでもクローンとプルができます。プッシュやロックはできません。ミラーと読み取りゲートウェイについては、[ミラーと読み取りゲートウェイ](#mirrors-and-read-gateways)を参照してください。

## 転送の仕組み {#how-it-works}

日常の作業でこれらの詳細を知る必要はありません。プロキシやファイアウォールをデバッグする際に役立ちます。

1. Git LFSは、操作（`download`または`upload`）とオブジェクト一覧を含む`POST /lfs/<repository>/objects/batch`を1件送信します。1リクエストあたり最大1000オブジェクトです。Git LFSは既定で最大100個を送ります。
2. Arkvoryは、転送が必要な各オブジェクトについて、1時間有効なリンクを返します。アップロードでは、すでに保持しているオブジェクトを省きます。
3. Git LFSは、`/lfs/<repository>/objects/<oid>`に対して、各オブジェクトを`PUT`で送信するか、`GET`でダウンロードします。リクエストには、バッチリクエストと同じキーを付けます。
4. `PUT`には`Content-Length`ヘッダーが必要です。チャンク転送によるアップロードは`422`で拒否します。

対応するもの：

| 項目                 | 値                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 転送アダプター       | `basic`のみ                                                                                                            |
| ハッシュアルゴリズム | `sha256`のみ。別のアルゴリズムを要求するクライアントには`409`を返します                                                |
| 認証                 | Basic（キーをパスワードに指定）またはBearer                                                                            |
| ダウンロード         | `Range`リクエストを伴う`GET`と`HEAD`                                                                                   |
| メディアタイプ       | JSONリクエストは`application/vnd.git-lfs+json`。オブジェクトのボディは、任意のメディアタイプをバイト列として保存します |

エラーは、`message`と`request_id`を含むJSON文書です。管理者に支援を求める際は、`request_id`を伝えてください。

リンクは、クライアントがサーバーへの接続に使ったアドレスを指します。リバースプロキシでHTTPSを終端する場合は、インストールのnginxの例のように、`Host`ヘッダーを渡し、`X-Forwarded-Proto: https`を送信する必要があります。これにより、リンクが`https`を使います。Arkvoryは、リンクが`https`であるか、ローカルコンピューターを指す場合にのみ、リンクにキーを含めます。別のホストへの平文HTTPでは、gitがオブジェクトとともにキーを送信できず、転送は失敗します。

## 大きなファイルと再開 {#large-files}

- Git LFSは、各オブジェクトを1つの`PUT`リクエストで送信します。失敗すると、最初のバイトからやり直します。オブジェクトの途中から再開する`tus`アダプターには対応していません。
- アップロードリクエストは30分以内に完了する必要があり、30秒を超えて停止できません（`ARKVORY_UPLOAD_DEADLINE_MS`、`ARKVORY_UPLOAD_IDLE_TIMEOUT_MS`）。何ギガバイトもあるファイルには、高速で安定したネットワークが必要です。さらに大きいファイルには、パートに分けてアップロードする[`arkvoryctl`](./cli)を使ってください。
- ダウンロードは`Range`リクエストを受け付けます。
- オブジェクトは、インストールの最大オブジェクトサイズまで対応します（`ARKVORY_MAX_OBJECT_BYTES`、既定で約10 TiB）。それを超えるオブジェクトは、バッチ応答で`422`により拒否します。

既定では、サーバーは同時に8件、キーごとに4件のアップロードを実行します（`ARKVORY_MAX_UPLOADS`、`ARKVORY_MAX_UPLOADS_PER_PRINCIPAL`）。Git LFSは既定で8個のオブジェクトを同時に送信します。他のアップロードは空き枠を待ち、20秒後（`ARKVORY_TRANSFER_QUEUE_TIMEOUT_MS`）に`503`で断念します。Git LFSは失敗したオブジェクトを数回再試行しますが、大きなファイルのプッシュは、並列転送数を減らすとより確実です。

```bash
git config lfs.concurrenttransfers 1
```

管理者に制限の引き上げを依頼することもできます。制限は[環境変数](../reference/environment#transfers-and-bandwidth)に記載しています。

## ミラーと読み取りゲートウェイ {#mirrors-and-read-gateways}

| 接続先                                           | クローンとフェッチ                                                                   | プッシュとロック                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| メインサーバー                                   | 可                                                                                   | 可                                                                      |
| [ミラー](../operate/mirrors)                     | 可。ミラーはミラー元のオブジェクトを持つので、`lfs.url`をミラーに向けてください      | 拒否（`409`、理由`mirror_read_only`）。ロックはミラーにコピーされません |
| [読み取りゲートウェイ](../operate/read-gateways) | 不可。ダウンロード一覧は`POST`リクエストであり、読み取りゲートウェイは受け付けません | 不可                                                                    |

`lfs.url`は、常にメインサーバーに向けるか、読み取り専用のマシンではミラーに向けてください。

## トラブルシューティング {#troubleshooting}

| メッセージまたは症状                                          | 原因                                                                             | 対処                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `401`または認証エラー                                         | キーがない、キーが間違っている、またはトークンが期限切れか失効済み               | 認証情報マネージャーに保存された認証情報を削除し、有効なキーで再度プッシュします                                                                                                                                                                           |
| `403`と「Read-only personal access token」                    | トークンのスコープが`read`                                                       | スコープ`read-write`のトークンを作成します                                                                                                                                                                                                                 |
| `403`                                                         | この操作のアクセス権がキーにない、またはリポジトリへのアクセスが付与されていない | [権限](#permissions)のアクションを追加します                                                                                                                                                                                                               |
| `Lock failed: already created lock`                           | 誰かがロックを保持している                                                       | 所有者に解除を依頼するか、管理者に`--force`の使用を依頼します                                                                                                                                                                                              |
| `422`「Object exceeds the maximum size」                      | オブジェクトがインストールの制限を超えている                                     | `arkvoryctl`にも同じ制限が適用されます。より小さいオブジェクトを使用するか、インストールに低い上限が設定されている場合は、管理者に`ARKVORY_MAX_OBJECT_BYTES`（バイト単位）の引き上げを依頼してください。ハード上限の10,000 GiBを超える値は設定できません。 |
| アップロード時に`422`                                         | 内容が`oid`と一致しない。プッシュ中にファイルが変わった                          | `git lfs push`を再実行します                                                                                                                                                                                                                               |
| `503`または`Retry-After`                                      | 同時転送が多すぎる                                                               | `lfs.concurrenttransfers`を下げて再試行します                                                                                                                                                                                                              |
| `507`                                                         | リポジトリのクォータ、またはインストールの容量に達した                           | 空き容量を確保するか、クォータの引き上げを依頼します                                                                                                                                                                                                       |
| アップロード時に`409`                                         | リポジトリがミラーである                                                         | メインサーバーにプッシュします                                                                                                                                                                                                                             |
| 作業ツリーのファイルが`oid`を含む小さなテキストファイルになる | オブジェクトがダウンロードされていない、または`git lfs install`を実行していない  | `git lfs install`、続いて`git lfs pull`を実行します                                                                                                                                                                                                        |
| `x509: certificate signed by unknown authority`               | クライアントが証明書を信頼していない                                             | システムの信頼ストアに認証局を追加するか、`http.sslCAInfo`を設定します                                                                                                                                                                                     |

TLS検証を無効にしないでください（`GIT_SSL_NO_VERIFY`）。キーは各リクエストで送信されます。
