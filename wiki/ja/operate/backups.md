# バックアップ

バックアップエージェントは、インストールのデータベースと保存済みファイルを、別のディスクまたはネットワーク共有上のディレクトリである**保管庫**にコピーします。利用者がアップロードやダウンロードを続けている間も動作します。完了した各バックアップが、検証と復元のできる**復元ポイント**になります。

このページでは、保管庫、スケジュール、保持、検証、状態画面、復元手順を説明します。復元はサーバー上で実行するコマンドです。コンソールに復元ボタンはありません。

## バックアップの仕組み {#how-backups-work}

エージェントは、API とワーカーに並ぶ、インストールの 3 つ目のサービスです。Linux では `arkvory-backup`、Windows では `Arkvorybackup`、Docker Compose では `backup` という名前です。同時に動作するエージェントは 1 つだけです。2 つ目のエージェントは待機し、最初のエージェントが停止すると引き継ぎます。

エージェントは次の 3 つを行います。

- 日次プランが有効な場合に、そのプランを実行します。
- コンソール、`arkvoryctl`、API から要求したジョブを実行します。
- 新しい復元ポイントを毎回検証し、保持ルールを適用します。

復元ポイントは、スナップショット時刻 **T** におけるインストールの公開済み状態を保持します。T より後に公開されたファイルは次のバックアップに入ります。コンソールは、コピーの完了時刻ではなく T からバックアップの経過時間を数えます。

次の点に注意してください。

- バックアップはアップロードやダウンロードを停止しません。実行中、物理クリーンアップはバックアップに必要なファイルを残し、後の処理で削除します。
- 同じファイルをいくつの復元ポイントが含んでいても、保管庫には 1 度だけ保存します。最初のバックアップはすべてをコピーするため、テラバイト単位の内容では長時間かかります。以後は新しいファイルだけをコピーします。
- 復元ポイントはコピーが完了して初めて表示されます。失敗・中断したバックアップが以前の復元ポイントを破損することはありません。
- バックアップはポイントインタイムリカバリーのシステムでも、高可用性でもありません。1 つの復元ポイントの状態を復元し、その T より後の変更は失われます。

## バックアップに含まれるもの {#contents}

復元ポイントには次が含まれます。

- データベースのカタログテーブル：アーティファクト、パッケージ、ファイルパスとその履歴、ラベルとメタデータ、ステージ、添付ファイル、アカウント、グループと権限付与、サービスアカウントとキー、監査証跡、ストレージとクリーンアップのポリシー、コンテナイメージ・Git LFS・npm レジストリのデータ、ミラーの状態。
- 公開済みのすべてのファイルの内容。

復元ポイントには次は含まれません。

- サインインセッション、ダウンロードリンク、読み取りゲートウェイの実行時状態。
- 未完了のアップロード。復元時にキャンセルされ、クライアントは再び開始します。
- バックアッププランとエージェントの状態。復元したインストールではバックアップは無効な状態で始まります。
- インストールの `config/` ディレクトリ：設定、TLS ファイル、ミラーキー、回復キー。これらのファイルは自分でコピーを保管してください。
- Arkvory のプログラム。先にリリースをインストールし、その後に復元します。

## 保管庫の準備 {#vault}

### 要件 {#vault-requirements}

| 要件                                                                                                                   | 理由                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新しい、または空のディレクトリで、サービスの起動前にマウント済み                                                       | エージェントはそこに `vault.json` と復元ポイントを書き込みます                                                                                                                                            |
| リンク、ジャンクション、短いファイル名で解決した場合も、インストールディレクトリとストレージディレクトリの外にあること | ストレージ内の保管庫は、ストレージとともに失われます。これらを内包するパス、またはこれらの内部にあるパスは検査で拒否されます。すべての[ストレージボリューム](./storage#volumes)にも同じ規則が適用されます |
| サービスアカウントが書き込めること                                                                                     | Linux では `arkvory`、Windows では `NT AUTHORITY\LocalService` です。`arkvory configure` がアクセス権を設定します                                                                                         |
| コピーするデータに加えて、少なくとも 1 GiB の空き容量                                                                  | 保管庫はこの予備領域を維持します。ボリュームがいっぱいになると `vault_full` でバックアップが終了し、以前のポイントはそのまま残ります                                                                      |
| Linux では `/home`、`/root`、`/run/user`、`/tmp`、`/var/tmp` の下に配置しないこと                                      | サービスのサンドボックスでは、これらのツリーが見えません                                                                                                                                                  |
| Windows ではドライブ文字を持つローカルまたは iSCSI ボリューム                                                          | `LocalService` は SMB 共有にサインインできないため、`\\nas\share` のようなパスは拒否されます                                                                                                              |

ストレージディスクの障害でバックアップも失わないように、別のディスクまたは NAS 上のボリュームを使ってください。ストレージと同じ物理ディスク上の保管庫は、操作ミスからは保護しますが、ディスク障害からは保護しません。

**保管庫は既定で暗号化されます。** Arkvory はファイル、カタログ、ポイントの説明情報を暗号化します（[保管庫の暗号化](#encryption)を参照）。暗号化せずに作成した保管庫には、カタログ、パスワードハッシュ、すべての公開済みファイルが平文で保存されます。暗号化ボリューム（LUKS、BitLocker、NAS の暗号化）に置き、アクセスをサービスアカウントとバックアップ管理者だけに制限してください。

### 保管庫の暗号化 {#encryption}

保管庫は作成時に暗号化され、その後も暗号化されたままです。Arkvory はファイルの内容、カタログ、ポイントの説明情報を AES-256-GCM で暗号化し、保管庫の読み取り時に、変更、切り詰め、差し替えられたファイルを検出します。ファイル名、サイズ、ポイント数は隠しません。

サーバー上で `arkvory-backup` プログラムを使って保管庫を作成します（[開始前の準備](#restore-prepare)を参照）。両方のファイルは新規で、保管庫とストレージの外にある必要があります。

```bash
arkvory-backup vault init /mnt/backup/arkvory \
  --kit-file /root/arkvory-recovery-kit.txt \
  --agent-key-file /root/arkvory-agent.key
```

1. コマンドは、エージェントキー（`arkvory-agent.key`）と回復キット内の回復キーという 2 つのキーを持つ保管庫を作成します。成功を報告する前に、それぞれのキーで保管庫を開きます。
2. 回復キットを今すぐこのサーバーの外に移してください。パスワードマネージャーや金庫に保管します。キットもエージェントキーもなければ、誰もバックアップを読めず、代わりに復元することもできません。キットと保管庫のコピーを持つ人は、そこにあるすべてのバックアップを読めます。
3. 次の節の手順でエージェントキーを使って保管庫を接続し、手元のキーファイルのコピーを削除します。インストールは、サービスアカウントだけが読み取れる `config/backup/vault.key` に独自のコピーを保持します。

キット内の回復キーが開けるのは、この保管庫だけです。インストールの回復キー（`config/bootstrap-token.txt`）とは異なります。

今すぐ、またキーを変更するたびに、キットで保管庫を開けることを確認してください。

```bash
arkvory-backup vault key verify --vault /mnt/backup/arkvory --key-file /root/arkvory-recovery-kit.txt
```

キーはスロットに属し、各スロットは独自のキーで保管庫を開きます。次のコマンドでスロットを変更します。キーを表示するものはありません。

| コマンド                                                                 | 動作                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vault key list --vault DIR`                                             | スロットの ID、種類（`agent` または `recovery`）、作成時刻を一覧表示します。キーは不要です                                                                                                                                                        |
| `vault key add-recovery --vault DIR --key-file KEY --kit-file NEW`       | 別の人や別の金庫用に、回復スロットを追加してキットを書き出します                                                                                                                                                                                  |
| `vault key rotate-agent --vault DIR --key-file KEY --agent-key-file NEW` | 新しいエージェントキーファイルとスロットを作成します。古いエージェントキーも引き続き使えます。新しいキーファイルで `arkvory configure` を実行し、その後 `vault key remove` で古いスロット（出力の `backup.vault.key.previous`）を削除してください |
| `vault key remove --vault DIR --key-file KEY --slot ID`                  | スロットを削除します。最後のスロットと最後の回復スロットは残されます                                                                                                                                                                              |

スロットを削除すると、そのキーだけを持つ人は保管庫を開けなくなります。以前のポイントを再暗号化することはありません。削除前に保管庫とキーをコピーした人は、そのコピーを引き続き読めます。キーが漏えいした可能性がある場合は、新しいキーで新しい保管庫を作り、そこで新しいポイントの作成を始めてください。

暗号化しない保管庫も作成できます：`arkvory-backup vault init DIR --no-encryption`。カタログ、パスワードハッシュ、すべてのファイルを平文で保持するため、暗号化ボリュームを使い、アクセスをサービスアカウントだけに制限する必要があります。

### 保管庫の接続 {#connect-vault}

サーバー上で root または管理者としてコマンドを実行します。何も変更する前にディレクトリを確認します。

```bash
sudo arkvory configure --root /opt/proanima-arkvory --backup-vault /mnt/backup/arkvory --vault-key-file /root/arkvory-agent.key
```

```powershell
$root = 'C:\ProgramData\ProAnima\Arkvory'
& 'C:\Program Files\ProAnima\Arkvory\arkvory.ps1' configure --root $root --backup-vault D:\Backup\Arkvory --vault-key-file C:\Private\arkvory-agent.key
```

Windows のスクリプトによるインストールでは、[Windows](../install/windows#manage-the-services)の説明に従って `manage.mjs` を起動します。

1. パスが絶対パスで、既存の書き込み可能なディレクトリを指し、インストールとストレージの外にあり、サービスから見えることを確認します。
2. 既定の暗号化保管庫は、`arkvory-backup vault init` で作成済みである必要があります。`--vault-key-file` でサービスにキーを渡します（`AK1-…` キーであり、回復キーは指定しません）。代わりに `--init-vault --vault-no-encryption` を指定すると、**空の**ディレクトリに暗号化しない保管庫を作成します。同じディレクトリを二度初期化することはありません。`vault.json` がなく、`--init-vault` も指定されていなければ拒否します。これにより、未マウントの NAS を空の保管庫と誤認することを防ぎます。
3. サービスアカウントにアクセスを付与し、キーを `config/backup/vault.key` にコピーし、`config/runtime.json` に `ARKVORY_BACKUP_VAULT` と `ARKVORY_BACKUP_VAULT_KEY_FILE` を書き込み、エージェントだけを再起動します。
4. エージェントがこの保管庫を利用可能と報告するまで、最大 150 秒待ちます。この確認では `config/bootstrap-token.txt` を読み取るため、そのファイルは削除しないでください。
5. 何かが失敗すると、以前の設定とアクセス権に戻し、エージェントを再起動します。

例えば新しいサーバーで既存の保管庫を使う場合は、`--vault-key-file` でキーを指定し、`--init-vault` は指定しません。切断するには `--backup-vault-off` を使います。ディレクトリとそのファイルはそのまま残り、インストールのキーファイルは削除されます。再起動すると実行中のバックアップは中断され、エージェントが再試行します。

Docker Compose では、保管庫は `config/compose.vault.yml` のバインドマウントです。Compose コマンドを自分で実行する場合は、`-f config/compose.vault.yml` を追加してください。省略すると、`up` は保管庫なしでエージェントのコンテナを作成します。

### ネットワーク共有上の保管庫 {#network-share}

Linux では、NAS を SMB 3 と NFS 4 で使えます。ファイルがサービスアカウントの所有になるように共有をマウントしてください。そうしないとエージェントは書き込めず、`configure` が拒否して以前の設定に戻します。

```bash
sudo mount -t cifs //nas/arkvory /mnt/backup/arkvory \
  -o credentials=/etc/arkvory/smb.credentials,uid=$(id -u arkvory),gid=$(id -g arkvory),file_mode=0600,dir_mode=0700,vers=3.1.1
```

- 認証情報ファイルのモードを `0600` にします。
- NFS では、ファイルが `arkvory` の所有になるように所有者を対応付けます。エクスポートで `no_root_squash` を使うか、両側で同じユーザー ID を使います。
- `_netdev` を付けて `/etc/fstab` にマウントを追加します。SMB で起動時に NAS が利用できない可能性がある場合は、`nofail` も追加します。
- NAS が切断されると、エージェントは `vault_unavailable` を報告します。保管庫の識別情報が `vault.json` に保存されているため、空のマウントポイントには書き込みません。

## スケジュールと保持 {#schedule}

### スケジュールの設定 {#set-schedule}

[[ui:backups]] を開き、[[ui:backupPlan]] を使います。バックアップの管理権限が必要です。権限がない場合、フォームには [[ui:backupReadOnly]] と表示されます。

| 設定                                                          | 意味                                                                                                                   | 既定値  |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------- |
| [[ui:backupEnabled]]                                          | 日次プランを有効にします。有効にしてもバックアップが直ちに始まるわけではありません                                     | 無効    |
| [[ui:backupTime]]                                             | 日次バックアップの現地時刻。分単位                                                                                     | 02:00   |
| [[ui:backupTimezone]]                                         | その現地時刻の IANA タイムゾーン。例：`Europe/Moscow`、`UTC`。`+03:00` のようなオフセットは指定できません              | `UTC`   |
| [[ui:backupDaily]]、[[ui:backupWeekly]]、[[ui:backupMonthly]] | 何日分、何週分、何か月分の復元ポイントを保持するか。[保持](#retention)を参照してください。範囲：0～366、0～260、0～120 | 7、4、6 |

[[ui:backupPlanSave]] を選択します。その間に他の人がプランを変更していた場合、コンソールは現在のプランを読み込みます。確認して再度保存してください。

スケジュールは次の規則に従います。

- 時刻変更の日に存在しない現地時刻は、変更の瞬間に実行します。2 回現れる現地時刻は、最初の 1 回だけ実行します。
- 停止期間後は、逃した日ごとではなく、追いつくためのバックアップを 1 回だけ実行します。スケジュールを変更しても、変更前の時刻分を補うバックアップは発生しません。
- インストールの既定の更新時間帯は 03:00 UTC です。更新はエージェントを停止するため、実行中のバックアップは中断され、後で再試行されます。更新時間帯と重ならないバックアップ時刻を選んでください。[更新](../install/updates)を参照してください。

### 保持 {#retention}

保持処理は、プランのタイムゾーンで数えた直近 N 日の各日、直近 N ISO 週の各週、直近 N か月の各月について、最新の復元ポイントを残します。3 つのグループの和集合を保持するため、7、4、6 なら最大 17 ポイントで、通常はそれより少なくなります。

保持処理は次を必ず残します。

- 固定されたポイント。
- 最新のポイント。少なくとも 1 ポイントは必ず残ります。

検証に失敗したポイントは削除せず、同じ保管庫にある別のインストールのポイントにも触れません。

バックアップごとに、エージェントは保持処理を別のジョブとしてキューに入れます。[[ui:backupRetentionApply]] を選択することもできます。コンソールはまず、残すポイントと削除するポイントを表示します。削除は取り消せません。エージェントはポイントを削除し、その後、残ったどのポイントも必要としないファイルを削除します。保管庫に破損したポイント（`COMMITTED` のないポイントディレクトリ、または不正なマニフェスト）がある場合、削除は `invalid_manifest` で停止します。保管庫をそのままにして原因を調べ、その後、破損したディレクトリを手動で削除してください。

バックアップの保持処理は、リポジトリ内のビルドの保持設定を変更しません。[ストレージ](./storage)を参照してください。

### 復元ポイントの固定 {#pin}

固定したポイントは、保持ルールを超えて残されます。例えば、大規模な移行の前のポイントを固定します。

- コンソール：[[ui:backupPoints]] のポイント行で [[ui:backupPin]] を選択します。[[ui:backupUnpin]] で解除します。
- CLI：`arkvoryctl backup pin POINT_ID`、解除は `arkvoryctl backup pin POINT_ID --off`。
- API：[setBackupPointPin](../api/reference/backups#setBackupPointPin)。

## 検証 {#verification}

検証には 2 種類あります。

| 種類                                                 | 確認する内容                                                                                                           | 実行時期                                                                                                                                                       |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 簡易（コンソールでは [[ui:backupVerifyStructural]]） | ポイントの各ファイルをマニフェストのダイジェストと照合し、保存済みの各ファイルが正しいサイズで存在することを確認します | バックアップのたびに自動実行                                                                                                                                   |
| 完全（[[ui:backupVerifyDeep]]）                      | 簡易検証に加え、保存済みの全ファイルを読み取り、SHA-256 を検証します                                                   | 最新ポイントに対して 7 日ごとに自動実行。[[ui:backupVerifyDeepAction]]、`arkvoryctl backup verify POINT_ID`、`arkvory-backup verify --deep` からの要求でも実行 |

完全検証はポイント全体を読むため、大きな保管庫では時間とディスクの処理能力が必要です。ポイントが検証に失敗すると、コンソールはエラーコード付きで [[ui:backupVerifyFailed]] を表示し、警告 `verify_failed` が有効になります。原因が分かるまで保管庫を変更しないでください。

まだ検証されていないポイントは [[ui:backupVerifyNone]] と表示されます。最新ポイントの完全検証は、保管庫を読み取れることを定期的に確認する最良の方法でもあります。

## 今すぐバックアップを実行 {#run-now}

次のいずれかを使います。

- コンソール：[[ui:backups]] の [[ui:backupRun]]。
- CLI：`arkvoryctl backup run`。
- API：[requestBackupRun](../api/reference/backups#requestBackupRun) は、キューに入れたジョブを含む 202 を返します。

エージェントは 15 秒ごと（`ARKVORY_BACKUP_POLL_SECONDS`）にキューを確認するため、ジョブはその後まもなく始まります。ジョブは 1 件ずつ実行され、コンソールを閉じても停止しません。再起動や競合で停止したジョブは、最大 5 回まで試行されます。コピー速度の上限 `ARKVORY_BACKUP_BYTES_PER_SECOND` を含むエージェントの設定は、[環境変数](../reference/environment#backups)を参照してください。

バックアップは次のフェーズを進み、コンソールの [[ui:backupJobPhase]] に表示されます：[[ui:backupPhasePreparing]]、[[ui:backupPhaseCatalog]]、[[ui:backupPhaseTransfer]]、[[ui:backupPhaseFinishing]]、[[ui:backupPhaseDone]]。簡易検証では [[ui:backupPhaseStructural]]、完全検証では [[ui:backupPhaseDeep]] が表示されます。

バックアップ中にデータベースのマイグレーションやオフラインツールの `gc`、`scrub` を実行しないでください。バックアップの終了を待つか、`busy` で拒否されます。

## 状態の確認 {#status}

### コンソールでの確認 {#status-console}

[[ui:backups]] は管理者と回復キーに表示されます。サービスキーと個人用アクセストークンには表示されません。ページには次が表示されます。

- 状態：[[ui:backupStateOk]]、[[ui:backupStateWarning]]、[[ui:backupStateCritical]]。
- T からの経過時間付きの [[ui:backupNewest]]、実行が遅れた場合の [[ui:backupOverdue]] を伴う [[ui:backupNextRun]]、最後の通知を示す [[ui:backupAgent]]、空き容量と暗号化の有無（[[ui:backupVaultEncrypted]] または [[ui:backupVaultPlain]]）を示す [[ui:backupVault]]。暗号化していない保管庫には、警告ではなくヒントも表示されます。
- 現在実行中のジョブと、対処のヒント付きの各警告。
- [[ui:backupPoints]]。[[ui:backupSnapshot]]、[[ui:backupCompleted]]、[[ui:backupSize]]、[[ui:backupFiles]]、[[ui:backupVerification]]、固定操作が含まれます。
- [[ui:backupJobs]]。種類（[[ui:backupKindCapture]]、[[ui:backupKindVerify]]、[[ui:backupKindRetention]]）、状態、フェーズ、時刻、エラーコード、進行状況が含まれます。

ジョブの状態は [[ui:backupJobQueued]]、[[ui:backupJobRunning]]、[[ui:backupJobCommitting]]、[[ui:backupJobCompleted]]、[[ui:backupJobFailed]]、[[ui:backupJobInterrupted]] のいずれかです。ジョブの実行中はページが更新されます。[[ui:backupRefresh]] はいつでも使えます。

### 警告 {#warnings}

| コード                 | レベル | 対処                                                                                                                                                                                            |
| ---------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vault_not_configured` | 警告   | 保管庫を接続します。[保管庫の接続](#connect-vault)を参照してください                                                                                                                            |
| `agent_offline`        | 重大   | 2 分間通知がありません。エージェントサービスを起動し、ログを読んでください                                                                                                                      |
| `schedule_disabled`    | 警告   | 日次バックアップが必要ならプランを有効にします                                                                                                                                                  |
| `no_backup_yet`        | 警告   | 最初のバックアップを作成します                                                                                                                                                                  |
| `backup_stale`         | 重大   | プランが有効なのに最新ポイントが 26 時間より古くなっています。ジョブのエラーコードとエージェントのログを読んでください                                                                          |
| `last_run_failed`      | 警告   | 前回のバックアップが失敗しました。エラーコードはジョブ一覧にあります                                                                                                                            |
| `vault_unavailable`    | 重大   | ボリュームが未マウント、`vault.json` がない、保管庫に書き込めない、または暗号化保管庫に有効なキーがありません（エージェントのログは `vault_key_missing` または `vault_key_invalid` を示します） |
| `vault_low_space`      | 警告   | ボリュームの空きが 10% 未満、または前回のバックアップで追加されたデータの 2 倍未満です。空きを確保するか、保持するポイント数を減らしてください                                                  |
| `verify_failed`        | 重大   | ポイントが検証に失敗しました。保管庫を変更せず、調査してください                                                                                                                                |
| `never_deep_verified`  | 警告   | 8 日を超えて完全検証が行われていません。エージェントの動作を確認するか、完全検証を開始してください                                                                                              |

### CLI と API での確認 {#status-cli}

```bash
arkvoryctl backup status
arkvoryctl backup jobs
arkvoryctl backup points
arkvoryctl backup status --json || echo "backup problem"
```

重大な警告が有効な間、`backup status` は終了コード 9 で終了するため、監視に使えます。これらのコマンドには、所有者のファイルキーまたはアカウント管理者のセッションが必要です。[コマンドラインクライアント](../protocols/cli#backups)と [TypeScript SDK](../protocols/sdk#backups)を参照してください。HTTP 操作は[バックアップ API リファレンス](../api/reference/backups)にあります。

Prometheus 向けに、API は `arkvory_backup_last_success_timestamp_seconds`（最新ポイントの T）、`arkvory_backup_agent_last_seen_timestamp_seconds`、`code` ラベル付きの `arkvory_backup_warnings` を公開します。[監視](./monitoring)を参照してください。

## 復元 {#restore}

復元は、**空の**データベースと**空の**ストレージディレクトリに書き込みます。実行中のインストールを上書きすることはありません。復元後は、復元したデータで別のインスタンスを起動して確認し、それから古いサーバーを置き換えるかどうかを決めます。

### 開始前の準備 {#restore-prepare}

- **プログラム。** 復元コマンドは、インストール済みリリースの `arkvory-backup` プログラムです。インストールに含まれる Node.js で起動します。
  - Linux パッケージ：`/opt/proanima-arkvory/runtime/node /opt/proanima-arkvory/releases/VERSION/apps/backup/dist/main.js COMMAND`
  - Windows のグラフィカルインストーラー：`& "$root\runtime\node.exe" "$root\releases\VERSION\apps\backup\dist\main.js" COMMAND`

  `VERSION` は `installation.json` に記録されたインストール済みバージョンです。このページの以降の部分では、`arkvory-backup` はこのコマンドライン全体を表します。Docker Compose では、リリースイメージのコンテナ内から同じプログラムを実行します。スクリプトによるインストールでは、`runtime/` の下の Node.js フォルダーを使います。

- **リリース。** ポイントを作成したリリース、またはそれより新しいリリースを使います。より新しいリリースのポイントは `schema_mismatch` で拒否されます。
- **アカウント。** 保管庫を読み取れるアカウントでコマンドを実行します。Linux では、保管庫は `arkvory` の所有でモードは 0700 のため、`sudo -u arkvory` を使います。Windows では管理者権限の PowerShell を使います。新しいストレージディレクトリは、最終的に API を実行するアカウントの所有にする必要があります。
- **キー。** 暗号化保管庫にはキーが必要です。以降の各コマンドに回復キットまたはキーファイルを `--key-file FILE` として指定するか、`ARKVORY_BACKUP_VAULT_KEY_FILE` を設定します。キーは常にファイルで渡し、キー自体を引数にしません。
- **復元先。** 空のデータベースを作成します。例：`CREATE DATABASE arkvory_restore OWNER arkvory;`。保管庫と異なるボリュームで、元のストレージの内部ではない場所に、存在しないか空のストレージディレクトリを選びます。[複数ボリューム](./storage#volumes)を持つインストールには、各ボリューム用に追加の空ディレクトリが必要です。[複数ボリュームの復元](#restore-volumes)を参照してください。
- **データベース URL。** 引数はプロセス一覧から見えるため、引数ではなく環境変数で渡します。

### 復元の手順 {#restore-steps}

1. 復元ポイントを一覧表示し、1 つ選びます。ポイント ID をコピーします。

   ```bash
   arkvoryctl backup points
   arkvory-backup list --vault /mnt/backup/arkvory
   ```

2. ポイントを完全検証します。

   ```bash
   arkvory-backup verify --vault /mnt/backup/arkvory --point POINT_ID --deep
   ```

3. 環境変数に復元先のデータベースを設定します。

   ```bash
   export ARKVORY_RESTORE_DATABASE_URL='postgresql://arkvory@db.example/arkvory_restore'
   ```

4. `--yes` **なし**で復元を実行します。これはドライランです。ポイント、ファイルのハッシュ、スキーマバージョン、復元先が空であることを確認し、何も書き込みません。

   ```bash
   arkvory-backup restore --vault /mnt/backup/arkvory --point POINT_ID --storage /srv/arkvory-restore
   ```

   確認に成功すると、終了コード 0 とログ行 `backup.restore.planned` で終了します。

5. 同じコマンドを `--yes` 付きで実行します。レポートファイルを残すには `--report` を追加します。そのファイルはまだ存在していてはなりません。

   ```bash
   arkvory-backup restore --vault /mnt/backup/arkvory --point POINT_ID --storage /srv/arkvory-restore --yes --report /root/restore-report.json
   ```

   復元は `verify`、`content`、`schema`、`tables`、`migrate`、`done` の各フェーズを進みます。すべてのファイルをコピーして SHA-256 を確認し、スキーマを作成し、1 つのトランザクションですべてのテーブルを読み込み、正規化を適用してから、残りのマイグレーションを実行します。レポートには識別子と件数だけが含まれ、パスや認証情報は含まれません。

6. 復元したデータで別の API インスタンスを起動します。新しいデータベースの `ARKVORY_DATABASE_URL`、新しいディレクトリの `ARKVORY_DATA_DIR`、専用の `ARKVORY_KEYS_FILE`、別のポートを指定します。`/health/ready` が応答すること、サインインできること、カタログが完全であること、確認用ファイルを同じ SHA-256 でダウンロードできることを確認します。

復元に失敗した場合は、復元先のデータベースとディレクトリを削除し、作成し直してください。空でない復元先は `target_not_empty` で拒否され、既存のデータが保護されます。

### 複数ボリュームの復元 {#restore-volumes}

復元ポイントは各ファイルのボリュームを記録しています。各ファイルを対応するボリュームに復元します。

1. 復元したインストールのモジュールファイルを作成します。ソースの各ボリュームについて、同じ ID のインスタンスと、新しい空のディレクトリを指定します。例は `/srv/arkvory-restore-volume-2` です。ディレクトリには `--storage` と同じ規則が適用されます。
2. 両方の復元コマンドに `--modules-file FILE` を追加します。

   ```bash
   arkvory-backup restore --vault /mnt/backup/arkvory --point POINT_ID --storage /srv/arkvory-restore --modules-file /srv/arkvory-restore-modules.json
   ```

3. このモジュールファイルを `ARKVORY_MODULES_FILE` に指定して、復元したインスタンスを起動します。

復元先に指定されていないボリュームのファイルを含むポイントは、ドライランでも、何も書き込む前に拒否されます。配置ポリシーはバックアップに含まれます。ボリュームの識別情報は含まれません。復元後の API が初回起動時に新しいディレクトリを登録します。

### 復元による変更 {#after-restore}

復元は決められた変更を適用し、新しいインスタンスが進行中だった処理を引き継いだり、古い認証情報を有効にしたりしないようにします。

- 未完了のアップロードはキャンセルされ、クォータが解放されます。待機中・実行中の完了ジョブは `conflict` コードで失敗状態になります。未完了のプロモーションは破棄されます。
- セッションは復元されません。全員がサインインし直します。
- すべての個人用アクセストークンは取り消され、すべてのサービスキーは `revoked` になります。新しいキーを発行してください。
- 全リポジトリで、ストレージの保持処理と物理クリーンアップが無効になります。意図して再び有効にしてください。
- バックアップは無効で、保管庫は設定されていません。ダウンロードリンクと読み取りゲートウェイの設定は引き継がれません。
- アカウント、グループ、権限付与は、T 時点のパスワードハッシュとともに残ります。T より後に変更したパスワードは古いものに戻るため、自分のポリシーに従ってリセットしてください。
- 回復キーとファイルキーは、復元データを実行するインストールのキーファイルから取得します。
- ミラーは位置を保持しますが、設定は `config/` にあります。再接続してください。[ミラー](./mirrors)を参照してください。
- セキュリティ監査の `backup.restored` 項目に、ポイントと件数が記録されます。

### 別のサーバーへの移行 {#move-server}

バックアップを使って、インストールを別のサーバーに移行できます。

1. 同じリリースまたはそれより新しいリリースの Arkvory を新しいサーバーにインストールします。[インストール方式の選択](../install/index)を参照してください。
2. 同じ保管庫、またはそのコピーを新しいサーバーに接続します。既存の保管庫には `--init-vault` を使わないでください。
3. 上記の手順で、最新ポイントを新しい空のデータベースと空のディレクトリに復元し、結果をテストします。
4. インストールの参照先を復元データに変更します。`config/runtime.json` に `ARKVORY_DATABASE_URL` と `ARKVORY_DATA_DIR` を設定し、サービスを再起動します。[設定](../install/configuration)を参照してください。
5. 新しいキーを発行し、保持とクリーンアップのポリシーを再設定し、ミラーとバックアッププランを接続し、クライアントに新しいアドレスを知らせます。

最後の 2 手順は手動であり、ガイド付き切り替えの一部ではありません。最初に予備のサーバーで一連の手順全体を予行演習してください。古いサーバーで T より後に行った変更は失われるため、クライアントを移す前に古いサーバーを停止します。

## 復元の定期テスト {#test-restore}

一度も復元していないバックアップは、期待にすぎません。製品はポイントのバイト列を検証しますが、復元テストは記録しません。実施日と結果は自分で記録してください。

少なくとも、次のタイミングでテストします。

- 最初のバックアップの後。
- データベーススキーマを変更する更新の後、毎回。
- 自分で決めたスケジュールに従って。例えば四半期ごと。

各テストでは、予備のサーバーまたはテスト用データベースで[復元の手順](#restore-steps)を実施し、最後にサインイン、カタログの確認、確認用ファイルのダウンロードを行います。終了後はテスト用データベースとディレクトリを削除します。

## 終了コードとログ行 {#exit-codes}

### 終了コード {#exit-codes-table}

`arkvory-backup` プログラムは、標準出力に 1 行につき 1 つの JSON オブジェクトを書き込み、失敗時は標準エラー出力にヒントを 1 行書き込みます。

| コード | 意味                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 0      | 成功。`--yes` なしの `restore` では、確認に成功しました                                                                              |
| 1      | 実行失敗。データベースやディスクが利用不能、リースやスナップショットの喪失、保管庫や復元先の容量不足です。復元ポイントは破損しません |
| 2      | 引数または環境変数が不正です                                                                                                         |
| 3      | 安全性確認で拒否されました。`vault.json` がない、ディレクトリの重複、空でない復元先、未対応のスキーマ、指定ポイントがない場合です    |
| 4      | 整合性の問題。ハッシュ、ファイルの欠落、変更されたマニフェストが原因です。原因が分かるまで保管庫を変更しないでください               |
| 5      | 使用中。他のバックアップやメンテナンスが実行中、または削除が時間内に終わりませんでした。後で再試行してください                       |

### ログ行 {#log-lines}

各行の `component` は `backup` です。パス、URL、秘密情報は記録されません。特に役立つ行は次のとおりです。

| コード                                                                                      | 意味                                                                                                                         |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `backup.phase`                                                                              | バックアップのフェーズ移行：`barrier`、`pins`、`tables`、`blobs`、`manifest`、`commit`、`done`                               |
| `backup.capture.completed`                                                                  | バックアップ完了。フィールド：`pointId`、`outcome`、`blobs`、`copied`、`reused`、`copiedBytes`、`contentBytes`、`durationMs` |
| `backup.point`                                                                              | `list` の出力の 1 つの復元ポイント                                                                                           |
| `backup.verify.point`、`backup.verify.problem`                                              | 検証結果と、`errorCode` 付きの各問題                                                                                         |
| `backup.restore.phase`、`backup.restore.planned`、`backup.restore.completed`                | 復元の進行状況と結果。行数と、上記の各変更の件数を含みます                                                                   |
| `backup.failed`                                                                             | コマンドの失敗。`errorCode` を読んでください                                                                                 |
| `backup.agent.started`、`.standby`、`.lease_acquired`、`.lease_lost`、`.stopped`、`.failed` | エージェントのライフサイクル                                                                                                 |
| `backup.request.started`、`.done`、`.failed`、`.requeued`                                   | `kind` と `errorCode` を伴う、エージェントのジョブ                                                                           |
| `backup.schedule.due`                                                                       | プランがバックアップを開始しました                                                                                           |
| `backup.retention.applied`                                                                  | 保持処理の完了。フィールド：`forgotten`、`blobs`、`freedBytes`                                                               |

エージェントのログは、Linux では `journalctl -u arkvory-backup`、Windows ではインストールルートの `logs\`、Compose では `docker compose logs backup` で読み取れます。

| `errorCode`                                              | 終了コード | 対処                                                                                                                                       |
| -------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `vault_missing`                                          | 3          | ディレクトリに `vault.json` がありません。ボリュームをマウントするか、`vault init` を 1 回実行してください                                 |
| `vault_key_missing`                                      | 3          | 保管庫は暗号化されていますが、キーが指定されていません。`--key-file FILE` または `ARKVORY_BACKUP_VAULT_KEY_FILE` を使ってください          |

| `unsafe_path`                                            | 3          | 保管庫、ストレージ、復元先を別々のディレクトリツリーに配置してください                                                                     |
| `target_not_empty`                                       | 3          | 復元は空のデータベースと空のディレクトリだけに書き込みます                                                                                 |
| `schema_mismatch`                                        | 3          | ポイントがリリースより新しいか、対応する復元範囲より古くなっています。別のリリースを使ってください                                         |

| `integrity_mismatch`、`invalid_manifest`、`blob_missing` | 4          | 保管庫を変更しないでください。`verify --deep` を実行して調査します                                                                         |
| `busy`、`barrier_timeout`                                | 5          | 他の操作が実行中です。後で再試行してください                                                                                               |
| `vault_full`、`storage_full`                             | 1          | 空き容量を確保してください。以前のポイントは無事です                                                                                       |
| `attempts_exhausted`                                     | 3          | この要求は 5 回の試行を使い切りました。新しいバックアップを開始してください                                                                |

## 制限 {#limits}

- 1 インストールにつきプランと保管庫はそれぞれ 1 つです。保管庫はディスクまたはマウント済み共有上のディレクトリで、S3、オフサイト用の構成、不変性を保証する構成はありません。
- 暗号化は内容とカタログを隠しますが、ファイル名、サイズ、ポイント数は隠しません。キーを失うとバックアップを失います。キースロットを削除しても、以前のポイントを再暗号化することはありません。
- バックアップジョブの一時停止やキャンセルはできず、コンソールには復元ウィザードや復元テストの状態表示はありません。
- 復元には空の復元先が必要で、復元したデータへの切り替えは手動です。
- バックアップエージェントは高可用性システムではありません。2 つ目のエージェントは予備として待機するだけです。

## 元のストレージを使わない復元 {#restore-default-storage}

復元コマンドに `--to-default-storage` を追加すると、元のボリュームやモジュールを使わず、すべてのオブジェクトを既定のストレージに配置できます。オブジェクトの全バイト列を収容する容量を確保してください。`--yes` がなければ、確認と計画の報告だけを行います。データベースとストレージは空である必要があります。このモードでは配置ルールを消去し、公開済みコンテンツを通常の blob として復元します。復旧後に新しい配置ルールを設定してください。

論理バックアップは、インストール済みモジュールのバックアップ用の役割を通じて、公開済みオブジェクトのバイト列を取得します。モジュールディレクトリ、キャッシュ、非公開の調整用状態をファイルシステムイメージとしてコピーするものではありません。取得が完了するまで、ソースのモジュールをインストール済みで読み取り可能な状態に保ってください。[--to-default-storage](#restore-default-storage) による復元では、元のモジュールや有料ライセンスなしで、これらのオブジェクトを通常のコア blob として復旧できます。論理サイズ全体の容量を確保してください。インストールの秘密情報は別に保管し、有料の書き込み機能を再び有効にする前にライセンスの復旧手順に従ってください。
