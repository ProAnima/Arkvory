# ストレージ

Arkvoryは、公開した各ファイルを変更せずに1回だけ保存します。保存先はサーバーのローカルディスク上のストレージディレクトリで、必要に応じて[複数のボリューム](#volumes)を利用できます。このページでは、ディスク容量を使用するもの、クォータと保持ポリシーによる制限、削除したファイルがディスクから消える仕組み、ディスクが満杯になった場合の対処を説明します。

## コンテンツの保存先 {#location}

ストレージディレクトリは`ARKVORY_DATA_DIR`で設定します。インストーラーは次の場所を使用します。

| インストール方式 | ストレージ                                   |
| ---------------- | -------------------------------------------- |
| Windows          | `C:\ProgramData\ProAnima\Arkvory`内の`data\` |
| Linux            | `/opt/proanima-arkvory`内の`data/`           |
| Docker Compose   | Dockerボリューム`proanima-arkvory_storage`   |

この中で、`blobs/`には完成したファイル、`staging/`と`parts/`には進行中のアップロードを保存します。`storage-id`ファイルはディレクトリとデータベースを結び付けます。すべての名前、ラベル、バージョン、権限を含むカタログはPostgreSQLにあります。ファイルとデータベースは一体として扱ってください。

- ハードリンクをサポートするローカルファイルシステムを使用してください。ストレージにネットワーク共有は使用しないでください。
- ディレクトリ内のファイルを手動で追加、変更、削除しないでください。Arkvoryが、以下で説明する仕組みでファイルを削除します。
- 公開済みファイルは変更されません。新しい内容は、新しいIDを持つ新しいファイルになります。

## 複数のボリューム {#volumes}

1つのボリュームを拡張する代わりに、2台目のディスクなどにストレージディレクトリを追加できます。追加する各ディレクトリは、固有のIDを持つ組み込みモジュール`local-storage`のインスタンスです。`ARKVORY_DATA_DIR`のストレージディレクトリは常に`default`インスタンスです。

モジュールファイル（`ARKVORY_MODULES_FILE`。[環境変数](../reference/environment)を参照）でインスタンスを設定します。

```json
{
  "format": 1,
  "modules": {
    "local-storage": {
      "enabled": true,
      "config": {
        "instances": {
          "volume-2": { "directory": "/srv/arkvory-volume-2" }
        }
      }
    }
  }
}
```

| フィールド      | 意味                                                                                                                                  | デフォルト                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `directory`     | ディレクトリの絶対パス。ストレージディレクトリや他のインスタンスを内包することも、その中に配置することもできません                    | 必須                            |
| `acceptsWrites` | `false`にすると、このボリュームへの新規アップロードを停止します。ファイルは引き続き読み取れ、すでに開始したアップロードは完了できます | `true`                          |
| `mode`          | `read-only`はダウンロードと検査のみを提供し、すべての書き込みと削除を拒否します。読み取り専用でマウントしたボリュームなどに使用します | `full`                          |
| `enabled`       | `false`にするとボリュームを閉じます。再び有効にするまで、そのファイルはダウンロードできません                                         | `true`                          |
| `reserveBytes`  | このボリュームに残す空き容量（バイト）                                                                                                | `ARKVORY_STORAGE_RESERVE_BYTES` |

IDには英小文字、数字、`-`を使い、英字で始めます。`default`は使用できません。インスタンスは最大16個追加できます。すべてのプロセス（API、読み取りゲートウェイ、ワーカー、バックアップエージェント）が同じモジュールファイルを読み取る必要があります。異なるインスタンス構成を計画するプロセスは準備完了になりません。変更後はすべてのサービスを再起動してください。

ボリュームを追加するには：

1. ボリュームをマウントし、ディレクトリを作成します。サービスを実行するアカウントが所有していなければなりません。Arkvoryはこのディレクトリを作成しません。ボリュームがマウントされていないなどの理由でディレクトリがなければ、そのボリュームは利用不可のままとなり、マウントポイントの下には何も書き込みません。
2. `arkvory volume-init --directory /srv/arkvory-volume-2`で、ディレクトリを新しいボリュームとして識別します。`--root`は不要です。存在しないディレクトリや空でないディレクトリは拒否します（`lost+found`だけは存在していても構いません）。識別ファイル`storage-id`を書き込みます。Linuxでは、未マウントのボリューム用の空ディレクトリなど、マウントポイントではないディレクトリも拒否します。マウント済みボリューム内のディレクトリには`--no-expect-mount`を追加してください。Windowsでは`--expect-mount`でこの確認を有効にします。サービス自体がこのファイルを作成することはなく、ファイルのないボリュームは利用不可のままです。
3. モジュールファイルにインスタンスを追加し、サービスを再起動します。初回起動時にAPIが、そのディレクトリの`storage-id`ファイルにあるボリュームの識別情報を記録します。以後、すべてのプロセスがこのファイルを確認します。未マウントのボリュームや、同じパスにある別のボリュームには書き込みません。ボリューム上で書き込みや削除を行う前にも、毎回このファイルを再確認します。
4. [配置ポリシー](#placement)で、このボリュームに送るアップロードを選択します。

### 新規アップロードの配置 {#placement}

リポジトリの配置ポリシーは、新しいアップロードごとにストレージを選択します。各ルールにはID、ストレージ（`backendId`）、任意の2つの条件（パッケージグループ（`models/*`、`tools`、`*`）と最小サイズ（バイト））があります。条件を満たす最初のルールを適用します。一致するルールがなければ、`default`にアップロードします。1つのリポジトリには最大32個のルールを設定できます。

`arkvoryctl`またはAPI操作[getStoragePlacement](../api/reference/storage#getStoragePlacement)と[setStoragePlacement](../api/reference/storage#setStoragePlacement)でポリシーを読み取り、変更します。

```bash
arkvoryctl storage placement --repository releases
arkvoryctl storage placement --repository releases --revision 0 --file rules.json
```

`rules.json`ファイルにはルールのリストを記述します。次の例は、1 GiB以上のすべてのファイルを`volume-2`に配置します。

```json
[{ "id": "large", "backendId": "volume-2", "packageGroup": null, "minSizeBytes": "1073741824" }]
```

- ポリシーの読み取りには`storage.read`、変更には`storage.manage`が必要です。応答には、すべてのストレージとその状態（`accepting`、`not_accepting`、`read_only`、`disabled`、`unavailable`、`not_loaded`）も含まれます。
- ルールには設定済みのストレージだけを指定できます。他の名前は400 `backend_unknown`で拒否します。
- ポリシーはリビジョン付きで保存します。他の人が変更した場合は、再度読み取ってから保存してください。
- 変更は新規アップロードにのみ適用します。保存済みファイルは元の場所に残ります。移動するには[保存済みファイルを別のボリュームへ移動](#rehome)を参照してください。

### ボリュームが新規アップロードを受け付けない場合 {#placement-fallback}

配置を理由に公開が失敗することはありません。`acceptsWrites: false`、`read-only`、`enabled: false`、インスタンスの欠落、またはボリュームの利用不可（未マウント、識別確認の失敗、応答なし）により、その時点で選択先がアップロードを受け付けない場合、新しいアップロードは代わりに`default`に作成します。アップロードの`storageBackend`にストレージを示し、メトリクス`arkvory_storage_placement_fallback_total`で回数を数え、ログに`storage.placement_fallback`を記録します。

- **進行中のアップロードは移動しません。** パート形式のアップロード中にボリュームがデータの受け付けを停止すると、新しいパートは409 `backend_read_only`で拒否し、クライアントは新しいアップロードを開始します。すべてのパートがすでに存在する場合は、完了時にファイルを`default`へ書き込みます。パートは元のボリュームから読み取ります。中断した試行ですでにそのボリュームに完全保存されたファイルは、そこに残ります。
- **利用不可のボリューム**上のファイルは、ボリュームが復帰するまで503 `unavailable`でダウンロードに失敗します。サーバーは稼働を続け、準備状態と`writable`は`default`の状態だけに従います。各プロセスは30秒ごとにボリュームを再確認します。
- **物理クリーンアップ**は、別のボリュームに残ったパートも含め、各ファイルをその保存先ボリュームから削除します。利用不可または読み取り専用のボリューム上では、そのファイルをスキップして後で再試行します。
- **クォータと制限。** クォータと`ARKVORY_CAPACITY_BYTES`は全ボリュームを合算します。予備領域は各ボリュームに適用します。
- raw、OCI、ミラーのアップロードの**一時ファイル**は、`default`のストレージディレクトリに置かれます。
- **クラスター。** [高可用性クラスター](./cluster)では、ストレージディレクトリと同様、すべてのボリュームをレプリケーション対象ボリューム上のディレクトリにする必要があります。別のディスクは他のサーバーにコピーされません。この条件を満たさないとAPIは起動しません。
- **設定から削除したボリューム。** Arkvoryは、データを保持したすべてのボリュームを記憶します。モジュールファイルから削除したボリューム上のファイルは、ダウンロード、物理クリーンアップ、バックアップができなくなります。バックアップは`blob_missing`で失敗します。各プロセスは、メトリクス`arkvory_storage_backend_unconfigured`、ログ`storage.backend_unconfigured`、アラート`ArkvoryStorageVolumeUnconfigured`で報告し、配置の応答では`not_loaded`と表示します。再設定すると解消します。ボリュームを廃止するには、`acceptsWrites: false`を設定し、[ファイルを移動](#rehome)して、移動完了まで設定を維持してください。

`arkvory_storage_backend_up`と`arkvory_storage_backend_accepting`を監視してください。[監視](./monitoring#metrics)を参照してください。バックアップはすべてのボリュームをコピーします。復元には、ボリュームごとに空のディレクトリが必要です。[複数ボリュームの復元](./backups#restore-volumes)を参照してください。

### 保存済みファイルを別のボリュームへ移動 {#rehome}

ボリュームの廃止や新しいボリュームへの格納などのため、保存済みファイルを移動するには、サーバー上で移動を計画します。サービスは稼働を続けます。

```bash
arkvory storage rehome --root /opt/proanima-arkvory --from volume-2 --to default
arkvory storage moves --root /opt/proanima-arkvory
```

1. `rehome`は、`--from`のストレージ上の公開済みファイルごとに移動を計画し、計画した数と状態別の移動数を表示します。`--repository <name>`で1つのリポジトリに、`--limit <n>`でファイル数（デフォルト10 000、最大100 000）に制限します。すでに移動中のファイルを再度計画することはありません。両方のストレージが設定済みである必要があります。移動先は新規アップロードを受け付ける必要があり、そうでなければ`backend_read_only`で失敗します。移動元は読み取り専用でも構いません。
2. ワーカーが2つずつ並行して移動します。各ファイルのバイト列を移動先にコピーし、サイズとSHA-256を確認し、ファイルの保存先を切り替えてから、移動元のコピーを削除します。IDは維持するため、リンク、パス、ステージ、参照は有効なままです。
3. `moves`は状態別に移動を表示します。状態は`planned`、`copied`、`switched`、`released`（完了）、`skipped`（途中でファイルが削除されたため、移動先のコピーも削除）、`failed`です。

- **ダウンロードとバックアップ。** 切り替え前に開始したダウンロードは、移動元から最後まで読み取ります。移動元のコピーは、そのダウンロードと、そのファイルを含むすべてのバックアップの終了後に削除します。削除側が待機し、ダウンロードを妨げることはありません。
- **失敗。** 失敗した処理は、待ち時間を増やしながら再試行します。5回失敗するか、移動先がアップロードの受け付けを停止すると、移動は`failed`になり、ファイルは元の場所に残ります。`rehome`を再実行して新しい移動を計画してください。次の移動では、失敗時に移動先に残したコピーを確認して再利用します。これは切り替えまでの動作です。切り替え後の移動は`failed`にならず、移動元のコピーの削除を成功するまで再試行します。退避元などのストレージが利用不可または読み取り専用の間、その処理は待機し、5分ごとに再確認します。
- **速度。** `ARKVORY_REHOME_BYTES_PER_SECOND`でワーカーのコピー速度を制限します。デフォルトは無制限です。
- **クォータ**は、移動中も移動後も各ファイルを1回だけ数えます。
- Docker Composeでは、コマンドが一時的なワーカーコンテナを実行します。

ワーカーは`storage.move_completed`、`storage.move_skipped`、`storage.move_failed`をログに記録します。

## ディスク容量の計画 {#disk}

ストレージボリュームでは、次のものがディスク容量を使用します。

| 対象                                       | 補足                                                                                                                            |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| 公開済みファイル                           | 保持するすべてのバージョン                                                                                                      |
| 進行中のアップロード                       | アップロード終了までのパートとステージングファイル                                                                              |
| パート形式で完了したアップロードのファイル | 一時パートは、物理クリーンアップの処理で削除するまで完成したファイルと併存します。[物理クリーンアップ](#physical-cleanup)を参照 |
| 削除済みファイル                           | 猶予期間が終了し、クリーンアップ処理が削除するまでディスクに残ります                                                            |
| ミラーのコピー                             | ミラーがファイルをコピーする間の`mirror-staging`内のパート。[ミラー](./mirrors)を参照                                           |

ストレージのほかに、PostgreSQLデータベース、ログ、バックアップ保管庫の容量も計画し、可能なら別々のボリュームに配置してください。[バックアップ](./backups)を参照してください。

Arkvoryは、ストレージボリュームに空き容量の**予備領域**を確保します。デフォルトは1 GiB（`ARKVORY_STORAGE_RESERVE_BYTES`）です。予備領域を消費するアップロードは、HTTP 507と理由`storage_full`で拒否します。ダウンロードは引き続き利用できます。新しいデータを保存する空き容量がない間、`GET /health/ready`は`writable: false`を示します。

各ボリュームでは100 000個の空きinodeも確保します（`ARKVORY_STORAGE_RESERVE_INODES`）。保存済みファイルも各パートもそれぞれ1つのファイルなので、バイト容量より先にinodeが尽きる場合があります。この予備分を消費する書き込みも同じように拒否します。NTFSなどinode数を取得できないファイルシステムでは、バイト容量だけを確認します。

ディスクとは独立して、2つの制限も適用します。

- `ARKVORY_CAPACITY_BYTES`は、インストール全体の予約済みコンテンツを制限します。デフォルトは10 TiBです。論理的な制限であり、ディスクの確認ではありません。上限に達すると、アップロードはHTTP 507と理由`catalog_limit`で失敗します。
- `ARKVORY_MAX_OBJECT_BYTES`は、1つのファイルのサイズを制限します。

[環境変数](../reference/environment#storage-and-limits)を参照してください。Arkvoryにはストレージやデータベースの空き容量メトリクスはありません。OSのツールやnode exporterでボリュームを監視してください。

## ストレージを管理できるユーザー {#permissions}

ストレージ設定は、通常の読み取り・書き込み権限には含まれません。サービスキーには、リポジトリに対する明示的な操作権限が必要です。

| 操作               | 許可する内容                                                                         |
| ------------------ | ------------------------------------------------------------------------------------ |
| `storage.read`     | ポリシー、使用量、物理クリーンアップ設定、配置の表示                                 |
| `storage.manage`   | ポリシー、クォータ、物理クリーンアップ設定、配置の変更と、クリーンアップバッチの要求 |
| `artifact.delete`  | 削除のプレビュー、アーティファクトの削除、自動保持ポリシーの有効化                   |
| `diagnostics.read` | ストレージイベントの読み取り                                                         |

パスワードを使うアカウントと回復キーには、これらの権限が自動では付与されません。コンソールでストレージを管理するには：

1. 4つの操作を含む対象リポジトリのポリシーを持つサービスアカウントを作成します。[アカウントとアクセス](../use/accounts)を参照してください。
2. そのアカウントのキーを発行して有効化します。
3. コンソールで[[ui:keySignIn]]を開き、キーを貼り付けて[[ui:connect]]を選択します。
4. [[ui:repositories]]を開き、対象リポジトリのカードで[[ui:repositoryStorage]]を選択します。

カタログの上に[[ui:storageTitle]]パネルが表示されます。権限がなければパネルは表示されません。

有効な保持ポリシーは、**有効化したキー**に結び付いています。自動実行のたびに、そのキーが引き続き有効で、期限切れでなく、`storage.manage`と`artifact.delete`を持つことを再確認します。キーを取り消したり権限を狭めたりすると削除を停止し、`retention.failed`イベントを記録します。キーをローテーションした後は、新しいキーでポリシーを再保存してください。

## クォータと警告しきい値 {#quotas}

リポジトリにはクォータを設定できます。クォータがなければ、全体の制限だけを適用します。

| 設定         | コンソールのフィールド        | 意味                                                                                                              | デフォルト |
| ------------ | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------- |
| クォータ     | [[ui:storageQuota]]           | リポジトリが使用できる最大容量。APIは1～9 007 199 254 740 991の正確なバイト数を受け取り、`null`は無制限を表します | 無制限     |
| 警告しきい値 | [[ui:storageWarningPercent]]  | 警告を発生させるクォータの使用割合。1～98                                                                         | 80         |
| 重大しきい値 | [[ui:storageCriticalPercent]] | エラーを発生させる割合。2～99で、警告しきい値より大きい値                                                         | 95         |

クォータに計上する使用量は、そのリポジトリの、まだディスクから削除していないすべてのファイルのサイズです。公開済みファイル、未完了のアップロード、クリーンアップ待ちの削除済みファイルを含みます。そのため、削除済みファイルもクリーンアップで除去するまでクォータを使用します。

- **確認。** アップロード開始時にサーバーがクォータを確認します。クォータを超える新規アップロードはHTTP 507と理由`storage_quota`で失敗します。同じ冪等キーで再試行しても、容量を二重に予約することはありません。
- **引き下げ。** 現在の使用量より小さいクォータを設定できます。進行中のアップロードは完了できますが、上限を超える新規アップロードは拒否します。
- **自動解放はしません。** クォータを理由に削除することはありません。保持処理も、クォータを満たすために余分なビルドを削除することはありません。
- **状態。** 状態は`unlimited`、`normal`、`warning`、`critical`、`exceeded`です。状態が変わると、ストレージイベントとして1回記録します。
- **監視。** 自動削除が無効でも、サーバーは毎分最大20個のリポジトリの状態を再確認します。

これらの数値は論理的な予約量で、ディスクの空き容量ではありません。ディスクにはステージングファイルや他のリポジトリも保存するため、リポジトリがクォータ内でもディスクが満杯になることがあります。

## 保持ポリシー {#retention}

保持ポリシーは、古い**登録済みUPackビルド**を自動で削除し、最新N個を保持します。他のファイルは削除しません。パス指定の通常ファイル、コンテナイメージ、Git LFSオブジェクト、npmパッケージは対象外です。ポリシーがなければ自動削除しません。

### 設定 {#retention-settings}

| 設定         | コンソールのフィールド  | 意味                                                                                                   | デフォルト                            |
| ------------ | ----------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| 有効化       | [[ui:storageEnabled]]   | 自動削除を有効にします                                                                                 | 無効                                  |
| グループ化   | [[ui:storageGrouping]]  | 数える単位：[[ui:storagePerChannel]]、[[ui:storagePerPackage]]、[[ui:storageGlobal]]                   | パッケージとチャネル                  |
| 最新N個      | [[ui:storageKeep]]      | 各カウンターで保持するビルド数。1～100 000                                                             | 10                                    |
| チャネル     | [[ui:storageChannels]]  | ラベルごとに`label=N`形式でNを指定。1行に1つ、最大32個。パッケージとチャネルによるグループ化でのみ使用 | `test=10`、`staging=10`、`release=10` |
| 最低経過時間 | [[ui:storageAge]]       | この時間より新しいビルドを保持。単位は時間、0～87 600                                                  | 24                                    |
| 保護ラベル   | [[ui:storageProtected]] | いずれかのラベルを持つビルドは削除しない。カンマ区切りで最大32個                                       | `bse`、`release`                      |
| 間隔         | [[ui:storageInterval]]  | 実行間隔（分）。1～10 080                                                                              | 60                                    |

ラベルは1～64文字で、英字、数字、`_ . : -`を使用できます。

### ビルドの選び方 {#retention-rules}

1. サーバーは、各カウンターのビルドを**公開時刻**の新しい順に並べます。バージョンのSemVer順ではありません。
2. カウンターはグループ化によって決まります。パッケージとチャネルの場合、ビルドが持つ設定済みチャネルラベルごとに、パッケージ（`group/name`）単位で別々に数えます。設定済みラベルを持たないビルドは、そのパッケージの1つの共通カウンターに入り、デフォルトのNを使用します。パッケージ単位の場合、各パッケージに1つのカウンターがあります。リポジトリ全体の場合、すべてのビルドが1つのカウンターを共有します。パッケージ名は大文字と小文字を区別せず、ラベルは区別します。
3. 所属する**いずれか**のカウンターで最新N個に含まれるビルドは保持します。
4. 最低経過時間より新しいビルドは保持します。
5. 保護ラベルを持つビルドは保持します。ラベルは現在の注釈から取得し、注釈がなければアップロードから取得します。保護されたビルドも順位付けに含むため、保持数がNを上回る場合があります。

次のような依存先がある間、ビルドを削除することはありません。

- 外部サービスが参照を保持している。
- 現在または履歴内のファイルパスが使用している。
- 他のビルドが現在または履歴内の添付ファイルとして登録している。
- ステージにプロモートされている。先にステージを削除してください。
- コンテナイメージ、Git LFS、npmのエントリが使用している。

ビルドの削除は論理削除です。一覧から消え、新しいダウンロードは404で失敗します。バイト列は後で[物理クリーンアップ](#physical-cleanup)がディスクから削除します。パッケージのバージョンは予約されたままなので、同じバージョンを別の内容で再公開することはできません。

### ポリシーを安全に有効化する {#retention-enable}

先にプレビューし、その後で有効にしてください。プレビューは、保存済みポリシーが削除する対象を表示するだけで、何も削除しません。

1. 4つの操作権限を持つキーで接続し、対象リポジトリのストレージパネルを開きます。
2. フィールドを設定し、[[ui:storageEnabled]]は無効のまま、[[ui:storageSave]]を選択します。
3. [[ui:storagePreview]]を選択します。保存済みポリシーが1バッチで削除する最大100個のビルドを一覧に表示します。候補がさらにある場合、コンソールにその旨を表示します。
4. 一覧が適切なら、[[ui:storageEnabled]]と確認項目[[ui:storageAcknowledge]]にチェックを入れ、再保存します。これには`artifact.delete`が必要です。

補足：

- プレビューは、ある時点の状態を表示します。ポリシー実行時には、順位と依存関係を再確認します。
- ポリシーはリビジョン付きで保存します。他の人が変更した場合は、再読み込みしてから保存してください。
- [[ui:storageRefresh]]で設定と使用量を再読み込みします。

### 実行の仕組み {#retention-run}

書き込みを行うAPIプロセス（読み取りゲートウェイではありません）が60秒ごとに確認し、実行時刻に達したポリシーを最大20個処理します。1バッチで最大100個のビルドを削除します。候補が残っていれば1分後に次のバッチを開始し、残っていなければ設定した間隔の後に次回実行します。スケジュールはデータベースに保存するため、再起動後も維持します。

API操作[runStoragePolicy](../api/reference/storage#runStoragePolicy)で、1バッチを手動実行することもできます。使用量、プレビュー、イベントの操作も同じ[ストレージAPIリファレンス](../api/reference/storage)にあります。

## 物理クリーンアップ {#physical-cleanup}

人またはポリシーがアーティファクトを削除しても、カタログから除去するだけです。**物理クリーンアップ**は、API、ワーカー、読み取りゲートウェイを停止せずに、バックグラウンドでディスクからバイト列を削除します。また、次の処理も行います。

- 未完了のまま期限切れになったアップロードをキャンセルし、パートを削除します。
- 完了済みアップロードの一時パートを削除します。

削除するビルドを選ぶ処理ではありません。すでに削除またはキャンセルしたものだけを除去します。

**物理クリーンアップはデフォルトで無効で、リポジトリごとに設定します。** 使用するすべてのリポジトリで有効にしてください。有効にするまでは、削除済みファイル、期限切れアップロード、完了済みアップロードのパートがディスクに残り、削除済みファイルもクォータに計上します。

### 設定 {#cleanup-settings}

リポジトリのパネルで[[ui:cleanupTitle]]を開きます。

| 設定     | コンソールのフィールド | 意味                                         | デフォルト | 範囲      |
| -------- | ---------------------- | -------------------------------------------- | ---------- | --------- |
| 有効化   | [[ui:cleanupEnabled]]  | バックグラウンドの物理クリーンアップを有効化 | 無効       |           |
| 猶予期間 | [[ui:cleanupGrace]]    | 削除済みファイルをディスクに残す時間（時間） | 24         | 0～8760   |
| バッチ   | [[ui:cleanupBatch]]    | 1バッチで処理するファイル数                  | 25         | 1～100    |
| 間隔     | [[ui:cleanupInterval]] | バッチ間隔（秒）                             | 60         | 5～86 400 |
| 遅延     | [[ui:cleanupDelay]]    | ファイル間の待ち時間（ミリ秒）               | 50         | 0～1000   |

[[ui:cleanupSave]]を選択すると、設定をすぐに適用します。無効にすると、処理中のファイルが終わった後に停止します。[[ui:cleanupRun]]は、近いうちにバッチを実行するよう要求する操作で、その場で削除するわけではありません。[[ui:cleanupRefresh]]で直近のバッチ結果を確認できます。

猶予期間はごみ箱ではありません。0を設定すると、ファイルは論理削除され、読み取り中の利用者がいなくなった直後に除去される場合があります。Arkvoryは削除済みアーティファクトを復元できません。

### 処理するものとスキップするもの {#cleanup-rules}

- キャンセルまたは削除済みで、猶予期間を過ぎたファイルだけを除去します。参照、ファイルパスの履歴、添付ファイルの履歴のどれにも使用されていないことを再確認します。
- ダウンロード中のファイル、書き込み中のアップロード、実行中のバックアップに必要なファイルは**スキップ**します。次のバッチで再試行します。直近の結果には、処理、スキップ、失敗のファイル数と解放したバイト数を表示します。
- クォータと論理容量は、ファイルをディスクから除去して初めて解放します。
- バッチサイズと遅延で処理を制限し、ディスク負荷を抑えます。厳密なディスクスループットを保証するものではなく、他のリクエストの遅延に影響しないとも保証できません。
- 物理クリーンアップは、データベースごとに1つの書き込みAPIで実行します。書き込みAPIは5秒ごとに、実行時刻に達した1つのリポジトリを確認します。書き込みAPIが稼働していなければ、物理クリーンアップは行いません。
- ゲートウェイとワーカーを含むすべてのArkvoryプロセスを更新してから有効にしてください。クリーンアッププロトコルに対応しない古いプロセスがあると、処理を延期します。

## アーティファクトの削除 {#delete-artifacts}

公開済みアーティファクトを1つずつ手動で削除できます。リポジトリの`artifact.delete`が必要です。

1. [[ui:metadata]]でアーティファクトを開き、[[ui:deletionTitle]]を探します。
2. [[ui:deletionInspect]]を選択します。コンソールに、そのアーティファクトをまだ使用しているものを表示します。削除を妨げるものがあれば、先にその依存関係を除去してください。
3. 確認のためアーティファクトのIDを貼り付け、[[ui:deletionSubmit]]を選択します。

この方法では対象を自分で選ぶため、保護ラベルを確認しません。依存関係は常に確認します。削除後は：

- 一覧と検索からアーティファクトが消えます。新しいダウンロードは404で失敗します。すでに進行中のダウンロードは完了できます。
- パッケージのバージョンは予約されたままです。
- 猶予期間後に[物理クリーンアップ](#physical-cleanup)が除去するまで、バイト列はディスクに残ります。
- コンソールやAPIで取り消すことはできません。

多数のアーティファクト向けに、APIは[previewRetention](../api/reference/storage#previewRetention)と[applyRetention](../api/reference/storage#applyRetention)を提供します。プレビューは、指定日より前に公開した候補と、削除を妨げる理由を一覧表示します。適用時は、渡したIDだけを1回につき最大100個削除し、各IDに`deleted`、`already_deleted`、`protected`、`changed`、`not_eligible`、`not_found`の結果を返します。HTTPステータスだけでなく、すべての結果を確認してください。

## ストレージの診断とイベント {#diagnostics}

[[ui:storageEvents]]には、リポジトリで起きた事象を古い順に、1ページ100件表示します。次のページは[[ui:storageMore]]を選択します。読み取りには`diagnostics.read`が必要です。API操作は[getStorageEvents](../api/reference/storage#getStorageEvents)で、レベル（`info`、`warning`、`error`）で絞り込めます。

| イベント                                                                                              | レベル                   | 意味                                                                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `storage.policy_updated`                                                                              | info                     | 保持ポリシーを保存した                                                                                       |
| `retention.completed`                                                                                 | info                     | バッチがビルドを削除した。イベントに件数を含む                                                               |
| `retention.failed`                                                                                    | error                    | 許可に使用したキーの取り消しなどにより、自動削除を停止した                                                   |
| `cleanup.configured`                                                                                  | info                     | 物理クリーンアップ設定を保存した                                                                             |
| `storage.placement_updated`                                                                           | info                     | 配置ポリシーを保存した                                                                                       |
| `cleanup.completed`                                                                                   | infoまたはerror          | クリーンアップバッチがファイルを処理、スキップ、または処理に失敗した。件数と解放したバイト数を含む           |
| `capacity.normal`、`capacity.warning`、`capacity.critical`、`capacity.exceeded`、`capacity.unlimited` | info、warningまたはerror | クォータの状態が変わった                                                                                     |
| HTTPエラーコード                                                                                      | warningまたはerror       | 管理対象キーによる、このリポジトリへのリクエストが失敗した。イベントにリクエストID、ルート、ステータスを保持 |

履歴には上限があり、リポジトリごとに1000件、全体で20 000件です。古いものから破棄します。これはベストエフォートの診断情報であり、配信を保証するログではありません。必要な情報は間に合ううちにエクスポートし、長期間の証跡にはサーバーログを使用してください。[監視](./monitoring)を参照してください。

パネルには、公開済みバイト数、未完了アップロード、クリーンアップ待ちのバイト数、クォータに対する合計使用量も表示します。API操作は[getStorageUsage](../api/reference/storage#getStorageUsage)です。

## ディスクが満杯になった場合 {#disk-full}

兆候として、アップロードがHTTP 507と理由`storage_full`で失敗する、`GET /health/ready`が`writable: false`を示す、OSが空き容量不足を報告する、などがあります。ダウンロードは引き続き利用できます。容量を解放した後、クライアントはアップロードを再開できます。

1. **原因を調べます。** ストレージ、データベース、保管庫の各ボリュームの空き容量を確認します。ストレージパネルの使用量と比較してください。「クリーンアップ待ち」が大きければ、削除済みデータがまだディスクに残っています。「未完了アップロード」が大きければ、放置されたアップロードがあります。
2. **物理クリーンアップを実行します。** 無効であれば、すべてのリポジトリで有効にします。削除済みファイルを直ちに除去してよければ0など、短い猶予期間を設定します。[[ui:cleanupRun]]を選択します。完了済みアップロードの一時パートと期限切れアップロードも削除します。バッチの処理を待ち、直近の結果を確認してください。使用中のファイルはスキップするため、繰り返し実行します。
3. **不要なものを削除します。** 保持ポリシーを適用するか、アーティファクトを削除します。物理クリーンアップがバイト列を除去して初めて、容量が空きます。
4. **容量を増やします。** ボリュームやディスクを拡張します。保管庫や他のデータが同じボリュームを共有していれば、別の場所に移します。[ボリュームを追加](#volumes)して、新規アップロードをそこに配置することもできます。
5. **復旧を確認します。** 空き容量ができると`writable`が`true`に戻り、アップロードが再び機能します。

`blobs/`、`staging/`、`parts/`内のファイルを手動で削除しないでください。データベースとディスクの対応関係が壊れます。同じボリューム上のログとデータベースに対して予備領域が小さすぎる場合は、`ARKVORY_STORAGE_RESERVE_BYTES`を増やしてください。

アップロードの失敗理由が`storage_quota`または`catalog_limit`の場合、問題はディスクではありません。クォータか全体の制限を引き上げるか、データを削除してください。

## 制限 {#limits}

- 保持ポリシーは登録済みUPackビルドだけを処理します。他のファイルは削除しません。
- 保持の順序は公開時刻であり、バージョン番号ではありません。
- ストレージ、クォータ、物理クリーンアップには、明示的なサービスキーの操作権限が必要です。パスワードアカウントと回復キーはこれらを持ちません。
- 物理クリーンアップはデフォルトで無効で、リポジトリごとに設定します。
- 削除済みアーティファクトは復元できません。バックアップからデータを復元してください。[バックアップ](./backups)を参照してください。
- ミラーリポジトリではストレージポリシーを実行しません。[ミラー](./mirrors)を参照してください。
- ストレージはローカルファイルシステムでなければなりません。ネットワーク共有には対応しません。追加の[ボリューム](#volumes)もローカルディレクトリです。保存済みファイルをボリューム間で移動できるのは、サーバー上のコマンド[`arkvory storage rehome`](#rehome)だけで、APIからは移動できません。
- Windowsでは、各ファイルをディスクに同期しますが、公開に使用するディレクトリエントリは同期できません。WindowsのNode.jsはディレクトリの同期に対応していないためです。アップロード直後の停電で、公開済みファイルがディスクから失われる場合があります。UPSを使用し、[バックアップ](./backups)または[ミラー](./mirrors)を保持してください。Linuxではディレクトリエントリも同期します。

署名付きストレージモジュールは、オフラインの`scrub`でも読み取り専用モードで利用できます。インストール済みモジュールとその設定を残してください。`storage rehome`は、設定済みのモジュールストレージから通常のストレージへの移動を計画できます。ワーカーはコピー前に移動先を確認します。インストール済みモジュールの計画は、書き込みAPIのものと一致する必要があります。`scrub`の前にAPIとワーカーを停止してください。

モジュールの復旧中は、書き込みを利用できなくても既存データを読み取れる場合があります。使用量が不明な場合は`busy`を返し、空きクォータとして扱うことはありません。データの書き込みや削除を行う操作は、復旧を待ってから開始してください。復旧に失敗した場合は調査が必要であり、モジュール起動タイムアウトを延長して解決する問題ではありません。
