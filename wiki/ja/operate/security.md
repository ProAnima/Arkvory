# セキュリティ

このページは、サーバーを運用する管理者向けです。新しいインストールを保護する手順から始め、各保護機能を詳しく説明します。

プロジェクトでは、脅威モデルと外部のセキュリティレビューは、まだ未完了としています。サーバーをインターネット全体に公開しないでください。クライアントのネットワークからだけ到達できるようにしてください。

## 新しいサーバーの保護 {#checklist}

1. HTTPSが機能するまで、デフォルトの待ち受けアドレス`127.0.0.1`を維持します。[ネットワークとHTTPS](#network)を参照してください。
2. HTTPSを有効にし、クライアントのネットワークにHTTPSポートだけを開放します。データベースのポートは開放しないでください。
3. 管理者ごとに個人のアカウントを作成します。回復キーは緊急時のために保管してください。[回復キー](../install/index#recovery-key)を参照してください。
4. 各ツールやCIシステムに、それぞれ最小限の権限を持つキー付きのサービスアカウントを割り当てます。[キーとトークン](#keys)を参照してください。
5. 自己登録は無効のままにします。デフォルトで無効です。
6. Arkvoryの前段にリバースプロキシを置く場合は、`ARKVORY_TRUSTED_PROXIES`を設定します。[サインインの制限](#sign-in-limits)を参照してください。
7. バックアップ保管庫を暗号化し（デフォルト）、回復キットをサーバー外に保管します。保管庫自体も、サービスアカウントとバックアップ管理者だけが読める暗号化ボリュームに配置してください。[バックアップ](./backups#encryption)を参照してください。
8. 秘密情報ファイルのコピーをサーバー外に保管します。[秘密情報のバックアップ](#secret-backups)を参照してください。
9. メトリクスとアラートを接続します。[監視](./monitoring)を参照してください。

## ネットワークとHTTPS {#network}

サーバーはデフォルトで`127.0.0.1:8080`で待ち受けます。ネイティブインストールでは、HTTPSを設定した後に別のアドレスで待ち受けることができます。

```bash
sudo arkvory configure --root /opt/proanima-arkvory --tls-cert /etc/arkvory/fullchain.pem --tls-key /etc/arkvory/privkey.pem --listen-host 0.0.0.0
```

このコマンドはファイルを確認してサービスを再起動し、サービスが起動しなければ以前の設定に戻します。完全な手順と、リバースプロキシが必要なDocker Composeについては、[HTTPSとリバースプロキシ](../install/https)を参照してください。

- 証明書と鍵は、読み取り可能で、互いに一致し、期限切れでない必要があります。そうでなければAPIは起動せず、平文HTTPにフォールバックすることもありません。
- TLSの最小バージョンは1.2です。1.3を必須にするには`ARKVORY_TLS_MIN_VERSION=TLSv1.3`を設定します。クライアント証明書には対応しません。
- サーバー自身がHTTPSを提供する場合、`Strict-Transport-Security: max-age=31536000`を返します。プロキシがTLSを終端する場合、このヘッダーはプロキシが管理します。
- 証明書ファイルは、再起動せずに300秒ごと（`ARKVORY_TLS_RELOAD_SECONDS`）に再読み込みします。新しい接続は新しい証明書を使用します。ファイルを読み取れない場合は動作中の証明書を維持し、`tls.reload_failed`を記録します。有効期限までの最後の14日間は、毎日`tls.expiring`を記録します。
- ループバック以外のアドレスで、TLSも信頼済みプロキシも使用しない場合、起動時に`http.plaintext_exposed`を警告します。クライアントに接続を許可する前に修正してください。
- Arkvoryは、ミラー、ハブ、コマンドラインクライアントのいずれでも、受信した証明書の検証を無効にしません。独自の認証局は、ミラー用の`--mirror-ca-file`で追加してください。

リバースプロキシの背後では、APIをループバックで待ち受けさせます。プロキシはファイル全体をバッファーせず、本文をストリーミングする必要があります。ダウンロードリンクはクエリ文字列に秘密情報を含むため、プロキシでクエリ文字列を記録しないでください。

## サーバー上の秘密情報 {#secrets}

インストーラーは、インストールルートに次のファイルを作成します。インストーラーが設定したアクセス権を維持してください。

| ファイル                     | 内容                                                        | アクセス                                                                           |
| ---------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `config/bootstrap-token.txt` | 管理者権限を持つ回復キー                                    | Linux：rootのみ（モード0600）。Windows：SYSTEMとAdministrators                     |
| `config/keys.json`           | 回復キーとヘルスキーのSHA-256ハッシュ。キー自体は含まない   | Linux：rootが書き込み、サービスグループが読み取り（0640）。Windows：ルートから継承 |
| `config/health-token.txt`    | リポジトリ権限を持たないヘルスキー`deployment-health`       | Linux：rootのみ。Compose：コンテナ内で読み取り可能                                 |
| `config/runtime.json`        | パスワード付きデータベースURLを含む、サーバーのすべての設定 | Linux：rootが書き込み、サービスグループが読み取り（0640）。Windows：ルートから継承 |
| `config/postgres.env`        | Composeインストールのデータベースパスワード                 | rootのみ、またはSYSTEMとAdministrators                                             |
| `github-token.txt`           | 任意で設定する更新用GitHubトークン                          | rootのみ、またはSYSTEMとAdministrators                                             |
| `config/mirrors/*.token`     | ミラー元サーバーの読み取りキー                              | サービスアカウント                                                                 |
| TLS秘密鍵                    | 証明書の秘密鍵                                              | 配置先は自分で選択。サービスアカウントだけに許可                                   |

Windowsのルートは、SYSTEMとAdministratorsにフルコントロールを付与します。サービスアカウント`LocalService`はルートを読み取り、`data\`、`logs\`、更新受信箱だけに書き込みます。データベースは別のアカウントで実行するため、APIはデータベースファイルを読み取れません。

すべての秘密情報に適用する規則：

- ファイルまたは環境変数で渡し、コマンド引数には指定しないでください。引数はプロセス一覧に表示されます。
- 回復キーをクライアント、CIシステム、スクリプトにコピーしないでください。日常作業にはアカウントとサービスキーを作成してください。
- サーバーは、キー、パスワード、トークン、`Authorization`ヘッダー、クエリ文字列をログに書き込みません。[監視](./monitoring#never-logged)を参照してください。
- インストーラーのコマンド出力では、データベースURL、キー、長い秘密情報をマスクします。

回復キーを交換するには、`bootstrap-token.txt`と`config/keys.json`内のそのハッシュを一緒に変更し、`deployment-health`のエントリを維持して、APIとワーカーを再起動します。[設定](../install/configuration)を参照してください。

## パスワードとサインインの制限 {#sign-in-limits}

パスワードは12～128文字で、ソルト付きハッシュ（scrypt）としてのみ保存します。サインインの有効期間は12時間です。1アカウントにつき有効なセッションは最大32個で、新しくサインインすると最古のセッションを終了します。パスワードの変更やリセットでは、すべてのセッションを終了し、そのアカウントの個人用トークンをすべて取り消します。

名前を知るだけで所有者を締め出せる恒久的なロックアウトは行いません。複数の層で攻撃を遅くします。

| 層                       | 制限                                                                                                                                                                               |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| アドレスごとのサインイン | 一度に10回、その後は15秒ごとに1回補充。正しいパスワードなら試行枠を返却。IPv6は/64ネットワーク単位で計上                                                                           |
| アドレスごとの自己登録   | 3回、その後は20分ごとに1回。プロセス全体では20回、その後は3分ごとに1回                                                                                                             |
| アカウントごと           | パスワードを間違えるたびに負債を1加算。負債は6秒ごとに1減少。20を超えると、誤ったパスワードごとに、1秒から最大2分まで倍増する待ち時間を追加。待機中は正しいパスワードでも429を返す |
| 同時サインインリクエスト | 最大16件。本文は10秒以内に到着する必要がある                                                                                                                                       |
| パスワードの検証         | 匿名用と管理者用に別のキューを使い、大量のサインインで管理者を妨げない                                                                                                             |

応答は、理由`login_attempts`と`Retry-After`ヘッダーを伴う429 `rate_limited`です。アドレスのカウンターはプロセス内にあり、再起動でリセットします。アカウントの負債はデータベースに保存します。管理者によるパスワードリセットで負債を消去します。

リバースプロキシの背後では、`ARKVORY_TRUSTED_PROXIES`にプロキシのアドレスを設定します（IPまたはCIDR、最大32個）。`X-Forwarded-For`でクライアントのアドレスを指定できるのは、これらのアドレスだけです。未設定では、すべてのクライアントがプロキシのアドレスを共有するため、数回のサインイン失敗で全員がしばらく締め出されます。

## キー、トークン、有効期限 {#keys}

| 認証情報               | 有効期間                                                                            | ローテーション                                                                                     |
| ---------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| サインインセッション   | 12時間                                                                              | 再度サインイン                                                                                     |
| 個人用アクセストークン | デフォルト90日、最大365日。スコープは`read`または`read-write`。管理者権限は持たない | [[ui:personalAccessTokens]]で新しいトークンを作成し、古いものを取り消す                            |
| サービスキー           | デフォルト90日、最大365日。発行済みでも未有効化のキーは15分後に期限切れ             | [[ui:keyRotate]]で新しいキーを発行。古いキーは最長でさらに24時間有効。[[ui:keyRevoke]]で直ちに停止 |
| ダウンロードリンク     | コンソールでは1時間                                                                 | 新しいリンクを作成                                                                                 |
| 回復キーとヘルスキー   | 無期限                                                                              | 手動で交換。[サーバー上の秘密情報](#secrets)を参照                                                 |

個人用トークンの作成とパスワードの変更は、サインイン済みセッションからだけ行います。トークンからトークンを作成することはできません。個人用トークンは、所有者にかかわらず管理者権限を持ちません。

ツールには最小限の権限を付与してください。

- [[ui:services]]で利用者ごとに1つのサービスアカウントを作成し、[[ui:servicePolicy]]で必要なリポジトリと操作だけを正確に指定します。[[ui:bindingRead]]と[[ui:bindingPublish]]で典型的な操作の組み合わせを設定できます。
- アカウントと許可の作成には、回復キーまたは委任の別の権限が必要です。所有者は[[ui:delegations]]で、限られた権限をオペレーターに渡せます。委任されたキーの有効期限は、発行元キーの有効期限を超えません。
- メトリクス収集には、最小限の権限を持つ専用キーを付与します。
- 許可を取り消すと有効化待ちのキーをブロックしますが、有効なキーを取り消すことはありません。それらは自分で取り消すか無効化してください。開始済みのダウンロードは取り消し後も継続します。
- 権限の変更は次のリクエストから適用します。サーバーは、一覧、メタデータ、ファイルのバイト列を含め、各リクエストでアクセスを再確認します。

## 監査ログ {#audit}

| ジャーナル                   | 記録内容                                                                                                                                               | 読み取り先                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| セキュリティジャーナル       | サインインと失敗、登録、アカウント、グループ、許可、パスワード、個人用トークンの変更。操作者、認証情報の種類、対象、結果、クライアントのアドレスを含む | `GET /api/v1/security/audit`。管理者セッションまたは回復キーが必要  |
| カタログ監査                 | リポジトリ内のアーティファクト、パス、注釈、ステージの変更                                                                                             | `GET /api/v1/repositories/{repository}/audit`。監査を読む権限が必要 |
| サービスアカウントの操作履歴 | サービスアカウントの作成、変更、キーの発行と取り消し                                                                                                   | コンソールの[[ui:serviceAudit]]                                     |
| プロセスログ                 | リクエストごとに、`principal`と`clientIp`を含む`http.access`を1行                                                                                      | [監視](./monitoring#logs)を参照                                     |

セキュリティジャーナルは追記専用で、データベースは行の変更や削除を拒否します。サーバーは365日間、最大1,000,000行を保持し、古い行をバッチで削除します。レート制限で拒否したリクエストは記録しないため、大量のリクエストでテーブルが増えることはありません。より長い履歴が必要な場合は、独自のイベントストアにエクスポートしてください。

```bash
curl -fsS -H "Authorization: Bearer $ARKVORY_KEY" "https://arkvory.example/api/v1/security/audit?limit=100"
```

古い行を読むには、最後のIDを`after`パラメーターに指定します。

## コンソールとブラウザー {#console-headers}

サーバーは、コンソールの応答に次のヘッダーを設定します。

| ヘッダー                  | 値                                                                                                                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Content-Security-Policy` | `default-src 'none'; img-src 'self' blob:; script-src 'self'; style-src 'self'; connect-src 'self'; worker-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` |
| `Referrer-Policy`         | `no-referrer`                                                                                                                                                                       |
| `X-Content-Type-Options`  | `nosniff`                                                                                                                                                                           |
| `Cache-Control`           | `private, no-store`                                                                                                                                                                 |
| `X-Request-Id`            | 応答のリクエストID                                                                                                                                                                  |

すべてのAPI応答にも、`X-Content-Type-Options`、`Cache-Control`、`X-Request-Id`が付きます。CSPは、インラインスクリプト、外部スクリプト、フレームへの埋め込み、他のホストへの接続を許可しません。`blob:`の画像は、フィードバックメッセージに追加するスクリーンショットです。

サーバーはCookieを設定しません。コンソールは、キーやセッショントークンをブラウザータブのメモリ内にだけ保持します。ブラウザーに保存するのは、テーマと言語の選択、およびダウンロードキューの非公開ファイルだけです。別のアドレスのブラウザーページからAPIを呼び出すことはできません。`ARKVORY_CORS_ORIGINS`はデフォルトで空です。外部コンソール用の正確なオリジンを最大16個指定でき、HTTPS、またはループバック上のHTTPを使用します。すべてのリクエストにキーが必要なため、許可されたオリジンに追加の権限が付くことはありません。

## 更新の署名 {#update-signing}

各リリースには、アーカイブとインストーラーのSHA-256を記載したマニフェスト`arkvory-release.json`と、署名`arkvory-release.json.sig`があります。署名はminisign形式のEd25519署名です。更新サービスはコード内に公開鍵を保持します。

- ハブまたはGitHubからのリリースは、署名が組み込み鍵と一致し、SHA-256がマニフェストと一致する場合だけインストールします。署名の不一致はエラーとなり、別の取得元を探すことはありません。
- 署名秘密鍵は保守担当者が保管し、サーバーには置きません。鍵のローテーションのため、リリースに新旧の公開鍵を含めることがあります。
- `--artifact`で渡すローカルフォルダーは、自分の判断で選びます。署名ファイルがあれば検証します。
- グラフィカルインストーラーと`.deb`、`.rpm`パッケージには、まだ発行元証明書の署名がありません。Windowsでは発行元が不明と表示されます。[GitHub Releases](https://github.com/ProAnima/Arkvory/releases)からだけダウンロードし、`release-checksums.json`とSHA-256を比較してください。
- データベーススキーマを変更するリリースは、サーバーが新しいバックアップを作成して検証した後にだけインストールします。[更新](../install/updates)を参照してください。

## Arkvoryが読み込むコード {#code-loading}

サービス、`arkvory`、インストーラー、`arkvoryctl`、Remote Setupを含むすべてのArkvoryプロセスは、自身のリリースディレクトリとNode.jsの組み込みモジュールからだけJavaScriptを読み込みます。通常のNode.jsは、各親ディレクトリの`node_modules`フォルダー、アカウントのホームディレクトリ、`NODE_PATH`からもライブラリを探します。Arkvoryはこれらをすべて拒否するため、他の人がそこに配置したライブラリが実行されることはありません。

- サービス定義は`NODE_PATH`を消去します。
- Windowsでは、デフォルトルートの上位にある`%ProgramData%\ProAnima`を変更できるのは管理者だけです。`%ProgramData%`自体には、すべてのユーザーがフォルダーを作成できます。セットアップは、Arkvoryのインストール時やサービス修復時にアクセス権を変更します。別の場所のルートは、その親のアクセス権を維持します。親フォルダーを管理者だけが変更できる場所を選んでください。
- 拒否したライブラリは、`Cannot find module '…': module resolution is confined to the release directory`とファイルパスを表示して終了します。Arkvoryはそのファイルを必要としていません。誰が配置したか調べてください。

## ProAnimaStudioハブへの送信内容 {#hub}

更新はProAnimaStudioのハブ（`https://hub.proanima.net`）で承認されます。次の場合にサーバーが接続します。

| データ            | タイミング                                       | 内容                                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 更新の確認        | 6時間ごと                                        | 現在のバージョン、OS、アーキテクチャがアドレスの一部となる。統計が有効なら、ランダムなインストールIDを`X-Install-Id`ヘッダーで送信                                                                         |
| イベント`updated` | 統計が有効で、更新をインストールした後           | バージョンとインストールID                                                                                                                                                                                 |
| フィードバック    | ユーザーがコンソールのフォームを送信したときだけ | テキスト、任意の返信用メールアドレス、最大6枚のスクリーンショット、ブラウザーページのログ。管理者はAPIログの末尾1.5 MiBとシステム概要を追加可能。送信前にすべてをフォームで確認できる（[[ui:reportShow]]） |

インストールIDは、`config/install-id`に保存するランダムなUUIDです。名前、住所、コンテンツは含みません。プロジェクトでは、ハブにIPアドレス、人名、ファイル内容を保存しないとしています。統計が無効ならIDを送信せず、ハブは全インストールに公開されたバージョンだけを提示します。システム概要には、バージョン、スキーマ番号、更新とミラーの状態を含み、アドレスと秘密情報は含みません。APIログにも秘密情報は含みません。

無効にするには：

```bash
sudo arkvory configure --root /opt/proanima-arkvory --statistics off
sudo arkvory configure --root /opt/proanima-arkvory --hub-off
```

- `--statistics off`は、インストールIDと`updated`イベントの送信を停止します。コンソールにも同じ切り替えがあり、[[ui:updates]]の[[ui:updateStatistics]]で設定します。
- `--hub-off`はハブへのすべての接続を停止します。以後、更新はGitHubからだけ取得し、サービスの次回再起動後にコンソールのフィードバックを無効にします。代わりに、コンソールの連絡先アドレスをユーザーに表示します。
- `--hub-url https://hub.example`は、別のハブを指定します。HTTPS、またはループバック上のHTTPだけを受け付けます。

自動インストールが無効でも、6時間ごとの確認を実行します。インターネットに接続できないサーバーは、リリースのローカルコピーからインストールします。[更新](../install/updates)を参照してください。

## 秘密情報のバックアップ {#secret-backups}

バックアップ保管庫には、カタログ、パスワードハッシュ、すべての公開済みファイルを保存します。Arkvoryは作成時に保管庫を暗号化し、回復キットはサーバー外に保管する必要があります（[バックアップ](./backups#encryption)を参照）。保管庫には設定ファイルを含みません。次のファイルの2つ目のコピーを、サーバー外の暗号化された場所に保管してください。

- バックアップ保管庫の回復キット。サーバーと鍵ファイルを失った場合にバックアップを読む唯一の方法です。2つの場所に2部保管してください。
- `config/keys.json`と`config/bootstrap-token.txt`（回復キー）。
- `config/runtime.json`。
- TLS証明書と秘密鍵。
- ミラーのキーを含む`config/mirrors/`。
- 使用している場合は`config/hub.json`と`github-token.txt`。

復元は、独自の設定とキーファイルを持つ新しいインスタンスを作成します。復元後はセッションがなくなり、個人用トークンとサービスキーを取り消し、物理クリーンアップと保持ポリシーを無効にします。新しいキーを発行し、意図を確認してポリシーを再び有効にしてください。パスワードはスナップショット時点の状態に戻ります。これらのファイルのコピーは、すべて秘密情報として扱ってください。[バックアップ](./backups)を参照してください。
