# モジュール

モジュールパッケージはArkvoryに機能を追加します。Arkvoryは、署名を検証できるパッケージだけをインストールします。このページのコマンドは、インストール先ホストで、Linuxではroot、Windowsでは管理者として実行します。コンソールとHTTP APIからは、モジュールのインストールや鍵の信頼設定はできません。そのため、コンソールの管理者アカウントが盗まれても、サーバー上でコードを実行することはできません。

サービスは起動するたびにインストール済みモジュールを再検証して読み込みます。モジュールは、有効化して初めて動作します。

## Arkvory Pro {#pro}

Arkvory Proは、無料のArkvoryコアに追加できる、ProAnimaStudioの有料署名付きモジュール群です。Pro 0.1.0は、Windows/Linux x64のArkvory 0.6.3に対応します。モジュールパッケージとライセンスはProAnimaStudioから入手し、コアとは別にインストールします。[インストール](#install)と[ライセンス](licenses)を参照してください。

- **重複排除**は、共有チャンクを1回だけ保存し、複数のオブジェクトで再利用します。共有カタログが、公開、読み取り、バックアップとガベージコレクションを調整します。
- **差分転送**は、互換クライアントがすでに持つコンテンツを再利用し、不足するデータやパッチを転送します。バンドルには、サーバーのストレージ・転送モジュールと、差分クライアントモジュールを含みます。削減量はデータとクライアントによって異なり、通常のHTTPダウンロードが自動的に差分転送になるわけではありません。
- **ライセンス管理**は、有料機能の書き込みと最適化を制御します。ライセンスが期限切れまたは利用不可でも、既存データは読み取れます。新規アップロードはコアのストレージと通常の転送にフォールバックします。Proのクォータは、受け付け済みの未完了アップロードを含む論理的なProデータ量を数え、重複排除による割り引きは行いません。ライセンスのupdatesUntilは、新しいモジュールビルドを利用できる範囲を制限します。

モジュールはサービス起動時に読み込みます。Docker Composeのインストールでは読み込みません。アップグレード前にメタデータとモジュールデータをバックアップしてください。共有カタログを初めて導入するときは、古いAPIとワーカーの書き込みプロセスを停止してください。新旧の書き込みプロセスの混在には対応しません。データとライセンス状態を一緒に復元し、復旧を待ち、新しいProアップロードを検証してから通常の書き込みを再開してください。

大規模なカタログの復旧には時間がかかる場合があります。受け入れ検証環境では、共有カタログを復元済みの400万チャンクが、再起動なしで32分43秒後に書き込み可能になりました。これは復元時間の保証でも、4 TBのスループット測定でもありません。1台の物理ホスト上でのHA受け入れ検証は、現地でのフェンシングや障害ドメインの確認を代替しません。Proによってコアのライセンス条件が変わることはありません。

## モジュールの機能とサードパーティープラグイン {#module-capabilities}

署名付きのProAnimaStudioモジュールは、ストレージ、転送プロトコル、HTTPルートを追加できます。役割に応じて、バックグラウンド処理、制限付きの計算、調整されたデータクリーンアップのサービスを利用します。無料モジュールには有料機能ライセンスは不要で、有料モジュールは必要なライセンスを宣言します。各パッケージは、コアの拡張APIに適合し、署名と整合性の検証に合格する必要があります。

このリリースでは、サードパーティープラグインのインストールと実行は利用できません。[信頼する作者の鍵](#trust)は管理できますが、鍵を追加してもプラグインをインストールできるようにはなりません。モジュールインターフェースを、任意のコードを安全に隔離するサンドボックスと見なさないでください。

## パッケージのインストール {#install}

1. パッケージファイル`arkvory-module-<id>-<version>.tgz`をホストにコピーします。
2. 検証し、利用条件を読みます。

   ```bash
   sudo arkvory module install /root/arkvory-module-sample-1.0.0.tgz --root /opt/proanima-arkvory
   ```

   コマンドは、モジュール、役割、保持するデータ、署名鍵、パッケージのSHA-256を示した後、モジュールの利用条件を表示します。この時点では何も変更しません。

3. インストールします。

   ```bash
   sudo arkvory module install /root/arkvory-module-sample-1.0.0.tgz --root /opt/proanima-arkvory --yes
   ```

次の場合、Arkvoryはパッケージを拒否します。

| 理由                                                                                         | メッセージのコード                                             |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| ProAnimaStudioのモジュール鍵による署名ではない、またはマニフェストが変更されている           | `unknown_key`、`wrong_key_class`、`signature_invalid`          |
| ファイルが欠けている、変更されている、またはマニフェストに記載されていない                   | `file_missing`、`file_mismatch`、`file_unlisted`               |
| アーカイブにリンク、デバイス、パッケージ外のパス、または大文字と小文字だけが異なる名前がある | `link_entry`、`special_entry`、`unsafe_path`、`case_collision` |
| アーカイブにネイティブアドオン（`.node`）がある                                              | `native_addon`                                                 |
| モジュールが別のArkvoryバージョンを必要とする                                                | `module_incompatible`                                          |
| ProAnimaStudioがこのバージョンを取り消した                                                   | `module_revoked`。置き換え先バージョンも表示                   |
| 有効な失効リストがない（下記参照）                                                           | `stale_revocations`                                            |

上限はパッケージごとに1 GiB、ファイルごとに256 MiB、4096ファイルです。これより大きいパッケージは、データを読み取る前に拒否します。

同じバイト列の同じバージョンがすでにインストールされていれば、そのままにします。同じバージョンでもバイト列が異なる場合は拒否します。

## モジュールの有効化と読み込み {#load}

インストール済みモジュールは、有効化するまで無効のままです。サービスは起動時にだけモジュールを読み込みます。

1. モジュールファイル（`ARKVORY_MODULES_FILE`。[環境変数](../reference/environment#core)を参照）にモジュールを追加します。モジュール設定は`config`に記述します。

   ```json
   { "format": 1, "modules": { "sample": { "enabled": true } } }
   ```

2. モジュールがファイルを保持する場合、`resources`でデータディレクトリのサイズを承認します。例えば`enabled`の隣に`"resources": { "dataMiB": 512, "dataFiles": 10000 }`を指定します。これがパッケージの要求するサイズに代わります。[モジュールのデータディレクトリ](#data)を参照してください。
3. [変更の適用](../install/configuration#apply-change)に従ってサービスを再起動します。
4. グローバル管理者としてモジュールを確認します。APIと各読み取りゲートウェイで、`GET /api/v1/system/modules`がそのモジュールを`running: true`、`health.status`が`ok`として表示することを確認してください。

署名付きモジュールは、宣言された役割に従い、API、読み取りゲートウェイ、ワーカー、バックアップエージェントで実行します。各プロセスは、その役割で利用でき、`uses`に宣言したサービスだけをモジュールに渡します。ルートのプレフィックスには、引き続き`routes`サービスが必要です（`routes_unsupported`）。Docker Composeのインストールでは、まだモジュールを読み込みません。

モジュールストレージは、`<module>.<name>`という名前のインスタンスを登録します。配置ポリシーは、新規アップロード先にこれらを選択できます。インスタンスが書き込みを受け付けなくなると、新規アップロードは`default`にフォールバックします。コアは、保存済みパートから構成するオブジェクトを公開する前に、バイト列全体を検証します。コンテンツの読み取り、バックアップの固定、または取得バリアがインストールを保護している間、モジュールデータのクリーンアップは待機します。計算は制限付きのスレッドで実行します。バックグラウンドの購読は、ハンドラーが成功して初めてイベントを確認済みにし、失敗後に再配信する場合があります。

サービスがモジュールのコードをインポートする前に、パッケージを再検証します。

1. インストールディレクトリ、`modules/`、モジュールセット、失効リストとそのディレクトリを変更できるのは、root（WindowsではSYSTEMとAdministrators）またはインストールディレクトリの所有者だけです。インストール時にこの設定を行います。他のアカウントが変更できるファイルや、パッケージ内のリンクは拒否します（`access_unsafe`、`access_link`）。
2. `module install`と同じように、署名、すべてのファイル、Arkvoryのバージョンを確認します。
3. 失効リストを確認します。取り消されたバージョンは読み込みません。リストの期限切れや欠落だけではモジュールを停止しません。

確認に失敗したモジュールは読み込まず、他のモジュールとArkvoryは動作を続けます。`GET /api/v1/system/modules`は、そのモジュールを`running: false`で表示します。

| `health.status` | 意味                                                         | コード                                                                                                       |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `failed`        | パッケージを拒否した、またはコードの読み込み・起動に失敗した | `file_mismatch`、`unknown_key`、`module_incompatible`、`access_unsafe`、`config_invalid`、`start_failed`など |
| `revoked`       | ProAnimaStudioがこのバージョンを取り消した                   | 失効リストにある理由                                                                                         |
| `unavailable`   | ホストにパッケージディレクトリがない                         | `module_unavailable`                                                                                         |

モジュールの失敗でArkvoryが準備未完了になる（`/health/ready`が503と`module_failed`を返す）のは、他の有効なモジュールがそれを必要とする場合だけです。公開済みファイルのバイト列を保存するモジュール（データ`layout`）ではそうなりません。Arkvoryはそのデータの提供を続け、新規アップロードはモジュールではなく自身のストレージに書き込みます。ログには`module.refused`と`module.failed`を、`errorCode`のコードとともに記録します。

変更または欠落したパッケージを修復するには、再インストールしてください。インストール内のすべてのサービスが、有効・無効を問わず同じモジュールを参照する必要があります。異なるモジュール構成の読み取りゲートウェイやワーカーは準備完了になりません（`module_plan_mismatch`）。各読み取りゲートウェイのホストにも同じパッケージをインストールしてください。

### モジュールのデータディレクトリ {#data}

独自の索引、キャッシュ、状態を保持するモジュールには、`default`のストレージディレクトリ内の`module-data/<id>/`として、データボリューム上のディレクトリを割り当てます。`data`部分はバックアップの対象で、`cache`部分は対象外です。Arkvoryは、両方の合計について、すべての書き込みを承認済みのMiB数とファイル数に計上します。上限を超える書き込みは拒否し（`module_quota_exceeded`）、モジュールは稼働を続けます。承認済みのサイズがなければ読み取りだけが可能です。[ボリュームの予備領域](./storage#disk)も適用します。読み取りゲートウェイでは同じファイルを読み取れますが、変更できません。

論理バックアップは、インストール済みモジュールのバックアップ用の役割を通じて、公開済みオブジェクトのバイト列を取得します。モジュールディレクトリ、キャッシュ、内部の調整状態をファイルシステムイメージとしてコピーするものではありません。取得が終わるまで、ソースのモジュールをインストール済みかつ読み取り可能な状態に保ってください。[--to-default-storage](backups#restore-default-storage)を指定した復元では、元のモジュールや有料ライセンスなしで、オブジェクトを通常のコアblobとして復旧できます。その論理サイズ全体の容量を確保してください。インストールの秘密情報は別途保全し、有料機能の書き込みを再開する前にライセンスの復旧手順に従ってください。モジュールを削除してもデータディレクトリは削除しません。公開済みオブジェクトがまだ参照するファイルを削除しないでください。

拡張API 0.7.0にアップグレードする前に、モジュールデータを書き込む古いAPIとワーカーのすべてのプロセスを停止してください。新しい書き込みプロセスはすべて、インストールのPostgreSQLコーディネーターを通じてクォータの計上を共有します。一時ファイルもクォータに含みます。新旧の書き込みプロセスの混在には対応しません。クラッシュ後、Arkvoryは必要に応じて計上情報を再構築し、新しいプロトコルの一時ディレクトリを、前の所有者のデータベースロックを取得した後に限って回収します。従来の一時ファイルは自動削除せず、引き続きクォータに含めます。書き込みプロセスを停止して別途確認してください。バックアッププロセスは読み取り専用です。

## モジュールのルート {#routes}

モジュールは、自身のプレフィックス`/api/ext/<id>/v<major>/`（例：`/api/ext/sample/v1/`）の下にHTTPルートを追加できます。Arkvoryは、モジュールのコードを実行する前に、すべてのリクエストを確認します。

| 確認           | `/api/v1`と同じ規則                                                                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 認証情報       | 同じキー、セッション、トークンを使用。ルートの利用者は、すべてのサインイン済み呼び出し元、またはグローバル管理者のみ                                                          |
| 権限           | ルートのパス内のリポジトリに対し、そのルートが指定する`content.read`や`upload.create`などの権限。サービスキーにはその権限が、アカウントには読み取りまたは書き込みの付与が必要 |
| リクエスト本文 | ルートのサイズ上限と、サーバーのアップロード制限、期限、帯域幅                                                                                                                |
| ファイル       | Arkvory自身が送信。ETag、Range、`If-Range`、304、ダウンロードキュー、ダウンロード帯域幅を適用                                                                                 |

エラーはAPIのエラー形式です。モジュールに認証情報や他のヘッダーを渡すことはありません。読み取りゲートウェイはモジュールの読み取りルートを提供し、他のルートには`read_only`を返します。

各モジュールはOpenAPI文書にルートを記述し、Arkvoryは起動時に両者を比較します。規則に違反するルートを持つモジュールは起動せず、何も提供しません。Arkvoryは稼働を続けます。`GET /api/v1/system/modules`は、そのモジュールを`running: false`、`health.status`が`failed`として表示します。

| コード                   | 意味                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `routes_invalid`         | モジュールのプレフィックス外のパスや、すべてのサインイン済み呼び出し元に開放された変更操作など、ルートが規則に違反 |
| `openapi_invalid`        | OpenAPI文書がない、または無効                                                                                      |
| `openapi_route_mismatch` | ルートに対応する操作が文書にない、または操作に対応するルートがない                                                 |
| `transfer_invalid`       | モジュールが、提供を許可されていない転送プロトコルを提示                                                           |

ルートの文書：

| アドレス                                                                                    | 読み取れるユーザー               | 内容                                                                         |
| ------------------------------------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------- |
| `GET /api/ext/openapi.json`                                                                 | すべてのサインイン済み呼び出し元 | このサービスが実行する全モジュールのルートと、その呼び出し元が実行できる操作 |
| [`GET /api/v1/system/modules/{id}/openapi`](../api/reference/system#getSystemModuleOpenApi) | グローバル管理者                 | 1つのモジュールのルート                                                      |

`/api/v1/openapi.json`には、モジュールのルートは含みません。種類が`transfer`のモジュールは別のファイル転送方法を提供でき、`GET /api/v1/capabilities`の`transfer`に表示します。クライアントは対応する拡張機能がある場合だけそれを使い、なければ通常どおりに転送します。

## 更新、固定、ダウングレード {#versions}

`--yes`を指定し、新しいバージョンのファイルをインストールします。前のパッケージは、次のモジュール変更までホストに残ります。

| 作業                             | コマンド                                                        |
| -------------------------------- | --------------------------------------------------------------- |
| インストール済みバージョンを維持 | `sudo arkvory module pin sample 1.0.0 --root …`                 |
| 他のバージョンを再び許可         | `sudo arkvory module pin sample --unpin --root …`               |
| 古いバージョンをインストール     | `sudo arkvory module install <file> --downgrade --yes --root …` |

固定したモジュールは、固定を解除するまで他のすべてのバージョンを拒否します。インストール済みのものより古いバージョン、または削除済みでもパッケージがホストに残るものより古いバージョンには、`--downgrade`が必要です。

## インストール済みモジュールの確認 {#list}

```bash
sudo arkvory module list --root /opt/proanima-arkvory
```

このコマンドは、サービスが読み込み前に行うのと同じように、インストール済みの各パッケージの署名、すべてのファイル、アーカイブを再検証します。各モジュールは次のいずれかの状態を示します。

| 状態                 | 意味                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `ok`                 | パッケージに破損がない                                                                                         |
| `refused: <code>`    | ファイルが変更、追加、またはリンクに置換されている（`file_mismatch`、`file_unlisted`、`link_entry`など）       |
| `revoked (<reason>)` | ProAnimaStudioがこのバージョンを取り消した。`read path only`は、データの読み取りが引き続き可能であることを示す |

拒否したパッケージを使用することはありません。修復するには、パッケージファイルを再インストールしてください。

## モジュールの削除 {#remove}

```bash
sudo arkvory module remove sample --root /opt/proanima-arkvory
```

モジュールをインストールから除外し、そのパッケージは次のモジュール変更までホストに残します。公開済みファイルのバイト列を保存するモジュール（データ`layout`）は削除できません。データが読めなくならないよう、Arkvoryは`module_owns_data`で拒否します。

## 失効リスト {#revocations}

ProAnimaStudioは、取り消したモジュールバージョンの署名付きリストを公開します。各リストには番号があり、Arkvoryは現在保持するものより小さい番号のリストを受け入れません。モジュールパッケージに新しいリストが含まれていれば、パッケージのインストール時に保存します。ハブに接続できないホストでは、リストファイルを自分で保存してください。

```bash
sudo arkvory module revocations /root/module-revocations.json --root /opt/proanima-arkvory
```

各リストには有効期限を付けて署名します。デフォルトは90日、最長でも180日です。`module install`と`module pin <id> <version>`には有効なリストが必要です。リストが期限切れ、または存在しない場合、`stale_revocations`で拒否します。有効なリストを含むパッケージでも条件を満たします。それでも続行するには`--allow-stale-revocations`を追加します。Arkvoryは警告を表示し、その判断を`modules/audit.jsonl`に記録します。期限切れのリストがインストール済みモジュールを停止させることはありません。モジュールは稼働を続け、データも読み取れます。バージョンを停止させるのは失効エントリだけです。番号が大きいリストは、期限切れでも常に保存済みリストを置き換えます。

ProAnimaStudioがモジュール署名鍵を交換するときは、1つのリリースに両方の鍵を含め、次のリストを新しい鍵で署名し、さらに後のリリースで古い鍵を削除します。ホストが古い鍵で署名したリストをまだ保持している間は、そのリリースへの更新を拒否します。先に有効なリストを保存してください。`sudo arkvory module check-revocations --root …`で、このリリースが保存済みリストの鍵を信頼するか確認できます。

## プラグイン作者の信頼設定 {#trust}

自分のチームや他の作者のプラグインは、その作者の鍵で署名します。そのようなプラグインをインストールする前に、ホストの信頼リストに鍵を追加します。信頼リストはホストに属し、サービスは読み取れますが変更できません。

1. 作者から公開鍵ファイル（`.pub`、minisign形式）を入手し、別の経路でフィンガープリントを取得します。
2. 鍵を表示し、フィンガープリントを比較します。

   ```bash
   sudo arkvory module trust add /root/acme.pub --label "Acme platform team" --plugins "op-acme-*" --root /opt/proanima-arkvory
   ```

3. `--yes`を指定して追加します。

| オプション           | 意味                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------- |
| `--label`            | 鍵の所有者。必須                                                                                        |
| `--plugins`          | その鍵で署名できるプラグインID。カンマ区切りで、正確なIDまたは`*`付きプレフィックス。デフォルトは`op-*` |
| `--expires`          | `2027-01-31T00:00:00Z`などのUTC時刻。それ以降、その鍵による新規インストールを受け付けない               |
| `--allow-in-process` | その鍵のプラグインをArkvoryプロセス内で実行することを許可。そのコードはサービスの全権限を得る           |

プラグインIDは必ず`op-`で始まります。プラグイン鍵はProAnimaStudioモジュールに署名できず、ProAnimaStudioの鍵も`op-`プラグインに署名できません。別のIDや別の種類の鍵としてホストに登録済みの鍵は拒否します（`duplicate_key`）。署名は、現在のminisignのデフォルトである事前ハッシュ方式でなければなりません。旧方式の署名は`signature_algorithm`で拒否します。

`sudo arkvory module trust list --root …`で信頼済みの鍵を表示します。`sudo arkvory module trust remove <key id> --root …`で1つ削除します。

このリリースでは信頼リストを保持します。プラグインのインストールは後のリリースで利用可能になります。

## 中断後の復旧 {#recover}

モジュールセットへのすべての変更を更新ジャーナルに記録します。コマンドが途中で停止すると、次のデプロイコマンドは`Interrupted deployment`で拒否します。`sudo arkvory recover --root …`を実行してください。前のモジュールセットを復元します。それまでは、`module trust`と`module revocations`を含む、変更を行うすべてのモジュールコマンドを拒否します。

## モジュールのリクエスト有効期間 {#request-scope}

モジュールのルートは、ストリーミング中も含め、応答が終了するまで呼び出し元の権限を使用します。キャンセルまたは完了すると、その権限を取り消して読み取りリソースを閉じます。`upload-read`サービスは、所有権、`upload.read`、範囲、キャンセルを確認してから、未完了アップロードの受け付け済みパートを読み取ります。モジュールは稼働中に転送方式の提示を取り下げることができます。その後の機能問い合わせには含めませんが、ルートと進行中の転送は残ります。クライアントは古い提示内容をキャッシュしている場合があるため、ルートは操作ごとに確認する必要があります。

## 派生キャッシュの復旧 {#derived-cache}

署名付きモジュールは`derived-cache`を宣言できます（拡張API 0.9.0）。APIとワーカーは不変の世代を構築して読み取り、読み取りゲートウェイは読み取りのみを行います。バックアッププロセスにはこのサービスを渡しません。ソースの権限は引き続きリクエストごとに確認する必要があります。承認済みのモジュールリソース枠は、従来のdata/cacheと保持中の派生世代の両方を含みます。キャッシュミス時には再生成またはフォールバックが必要です。

PostgreSQLセッションの喪失は、ファイルI/Oの停止を証明しません。所有者の状態が不明な予約と、永続化済みの読み取り参照は、引き続きクォータに計上します。最初に、このコアバージョンのデータベースマイグレーションを適用してください。復旧前に、参加するすべてのホストを停止してプロセスとI/Oの終了を確認するか、該当する所有者プロセスの特定の実行個体が終了し、再開できないことを証明してください。到達できないホストはフェンシングします。診断情報から正確な所有者UUIDを取得し、根拠を記録してください。PID、タイムアウト、データベースロックの欠如から終了を推測してはいけません。

信頼できるホストで`ARKVORY_DATABASE_URL`を設定し、このコアバージョンのビルド済みパッケージを使って次のコマンドを実行します。このフラグは物理的な停止を確認したことを表しますが、所有者のロックが有効なら復旧は引き続き拒否します。確認を指定しなければ何も行いません。その後に整合性回復処理を再開し、回収を検証してください。確認の指定だけでクォータがすぐに空くわけではありません。これはホストのメンテナンスであり、モジュールやリモートCLIの権限ではありません。

```sh
node scripts/recover-derived-cache.mjs --owner UUID --confirm-owner-stopped
```

## モジュールの調整状態 {#module-state}

拡張API 0.10.0は、署名付きモジュール向けに、上限のあるアトミックな状態レジスターを追加します。HAフェイルオーバー後も維持しますが、可搬な論理バックアップには含みません。復元後は、モジュールが明示する再初期化手順に従ってください。保存済みオブジェクトの読み取りと復元は、引き続き利用できなければなりません。この状態はオブジェクトストレージとは別であり、モジュールの再インストールではリセットしません。

転送モジュールは、Arkvoryを再起動せずに、プロトコルを一時的に取り下げ、ポリシーの確認に成功した後で再提示できます。各リクエストには、常に現在のモジュールポリシーを適用します。

拡張API 0.12.0では、署名付きストレージモジュールが論理バイト数の上限を設定できます。コアは、リポジトリをまたいですべてのオブジェクトの全サイズと受け付け済み未完了アップロードを数え、重複排除による割り引きは行いません。上限に達すると、新規アップロードはデフォルトストレージを使います。受け付け済みアップロードの保存先は維持し、保存済みオブジェクトは引き続き読み取れます。カウンターからバイト数を減らすのは、物理クリーンアップ後だけです。

## 共有リソースカタログ {#resource-catalog}

拡張API 0.13.0は、署名付きモジュール向けの共有リソースカタログを提供します。アップロードや依存リソースがファイルを参照する間、ファイルを保護します。アップロードの所有権を解放するのは、コアの物理クリーンアップだけです。物理回収は読み取りとバックアップの終了を待ち、削除に失敗した場合は、再試行のため依存関係を保持します。

このカタログを使うモジュールへ初めてアップグレードする前に、古いAPIとワーカーの全プロセスを停止してください。新旧の書き込みプロセスを混在させないでください。論理復元後は、モジュールがすべてのレシピ、ファイル、依存関係の確認に成功するまで、回収を無効に保ちます。欠けたデータや破損したデータを修復してから、回収を再開してください。
