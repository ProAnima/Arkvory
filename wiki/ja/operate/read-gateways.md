# 読み取りゲートウェイ

**読み取りゲートウェイ**は、ダウンロードだけを提供する追加の API プロセスです。メイン API（**書き込みプロセス**）と同じサーバーで動作し、同じ PostgreSQL データベースとストレージディレクトリを使い、書き込みプロセスと他のゲートウェイとで 1 つのダウンロード帯域予算を共有します。

ゲートウェイを使うと、多数の並列ダウンロードを複数のプロセスに分散しながら、ダウンロードの合計速度を設定した 1 つの上限以内に維持できます。ゲートウェイはデータをコピーしません。書き込みプロセスが公開したファイルを読み取るため、遅延も発生しません。一方、サーバーやディスクの喪失に対する保護にはなりません。その対策は[バックアップ](./backups)と[ミラー](./mirrors)を参照してください。

## 仕組み {#how-it-works}

- 1 つのインストールには、書き込みプロセスが 1 つと、読み取りゲートウェイが最大 15 個あります。合わせて最大 16 **スロット**です。書き込みプロセスは常にスロット 0 を使います。各ゲートウェイは、1 からスロット数マイナス 1 までの独自のスロットを使います。
- すべてのプロセスが 1 つの PostgreSQL データベースと 1 つのストレージディレクトリを使います。ゲートウェイは、ストレージが存在し、そのデータベースに属していることを確認します。ストレージを作成することはありません。
- すべてのプロセスの合計ダウンロード速度を 1 つ設定します。各プロセスには、合計をスロット数で割り、小数点以下を切り捨てた、均等で固定の割り当てが与えられます。
- プロセスは、データベース内のリースでスロットを保持します。リースを失うと新しいペイロードの提供を停止し、再起動が必要になります。これにより、すべての割り当ての合計を全体の予算以内に保ちます。

書き込みプロセスは通常の役割を維持します。アップロード、コンソール、バックグラウンドクリーンアップ、すべての変更を担当します。ゲートウェイはクリーンアップを実行しません。

## ゲートウェイが拒否する操作 {#refusals}

ゲートウェイが受け付けるのは `GET` と `HEAD` だけです。変更するリクエストは、キーに書き込み権限があっても、すべて `Allow: GET, HEAD` ヘッダーと `read_only` コードを伴う HTTP 405 になります。サインインと自己登録も含まれます。コンソールは書き込みプロセスだけに含まれるため、ゲートウェイでは利用できません。

リポジトリの権限は、書き込みプロセスと同様に、読み取りごとに確認されます。セッション、個人用トークン、サービスキーを使ってゲートウェイで読み取れます。

## 要件 {#requirements}

- **同じサーバー。** ゲートウェイは、書き込みプロセスが公開したファイルを遅延なく正確に参照できる必要があります。`rsync` などの非同期コピーを使う独立したディスクは適しません。検証済みのネットワークファイルシステムはまだないため、1 台のサーバー上の複数プロセスとして使ってください。
- **同じサービスキー。** ファイルキーとその ID が一致するよう、すべてのプロセスに同じ内容の `ARKVORY_KEYS_FILE` を指定してください。管理対象のサービスキーはデータベースに保存されるため、自動的に一致します。
- **専用ポート。** 同じホスト上の各プロセスには、それぞれ異なる `ARKVORY_PORT` が必要です。
- **ファイルの読み取り専用ビュー。** 可能なら、ゲートウェイ向けにはストレージディレクトリを読み取り専用でマウントしてください。HTTP での拒否は OS のアクセス権の代わりにはなりません。なお、ゲートウェイは引き続きデータベースに書き込みます。リース、ストレージ診断、個人用トークンの最終使用時刻、読み取り中のファイルを保護するロックが対象です。
- **データベース接続。** 各ゲートウェイは、`ARKVORY_DATABASE_POOL_SIZE` でサイズを指定するクエリ用プールと、長期間維持するセッション用の独立した最大 8 接続のプールを使います。後者はストレージの所有権、ダウンロード中のファイルの削除防止、ゲートウェイのリースに使います。PostgreSQL の `max_connections` には両方のプールを算入してください。

## ゲートウェイの起動 {#run}

インストーラーは API、ワーカー、バックアップエージェントを登録します。ゲートウェイは登録せず、`arkvory status` も管理しません。インストール済みリリースの API プログラムを追加のインスタンスとして、自分で起動します。専用の環境設定を用意し、自分のサービスマネージャーで管理してください。

合計 2 プロセスで、全体が 64 MiB/s、1 アカウントまたはキーが 16 MiB/s の場合、全プロセスに共通する設定は次のとおりです。

```dotenv
ARKVORY_GATEWAY_SLOTS=2
ARKVORY_SHARED_DOWNLOAD_BYTES_PER_SECOND=67108864
ARKVORY_SHARED_DOWNLOAD_BYTES_PER_SECOND_PER_PRINCIPAL=16777216
```

書き込みプロセスには次を追加します。

```dotenv
ARKVORY_ROLE=api
ARKVORY_GATEWAY_SLOT=0
```

ゲートウェイには次を追加します。

```dotenv
ARKVORY_ROLE=reader
ARKVORY_GATEWAY_SLOT=1
ARKVORY_PORT=8081
```

ゲートウェイには、その他の API 設定も必要です。同じデータベースの `ARKVORY_DATABASE_URL`、同じストレージを指す `ARKVORY_DATA_DIR`（パスは異なっても構いませんが、ストレージの識別情報は一致しなければなりません）、`ARKVORY_KEYS_FILE`、他のコンピューターから接続する場合は HTTPS 設定を指定します。[環境変数](../reference/environment#read-gateways)を参照してください。

| 変数                                                     | 規則                                                                                                 |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `ARKVORY_GATEWAY_SLOTS`                                  | 書き込みプロセスを含むプロセス数。2～16                                                              |
| `ARKVORY_GATEWAY_SLOT`                                   | このプロセスのスロット。0 からスロット数マイナス 1 まで。書き込みプロセスは 0、ゲートウェイは 0 以外 |
| `ARKVORY_SHARED_DOWNLOAD_BYTES_PER_SECOND`               | 必須。全プロセスの合計速度。最小は 65,536 × スロット数、最大は毎秒 1 TiB                             |
| `ARKVORY_SHARED_DOWNLOAD_BYTES_PER_SECOND_PER_PRINCIPAL` | 全プロセスを通じた 1 アカウントまたはキーの合計速度。`0` は制限なし。それ以外の範囲は上記と同じ      |

これらの変数を 1 つでも設定する場合は、すべてのプロセスにスロット、スロット数、合計速度を設定してください。不正な値があると、変数名を示すメッセージを出して起動時に停止します。共有ダウンロード設定のないゲートウェイは起動を拒否します。

1. スロット数と速度を決めます。
2. 共通の 3 変数と書き込みプロセス専用の 2 変数を書き込みプロセスに追加し、再起動します。ポリシーがデータベースに保存されます。
3. ゲートウェイ専用の変数を指定して起動します。保存済みのポリシーと数値が異なる場合は起動しません。
4. すべてのプロセスの準備状態を確認し、それぞれで範囲指定のダウンロードをテストします。[ゲートウェイの監視](#monitoring)を参照してください。
5. その後に初めてゲートウェイをロードバランサーに追加します。

この構成を保護する規則があります。

- ゲートウェイは、書き込みプロセスがポリシーを保存した後にだけ起動できます。
- データベースにポリシーが存在すると、これらの変数のない書き込みプロセスは起動しません。共有ダウンロード設定がデータベースに必要であるというメッセージを出して停止します。
- 実行中のインストールで速度やスロット数を変更することはできません。[設定の変更](#change)を参照してください。

## ダウンロード帯域予算 {#budget}

各プロセスには `total / slots` の小数点以下を切り捨てた値が割り当てられます。1 アカウントまたはキーの速度にも同じ計算を適用します。例えば、64 MiB/s で 2 スロットなら各プロセスは最大 32 MiB/s を提供し、1 アカウントは各プロセスで最大 8 MiB/s を使えます。

- 他のプロセスの割り当ては使えません。2 プロセスのうち 1 つが停止していれば、使えるのは合計の半分です。これにより上限を単純で検証可能に保ちます。
- ローカル設定の `ARKVORY_DOWNLOAD_BYTES_PER_SECOND` と `ARKVORY_DOWNLOAD_BYTES_PER_SECOND_PER_PRINCIPAL` は、割り当てを下げることはできますが、上げることはできません。
- ゲートウェイはアップロードを受け付けないため、アップロードの帯域予算は書き込みプロセスに残ります。
- 待機中の転送のキューと実行中の転送数の上限は、各プロセス内にあります。そのため、すべてのプロセスの容量が加算されます。

制限の対象はアプリケーションのペイロードで、小さなバーストを許容します。ネットワークインターフェイスの制限ではありません。[環境変数](../reference/environment#transfers-and-bandwidth)を参照してください。

## リースと障害 {#leases}

データベースはスロットを 10 秒間予約します。プロセスは 2 秒ごとに更新し、ローカルではリースを最大 8 秒間信頼します。有効期間を過ぎたリースは、遅れた応答が届いても復活しません。

- **リースの喪失。** プロセスは新しいペイロードの提供を停止し、新しい認可済みリクエストに 503 を返し、再起動が必要になります。中断したダウンロードは、再試行または範囲リクエストで再開できます。書き込みプロセスにも適用されます。
- **同じスロットの再起動。** 新しいプロセスは古い予約が切れるまで待ちます。前回の更新から最大 10 秒、待機全体では最大 15 秒です。実行中のゲートウェイがまだスロットを保持している場合、新しいプロセスは `busy` で停止します。
- **時計。** リースは安定した時計に依存します。データベースサーバーの時計の急変や仮想マシンの停止があると、プロセスがリース期限後も提供を続ける可能性があります。その場合は、代替を起動する前に古いプロセスを停止してください。
- **データベース障害。** データベースが弱点になります。到達不能になるとリースが切れ、すべてのプロセスがペイロードの提供を停止します。

サーバーが、ネットワーク接続を失った停止プロセスを検知できるのは、TCP keepalive を通じてだけです。例えば、PostgreSQL の `tcp_keepalives_idle` を 10 秒、`tcp_keepalives_interval` を 5 秒、`tcp_keepalives_count` を 3 回のプローブに設定するか、`tcp_user_timeout` を設定します。設定しない場合、新しい書き込みプロセスやワーカーは、OS の長い既定タイムアウトを待つことがあります。

## ゲートウェイの監視 {#monitoring}

- `GET /health/status` は公開されており、`ready`、`unavailable`、`draining` だけを返します。プロセスが提供できない場合（スロットやリースの喪失、ドレイン中）は 503 を返します。ロードバランサーに使ってください。
- `GET /health/ready` にはキーが必要です。`role`、`writable`（ゲートウェイでは常に `false`）、`slot`、`slots`、`active`、`leaseSeconds` を含む `sharedDownloads`、およびローカル転送キューの数値を返します。スロットを失うと 503 を返します。単独インストールでは `sharedDownloads` は `null` です。
- `GET /health/live` は HTTP プロセスの動作だけを示します。ゲートウェイが提供できるかどうかは示しません。
- 各プロセスの `GET /health/metrics` は、そのプロセスだけの情報を示します。すべてのゲートウェイを収集対象にし、プロセス単位の HTTP・転送メトリクスを使ってください。

各プロセスを個別に確認します。ゲートウェイの `writable` が false なのは正常です。[監視](./monitoring)を参照してください。

## リクエストの振り分け {#routing}

ロードバランサーは自分で用意します。Arkvory には付属しません。

- データを変更するすべてのリクエストと `/console/` は書き込みプロセスに送ります。
- バイト列の読み取りは、書き込みプロセスとゲートウェイに分散できます。対象は `/api/v1/repositories/NAME/artifacts/ID/content`、`.../packages/content`、`.../asset/content` に対する `GET` と `HEAD` です。他のリクエストは書き込みプロセスに送ってください。
- `Authorization`、`Range`、`If-Range`、`ETag` ヘッダーを渡します。ファイル全体をバッファリングせず、本文をストリーミングしてください。キーを含む URL にクライアントをリダイレクトしないでください。
- 認証付きの準備状態確認が正常な場合にだけ、バックエンドをロードバランサーに追加します。

TypeScript SDK は、同じアドレスの背後にある別の正常なバックエンドを通じて、中断したダウンロードを再開できます。実行中の TCP 接続がサーバー間を移動することはありません。

## 設定の変更 {#change}

インストールの実行中は、速度やスロット数を変更できません。ポリシーが存在する間は単一プロセスにも戻せません。すべてのゲートウェイを停止しても、保存済みポリシーが制限なしの起動を防ぎます。

1. 流入するトラフィックを停止します。書き込みプロセス、すべてのゲートウェイ、ワーカーを停止し、実際に停止したことを確認します。
2. データベース内のリースが期限切れになるまで待ちます。
3. バックアップを作成します。[バックアップ](./backups)を参照してください。
4. Arkvory データベースの管理者が、1 つのトランザクション内で `arkvory_gateway_leases` と `arkvory_download_policy` の全行を削除します。リセットされるのは調整用の状態だけで、カタログではありません。
5. 新しい設定で書き込みプロセスを起動し、その後ゲートウェイを起動します。

いずれかのプロセスがまだ動いている可能性がある間は、絶対に実行しないでください。

データベーススキーマを変更する更新にも同じ注意が必要です。インストールを更新する前にすべてのゲートウェイを停止し、更新後は新しいリリースから起動してください。新しいデータベーススキーマに対して古いコードで動き続けるゲートウェイは、準備未完了を報告します。スキーマを変更しない更新には、この手順は不要です。両者が同じ設定で同じモジュールを計画している限り、前のリリースのゲートウェイは更新済みの書き込みプロセスと並行して提供を続け、都合のよいときに新しいリリースから再起動できます。オフラインのクリーンアップ修復ツールにも、全ゲートウェイの停止が必要です。書き込みプロセスのオンラインクリーンアップには不要です。

## ゲートウェイとミラーの比較 {#gateways-or-mirrors}

| 項目                               | 読み取りゲートウェイ                           | ミラー                                               |
| ---------------------------------- | ---------------------------------------------- | ---------------------------------------------------- |
| 構成                               | 同じサーバーとストレージ上の追加 API プロセス  | データのコピーを持つ、独立した 2 つ目のインストール  |
| データ                             | 1 つのコピーを即時に読み取ります               | 遅延を伴って取得する 2 つ目のコピー                  |
| アカウントとキー                   | 書き込みプロセスと同じ                         | 独自に保持                                           |
| 追加ディスク                       | 不要                                           | 必要。リポジトリの容量と同じだけ必要です             |
| 必要なもの                         | 同じデータベースと同じファイルシステム         | ソースへの HTTPS 接続と読み取り専用キー              |
| サーバーやディスクの喪失からの保護 | なし                                           | 一部あり。ソースの停止中も提供し、切り替えもできます |
| 用途                               | 1 つの共有速度制限で並列ダウンロード数を増やす | 第 2 サイト、利用者に近い拠点、待機系                |

どちらもバックアップを補うもので、代わりにはなりません。

## 制限 {#limits}

- すべてのプロセスが 1 台のサーバーと 1 つのストレージディレクトリを共有する必要があります。別々のマシンでは、この用途でテスト済みのファイルシステムが必要ですが、まだテスト済みのものはありません。
- インストーラーの対応、自動フェイルオーバー、組み込みロードバランサーはありません。
- 1 つのデータベースと 1 つの書き込みプロセスは、引き続き単一障害点です。
- 予算はスロットごとに固定され、再配分されません。優先度に基づくスケジューリングもありません。
- 実行中のインストールでポリシーを変更することはできません。
