# ミラーと第 2 サイト

**ミラー**は、ある Arkvory インストール上のリポジトリで、別のインストールである**ソース**のリポジトリの読み取り専用コピーです。ミラー側のインストールが HTTPS 経由でソースから変更を取得します。データベース、ストレージ、アカウント、キーは独自に保持します。

ミラーは、別の場所からダウンロードを提供したり、ソースを失ったときに引き継げる第 2 サイトを維持したりするために使います。ミラーはソースのバックアップではなく、自動的な高可用性も提供しません。切り替えは自分で行います。他の保護手段は[バックアップ](./backups)と[読み取りゲートウェイ](./read-gateways)を参照してください。

## ミラーとは {#what-a-mirror-is}

ミラー対象のリポジトリについて、ミラー側のインストールは次をコピーします。

- 公開済みファイルのバイト列と、ソースと**同じアーティファクト ID**。
- ラベル、メタデータ、コレクション。
- UPack 登録、ステージ、現在のファイルパス。
- リポジトリのコンテナイメージ、Git LFS オブジェクト、npm パッケージ。
- 削除。ソースで削除したファイルは、ミラーでも削除されます。

ID、パッケージ（バージョン、範囲、ステージ）、ファイルパスによるダウンロードは、最後の同期時点のソースと同じ内容をミラーから返します。ソースが停止しても使い続けられます。

ミラーは次をコピーしません。

- アカウント、グループ、キー、権限付与。ミラーは独自に保持し、独立しています。ソースでキーを取り消しても、ミラーには影響しません。
- クリーンアップからファイルを保護する参照、ビルドの添付ファイル、監査証跡、ストレージポリシー。
- 初回同期より前のファイルパスの履歴。ミラー上のラベルとパスのリビジョン番号は、ミラー独自のものです。

クライアントはミラー対象のリポジトリに書き込めません。アップロード、ラベルの変更、ファイルパス、ステージ、削除、ミラーへのプロモーションは、理由 `mirror_read_only` を伴う HTTP 409 になります。ミラー側のインストールの他のリポジトリは通常どおり動作します。ミラー対象のリポジトリではストレージポリシーは実行されず、削除は同期によってのみ行われます。

## ミラーの設定 {#set-up}

ソース側のキーと、ミラー側での 1 つのコマンドが必要です。

### ソースでのキーの作成 {#source-key}

ミラーには、ソースのリポジトリを読み取ることだけができるキーが必要です。書き込みキーは不要です。

1. ソースで、回復キーまたは運用担当者のキーを使って [[ui:services]] を開きます。
2. [[ui:serviceCreate]] を選択し、[[ui:servicePolicy]] にリポジトリを追加します。[[ui:bindingRead]] を選択して、ミラーに必要な権限を入力します。`artifact.list`、`artifact.read`、`content.read`、`annotation.read`、`asset.read`、`package.read` が含まれます。
3. [[ui:keyIssue]] を選択し、秘密情報をコピーして [[ui:keySaved]] を確認し、[[ui:keyActivate]] を選択します。有効化しないキーは 15 分後に失効します。
4. ミラーサーバー上のファイルに秘密情報を保存します。ファイルにはキーだけを 1 行で記述します。印字可能な 16～4000 文字です。読み取れるのは root または Administrators グループだけにしてください。

ソースは変更フィードを備えたリリースである必要があります。次の手順のコマンドで確認します。

### ミラーでのリポジトリの接続 {#attach}

ミラー側には、**新しい空の**リポジトリ名を使ってください。同期はリポジトリをソースと同じ内容にしますが、ソースに一度も存在しなかったものを削除することはありません。

```bash
sudo arkvory configure --root /opt/proanima-arkvory \
  --mirror releases \
  --mirror-upstream https://arkvory.example \
  --mirror-token-file /root/mirror-releases.key
```

```powershell
$root = 'C:\ProgramData\ProAnima\Arkvory'
& 'C:\Program Files\ProAnima\Arkvory\arkvory.ps1' configure --root $root `
  --mirror releases --mirror-upstream https://arkvory.example `
  --mirror-token-file C:\secure\mirror-releases.key
```

| オプション                 | 意味                                                                                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--mirror NAME`            | このインストール上のリポジトリ。英小文字、数字、`_`、`-` の 1～64 文字で、英字または数字で始めます                                                          |
| `--mirror-upstream URL`    | ソースのオリジン。`https://host` の形式で、パス、認証情報、クエリは指定できません。通常の `http://` は `localhost`、`127.0.0.1`、`[::1]` だけで許可されます |
| `--mirror-token-file FILE` | キーファイルへの絶対パス                                                                                                                                    |
| `--mirror-source NAME`     | ソース上のリポジトリ。既定は `--mirror` と同じ名前                                                                                                          |
| `--mirror-ca-file FILE`    | ソースの認証局を含む PEM ファイル。[独自の認証局による HTTPS](#ca-file)を参照してください                                                                   |

1 回のコマンドでは 1 つのリポジトリを指定します。同じ呼び出しで、ミラーの変更と HTTPS、保管庫、更新の変更を組み合わせることはできません。

1. コマンドは、何も変更する前にキーでソースを確認します。ソースがミラー変更フィードを提供すると報告し、ソースのリポジトリのフィードが応答する必要があります。
2. キーを `config/mirrors/NAME.token` に保存し、`config/mirrors/mirrors.json` を書き込み、`config/runtime.json` に `ARKVORY_MIRRORS_FILE` を設定します。
3. API とワーカーを再起動し、準備完了まで待ちます。何かが失敗すると、以前のファイルに戻して再度再起動します。

Docker Compose では、API とワーカーのコンテナにミラーファイルをマウントする `config/compose.mirrors.yml` も書き込みます。自分で実行する Compose コマンドには、このファイルを追加してください。

リポジトリのキーを交換するには、`--mirror` と新しい `--mirror-token-file` だけを指定してコマンドを再実行します。ソース、ステージ、認証局は維持され、コマンドの再実行でミラーがインポートに変わることはありません。コマンドは API とワーカーを再起動します。ワーカーは失敗のたびにキーファイルを読み直すため、手動で交換したキーファイルは再起動なしでも反映されます。

```bash
sudo arkvory configure --root /opt/proanima-arkvory \
  --mirror releases --mirror-token-file /root/new-mirror-releases.key
```

ソースがキーを拒否すると、コマンドは何も変更せずに停止し、理由を示します。キーが受け付けられない場合は 401、リポジトリを読み取れない場合は 403、ソースにリポジトリが存在しない場合は 404 です。すでに別のソースをミラーしているリポジトリは、`NAME mirrors another source; detach it first` というメッセージで他のソースを拒否します。

ミラー側のインストールで、利用者とツールにリポジトリへのアクセスを付与してください。権限付与またはサービスポリシーで名前を指定すると、リポジトリが存在するようになります。利用者には [[ui:administration]] の [[ui:manageGrants]]、ツールにはサービスポリシーを使います。ソースの権限は引き継がれません。

### 独自の認証局による HTTPS {#ca-file}

ソースが社内または自己署名の認証局の証明書を使う場合は、`--mirror` コマンドに `--mirror-ca-file /path/ca.pem` を追加します。各証明書が読み取り可能で期限切れでないことを確認し、1～64 個の証明書を `config/mirrors/ca.pem` に保存します（ファイルは最大 1 MiB）。ワーカーは標準の認証局に加えて、それらを信頼します。

- ファイルはインストールのすべてのミラーで使います。新しい `--mirror-ca-file` は証明書を追加し、すでにある証明書は 1 つだけ保持します。最後のミラーを切り離すとファイルは削除されます。
- ワーカーは、1 つのミラーだけでなく、すべての接続でこの認証局全体を信頼します。
- 証明書の検証が無効になることはありません。

## コピーの対象と頻度 {#sync}

同期はミラー側のインストールのワーカーが行います。専用サービスはありません。ミラー対象のリポジトリごとに次の手順を実行します。

1. **初期取り込み。** ワーカーはソースの変更フィードの現在位置を記録します。次にアーティファクト、パッケージ、ファイルパスの一覧をページごとに読み取り、ミラーを同じ内容にします。
2. **追従。** ワーカーはソースのフィードを読み取ります。追いつくと 10 秒ごとに再確認します。適用した変更ごとに位置を保存します。
3. **ファイルのコピー。** ファイルはパートに分けてコピーします。各パートとファイル全体の SHA-256 を検証します。中断後は最初の未取得パートから再開します。パートは、ミラーのストレージディレクトリ内の `mirror-staging` に一時保存されます。
4. **エラー後。** 2 秒から始まり、最大 5 分まで倍増する待ち時間の後、同じ手順を再試行します。1 つのミラーの失敗で他のミラーが停止することはありません。

1 つのインストールで最大 64 リポジトリをミラーできます。コピーはミラー側の容量上限とディスク容量に算入されるため、ソースのリポジトリに必要な容量と同じだけ確保してください。[ストレージ](./storage)を参照してください。

ソースのキーが取り消されたり、ソースに到達できなくなったりしても、ミラーは取得済みの内容を提供し続け、状態にエラーを表示します。

## 同期状態の確認 {#status}

### コンソールでの確認 {#status-console}

メニューの [[ui:mirrors]] には、読み取り権限があるリポジトリのすべてのミラーとインポートが、ソース、状態、前回の同期、コピー済みの内容とともに表示されます。管理者は常にこのページを表示できます。ミラーがまだない場合は設定方法が表示されます。ページは 20 秒ごとに自動更新されます。

| 状態                      | 意味                                                                           |
| ------------------------- | ------------------------------------------------------------------------------ |
| [[ui:mirrorStateSynced]]  | ソースに追いついています                                                       |
| [[ui:mirrorStateBehind]]  | 前回の確認以降にソースで行われた変更をコピーしています                         |
| [[ui:mirrorStatePending]] | 設定済みですが、ワーカーはまだ処理を始めていません                             |
| [[ui:mirrorStateSeeding]] | 初期取り込み中、またはソースの復元後の再取り込み中です                         |
| [[ui:mirrorStateFailing]] | 前回の試行に失敗しました。ダウンロードは利用でき、ワーカーは自動で再試行します |

同期が停止した場合、ページには理由と次の対処が表示されます。修正コマンドがある場合は、それも表示されます。例えば、ソースが古いキーを拒否した場合の新しいキーの指定です。説明は[エラーコード](#error-codes)に対応しています。

ミラー対象のリポジトリに接続すると、コンソールはカタログの上にも [[ui:mirrorBadge]]、[[ui:mirrorBehind]]、[[ui:mirrorFailing]] のバッジを表示します。同期の停止中は、その下に理由と次の対処が表示されます。バッジは再読み込みなしでサーバーの状態に追従します。バッジのヘルプ（[[ui:mirrorHelpLabel]]）を開くと、ソースと前回の同期時刻を確認できます。ミラー対象のリポジトリでは、アップロードと変更のボタンは非表示になります。

### API での確認 {#status-api}

[getRepositoryMirror](../api/reference/mirrors#getRepositoryMirror) はリポジトリの状態を返します。そのリポジトリの読み取り権限が必要です。通常のリポジトリへの応答は 404 です。

| フィールド                       | 意味                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `mode`                           | `mirror` または `import`                                                                                                       |
| `phase`                          | `pending`（ワーカーが未開始）、`seeding`（初期取り込み）、`following`                                                          |
| `caughtUp`                       | 保存済み位置がソースの最新位置と一致すると `true`。初期取り込みの完了前は `null`                                               |
| `checkedAt`、`syncedAt`          | ワーカーが最後にフィードを読んだ時刻と、最後に追いついた時刻                                                                   |
| `copiedArtifacts`、`copiedBytes` | これまでのコピーの合計（`copiedBytes` は 10 進数の文字列）                                                                     |
| `conflicts`                      | 適用を保留したソースの項目。`count`、`oldestAt`、`sample` 内の最大 10 項目。[適用を保留した項目](#conflicts)を参照してください |
| `errorCode`、`errorAt`           | 直近の手順の失敗、または `null`                                                                                                |

### エラーコード {#error-codes}

| `errorCode`               | 意味と対処                                                                                                                                                                                                                                                                                                            |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mirror_mismatch`         | 同じアーティファクト ID がソースで異なる内容を持っています。ミラーは自分のファイルを保持します。アーティファクトを調査してください。原因が分かるまでは、どちらのコピーも削除しないでください                                                                                                                          |
| `mirror_source_changed`   | リポジトリはすでに別のソースのコピーを保持しています。切り離すか、新しいソースを新しいリポジトリにミラーしてください                                                                                                                                                                                                  |
| `mirror_source_behind`    | ソースが復元または再インストールされ、ミラーが保持する位置の変更が、そこで適用したものと異なっています。ミラーはソースを再度読み取り、追いつくとコードが消えます。復元後のソースにないファイルはミラーに残ります                                                                                                      |
| `mirror_delete_blocked`   | ソースが削除したファイルを、ミラーでは削除できません。参照やファイルパスの履歴など、こちらでまだ使われているためです                                                                                                                                                                                                  |
| `mirror_detached`         | リポジトリは切り離され、独自の変更を持っています。再同期されることはありません。ソースを新しいリポジトリにミラーしてください                                                                                                                                                                                          |
| `mirror_package_conflict` | ソースのバージョンが持つパッケージバージョンを、このリポジトリでは異なるバイト列ですでに保持しています。その項目は保留され、同期は続きます。[適用を保留した項目](#conflicts)を参照してください。以前のリリースではここで停止していました                                                                              |
| `mirror_id_taken`         | ソースのアーティファクトを、このインストールの別のリポジトリが保持しています。項目は保留されます。[適用を保留した項目](#conflicts)を参照してください。ただし、イメージタグ、Git LFS オブジェクト、npm パッケージの変更では同期が停止します。1 つのソースリポジトリが供給できるのは、こちらの 1 つのリポジトリだけです |
| `mirror_unreachable`      | ソースに到達できません。接続拒否、タイムアウト、名前解決の失敗です。ワーカーは自動で再試行します。ネットワーク、ファイアウォール、ソースの動作を確認してください                                                                                                                                                      |
| `mirror_certificate`      | ソースの証明書が信頼されていない、期限切れ、または名前に一致しません。`--mirror-ca-file` で認証局を追加してください（[独自の認証局による HTTPS](#ca-file)を参照）                                                                                                                                                     |
| `mirror_failed`           | より具体的なコードのない失敗です。ワーカーのログを読んでください                                                                                                                                                                                                                                                      |
| その他のコード            | 失敗したリクエストのコードです。`unauthorized` はソースがキーを受け付けなくなった場合（ミラーに新しいキーを指定）、`forbidden` はキーがリポジトリを読み取れない場合、`not_found` はソースのリポジトリがなくなった場合、`capacity_exceeded` はミラーがいっぱいの場合です                                               |

ワーカーのログ（`component` は `mirror`）には、`mirror.started`、`errorCode` と `attempts` を伴う `mirror.step_failed`、`mirror.recovered`、`mirror.stopped` が記録されます。

### 適用を保留した項目 {#conflicts}

ソースの変更には、こちらの内容を壊さずには適用できないものがあります。ワーカーはその項目の適用を保留し、フィードの残りを処理し続けます。そのため、1 つのバージョンが以後のすべての変更を止めることはありません。黙って無視されるものはなく、保留されたすべての項目が解決まで表示されます。

| コード                    | 意味                                                                                                                                                                                                                         | 対処                                                                                                                                       |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `mirror_package_conflict` | そのバージョンのパッケージバージョン（グループ、名前、バージョン）を、このリポジトリでは異なるバイト列で保持しています。クライアントは引き続きこちらのバージョンを取得し、コピー済みファイルはパッケージ未登録のまま残ります | ソースでステージまたはバージョンを削除するか、別のバージョンで公開してください。インポートでは、こちらのバージョンを削除することもできます |
| `mirror_id_taken`         | このインストールの別のリポジトリがアーティファクト ID を保持しています                                                                                                                                                       | 1 つのソースリポジトリが供給するのは、こちらの 1 つのリポジトリです。他方のミラーやインポートを切り離すか、他方のコピーを削除してください  |

- ワーカーは、各項目の前回の試行から 10 分後に再試行します。ソースに追いつくたびに最大 8 項目を試します。適用できた場合、またはソースからなくなった場合に、その項目は保留一覧から削除されます。ソースでバージョンを削除した場合や、インポートではステージを削除した場合が該当します。
- 状態の `conflicts` には、保留中の件数、最も古い保留の時刻、最大 10 項目が表示されます。各項目にはアーティファクト ID、変更（`action` と `detail`）、コード、最初と最後の試行、試行回数が含まれます。
- コンソールは [[ui:mirrors]] とリポジトリのバッジの下に件数を表示します。他の内容の同期は続くため、状態は変わりません。
- ワーカーのログには、失敗した試行ごとに `mirror.conflict_set_aside`（警告。`artifactId`、`action`、`errorCode`、`attempts` を含む）、保留項目が削除されたときに `mirror.conflict_resolved` が記録されます。
- メトリクス `arkvory_mirror_conflicts` が件数を数え、30 分間存在すると規則 `ArkvoryMirrorConflicts` が警告します。

イメージタグとマニフェスト、Git LFS オブジェクト、npm パッケージの変更は保留されません。順序が重要で、後で適用すると新しい変更を取り消す可能性があるためです。その競合は、解決するまで該当するコードで同期を停止します。

## ミラーの監視 {#monitoring}

ミラー側のインストールの API は、ミラー対象のリポジトリごとに、`repository` と `mode` のラベルを持つ 4 つのメトリクスを公開します。

- `arkvory_mirror_last_sync_timestamp_seconds`：ミラーが最後に追いついた時刻。
- `arkvory_mirror_last_check_timestamp_seconds`：最後にフィードを読み取った時刻。
- `arkvory_mirror_failing`：前回の試行が失敗している間は 1。復元されたソースを再読み取り中（`mirror_source_behind`）は含みません。
- `arkvory_mirror_conflicts`：[適用を保留した項目](#conflicts)の数。

付属の Prometheus 規則は、`ArkvoryMirrorStale`（追いついていない時間が 1 時間を超えた状態が 15 分続く）、`ArkvoryMirrorFailing`（失敗が 15 分続く）、`ArkvoryMirrorConflicts`（保留項目が 30 分存在する）です。[監視](./monitoring)を参照してください。ワーカーがまだ処理を始めていないミラーには同期時刻がないため、初回同期前に stale 規則は発火しません。

## ステージによるインポート {#import}

`--mirror-stages` を指定すると、第 2 インストールのリポジトリはミラーにはなりません。ソース上の指定ステージのいずれかを持つバージョンを取り込む、書き込み可能な通常のリポジトリです。開発サーバーから本番サーバーへビルドを移すために使います。

```bash
sudo arkvory configure --root /opt/proanima-arkvory \
  --mirror releases --mirror-upstream https://dev.example \
  --mirror-token-file /root/dev.key --mirror-stages release
```

- 異なるステージ名を 1～16 個、カンマ区切りで指定します。
- バージョンは 1 度コピーされます。同じ ID、バイト列、ラベル、UPack 登録、および一致するステージを持ちます。
- 以後、そのバージョンはこのインストールに属します。ソースでの変更、ステージ削除、バージョン削除は反映されません。こちらで削除したバージョンは再インポートされません。こちらで削除したステージは削除されたままです。その後ソースが同じバージョンに別の設定対象ステージを付けた場合は、そのステージだけが追加されます。
- リポジトリのアップロードとストレージポリシーは通常どおり動作します。
- コンテナイメージ、Git LFS、npm レジストリのデータは引き継がれません。
- ステージを変更すると、新しい初期取り込みが始まります。まだこちらにないバージョンだけを取り込み、すでにあるものはそのままにします。
- ソースのパッケージバージョンをこのリポジトリが異なるバイト列ですでに保持している場合、そのバージョンは `mirror_package_conflict` で保留され、次のバージョンのインポートへ進みます。クライアントは引き続きこちらのバージョンを取得します。[適用を保留した項目](#conflicts)を参照してください。

2 つのインストールが互いにインポートすることもできます。例えば、本番がステージングから `release` を取り込み、ステージングが本番から `hotfix` を取り込みます。バージョンは両側で同じ ID を維持するため、二重にコピーされたり循環したりしません。

- ステージングで作成され、本番から戻ったバージョンには、新しいステージだけが追加されます。
- 片側で削除したバージョンは、後で他方がステージを付けても、そこから再インポートされません。
- 削除は他方に伝わりません。他方でも削除するまで、コピーが残ります。

双方向には異なるステージを使ってください。同じステージを使うと、片側で削除したステージが、他方でそのバージョンに再度ステージを付けたときに戻ってきます。

コンソールには [[ui:mirrorImport]]、前回の試行が失敗した場合は [[ui:mirrorImportFailing]] のバッジが表示されます。ソースのキーには、ミラーと同じ読み取り専用権限が必要です。

## ソースを失った場合のフェイルオーバー {#failover}

これは、2 つのサイト上の独立したインストール間で行う手動の切り替えです。自動ではありません。ミラーがまだ取得していなかった変更は失われます。

### 事前の準備 {#failover-prepare}

1. 可能ならソースと同じリリースで、独自の PostgreSQL とディスクを持つ第 2 サイトをインストールします。2 つのサイトは何も共有しません。
2. ソースで読み取り専用キーを作成し、各リポジトリをミラーとして接続します。後からソースで作成したリポジトリは自動ではミラーに現れないため、同じ方法で接続してください。
3. ミラーで、切り替え後に書き込めるキーを含め、利用側に必要なキーを発行します。ソースの権限は引き継がれないため、ソースが侵害されてもミラーへのアクセスは与えられません。
4. CI やデプロイエージェントなどの利用側に、ダウンロードの代替先としてミラーのアドレスを設定します。ソースへの回線の負荷も減らせます。
5. ソースを、そのサイトの外にある保管庫にバックアップします。[バックアップ](./backups)を参照してください。ミラーはその代わりにはなりません。
6. 上記の規則でミラーを監視します。

### 切り替え {#failover-switch}

1. ソースがクライアントから本当に利用できず、自動で戻ってこないことを確認します。1 つの論理リポジトリへの書き込みを両方のサイトが受け付けると、後で統合できません。ソースに部分的に接続できる場合は、サービスを停止するかポートを閉じます。
2. ミラーで、各リポジトリの `syncedAt` を読み取ります。その時刻以降のソースの変更はミラーにはありません。
3. ミラー側で、各ミラー対象リポジトリを切り離します。同じアーティファクト ID とすべてのデータを持つ、通常の書き込み可能なリポジトリになります。

   ```bash
   sudo arkvory configure --root /opt/proanima-arkvory --mirror-detach releases,prod
   ```

   複数のリポジトリをカンマ区切りで指定するか、すべてのミラーとインポートを対象にするには `all` を指定します。コマンドは API とワーカーを 1 回再起動するため、短時間の中断が発生します。

4. DNS または CI の設定で、書き込みを行うクライアントの接続先をミラーに変更します。
5. ミラーで確認用ファイルをアップロードし、ダウンロードします。

クライアントから見た動作は次のとおりです。

- 切り替え前は、ミラーからのダウンロードは動作し、書き込みは 409 `mirror_read_only` になります。
- 切り離した後は書き込みが可能になり、バッジが消えます。
- ミラーに同じアカウントを作成していない限り、ソースのキーとパスワードはミラーで使えません。

元に戻すことはできません。切り離したリポジトリはミラーとして再接続できず、同期は `mirror_detached` で停止します。以前のソースを復帰させるには、内容を消去するか新たにインストールし、新しいプライマリーのリポジトリをミラーとして接続します。古いソースと新しいプライマリーを、書き込みを有効にしたまま同時に実行しないでください。

### 切り替えの予行演習 {#failover-rehearse}

四半期ごとと更新後に、切り替えを予行演習してください。予備のコピーで 1 つのリポジトリを切り離し、`syncedAt`、ダウンロード、アップロードを確認し、日付と結果を記録します。ソースのバックアップを空のインストールに復元するテストも、別途実施してください。[復元の定期テスト](./backups#test-restore)を参照してください。

## 制限 {#limits}

- ミラーは切り離すまで読み取り専用です。切り離したリポジトリをミラーに戻すことはできません。
- ミラーはバックアップではありません。アカウント、キー、権限付与のコピーはなく、参照、添付ファイル、監査証跡、ストレージポリシーもコピーしません。
- インポートモードでは、コンテナイメージ、Git LFS、npm のデータをコピーしません。
- 新しい初期取り込みは追加と更新だけを行います。ソースの復元後、ソースが失ったファイルはミラーに残ります。
- 1 つのソースリポジトリが供給するのは、あるインストールの 1 つのリポジトリです。アーティファクト ID が両側で同じなので、同じソースの 2 つ目のミラーまたはインポートは設定時に拒否されます。同じ理由で、互いにインポートする 2 つのインストールでは、両側で同じリポジトリ名を使う必要があります。他方から来たバージョンをこちらの異なるリポジトリに取り込むことはできず、`mirror_id_taken` で保留されます。
- すでにこちらで異なるバイト列を保持しているパッケージバージョンは、コピー後に `mirror_package_conflict` で保留されます。削除するまで、コピーはパッケージ未登録のままリポジトリに残ります。
- 保留された項目は、解決するまでこちらで利用できません。イメージタグ、Git LFS オブジェクト、npm パッケージの変更の競合は、引き続き同期を停止します。
- ミラー側のインストールをバックアップから復元すると、バックアップ取得後にインポートされて削除されたバージョンが、再びインポートされることがあります。
- 両方のインストールは、それぞれ個別に更新します。ソースはミラー変更フィードを提供する必要があります。
- ソースの信頼された認証局の集合は、ワーカー全体に適用されます。
- 自動フェイルオーバー、以前のソースのフェンシング、逆方向の同期はありません。
