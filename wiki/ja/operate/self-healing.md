# 自己修復

Arkvoryは、失敗したサービスを自動で再起動し、オペレーターの操作なしで中断した処理を再開します。このページでは、再起動する対象、各復旧にかかる時間、引き続き対処が必要な問題を説明します。1台のサーバーは高可用性システムではありません。再起動により接続が短時間中断し、クライアントが転送を再開します。

## 自動で再起動するもの {#overview}

すべてのサービスは、各プラットフォームのサービスマネージャーの管理下で実行します。API、ワーカー、バックアップエージェントは、安全に処理を続けられなくなると自身のプロセスを終了します。その後、サービスマネージャーが新しいプロセスを起動します。

| 状況                                  | Linux（systemd）                       | Windowsサービス                                   | Docker Compose                                                         |
| ------------------------------------- | -------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------- |
| クラッシュ、強制終了、メモリ不足      | 10 s後に再起動                         | 10 s後に再起動                                    | エンジンが待ち時間を増やしながらコンテナを再起動                       |
| 停止要求なしの終了。終了コード0も含む | 再起動                                 | ランチャーが終了コードを1に変更し、10 s後に再起動 | 再起動                                                                 |
| ストレージの所有権またはリースの喪失  | 終了コード1で終了し再起動              | 終了コード1で終了し再起動                         | 終了コード1で終了し再起動                                              |
| メインスレッドのハング                | ウォッチドッグがプロセスを終了し再起動 | 同じ                                              | 同じ                                                                   |
| 起動時にデータベースへ接続できない    | 終了コード1で終了し、10 sごとに再試行  | 終了コード1で終了し、10 sごとに再試行             | 終了コード1で終了し、待ち時間を増やしながら再試行                      |
| マシンの再起動                        | サービスを`multi-user.target`で有効化  | 自動（遅延開始）                                  | コンテナエンジンの起動に従う。Docker Desktopではユーザーのサインイン後 |
| ユーザーがサービスを停止              | 次回のOS起動まで停止を維持             | 次回のOS起動まで停止を維持                        | `docker compose stop`による停止を維持                                  |

準備状態の確認に失敗しただけで、サービスを再起動することはありません。停止前のドレイン中や、ストレージディレクトリ内のフォルダーがない場合にも確認は失敗します。再起動してもこれらの原因は解消しません。

## Windowsサービス {#windows}

グラフィカルインストーラーと`install.ps1`は、アカウント`NT AUTHORITY\LocalService`を共有する`Arkvoryapi`、`Arkvoryworker`、`Arkvorybackup`と、管理対象データベース用のサービス`Arkvorydatabase`を登録します。[Windows](../install/windows#services)を参照してください。

- **スタートアップの種類。** API、ワーカー、バックアップエージェントは自動（遅延開始）を使用し、データベースは自動を使用します。遅延開始のサービスは、OS起動と同時ではなく、起動してからしばらく後に開始します。
- **回復操作。** 障害後、Windowsは10秒後にサービスを再起動します。その後の障害でも同じ操作を繰り返します。障害カウンターは1時間後にリセットします。プロセスがエラーコードで終了した場合にも回復操作を適用します。
- **停止タイムアウト。** 実行中のリクエストを完了させるため、120秒です。
- **ログ。** 各サービスの出力は`logs\`に保存し、20 MiBでローテーションして旧ファイルを5個保持します。

サービスの回復操作を表示するには：

```powershell
sc.exe qfailure Arkvoryapi
```

グラフィカルインストーラーを再実行すると、スタートアップの種類と回復操作を復元します。自分で停止したサービスは停止したままです。

## Linuxのsystemdユニット {#linux}

パッケージと`install.sh`は、`arkvory-api`、`arkvory-worker`、`arkvory-backup`を作成し、管理対象データベースの場合は`arkvory-database`も作成します。

- `Restart=always`と`RestartSec=10`により、API、ワーカー、バックアップエージェントは、停止を要求していないすべての終了後に再起動します。終了コード0も含みます。
- `StartLimitIntervalSec=0`で再起動試行回数の制限をなくすため、systemdが失敗したサービスの再起動を諦めることはありません。設定ミスなどの恒久的な問題があれば、修正するまで10秒ごとに再起動します。
- データベースユニットは`Restart=on-failure`を使用し、同じ10秒の間隔を設けます。
- `TimeoutStopSec=120`により、停止中のサービスに2分を与えます。
- ユニットは`multi-user.target`で有効化します。

```bash
systemctl is-enabled arkvory-api arkvory-worker arkvory-backup
systemctl status arkvory-api arkvory-worker arkvory-backup
```

ネイティブサービスが対応するのはsystemdのみです。他のinitシステムではDocker Composeを使用してください。

## Docker Compose {#compose}

プロジェクト`proanima-arkvory`のすべてのサービスは`restart: unless-stopped`を使用します。1回限りの処理`initialize`と`migrate`は再起動しません。

- APIコンテナにはヘルスチェックがあります。開始猶予期間は20秒で、10秒ごとにヘルスキーを使って`/health/ready`に問い合わせます。正常でないコンテナにはその印を付けますが、Dockerは再起動しません。ワーカーは起動時にAPIが正常になるまで待ちます。
- コンテナの停止には120秒を与えます。
- コンテナエンジンはOS起動時に開始する必要があります。Linuxでは`systemctl is-enabled docker`で確認してください。Arkvoryはエンジンの設定を変更しません。
- WindowsのDocker Desktopは、1人のユーザーのアプリケーションです。そのユーザーがサインインしてDocker Desktopが起動するまで、コンテナは稼働しません。**サインイン時にDocker Desktopを起動する（Start Docker Desktop when you sign in）**を有効にしてください。無効の場合はインストーラーと`arkvory status`が警告します。サインインなしで起動する必要があるサーバーには、ネイティブWindowsサービスを使用してください。

## ハング後の再起動 {#hang}

無限ループ、ブロッキング呼び出し、ネイティブコードのハングなどにより、プロセスが終了せずに動作を停止することがあります。プロセス自体は存在するため、サービスマネージャーは検出できません。そのため、API、ワーカー、バックアップエージェントはそれぞれウォッチドッグを備えます。

1. メインスレッドが毎秒1回カウンターを増やします。
2. 別のスレッドが毎秒1回カウンターを確認します。
3. `ARKVORY_WATCHDOG_SECONDS`回の連続した確認でカウンターが動いていなければ（デフォルト60回）、ウォッチドッグは`stalledSeconds`フィールドを含む`process.stalled`を標準エラーに記録し、プロセスを終了します。
4. サービスマネージャーが、クラッシュ後と同様にプロセスを再起動します。

ウォッチドッグは実時刻ではなく、自身の確認周期を数えます。ホストがスリープしたり仮想マシンが一時停止したりすると、両方のスレッドが停止するため、復帰時に誤ってハングと判定しません。そのため、ハングからの復旧には最大60秒と、再起動の10秒がかかります。

`ARKVORY_WATCHDOG_SECONDS`には10～3600を指定できます。`0`はウォッチドッグを無効にします。制限時間より長くプロセスを一時停止すると再起動されるため、無効化はデバッガーで停止させる場合だけにしてください。長時間のブロッキング処理もハングとして数えます。ウォッチドッグ自体を起動できない場合、サービスは`process.watchdog_failed`を記録し、ウォッチドッグなしで稼働を続けます。管理対象PostgreSQLにはウォッチドッグがありません。クラッシュ後はサービスマネージャーが再起動します。[環境変数](../reference/environment#watchdog)を参照してください。

## データベースセッションまたはストレージ所有権の喪失 {#ownership}

APIはデータベースセッションを使って、ストレージディレクトリへの唯一の書き込みプロセスであることを保証します。このセッションは2秒ごとに確認し、8秒以内に応答しない確認は喪失と見なします。ワーカーも同じ方法で役割を保証します。別のプロセスが引き継いでいる可能性があるため、実行中のプロセス内で所有権を取り戻すことはありません。

PostgreSQLの再起動などで所有権を失うと、プロセスは次のように動作します。

1. `api.ownership_lost`または`worker.ownership_lost`を記録します。
2. 新しい処理の受け付けを停止し、転送をキャンセルします。
3. 終了コード1で終了します。

サービスマネージャーが新しいプロセスを起動し、そのプロセスが最初からすべてを再確認します。データベースが停止している間、新しいプロセスは起動できず、PostgreSQLが応答するまでAPIは10秒ごとに終了と再起動を繰り返します。これは想定どおりの動作です。その間、クライアントには`Retry-After`を伴う503 `unavailable`を返します。稼働中のバックアップエージェントは、データベースが利用できなくても終了しません。エラーを記録し、ポーリング間隔（デフォルト15秒）の後に再試行します。

## 進行中の処理への影響 {#work}

クラッシュすると開いている接続が切れます。成功を応答済みのデータは残ります。その後の動作は処理の種類によって異なります。

| 処理                                    | 再起動後                                                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| ダウンロード                            | クライアントが範囲リクエストで再開。SDKとコマンドラインクライアントは自動で実行                                                      |
| マルチパートアップロード                | 記録済みパートはサーバーに残る。クライアントが存在するパートを問い合わせ、不足分を送信。セッションは作成から7日間開いた状態を維持    |
| ファイル全体を1リクエストでアップロード | クライアントが最初のバイトからファイルを再送                                                                                         |
| ワーカーによるアップロード完了          | 下記参照                                                                                                                             |
| バックアップ                            | 下記参照                                                                                                                             |
| ミラー同期                              | ワーカーが適用済みの変更ごとに位置を保存し、ファイルは最初に不足しているパートからコピー。失敗後は2秒待ち、試行間隔を最大5分まで倍増 |
| 更新                                    | インストーラーがロックとジャーナルを保持。自動では継続しない。[トラブルシューティング](./troubleshooting#update-failed)を参照        |

SDKとコマンドラインクライアントは、ネットワーク障害、および408、429、502、503、504の応答に対して、回数を限定して再試行します。他のクライアントには独自の再試行処理が必要です。[転送](../use/transfers)を参照してください。

**完了ジョブ。** 大きなアップロードはワーカーが完了させます（SDKとコマンドラインクライアントは16 GiB以上でこの方式を使用）。ワーカーはジョブに対して30秒のリースを保持し、2秒ごとに更新します。ワーカーがクラッシュすると30秒以内にリースが切れ、再起動したワーカーがジョブを再取得します。1ジョブの実行は最大5回です。失敗後は2秒待ち、最大60秒まで待ち時間を倍増します。`forbidden`、`invalid_input`、`integrity_mismatch`、`not_found`は直ちにジョブを終了させます。試行回数を使い切ったジョブには`completion.attempts_exhausted`を記録します。同じアップロードの完了を再要求すると、ジョブを再びキューに入れます。完了処理は保存済みバイト列を確認するため、安全に繰り返せます。

同じデータベースに接続する2つ目のワーカーは、スタンバイ（`worker.standby`）として待機し、最初のワーカーがいなくなったかを5秒ごとに確認します。

**バックアップエージェント。** エージェントは60秒のリース（`ARKVORY_BACKUP_LEASE_SECONDS`）を保持し、20秒ごとに更新します。クラッシュ後は、リースが切れると別のエージェントまたは再起動した同じエージェントが取得するため、バックアップは最大1分待ちます。中断したジョブは同じキーで最大5回再実行します。新しい取得処理は、停止した取得処理のロックを解放します。ハートビートが2分間ないと`agent_offline`警告が表示されます。更新時はインストーラーが先にエージェントを停止し、実行中のバックアップは`interrupted`で終了して、再びキューに入ります。

**レート制限。** アドレスごとのサインインカウンターはプロセス内にあり、再起動でリセットします。アカウントのバックオフはデータベースに保存するため維持します。

## 起動時の確認 {#startup-checks}

各プロセスは、処理を開始する前に環境を確認します。確認に失敗すると終了コード1で終了し、`startup.failed`（API）または`worker.unavailable`（ワーカー）を1行記録します。`reason`には秘密情報を含めず、原因を記します。

| プロセス                 | 確認内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API                      | すべての設定値が有効であること。メッセージには変数名だけを含め、値は含めない。キーファイルを最大1 MiBのJSONとして読み取れること。組み込みTLSでは、証明書と鍵を読み取れ、互いに一致し、期限切れでないこと。HTTPへのフォールバックは行わない。ストレージディレクトリに書き込めること。データベースが応答し、このリリースのすべてのマイグレーションを持ち、新しいリリースのものは持たないこと。ストレージディレクトリの`storage-id`ファイルが、データベースに保存した識別情報と一致すること。他の書き込みプロセスがデータベースを所有していないこと |
| ワーカー                 | 同じ設定、データベース、ストレージ識別情報、単一ワーカーのロック。2つ目のワーカーはスタンバイとして待機                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| バックアップエージェント | ストレージ識別情報、スキーマ番号、保管庫がストレージディレクトリと重複しないこと。保管庫がない場合や未マウントの場合は致命的なエラーにせず、警告として報告                                                                                                                                                                                                                                                                                                                                                                                       |

更新後、インストーラーは準備完了の応答が3回連続で成功し、ワーカーが稼働するまで待ちます。その後、バックアップエージェントのハートビートを約90秒待ちます。エージェントが見つからない場合は警告にとどめ、それを理由に更新をロールバックすることはありません。

## 引き続き操作が必要なもの {#operator}

自己修復は、プロセスの障害に対応します。次の場合はオペレーターの対処が必要です。

- **恒久的な問題。** 設定ミス、接続できないデータベース、満杯のディスク、権限の誤りがあると、サービスは10秒ごとに再起動して失敗し続けます。`startup.failed`を読み、原因を修正してください。[トラブルシューティング](./troubleshooting)を参照してください。
- **更新の失敗。** 中断した更新は、`recover`を実行するまでロックとジャーナルを保持します。
- **バックアップの破損。** `verify_failed`と`vault_unavailable`には人の対処が必要です。エージェントは保管庫を変更せずに維持します。
- **証明書。** Arkvoryは更新済み証明書ファイルを再起動せずに読み取ります（デフォルト300秒ごと）が、証明書自体は自分のツールで更新する必要があります。
- **停止したサービス。** 自分で停止したサービスは停止したままです。
- **プラットフォーム。** DockerはOS起動時に開始する必要があります。PostgreSQLのメジャーバージョン、Node.js、OSは自分で更新します。
- **サーバーやディスクの喪失。** 単独構成にはフェイルオーバーがないため、バックアップから復元します。HA クラスターは、レプリケーションとフェンシングの規則に従って別のデータサーバーへ切り替えられます。[バックアップ](./backups)と[高可用性クラスター](./cluster)を参照してください。
