# 高可用性クラスター

Arkvoryクラスターは、サイト内のサーバーが1台故障しても稼働を続けます。2台または3台のLinuxサーバーが、1つのブロックボリュームの同じコピーを保持します。1台が**アクティブ**になり、Arkvoryを実行します。そのサーバーが故障すると、クラスターマネージャーがそのサーバーをフェンシングし、同じデータを使って別のサーバーでArkvoryを起動します。

クラスターは、同一サイト内でのサーバー、ディスク、ネットワークリンクの喪失に備えます。サイト全体の喪失には対応しません。それに備えるには、別のサイトに[ミラー](./mirrors)を、クラスターの外に[バックアップ](./backups)を保持してください。

## 仕組み {#how-it-works}

- **1つのボリューム、同期コピー。** DRBD 9は、ボリュームへの各書き込みを、完了する前に他のサーバーへコピーします（プロトコルC）。データベース、ストレージ、設定、リリースを含むインストール全体がこのボリュームに置かれます。カタログとファイルのバイト列が食い違うことはありません。
- **PacemakerがArkvoryの実行先を決定します。** CorosyncとPacemakerはクォーラムを維持し、アクティブサーバーを選び、ボリューム、ファイルシステム、ボリュームに保存されたサービス定義（`arkvory-units`）、データベース、`arkvory-replica`、API、ワーカー、バックアップエージェント、更新タイマー、仮想IPアドレスの順に起動します。Arkvory自体は選出を行いません。
- **フェンシングは必須です。** 別のサーバーが処理を引き継ぐ前に、Pacemakerは電源制御装置（IPMI、iDRAC、iLO、Redfish、PDU）またはハイパーバイザーを使って、故障したサーバーの電源を切ります。フェンシングがなければ、2台のサーバーが同時に書き込む可能性があります。フェンシングのないクラスターは起動しません。
- **成功を応答したすべての書き込みに2つのコピー。** Arkvoryは、書き込みが少なくとも2つの完全なコピーに保存された場合にのみ成功を応答します（[書き込み](#writes)を参照）。コピーが不足すると書き込みを停止し、読み取りは継続します。

| プロファイル | データサーバー数 | ウィットネス                                                                       | データサーバーが1台故障した場合                                |
| ------------ | ---------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `ha-2`       | 2                | 必須：データを持たず、`corosync-qnetd`とDRBDタイブレーカーを実行する小規模サーバー | サーバーが復帰するか、オペレーターが判断するまで書き込みを停止 |
| `ha-3`       | 3                | 使用しない：3台のサーバーの多数決で決定                                            | 2つのコピーが残るため書き込みを継続                            |

推奨プロファイルは`ha-3`です。`ha-2`は低コストで、データを1つのコピーだけに保存して処理を続けるのではなく、書き込みを停止します。

クラスターはネイティブLinuxパッケージ向けです。WindowsインストールとDocker Composeは、ミラーとバックアップを備えたスタンドアロンサーバーとして運用します。

## 書き込みとコピー {#writes}

**完全なコピー**には、最新状態のアクティブサーバーのローカルディスクと、接続済みでレプリケーションが動作し、最新状態になっている他の各データサーバーが含まれます。再同期中のサーバーは、最新状態になるまで数えません。ウィットネスはデータを持たないため、決して数えません。

データを変更するすべてのリクエスト（HTTP API、コンテナレジストリ、Git LFS、npm）を2回確認します。

- 実行**前**に、直近1秒間のコピー状態を確認します。
- データのコミットと同期の**後**に、ボリュームの状態を新たに読み取って確認します。

完全なコピーの数が書き込みに必要な数を下回ると、クライアントにはコード`unavailable`、理由`replication_degraded`、`Retry-After`ヘッダーを伴うHTTP 503を返し、2xxは返しません。アップロード完了ジョブの状態（`GET /api/v1/jobs/{id}`）も同様に確認します。これは、大きなアップロードが公開済みになったことをクライアントに伝える応答だからです。

コミット後の503は、その操作が1つのコピーにしか保存されていない可能性を示します。同じ`Idempotency-Key`でリクエストを再送してください。再送時は既存の結果を返し、2つのコピーが再びそろうと2xxで確定を通知します。

書き込み停止中も、読み取り、ダウンロード、コンソール、サインインとサインアウト、フィードバック、Git LFSのバッチリクエストは利用できます。

コンソールにサインインした管理者には、書き込み停止中、または単一コピーでの運用判断が有効な間、バナーを表示します。

## 要件 {#requirements}

- 同じLinuxディストリビューション、同じArkvoryパッケージバージョンを使用する2台または3台のデータサーバー。それぞれに、ボリューム全体を保存できる容量のディスク（または論理ボリューム）が必要です。ストレージ全体とデータベースの容量を見込んでください。
- `ha-2`では、ウィットネスとして3台目の小規模サーバーが必要です。データ用ディスクは不要で、Arkvoryも実行しません。
- サーバー間の低遅延ネットワーク。すべての書き込みが他のサーバーを待つため、各書き込みに通信遅延が加わります。可能なら専用リンクを使用してください。
- DRBD 9（カーネルモジュールと`drbd-utils` 9。多くのディストリビューションは古い8.4モジュールを同梱するため、LINBITパッケージを使用）、`pacemaker`、`pcs`、`corosync`、`resource-agents`（Ubuntuでは`resource-agents-base`と`resource-agents-extra`）、使用するハードウェア用のフェンスエージェント。`ha-2`では、データサーバーに`corosync-qdevice`、ウィットネスに`corosync-qnetd`が必要です。
- 各データサーバーのフェンス装置と、その認証情報。
- サーバーのネットワーク内の未使用IPアドレス。クライアントはこの仮想アドレスに接続します。
- 仮想アドレス用のTLS証明書。すべてのサーバーが同じパスで参照できるよう、証明書と秘密鍵をボリュームに保存してください。

## クラスターの構築 {#build}

以下のコマンドは、デフォルトのリソース名`arkvory`、インストールディレクトリ`/opt/proanima-arkvory`、基盤ディスク`/dev/vg0/arkvory`を使用します。rootとして実行してください。

1. すべてのデータサーバーで、Arkvoryパッケージをインストールせずに展開します。ファイルと`arkvory`コマンドが追加されますが、`/opt/proanima-arkvory`には何も作成されません。

   ```bash
   dpkg --unpack Arkvory-amd64.deb
   ```

   RPMパッケージでは、スクリプトを実行せずにファイルをインストールします：`rpm -i --noscripts Arkvory-x86_64.rpm`。最初のサーバーでは、代わりに手順5で通常どおりパッケージをインストールするため、手順2の計画作成は別のデータサーバーで行ってください。

2. いずれか1台のデータサーバーで計画を作成します。確認できるよう、DRBDリソースとPacemakerコマンドがディレクトリに書き出されます。

   ```bash
   arkvory cluster-plan --cluster ha-2 \
     --nodes node-a=10.0.0.11,node-b=10.0.0.12 --witness witness=10.0.0.13 \
     --disk /dev/vg0/arkvory --fence-agent fence_ipmilan \
     --virtual-ip 10.0.0.100/24 --output /root/arkvory-plan
   ```

   `ha-3`では、`--nodes`に3台のサーバーを指定し、`--witness`を省略します。任意のオプションは`--cluster-resource`、`--drbd-minor`（デフォルト0）、`--drbd-port`（デフォルト7789）、`--filesystem`（`xfs`または`ext4`、デフォルト`xfs`）です。名前は各サーバーのホスト名でなければなりません。アドレスはIPv4です。

3. ウィットネスを含むすべてのサーバーで、`arkvory.res`を`/etc/drbd.d/`にコピーします。データサーバーでメタデータを作成し、すべてのサーバーでリソースを起動します。

   ```bash
   drbdadm create-md arkvory   # データサーバーのみ
   drbdadm up arkvory          # すべてのサーバー
   ```

   ウィットネスでは、再起動後もタイブレーカーが復帰するよう、`systemctl enable drbd@arkvory.service`も実行します。

   この計画では、復帰したコピーを、書き込み負荷がある場合でも最低20 MB/s、最大1 GB/sで再同期できます。`disk`セクションの`c-min-rate`と`c-max-rate`を、レプリケーションリンクの能力に合わせて設定してください。

4. 最初のデータサーバーをプライマリにし、ファイルシステムを作成してマウントします。新品の空のディスクでは、最初に初期同期を省略します。

   ```bash
   drbdadm new-current-uuid --clear-bitmap arkvory/0
   drbdadm primary arkvory
   mkfs.xfs /dev/drbd0
   mkdir -p /opt/proanima-arkvory && mount /dev/drbd0 /opt/proanima-arkvory
   ```

5. マウントしたボリュームにArkvoryをインストールし（RPMでは`dpkg --configure`の代わりに`rpm -i Arkvory-x86_64.rpm`）、TLSファイルをボリュームに配置して、クラスターモードを有効にします。

   ```bash
   dpkg --configure proanima-arkvory
   install -d -m 0750 -o root -g arkvory /opt/proanima-arkvory/config/tls
   install -m 0644 tls.crt /opt/proanima-arkvory/config/tls/tls.crt
   install -m 0640 -g arkvory tls.key /opt/proanima-arkvory/config/tls/tls.key
   arkvory configure --root /opt/proanima-arkvory --tls-cert /opt/proanima-arkvory/config/tls/tls.crt --tls-key /opt/proanima-arkvory/config/tls/tls.key --listen-host 0.0.0.0
   arkvory configure --root /opt/proanima-arkvory --cluster ha-2
   ```

   `configure --cluster`は、インストールディレクトリがマウント済みのDRBDデバイスであること、このサーバーがプライマリであること、少なくとも2つのコピーが完全であることを確認します。`arkvory-replica`を起動し、完全なコピーが2つある場合にのみArkvoryが書き込みを成功として応答するよう設定し、Arkvoryサービスの自動起動を無効にします。以後はPacemakerが起動を管理します。いずれかの処理が失敗すると、スタンドアロン設定に戻します。

6. 最初のサーバーでArkvoryを停止し、ボリュームを解放します。

   ```bash
   arkvory cluster-release --root /opt/proanima-arkvory
   ```

   このコマンドはArkvoryサービスを順番に停止し、ボリュームをアンマウントして、このサーバーをセカンダリにします。

7. 他の各データサーバーを1台ずつ準備します。

   ```bash
   arkvory cluster-node --root /opt/proanima-arkvory
   dpkg --configure proanima-arkvory   # .debのみ。RPMでは追加の処理は不要
   ```

   `cluster-node`はボリュームを取得し、サーバーを準備してから、ボリュームを再び解放します。途中で失敗した場合も解放し、最初のエラーを報告します。`--cluster-resource`はリソース名が`arkvory`でない場合にのみ必要です。ボリュームをマウントしてすでにクラスターの処理を提供しているサーバーでは拒否します（先に`cluster-release`で解放してください）。PacemakerがArkvoryグループを管理している間も、ボリュームがクラスターに属するため拒否します。稼働中のクラスターにサーバーを追加する手順は[サーバーの交換](#replace-node)を参照してください。`cluster-node`は、最初のサーバーと同じユーザーIDとグループIDでサービスアカウントを作成し（ボリューム上のファイルはこれらのアカウントが所有）、同じサービスをインストールします。いずれのサービスも自動起動しません。異なるIDのアカウントがすでに存在すると、コマンドは停止し、設定すべきIDを表示します。サーバーがアクティブになるたびに、`arkvory-units`が最初にボリュームからサービス定義を取得します。そのため、後でアクティブサーバー上で変更した設定（バックアップ保管庫など）も、フェイルオーバー後に適用されます。

8. データサーバーで`pcs`を使い、Corosyncクラスターを設定します（`pcs host auth`、`pcs cluster setup`、`pcs cluster start --all`）。DebianとUbuntuでは、先に各データサーバーで`pcs cluster destroy`を実行してください。パッケージがインストールするCorosyncのサンプル設定を、`pcs`が既存のクラスターと見なすためです。`pcs cluster enable`は実行しないでください。フェンシングされたサーバーは、手動で開始したときだけ再参加させます。`ha-2`では、ウィットネスも認証し、その上で`pcs qdevice setup model net --enable --start`を実行します。DebianとUbuntuでは、パッケージが専用サービスアカウント用のクォーラムデバイスをすでに設定しているため、代わりにそのサーバーで`systemctl enable --now corosync-qnetd`を実行してください。

9. `/root/arkvory-plan/pacemaker.sh`を開きます。各`<agent parameters: …>`を、フェンス装置のパラメーター（アドレス、ログイン名、パスワードファイルまたは鍵、そのサーバーのプラグまたはポート）に置き換えます。その後、いずれか1台のデータサーバーでスクリプトを実行します。

   ```bash
   sh /root/arkvory-plan/pacemaker.sh
   ```

   このスクリプトは、フェンシング、クォーラムポリシー、DRBDリソース、Arkvoryグループとその制約を含む設定全体をファイルに構築し、一括で適用します。

10. アクティブサーバーでクラスターを確認します。

    ```bash
    arkvory cluster-check --root /opt/proanima-arkvory
    ```

    このコマンドは、クォーラム、フェンシングの有効化、すべてのサーバーにフェンス装置があること、DRBDのクォーラムとフェンシングの設定、少なくとも2つの完全なコピーがあること、Arkvoryがちょうど1台のサーバーで稼働していることを確認します。確認に失敗するとエラー終了します。

11. 各スタンバイサーバーを一度フェンシングして復帰させ、動作を検証します（[フェンシングのテスト](#fence-test)を参照）。

クライアントとDNS名の接続先を仮想アドレスに設定してください。

## 日常の運用 {#operation}

これらのコマンドはrootとして実行してください。`cluster-status`、`cluster-single-copy`、`cluster-kit`はボリュームを読み取るため、アクティブサーバーで実行します。`cluster-check`、`cluster-switchover`、`cluster-fence-test`は、どのデータサーバーでも実行できます。

| コマンド                                                                  | 動作                                                                                                    |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `arkvory cluster-status --root <dir>`                                     | プロファイル、このサーバーの役割、完全なコピー数と必要なコピー数、オペレーターの判断をJSONで表示        |
| `arkvory cluster-check --root <dir>`                                      | 正常なクラスターに必要なすべての確認を実行し、1つでも失敗するとエラー終了                               |
| `arkvory cluster-switchover --root <dir> --to <server>`                   | 別のデータサーバーへArkvoryを計画的に移動。移動先が完全なコピーを保持していなければ拒否                 |
| `arkvory cluster-fence-test --root <dir> --node <standby> [--yes]`        | フェンス装置を検証するため、スタンバイサーバーをフェンシング。アクティブサーバーは対象にできない        |
| `arkvory cluster-single-copy --root <dir> --until <time> --reason <text>` | 指定時刻まで単一コピーでの書き込みを受け付ける。[単一コピー](#single-copy)を参照                        |
| `arkvory cluster-kit --root <dir> --output <file>`                        | アクティブサーバーで、新しいサーバーの参加に必要なファイルを作成。[サーバーの交換](#replace-node)を参照 |
| `arkvory cluster-node --root <dir> --kit <file>`                          | 新しいサーバーで、ボリュームを取得せずにそのファイルを使って参加                                        |

`pcs status`は、Pacemakerが認識しているクラスターの状態を表示します。

### コンソールでの確認 {#console}

クラスター構成の管理者は、メニューから[[ui:cluster]]を開けます。このページには、構成、現在処理を提供しているサーバー、完全なコピー、書き込みを受け付けているかどうか、他の各サーバーの接続状態とコピーの状態（[[ui:clusterCopyComplete]]、[[ui:clusterCopySyncing]]、[[ui:clusterCopyMissing]]）を表示します。その下の[[ui:clusterNextStep]]には、現在の状態に合う次の1つの手順とコマンドを表示します。すべてのコピーが完全なら計画的な切り替え、コピーが不足していればサーバーの復帰または交換（`ha-3`で2つのコピーによる書き込みが続いている場合も含む）、単一コピーでの運用判断が有効ならその終了方法です。ページは15秒ごとに自動更新します。

書き込みを停止すると、すべての画面にその旨のバナーを表示します。管理者はバナーからこのページを開けます。管理権限のないユーザーには、ダウンロードは引き続き利用でき、アップロードは一時停止することだけを表示します。

### 計画的な切り替え {#switchover}

`cluster-switchover`はPacemakerにグループの移動を要求し、移動先でArkvoryが稼働するまで最大5分待ってから、一時的な配置ルールを削除します。再同期中など、移動先が自身の完全なコピーを持っていない間は拒否します。移動中は旧サーバーへの接続が切れるため、クライアントはリクエストを再送します。Arkvoryが自動で元のサーバーへ戻ることはありません。

### フェンシングのテスト {#fence-test}

`cluster-fence-test`は最初に`cluster-check`の確認を実行し、1つでも失敗すると拒否します。`ha-2`では、唯一のスタンバイをフェンシングすると復帰まで書き込みが停止するため、`--yes`も必要です。フェンス装置を通じてスタンバイを再起動します。再起動後、そのサーバーで`pcs cluster start`を実行してクラスターを開始してください。再起動後にクラスターサービスが自動起動することはありません（[クラスターの構築](#build)の手順8）。そのため、フェンシングされたサーバーが操作なしで再参加することはありません。

### 更新 {#updates}

すべてのデータサーバーに新しいパッケージをインストールしてください。リリースはボリューム上にあるため、スタンバイサーバーではパッケージがプログラムファイルだけを置き換えます。アクティブサーバーでは、パッケージがリリースを適用します。ArkvoryはPacemakerにグループへの介入を停止させ、サービスを停止し、移行を実行し、サービスを起動し、準備完了まで待ってから、グループを管理下に戻します。アクティブサーバーでの自動更新も同じ手順です。更新とロールバックの両方が失敗すると、グループは管理対象外のままとなり、Pacemakerはフェイルオーバーしません。原因を解消してから、`pcs resource cleanup arkvory`と`pcs resource manage arkvory`を実行してください。

クラスターサーバー上で`systemctl`を使ってArkvoryサービスを起動または停止しないでください。Pacemakerが障害と見なします。サービス全体を計画的に停止する場合は、`pcs resource disable arkvory`と`pcs resource enable arkvory`を使用してください。

## 障害 {#failures}

| 発生した事象                                                   | `ha-2`                                                                                                                        | `ha-3`                                                                |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| スタンバイサーバーが故障                                       | フェンシング。読み取りは継続し、書き込みは503 `replication_degraded`を返す                                                    | フェンシング。読み取りと書き込みを継続                                |
| アクティブサーバーが故障                                       | フェンシングし、もう一方のサーバーでArkvoryを起動。読み取りは復旧し、書き込みは2つ目のコピーを待つ                            | フェンシングし、別のサーバーでArkvoryを起動。読み取りと書き込みが復旧 |
| データサーバー間のネットワーク分断                             | ウィットネスが一方にクォーラムを与え、もう一方をフェンシング。書き込みを行うサーバーが2台になることはない                     | 過半数側が継続し、もう一方のサーバーをフェンシング                    |
| 3メンバーのうち2つが故障（ha-2：データサーバーとウィットネス） | 残りのサーバーにクォーラムがないためArkvoryを停止。クォーラムなしで書き込みを行うことはない。サーバーを復帰させる（下記参照） | 2台のデータサーバーが故障した場合も同じ                               |
| フェンシングが機能しない                                       | フェイルオーバーしない。フェンシングが成功するまでArkvoryは停止したまま                                                       | 同じ                                                                  |

フェンシングされたサーバーを復帰させるには：

1. 原因を修復し、サーバーを起動します。
2. そのサーバーで`pcs cluster start`を実行します。
3. ボリュームが変更されたブロックを再同期します。必要なすべてのコピーが再び完全になると、書き込みは自動で再開します。`arkvory cluster-status`で進捗を確認できます。

クォーラムを失った後は、復帰したすべてのサーバーでクラスターを開始してください。Pacemakerは最新のコピーを持つサーバーでArkvoryを再起動します。最後にクォーラムを失ったサーバーは正常に停止できていなかった可能性があるため、復帰時に再度フェンシングされることがあります。その場合は、再起動後にそのサーバーでクラスターをもう一度開始してください。

フェンシングの失敗原因を修復したら、稼働中のサーバーで失敗履歴を消去し、Pacemakerに再試行させます：`pcs stonith history cleanup <server>`と`pcs resource cleanup`。

### サーバーの交換 {#replace-node}

データサーバーを復旧できなくなったら、同じ名前とアドレスを持つ新しいサーバーに交換します。作業中も、アクティブサーバーのArkvoryは処理を提供し続けます。新しいコピーが完全になると書き込みが再開します。

1. 新しいサーバーに同じLinuxディストリビューション、DRBD、Pacemaker、フェンスエージェントをインストールし、[クラスターの構築](#build)の手順1と同様に、同じバージョンのArkvoryパッケージを展開します。`ha-2`では`corosync-qdevice`もインストールしてください。
2. アクティブサーバーで、新しいサーバーに必要なリソース名、サービスアカウントのID、サービスを含むファイルを書き出します。

   ```bash
   arkvory cluster-kit --root /opt/proanima-arkvory --output /root/arkvory-node.kit
   ```

   安全な経路で新しいサーバーにコピーします。秘密情報は含みませんが、クラスターの構成を記述したファイルです。

3. 新しいサーバーで、そのファイルを使って参加します。ボリュームは必要ありません。

   ```bash
   arkvory cluster-node --root /opt/proanima-arkvory --kit /root/arkvory-node.kit
   dpkg --configure proanima-arkvory   # .debのみ
   ```

4. 他のデータサーバーから`/etc/drbd.d/arkvory.res`をコピーし、メタデータを作成してリソースを起動します。新しいコピーへのデータ転送がアクティブサーバーから始まります。

   ```bash
   drbdadm create-md arkvory
   drbdadm up arkvory
   ```

5. クラスターメンバーを置き換えます。アクティブサーバーで`pcs host auth <server>`、`pcs cluster node remove <server>`、`pcs cluster node add <server> addr=<address> --start`の順に実行します。新しいサーバーが同じ装置設定で応答するなら、フェンス装置の設定はそのまま利用できます。そうでなければ`pcs stonith update`で更新してください。
6. コンソールの[[ui:cluster]]または`arkvory cluster-status`を確認します。コピーが完全になるまでサーバーは[[ui:clusterCopySyncing]]と表示されます。完了すると書き込みが自動で再開します。
7. `arkvory cluster-fence-test --node <server> --yes`で新しいサーバーのフェンス装置を検証し、`arkvory cluster-check`を実行します。

### 単一コピー {#single-copy}

ディスク交換などでデータサーバーが長期間復帰せず、書き込み停止の損失がリスクを上回る場合、オペレーターは期間を限定して1つのコピーで書き込みを受け付けるよう設定できます。

```bash
arkvory cluster-single-copy --root /opt/proanima-arkvory --until "$(date -u -d '+2 hours' +%Y-%m-%dT%H:%M:%SZ)" --reason "disk replacement on node-b"
```

- 時刻は今後7日以内で、UTCの`Z`や`+03:00`などのオフセットを付ける必要があります。タイムゾーンがなければ、アクティブサーバーが自身のローカル時刻として解釈してしまうため、コマンドは拒否します。このコマンドはコピーが不足している間だけ使用できます。
- この判断が有効な間にアクティブサーバーを失うと、判断後に成功を応答した書き込みが失われます。
- コンソールのバナー、メトリクス`arkvory_replication_required_copies`、アラート`ArkvorySingleCopyWrites`で、この判断が有効であることを確認できます。
- 指定時刻に達したとき、`--off`を指定したとき、またはすべてのコピーが再び完全になった時点で自動的に終了します。その後にコピーを失えば、再び書き込みを停止します。

## 監視 {#monitoring}

書き込み停止中も、アクティブサーバーの`GET /health/ready`は200を維持します。これにより、監視が正常なサーバーを移動させることを防ぎます。フィールド`writable`は`false`になり、`replication`フィールドは`copies`、`required`、`singleCopyUntil`を示します。コピー状態を読み取れない場合、`replication`は`null`です。管理者向けには、`node`（応答しているサーバー）、`profile`、他のサーバーの接続状態とコピーを示す`peers`も含み、[コンソールのページ](#console)に表示します。スタンドアロンサーバーには`replication`フィールドはありません。

| メトリクス                                 | 意味                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `arkvory_replication_copies`               | 最後の確認時点での完全なコピー数                                       |
| `arkvory_replication_required_copies`      | 書き込みに必要なコピー数：通常は2、単一コピーでの運用判断が有効な間は1 |
| `arkvory_replication_writes_refused_total` | 503 `replication_degraded`で応答した書き込み数                         |
| `arkvory_replication_check_failures_total` | コピー状態の読み取り失敗数                                             |

`deploy/monitoring/arkvory-alerts.yml`のアラートルールには、`ArkvoryReplicationDegraded`、`ArkvorySingleCopyWrites`、`ArkvoryReplicationCheckFailing`が含まれます。クラスター自体も監視してください。`arkvory cluster-check`を定期実行して終了コードで通知するか、Pacemaker環境の監視を使用します。[監視](./monitoring)を参照してください。

## バックアップ {#backups}

バックアップエージェントは、グループの一部としてアクティブサーバー上でのみ稼働します。バックアップ保管庫は、NASなど、クラスターボリュームの外に置いてください。[バックアップ](./backups)を参照してください。

## 制限 {#limits}

- ネイティブパッケージを使用するLinuxのみです。WindowsインストールとDocker Composeはクラスターに参加できません。
- フェンシングは必須です。各データサーバー用のフェンス装置がなければクラスターは起動せず、Pacemakerはフェンシングの完了を確認せずにArkvoryを移動しません。SSHによるサーバー停止はフェンシングではありません。
- `ha-2`のウィットネスは、データサーバーと電源もホストも共有しない別のマシンに置く必要があります。データサーバー上や同じハイパーバイザー上に置くと、1回の故障でクォーラムを失います。`ha-3`ではウィットネスは不要です。
- 各リリースは、`fence_virsh`を使った仮想マシンでテストします。使用するフェンスエージェントと装置（IPMI、iDRAC、iLO、Redfish、PDU、ハイパーバイザー）はその対象ではありません。クラスターを運用上の前提にする前に、現地ですべてのデータサーバーに対して`arkvory cluster-fence-test`を実行し、サーバーの交換やフェンス装置の変更後にも再検証してください。
- 対象は1つのサイトのみです。サイトの喪失や、ボリュームから全サーバーに複製される削除・破損には対応しません。別のサイトに[ミラー](./mirrors)を置き、[バックアップ](./backups)を保持してください。
- [単一コピーでの運用判断](#single-copy)が有効な間にアクティブサーバーを失うと、判断後に成功を応答した書き込みが失われます。
- すべての書き込みが他のデータサーバーを待つため、各書き込みにリンクの遅延が加わります。
- Arkvoryが修復済みのサーバーへ自動で戻ることはありません。

ha-2の生成計画では、DRBDノードIDが最小のノードに対するフェンシングを15秒遅延させます（`pcmk_delay_base`）。もう一方の対象には遅延を設けません。この遅延が、実測したフェンシング所要時間と障害検出時刻のずれを上回る場合、同時のフェンシング要求で両ノードの電源が切れることを防ぎます。実際のフェンスエージェントでこの余裕を検証してください。既存のクラスターでは、対応する`pcs stonith update`コマンドを適用し、両方向の障害テストを再実行する必要があります。計画の再生成だけではクラスターは更新されません。クォーラムと必須のフェンシングは引き続き有効です。
