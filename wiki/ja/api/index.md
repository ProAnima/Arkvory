# HTTP APIの概要

HTTP APIは、Webコンソール、コマンドラインクライアント、SDKが使用するインターフェースです。これらが行う操作は、任意の言語の連携からも実行できます。このページでは、すべての操作に適用する規則を説明します。[リファレンスのページ](#reference-pages)には、操作ごとのアクセス規則、再試行規則、パラメーター、応答を記載します。これらは、サーバーが適用する契約から生成します。

## 基本 {#basics}

- **ベースパス。** すべての操作は`/api/v1`の下にあります。例は`https://arkvory.example/api/v1/repositories`です。例外は`/health`のヘルスチェックだけです。
- **形式。** リクエストと応答はJSON（`application/json`）です。JSON本文の上限は64 KiBで、JSON操作に別のコンテンツタイプを送ると`415`になります。ファイルのバイト列は`application/octet-stream`で送信します。
- **未知のフィールド。** ほとんどの操作は、定義していないフィールドがあるリクエストを拒否します（`400`。`details`にフィールドを表示）。応答では、知らないフィールドを無視してください。
- **時刻**はUTCのRFC 3339タイムスタンプです。アーティファクト、アップロード、ジョブ、アカウント、キーの**ID**はUUIDです。
- **名前。** リポジトリ名は`[a-z0-9][a-z0-9_-]{0,63}`に一致します。ファイル名（アーティファクト名）は最大240文字で、`/`と`\`は使えません。リポジトリ内のパスは最大1,024文字です。
- **キャッシュ。** 応答には`Cache-Control: private, no-store`が付きます。
- **他のプロトコル。** `/v2`（コンテナ）、`/lfs`（Git LFS）、`/npm`は、各クライアントの仕様と独自のエラー形式に従います。OpenAPI文書には含みません。[クライアントとプロトコル](../protocols/index)を参照してください。

### サイズと件数 {#sizes}

JSONの数値では、すべての64ビット値を表せません。そのため、Arkvoryは**サイズとバイトカウンターを10進文字列で送信**します。例は`"size": "1048576"`です。アップロード作成時に申告するサイズも同じです。サイズには符号や先頭のゼロを付けず、16桁以内にします。件数、リビジョン、上限、パートインデックスは通常のJSON整数です。

管理者が`ARKVORY_MAX_OBJECT_BYTES`を引き下げない限り、オブジェクトの最大サイズは10,000 GiB（10 737 418 240 000バイト）です。それより大きい申告サイズは`400`で拒否します。

## 認証 {#authentication}

サインイン、自己登録、公開ヘルスチェック、サインインの選択肢を除くすべての操作には、`Authorization: Bearer <credential>`ヘッダーの認証情報が必要です。自己登録（`POST /api/v1/auth/register`、`registerAccount`）には認証情報が不要です。管理者が`ARKVORY_ALLOW_REGISTRATION=true`を設定した場合にのみ成功する可能性があり、無効の場合は理由`registration_disabled`付きの`403`を返します。認証情報には、コンソールセッション、個人用アクセストークン、サービスキー、回復キーを使用します。許可される操作は、認証情報の種類と各操作の**アクセス規則**で決まります。連携を設計する前に[認証](./authentication)を読み、自動化には必要な操作だけを許可するサービスキーを付与してください。

## 機能の検出 {#discovery}

クライアントは推測せずに、サーバーの対応機能を問い合わせることができます。次のすべてに認証情報が必要です。

| リクエスト                     | 応答                                                                                                                                                                                                                                                                                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/capabilities`     | APIバージョン（`v1`）、ゲートウェイの役割（`api`または`reader`）、機能フラグ、サーバーの制限：`maxObjectBytes`、`partBytes`（最小パート、8 MiB）、`maxPartBytes`（1 GiB）、`maxParts`（10,000）、`maxPageSize`（100）                                                                    |
| `GET /api/v1/operations`       | この認証情報で呼び出せる可能性がある操作。それぞれの`operationId`、メソッド、パス、`surface`、`retry`クラス、必要な操作権限、残る条件を表示。`repository`、`surface`、`after`、`limit`（1～100、デフォルト50）で絞り込み可能。この一覧は参考情報であり、最終判断は実際のリクエストで行う |
| `GET /api/v1/openapi.json`     | 書き込みAPIのOpenAPI 3.0.3文書。`?surface=<name>`を追加すると1つの領域だけを取得                                                                                                                                                                                                         |
| `GET /api/v1/auth/permissions` | 呼び出し元の認証情報に許可された、リポジトリごとの操作                                                                                                                                                                                                                                   |
| `GET /api/v1/auth/me`          | 認証情報の主体、種類、大まかな`read`/`write`の許可                                                                                                                                                                                                                                       |
| `GET /api/v1/repositories`     | 認証情報が参照できるリポジトリ                                                                                                                                                                                                                                                           |

制限を固定値として埋め込まず、`capabilities`から取得してください。知らない機能フラグは`false`として扱います。

### 領域 {#surfaces}

操作は6つの**領域**に分類します。契約上のラベルであり、別々のサービスではありません。URLは変わりません。

| 領域             | 対象                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `discovery`      | 対応機能、操作カタログ、OpenAPI、リポジトリ                                                  |
| `identity`       | サインイン、呼び出し元自身の識別情報、トークン、キーの有効化                                 |
| `catalog`        | アーティファクト、注釈、パッケージ、パス指定ファイル、ステージ、プロモーション、添付ファイル |
| `transfers`      | アップロードセッション、パート、完了ジョブ、ダウンロード                                     |
| `administration` | アカウント、グループ、サービスアカウント、キー、委任、更新、バックアップ                     |
| `operations`     | 稼働、準備状態、メトリクス、フィードバック                                                   |

ヘルスチェックには、認証情報が不要な`GET /health/live`（プロセスが稼働）と`GET /health/status`（公開。`{"status":"ready"}`または`unavailable`）、認証情報が必要な`GET /health/ready`と`GET /health/metrics`があります。リクエスト枠を使わないため、負荷を理由にロードバランサーがサーバーを除外することを防ぎます。

## ページ分割 {#pagination}

一覧は1ページずつ返します。応答には`items`と`next`があります。`next`が`null`でなければ、その値を変更せずクエリパラメーター`after`に渡して次ページを読みます。`null`なら一覧の終わりです。カーソルは内部構造を解釈せず、そのまま扱い、自分で作成しないでください。

`limit`で1～100のページサイズを設定します。省略時は、ほとんどの一覧が50件を返します。ページはスナップショットではないため、読み取り中に追加された項目が表示される場合とされない場合があります。`next`をたどる間、フィルターと並び順を維持してください。

## リビジョンと比較交換 {#revisions}

人が編集するものには、1から増加する**リビジョン**があります。アーティファクトのラベル・メタデータ・コレクション、ビルドの添付ファイル、ファイルパス、ストレージポリシー、バックアップ計画、サービスアカウントの設定が対象です。変更時は、リクエスト本文の`expectedRevision`に期待するリビジョンを指定します。

```json
{ "expectedRevision": 3, "value": { "labels": ["tested"], "metadata": {}, "collections": [] } }
```

現在のリビジョンが3でなければ、何も変更せず、理由`revision_mismatch`を伴う`409`を返します。これが**比較交換（compare-and-swap）**です。状態を再取得し、その状態に変更を適用して、新しいリビジョンを送ってください。数値を増やして書き込みを強制するループは作らないでください。新しいパスなど、まだ存在しないものには`0`を使用します。APIは`If-Match`ヘッダーを使用しません。

**ダウンロードしたアーティファクト**には、別の検証子`ETag`があります。[範囲ダウンロードとETag](#range-downloads)を参照してください。

## 冪等キー {#idempotency}

`Idempotency-Key`ヘッダーを使うと、リクエストを繰り返しても効果は1回分になります。英字、数字、`_ . : -`からなる1～128文字の値を使い、最初のリクエスト前にジョブの状態と一緒に保存してください。再起動したジョブも同じキーで再試行できます。次の書き込みにはこのキーが必要です。

| 操作                                                                | 同じキーと本文による再試行                                                                            |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `createUpload`                                                      | 同じアップロードセッションを返す                                                                      |
| `issueServiceKey`と`rotateServiceKey`                               | 秘密情報なしで、キーのメタデータを`200`で返す。秘密情報を失った場合は、キーを取り消して別のキーを発行 |
| `requestBackupRun`、`requestBackupVerify`、`requestBackupRetention` | 別の要求をキューに追加せず、同じ要求を返す                                                            |

同じキーに異なる本文を指定すると、`409`と理由`idempotency_mismatch`で拒否します。キーのスコープは呼び出し元と対象に限定するため、異なる呼び出し元が同じ値を使用できます。

他の書き込みも、状態の設定（ステージ設定、パッケージ登録、キーの取り消し）、または比較交換であるため、安全に繰り返せます。どれに該当するかは次の節で説明します。

## 再試行の規則 {#retry-rules}

各操作には**再試行クラス**があります。応答を受け取れなかったときのクライアントの動作を指定します。リファレンスでは、各操作の再試行の項目に表示します。

| クラス             | 意味                                     | 対処                                                                                                                                            |
| ------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `read`             | 読み取りは何も変更しない                 | バックオフを設けて再試行                                                                                                                        |
| `idempotent`       | 同じリクエストの効果は同じ               | 再試行。詳細な応答は異なる場合がある。例えば2回目の削除で、対象がすでにないと報告する場合がある                                                 |
| `idempotency-key`  | キーがある場合だけ安全                   | 同じ`Idempotency-Key`と同じ本文で再試行                                                                                                         |
| `compare-and-swap` | リビジョンに依存する変更                 | 状態を読み、改めて判断し、取得したリビジョンで再試行。`409`を回避するために`expectedRevision`を引き上げない                                     |
| `reconcile-upload` | アップロードセッションの1段階            | 先にアップロードとパートを取得（`getUpload`、`listUploadParts`）し、不足分を送信。ファイル全体の`PUT`は途中から再開できず、最初のバイトから再送 |
| `reconcile-job`    | 完了ジョブをキューに追加                 | 先にジョブを取得（`getCompletionJob`）。失敗したジョブは再度キューに追加可能                                                                    |
| `never-automatic`  | 繰り返すと操作を二重実行する可能性がある | 自動再試行しない。結果を確認してから判断。例：アカウント、トークン、ダウンロードリンクの作成、ストレージポリシーの実行、フィードバックの送信    |

ネットワーク障害と`408`、`429`、`502`、`503`、`504`は一時的です。クラスに従って再試行し、少なくとも`Retry-After`の時間だけ待ち、試行回数を制限した指数バックオフを加えてください。リクエストを変えずに`401`、`403`、他の`4xx`を再試行しないでください。`500`を無条件に再試行せず、リクエストIDをサポートに伝えてください。変更操作で`503`を受け取った場合は結果が不明なので、クラスに従って実際の結果を確認します。SDKとコマンドラインクライアントもこの規則を適用します。

## 範囲ダウンロードとETag {#range-downloads}

`…/artifacts/{id}/content`の`GET`と`HEAD`は、元のバイト列と、`"sha256:<hex>"`形式の強い`ETag`、`Accept-Ranges: bytes`を返します。パッケージ（`…/packages/content`）とファイルパス（`…/asset/content`、`…/raw/{path}`）によるダウンロードも同じです。各リクエストで現在のアーティファクトを特定します。`packages/content`と`raw`は、再開時に固定できるよう、選択したアーティファクトを`X-Arkvory-Artifact-Id`に示します。

- `Range: bytes=0-1023`、`bytes=1024-`、`bytes=-1024`は、`Content-Range`付きの`206`を返します。サーバーは1つの範囲に対応し、範囲リストにはファイル全体を返します。
- ファイル末尾を超える開始位置には、コード`invalid_input`、理由`range_not_satisfiable`、`Content-Range: bytes */<size>`付きの`416`を返します。
- 再開するには、`Range`と`If-Range: "<the ETag you saw>"`を一緒に送ります。名前が指すコンテンツが変わった場合、`ETag`が異なるため、異なる内容が混ざる代わりに新しいファイル全体を受け取ります。
- `ETag`を指定した`If-None-Match`は、本文なしの`304`を返します。
- 保存した内容のSHA-256を検証してください。ETagにその値が含まれます。

ダウンロードリンク（`?token=`）は、1つのアーティファクトのコンテンツルートで使えます。[認証](./authentication#download-links)を参照してください。

## エラー {#errors}

すべての失敗は共通のJSONエンベロープです。`code`、`message`、`requestId`と、追加情報がある場合は`reason`、`details`、`retryAfterSeconds`を含みます。`message`ではなく、`code`と`reason`で判断してください。未知の理由は存在しないものとして扱い、未知の`code`はHTTPステータスに基づいて処理します。[エラー](./errors)を参照してください。

## レート制限とビジー状態のサーバー {#rate-limits}

Arkvoryは、1分あたりのAPI呼び出し数を計測して制限する方式ではありません。同時に処理する量と、パスワードを推測する試行を制限します。

- **ビジー。** サーバーは、同時に受け付けるリクエストと転送の数を制限します（`ARKVORY_MAX_REQUESTS`はデフォルト128、アップロードは2、ダウンロードは16）。転送は上限付きキューで最大20秒待つことがあります。空きがなければ、コード`busy`付きの`503`を返します。`Retry-After`の後に再試行してください。
- **容量。** ディスクの予備領域不足、クォータ、オブジェクト数の上限は`507`を返し、待つだけでは改善しません。
- **試行。** サインイン、登録、パスワード、フィードバックの試行が多すぎると、コード`rate_limited`付きの`429`を返します。[認証](./authentication#sign-in-limits)を参照してください。

`429`と`503`には、秒単位の`Retry-After`ヘッダー（サーバーが推定できない場合は2）と、同じ数値の`retryAfterSeconds`が付きます。プロキシを通るリクエストには、プロキシ独自の制限が加わる場合があります。

## リクエストID {#request-ids}

すべての応答に`X-Request-Id`ヘッダーが付き、すべてのエラーの`requestId`にも同じ値が入ります。自分のジョブと一緒に記録し、サポートに伝えてください。送信したリクエストIDが使われるのは、`ARKVORY_TRUSTED_PROXIES`に指定したプロキシを経由し、安全な文字による8～128文字の値である場合だけです。それ以外では、サーバーが新しいIDを作成します。W3Cの`traceparent`ヘッダーは、サーバーのアクセスログにだけ記録します。

## ブラウザーとCORS {#cors}

Arkvoryと同じアドレスのWebページは、設定なしで動作します。別のアドレスのページは、管理者が`ARKVORY_CORS_ORIGINS`に正確なオリジンを登録した場合だけ動作します（最大16個、HTTPSまたはループバックHTTP）。それ以外のオリジンには、キーが有効でも理由`origin_not_allowed`付きの`403`を返します。リクエストでCookieを使うことはありません。キーは`Authorization`ヘッダーで送信し、メモリ内に保持してください。[環境変数](../reference/environment)を参照してください。

## 互換性の保証 {#evolution}

`/api/v1`は、新しい操作、任意のリクエストフィールド、応答フィールド、エラーの理由、機能フラグの追加だけで変更します。意味の変更、新しい必須フィールド、異なるステータス、ページ分割の変更など、クライアントを壊す変更には、新しいAPIバージョンと両方が動作する移行期間を設けます。その代わり、クライアントには次が必要です。

- 知らない応答フィールドを無視する。
- 未知の`reason`は存在しないものとし、未知の`code`はHTTPステータスに基づいて処理する。
- `capabilities`から制限を取得する。
- 操作が定義するフィールドだけを送信する。

`operationId`の値は安定した名前です。操作を自分のコードに対応付けるときに使用してください。

## 例：1つのファイルをアップロードしてダウンロードする {#example}

この手順では、1つのリクエストでファイルをアップロードします。数ギガバイトを超えるファイルや不安定な回線では、パートを送信して失敗後に継続できる[`arkvoryctl`](../protocols/cli)または[SDK](../protocols/sdk)を使ってください。例ではJSONの読み取りに`jq`を使用します。

最初にアドレスとキーを設定し、ファイルサイズとSHA-256を計算します。

```bash
export ARKVORY_URL=https://arkvory.example
export ARKVORY_KEY="$(cat ~/.arkvory/key)"
FILE=./Setup.exe
SIZE=$(stat -c %s "$FILE")
SHA=$(sha256sum "$FILE" | cut -d ' ' -f 1)
```

**手順1：アップロードを予約。** 同じ`Idempotency-Key`は同じセッションを返すため、安全に繰り返せます。

```bash
ID=$(curl -fsS -X POST "$ARKVORY_URL/api/v1/repositories/releases/uploads" \
  -H "Authorization: Bearer $ARKVORY_KEY" \
  -H "Idempotency-Key: build-1042-setup" \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"Setup.exe\",\"size\":\"$SIZE\",\"sha256\":\"$SHA\",\"labels\":[\"nightly\"]}" \
  | jq -r .id)
```

**手順2：バイト列を送信。** サイズとSHA-256が一致すると、サーバーがアーティファクトを公開します。

```bash
curl -fsS -X PUT "$ARKVORY_URL/api/v1/repositories/releases/uploads/$ID/content" \
  -H "Authorization: Bearer $ARKVORY_KEY" \
  -H "Content-Type: application/octet-stream" \
  -T "$FILE" | jq '{id, status}'
```

**手順3：ダウンロード。** アーティファクトIDはアップロードIDと同じです。

```bash
curl -fL -o Setup-copy.exe \
  -H "Authorization: Bearer $ARKVORY_KEY" \
  "$ARKVORY_URL/api/v1/repositories/releases/artifacts/$ID/content"
sha256sum Setup-copy.exe
```

手順2は`{"id": "…", "status": "available"}`を返します。手順2で接続が切れた場合、`GET …/uploads/$ID`でアップロードを取得し、状態が`pending`なら最初からファイルを再送します。アップロードセッションの有効期間は7日です。キーには、`releases`に対する`upload.create`、`upload.write`、`upload.complete`、`content.read`が必要です。[アップロード](./reference/uploads)と[転送](../use/transfers)を参照してください。
