# 認証

公開ヘルスチェック、サインインの選択肢、サインイン、登録を除き、`/api/v1`のすべての呼び出しには認証情報が必要です。このページでは、認証情報の種類、それぞれの取得・送信方法、[APIリファレンス](./index#reference-pages)のアクセス規則の意味を説明します。アクセスを管理する人の規則は、[アカウントとアクセス](../use/accounts)を参照してください。

## 認証情報の一覧 {#credentials}

| 認証情報               | 形式        | 取得方法                                           | 有効期間                  | 用途                                                   |
| ---------------------- | ----------- | -------------------------------------------------- | ------------------------- | ------------------------------------------------------ |
| コンソールセッション   | `dps_…`     | 名前とパスワードでサインイン                       | 12時間                    | コンソールのユーザー、またはサインインするスクリプト   |
| 個人用アクセストークン | `pat_…`     | セッションから作成                                 | デフォルト90日、最大365日 | 個人のスクリプトとツール                               |
| サービスキー           | `arkvory_…` | サービスアカウント向けに発行して有効化             | デフォルト90日、最大365日 | CI/CD、デプロイエージェント、他のシステム              |
| 回復キー               | 16進数64桁  | インストーラーが`config/bootstrap-token.txt`に保存 | 無期限                    | 所有者の作成、サービスアカウントの管理、アクセスの復旧 |
| ダウンロードリンク     | `dtl_…`     | 1つのアーティファクト向けに作成                    | 60秒～24時間              | キーを持たない人に1つのアーティファクトを渡す          |

自動化にはサービスキー、個人のツールには個人用アクセストークンを使ってください。回復キーを日常作業に使わないでください。

## ヘッダーの形式 {#headers}

`/api/v1`は、1つのヘッダーで認証情報を受け付けます。

```http
Authorization: Bearer <credential>
```

- 認証情報の長さは32～512文字です。それ以外は直ちに`credential_invalid`になります。
- コンテナレジストリ（`/v2`）、Git LFS（`/lfs`）、npmレジストリ（`/npm`）はHTTP Basicも受け付けます。`docker login`、git、npmがその方式で認証情報を送るためです。ユーザー名は確認せず、パスワードを認証情報として使用します。[クライアントとプロトコル](../protocols/index#credentials)を参照してください。
- ダウンロードリンクは、`?token=dtl_…`としてクエリ文字列に指定し、1つのアーティファクトのコンテンツルートでだけ使えます。[ダウンロードリンク](#download-links)を参照してください。`Authorization`ヘッダーがあれば、常にクエリより優先します。
- 有効な認証情報がないリクエストには、`WWW-Authenticate: Bearer`と、`credential_missing`、`credential_invalid`、`session_expired`、`token_expired`のいずれかの理由付きの`401`を返します。期限切れと分かるのは、その認証情報の正確な秘密情報を持つ人だけです。
- **Cookieは使いません。** ArkvoryはCookieを設定も読み取りもしないため、ブラウザーが認証情報を自動添付することはなく、防御すべきクロスサイトリクエストフォージェリもありません。スクリプトは毎回ヘッダーを送信します。コンソールはブラウザータブのメモリ内にセッショントークンを保持し、タブを閉じると破棄します。
- **別のオリジン。** Arkvoryと同じアドレスのページは設定不要です。別のアドレスのページは、管理者が`ARKVORY_CORS_ORIGINS`にオリジンを登録しない限り、有効な認証情報があっても理由`origin_not_allowed`付きの`403`で拒否します。HTTPSを使ってください。平文HTTPの認証情報はネットワーク上で読めます。[HTTPS](../install/https)を参照してください。

認証情報の主体と、実行できる操作を確認するには：

```bash
curl -fsS -H "Authorization: Bearer $ARKVORY_KEY" "$ARKVORY_URL/api/v1/auth/me"
curl -fsS -H "Authorization: Bearer $ARKVORY_KEY" "$ARKVORY_URL/api/v1/auth/permissions"
```

## コンソールのサインインセッション {#sessions}

ユーザーは名前とパスワードでサインインし、セッションを受け取ります。コンソールが代行しますが、スクリプトでも同じ処理ができます。

1. コマンドラインやプロセス一覧に表示されないよう、名前とパスワードを非公開ファイル`login.json`に保存します。

   ```json
   { "name": "alice", "password": "a long password of 12 to 128 characters" }
   ```

2. `login`を呼び出します。

   ```bash
   curl -fsS -X POST "$ARKVORY_URL/api/v1/auth/login" \
     -H "Content-Type: application/json" -d @login.json
   ```

3. 応答にはセッショントークンと有効期限を含みます。

   ```json
   {
     "token": "dps_…",
     "expiresAt": "2026-10-05T21:30:00.000Z",
     "account": { "id": "…", "name": "alice", "administrator": false, "enabled": true }
   }
   ```

4. `Authorization: Bearer dps_…`としてトークンを送信します。

セッションの規則：

- 有効期間は12時間で延長しません。その後は、すべての呼び出しに理由`session_expired`付きの`401`を返します。再度サインインしてください。
- アカウントは最大32個のセッションを持てます。新しくサインインすると、超過した分の最古のセッションを終了します。
- `POST /api/v1/auth/logout`はセッションを終了します。自分のパスワード変更や管理者によるリセットは、アカウントのすべてのセッションと個人用トークンを終了します。アカウントの無効化でも使用できなくなります。
- セッションは、管理者フラグを含むアカウントの全権限を持ちます。個人用トークンの作成と取り消し、自分のパスワードの変更ができるのはセッションだけです。
- 名前は大文字と小文字を区別せず比較します。名前の誤り、パスワードの誤り、無効なアカウントには、同じ理由`invalid_credentials`付きの`401`を返します。
- 読み取りゲートウェイではサインインできません。書き込みAPIを使ってください。

### 自己登録 {#self-registration}

`GET /api/v1/auth/options`は公開されており、ユーザーが自分でアカウントを作成できるかを示します。管理者が`ARKVORY_ALLOW_REGISTRATION=true`を設定しない限り、自己登録は無効です。有効にすると、サインインと同じ本文を指定した`POST /api/v1/auth/register`が通常のアカウント（管理者ではなく、どのリポジトリにもアクセス権を持たない）を作成し、`201`でセッションを返します。無効の場合は、理由`registration_disabled`付きの`403`を返します。管理者が上限の1,000アカウントまで作成できるよう、自己登録は900アカウントで停止します。

## 個人用アクセストークン {#personal-tokens}

個人用アクセストークンを使うと、パスワードなしでスクリプトが自分として動作できます。作成できるのはサインイン済みセッションだけです。

```bash
curl -fsS -X POST "$ARKVORY_URL/api/v1/auth/tokens" \
  -H "Authorization: Bearer $SESSION" -H "Content-Type: application/json" \
  -d '{"name":"laptop-cli","scope":"read-write","expiresAt":"2026-12-31T00:00:00Z"}'
```

コンソールで[[ui:connection]]カードの[[ui:personalAccessTokens]]を開き、[[ui:tokenName]]を入力し、[[ui:tokenScope]]と[[ui:tokenExpiry]]を選び、[[ui:generateToken]]を選択します。

| フィールド  | 規則                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| `name`      | 1～64文字                                                                                                  |
| `scope`     | `read`または`read-write`。省略するとAPIは`read-write`を使用し、コンソールは[[ui:tokenScopeRead]]を先に提示 |
| `expiresAt` | 今後365日以内の、未来のRFC 3339時刻。デフォルトは90日。無期限のトークンはない                              |

`201`応答は、`token`としてトークンを1回だけ返します。その場で保存してください。サーバーはハッシュだけを保持し、一覧には短いプレフィックスを表示します。その後の規則は次のとおりです。

- トークンはアカウントのリポジトリアクセス権だけを持ち、それ以上の権限は持ちません。管理者フラグは持たないため、アカウント、グループ、更新、バックアップを管理できません。
- `read`トークンは読み取り専用です。`logout`を除く変更リクエストは、操作を実行する前に理由`read_only_token`付きの`403`で拒否します。
- トークンは、トークンの作成やパスワードの変更を行えません。これらにはセッションが必要です。
- アカウントの有効なトークンは最大50個です。`GET /api/v1/auth/tokens`は、プレフィックス、スコープ、有効期限、最終使用時刻を一覧表示します。`DELETE /api/v1/auth/tokens/{id}`は1つを直ちに取り消します（コンソールでは[[ui:revokeToken]]）。管理者は、任意のアカウントのトークンを一覧表示して取り消せます。
- 期限切れのトークンは、理由`token_expired`付きの`401`を返します。

## サービスアカウントとキー {#service-accounts}

**サービスアカウント**は、ビルドエージェントなどのツールの識別主体です。**ポリシー**には**バインディング**を列挙し、それぞれで1つのリポジトリと、そこで許可する正確な**操作**を指定します（[リポジトリの操作](#repository-actions)を参照）。1つのポリシーには最大64個のバインディングを指定できます。キーが開始したアップロードとジョブはアカウントが所有するため、キーをローテーションしても失われません。1サーバーのサービスアカウントは最大1,000個です。

サービスアカウントを作成できるのは[回復キー](#recovery-key)だけです。既存アカウントの変更は、回復キー、または[委任](#delegation)されたオペレーターが行います。コンソールでは[[ui:services]]で[[ui:serviceCreate]]を選び、[[ui:servicePolicy]]を設定します。[[ui:bindingRead]]は7つの読み取り操作を設定し、[[ui:bindingPublish]]はアップロードとパッケージ登録に必要な操作を追加します。

```bash
curl -fsS -X POST "$ARKVORY_URL/api/v1/service-accounts" \
  -H "Authorization: Bearer $RECOVERY_KEY" -H "Content-Type: application/json" \
  -d '{"name":"ci-release","bindings":[{"resource":{"kind":"repository","id":"releases"},
       "actions":["repository.read","artifact.read","upload.create","upload.read","upload.write",
                  "upload.complete","upload.cancel","job.read","package.publish"]}]}'
```

名前は3～64文字で、英字、数字、`_`、`.`、`-`を使用します。ポリシーを変更するには、取得した`expectedRevision`を指定して`PUT /api/v1/service-accounts/{id}/policy`を送信します（[比較交換](./index#revisions)を参照）。アカウントを無効にするには、`{"expectedRevision": n, "enabled": false}`を指定して`PATCH /api/v1/service-accounts/{id}`を送信します。再び有効にするまで、そのアカウントのすべてのキーが使えなくなります。

### サービスキー {#service-keys}

キーは、サービスアカウントがサインインに使用する秘密情報です。形式は`arkvory_<uuid>.<secret>`です。キーには`pending`、`active`、`revoked`の3つの状態があります。

1. **発行。** `Idempotency-Key`、`name`、キーが使用できる`bindings`、必要に応じて`expiresAt`（UTCで今後365日以内、デフォルト90日）を指定し、`POST /api/v1/service-accounts/{id}/keys`を送信します。キーのバインディングは、アカウントのポリシー内に収める必要があります。`201`応答にはキーのメタデータと、この1回だけ`secret`を含みます。同じ冪等キーで再試行すると、秘密情報なしでメタデータを`200`で返します。
2. **有効化。** 新しいキーは`pending`で、新しい秘密情報を認証情報として使う`POST /api/v1/auth/activate-key`以外には使用できません。応答は`204`です。15分以内に行ってください。それ以降は未使用のまま期限切れになります。コンソールでは秘密情報をコピーし、[[ui:keySaved]]、[[ui:keyActivate]]の順に選択します。有効化を繰り返しても問題ありません。
3. **使用。** キーは`expiresAt`まで、または取り消されるか、アカウントが無効になるまで使用できます。

```bash
curl -fsS -X POST "$ARKVORY_URL/api/v1/service-accounts/$ACCOUNT/keys" \
  -H "Authorization: Bearer $RECOVERY_KEY" -H "Idempotency-Key: ci-release-2026-10" \
  -H "Content-Type: application/json" \
  -d '{"name":"ci-release-2026-10","bindings":[{"resource":{"kind":"repository","id":"releases"},
       "actions":["upload.create","upload.read","upload.write","upload.complete","job.read"]}]}'
curl -fsS -X POST "$ARKVORY_URL/api/v1/auth/activate-key" -H "Authorization: Bearer $NEW_SECRET"
```

上限：1アカウントが同時に持てるのは、有効なキー3個と有効化待ちのキー2個までです（理由`key_limit`付きの`507`）。

**ローテーション。** `POST /api/v1/api-keys/{id}/rotate`は、発行時と同じ本文と`Idempotency-Key`を使い、同じアカウントの新しい有効化待ちキーを発行します。バインディングは古いキーの範囲内でなければなりません。新しいキーを有効化すると、古いキーの有効期限を、その時点から最長24時間に短縮します。ツールを新しいキーに切り替えてから、古いキーを取り消してください。コンソールでは[[ui:keyRotate]]です。

**取り消し。** `POST /api/v1/api-keys/{id}/revoke`は、キーを恒久的に無効にします。繰り返しても問題ありません。コンソールでは[[ui:keyRevoke]]です。キーを取り消しても、開始済みの転送は停止しません。有効化待ちキーの秘密情報を失った場合は、取り消してから新しい冪等キーで別のキーを発行してください。

### 委任 {#delegation}

回復キーは、管理の一部を**オペレーター**に渡せます。オペレーターは、他のサービスアカウントを管理できるキーを持つサービスアカウントです。**委任**には、オペレーターのキー、対象アカウント、それに対して使用できる**管理操作**、付与できるリポジトリ操作の**上限**を指定します。7つの管理操作は次のとおりです。

| 操作                     | 許可する内容                                  |
| ------------------------ | --------------------------------------------- |
| `service-account.read`   | 一覧でアカウントを参照し、カードを読む        |
| `service-account.manage` | アカウントの有効化と無効化                    |
| `policy.read`            | アカウントのポリシーを読む                    |
| `policy.manage`          | アカウントのポリシーを置き換える              |
| `credential.read`        | アカウントのキーを一覧表示し、1つのキーを読む |
| `credential.manage`      | キーの発行、ローテーション、取り消し          |
| `service-audit.read`     | アカウントのキー履歴を読む                    |

規則：オペレーターのキーは回復キーが発行したものでなければなりません。オペレーターは自分のアカウントを管理できません。委任の上限やアカウントのポリシーを超える権限は付与できません。発行するキーの有効期限は自分のキーを超えられません。委任を終了しても、有効化済みキーは取り消しません。アカウントの作成と委任の設定（`PUT`および`DELETE /api/v1/api-keys/{id}/delegations/{accountId}`）は、回復キーだけが行えます。1つのオペレーターキーには最大64個の委任を設定できます。コンソールでは[[ui:delegations]]を使います。委任の範囲外を要求すると、管理していないアカウントには`404`、または`403`を返します。

## 回復キー {#recovery-key}

インストーラーは**回復キー**を1回作成し、[インストールルート](../install/index#installation-directory)の`config/bootstrap-token.txt`に書き込みます。読み取れるのはWindowsのAdministratorsグループ、またはLinuxのrootだけです。そのハッシュは、サーバーのキーファイル（`ARKVORY_KEYS_FILE`）に`bootstrap-owner`という名前で保存します。インストーラーは、リポジトリ権限を持たず、認証付きヘルスチェックとメトリクスを呼び出せる2つ目のキーを、`config/health-token.txt`に作成します。

回復キーができること：

- 最初とそれ以降のアカウントの作成、パスワードのリセット、アカウントの無効化、グループとそのリポジトリ許可の管理。
- セキュリティ監査の読み取りと、任意のアカウントの個人用トークンの取り消し。
- サービスアカウントの作成、ポリシー設定、キーの発行・取り消し、委任の設定。
- バックアップと更新の参照・要求、およびフィードバック用のサーバーログのダウンロード。
- [[ui:write]]アクセスを持つグループのメンバーと同様に、リポジトリ`releases`の読み取りと書き込み。

できないこと：`releases`以外のリポジトリにはアクセスできず、アーティファクトの削除やストレージポリシーの管理もできません（これらの操作はサービスキーだけにあります）。セッションではないため、個人用トークンの作成やパスワードの変更もできません。サーバーに保管してください。インストールツールはそこで読み取ります。CIに配置したりツールに貼り付けたりせず、代わりにサービスキーを作成してください。交換方法は[設定](../install/configuration)を参照してください。

コンソールの[[ui:welcomeOwner]]フォーム（[[ui:navStart]]の下）は、回復キーで最初の所有者を作成します。アカウントが1つも存在しない間だけ動作します。セッションなしで既存アカウントのパスワードをリセットするには、`GET /api/v1/users`でIDを調べ、新しいパスワード（12～128文字）を非公開ファイルに入れ、回復キーを使って送信します。リセットにより、そのアカウントのすべてのセッションとトークンを終了します。

```bash
echo '{"password": "a new password of 12 to 128 characters"}' > reset.json
curl -fsS -X PATCH "$ARKVORY_URL/api/v1/users/$USER_ID" \
  -H "Authorization: Bearer $RECOVERY_KEY" -H "Content-Type: application/json" -d @reset.json
rm reset.json
```

管理者は、キーファイルに他のファイルキーを追加できます。各エントリには`id`、秘密情報の`sha256`、対象の`repositories`、付与する`permissions`（`read`と`write`）、任意の`administrator`と`serviceAdministrator`フラグがあります。ファイルは起動時に読み取るため、変更後はAPIとワーカーを再起動してください。

## ダウンロードリンク {#download-links}

`POST /api/v1/repositories/{repository}/artifacts/{id}/links`は、1つのアーティファクトの`token`（`dtl_…`）と`url`を返します。`ttlSeconds`で有効期間を指定します。60～86,400で、デフォルトは3,600です。呼び出し元には`content.read`が必要です。

リンクは、そのリポジトリ内のそのアーティファクトに対する`GET`または`HEAD`の`/api/v1/repositories/{repository}/artifacts/{id}/content?token=…`だけで使え、読み取り専用です。秘密情報として扱ってください。サーバーは有効期限前に取り消せず、ログにも記録しません。必要な最短の有効期間で作成してください。

## アクセス規則の意味 {#access-rules}

リファレンスの各操作には、**アクセス**の行があります。規則の種類は次のとおりです。

| リファレンスの規則                                 | 必要なもの                                                                                                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| キー不要で誰でも利用可能                           | 不要。稼働確認、準備状態のステータス、サインインの選択肢、サインイン、登録                                                                                                                       |
| 任意の有効なキーまたはセッション                   | 有効な認証情報。例：対応機能、操作一覧、自分の識別情報、準備状態の詳細、メトリクス                                                                                                               |
| サインイン済みアカウントのセッション（キーは不可） | ユーザーのセッション。個人用トークンとキーは拒否（`session_required`）。例：自分のトークンの作成・取り消し、自分のパスワード変更                                                                 |
| 管理者                                             | 管理者アカウントのセッション、または回復キーなど管理者フラグ付きのファイルキー。個人用トークンとサービスキーは拒否（`administrator_required`）。例：アカウント、グループ、セキュリティ監査、更新 |
| ブートストラップキー（インストールの回復キー）     | サービス管理フラグ付きのファイルキー。回復キーはこのフラグを持つ。例：サービスアカウント作成、委任の設定                                                                                         |
| ブートストラップキー、またはキー自身               | 回復キー、または委任一覧の対象となるキー                                                                                                                                                         |
| 発行済みキー。有効化前後のどちらでも可能           | 有効化待ちキーを受け付ける唯一の操作である、キーの有効化                                                                                                                                         |
| 呼び出し元が参照できるリポジトリ                   | そのリポジトリの`repository.read`、またはセッション・ファイルキーの任意のアクセス権。参照できないリポジトリは一覧から省き、`404`を返す                                                           |
| システム権限`backup.read`または`backup.manage`     | 管理者セッションと、管理者フラグ付きファイルキーが持つ。サービスキーと個人用トークンは持たない。`backup.manage`は`backup.read`を含む                                                             |
| サービス管理権限                                   | 委任から得る対象アカウントへの7つの[管理操作](#delegation)のいずれか、または回復キー                                                                                                             |
| リポジトリ権限                                     | パスに指定したリポジトリに対する、列挙したリポジトリ操作の**すべて**。操作によっては、アップロード、ジョブ、参照が呼び出し元に属することなどの追加条件がある                                     |

リポジトリの行の後半（例えば「ファイルキー：`read`、`write`」）は、ユーザーとファイルキーが正確な操作権限の代わりに必要とする大まかな許可です。[グループの許可](#group-grants)を参照してください。

アクセス規則に加え、ミラーであるリポジトリの変更は拒否します（`409`、`mirror_read_only`）。読み取りゲートウェイも、すべての変更を拒否します（`405`、`read_only`）。

## リポジトリの権限 {#repository-permissions}

### グループの許可 {#group-grants}

ユーザーは**グループ**を通じてリポジトリアクセスを得ます。管理者は、グループにリポジトリの`read`または`write`（「読み取りと書き込み」と表示）を付与し、アカウントをグループに追加します。コンソールでは[[ui:administration]]から[[ui:manageGrants]]、[[ui:saveGrant]]を選択します。API呼び出しは、`{"access": "read"}`または`{"access": "write"}`を指定する`PUT /api/v1/access-groups/{id}/grants/{repository}`と、`PUT /api/v1/access-groups/{id}/members/{userId}`です。権限は各リクエストで再計算するため、変更は直ちに適用します。

`read`は、`repository.read`、`artifact.read`、`artifact.list`、`content.read`、`package.read`、`asset.read`、`annotation.read`を付与します。`write`は、さらに`upload.create`、`upload.read`、`upload.write`、`upload.complete`、`upload.cancel`、`job.read`、`package.publish`、`asset.write`、`asset.restore`、`annotation.write`、`reference.write`、`artifact.promote`、`audit.read`を追加します。`artifact.delete`、`storage.read`、`storage.manage`、`diagnostics.read`はグループからは付与できず、サービスキーだけが持てます。

### リポジトリの操作 {#repository-actions}

サービスキーは、リポジトリごとに正確な操作権限を持ちます。24種類あります。

| 操作               | 許可する内容                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `repository.read`  | リポジトリとそのミラー状態の参照                                                                                 |
| `artifact.read`    | アーティファクトの詳細、ステージ、プロモーションの読み取り。アーティファクトへのすべての変更でも必要             |
| `artifact.list`    | アーティファクトの一覧・検索、ステージ上のアーティファクト一覧、プロモーションジャーナルと変更フィードの読み取り |
| `artifact.promote` | ステージの設定・削除、別のリポジトリへのプロモーション（コピーまたは移動）                                       |
| `artifact.delete`  | アーティファクトの削除、保持のプレビュー・適用、コンテナイメージの削除、Git LFSファイルの強制ロック解除          |
| `content.read`     | ID、パッケージ、パスによるバイト列のダウンロードと、ダウンロードリンクの作成                                     |
| `upload.create`    | アップロードセッションの作成。レジストリとGit LFSへのプッシュでも使用                                            |
| `upload.read`      | 自分のアップロードセッションとそのパートの読み取り                                                               |
| `upload.write`     | 自分のアップロードのパートまたは内容全体の送信                                                                   |
| `upload.complete`  | 自分のアップロードの完了、または完了処理のキューへの追加                                                         |
| `upload.cancel`    | 自分の未完了アップロードのキャンセル                                                                             |
| `job.read`         | 自分の完了ジョブの読み取り                                                                                       |
| `package.read`     | パッケージ一覧、バージョンの解決、パッケージのダウンロード                                                       |
| `package.publish`  | UPackアーカイブをパッケージとして登録                                                                            |
| `asset.read`       | パス指定ファイルの一覧、ポインター、履歴、リビジョンの読み取り。バイト列のダウンロードには`content.read`が必要   |
| `asset.write`      | パスからアーティファクトへの参照設定、またはrawファイルの保存                                                    |
| `asset.restore`    | パスの以前のリビジョンを復元                                                                                     |
| `annotation.read`  | ラベル、メタデータ、コレクション、添付ファイルの読み取り                                                         |
| `annotation.write` | ラベル、メタデータ、コレクション、添付ファイルの置き換え                                                         |
| `reference.write`  | アーティファクトを保護する参照の追加・削除                                                                       |
| `audit.read`       | リポジトリのカタログ監査の読み取り                                                                               |
| `storage.read`     | クォータ、使用量、ストレージポリシー、物理クリーンアップ設定の読み取り                                           |
| `storage.manage`   | ストレージポリシーと物理クリーンアップ設定の変更、物理クリーンアップの実行                                       |
| `diagnostics.read` | ストレージイベントの読み取り                                                                                     |

操作が必要とする正確な組み合わせは、リファレンスの各行に示します。例えば`putUploadContent`には`upload.write`と`upload.complete`が必要です。リポジトリへの変更には、`annotation.write`と`artifact.read`のように、対応する`read`操作も必要です。

アップロードとジョブには所有者の条件があり、自分のアカウントが作成したアップロードセッションと完了ジョブだけを操作できます。1つのサービスアカウントのすべてのキー、および1人のユーザーのすべてのセッションとトークンは、同じ所有者として扱います。そのため、同じリポジトリ内の複数サービスは、パスのプレフィックスではなく、アカウントとリポジトリで分離します。

### 管理権限とシステム権限 {#administration-permissions}

リポジトリの操作ではない権限が、他に2種類あります。7つの管理操作は[委任](#delegation)に記載しています。2つのシステム権限`backup.read`と`backup.manage`は、管理者と回復キーだけが持ちます。

## サインインの制限 {#sign-in-limits}

サーバーは、パスワードの検証前にパスワード推測を遅くします。アドレスごとのカウンターとサーバー全体の登録カウンターは各APIプロセスのメモリ内にあり、再起動後は最初から始まります。アドレスの制限はクライアントアドレスごとに適用し、IPv6は/64プレフィックス単位で数えます。アカウントごとのパスワード失敗の負債とロック状態はPostgreSQLに保存され、すべてのAPIプロセスで共有され、再起動後も保持されます。リバースプロキシの背後では、`ARKVORY_TRUSTED_PROXIES`を設定しないと、全クライアントがプロキシとして見えます。

| 制限                           | 値                                                                                                                                                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| アドレスごとのサインイン試行   | 一度に10回、その後は15秒ごとに1回追加。サインイン成功時は試行枠を消費しない                                                                                                                                                                              |
| アカウントごとのパスワード失敗 | 誤ったパスワードごとに負債を1加算し、6秒ごとに1減らす。20を超えると1秒間試行を拒否し、その後の失敗ごとに最大2分まで倍増。その間は正しいパスワードでも`429`。サインイン成功、自分のパスワードの変更成功、または管理者によるパスワードリセットで負債を消去 |
| アドレスごとの登録             | 3回、その後は20分ごとに1回追加                                                                                                                                                                                                                           |
| サーバーごとの登録             | 20回、その後は3分ごとに1回追加                                                                                                                                                                                                                           |
| 進行中のサインインリクエスト   | APIプロセスごとに16件。本文は10秒以内に到着する必要がある。超過するとコード`busy`付きの`503`                                                                                                                                                             |

拒否した試行には、コード`rate_limited`、理由`login_attempts`、`registration_attempts`、`password_attempts`のいずれか、および秒単位の`Retry-After`付きの`429`を返します。その時間だけ待ち、ループで再試行しないでください。一時的なロック中でない場合、自分のパスワードを変更するときに現在のパスワードを間違えると、同じアカウントの負債が増え、理由`current_password_invalid`付きの`401`を返します。一時的なロック中は、パスワード変更に理由`password_attempts`付きの`429`を返します。管理者によるパスワードリセットは負債を消去します。アドレスごとの試行枠はアカウントの負債とは独立しています。サインイン、登録、パスワード変更、トークン変更はすべてセキュリティ監査（`GET /api/v1/security/audit`、管理者のみ）に記録し、365日間保持します。
