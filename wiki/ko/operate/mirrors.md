# 미러와 두 번째 사이트

**미러**는 다른 설치 환경에 있는 리포지토리, 즉 **원본**의 읽기 전용 사본인 리포지토리입니다. 미러 설치 환경은 HTTPS로 원본에서 변경 사항을 가져옵니다. 데이터베이스, 스토리지, 계정, 키는 자체적으로 유지합니다.

미러는 두 번째 위치에서 다운로드를 제공하거나, 원본을 잃었을 때 인계받을 수 있는 두 번째 사이트를 유지하는 데 사용하세요. 미러는 원본의 백업이 아니며 자동 고가용성도 아닙니다. 전환은 직접 수행합니다. 다른 보호 수단은 [백업](./backups)과 [읽기 게이트웨이](./read-gateways)를 참조하세요.

## 미러란 무엇인가 {#what-a-mirror-is}

미러링되는 리포지토리에 대해 미러 설치 환경은 다음을 복사합니다.

- 게시된 파일. 바이트와 원본과 **같은 아티팩트 ID**를 그대로 가져옵니다.
- 레이블, 메타데이터, 컬렉션.
- UPack 등록 정보, 스테이지, 현재 파일 경로.
- 리포지토리의 컨테이너 이미지, Git LFS 객체, npm 패키지.
- 삭제. 원본에서 삭제한 파일은 미러에서도 삭제됩니다.

ID, 패키지(버전, 범위, 스테이지), 파일 경로로 하는 다운로드는 미러에서 마지막 동기화 시점의 원본과 같은 방식으로 응답합니다. 원본이 중단되어도 계속 동작합니다.

미러가 복사하지 않는 것은 다음과 같습니다.

- 계정, 그룹, 키, 권한 부여. 미러에는 자체 항목이 있으며 서로 독립적입니다. 원본에서 키를 폐기해도 미러에는 영향이 없습니다.
- 파일을 정리로부터 보호하는 참조, 빌드의 첨부 파일, 감사 기록, 스토리지 정책.
- 첫 번째 동기화 이전의 파일 경로 기록. 미러의 레이블과 경로의 리비전 번호는 미러 자체의 번호입니다.

클라이언트는 미러링되는 리포지토리에 쓸 수 없습니다. 이곳에 대한 업로드, 레이블 변경, 파일 경로, 스테이지, 삭제, 승격은 이유 `mirror_read_only`와 함께 HTTP 409를 받습니다. 미러 설치 환경의 다른 리포지토리는 평소처럼 동작합니다. 미러링되는 리포지토리에서는 스토리지 정책이 실행되지 않으며, 동기화만 삭제를 수행합니다.

## 미러 설정 {#set-up}

원본에서 키 하나를, 미러에서 명령 하나를 사용합니다.

### 원본에서 키 만들기 {#source-key}

미러에는 원본 리포지토리를 읽기만 할 수 있는 키가 필요합니다. 쓰기 키는 필요하지 않습니다.

1. 원본에서 복구 키 또는 운영자 키로 연결하고 [[ui:services]] 섹션을 여세요.
2. [[ui:serviceCreate]] 버튼을 선택하고, [[ui:servicePolicy]] 항목에서 리포지토리를 추가하세요. [[ui:bindingRead]] 버튼을 선택하면 미러에 필요한 권한이 채워집니다. 여기에는 `artifact.list`, `artifact.read`, `content.read`, `annotation.read`, `asset.read`, `package.read`가 포함됩니다.
3. [[ui:keyIssue]] 버튼을 선택하고, 시크릿을 복사한 뒤 [[ui:keySaved]] 확인란을 선택하고 [[ui:keyActivate]] 버튼을 선택하세요. 활성화하지 않은 키는 15분 후에 만료됩니다.
4. 시크릿을 미러 서버의 파일에 저장하세요. 파일에는 키만 한 줄로 들어가며, 출력 가능한 문자 16~4000자여야 합니다. root 또는 Administrators 그룹만 읽을 수 있어야 합니다.

원본은 변경 피드를 제공하는 릴리스여야 합니다. 다음 단계의 명령이 이를 확인합니다.

### 미러에서 리포지토리 연결 {#attach}

미러에서는 **새롭고 비어 있는** 리포지토리 이름을 사용하세요. 동기화는 리포지토리를 원본과 같게 만들지만, 원본에 없던 것을 삭제하지는 않습니다.

```bash
sudo arkvory configure --root /opt/proanima-arkvory \
  --mirror releases \
  --mirror-upstream https://arkvory.example \
  --mirror-token-file /root/mirror-releases.key
```

```powershell
$root = 'C:\ProgramData\ProAnima\Arkvory'
& 'C:\Program Files\ProAnima\Arkvory\arkvory.ps1' configure --root $root `
  --mirror releases --mirror-upstream https://arkvory.example `
  --mirror-token-file C:\secure\mirror-releases.key
```

| 옵션                       | 의미                                                                                                                                      |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `--mirror NAME`            | 이 설치 환경의 리포지토리. 1~64자: 소문자, 숫자, `_`, `-`이며 문자 또는 숫자로 시작합니다                                                 |
| `--mirror-upstream URL`    | 원본의 오리진: `https://host`. 경로, 자격 증명, 쿼리는 없어야 합니다. 일반 `http://`는 `localhost`, `127.0.0.1`, `[::1]`에서만 허용됩니다 |
| `--mirror-token-file FILE` | 키 파일의 절대 경로                                                                                                                       |
| `--mirror-source NAME`     | 원본의 리포지토리. 기본값은 `--mirror`와 같은 이름입니다                                                                                  |
| `--mirror-ca-file FILE`    | 원본의 인증 기관이 들어 있는 PEM 파일. [자체 인증 기관을 사용하는 HTTPS](#ca-file)를 참조하세요                                           |

한 번의 명령에는 리포지토리 하나만 지정하세요. 같은 호출에서 미러 변경을 HTTPS, 백업 보관소, 업데이트 변경과 함께 실행할 수 없습니다.

1. 명령은 아무것도 바꾸기 전에 키로 원본을 확인합니다. 원본이 미러 변경 피드를 보고해야 하며, 원본 리포지토리의 피드가 응답해야 합니다.
2. 키를 `config/mirrors/NAME.token`에 저장하고, `config/mirrors/mirrors.json`을 쓰고, `config/runtime.json`에 `ARKVORY_MIRRORS_FILE`을 설정합니다.
3. API와 워커를 다시 시작하고 준비될 때까지 기다립니다. 어느 단계든 실패하면 이전 파일을 복원하고 다시 시작합니다.

Docker Compose에서는 이 명령이 `config/compose.mirrors.yml`도 씁니다. 이 파일은 미러 파일을 API 및 워커 컨테이너에 마운트합니다. 직접 실행하는 Compose 명령에 이 파일을 추가하세요.

리포지토리의 키를 교체하려면 새 `--mirror-token-file`로 명령을 다시 실행하세요. 워커는 실패할 때마다 키 파일을 다시 읽으므로 새 키는 다시 시작하지 않아도 동작합니다. 이미 한 원본을 미러링하는 리포지토리에 다른 원본을 지정하면 `NAME mirrors another source; detach it first` 메시지와 함께 거부됩니다.

미러 설치 환경에서 사람과 도구가 리포지토리에 접근할 수 있게 하세요. 권한 부여나 서비스 정책에 이름이 지정되는 즉시 리포지토리가 존재합니다. 사람에게는 [[ui:administration]] 섹션의 [[ui:manageGrants]] 항목을, 도구에는 서비스 정책을 사용하세요. 원본의 권한은 이어지지 않습니다.

### 자체 인증 기관을 사용하는 HTTPS {#ca-file}

원본이 기업 인증 기관 또는 자체 서명 인증 기관의 인증서를 사용한다면 `--mirror` 명령에 `--mirror-ca-file /path/ca.pem`을 추가하세요. 명령은 각 인증서를 읽을 수 있고 만료되지 않았는지 확인한 다음, 인증서 1~64개를 `config/mirrors/ca.pem`에 저장합니다(파일은 1 MiB를 넘을 수 없습니다). 이후 워커는 표준 인증서에 더해 이 인증서도 신뢰합니다.

- 이 파일은 설치 환경의 모든 미러에 적용됩니다. 새 `--mirror-ca-file`은 기존 파일에 추가되며, 이미 있는 인증서는 한 번만 유지됩니다. 마지막 미러를 분리하면 파일이 제거됩니다.
- 워커는 한 미러뿐 아니라 모든 연결에 이 전체 집합을 신뢰합니다.
- 인증서 검사는 절대 끄지 않습니다.

## 복사 대상과 주기 {#sync}

동기화는 미러 설치 환경의 워커가 수행합니다. 별도의 서비스는 없습니다. 워커는 미러링되는 각 리포지토리에 대해 다음 단계를 실행합니다.

1. **최초 채우기.** 워커는 원본 변경 피드의 현재 위치를 기록합니다. 그런 다음 아티팩트, 패키지, 파일 경로의 목록을 페이지 단위로 읽어 미러를 그와 같게 만듭니다.
2. **추적.** 워커는 원본의 피드를 읽습니다. 따라잡으면 10초마다 다시 확인합니다. 적용한 변경마다 자신의 위치를 저장합니다.
3. **파일 복사.** 파일은 파트 단위로 복사됩니다. 워커는 각 파트와 전체 파일의 SHA-256을 확인합니다. 중단된 뒤에는 처음으로 누락된 파트부터 이어서 복사합니다. 파트는 미러의 스토리지 디렉터리 안의 `mirror-staging`에서 대기합니다.
4. **오류 후.** 워커는 2초에서 시작해 최대 5분까지 두 배씩 늘어나는 시간만큼 쉰 뒤 단계를 반복합니다. 실패하는 미러 하나가 다른 미러를 멈추지 않습니다.

설치 환경 하나는 미러링되는 리포지토리를 최대 64개까지 가질 수 있습니다. 사본은 미러의 용량 제한과 디스크를 사용하므로 원본 리포지토리에 필요한 만큼의 공간을 계획하세요. [스토리지](./storage)를 참조하세요.

원본 키가 폐기되었거나 원본에 접근할 수 없으면 미러는 이미 가진 데이터를 계속 제공하고 상태에 오류를 표시합니다.

## 동기화 상태 확인 {#status}

### 콘솔에서 {#status-console}

미러 설치 환경의 콘솔을 미러링되는 리포지토리에 연결하세요. 카탈로그 위의 배지가 상태를 보여 줍니다.

- [[ui:mirrorBadge]] 배지는 미러가 따라잡았다는 뜻입니다.
- [[ui:mirrorBehind]] 배지는 아직 복사 중이거나 아직 시작되지 않았다는 뜻입니다.
- [[ui:mirrorFailing]] 배지는 마지막 시도가 실패했다는 뜻입니다. 다운로드는 계속 동작합니다.

배지의 도움말([[ui:mirrorHelpLabel]])을 열면 원본, 마지막 동기화 시각, 오류 코드를 볼 수 있습니다. 콘솔은 미러링되는 리포지토리에서 업로드 버튼과 변경 버튼을 숨깁니다.

### API로 {#status-api}

[getRepositoryMirror](../api/reference/mirrors#getRepositoryMirror)는 리포지토리의 상태를 반환합니다. 리포지토리를 읽을 수 있는 권한이 필요합니다. 일반 리포지토리에 대해서는 404로 응답합니다.

| 필드                             | 의미                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `mode`                           | `mirror` 또는 `import`                                                             |
| `phase`                          | `pending`(워커가 아직 시작하지 않음), `seeding`(최초 채우기), `following`          |
| `caughtUp`                       | 저장된 위치가 원본의 최신 위치와 같으면 `true`. 최초 채우기가 끝나기 전에는 `null` |
| `checkedAt`, `syncedAt`          | 워커가 피드를 마지막으로 읽은 시각, 마지막으로 따라잡은 시각                       |
| `copiedArtifacts`, `copiedBytes` | 지금까지 복사한 합계(`copiedBytes`는 10진수 문자열)                                |
| `errorCode`, `errorAt`           | 단계의 마지막 실패, 또는 `null`                                                    |

### 오류 코드 {#error-codes}

| `errorCode`             | 의미와 해야 할 일                                                                                                                                                     |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mirror_mismatch`       | 같은 아티팩트 ID가 원본에서는 다른 콘텐츠입니다. 미러는 자신의 파일을 유지합니다. 아티팩트를 조사하세요. 원인을 알기 전에는 어느 사본도 삭제하지 마세요               |
| `mirror_source_changed` | 리포지토리에 이미 다른 원본의 사본이 있습니다. 분리하거나, 새 원본을 새 리포지토리에 미러링하세요                                                                     |
| `mirror_source_behind`  | 원본이 복원되었거나 다시 설치되어 피드가 미러보다 뒤처져 있습니다. 미러가 피드를 다시 읽으며, 따라잡으면 코드가 사라집니다. 복원된 원본에 없는 파일은 미러에 남습니다 |
| `mirror_delete_blocked` | 원본이 미러에서는 삭제할 수 없는 파일을 삭제했습니다. 참조나 파일 경로 기록처럼 이곳의 무언가가 아직 그 파일을 사용하기 때문입니다                                    |
| `mirror_failed`         | 더 구체적인 코드가 없는 실패입니다. 워커 로그를 읽으세요                                                                                                              |
| 그 외 코드              | 실패한 요청의 코드. 예를 들어 키가 폐기되었으면 `unauthorized`, 미러가 가득 찼으면 `capacity_exceeded`                                                                |

워커 로그(`component`가 `mirror`)에는 `mirror.started`, `errorCode`와 `attempts`가 있는 `mirror.step_failed`, `mirror.recovered`, `mirror.stopped`가 있습니다.

## 미러 모니터링 {#monitoring}

미러 설치 환경의 API는 미러링되는 리포지토리마다 `repository`와 `mode` 레이블이 있는 메트릭 세 개를 제공합니다.

- `arkvory_mirror_last_sync_timestamp_seconds`: 미러가 마지막으로 따라잡은 시각.
- `arkvory_mirror_last_check_timestamp_seconds`: 피드를 마지막으로 읽은 시각.
- `arkvory_mirror_failing`: 마지막 시도가 실패한 동안 1.

바로 사용할 수 있는 Prometheus 규칙은 `ArkvoryMirrorStale`(1시간 넘게 따라잡지 못함)과 `ArkvoryMirrorFailing`(실패가 15분 동안 지속됨)입니다. [모니터링](./monitoring)을 참조하세요. 워커가 아직 도달하지 않은 미러에는 동기화 시각이 없으므로, stale 규칙은 첫 번째 동기화 전에는 발동하지 않습니다.

## 스테이지별 가져오기 {#import}

`--mirror-stages`를 지정하면 두 번째 설치 환경의 리포지토리는 미러가 **아닙니다**. 원본에서 지정한 스테이지가 붙은 버전을 가져오는 일반 쓰기 가능 리포지토리입니다. 개발 서버의 빌드를 프로덕션 서버로 옮길 때 사용하세요.

```bash
sudo arkvory configure --root /opt/proanima-arkvory \
  --mirror releases --mirror-upstream https://dev.example \
  --mirror-token-file /root/dev.key --mirror-stages release
```

- 서로 다른 스테이지 이름을 1~16개, 쉼표로 구분해 나열합니다.
- 버전은 같은 ID, 바이트, 레이블, UPack 등록 정보, 일치하는 스테이지와 함께 한 번 복사됩니다.
- 그 이후에는 이 설치 환경에 속합니다. 원본에서의 변경, 스테이지 제거, 삭제는 반영되지 않습니다. 여기에서 삭제한 버전은 다시 가져오지 않습니다.
- 리포지토리의 업로드와 스토리지 정책은 평소처럼 동작합니다.
- 컨테이너 이미지, Git LFS, npm 레지스트리 데이터는 가져오지 않습니다.
- 스테이지를 변경하면 새로 최초 채우기를 시작합니다. 추가만 하며 이미 있는 것은 건너뜁니다.

콘솔에는 [[ui:mirrorImport]] 배지가 표시되고, 마지막 시도가 실패하면 [[ui:mirrorImportFailing]] 배지가 표시됩니다. 원본의 키에는 미러와 같은 읽기 전용 권한이 필요합니다.

## 원본을 잃었을 때 장애 조치 {#failover}

이것은 두 사이트의 독립된 설치 환경 두 개를 위한 수동 전환입니다. 자동이 아닙니다. 미러가 아직 가져오지 못한 변경은 사라집니다.

### 미리 준비하기 {#failover-prepare}

1. 가능하면 원본과 같은 릴리스로 두 번째 사이트를 설치하세요. 자체 PostgreSQL과 자체 디스크를 사용합니다. 두 사이트는 아무것도 공유하지 않습니다.
2. 원본에 읽기 전용 키를 만들고 모든 리포지토리를 미러로 연결하세요. 나중에 원본에서 만든 리포지토리는 미러에 저절로 나타나지 않으므로 같은 방식으로 연결하세요.
3. 미러에서는 클라이언트가 사용할 키를 발급하세요. 전환 후 쓰기가 가능한 키도 포함합니다. 원본의 권한은 이어지지 않으므로, 원본이 침해되어도 미러에는 접근할 수 없습니다.
4. 다운로드용 대체 경로로 미러의 주소를 클라이언트(CI, 배포 에이전트)에 설정하세요. 이렇게 하면 원본과의 링크 부하도 줄어듭니다.
5. 원본을 해당 사이트 밖의 백업 보관소에 백업하세요. [백업](./backups)을 참조하세요. 미러는 이를 대체하지 않습니다.
6. 위의 규칙으로 미러를 모니터링하세요.

### 전환 {#failover-switch}

1. 원본이 클라이언트에게 실제로 사용할 수 없고 저절로 돌아오지 않을 것인지 확인하세요. 하나의 논리적 리포지토리에 쓰기를 받는 두 사이트는 나중에 병합할 수 없습니다. 원본에 일부 접근할 수 있다면 서비스를 중지하거나 포트를 닫으세요.
2. 미러에서 각 리포지토리의 `syncedAt`을 읽으세요. 그 시각 이후 원본에서 일어난 변경은 미러에 없습니다.
3. 미러에서 미러링되는 각 리포지토리를 분리하세요. 분리하면 같은 아티팩트 ID와 모든 데이터를 가진 일반 쓰기 가능 리포지토리가 됩니다.

   ```bash
   sudo arkvory configure --root /opt/proanima-arkvory --mirror-detach releases
   ```

   이 명령은 API와 워커를 다시 시작하므로 잠시 중단됩니다.

4. 쓰기를 하는 클라이언트가 DNS 또는 CI 구성을 통해 미러를 가리키게 하세요.
5. 미러에 확인용 파일을 업로드하고 다운로드하세요.

클라이언트에게 보이는 동작은 다음과 같습니다.

- 전환 전에는 미러에서의 다운로드가 동작하고, 쓰기는 409 `mirror_read_only`를 받습니다.
- 분리한 후에는 쓰기가 동작합니다. 배지가 사라집니다.
- 같은 계정을 미러에 만들어 두지 않았다면 원본의 키와 비밀번호는 미러에서 동작하지 않습니다.

되돌릴 방법은 없습니다. 분리한 리포지토리를 다시 미러로 연결하지 마세요. 이전 원본을 되살리려면 그 원본을 비우거나 새로 설치하고, 새 기본 서버의 리포지토리를 미러로 연결하세요. 쓰기가 켜진 상태로 이전 원본과 새 기본 서버를 나란히 실행하지 마세요.

### 예행연습 {#failover-rehearse}

분기마다, 그리고 업데이트 후에 전환을 예행연습하세요. 예비 사본에서 리포지토리 하나를 분리하고, `syncedAt`, 다운로드, 업로드를 확인한 다음 날짜와 결과를 기록하세요. 원본 백업을 빈 설치 환경에 복원하는 테스트는 별도로 수행하세요. [복원을 정기적으로 테스트](./backups#test-restore)를 참조하세요.

## 제한 사항 {#limits}

- 미러는 분리하기 전까지 읽기 전용입니다. 분리한 리포지토리는 다시 미러가 될 수 없습니다.
- 미러는 백업이 아닙니다. 계정, 키, 권한 부여의 사본이 없으며, 참조, 첨부 파일, 감사 기록, 스토리지 정책을 복사하지 않습니다.
- 가져오기 모드는 컨테이너 이미지, Git LFS, npm 데이터를 복사하지 않습니다.
- 동기화는 추가와 업데이트만 합니다. 원본을 복원한 뒤에는 원본이 잃은 파일이 미러에 남습니다.
- 두 설치 환경은 각각 따로 업데이트합니다. 원본은 미러 변경 피드를 제공해야 합니다.
- 원본의 신뢰할 인증 기관 집합은 워커 전체에 적용됩니다.
- 자동 장애 조치, 이전 원본의 펜싱, 역방향 동기화는 없습니다.
