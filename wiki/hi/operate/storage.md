# स्टोरेज

Arkvory हर प्रकाशित फ़ाइल को एक बार, अपरिवर्तित, सर्वर की स्थानीय डिस्क पर एक स्टोरेज डायरेक्टरी में, और वैकल्पिक रूप से [और वॉल्यूम](#volumes) पर, रखता है। यह पेज बताता है कि डिस्क स्थान क्या लेता है, कोटा और प्रतिधारण नीतियों से इसे कैसे सीमित करें, हटाई गई फ़ाइलें डिस्क से कैसे जाती हैं, और डिस्क भर जाने पर क्या करें।

## सामग्री कहाँ रहती है {#location}

स्टोरेज डायरेक्टरी `ARKVORY_DATA_DIR` से सेट होती है। इंस्टॉलर ये स्थान इस्तेमाल करते हैं:

| इंस्टॉलेशन     | स्टोरेज                                       |
| -------------- | --------------------------------------------- |
| Windows        | `C:\ProgramData\ProAnima\Arkvory` में `data\` |
| Linux          | `/opt/proanima-arkvory` में `data/`           |
| Docker Compose | Docker वॉल्यूम `proanima-arkvory_storage`     |

इसके भीतर, `blobs/` तैयार फ़ाइलें रखता है, `staging/` और `parts/` प्रगतिरत अपलोड रखते हैं, और `storage-id` फ़ाइल डायरेक्टरी को डेटाबेस से जोड़ती है। कैटलॉग, सभी नामों, लेबलों, संस्करणों और अनुमतियों के साथ, PostgreSQL में है। फ़ाइलें और डेटाबेस एक साथ रहते हैं।

- ऐसा स्थानीय फ़ाइल सिस्टम इस्तेमाल करें जो हार्ड लिंक का समर्थन करता हो। स्टोरेज के लिए नेटवर्क शेयर इस्तेमाल न करें।
- डायरेक्टरी में हाथ से फ़ाइलें न जोड़ें, न बदलें और न हटाएँ। Arkvory खुद फ़ाइलें हटाता है, जैसा नीचे बताया गया है।
- प्रकाशित फ़ाइल कभी नहीं बदली जाती। नई सामग्री नई ID वाली नई फ़ाइल होती है।

## कई वॉल्यूम {#volumes}

एक वॉल्यूम बढ़ाने के बजाय आप Arkvory को और स्टोरेज डायरेक्टरी दे सकते हैं, उदाहरण के लिए दूसरी डिस्क पर। हर अतिरिक्त डायरेक्टरी बिल्ट-इन मॉड्यूल `local-storage` का एक इंस्टेंस है, जिसकी अपनी ID होती है। `ARKVORY_DATA_DIR` की स्टोरेज डायरेक्टरी हमेशा इंस्टेंस `default` होती है।

इंस्टेंस मॉड्यूल फ़ाइल में कॉन्फ़िगर करें (`ARKVORY_MODULES_FILE`, [एनवायरनमेंट वेरिएबल](../reference/environment) देखें):

```json
{
  "format": 1,
  "modules": {
    "local-storage": {
      "enabled": true,
      "config": {
        "instances": {
          "volume-2": { "directory": "/srv/arkvory-volume-2" }
        }
      }
    }
  }
}
```

| फ़ील्ड          | अर्थ                                                                                                                                        | डिफ़ॉल्ट                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `directory`     | डायरेक्टरी का निरपेक्ष पथ। इसमें स्टोरेज डायरेक्टरी या कोई अन्य इंस्टेंस नहीं होना चाहिए, और यह उनके अंदर भी नहीं होनी चाहिए                | आवश्यक                          |
| `acceptsWrites` | `false` इस वॉल्यूम पर नए अपलोड रोकता है। इसकी फ़ाइलें पढ़ी जा सकती रहती हैं, और जो अपलोड इस पर पहले से शुरू हो चुके हैं वे पूरे हो सकते हैं | `true`                          |
| `mode`          | `read-only` केवल डाउनलोड और जाँचें देता है, और हर लेखन और हटाने को अस्वीकार करता है, उदाहरण के लिए केवल-पठन माउंट किए गए वॉल्यूम के लिए     | `full`                          |
| `enabled`       | `false` वॉल्यूम बंद करता है: जब तक आप इसे फिर चालू नहीं करते, इसकी फ़ाइलें डाउनलोड नहीं की जा सकतीं                                         | `true`                          |
| `reserveBytes`  | इस वॉल्यूम पर रखा जाने वाला खाली स्थान, बाइट में                                                                                            | `ARKVORY_STORAGE_RESERVE_BYTES` |

ID में छोटे अक्षर, अंक और `-` होते हैं, यह अक्षर से शुरू होती है और `default` नहीं होती। आप 16 तक इंस्टेंस जोड़ सकते हैं। हर प्रोसेस (API, रीड गेटवे, वर्कर और बैकअप एजेंट) को एक ही मॉड्यूल फ़ाइल पढ़नी चाहिए: अलग इंस्टेंस की योजना वाला प्रोसेस तैयार नहीं होता। बदलाव के बाद सभी सेवाएँ फिर से शुरू करें।

वॉल्यूम जोड़ने के लिए:

1. वॉल्यूम माउंट करें और डायरेक्टरी बनाएँ। यह उस खाते की होनी चाहिए जो सेवाएँ चलाता है। Arkvory यह डायरेक्टरी नहीं बनाता। अगर यह मौजूद नहीं है, उदाहरण के लिए क्योंकि वॉल्यूम माउंट नहीं है, तो वॉल्यूम अनुपलब्ध रहता है और माउंट पॉइंट के नीचे कुछ नहीं लिखा जाता।
2. डायरेक्टरी को नए वॉल्यूम के रूप में चिह्नित करें: `arkvory volume-init --directory /srv/arkvory-volume-2`। इस कमांड को `--root` की ज़रूरत नहीं। यह ऐसी डायरेक्टरी अस्वीकार करता है जो मौजूद नहीं है या खाली नहीं है (केवल `lost+found` हो सकता है), और पहचान फ़ाइल `storage-id` लिखता है। Linux पर यह ऐसी डायरेक्टरी भी अस्वीकार करता है जो माउंट पॉइंट नहीं है, जैसे माउंट न किए गए वॉल्यूम की खाली डायरेक्टरी। माउंट किए गए वॉल्यूम के अंदर की डायरेक्टरी के लिए `--no-expect-mount` जोड़ें। Windows पर `--expect-mount` यह जाँच चालू करता है। सेवाएँ यह फ़ाइल कभी नहीं बनातीं: इसके बिना वॉल्यूम अनुपलब्ध रहता है।
3. इंस्टेंस को मॉड्यूल फ़ाइल में जोड़ें और सेवाएँ फिर से शुरू करें। पहली शुरुआत पर API वॉल्यूम की पहचान दर्ज करता है, यानी डायरेक्टरी में `storage-id` फ़ाइल। उसके बाद हर प्रोसेस यह फ़ाइल जाँचता है। जो वॉल्यूम माउंट नहीं है, या उसी पथ पर कोई दूसरा वॉल्यूम, उस पर कभी नहीं लिखा जाता। वॉल्यूम पर हर लेखन और हटाने से पहले यह फ़ाइल फिर से जाँची जाती है।
4. [प्लेसमेंट नीति](#placement) से चुनें कि कौन-से अपलोड इस वॉल्यूम पर जाएँ।

### नए अपलोड का प्लेसमेंट {#placement}

रिपॉज़िटरी की प्लेसमेंट नीति हर नए अपलोड के लिए स्टोरेज चुनती है। एक नियम में एक ID, एक स्टोरेज (`backendId`) और दो वैकल्पिक शर्तें होती हैं: पैकेज समूह (`models/*`, `tools` या `*`) और बाइट में न्यूनतम आकार। जिस पहले नियम की शर्तें पूरी होती हैं, वही लागू होता है। कोई मेल न होने पर अपलोड `default` में जाता है। एक रिपॉज़िटरी में 32 तक नियम हो सकते हैं।

नीति `arkvoryctl` से या API ऑपरेशन [getStoragePlacement](../api/reference/storage#getStoragePlacement) और [setStoragePlacement](../api/reference/storage#setStoragePlacement) से पढ़ें और बदलें:

```bash
arkvoryctl storage placement --repository releases
arkvoryctl storage placement --repository releases --revision 0 --file rules.json
```

फ़ाइल `rules.json` में नियमों की सूची होती है, उदाहरण के लिए 1 GiB या उससे बड़ी सभी फ़ाइलें `volume-2` पर:

```json
[{ "id": "large", "backendId": "volume-2", "packageGroup": null, "minSizeBytes": "1073741824" }]
```

- नीति पढ़ने के लिए `storage.read` चाहिए, बदलने के लिए `storage.manage`। उत्तर हर स्टोरेज को उसकी स्थिति के साथ भी सूचीबद्ध करता है: `accepting`, `not_accepting`, `read_only`, `disabled`, `unavailable` या `not_loaded`।
- नियम केवल कॉन्फ़िगर किए गए स्टोरेज का नाम ले सकता है। कोई अन्य नाम 400 `backend_unknown` के साथ अस्वीकार किया जाता है।
- नीति एक संशोधन के साथ सहेजी जाती है। अगर किसी और ने इसे बदल दिया, तो इसे फिर पढ़ें और दोबारा सहेजें।
- बदलाव केवल नए अपलोड पर लागू होता है। पहले से संग्रहीत फ़ाइलें जहाँ हैं वहीं रहती हैं; उन्हें स्थानांतरित करने के लिए [संग्रहीत फ़ाइलों को दूसरे वॉल्यूम पर ले जाएँ](#rehome) देखें।

### जब कोई वॉल्यूम नए अपलोड नहीं लेता {#placement-fallback}

प्रकाशन प्लेसमेंट की वजह से कभी विफल नहीं होता। अगर चुना गया स्टोरेज उस समय अपलोड स्वीकार नहीं करता, `acceptsWrites: false`, `read-only`, `enabled: false`, गायब इंस्टेंस या अनुपलब्ध वॉल्यूम (माउंट नहीं, पहचान जाँच विफल, कोई उत्तर नहीं) के कारण, तो नया अपलोड इसके बजाय `default` में बनाया जाता है। अपलोड अपना स्टोरेज `storageBackend` में दिखाता है, मेट्रिक `arkvory_storage_placement_fallback_total` उसे गिनता है, और log में `storage.placement_fallback` पंक्ति होती है।

- **प्रगतिरत अपलोड नहीं हटाए जाते।** अगर भागों में चल रहे अपलोड के दौरान कोई वॉल्यूम डेटा लेना बंद कर दे, तो नए भाग 409 `backend_read_only` के साथ अस्वीकार किए जाते हैं, और क्लाइंट नया अपलोड शुरू करता है। अगर सभी भाग पहले से मौजूद हैं, तो अपलोड पूरा करने पर फ़ाइल `default` में लिखी जाती है। भाग उसी वॉल्यूम से पढ़े जाते हैं जहाँ वे हैं। जो फ़ाइल किसी बाधित प्रयास ने पहले ही वॉल्यूम पर पूरी तरह सहेज दी है, वह वहीं रहती है।
- **अनुपलब्ध वॉल्यूम** की फ़ाइलों के डाउनलोड उसके लौटने तक 503 `unavailable` के साथ विफल होते हैं। सर्वर चलता रहता है, और तैयारी और `writable` केवल `default` का अनुसरण करते हैं। हर प्रोसेस हर 30 सेकंड में अपने वॉल्यूम फिर से जाँचता है।
- **क्लीनअप** हर फ़ाइल को उसी वॉल्यूम पर हटाता है जिस पर वह है, किसी दूसरे वॉल्यूम पर बचे भागों सहित। अनुपलब्ध या केवल-पठन वॉल्यूम पर क्लीनअप फ़ाइल छोड़ देता है और बाद में फिर कोशिश करता है।
- **कोटा और सीमाएँ।** कोटा और `ARKVORY_CAPACITY_BYTES` सभी वॉल्यूम को एक साथ गिनते हैं। रिज़र्व हर वॉल्यूम पर लागू होता है।
- raw, OCI और मिरर अपलोड की **अस्थायी फ़ाइलें** स्टोरेज डायरेक्टरी `default` में रहती हैं।
- **क्लस्टर।** [हाई-अवेलेबिलिटी क्लस्टर](./cluster) में हर वॉल्यूम, स्टोरेज डायरेक्टरी की तरह, रेप्लिकेट होने वाले वॉल्यूम पर एक डायरेक्टरी होना चाहिए: दूसरी डिस्क बाकी सर्वरों पर कॉपी नहीं होती। वरना API शुरू नहीं होता।
- **कॉन्फ़िगरेशन से हटाया गया वॉल्यूम।** Arkvory हर उस वॉल्यूम को याद रखता है जिस पर डेटा रहा है। अगर कोई वॉल्यूम अब मॉड्यूल फ़ाइल में नहीं है, तो उसकी फ़ाइलें डाउनलोड, साफ़ या बैकअप नहीं की जा सकतीं: बैकअप `blob_missing` के साथ विफल होता है। हर प्रक्रिया इसे मेट्रिक `arkvory_storage_backend_unconfigured`, लॉग पंक्ति `storage.backend_unconfigured` और अलर्ट `ArkvoryStorageVolumeUnconfigured` से बताती है, और प्लेसमेंट उत्तर इसे `not_loaded` स्थिति में दिखाता है। ठीक करने के लिए इसे फिर से कॉन्फ़िगर करें। वॉल्यूम को सेवा से हटाने के लिए `acceptsWrites: false` सेट करें, उसकी [फ़ाइलें दूसरे वॉल्यूम पर ले जाएँ](#rehome) और स्थानांतरण पूरे होने तक उसे कॉन्फ़िगर रहने दें।

`arkvory_storage_backend_up` और `arkvory_storage_backend_accepting` पर नज़र रखें, [मॉनिटरिंग](./monitoring#metrics) देखें। बैकअप हर वॉल्यूम की प्रतिलिपि बनाते हैं। पुनर्स्थापना के लिए हर वॉल्यूम के लिए एक खाली डायरेक्टरी चाहिए, [कई वॉल्यूम पुनर्स्थापित करें](./backups#restore-volumes) देखें।

### संग्रहीत फ़ाइलों को दूसरे वॉल्यूम पर ले जाएँ {#rehome}

पहले से संग्रहीत फ़ाइलों को ले जाने के लिए, उदाहरण के लिए किसी वॉल्यूम को सेवा से हटाने या नए वॉल्यूम को भरने के लिए, सर्वर पर स्थानांतरण की योजना बनाएँ। सेवाएँ चलती रहती हैं।

```bash
arkvory storage rehome --root /opt/proanima-arkvory --from volume-2 --to default
arkvory storage moves --root /opt/proanima-arkvory
```

1. `rehome` `--from` स्टोरेज की हर प्रकाशित फ़ाइल के लिए स्थानांतरण की योजना बनाता है और नियोजित स्थानांतरणों की संख्या तथा स्थिति के अनुसार स्थानांतरण दिखाता है। `--repository <name>` इसे एक रिपॉज़िटरी तक सीमित करता है, `--limit <n>` फ़ाइलों की संख्या तक (डिफ़ॉल्ट 10 000, अधिकतम 100 000)। जिस फ़ाइल का स्थानांतरण पहले से चल रहा है, उसकी योजना दोबारा नहीं बनती। दोनों स्टोरेज कॉन्फ़िगर होने चाहिए। लक्ष्य को नए अपलोड स्वीकार करने चाहिए, वरना कमांड `backend_read_only` के साथ विफल होता है। स्रोत केवल-पठन हो सकता है।
2. वर्कर स्थानांतरण करता है, एक बार में दो। हर फ़ाइल के लिए वह बाइट लक्ष्य पर कॉपी करता है और आकार व SHA-256 जाँचता है, फ़ाइल को लक्ष्य पर स्विच करता है, फिर स्रोत की प्रति हटाता है। फ़ाइल अपनी ID रखती है: लिंक, पथ, स्टेज और संदर्भ मान्य रहते हैं।
3. `moves` स्थिति के अनुसार स्थानांतरण दिखाता है: `planned`, `copied`, `switched`, `released` (पूरा), `skipped` (इस बीच फ़ाइल हटा दी गई; लक्ष्य में उसकी प्रति हटा दी गई) और `failed`।

- **डाउनलोड और बैकअप।** स्विच से पहले शुरू हुआ डाउनलोड अंत तक स्रोत से पढ़ता है। स्रोत की प्रति उस डाउनलोड के बाद और फ़ाइल को शामिल करने वाले हर बैकअप के बाद ही हटाई जाती है। हटाना प्रतीक्षा करता है; यह कभी किसी डाउनलोड को नहीं रोकता।
- **विफलताएँ।** विफल चरण बढ़ते अंतराल के साथ दोहराया जाता है। 5 विफल प्रयासों के बाद, या जब लक्ष्य अपलोड लेना बंद कर दे, स्थानांतरण `failed` हो जाता है और फ़ाइल जहाँ है वहीं रहती है। नए स्थानांतरण की योजना के लिए `rehome` फिर से चलाएँ। अगला स्थानांतरण उस प्रति को जाँचकर फिर से इस्तेमाल करता है जो विफल स्थानांतरण ने लक्ष्य में छोड़ी थी। यह स्विच तक लागू होता है: उसके बाद स्थानांतरण कभी `failed` नहीं होता, और स्रोत की प्रति हटाना सफल होने तक दोहराया जाता है। जब तक कोई स्टोरेज अनुपलब्ध या केवल-पढ़ने योग्य है, जैसे निकासी का स्रोत, चरण उसकी प्रतीक्षा करता है और हर 5 मिनट में फिर जाँचा जाता है।
- **गति।** `ARKVORY_REHOME_BYTES_PER_SECOND` सीमित करता है कि वर्कर कितनी तेज़ी से कॉपी करता है। डिफ़ॉल्ट रूप से कोई सीमा नहीं है।
- **कोटा** हर फ़ाइल को स्थानांतरण के दौरान और बाद में एक ही बार गिनते हैं।
- Docker Compose के साथ, कमांड एक बार चलने वाला वर्कर कंटेनर चलाता है।

वर्कर लॉग पंक्तियाँ `storage.move_completed`, `storage.move_skipped` और `storage.move_failed` लिखता है।

## डिस्क की योजना बनाएँ {#disk}

निम्नलिखित स्टोरेज वॉल्यूम पर डिस्क स्थान लेते हैं:

| क्या                             | टिप्पणियाँ                                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| प्रकाशित फ़ाइलें                 | आपके रखे सभी संस्करण                                                                                                                |
| प्रगतिरत अपलोड                   | भाग और स्टेजिंग फ़ाइलें, जब तक अपलोड समाप्त न हो                                                                                    |
| भागों में तैयार अपलोड की फ़ाइलें | अस्थायी भाग तैयार फ़ाइल के पास तब तक रहते हैं जब तक कोई भौतिक क्लीनअप पास उन्हें हटा न दे। [भौतिक क्लीनअप](#physical-cleanup) देखें |
| हटाई गई फ़ाइलें                  | वे डिस्क पर तब तक रहती हैं जब तक छूट अवधि समाप्त न हो और कोई क्लीनअप पास उन्हें हटा न दे                                            |
| मिरर प्रतियाँ                    | जब तक मिरर कोई फ़ाइल कॉपी करता है, `mirror-staging` में एक भाग। [मिरर](./mirrors) देखें                                             |

स्टोरेज के अलावा, अगर हो सके तो PostgreSQL डेटाबेस, लॉग और बैकअप स्टोरेज (vault) की योजना अलग वॉल्यूम पर बनाएँ। [बैकअप](./backups) देखें।

Arkvory स्टोरेज वॉल्यूम पर मुक्त स्थान का एक **रिज़र्व** रखता है। डिफ़ॉल्ट रूप से यह 1 GiB (`ARKVORY_STORAGE_RESERVE_BYTES`) है। जो अपलोड रिज़र्व इस्तेमाल कर लेता, उसे HTTP 507 और कारण `storage_full` के साथ अस्वीकार कर दिया जाता है। डाउनलोड काम करते रहते हैं। नए डेटा के लिए जगह न होने पर `GET /health/ready` `writable: false` दिखाता है।

Arkvory हर वॉल्यूम पर 100 000 inode भी खाली रखता है (`ARKVORY_STORAGE_RESERVE_INODES`): हर संग्रहीत फ़ाइल और हर भाग एक फ़ाइल है, इसलिए किसी वॉल्यूम के inode बाइट से पहले खत्म हो सकते हैं। जो लेखन उन्हें इस्तेमाल कर लेता, उसे भी इसी तरह अस्वीकार किया जाता है। NTFS जैसे बिना inode गिनती वाले फ़ाइल सिस्टम केवल बाइट के लिए जाँचे जाते हैं।

दो सीमाएँ डिस्क से स्वतंत्र रूप से काम करती हैं:

- `ARKVORY_CAPACITY_BYTES` इंस्टॉलेशन की सभी आरक्षित सामग्री को सीमित करता है। डिफ़ॉल्ट 10 TiB है। यह एक तार्किक सीमा है, डिस्क की जाँच नहीं। इस तक पहुँचने पर, अपलोड HTTP 507 और कारण `catalog_limit` के साथ विफल हो जाते हैं।
- `ARKVORY_MAX_OBJECT_BYTES` एक फ़ाइल का आकार सीमित करता है।

[एनवायरनमेंट वेरिएबल](../reference/environment#storage-and-limits) देखें। Arkvory के पास स्टोरेज या डेटाबेस के मुक्त स्थान के लिए कोई मेट्रिक नहीं है। वॉल्यूम पर अपने ऑपरेटिंग सिस्टम उपकरणों या node exporter से नज़र रखें।

## स्टोरेज कौन प्रबंधित कर सकता है {#permissions}

स्टोरेज सेटिंग्स सामान्य पढ़ने और लिखने के अधिकारों का हिस्सा नहीं हैं। सेवा कुंजी को रिपॉज़िटरी पर स्पष्ट कार्रवाइयाँ चाहिए:

| कार्रवाई           | अनुमति देता है                                                                      |
| ------------------ | ----------------------------------------------------------------------------------- |
| `storage.read`     | नीति, उपयोग, क्लीनअप सेटिंग्स और प्लेसमेंट देखें                                    |
| `storage.manage`   | नीति, कोटा, क्लीनअप सेटिंग्स और प्लेसमेंट बदलें, और क्लीनअप बैच का अनुरोध करें      |
| `artifact.delete`  | विलोपन का पूर्वावलोकन करें, आर्टिफ़ैक्ट हटाएँ, और स्वचालित प्रतिधारण नीति चालू करें |
| `diagnostics.read` | स्टोरेज इवेंट पढ़ें                                                                 |

पासवर्ड वाले खातों और पुनर्प्राप्ति कुंजी के पास खुद से ये अधिकार नहीं होते। कंसोल में स्टोरेज प्रबंधित करने के लिए:

1. रिपॉज़िटरी के लिए ऐसी नीति वाला सेवा खाता बनाएँ जिसमें चारों कार्रवाइयाँ शामिल हों। [खाते और एक्सेस](../use/accounts) देखें।
2. उसके लिए एक कुंजी जारी करें और सक्रिय करें।
3. कंसोल में [[ui:keySignIn]] खोलें, कुंजी चिपकाएँ और [[ui:connect]] चुनें।
4. [[ui:repositories]] खोलें, और रिपॉज़िटरी के कार्ड पर [[ui:repositoryStorage]] चुनें।

कैटलॉग के ऊपर पैनल [[ui:storageTitle]] दिखाई देता है। अधिकारों के बिना, पैनल छिपा रहता है।

चालू प्रतिधारण नीति उस **कुंजी से बँधी होती है जिसने उसे चालू किया**। हर स्वचालित रन फिर जाँचता है कि यह कुंजी अब भी सक्रिय है, समाप्त नहीं हुई, और उसके पास अब भी `storage.manage` और `artifact.delete` हैं। अगर आप कुंजी निरस्त करते हैं या उसके अधिकार घटाते हैं, तो विलोपन रुक जाता है और इवेंट `retention.failed` दिखाई देता है। कुंजी रोटेट करने के बाद, नई कुंजी के साथ नीति दोबारा सहेजें।

## कोटा और चेतावनी थ्रेसहोल्ड {#quotas}

रिपॉज़िटरी का एक कोटा हो सकता है। कोटा के बिना, केवल वैश्विक सीमा लागू होती है।

| सेटिंग              | कंसोल फ़ील्ड                  | अर्थ                                                                                                                                | डिफ़ॉल्ट      |
| ------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| कोटा                | [[ui:storageQuota]]           | रिपॉज़िटरी जितना अधिकतम स्थान इस्तेमाल कर सकती है। API सटीक बाइट लेता है, 1 से 9 007 199 254 740 991 तक, और बिना सीमा के लिए `null` | कोई सीमा नहीं |
| चेतावनी थ्रेसहोल्ड  | [[ui:storageWarningPercent]]  | कोटा का वह हिस्सा जो चेतावनी देता है। 1–98                                                                                          | 80            |
| क्रिटिकल थ्रेसहोल्ड | [[ui:storageCriticalPercent]] | वह हिस्सा जो त्रुटि देता है। 2–99, चेतावनी थ्रेसहोल्ड से अधिक                                                                       | 95            |

कोटा के विरुद्ध गिना जाने वाला उपयोग रिपॉज़िटरी की उन सभी फ़ाइलों का आकार है जो अब तक डिस्क से नहीं हटाई गईं: प्रकाशित फ़ाइलें, अधूरे अपलोड और वे हटाई गई फ़ाइलें जो क्लीनअप की प्रतीक्षा कर रही हैं। इसलिए हटाई गई फ़ाइल तब तक कोटा इस्तेमाल करती रहती है जब तक कोई क्लीनअप पास उसे हटा न दे।

- **जाँच।** अपलोड शुरू होने पर सर्वर कोटा जाँचता है। जो नया अपलोड कोटा पार कर लेता, वह HTTP 507 और कारण `storage_quota` के साथ विफल हो जाता है। उसी आइडेम्पोटेंसी कुंजी के साथ रीट्राई स्थान दोबारा आरक्षित नहीं करती।
- **घटाना।** आप कोटा मौजूदा उपयोग से कम सेट कर सकते हैं। चल रहे अपलोड पूरे हो सकते हैं। सीमा से अधिक नए अपलोड अस्वीकार कर दिए जाते हैं।
- **कोई स्वचालित मुक्ति नहीं।** कोटा कभी विलोपन नहीं कराता। प्रतिधारण कोटा पूरा करने के लिए अतिरिक्त बिल्ड नहीं हटाता।
- **स्थितियाँ।** स्थिति `unlimited`, `normal`, `warning`, `critical` या `exceeded` होती है। स्थिति का बदलाव एक बार स्टोरेज इवेंट के रूप में दर्ज होता है।
- **निगरानी।** सर्वर हर मिनट अधिकतम 20 रिपॉज़िटरी की स्थितियाँ फिर जाँचता है, तब भी जब स्वचालित विलोपन बंद हो।

ये संख्याएँ तार्किक आरक्षण हैं, मुक्त डिस्क स्थान नहीं। कोई रिपॉज़िटरी अपने कोटा के भीतर हो सकती है जबकि डिस्क भरी हुई हो, क्योंकि डिस्क पर स्टेजिंग फ़ाइलें और अन्य रिपॉज़िटरी भी रहती हैं।

### बिल्ड कैसे चुने जाते हैं {#retention-rules}

1. सर्वर हर काउंटर के बिल्ड को **प्रकाशन समय** से क्रमबद्ध करता है, सबसे नया पहले। यह क्रम संस्करणों का SemVer क्रम नहीं है।
2. काउंटर समूहन पर निर्भर करता है। पैकेज और चैनल के साथ, एक बिल्ड प्रति पैकेज (`group/name`) उन सभी कॉन्फ़िगर किए गए चैनल लेबलों के लिए अलग-अलग गिना जाता है जो वह रखता है। बिना कॉन्फ़िगर किए लेबल वाला बिल्ड डिफ़ॉल्ट N के साथ पैकेज के एक साझा काउंटर में जाता है। पैकेज के साथ, हर पैकेज का एक काउंटर होता है। पूरी रिपॉज़िटरी के साथ, सभी बिल्ड एक काउंटर साझा करते हैं। पैकेज नाम केस की उपेक्षा करते हैं, लेबल नहीं।
3. कोई बिल्ड तब रहता है जब वह उन **किसी भी** काउंटर के अंतिम N में हो जिनसे उसका संबंध है।
4. न्यूनतम आयु से छोटा बिल्ड रहता है।
5. संरक्षित लेबल वाला बिल्ड रहता है। उसके लेबल वर्तमान एनोटेशन से आते हैं, या जब एनोटेशन न हो तो अपलोड से। संरक्षित बिल्ड अब भी रैंकिंग में हिस्सा लेते हैं, इसलिए रखी गई संख्या N से अधिक हो सकती है।

कोई बिल्ड तब तक कभी नहीं हटाया जाता जब तक उसकी किसी को ज़रूरत हो:

- कोई बाहरी सेवा उसका संदर्भ रखती है।
- कोई फ़ाइल पथ, वर्तमान या इतिहास से, उसे इस्तेमाल करता है।
- कोई अन्य बिल्ड उसे अटैचमेंट के रूप में सूचीबद्ध करता है, अभी या इतिहास में।
- उसे किसी स्टेज पर प्रमोट किया गया है। पहले स्टेज हटाएँ।
- कोई कंटेनर इमेज, Git LFS या npm प्रविष्टि उसे इस्तेमाल करती है।

बिल्ड हटाना तार्किक है: वह सूचियों से हट जाता है और नए डाउनलोड 404 के साथ विफल हो जाते हैं। बाइट बाद में डिस्क से जाते हैं, [भौतिक क्लीनअप](#physical-cleanup) में। पैकेज संस्करण आरक्षित रहता है, इसलिए वही संस्करण दूसरी सामग्री के साथ दोबारा प्रकाशित नहीं किया जा सकता।

### नीति सुरक्षित रूप से चालू करें {#retention-enable}

पहले पूर्वावलोकन करें, फिर चालू करें। पूर्वावलोकन दिखाता है कि सहेजी गई नीति क्या हटाएगी, और यह कुछ भी नहीं हटाता।

1. चारों कार्रवाइयाँ वाली कुंजी से कनेक्ट करें, और रिपॉज़िटरी का स्टोरेज पैनल खोलें।
2. फ़ील्ड सेट करें और [[ui:storageEnabled]] बंद छोड़ें। [[ui:storageSave]] चुनें।
3. [[ui:storagePreview]] चुनें। सूची अधिकतम 100 बिल्ड दिखाती है जिन्हें सहेजी गई नीति एक बैच में हटाएगी। अगर और उम्मीदवार बचे हैं, तो कंसोल यह बताता है।
4. अगर सूची सही है, तो [[ui:storageEnabled]] और पुष्टि [[ui:storageAcknowledge]] पर टिक करें, फिर दोबारा सहेजें। इसके लिए `artifact.delete` चाहिए।

नोट्स:

- पूर्वावलोकन किसी एक क्षण को दिखाता है। जब नीति चलती है, वह फिर रैंकिंग करती है और निर्भरताएँ फिर जाँचती है।
- नीति एक संशोधन के साथ सहेजी जाती है। अगर किसी और ने इसे बदल दिया, तो दोबारा लोड करें और सहेजें।
- [[ui:storageRefresh]] सेटिंग्स और उपयोग दोबारा लोड करता है।

### यह कैसे चलता है {#retention-run}

जो API प्रोसेस लिखता है (रीड गेटवे नहीं) वह हर 60 सेकंड में जाँचता है और अधिकतम 20 देय नीतियाँ संभालता है। एक बैच अधिकतम 100 बिल्ड हटाता है। अगर उम्मीदवार बचे हैं, तो अगला बैच एक मिनट बाद शुरू होता है। वरना अगला रन अंतराल के बाद आता है। शेड्यूल डेटाबेस में सहेजा जाता है और रीस्टार्ट के बाद बना रहता है।

आप API ऑपरेशन [runStoragePolicy](../api/reference/storage#runStoragePolicy) से खुद भी एक बैच चला सकते हैं। उपयोग, पूर्वावलोकन और इवेंट के ऑपरेशन उसी [Storage API reference](../api/reference/storage) में हैं।

## भौतिक क्लीनअप {#physical-cleanup}

किसी आर्टिफ़ैक्ट को हटाना, किसी व्यक्ति द्वारा या किसी नीति द्वारा, उसे केवल कैटलॉग से हटाता है। **भौतिक क्लीनअप** उसके बाइट डिस्क से हटाता है, पृष्ठभूमि में और API, वर्कर या रीड गेटवे को रोके बिना। यह यह भी करता है:

- बिना पूरे हुए समाप्त हो चुके अपलोड रद्द करता है, और उनके भाग हटाता है।
- तैयार अपलोड के अस्थायी भाग हटाता है।

यह हटाने के लिए बिल्ड नहीं चुनता। यह केवल वही हटाता है जो पहले ही हटाया या रद्द किया जा चुका है।

**भौतिक क्लीनअप डिफ़ॉल्ट रूप से बंद है, और यह प्रति रिपॉज़िटरी सेट होता है।** जिस भी रिपॉज़िटरी का आप इस्तेमाल करते हैं उसमें इसे चालू करें। तब तक, हटाई गई फ़ाइलें, समाप्त हो चुके अपलोड और तैयार अपलोड के भाग डिस्क पर रहते हैं, और कोटा हटाई गई फ़ाइलें गिनता है।

### सेटिंग्स {#cleanup-settings}

रिपॉज़िटरी के पैनल में, [[ui:cleanupTitle]] खोलें:

| सेटिंग    | कंसोल फ़ील्ड           | अर्थ                                                | डिफ़ॉल्ट | श्रेणी   |
| --------- | ---------------------- | --------------------------------------------------- | -------- | -------- |
| चालू करें | [[ui:cleanupEnabled]]  | पृष्ठभूमि क्लीनअप चालू करता है                      | बंद      |          |
| छूट अवधि  | [[ui:cleanupGrace]]    | हटाई गई फ़ाइल कितनी देर डिस्क पर रहती है, घंटों में | 24       | 0–8760   |
| बैच       | [[ui:cleanupBatch]]    | एक बैच में संभाली जाने वाली फ़ाइलें                 | 25       | 1–100    |
| अंतराल    | [[ui:cleanupInterval]] | बैचों के बीच सेकंड                                  | 60       | 5–86 400 |
| विलंब     | [[ui:cleanupDelay]]    | फ़ाइलों के बीच रुकावट के मिलीसेकंड                  | 50       | 0–1000   |

इन्हें लागू करने के लिए [[ui:cleanupSave]] चुनें। बदलाव तुरंत लागू होता है। अगर आप क्लीनअप बंद करते हैं, तो यह वर्तमान फ़ाइल के बाद रुक जाता है। [[ui:cleanupRun]] जल्द एक बैच माँगता है, यह तुरंत नहीं हटाता। अंतिम बैच का परिणाम देखने के लिए [[ui:cleanupRefresh]] चुनें।

छूट अवधि रीसायकल बिन नहीं है। मान 0 के साथ, कोई फ़ाइल हटाए जाने के तुरंत बाद और कोई पाठक उसे खोले बिना जा सकती है। Arkvory हटाए गए आर्टिफ़ैक्ट को पुनर्स्थापित नहीं कर सकता।

### क्लीनअप क्या करता है और क्या छोड़ता है {#cleanup-rules}

- यह केवल उन फ़ाइलों को हटाता है जो रद्द या हटाई गई हैं, छूट अवधि के बाद। यह फिर जाँचता है कि उन्हें कुछ भी इस्तेमाल नहीं करता: कोई संदर्भ, फ़ाइल पथ इतिहास या अटैचमेंट इतिहास नहीं।
- खुला हुआ डाउनलोड, लिखा जा रहा अपलोड और चल रहे बैकअप को चाहिए कोई फ़ाइल, क्लीनअप को उस फ़ाइल को **छोड़ने** पर मजबूर करते हैं। अगला बैच फिर कोशिश करता है। अंतिम परिणाम दिखाता है कि उसने कितनी फ़ाइलें संभालीं, छोड़ीं और विफल रहीं, और कितने बाइट मुक्त किए।
- कोटा और तार्किक क्षमता फ़ाइलों के डिस्क से हटाए जाने के बाद ही मुक्त होती हैं।
- बैच बैच आकार और विलंब से सीमित होता है, जो डिस्क लोड घटाता है। यह कठोर डिस्क थ्रूपुट की गारंटी नहीं देता, और अन्य अनुरोधों की विलंबता पर शून्य प्रभाव का वादा नहीं कर सकता।
- क्लीनअप writer API में चलता है, प्रति डेटाबेस एक बार। writer हर 5 सेकंड में एक देय रिपॉज़िटरी जाँचता है। चालू writer के बिना, कुछ भी साफ़ नहीं होता।
- क्लीनअप तभी चालू करें जब आप हर Arkvory प्रोसेस अपडेट कर चुके हों, गेटवे और वर्कर सहित। क्लीनअप प्रोटोकॉल के बिना पुराना प्रोसेस क्लीनअप को उसका काम टालने पर मजबूर करता है।

## आर्टिफ़ैक्ट हटाएँ {#delete-artifacts}

आप एक प्रकाशित आर्टिफ़ैक्ट हाथ से हटा सकते हैं। आपको रिपॉज़िटरी पर `artifact.delete` चाहिए।

1. [[ui:metadata]] में आर्टिफ़ैक्ट खोलें, और [[ui:deletionTitle]] ढूँढें।
2. [[ui:deletionInspect]] चुनें। कंसोल दिखाता है कि आर्टिफ़ैक्ट को अब भी क्या इस्तेमाल करता है। अगर कुछ विलोपन रोकता है, तो पहले वह निर्भरता हटानी होगी।
3. पुष्टि के लिए आर्टिफ़ैक्ट की ID चिपकाएँ, फिर [[ui:deletionSubmit]] चुनें।

इस तरह हटाने पर संरक्षित लेबल नहीं जाँचे जाते, क्योंकि वस्तु आप खुद चुनते हैं। निर्भरताएँ हमेशा जाँची जाती हैं। विलोपन के बाद:

- आर्टिफ़ैक्ट सूचियों और खोजों से हट जाता है। नया डाउनलोड 404 के साथ विफल हो जाता है। जो डाउनलोड पहले से चल रहा है वह पूरा हो सकता है।
- पैकेज संस्करण आरक्षित रहता है।
- बाइट डिस्क पर तब तक रहते हैं जब तक छूट अवधि के बाद [भौतिक क्लीनअप](#physical-cleanup) उन्हें न हटा दे।
- आप इसे कंसोल या API में पूर्ववत नहीं कर सकते।

कई आर्टिफ़ैक्ट के लिए, API [previewRetention](../api/reference/storage#previewRetention) और [applyRetention](../api/reference/storage#applyRetention) देता है। पूर्वावलोकन किसी तिथि से पहले प्रकाशित उम्मीदवारों को उनके अवरोधक कारणों के साथ सूचीबद्ध करता है। Apply केवल आपके दिए ID हटाता है, प्रति कॉल अधिकतम 100, और हर ID के लिए परिणाम लौटाता है: `deleted`, `already_deleted`, `protected`, `changed`, `not_eligible` या `not_found`। हर परिणाम जाँचें, केवल HTTP स्टेटस नहीं।

## स्टोरेज डायग्नोस्टिक्स और इवेंट {#diagnostics}

अनुभाग [[ui:storageEvents]] रिपॉज़िटरी में क्या हुआ, यह सूचीबद्ध करता है, सबसे पुराना पहले, 100 प्रति पेज। अगले पेज के लिए [[ui:storageMore]] चुनें। इसे पढ़ने के लिए `diagnostics.read` चाहिए। API ऑपरेशन [getStorageEvents](../api/reference/storage#getStorageEvents) है, स्तर (`info`, `warning`, `error`) से फ़िल्टर के साथ।

| इवेंट                                                                                                 | स्तर                   | अर्थ                                                                                               |
| ----------------------------------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------- |
| `storage.policy_updated`                                                                              | info                   | प्रतिधारण नीति सहेजी गई                                                                            |
| `retention.completed`                                                                                 | info                   | एक बैच ने बिल्ड हटाए। इवेंट गिनती रखता है                                                          |
| `retention.failed`                                                                                    | error                  | स्वचालित विलोपन रुक गया, उदाहरण के लिए क्योंकि अधिकृत करने वाली कुंजी निरस्त कर दी गई              |
| `cleanup.configured`                                                                                  | info                   | क्लीनअप सेटिंग्स सहेजी गईं                                                                         |
| `storage.placement_updated`                                                                           | info                   | प्लेसमेंट नीति सहेजी गई                                                                            |
| `cleanup.completed`                                                                                   | info या error          | एक क्लीनअप बैच ने फ़ाइलें संभालीं, छोड़ीं या विफल रहीं। यह गिनतियाँ और मुक्त बाइट सूचीबद्ध करता है |
| `capacity.normal`, `capacity.warning`, `capacity.critical`, `capacity.exceeded`, `capacity.unlimited` | info, warning या error | कोटा स्थिति बदली                                                                                   |
| HTTP error codes                                                                                      | warning या error       | इस रिपॉज़िटरी को किसी प्रबंधित कुंजी का अनुरोध विफल हुआ। इवेंट अनुरोध ID, रूट और स्टेटस रखता है    |

इतिहास सीमित है: प्रति रिपॉज़िटरी 1000 इवेंट और कुल 20 000, और सबसे पुराने हटा दिए जाते हैं। यह best-effort डायग्नोस्टिक्स है, गारंटीकृत डिलीवरी वाला लॉग नहीं। जो चाहिए उसे समय पर निर्यात करें, और दीर्घकालिक प्रमाण के लिए सर्वर लॉग इस्तेमाल करें। [निगरानी](./monitoring) देखें।

पैनल उपयोग भी दिखाता है: प्रकाशित बाइट, अधूरे अपलोड, क्लीनअप की प्रतीक्षा कर रहे बाइट, और कोटा के विरुद्ध कुल। API ऑपरेशन [getStorageUsage](../api/reference/storage#getStorageUsage) है।

## जब डिस्क भर जाए {#disk-full}

संकेत: अपलोड HTTP 507 और कारण `storage_full` के साथ विफल होते हैं, `GET /health/ready` `writable: false` दिखाता है, या ऑपरेटिंग सिस्टम मुक्त स्थान नहीं होने की सूचना देता है। डाउनलोड काम करते रहते हैं। आपके स्थान मुक्त करने के बाद क्लाइंट अपने अपलोड जारी रख सकते हैं।

1. **कारण ढूँढें।** स्टोरेज वॉल्यूम, डेटाबेस वॉल्यूम और vault वॉल्यूम का मुक्त स्थान जाँचें। स्टोरेज पैनल के उपयोग आँकड़ों की तुलना करें। बड़े "क्लीनअप की प्रतीक्षा" आँकड़ों का मतलब है कि हटाया गया डेटा अब भी डिस्क पर है। बड़ा "अधूरे अपलोड" आँकड़ा छोड़े गए अपलोड दर्शाता है।
2. **क्लीनअप चलाएँ।** अगर क्लीनअप बंद है, तो हर रिपॉज़िटरी में इसे चालू करें, छोटी छूट अवधि जैसे 0 के साथ अगर आप स्वीकार करते हैं कि हटाई गई फ़ाइलें तुरंत चली जाएँ। [[ui:cleanupRun]] चुनें। यह तैयार अपलोड के अस्थायी भाग और समाप्त हो चुके अपलोड भी हटाता है। बैचों की प्रतीक्षा करें और अंतिम परिणाम पढ़ें। क्लीनअप इस्तेमाल में रही फ़ाइलें छोड़ देता है, इसलिए इसे दोहराएँ।
3. **जो ज़रूरत न हो हटाएँ।** प्रतिधारण नीति लागू करें, या आर्टिफ़ैक्ट हटाएँ। यह स्थान तभी मुक्त करता है जब क्लीनअप बाइट हटा दे।
4. **स्थान बढ़ाएँ।** वॉल्यूम या डिस्क बढ़ाएँ। अगर vault या अन्य डेटा वही वॉल्यूम साझा करते हैं तो उन्हें हटाकर दूसरी जगह ले जाएँ। आप [एक वॉल्यूम जोड़](#volumes) भी सकते हैं और नए अपलोड वहाँ रख सकते हैं।
5. **रिकवरी जाँचें।** स्थान मुक्त होने के बाद, `writable` वापस `true` हो जाता है और अपलोड फिर काम करते हैं।

`blobs/`, `staging/` या `parts/` में हाथ से फ़ाइलें न हटाएँ: इससे डेटाबेस और डिस्क के बीच का संबंध टूट जाता है। अगर उसी वॉल्यूम पर आपके लॉग और डेटाबेस के लिए रिज़र्व बहुत छोटा है, तो `ARKVORY_STORAGE_RESERVE_BYTES` बढ़ाएँ।

अगर कोई अपलोड कारण `storage_quota` या `catalog_limit` के साथ विफल होता है, तो डिस्क समस्या नहीं है। कोटा या वैश्विक सीमा बढ़ाएँ, या डेटा हटाएँ।

## सीमाएँ {#limits}

- प्रतिधारण नीति केवल पंजीकृत UPack बिल्ड संभालती है। यह कभी अन्य फ़ाइलें नहीं हटाती।
- प्रतिधारण क्रम प्रकाशन समय है, संस्करण संख्या नहीं।
- स्टोरेज, कोटा और क्लीनअप के लिए सेवा कुंजी की स्पष्ट कार्रवाइयाँ चाहिए। पासवर्ड खातों और पुनर्प्राप्ति कुंजी के पास ये नहीं होतीं।
- भौतिक क्लीनअप डिफ़ॉल्ट रूप से बंद है और हर रिपॉज़िटरी के लिए सेट होता है।
- हटाया गया आर्टिफ़ैक्ट पुनर्स्थापित नहीं किया जा सकता। डेटा बैकअप से पुनर्स्थापित करें। [बैकअप](./backups) देखें।
- मिरर की गई रिपॉज़िटरी कोई स्टोरेज नीति नहीं चलातीं। [मिरर](./mirrors) देखें।
- स्टोरेज स्थानीय फ़ाइल सिस्टम होना चाहिए। नेटवर्क शेयर का कोई समर्थन नहीं है। अतिरिक्त [वॉल्यूम](#volumes) भी स्थानीय डायरेक्टरी होते हैं। संग्रहीत फ़ाइलें उनके बीच केवल सर्वर पर कमांड [`arkvory storage rehome`](#rehome) से जाती हैं, API से नहीं।
- Windows पर Arkvory हर फ़ाइल को डिस्क पर सिंक करता है, लेकिन उसे प्रकाशित करने वाली डायरेक्टरी एंट्री को सिंक नहीं कर सकता: वहाँ Node.js डायरेक्टरी सिंक नहीं देता। अपलोड के कुछ ही देर बाद बिजली जाने से प्रकाशित फ़ाइल डिस्क से गायब रह सकती है। UPS इस्तेमाल करें और [बैकअप](./backups) या [मिरर](./mirrors) रखें। Linux पर डायरेक्टरी एंट्री भी सिंक होती हैं।
