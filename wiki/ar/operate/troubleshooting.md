# استكشاف الأخطاء وإصلاحها

اعثر على العَرَض الذي تواجهه، واقرأ السبب وطبّق الحل. يسمي كل قسم حدث السجل أو الخطأ الذي ينبغي أن تراه. لمعنى رمز خطأ، انظر [الأخطاء](../api/errors).

## الخطوات الأولى {#first-steps}

1. استعلم من نقطة نهاية الحالة: `curl -fsS http://127.0.0.1:8080/health/status`. تعني `{"status":"ready"}` أن واجهة API تستطيع الوصول إلى قاعدة بياناتها وتخزينها.
2. اقرأ أحدث أسطر سجل الخدمة التي تفشل. انظر [السجلات والملاحظات](#logs-and-feedback).
3. ابحث عن الحدث `startup.failed` أو `worker.unavailable`. يسمي حقل `reason` السبب.
4. إذا أبلغ عميل عن خطأ، فاطلب معرّف الطلب وابحث عنه في السجل.

## الخادم لا يبدأ {#server-does-not-start}

يعيد مدير الخدمات تشغيل الخدمة الفاشلة كل 10 ثوانٍ. يكرر السجل حينئذٍ `startup.failed`. اقرأ الحقل `reason` والحقلين `errno` و`sqlstate`.

### المنفذ مشغول {#port-busy}

**السبب.** يتضمن `startup.failed` الحقل `errno` بالقيمة `EADDRINUSE`. يستمع برنامج آخر على المنفذ 8080 ‏(`ARKVORY_PORT`)، أو لا تزال عملية Arkvory قديمة تعمل.

**الحل.** اعثر على العملية المالكة للمنفذ وأوقفها، أو غيّر المنفذ.

```bash
sudo ss -ltnp 'sport = :8080'
```

```powershell
Get-NetTCPConnection -LocalPort 8080 | Select-Object LocalAddress, OwningProcess
```

لتغيير المنفذ، حرر `ARKVORY_PORT` في `config/runtime.json` وأعد تشغيل الخدمات. يتغير عنوان وحدة التحكم معه.

### يتعذر الوصول إلى قاعدة البيانات أو ترفض تسجيل الدخول {#database-problems}

**السبب.** يعرض السجل أحد الأسباب التالية:

| `reason`                                                                   | المعنى                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `dependency unavailable`، مع `errno` بالقيمة `ECONNREFUSED` أو `ETIMEDOUT` | ‏PostgreSQL متوقف، أو يستمع في مكان آخر، أو يحجبه جدار ناري  |
| `database authentication failed`                                           | المستخدم أو كلمة المرور في `ARKVORY_DATABASE_URL` غير صحيحين |
| `database does not exist`                                                  | قاعدة البيانات المسماة في عنوان URL مفقودة                   |
| `database role lacks a required privilege`                                 | لا يستطيع الدور إنشاء الجداول أو تغييرها                     |

**الحل.** ابدأ PostgreSQL، أو صحح `ARKVORY_DATABASE_URL` في `config/runtime.json` وأعد تشغيل الخدمات. تستمع قاعدة البيانات المُدارة على `127.0.0.1` بالمنفذ الموجود في `ARKVORY_DATABASE_URL` (الخدمة `Arkvorydatabase` على Windows و`arkvory-database` على Linux). تبدأ الخدمات تلقائياً عندما تستجيب قاعدة البيانات. لا تحذف المجلد `database/`. يعني سطر السجل `could not bind IPv4 address "127.0.0.1": Permission denied` على Windows أن Windows حجز ذلك المنفذ عند الإقلاع (يسرد `netsh int ipv4 show excludedportrange protocol=tcp` النطاقات المحجوزة). يستثني برنامج الإعداد منفذ قاعدة البيانات من هذه النطاقات: يظهر الاستثناء مع `*`، ويبقى بعد إعادة التشغيل، وتضيفه عملية الإصلاح أو التحديث مجدداً إذا غاب. لنقل تثبيت أقدم من منفذ محجوز، أوقف خدمات Arkvory، واضبط المنفذ الحر نفسه (مثلاً 45329) في `port` ضمن `database/settings.json` وفي `ARKVORY_DATABASE_URL` ضمن `config/runtime.json`، وشغّل برنامج الإعداد مجدداً: تستثني عملية الإصلاح المنفذ الجديد وتبدأ الخدمات.

### قاعدة البيانات والبرنامج غير متوافقين {#migrations}

**السبب.** يبدأ السبب بـ`unavailable:` ويقول `Database migrations 1 through N are required; run migrate` أو `Database schema is newer than this release` أو `database schema is missing; run migrations`. يحدث ذلك بعد تحديث توقف في منتصفه، أو بعد تشغيل إصدار قديم على قاعدة بيانات أحدث.

**الحل.** لا تبدأ إصداراً أقدم على قاعدة بيانات أحدث. افحص الحالة باستخدام `arkvory status --root <root>` وأكمل التحديث أو تراجع عنه باستخدام `recover`. انظر [فشل تحديث](#update-failed). للحفاظ على البيانات، لا تستعد من نسخة احتياطية إلا عندما يتعذر على `recover` الإكمال.

### عملية أخرى تملك التخزين {#storage-identity}

**السبب.** السبب هو `busy: Another writer or maintenance process owns this database` أو `conflict: Database belongs to a different storage directory`. تعمل واجهة API ثانية على قاعدة البيانات نفسها، أو ليس دليل البيانات هو الذي استُخدم مع هذه القاعدة. لكل دليل تخزين ملف `storage-id` تسجّله قاعدة البيانات.

**الحل.** أوقف العملية الأخرى. استخدم دليل البيانات الذي يخص قاعدة البيانات هذه. لا تنسخ `storage-id` إلى دليل آخر أبداً، ولا تربط تثبيتين بقاعدة البيانات نفسها أبداً.

### أذونات الجذر أو دليل البيانات {#root-permissions}

**السبب.** قيمة `errno` هي `EACCES` أو `EPERM`، أو السبب `Cannot read ARKVORY_KEYS_FILE (EACCES)`. لا يستطيع حساب الخدمة قراءة الإعدادات أو الكتابة إلى دليل البيانات. من الأسباب المعتادة التثبيت داخل ملف تعريف مستخدم أو مجلد نُسخ يدوياً أو تغيير المالك.

**الحل.**

- ‏Linux: يملك `root:arkvory` الجذر و`config/` بالوضع 0750. للملفين `config/runtime.json` و`config/keys.json` الوضع 0640. ويملك `arkvory:arkvory` الدليلين `data/` و`logs/`.
- ‏Windows: يجب أن يستطيع الحساب `NT AUTHORITY\LocalService` قراءة كل مجلد أب للجذر وتعديل `data\` و`logs\` وصندوق وارد التحديثات. شغّل برنامج التثبيت الرسومي مجدداً لاستعادة قواعد الوصول.
- ثبّت في مجلد مخصص خارج الأدلة الرئيسية وملفات تعريف المستخدمين.

### يُرفض إعداد أو شهادة {#invalid-configuration}

**السبب.** يسمي السبب متغيراً، مثل `Invalid ARKVORY_PORT`، أو مشكلة شهادة: `TLS certificate has expired` أو `TLS certificate and key do not match` أو `TLS key is not an unencrypted PEM private key`. لا يبدأ الخادم أبداً باستخدام HTTP غير المشفر عندما تكون الشهادة خاطئة.

**الحل.** صحح المتغير المسمى في `config/runtime.json`. توقف قيمة خارج نطاقها بدء التشغيل. جدد ملفات الشهادة أو استبدلها. استخدم `arkvory configure --tls-off` للعودة إلى HTTP غير المشفر أثناء إصلاح الملفات. انظر [متغيرات البيئة](../reference/environment).

## لا تستطيع وحدة التحكم الوصول إلى API {#console-unreachable}

| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |

| [[ui:errorGateway]]         | يستجيب وكيل عكسي، لكن واجهة API خلفه لا تستجيب                                                                                                         | تحقق من عمل واجهة API ومن توجيه الوكيل إلى منفذها. ارفع مهلة قراءة الوكيل لعمليات النقل الكبيرة      |

أثناء التحديث، تعيد وحدة التحكم الاتصال تلقائياً. لا ترسل طلب التثبيت مجدداً. عند استخدام Docker Desktop، يغيب الخادم حتى يعمل Docker Desktop. انظر [Docker](#docker).

## مشكلات تسجيل الدخول {#sign-in}

### اسم أو كلمة مرور خاطئان {#wrong-password}

**السبب.** الرسالة هي [[ui:signInFailed]] ‏(401 `invalid_credentials`). يقدم الخادم الاستجابة نفسها لاسم خاطئ وكلمة مرور خاطئة وحساب معطّل، كي لا يستطيع أحد معرفة الأسماء الموجودة.

**الحل.** يستطيع المسؤول فحص الحساب في [[ui:administration]] واستخدام [[ui:enableUser]] إذا كان معطّلاً، أو [[ui:resetPassword]] لتعيين كلمة مرور جديدة.

### محاولات أكثر من المسموح {#too-many-attempts}

**السبب.** الاستجابة هي 429 `rate_limited` مع `login_attempts` و`Retry-After`. استنفد العنوان محاولاته الـ10، أو دخل الحساب فترة انتظار بعد كلمات مرور خاطئة كثيرة (حتى 2 دقيقة). تنتظر حتى كلمة المرور الصحيحة خلال هذا الوقت.

**الحل.** انتظر عدد الثواني في `Retry-After`. يستطيع المسؤول مسح انتظار الحساب بإعادة تعيين كلمة المرور. تمسح إعادة تشغيل واجهة API عدّادات العناوين، لكنها لا تمسح انتظار الحساب.

### الجميع محجوبون خلف وكيل {#blocked-behind-proxy}

**السبب.** يرى الخادم عنوان الوكيل بوصفه عنوان كل عميل، لذلك يشترك جميع العملاء في ميزانية واحدة.

**الحل.** اضبط `ARKVORY_TRUSTED_PROXIES` على عناوين الوكيل وأعد تشغيل واجهة API. يجب أن يرسل الوكيل `X-Forwarded-For`. انظر [الأمان](./security#sign-in-limits).

### فقدان الوصول إلى حساب المالك {#owner-lost}

**السبب.** لا يتذكر أحد كلمة مرور مسؤول.

**الحل.** استخدم مفتاح الاسترداد على الخادم:

1. اقرأ المفتاح من `config/bootstrap-token.txt` بصلاحيات root أو مسؤول.
2. في وحدة التحكم، افتح [[ui:keySignIn]]، والصق المفتاح، واختر [[ui:connect]].
3. افتح [[ui:administration]]. استخدم [[ui:resetPassword]] للحساب أو [[ui:createUser]] لإنشاء مسؤول جديد.
4. اختر [[ui:disconnect]] وسجّل الدخول بالحساب.

لا يعمل نموذج [[ui:welcomeOwner]] إلا عندما لا توجد أي حسابات على الخادم.

### فقدان مفتاح الاسترداد {#recovery-key-lost}

**السبب.** حُذف الملف `config/bootstrap-token.txt` أو لم يُحفظ. لا يحتفظ الخادم إلا بتجزئة المفتاح.

**الحل.** بصلاحيات root أو مسؤول على الخادم، اكتب مفتاحاً جديداً وتجزئته. انظر [الإعدادات](../install/configuration). لا تحذف الملف مجدداً: تقرؤه أدوات التثبيت.

## عمليات الرفع {#uploads}

### عملية رفع لا تكتمل {#upload-stuck}

**السبب.** توجد عدة أسباب محتملة:

- فقد العميل الاتصال. تحتفظ عملية الرفع متعددة الأجزاء بأجزائها المسجّلة لمدة 7 أيام.
- تنتظر عملية رفع كبيرة العامل. العامل متوقف أو يفشل. وينتظر العامل الثاني في وضع الاستعداد.
- تعمل عمليات رفع كثيرة في الوقت نفسه. افتراضياً تعمل 2، و1 لكل حساب، وتنتظر العمليات الأخرى 20 ثانية ثم تتلقى 503 `busy`.
- يرفض وكيل عكسي جسماً كبيراً (413)، أو يوقف طلباً بطيئاً (502 أو 504).

**الحل.**

1. استعلم عن حالة الرفع: `arkvoryctl uploads status <id>`. استأنف بالملف نفسه وملف الحالة نفسه. انظر [سطر الأوامر](../protocols/cli#resume-interrupted-transfers).
2. افحص العامل: `systemctl status arkvory-worker` و`Get-Service Arkvoryworker`. ابحث عن `completion.failed` و`completion.attempts_exhausted` مع `uploadId`. يعرض المقياس `arkvory_completion_oldest_queued_seconds` مهمة منتظرة.
3. ارفع حدود الوكيل لحجم الجسم ووقت القراءة. يتوقف طلب الرفع بعد 30 ثانية دون بيانات وبعد 30 دقيقة إجمالاً.
4. تزول الجلسة الأقدم من 7 أيام (409 `upload_expired`). ابدأ عملية رفع جديدة.

### integrity_mismatch {#integrity-mismatch}

**السبب.** الاستجابة هي 422 `integrity_mismatch`، أو يخرج العميل بالرمز 5. لا تطابق البايتات الحجم المعلن أو SHA-256. تغيّر الملف أثناء إرساله، أو حُسبت التجزئة المعلنة لملف آخر، أو غيّر وكيل أو جهاز شبكة الجسم.

**الحل.** أرسل الملف مجدداً من نسخة لم تتغير. تبقى الجلسة مفتوحة، فيمكن إرسال ملف مصحح إليها. إذا فشل التحقق من تنزيل مراراً، فنزّله مجدداً عبر مسار آخر ثم أبلغ عن معرّف الطلب. انظر [السجلات والملاحظات](#logs-and-feedback).

## الانشغال وتقييد المعدل وعدم التوافر {#retry-after}

الرموز `busy` و`unavailable` و`rate_limited` مؤقتة. تحمل الاستجابة الترويسة `Retry-After` والحقل `retryAfterSeconds`. انتظر تلك المدة. مع `busy`، يستنتج الخادم الوقت من الطابور السابق وسرعة تحرير المواضع، لذلك يبعد الطابور الطويل العملاء لمدة أطول. تنتظر حزمة SDK وعميل سطر الأوامر حالتي `busy` و`rate_limited` ما دام الخادم يطلب ذلك (ضع حداً باستخدام `--wait-limit` أو `waitLimitMs`)، ويكرران الاستجابات الأخرى عدداً محدوداً من المرات.

| الاستجابة                            | السبب                                                                                                                               | الإجراء                                                                                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| ‏503 `busy`، السبب `request_limit`   | يعالج الخادم `ARKVORY_MAX_REQUESTS` طلباً في الوقت نفسه (128 افتراضياً)                                                               | انتظر. لا ترفع الحد إلا مع ذاكرة كافية. افحص `arkvory_http_requests_in_flight`                                                                     |
| ‏503 `busy`، السبب `download_queued` | ينتظر تنزيل كائن كبير في الطابور؛ يحدد `Arkvory-Queue-Position` و`Arkvory-Starts-At` الموضع ووقت البدء المتوقع                      | لا شيء: تنتظر حزمة SDK و`arkvoryctl` وتتابعان. يكرر العملاء الآخرون بعد `Retry-After` بالمفتاح نفسه ومن العنوان نفسه                               |
| ‏503 `busy`                          | طابور النقل ممتلئ، أو انتظرت عملية نقل أكثر من `ARKVORY_TRANSFER_QUEUE_TIMEOUT_MS` ‏(20 ثانية)، أو يستنزف الخادم الطلبات قبل التوقف | انتظر وكرر. ارفع `ARKVORY_MAX_UPLOADS` أو `ARKVORY_MAX_DOWNLOADS` إذا تكرر ذلك كثيراً. يحصي `arkvory_transfer_admission_failures_total` حالات الرفض |
| ‏503 `unavailable`                   | تعيد قاعدة البيانات التشغيل، أو فقدت العملية ملكية تخزينها، أو يتعذر الوصول إلى المركز (`hub_unreachable`)                          | انتظر. تعيد الخدمات التشغيل تلقائياً. انظر [الإصلاح الذاتي](./self-healing)                                                                         |
| ‏429 `rate_limited`                  | محاولات تسجيل دخول أو تسجيل أو كلمات مرور أو ملاحظات أكثر من المسموح                                                                | انتظر. انظر [محاولات أكثر من المسموح](#too-many-attempts)                                                                                          |

لا تحمل 500 `internal` ترويسة `Retry-After`. لا تكررها عشوائياً. ابحث في السجل عن معرّف طلبها وأبلغ عنها.

## امتلاء القرص وحصة التخزين {#disk-full}

| الاستجابة والسبب     | السبب                                                                                                                       | الحل                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| ‏507 `storage_full`  | تقل المساحة الحرة لوحدة التخزين عن الاحتياطي `ARKVORY_STORAGE_RESERVE_BYTES` ‏(1 GiB افتراضياً)، أو امتلأ قرص قاعدة البيانات | حرر مساحة على الوحدة. افحص `df -h` أو `Get-PSDrive` ووحدة PostgreSQL                |
| ‏507 `storage_quota` | استُنفدت حصة المستودع                                                                                                        | احذف نسخ بناء قديمة أو غيّر سياسة الاحتفاظ أو ارفع الحصة في [[ui:repositoryStorage]] |
| ‏507 `catalog_limit` | سيتجاوز مجموع المحتوى المحجوز كله `ARKVORY_CAPACITY_BYTES` ‏(10 TiB افتراضياً)                                               | احذف محتوى أو ارفع القيمة في `config/runtime.json`                                  |
| ‏507 `queue_full`    | للحساب 100 مهمة إكمال مفتوحة، أو للخادم 10,000                                                                              | انتظر إكمال العامل لها                                                              |

أثناء امتلاء القرص، تستمر التنزيلات ووحدة التحكم في العمل. تعرض `/health/ready` القيمة `"writable": false`. لا يحرر حذف مُخرَج في Arkvory القرص فوراً: ينتظر الملف التنظيف الفعلي بعد فترة سماحه. انظر [التخزين](./storage). لا تخفض الاحتياطي لحشر مزيد من البيانات، لأن قاعدة البيانات والسجلات تحتاج إليه.

## فشل النسخ الاحتياطية {#backups-failing}

ابدأ بالتحذير في [[ui:backups]] أو `arkvoryctl backup status`، وبحدثي السجل `backup.request.failed` و`backup.agent.failed` مع `errorCode`. انظر [النسخ الاحتياطية](./backups).

| التحذير أو الرسالة                                                                       | السبب                                                                                                       | الحل                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `agent_offline`                                                                          | خدمة النسخ الاحتياطي متوقفة أو تفشل في البدء                                                                | ابدأ `arkvory-backup` أو `Arkvorybackup`. اقرأ سجلها                                                                                                                                                                     |
| `vault_unavailable`                                                                      | وحدة المخزن غير مرتبطة، أو لا تحتوي على `vault.json`، أو لا يستطيع حساب الخدمة الكتابة إليها                | اربط الوحدة قبل بدء الخدمة. افحص المالك والأذونات. على Windows، أعد تشغيل الوكيل إذا رُبطت الوحدة لاحقاً                                                                                                                   |
| `The vault directory does not exist; create it or mount its volume first`                | المسار خاطئ أو الوحدة مفقودة                                                                                | أنشئ الدليل أو اربطه                                                                                                                                                                                                     |
| `The vault directory is not writable`                                                    | لا يملك حساب الخدمة وصولاً للكتابة                                                                           | على Linux، اربط المشاركة باستخدام `uid` و`gid` للمستخدم `arkvory`. على Windows، استخدم وحدة محلية أو iSCSI                                                                                                               |
| `The directory has no vault.json: mount the vault volume, or create the vault first ...` | لا يحتوي الدليل على مخزن (وتبدو المشاركة غير المرتبطة بالطريقة نفسها)؛ ولا ينشئ configure مخزناً مشفراً بنفسه | اربط الوحدة الصحيحة أو شغّل `arkvory-backup vault init <dir> --kit-file <file> --agent-key-file <file>`، واحتفظ بالحزمة خارج الخادم، ثم مرر `--vault-key-file`. ينشئ `--init-vault --vault-no-encryption` مخزناً دون تشفير |
| `The vault must be outside the installation root and the storage directory`              | يتداخل المخزن مع البيانات                                                                                   | اختر دليلاً منفصلاً على وحدة أخرى                                                                                                                                                                                          |
| `Network share paths are not supported ...`                                              | مسار UNC على Windows. لا يستطيع `LocalService` تسجيل الدخول إلى مشاركات SMB                                 | استخدم حرف محرك أقراص لوحدة محلية أو iSCSI                                                                                                                                                                               |
| `The backup service cannot reach /home, /root, /run/user, /tmp or /var/tmp`              | تخفي بيئة عزل systemd هذه المجلدات                                                                          | اختر دليلاً آخر                                                                                                                                                                                                           |
| `vault_full` و`vault_low_space`                                                          | وحدة المخزن شبه ممتلئة                                                                                      | حرر مساحة أو احتفظ بنقاط أقل. تبقى النقاط السابقة سليمة                                                                                                                                                                  |
| `vault_key_missing` و`vault_key_invalid`                                                 | المخزن مشفر وليس لدى الوكيل مفتاح، أو لديه مفتاح خاطئ                                                       | شغّل `arkvory configure --backup-vault DIR --vault-key-file FILE` بمفتاح الوكيل. انظر [تشفير المخزن](./backups#encryption)                                                                                                |
| `last_run_failed`                                                                        | فشلت أحدث نسخة احتياطية                                                                                     | اقرأ `errorCode` باستخدام `arkvoryctl backup jobs`                                                                                                                                                                       |
| `verify_failed`                                                                          | فشلت نقطة في فحصها                                                                                          | لا تغيّر المخزن. احتفظ به للتحليل وأبلغ عنه                                                                                                                                                                               |

يستعيد `arkvory configure --backup-vault` الإعدادات القديمة إذا لم يبلغ الوكيل عن المخزن الجديد خلال 150 ثانية. يوقف التحديث وكيل النسخ الاحتياطي، لذلك تُكرر لاحقاً النسخة التي كانت تعمل حينها. عند تمكين التحديثات التلقائية، اجعل وقت النسخ الاحتياطي خارج ساعة التحديث (03:00 UTC افتراضياً).

## مرآة لا تتزامن {#mirror-not-syncing}

افتح [[ui:mirrors]] في وحدة التحكم: تعرض المرآة المتوقفة السبب والخطوة التالية والأمر الذي يصلحها إن وُجد. توجد الحالة نفسها في `GET /api/v1/repositories/{repository}/mirror` وفي أحداث العامل `mirror.step_failed`. تستمر التنزيلات من المحتوى المنسوخ. انظر [المرايا](./mirrors).

| `errorCode`                   | السبب                                                                                  | الحل                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mirror_unreachable`          | لا يستجيب المصدر: رُفض الاتصال، أو انتهت مهلته، أو تعذر تحليل الاسم                     | افحص الشبكة والجدار الناري والمصدر. يعيد العامل المحاولة تلقائياً                                                                                         |
| `unauthorized` أو `forbidden` | يرفض المصدر المفتاح، أو لا يجوز للمفتاح قراءة المستودع                                 | استبدل المفتاح باستخدام `arkvory configure --mirror NAME --mirror-token-file FILE`، أو امنحه وصول قراءة على المصدر. يعيد العامل قراءة المفتاح بعد كل فشل |
| `mirror_failed`               | فشل دون رمز أكثر تحديداً                                                                | اقرأ سجل العامل                                                                                                                                          |
| `mirror_mismatch`             | للمعرّف نفسه محتوى مختلف في المصدر                                                      | يُحتفظ بالنسخة. افحص المُخرَج                                                                                                                               |
| `mirror_source_changed`       | يحتفظ المستودع بالفعل بنسخة من مصدر آخر                                                | افصل باستخدام `--mirror-detach`، وأنشئ مرآة للمصدر الجديد في مستودع جديد                                                                                 |
| `mirror_source_behind`        | استُعيد المصدر أو أُعيد تثبيته                                                           | يُعاد البذر تلقائياً ويختفي الرمز                                                                                                                          |
| `mirror_certificate`          | يستخدم المصدر شهادة شركة أو شهادة موقّعة ذاتياً، أو انتهت صلاحية شهادته أو لا تطابق اسمه | مرر `--mirror-ca-file` إلى `arkvory configure`. لا يُعطل الفحص أبداً                                                                                       |

للرموز الأخرى وما يجب فعله حيالها: [المرايا، رموز الأخطاء](./mirrors#error-codes). يحتاج المصدر إلى إصدار يوفر تدفق المرآة. ينتظر العامل 2 ثانية بعد الفشل، مع المضاعفة حتى 5 دقائق. ينطلق `ArkvoryMirrorStale` بعد ساعة وربع دون اللحاق بالمصدر.

## فشل تحديث {#update-failed}

1. اقرأ الفشل. في وحدة التحكم، يعرض [[ui:updates]] رسالة. يكتب المحدّث `logs\updater.log` على Windows، و`journalctl -u arkvory-update` على Linux.
2. افحص الإصدار المثبّت: `arkvory status --root <root>`.
3. اعثر على حالتك.

| الحالة                                                          | ما حدث                                                                                 | الإجراء                                                                                                                                   |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| مخطط قاعدة البيانات نفسه وفشل عادي                              | بدأ برنامج التثبيت الإصدار السابق مجدداً                                                | أصلح السبب وحدّث مجدداً                                                                                                                     |
| تعرض وحدة التحكم [[ui:updateMaintenance]]                       | يحتاج إصدار يغيّر المخطط إلى نسخة احتياطية متحقق منها، ورفض برنامج التثبيت قبل أي تغيير | اربط مخزناً، وانتظر أول نسخة احتياطية، وافحص مجدداً                                                                                         |
| فشل الترحيل                                                     | تراجعت معاملته، ويعمل الإصدار السابق على المخطط السابق                                 | أصلح السبب وحدّث مجدداً                                                                                                                     |
| لم يبدأ الإصدار الجديد بعد ترحيل ناجح                           | يقول دفتر العمليات `maintenance-required` ويسمي نقطة نسخ احتياطي                       | أصلح السبب وشغّل `recover` الذي يكمل التحديث. أو استعد النقطة مع الإصدار السابق                                                            |
| أُنهي المحدّث قسرياً أو فقد الجهاز الطاقة                          | يبقى القفل `operation.lock` ودفتر العمليات. لا يواصل شيء تلقائياً                       | الإجراء أدناه                                                                                                                             |
| تعرض وحدة التحكم [[ui:updateStale]] أو [[ui:updateUnavailable]] | مجدول المضيف لا يعمل أو غير متصل                                                       | افحص المهمة `ProAnimaArkvoryUpdate` ‏(Windows) أو `arkvory-update.timer` ‏(Linux). اربطه باستخدام `arkvory updates-connect --root <root>` |

بعد انقطاع المحدّث:

1. أوقف المجدول وتأكد من عدم عمل أي محدّث. احفظ `journal.json` والسجلات.
2. بعد ذلك فقط احذف الملف `operation.lock` في جذر التثبيت. لا تحذفه أبداً أثناء عمل تحديث.
3. شغّل `recover`:

   ```bash
   sudo arkvory recover --root /opt/proanima-arkvory
   ```

   ```powershell
   & 'C:\Program Files\ProAnima\Arkvory\arkvory.ps1' recover --root C:\ProgramData\ProAnima\Arkvory
   ```

   قبل بدء الترحيل، يستعيد الإصدار السابق. وبعد بدء الترحيل، يكرر الترحيل ويبدأ الإصدار الجديد.

4. افحص `/health/ready` وطابور الإكمال وتنزيلاً اختبارياً واحداً. ثم أعد تمكين المجدول.

يمسح `arkvory updates-reset --root <root>` طلب تحديث مقبولاً بعد تسوية الحالة. لا يمكن الرجوع إلى إصدار أقدم. انظر [التحديثات](../install/updates).

## Docker {#docker}

- **لا يعمل شيء بعد إعادة تشغيل Windows.** يبدأ Docker Desktop عندما يسجل المستخدم الدخول. فعّل **بدء Docker Desktop عند تسجيل الدخول**، أو استخدم الخدمات الأصلية.
- **لا يعمل شيء بعد إعادة تشغيل مضيف Linux.** تحقق من بدء المحرك عند الإقلاع: `systemctl is-enabled docker`.
- **لا تستطيع حاوية قراءة ملف في `config/`.** تعمل الحاويات بالمستخدم `node` ‏(uid 1000). يجعل برنامج التثبيت `runtime.json` و`keys.json` و`health-token.txt` قابلة للقراءة له. إذا غيّر تحرير يدوي المالك أو الوضع إلى 0600، تتوقف واجهة API بالرسالة `Cannot read ARKVORY_KEYS_FILE (EACCES)`. استعد الوضع 0644 لهذه الملفات الثلاثة. ويظل المجلد `config/` نفسه مغلقاً.
- **المخزن غير قابل للكتابة.** يعمل الوكيل بالمعرّف uid 1000، لذلك يجب أن يملك المخزن. يضبط `arkvory configure --backup-vault` ذلك بالملف `config/compose.vault.yml`. تحتاج المشاركة التي تربطها بنفسك إلى `uid=1000`. أدرج `-f config/compose.vault.yml` في كل أمر Compose يدوي، وإلا ينشئ `up` حاوية النسخ الاحتياطي دون المخزن.
- **حاوية بالحالة `unhealthy`.** يستدعي فحص الصحة `/health/ready` كل 10 ثوانٍ. يعلّم Docker الحاوية لكنه لا يعيد تشغيلها. اقرأ سجل حاوية API.

اعرض سجل حاوية:

```bash
docker logs --tail 100 proanima-arkvory-api-1
```

## خدمة Windows لا تبدأ {#windows-service}

1. اقرأ الحالة وخرج الأخطاء:

   ```powershell
   Get-Service Arkvoryapi, Arkvoryworker, Arkvorybackup, Arkvorydatabase
   Get-Content C:\ProgramData\ProAnima\Arkvory\logs\arkvory-api.err.log -Tail 50
   ```

2. افتح عارض أحداث Windows، **سجلات Windows > النظام**، وابحث عن أحداث مدير التحكم بالخدمات.
3. اعثر على السبب لديك:

| السبب                                                                  | الحل                                                       |
| ---------------------------------------------------------------------- | ---------------------------------------------------------- |
| الجذر داخل ملف تعريف مستخدم، أو لا يستطيع `LocalService` قراءة مجلد أب | ثبّت في مجلد مخصص. انظر [الأذونات](#root-permissions)       |
| المنفذ مشغول                                                           | انظر [المنفذ مشغول](#port-busy)                            |
| خدمة قاعدة البيانات لا تعمل                                            | ابدأ `Arkvorydatabase`. تعيد واجهة API المحاولة كل 10 ثوانٍ |
| بدأت الخدمات «متأخرة» بعد الإقلاع                                      | نوع بدئها تلقائي (بدء متأخر). انتظر بضع دقائق              |
| عزل برنامج مكافحة الفيروسات Node.js                                    | اسمح بالملفات في `runtime\`                                |
| `Another installation owns this service`                               | توجد خدمات تثبيت في جذر آخر. أزلها أولاً                    |
| خدمة تبقى متوقفة                                                       | أوقفتها أنت أو تحديث. ابدأها باستخدام `Start-Service`      |

شغّل برنامج التثبيت الرسومي مجدداً لاستعادة أنواع البدء وإجراءات الاسترداد للخدمات. انظر [Windows](../install/windows).

## السجلات ومعرّفات الطلبات والملاحظات {#logs-and-feedback}

**العثور على السجلات.** ‏Linux: ‏`journalctl -u arkvory-api -u arkvory-worker -u arkvory-backup`. ‏Windows: ‏`logs\` في جذر التثبيت. ‏Compose: ‏`docker logs <container>`. الصيغ والأحداث في [المراقبة](./monitoring#logs).

**العثور على معرّف الطلب.** لكل استجابة الترويسة `X-Request-Id`. ولكل جسم خطأ `requestId`. تعرضه وحدة التحكم بوصفه [[ui:requestIdLabel]] تحت الرسالة، ويطبعه عميل سطر الأوامر في سطر الخطأ. ابحث عن هذه القيمة في سجلات API والعامل لرؤية الطلب والمهام التي بدأها.

**إرسال ملاحظات مع السجلات.**

1. سجّل الدخول واختر [[ui:reportOpen]] في الشريط العلوي.
2. صف المشكلة وأضف معرّف الطلب. يمكنك إضافة حتى 6 لقطات شاشة.
3. إذا كنت مسؤولاً، فعّل [[ui:reportServerLog]]. يرفق ذلك أحدث أسطر سجل API (نحو 1.5 MiB) وملخصاً للنظام دون عناوين وأسرار.
4. اختر [[ui:reportShow]] لترى بدقة ما سيُرسل، ثم [[ui:reportSend]].

يرسل الخادم البلاغ إلى مركز ProAnimaStudio. إذا تعذر الوصول إلى المركز أو كانت الملاحظات معطّلة، تعرض وحدة التحكم العنوان `info@proanima.net` للمراسلة. انظر [الأمان](./security#hub) لمعرفة ما يُرسل.
