# التخزين

يحتفظ Arkvory بكل ملف منشور مرة واحدة دون تغيير، في دليل تخزين على قرص محلي للخادم، واختيارياً على [وحدات تخزين إضافية](#volumes). تشرح هذه الصفحة ما يشغل مساحة القرص، وكيفية تقييده بحصص التخزين وسياسات الاحتفاظ، وكيف تُزال الملفات المحذوفة من القرص، وما يجب فعله عند امتلائه.

## مكان المحتوى {#location}

يُحدد دليل التخزين باستخدام `ARKVORY_DATA_DIR`. تستخدم برامج التثبيت المواقع التالية:

| التثبيت        | التخزين                                              |
| -------------- | ---------------------------------------------------- |
| Windows        | `data\` داخل `C:\ProgramData\ProAnima\Arkvory`       |
| Linux          | `data/` داخل `/opt/proanima-arkvory`                 |
| Docker Compose | وحدة تخزين Docker المسماة `proanima-arkvory_storage` |

داخله، يحتوي `blobs/` على الملفات المكتملة، ويحتوي `staging/` و`parts/` على عمليات الرفع الجارية، ويربط الملف `storage-id` الدليل بقاعدة البيانات. يوجد الفهرس، بجميع الأسماء والتسميات والإصدارات والأذونات، في PostgreSQL. الملفات وقاعدة البيانات مرتبطان ببعضهما.

- استخدم نظام ملفات محلياً يدعم الروابط الصلبة. لا تستخدم مشاركة شبكية للتخزين.
- لا تضف ملفات في الدليل أو تغيّرها أو تحذفها يدوياً. يزيل Arkvory الملفات بنفسه، كما هو موضح أدناه.
- لا يتغير الملف المنشور أبداً. المحتوى الجديد ملف جديد بمعرّف جديد.

## عدة وحدات تخزين {#volumes}

يمكنك تزويد Arkvory بأدلة تخزين إضافية، على قرص ثانٍ مثلاً، بدلاً من توسيع وحدة واحدة. كل دليل إضافي مثيل للوحدة المدمجة `local-storage` وله معرّفه الخاص. يكون دليل تخزين `ARKVORY_DATA_DIR` دائماً هو المثيل `default`.

اضبط المثيلات في ملف الوحدات (`ARKVORY_MODULES_FILE`، انظر [متغيرات البيئة](../reference/environment)):

```json
{
  "format": 1,
  "modules": {
    "local-storage": {
      "enabled": true,
      "config": {
        "instances": {
          "volume-2": { "directory": "/srv/arkvory-volume-2" }
        }
      }
    }
  }
}
```

| الحقل           | المعنى                                                                                                                               | الافتراضي                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------- |
| `directory`     | المسار المطلق للدليل. يجب ألا يحتوي على دليل التخزين أو مثيل آخر، وألا يقع داخل أي منهما                                             | مطلوب                           |
| `acceptsWrites` | توقف القيمة `false` عمليات الرفع الجديدة إلى هذه الوحدة. تبقى ملفاتها قابلة للقراءة، ويمكن إكمال عمليات الرفع التي بدأت عليها بالفعل | `true`                          |
| `mode`          | يقدم `read-only` التنزيلات والفحوص فقط، ويرفض كل كتابة وإزالة، مثلاً لوحدة مرتبطة للقراءة فقط                                         | `full`                          |
| `enabled`       | تغلق القيمة `false` الوحدة: لا يمكن تنزيل ملفاتها حتى تفعّلها مجدداً                                                                   | `true`                          |
| `reserveBytes`  | المساحة الحرة المحفوظة على هذه الوحدة بالبايت                                                                                        | `ARKVORY_STORAGE_RESERVE_BYTES` |

يتكون المعرّف من أحرف لاتينية صغيرة وأرقام و`-`، ويبدأ بحرف، ولا يكون `default`. يمكنك إضافة ما يصل إلى 16 مثيلاً. يجب أن تقرأ كل عملية (واجهة API وبوابات القراءة والعامل ووكيل النسخ الاحتياطي) ملف الوحدات نفسه: فالعملية التي تخطط لمثيلات مختلفة لا تكون جاهزة. أعد تشغيل جميع الخدمات بعد أي تغيير.

لإضافة وحدة تخزين:

1. اربط الوحدة وأنشئ الدليل. يجب أن يملكه الحساب الذي يشغّل الخدمات. لا ينشئ Arkvory هذا الدليل. إذا كان مفقوداً، مثلاً لأن الوحدة غير مرتبطة، تبقى الوحدة غير متاحة ولا يُكتب شيء تحت نقطة الربط.
2. علّم الدليل بوصفه وحدة جديدة: `arkvory volume-init --directory /srv/arkvory-volume-2`. لا يحتاج الأمر إلى `--root`. يرفض دليلاً غير موجود أو غير فارغ (يُسمح بوجود `lost+found` فقط)، ويكتب ملف الهوية `storage-id`. على Linux، يرفض أيضاً الدليل الذي ليس نقطة ربط، مثل الدليل الفارغ لوحدة غير مرتبطة. لدليل داخل وحدة مرتبطة، أضف `--no-expect-mount`. على Windows، يفعّل `--expect-mount` هذا الفحص. لا تنشئ الخدمات الملف أبداً: تبقى الوحدة التي لا تحتوي عليه غير متاحة.
3. أضف المثيل إلى ملف الوحدات وأعد تشغيل الخدمات. عند بدء التشغيل الأول، تسجل واجهة API هوية الوحدة، أي ملف `storage-id` في الدليل. ومنذ ذلك الحين، تفحص كل عملية هذا الملف. لا يُكتب أبداً إلى وحدة غير مرتبطة أو إلى وحدة أخرى في المسار نفسه. وتعيد كل كتابة وإزالة على الوحدة فحص هذا الملف أولاً.
4. حدد عمليات الرفع التي تذهب إلى الوحدة باستخدام [سياسة توزيع التخزين](#placement).

### توزيع عمليات الرفع الجديدة {#placement}

تختار سياسة توزيع التخزين للمستودع مكان تخزين كل عملية رفع جديدة. تحتوي القاعدة على معرّف، ووحدة تخزين (`backendId`)، وشرطين اختياريين: مجموعة حزمة (`models/*` أو `tools` أو `*`) وحد أدنى للحجم بالبايت. تُطبّق أول قاعدة تتحقق شروطها. إذا لم تتطابق قاعدة، تذهب عملية الرفع إلى `default`. يمكن أن يحتوي المستودع على 32 قاعدة كحد أقصى.

اقرأ السياسة وغيّرها باستخدام `arkvoryctl` أو عمليتي API ‏[getStoragePlacement](../api/reference/storage#getStoragePlacement) و[setStoragePlacement](../api/reference/storage#setStoragePlacement):

```bash
arkvoryctl storage placement --repository releases
arkvoryctl storage placement --repository releases --revision 0 --file rules.json
```

يحتوي الملف `rules.json` على قائمة القواعد، مثلاً وضع جميع الملفات بحجم 1 GiB أو أكثر على `volume-2`:

```json
[{ "id": "large", "backendId": "volume-2", "packageGroup": null, "minSizeBytes": "1073741824" }]
```

- تتطلب قراءة السياسة `storage.read`، ويتطلب تغييرها `storage.manage`. تسرد الاستجابة أيضاً كل وحدة تخزين مع حالتها: `accepting` أو `not_accepting` أو `read_only` أو `disabled` أو `unavailable` أو `not_loaded`.
- لا يمكن للقاعدة تسمية سوى وحدة تخزين مضبوطة في الإعدادات. يُرفض أي اسم آخر بالاستجابة 400 `backend_unknown`.
- تُحفظ السياسة برقم مراجعة. إذا غيّرها شخص آخر، فاقرأها مجدداً واحفظها مرة أخرى.
- يسري التغيير على عمليات الرفع الجديدة فقط. تبقى الملفات المخزنة بالفعل في مكانها؛ لنقلها، انظر [نقل الملفات المخزنة إلى وحدة أخرى](#rehome).

### عندما لا تقبل وحدة عمليات رفع جديدة {#placement-fallback}

لا يفشل النشر أبداً بسبب توزيع التخزين. إذا لم تقبل الوحدة المختارة عمليات الرفع في تلك اللحظة، بسبب `acceptsWrites: false` أو `read-only` أو `enabled: false` أو مثيل مفقود أو وحدة غير متاحة (غير مرتبطة، أو فشل فحص الهوية، أو عدم استجابة)، تُنشأ عملية الرفع الجديدة في `default` بدلاً منها. تُظهر عملية الرفع وحدتها في `storageBackend`، ويحصيها المقياس `arkvory_storage_placement_fallback_total`، ويتضمن السجل السطر `storage.placement_fallback`.

- **لا تُنقل عمليات الرفع الجارية.** إذا توقفت وحدة عن قبول البيانات أثناء رفع مجزأ عليها، تُرفض الأجزاء الجديدة بالاستجابة 409 `backend_read_only`، ويبدأ العميل عملية رفع جديدة. إذا كانت جميع الأجزاء موجودة بالفعل، تكتب عملية إكمال الرفع الملف في `default`. تُقرأ الأجزاء من الوحدة التي توجد عليها. ويبقى في مكانه الملف الذي خزّنته محاولة منقطعة كاملاً على الوحدة بالفعل.
- **الوحدة غير المتاحة** تجعل تنزيل ملفاتها يفشل بالاستجابة 503 `unavailable` حتى تعود. يستمر الخادم في العمل، وتتبع الجاهزية و`writable` الوحدة `default` فقط. تعيد كل عملية فحص وحداتها كل 30 ثانية.
- **التنظيف الفعلي** يزيل كل ملف من الوحدة التي تحتوي عليه، بما في ذلك الأجزاء المتبقية على وحدة أخرى. على الوحدة غير المتاحة أو المخصصة للقراءة فقط، يتجاوز التنظيف الملف ويحاول مجدداً لاحقاً.
- **حصص التخزين والحدود.** تحتسب الحصص و`ARKVORY_CAPACITY_BYTES` جميع الوحدات معاً. وينطبق الاحتياطي على كل وحدة.
- **الملفات المؤقتة** لعمليات رفع raw وOCI والمرايا تبقى في دليل التخزين `default`.
- **العنقود.** في [عنقود عالي التوافر](./cluster)، يجب أن تكون كل وحدة دليلاً على وحدة التخزين المنسوخة، مثل دليل التخزين: فلا يُنسخ قرص آخر إلى الخوادم الأخرى. وإلا فلن تبدأ واجهة API.
- **وحدة أُزيلت من الإعدادات.** يتذكر Arkvory كل وحدة احتفظت ببيانات. إذا لم تعد إحداها في ملف الوحدات، فلا يمكن تنزيل ملفاتها أو تنظيفها أو نسخها احتياطياً: تفشل النسخة الاحتياطية بالرمز `blob_missing`. تُبلّغ كل عملية عنها بالمقياس `arkvory_storage_backend_unconfigured`، وسطر السجل `storage.backend_unconfigured`، والتنبيه `ArkvoryStorageVolumeUnconfigured`، وتسردها استجابة التوزيع بالحالة `not_loaded`. أعِد ضبطها في الإعدادات لإصلاح ذلك. لإخراج وحدة من الخدمة، اضبط `acceptsWrites: false`، و[انقل ملفاتها](#rehome) إلى وحدة أخرى، وأبقِها في الإعدادات حتى تنتهي عمليات النقل.

راقب `arkvory_storage_backend_up` و`arkvory_storage_backend_accepting`، وانظر [المراقبة](./monitoring#metrics). تنسخ النسخ الاحتياطية جميع الوحدات. وتتطلب الاستعادة دليلاً فارغاً لكل وحدة، انظر [استعادة عدة وحدات تخزين](./backups#restore-volumes).

### نقل الملفات المخزنة إلى وحدة أخرى {#rehome}

لنقل الملفات المخزنة بالفعل، مثلاً لإخراج وحدة من الخدمة أو لملء وحدة جديدة، خطط لعمليات النقل على الخادم. تواصل الخدمات العمل.

```bash
arkvory storage rehome --root /opt/proanima-arkvory --from volume-2 --to default
arkvory storage moves --root /opt/proanima-arkvory
```

1. يخطط `rehome` لنقل كل ملف منشور من وحدة التخزين `--from`، ويطبع عدد العمليات المخططة وتوزيعها حسب الحالة. يقصرها `--repository <name>` على مستودع واحد، و`--limit <n>` على عدد من الملفات (10 000 افتراضياً، و100 000 كحد أقصى). لا يُخطط مجدداً لملف توجد له عملية نقل جارية بالفعل. يجب ضبط وحدتي التخزين في الإعدادات. يجب أن يقبل الهدف عمليات رفع جديدة، وإلا يفشل الأمر بالرمز `backend_read_only`. يمكن أن يكون المصدر للقراءة فقط.
2. ينفّذ العامل عمليات النقل، اثنتين في الوقت نفسه. لكل ملف، ينسخ البايتات إلى الهدف ويفحص الحجم وSHA-256، ويحوّل الملف إلى الهدف، ثم يزيل النسخة من المصدر. يحتفظ الملف بمعرّفه: وتبقى الروابط والمسارات والمراحل والمراجع صالحة.
3. يطبع `moves` عمليات النقل حسب الحالة: `planned` و`copied` و`switched` و`released` (مكتملة) و`skipped` (حُذف الملف في أثناء ذلك؛ وأُزيلت نسخته من الهدف) و`failed`.

- **التنزيلات والنسخ الاحتياطية.** يواصل التنزيل الذي بدأ قبل التحويل القراءة من المصدر حتى نهايته. لا تُزال نسخة المصدر إلا بعد انتهاء ذلك التنزيل وأي نسخة احتياطية تتضمن الملف. تنتظر الإزالة؛ ولا تعيق التنزيل أبداً.
- **الأعطال.** تُكرر الخطوة الفاشلة بفاصل متزايد. بعد 5 محاولات فاشلة، أو عندما يتوقف الهدف عن قبول الرفع، تصبح حالة النقل `failed` ويبقى الملف في مكانه. شغّل `rehome` مجدداً لتخطيط نقل جديد. يفحص النقل التالي أي نسخة تركها نقل فاشل في الهدف ويعيد استخدامها. يسري ذلك حتى التحويل: بعده لا تصبح حالة النقل `failed` أبداً، وتُعاد محاولة إزالة نسخة المصدر حتى تنجح. ما دامت وحدة غير متاحة أو للقراءة فقط، مثل مصدر يجري إخلاؤه، تنتظرها الخطوة ويُعاد فحصها كل 5 دقائق.
- **السرعة.** يحدد `ARKVORY_REHOME_BYTES_PER_SECOND` سرعة نسخ العامل. لا يوجد حد افتراضياً.
- **حصص التخزين** تحتسب كل ملف مرة واحدة، أثناء النقل وبعده.
- مع Docker Compose، يشغّل الأمر حاوية عامل لمرة واحدة.

يكتب العامل أسطر السجل `storage.move_completed` و`storage.move_skipped` و`storage.move_failed`.

## تخطيط القرص {#disk}

يشغل ما يلي مساحة على وحدة التخزين:

| العنصر                              | ملاحظات                                                                                                          |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| الملفات المنشورة                    | جميع الإصدارات التي تحتفظ بها                                                                                    |
| عمليات الرفع الجارية                | الأجزاء وملفات التجهيز المؤقت، حتى انتهاء الرفع                                                                  |
| ملفات عمليات الرفع المجزأة المكتملة | تبقى الأجزاء المؤقتة إلى جانب الملف المكتمل حتى تزيلها دورة تنظيف فعلي. انظر [التنظيف الفعلي](#physical-cleanup) |
| الملفات المحذوفة                    | تبقى على القرص حتى انتهاء فترة السماح وإزالتها في دورة تنظيف                                                     |
| نسخ المرايا                         | جزء في `mirror-staging` أثناء نسخ المرآة لملف. انظر [المرايا](./mirrors)                                         |

إلى جانب التخزين، خطط لقاعدة بيانات PostgreSQL والسجلات ومخزن النسخ الاحتياطية على وحدات منفصلة متى أمكن. انظر [النسخ الاحتياطية](./backups).

يحتفظ Arkvory **باحتياطي** من المساحة الحرة على وحدة التخزين. قيمته الافتراضية 1 GiB ‏(`ARKVORY_STORAGE_RESERVE_BYTES`). تُرفض عملية الرفع التي ستستهلك الاحتياطي بالاستجابة HTTP 507 والسبب `storage_full`. تستمر التنزيلات في العمل. تعرض `GET /health/ready` القيمة `writable: false` ما دامت لا توجد مساحة لبيانات جديدة.

يُبقي Arkvory أيضاً 100 000 عقدة inode حرة على كل وحدة (`ARKVORY_STORAGE_RESERVE_INODES`): كل ملف مخزن وكل جزء هو ملف، ولذلك قد تنفد عقد inode من الوحدة قبل نفاد البايتات. تُرفض الكتابة التي ستستهلكها بالطريقة نفسها. تُفحص البايتات فقط في أنظمة الملفات التي لا توفر عدداً لعقد inode، مثل NTFS.

يعمل حدّان بصورة مستقلة عن القرص:

- يحدّ `ARKVORY_CAPACITY_BYTES` إجمالي المحتوى المحجوز للتثبيت. الافتراضي 10 TiB. وهو حد منطقي وليس فحصاً للقرص. عند بلوغه، تفشل عمليات الرفع بالاستجابة HTTP 507 والسبب `catalog_limit`.
- يحدّ `ARKVORY_MAX_OBJECT_BYTES` حجم الملف الواحد.

انظر [متغيرات البيئة](../reference/environment#storage-and-limits). لا يوفر Arkvory مقياساً للمساحة الحرة للتخزين أو قاعدة البيانات. راقب الوحدات بأدوات نظام التشغيل لديك أو بمصدّر مقاييس العقدة.

## من يمكنه إدارة التخزين {#permissions}

ليست إعدادات التخزين جزءاً من حقوق القراءة والكتابة العادية. يحتاج مفتاح الخدمة إلى إجراءات صريحة على المستودع:

| الإجراء            | ما يسمح به                                                            |
| ------------------ | --------------------------------------------------------------------- |
| `storage.read`     | عرض السياسة والاستخدام وإعدادات التنظيف وتوزيع التخزين                |
| `storage.manage`   | تغيير السياسة وحصة التخزين وإعدادات التنظيف والتوزيع، وطلب دفعة تنظيف |
| `artifact.delete`  | معاينة الحذف، وحذف المُخرَجات، وتمكين سياسة احتفاظ تلقائية              |
| `diagnostics.read` | قراءة أحداث التخزين                                                   |

لا تمتلك حسابات كلمة المرور ومفتاح الاسترداد هذه الحقوق بذاتها. لإدارة التخزين في وحدة التحكم:

1. أنشئ حساب خدمة بسياسة للمستودع تتضمن الإجراءات الأربعة. انظر [الحسابات والوصول](../use/accounts).
2. أصدر مفتاحاً له وفعّله.
3. في وحدة التحكم، افتح [[ui:keySignIn]]، والصق المفتاح، واختر [[ui:connect]].
4. افتح [[ui:repositories]]، واختر [[ui:repositoryStorage]] على بطاقة المستودع.

تظهر لوحة [[ui:storageTitle]] أعلى الفهرس. ومن دون الحقوق، تبقى اللوحة مخفية.

ترتبط سياسة الاحتفاظ المفعّلة **بالمفتاح الذي فعّلها**. يتحقق كل تشغيل تلقائي مجدداً من أن هذا المفتاح ما زال نشطاً، ولم تنته صلاحيته، وما زال يملك `storage.manage` و`artifact.delete`. إذا أبطلت المفتاح أو قلّصت حقوقه، يتوقف الحذف ويظهر الحدث `retention.failed`. بعد تدوير المفتاح، احفظ السياسة مجدداً بالمفتاح الجديد.

## حصص التخزين وحدود التحذير {#quotas}

يمكن أن تكون للمستودع حصة تخزين. ومن دون حصة، لا يسري إلا الحد العام.

| الإعداد     | حقل وحدة التحكم               | المعنى                                                                                                                          | الافتراضي |
| ----------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------- |
| حصة التخزين | [[ui:storageQuota]]           | أقصى مساحة يجوز للمستودع استخدامها. تقبل واجهة API عدداً دقيقاً من البايتات، من 1 إلى 9 007 199 254 740 991، و`null` لعدم التقييد | بلا حد    |
| حد التحذير  | [[ui:storageWarningPercent]]  | نسبة الحصة التي تثير تحذيراً. 1–98                                                                                               | 80        |
| الحد الحرج  | [[ui:storageCriticalPercent]] | النسبة التي تثير خطأ. 2–99، وأعلى من حد التحذير                                                                                 | 95        |

الاستخدام المحتسب ضمن الحصة هو حجم كل ملفات المستودع التي لم تُزل بعد من القرص: الملفات المنشورة، وعمليات الرفع غير المكتملة، والملفات المحذوفة التي تنتظر التنظيف. لذلك يواصل الملف المحذوف استهلاك الحصة حتى تزيله دورة تنظيف.

- **الفحص.** يفحص الخادم الحصة عند بدء عملية رفع. تفشل عملية الرفع الجديدة التي ستتجاوز الحصة بالاستجابة HTTP 507 والسبب `storage_quota`. لا تحجز إعادة المحاولة بمفتاح منع التكرار نفسه المساحة مرتين.
- **التخفيض.** يمكنك تعيين حصة أقل من الاستخدام الحالي. يمكن إكمال عمليات الرفع الجارية. وتُرفض عمليات الرفع الجديدة التي تتجاوز الحد.
- **لا تحرير تلقائي.** لا تتسبب الحصة في الحذف أبداً. ولا يحذف الاحتفاظ نسخ بناء إضافية للالتزام بحصة.
- **الحالات.** تكون الحالة `unlimited` أو `normal` أو `warning` أو `critical` أو `exceeded`. ويُسجل تغير الحالة مرة واحدة كحدث تخزين.
- **المراقبة.** يعيد الخادم فحص حالات ما يصل إلى 20 مستودعاً كل دقيقة، حتى عندما يكون الحذف التلقائي معطّلاً.

الأرقام حجوزات منطقية وليست مساحة القرص الحرة. قد يكون استخدام المستودع أقل من حصته بينما القرص ممتلئ، لأن القرص يحتوي أيضاً على ملفات التجهيز المؤقت ومستودعات أخرى.

## سياسة الاحتفاظ {#retention}

تحذف سياسة الاحتفاظ **نسخ بناء UPack المسجّلة** القديمة تلقائياً وتحتفظ بآخر N منها. ولا تحذف ملفات أخرى: فالملفات العادية حسب المسار وصور الحاويات وكائنات Git LFS وحزم npm خارج نطاقها. من دون سياسة، لا يُحذف شيء تلقائياً.

### الإعدادات {#retention-settings}

| الإعداد           | حقل وحدة التحكم         | المعنى                                                                                                   | الافتراضي                             |
| ----------------- | ----------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| التمكين           | [[ui:storageEnabled]]   | يفعّل الحذف التلقائي                                                                                      | معطّل                                  |
| التجميع           | [[ui:storageGrouping]]  | الوحدة المحتسبة: [[ui:storagePerChannel]] أو [[ui:storagePerPackage]] أو [[ui:storageGlobal]]            | الحزمة والقناة                        |
| آخر N             | [[ui:storageKeep]]      | عدد نسخ البناء المحتفظ بها لكل عدّاد، 1–100 000                                                           | 10                                    |
| القنوات           | [[ui:storageChannels]]  | قيمة N مستقلة لتسمية، بصيغة `label=N`، واحدة في كل سطر، حتى 32. تُستخدم فقط مع التجميع حسب الحزمة والقناة | `test=10` و`staging=10` و`release=10` |
| الحد الأدنى للعمر | [[ui:storageAge]]       | تُحفظ نسخة البناء الأصغر عمراً من هذه القيمة بالساعات، 0–87 600                                            | 24                                    |
| التسميات المحمية  | [[ui:storageProtected]] | لا تُحذف أبداً نسخ البناء التي تحمل إحدى هذه التسميات، حتى 32 تسمية مفصولة بفواصل                          | `bse` و`release`                      |
| الفاصل            | [[ui:storageInterval]]  | الدقائق بين مرات التشغيل، 1–10 080                                                                       | 60                                    |

تتكون التسمية من 1 إلى 64 حرفاً أو رقماً أو من المحارف `_ . : -`.

### كيفية اختيار نسخ البناء {#retention-rules}

1. يرتب الخادم نسخ البناء في كل عدّاد حسب **وقت النشر**، من الأحدث إلى الأقدم. وليس الترتيب هو ترتيب الإصدارات وفق SemVer.
2. يعتمد العدّاد على التجميع. عند التجميع حسب الحزمة والقناة، تُحتسب نسخة البناء بصورة منفصلة لكل تسمية قناة مضبوطة تحملها، لكل حزمة (`group/name`). وتدخل نسخة البناء التي لا تحمل تسمية مضبوطة في عدّاد مشترك واحد للحزمة بالقيمة الافتراضية N. عند التجميع حسب الحزمة، يكون لكل حزمة عدّاد واحد. وعند التجميع حسب المستودع كله، تشترك جميع نسخ البناء في عدّاد واحد. لا تراعي أسماء الحزم حالة الأحرف، بينما تراعيها التسميات.
3. تبقى نسخة البناء إذا كانت ضمن آخر N في **أي** عدّاد تنتمي إليه.
4. تبقى نسخة البناء التي يقل عمرها عن الحد الأدنى.
5. تبقى نسخة البناء التي تحمل تسمية محمية. تؤخذ تسمياتها من التعليق الوصفي الحالي، أو من عملية الرفع إذا لم يكن لها تعليق. وتظل نسخ البناء المحمية مشاركة في الترتيب، لذلك قد يزيد العدد المحتفظ به على N.

لا تُحذف نسخة بناء أبداً ما دام شيء يحتاج إليها:

- تحتفظ خدمة خارجية بمرجع إليها.
- يستخدمها مسار ملف، حالياً أو من المحفوظات.
- تسردها نسخة بناء أخرى كمرفق، حالياً أو في المحفوظات.
- جرت ترقيتها إلى مرحلة. أزل المرحلة أولاً.
- يستخدمها إدخال لصورة حاوية أو Git LFS أو npm.

حذف نسخة البناء منطقي: تغادر القوائم وتفشل التنزيلات الجديدة بالاستجابة 404. تغادر البايتات القرص لاحقاً، في [التنظيف الفعلي](#physical-cleanup). ويبقى إصدار الحزمة محجوزاً، لذلك لا يمكن نشر الإصدار نفسه مجدداً بمحتوى آخر.

### تمكين سياسة بأمان {#retention-enable}

عاين أولاً ثم فعّل. تعرض المعاينة ما ستحذفه السياسة المحفوظة، ولا تحذف شيئاً.

1. اتصل بمفتاح يملك الإجراءات الأربعة، وافتح لوحة تخزين المستودع.
2. اضبط الحقول واترك [[ui:storageEnabled]] معطّلاً. اختر [[ui:storageSave]].
3. اختر [[ui:storagePreview]]. تعرض القائمة ما يصل إلى 100 نسخة بناء ستحذفها السياسة المحفوظة في دفعة واحدة. وإذا بقيت عناصر مرشحة أخرى، تخبرك وحدة التحكم بذلك.
4. إذا كانت القائمة صحيحة، فحدد [[ui:storageEnabled]] والإقرار [[ui:storageAcknowledge]]، ثم احفظ مجدداً. يتطلب ذلك `artifact.delete`.

ملاحظات:

- تعرض المعاينة لحظة زمنية محددة. عند تشغيل السياسة، تعيد الترتيب وفحص التبعيات.
- تُحفظ السياسة برقم مراجعة. إذا غيّرها شخص آخر، فأعد تحميلها واحفظ مجدداً.
- يعيد [[ui:storageRefresh]] تحميل الإعدادات والاستخدام.

### كيفية التشغيل {#retention-run}

تفحص عملية API التي تكتب (وليست بوابة قراءة) كل 60 ثانية، وتعالج ما يصل إلى 20 سياسة حان موعدها. تحذف الدفعة الواحدة 100 نسخة بناء كحد أقصى. إذا بقيت عناصر مرشحة، تبدأ الدفعة التالية بعد دقيقة. وإلا يحدث التشغيل التالي بعد الفاصل المحدد. يُحفظ الجدول في قاعدة البيانات ويستمر بعد إعادة التشغيل.

يمكنك أيضاً تشغيل دفعة واحدة بنفسك باستخدام عملية API ‏[runStoragePolicy](../api/reference/storage#runStoragePolicy). تتوفر عمليات الاستخدام والمعاينة والأحداث في [مرجع API للتخزين](../api/reference/storage) نفسه.

## التنظيف الفعلي {#physical-cleanup}

لا يؤدي حذف مُخرَج، بواسطة شخص أو سياسة، إلا إلى إزالته من الفهرس. يزيل **التنظيف الفعلي** بايتاته من القرص في الخلفية، دون إيقاف واجهة API أو العامل أو بوابات القراءة. وهو أيضاً:

- يلغي عمليات الرفع التي انتهت مهلتها دون إكمالها، ويزيل أجزاءها.
- يزيل الأجزاء المؤقتة لعمليات الرفع المكتملة.

لا يختار نسخ بناء لحذفها. بل يزيل فقط ما حُذف أو أُلغي بالفعل.

**التنظيف الفعلي معطّل افتراضياً، ويُضبط لكل مستودع.** فعّله في كل مستودع تستخدمه. وحتى ذلك الحين، تبقى الملفات المحذوفة وعمليات الرفع المنتهية وأجزاء عمليات الرفع المكتملة على القرص، وتحتسب الحصة الملفات المحذوفة.

### الإعدادات {#cleanup-settings}

في لوحة المستودع، افتح [[ui:cleanupTitle]]:

| الإعداد     | حقل وحدة التحكم        | المعنى                                | الافتراضي | النطاق   |
| ----------- | ---------------------- | ------------------------------------- | --------- | -------- |
| التمكين     | [[ui:cleanupEnabled]]  | يفعّل التنظيف في الخلفية               | معطّل      |          |
| فترة السماح | [[ui:cleanupGrace]]    | مدة بقاء ملف محذوف على القرص بالساعات | 24        | 0–8760   |
| الدفعة      | [[ui:cleanupBatch]]    | الملفات المعالجة في دفعة واحدة        | 25        | 1–100    |
| الفاصل      | [[ui:cleanupInterval]] | الثواني بين الدفعات                   | 60        | 5–86 400 |
| التأخير     | [[ui:cleanupDelay]]    | مدة التوقف بين الملفات بالمللي ثانية  | 50        | 0–1000   |

اختر [[ui:cleanupSave]] لتطبيقها. يسري التغيير فوراً. إذا عطّلت التنظيف، يتوقف بعد الملف الحالي. يطلب [[ui:cleanupRun]] دفعة قريباً، ولا يحذف فوراً. اختر [[ui:cleanupRefresh]] لرؤية نتيجة آخر دفعة.

فترة السماح ليست سلة محذوفات. مع القيمة 0، يمكن أن يُزال الملف بمجرد حذفه إذا لم يكن مفتوحاً لدى أي قارئ. لا يمكن لـArkvory استعادة مُخرَج محذوف.

### ما ينظفه النظام وما يتجاوزه {#cleanup-rules}

- يزيل فقط الملفات الملغاة أو المحذوفة بعد انقضاء فترة السماح. ويتحقق مجدداً من عدم استخدام أي شيء لها: فلا مرجع ولا محفوظات مسار ملف ولا محفوظات مرفقات.
- تجعل عملية تنزيل مفتوحة، أو عملية رفع تجري كتابتها، أو نسخة احتياطية جارية تحتاج إلى الملف، التنظيف **يتجاوز** ذلك الملف. تحاول الدفعة التالية مجدداً. وتعرض النتيجة الأخيرة عدد الملفات التي عولجت وتُجاوزت وفشلت، وعدد البايتات المحررة.
- لا تُحرر حصة التخزين والسعة المنطقية إلا بعد إزالة الملفات من القرص.
- تُقيّد الدفعة بحجمها وبالتأخير، مما يقلل حمل القرص. ولا تضمن معدلاً صارماً لإنتاجية القرص، ولا يمكنها أن تَعِد بعدم التأثير على زمن استجابة الطلبات الأخرى.
- يجري التنظيف في واجهة API الكاتبة، مرة واحدة لكل قاعدة بيانات. يفحص الكاتب مستودعاً واحداً حان موعده كل 5 ثوانٍ. من دون كاتب يعمل، لا يُنظف شيء.
- لا تفعّل التنظيف إلا بعد تحديث كل عمليات Arkvory، بما فيها البوابات والعامل. تجعل أي عملية قديمة لا تدعم بروتوكول التنظيف النظام يؤجل عمله.

## حذف مُخرَج {#delete-artifacts}

يمكنك حذف مُخرَج منشور واحد يدوياً. تحتاج إلى `artifact.delete` على المستودع.

1. افتح المُخرَج في [[ui:metadata]]، وابحث عن [[ui:deletionTitle]].
2. اختر [[ui:deletionInspect]]. تعرض وحدة التحكم ما لا يزال يستخدم المُخرَج. إذا منع شيء الحذف، فيجب إزالة تلك التبعية أولاً.
3. الصق معرّف المُخرَج لتأكيده، ثم اختر [[ui:deletionSubmit]].

لا يفحص الحذف بهذه الطريقة التسميات المحمية، لأنك تختار الكائن بنفسك. وتُفحص التبعيات دائماً. بعد الحذف:

- يغادر المُخرَج القوائم ونتائج البحث. يفشل أي تنزيل جديد بالاستجابة 404. ويمكن أن يكتمل تنزيل جارٍ بالفعل.
- يبقى إصدار الحزمة محجوزاً.
- تبقى البايتات على القرص حتى يزيلها [التنظيف الفعلي](#physical-cleanup) بعد فترة السماح.
- لا يمكنك التراجع عنه في وحدة التحكم أو واجهة API.

للتعامل مع عدة مُخرَجات، توفر واجهة API العمليتين [previewRetention](../api/reference/storage#previewRetention) و[applyRetention](../api/reference/storage#applyRetention). تسرد المعاينة العناصر المرشحة المنشورة قبل تاريخ معين مع أسباب منع حذفها. ولا يحذف التطبيق إلا المعرّفات التي تمررها، حتى 100 لكل استدعاء، ويعيد نتيجة لكل معرّف: `deleted` أو `already_deleted` أو `protected` أو `changed` أو `not_eligible` أو `not_found`. افحص كل نتيجة، وليس حالة HTTP وحدها.

## تشخيصات التخزين وأحداثه {#diagnostics}

يسرد قسم [[ui:storageEvents]] ما حدث في المستودع، من الأقدم إلى الأحدث، بواقع 100 حدث في الصفحة. اختر [[ui:storageMore]] للصفحة التالية. تتطلب قراءته `diagnostics.read`. عملية API هي [getStorageEvents](../api/reference/storage#getStorageEvents)، مع مرشح حسب المستوى (`info` أو `warning` أو `error`).

| الحدث                                                                                                 | المستوى                 | المعنى                                                                           |
| ----------------------------------------------------------------------------------------------------- | ----------------------- | -------------------------------------------------------------------------------- |
| `storage.policy_updated`                                                                              | معلومات                 | حُفظت سياسة الاحتفاظ                                                              |
| `retention.completed`                                                                                 | معلومات                 | حذفت دفعة نسخ بناء. يتضمن الحدث العدد                                            |
| `retention.failed`                                                                                    | خطأ                     | توقف الحذف التلقائي، مثلاً بسبب إبطال المفتاح الذي يجيزه                          |
| `cleanup.configured`                                                                                  | معلومات                 | حُفظت إعدادات التنظيف                                                             |
| `storage.placement_updated`                                                                           | معلومات                 | حُفظت سياسة توزيع التخزين                                                         |
| `cleanup.completed`                                                                                   | معلومات أو خطأ          | عالجت دفعة تنظيف ملفات أو تجاوزتها أو فشلت فيها. وتسرد الأعداد والبايتات المحررة |
| `capacity.normal` و`capacity.warning` و`capacity.critical` و`capacity.exceeded` و`capacity.unlimited` | معلومات أو تحذير أو خطأ | تغيرت حالة حصة التخزين                                                           |
| رموز أخطاء HTTP                                                                                       | تحذير أو خطأ            | فشل طلب لمفتاح مُدار إلى هذا المستودع. يحتفظ الحدث بمعرّف الطلب والمسار والحالة    |

المحفوظات محدودة: 1000 حدث لكل مستودع و20 000 إجمالاً، وتُسقط الأحداث الأقدم. إنها تشخيصات بأفضل جهد، وليست سجلاً يضمن التسليم. صدّر ما تحتاج إليه في الوقت المناسب، واستخدم سجل الخادم للأدلة طويلة الأجل. انظر [المراقبة](./monitoring).

تعرض اللوحة أيضاً الاستخدام: البايتات المنشورة، وعمليات الرفع غير المكتملة، والبايتات التي تنتظر التنظيف، والإجمالي مقابل الحصة. عملية API هي [getStorageUsage](../api/reference/storage#getStorageUsage).

## عند امتلاء القرص {#disk-full}

العلامات: تفشل عمليات الرفع بالاستجابة HTTP 507 والسبب `storage_full`، أو تعرض `GET /health/ready` القيمة `writable: false`، أو يُبلغ نظام التشغيل بعدم وجود مساحة حرة. تستمر التنزيلات في العمل. ويمكن للعملاء استئناف الرفع بعد تحرير المساحة.

1. **اعثر على السبب.** افحص المساحة الحرة لوحدة التخزين ووحدة قاعدة البيانات ووحدة مخزن النسخ الاحتياطية. قارن أرقام الاستخدام في لوحة التخزين. تعني الأرقام الكبيرة للبيانات «بانتظار التنظيف» أن بيانات محذوفة ما زالت على القرص. ويعني الرقم الكبير «لعمليات الرفع غير المكتملة» وجود عمليات رفع متروكة.
2. **شغّل التنظيف.** إذا كان معطّلاً، ففعّله في كل مستودع بفترة سماح قصيرة، مثل 0 إذا كنت تقبل إزالة الملفات المحذوفة فوراً. اختر [[ui:cleanupRun]]. ويزيل التنظيف أيضاً الأجزاء المؤقتة لعمليات الرفع المكتملة وعمليات الرفع المنتهية. انتظر الدفعات واقرأ النتيجة الأخيرة. يتجاوز التنظيف الملفات المستخدمة، لذا كرره.
3. **احذف ما لا تحتاج إليه.** طبّق سياسة احتفاظ أو احذف مُخرَجات. لا يحرر ذلك المساحة إلا بعد إزالة البايتات بالتنظيف.
4. **أضف مساحة.** وسّع الوحدة أو القرص. انقل المخزن أو البيانات الأخرى خارج الوحدة إذا كانت تشترك فيها. يمكنك أيضاً [إضافة وحدة تخزين](#volumes) وتوجيه عمليات الرفع الجديدة إليها.
5. **تحقق من التعافي.** بعد توفر مساحة حرة، تعود `writable` إلى `true` وتعمل عمليات الرفع مجدداً.

لا تحذف الملفات في `blobs/` أو `staging/` أو `parts/` يدوياً: فهذا يقطع الرابط بين قاعدة البيانات والقرص. إذا كان الاحتياطي صغيراً جداً لسجلاتك وقاعدة بياناتك على الوحدة نفسها، فارفع `ARKVORY_STORAGE_RESERVE_BYTES`.

إذا فشلت عملية رفع بالسبب `storage_quota` أو `catalog_limit` بدلاً من ذلك، فليست المشكلة في القرص. ارفع الحصة أو الحد العام، أو احذف بيانات.

## الحدود {#limits}

- تتعامل سياسة الاحتفاظ مع نسخ بناء UPack المسجّلة فقط. ولا تزيل ملفات أخرى أبداً.
- ترتيب الاحتفاظ حسب وقت النشر، وليس رقم الإصدار.
- يتطلب التخزين والحصص والتنظيف إجراءات صريحة لمفتاح الخدمة. لا تملكها حسابات كلمة المرور ومفتاح الاسترداد.
- التنظيف الفعلي معطّل افتراضياً ويُضبط لكل مستودع.
- لا يمكن استعادة مُخرَج محذوف. استعد البيانات من نسخة احتياطية. انظر [النسخ الاحتياطية](./backups).
- لا تشغّل المستودعات المرآتية سياسة تخزين. انظر [المرايا](./mirrors).
- يجب أن يكون التخزين على نظام ملفات محلي. لا يوجد دعم للمشاركات الشبكية. و[وحدات التخزين](#volumes) الإضافية أدلة محلية أيضاً. لا تُنقل الملفات المخزنة بينها إلا بالأمر على الخادم، [`arkvory storage rehome`](#rehome)، وليس عبر واجهة API.
- على Windows، يزامن Arkvory كل ملف إلى القرص، لكنه لا يستطيع مزامنة إدخال الدليل الذي ينشره: لا يوفر Node.js مزامنة الأدلة هناك. قد يؤدي انقطاع الطاقة بعد الرفع بوقت قصير إلى فقدان ملف منشور من القرص. استخدم مزود طاقة غير منقطع UPS واحتفظ [بنسخ احتياطية](./backups) أو [مرآة](./mirrors). على Linux، تُزامن إدخالات الأدلة أيضاً.

تبقى وحدات التخزين الموقّعة متاحة لفحص `scrub` دون اتصال في وضع القراءة فقط. أبقِ الوحدات المثبّتة وإعداداتها في مكانها. يستطيع `storage rehome` التخطيط لنقل الملفات من تخزين وحدة مضبوطة في الإعدادات إلى التخزين العادي؛ ويفحص العامل الهدف قبل النسخ. يجب أن تطابق خطة الوحدات المثبّتة خطة الكاتب. أوقف واجهة API والعامل قبل `scrub`.

أثناء استرداد الوحدة، قد تبقى البيانات الموجودة قابلة للقراءة بينما تكون الكتابة غير متاحة. يعيد الاستخدام المجهول `busy`؛ ولا يُعامل أبداً بوصفه حصة حرة. انتظر اكتمال الاسترداد قبل بدء عمليات تكتب البيانات أو تزيلها. يتطلب فشل الاسترداد التحقيق، وليس زيادة مهلة بدء الوحدة.
