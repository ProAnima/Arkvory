# الإصلاح الذاتي

يعيد Arkvory تشغيل الخدمة المتعطلة تلقائياً ويستأنف العمل المنقطع دون مشغّل. تسرد هذه الصفحة ما يُعاد تشغيله، ومدة كل عملية تعافٍ، والمشكلات التي لا تزال تحتاج إلى تدخلك. الخادم الواحد ليس نظاماً عالي التوافر: تقطع إعادة التشغيل الاتصالات لفترة قصيرة، ويستأنف العملاء عمليات النقل.

## ما يُعاد تشغيله تلقائياً {#overview}

تعمل كل خدمة تحت إدارة مدير الخدمات للمنصة. تنهي واجهة API والعامل ووكيل النسخ الاحتياطي عملياتها الخاصة عندما يتعذر الاستمرار بأمان. ثم يبدأ مدير الخدمات عملية جديدة.

| الحالة                                   | Linux ‏(systemd)                       | خدمات Windows                                            | Docker Compose                                            |
| ---------------------------------------- | -------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| انهيار أو إنهاء قسري أو نفاد الذاكرة     | إعادة تشغيل بعد 10 ثوانٍ                | إعادة تشغيل بعد 10 ثوانٍ                                  | يعيد المحرك تشغيل الحاوية بفاصل متزايد                    |
| خروج دون طلب إيقاف، حتى برمز الخروج 0    | إعادة تشغيل                            | يحوّل المشغّل الخروج إلى الرمز 1، وإعادة تشغيل بعد 10 ثوانٍ | إعادة تشغيل                                               |
| فقدان ملكية التخزين أو الإيجار           | خروج بالرمز 1 وإعادة تشغيل             | خروج بالرمز 1 وإعادة تشغيل                               | خروج بالرمز 1 وإعادة تشغيل                                |
| توقف الخيط الرئيسي عن الاستجابة          | ينهي المراقب العملية، ثم تُعاد تشغيلها  | الأمر نفسه                                               | الأمر نفسه                                                |
| تعذر الوصول إلى قاعدة البيانات عند البدء | خروج بالرمز 1 وإعادة محاولة كل 10 ثوانٍ | خروج بالرمز 1 وإعادة محاولة كل 10 ثوانٍ                   | خروج بالرمز 1 وإعادة محاولة بفاصل متزايد                  |
| إعادة تشغيل الجهاز                       | الخدمات مفعّلة في `multi-user.target`   | تلقائي (بدء متأخر)                                       | مع محرك الحاويات. Docker Desktop: بعد تسجيل دخول المستخدم |
| إيقاف الخدمة بنفسك                       | تبقى متوقفة حتى الإقلاع التالي         | تبقى متوقفة حتى الإقلاع التالي                           | يبقيها `docker compose stop` متوقفة                       |

لا تؤدي نتيجة فاشلة لفحص الجاهزية وحدها إلى إعادة تشغيل الخدمة. قد يفشل لأن العملية تستنزف الطلبات قبل التوقف، أو لأن مجلداً في دليل التخزين مفقود. لن تصلح إعادة التشغيل هذه الأسباب.

## خدمات Windows {#windows}

يسجل برنامج التثبيت الرسومي و`install.ps1` الخدمات `Arkvoryapi` و`Arkvoryworker` و`Arkvorybackup`، التي تشترك في الحساب `NT AUTHORITY\LocalService`، وخدمة قاعدة البيانات `Arkvorydatabase` لقاعدة البيانات المُدارة. انظر [Windows](../install/windows#services).

- **نوع البدء.** تستخدم واجهة API والعامل ووكيل النسخ الاحتياطي البدء التلقائي المتأخر. وتستخدم قاعدة البيانات البدء التلقائي. يعني البدء المتأخر أن الخدمات تبدأ بعد الإقلاع بفترة، وليس في اللحظة نفسها.
- **إجراءات الاسترداد.** بعد الفشل، يعيد Windows تشغيل الخدمة بعد 10 ثوانٍ. ويتكرر الإجراء نفسه لكل فشل لاحق. يُصفّر عدّاد الفشل بعد ساعة واحدة. وتنطبق إجراءات الاسترداد أيضاً عندما تخرج العملية برمز خطأ.
- **مهلة الإيقاف.** 120 ثانية لإتاحة إكمال طلب جارٍ.
- **السجلات.** يذهب خرج كل خدمة إلى `logs\`، ويُدوّر عند 20 MiB مع الاحتفاظ بـ5 ملفات قديمة.

اعرض إجراءات الاسترداد لخدمة:

```powershell
sc.exe qfailure Arkvoryapi
```

يعيد تشغيل برنامج التثبيت الرسومي مجدداً ضبط أنواع البدء وإجراءات الاسترداد. وتبقى الخدمة التي أوقفتها بنفسك متوقفة.

## وحدات systemd على Linux {#linux}

تنشئ الحزم و`install.sh` الخدمات `arkvory-api` و`arkvory-worker` و`arkvory-backup`، وكذلك `arkvory-database` عندما تكون قاعدة البيانات مُدارة.

- تعيد `Restart=always` مع `RestartSec=10` تشغيل واجهة API والعامل ووكيل النسخ الاحتياطي بعد كل خروج لم تطلبه، بما في ذلك رمز الخروج 0.
- تزيل `StartLimitIntervalSec=0` الحد الأقصى لمحاولات إعادة التشغيل، فلا يتخلى systemd أبداً عن خدمة تفشل. يؤدي عطل دائم، مثل إعداد خاطئ، إلى إعادة التشغيل كل 10 ثوانٍ حتى تصلحه.
- تستخدم وحدة قاعدة البيانات `Restart=on-failure` مع مدة الـ10 ثوانٍ نفسها.
- تمنح `TimeoutStopSec=120` الخدمة التي تتوقف دقيقتين.
- الوحدات مفعّلة للهدف `multi-user.target`.

```bash
systemctl is-enabled arkvory-api arkvory-worker arkvory-backup
systemctl status arkvory-api arkvory-worker arkvory-backup
```

لا يُدعم للخدمات الأصلية إلا systemd. على نظام يستخدم نظام تهيئة آخر، استخدم Docker Compose.

## Docker Compose {#compose}

تستخدم جميع خدمات المشروع `proanima-arkvory` الإعداد `restart: unless-stopped`. ولا تُعاد خطوتا `initialize` و`migrate` اللتان تُنفّذان مرة واحدة.

- تحتوي حاوية API على فحص صحة: تستعلم عن `/health/ready` بمفتاح الصحة كل 10 ثوانٍ، مع فترة بدء 20 ثانية. تُعلّم الحاوية غير السليمة، لكن Docker لا يعيد تشغيلها. ينتظر العامل واجهة API سليمة عند البدء.
- تحصل الحاويات على 120 ثانية للتوقف.
- يجب أن يبدأ محرك الحاويات عند الإقلاع. على Linux، افحص `systemctl is-enabled docker`. لا يغيّر Arkvory إعداد المحرك.
- Docker Desktop على Windows تطبيق لمستخدم واحد. لا تعمل أي حاوية قبل تسجيل دخول المستخدم وبدء Docker Desktop. فعّل خيار **بدء Docker Desktop عند تسجيل الدخول**. يحذّر برنامج التثبيت و`arkvory status` عند تعطيله. لخادم يجب أن يبدأ دون تسجيل دخول، استخدم خدمات Windows الأصلية.

## إعادة التشغيل بعد توقف عن الاستجابة {#hang}

قد تتوقف العملية عن العمل دون أن تنتهي: حلقة لا نهائية، أو استدعاء يحجب التنفيذ، أو توقف في التعليمات البرمجية الأصلية. لا يرى مدير الخدمات ذلك، لأن العملية ما زالت موجودة. لذلك تحتوي كل من واجهة API والعامل ووكيل النسخ الاحتياطي على مراقب للاستجابة.

1. يزيد الخيط الرئيسي عدّاداً مرة كل ثانية.
2. يفحص خيط ثانٍ العدّاد مرة كل ثانية.
3. عندما لا يتحرك العدّاد خلال عدد متتالٍ من الفحوص يساوي `ARKVORY_WATCHDOG_SECONDS` (60 افتراضياً)، يكتب المراقب السجل `process.stalled` مع الحقل `stalledSeconds` إلى خرج الخطأ القياسي وينهي العملية.
4. يعيد مدير الخدمات تشغيل العملية كما بعد الانهيار.

يعد المراقب نبضاته الخاصة، وليس وقت الساعة. عندما يدخل المضيف في السكون أو يُوقف جهاز افتراضي مؤقتاً، يتوقف الخيطان، ولا يُفترض وجود توقف عن الاستجابة بعد الاستيقاظ. لذلك قد يستغرق التعافي من التوقف حتى 60 ثانية، إضافة إلى 10 ثوانٍ لإعادة التشغيل.

يقبل `ARKVORY_WATCHDOG_SECONDS` من 10 إلى 3600. تعطل القيمة `0` المراقب. استخدمها فقط عندما يوقف مصحح الأخطاء العملية مؤقتاً، لأن العملية الموقوفة لأكثر من الحد ستُعاد تشغيلها. تُحتسب العملية الطويلة التي تحجب التنفيذ توقفاً عن الاستجابة أيضاً. إذا تعذر بدء المراقب نفسه، تكتب الخدمة `process.watchdog_failed` وتواصل العمل دونه. ليس لدى PostgreSQL المُدار مراقب استجابة. يعيد مدير خدماته تشغيله بعد الانهيار. انظر [متغيرات البيئة](../reference/environment#watchdog).

## فقدان جلسة قاعدة البيانات أو ملكية التخزين {#ownership}

تثبت واجهة API عبر جلسة قاعدة بيانات أنها الكاتب الوحيد لدليل التخزين. تُفحص الجلسة كل 2 ثانية، ويُعد الفحص الذي لا يجيب خلال 8 ثوانٍ فقداناً لها. يثبت العامل دوره بالطريقة نفسها. لا تُستعاد الملكية أبداً داخل عملية جارية، لأن عملية ثانية قد تكون تولّت الدور.

عند فقدان الملكية، بعد إعادة تشغيل PostgreSQL مثلاً، فإن العملية:

1. تكتب `api.ownership_lost` أو `worker.ownership_lost`،
2. تتوقف عن قبول العمل وتلغي عمليات النقل،
3. تخرج بالرمز 1.

يبدأ مدير الخدمات عملية جديدة تفحص كل شيء من البداية. أثناء توقف قاعدة البيانات، لا تستطيع العملية الجديدة البدء، وتخرج واجهة API وتُعاد تشغيلها كل 10 ثوانٍ حتى يستجيب PostgreSQL. هذا متوقع. يتلقى العملاء في الأثناء 503 `unavailable` مع `Retry-After`. لا يخرج وكيل النسخ الاحتياطي الجاري عند غياب قاعدة البيانات. بل يسجل الخطأ ويحاول مجدداً بعد فاصل الاستقصاء (15 ثانية افتراضياً).

## ما يحدث للعمل الجاري {#work}

يقطع الانهيار الاتصالات المفتوحة. وتبقى البيانات التي أُكدت. يعتمد ما يحدث بعد ذلك على نوع العمل.

| العمل                     | بعد إعادة التشغيل                                                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| التنزيل                   | يستأنف العميل بطلب نطاق. تفعل حزمة SDK وعميل سطر الأوامر ذلك تلقائياً                                                                        |
| الرفع متعدد الأجزاء       | تبقى الأجزاء المسجّلة على الخادم. يستعلم العميل عن الأجزاء الموجودة ويرسل المفقود منها. تبقى الجلسة مفتوحة لمدة 7 أيام من إنشائها            |
| رفع ملف كامل بطلب واحد    | يعيد العميل إرسال الملف من البايت الأول                                                                                                     |
| إكمال الرفع بواسطة العامل | انظر أدناه                                                                                                                                  |
| النسخ الاحتياطي           | انظر أدناه                                                                                                                                  |
| مزامنة المرآة             | يحفظ العامل موضعه بعد كل تغيير مطبّق، وينسخ الملف بدءاً من أول جزء مفقود. بعد الفشل ينتظر 2 ثانية، مع مضاعفة الفاصل بين المحاولات حتى 5 دقائق |
| التحديث                   | يحتفظ برنامج التثبيت بقفله ودفتر عملياته. ولا يواصل تلقائياً. انظر [استكشاف الأخطاء وإصلاحها](./troubleshooting#update-failed)               |

تعيد حزمة SDK وعميل سطر الأوامر المحاولة عدداً محدوداً من المرات عند أعطال الشبكة والاستجابات 408 و429 و502 و503 و504. يحتاج العملاء الآخرون إلى آلية إعادة محاولة خاصة بهم. انظر [عمليات النقل](../use/transfers).

**مهام الإكمال.** يُكمل العامل عملية الرفع الكبيرة (تستخدم حزمة SDK وعميل سطر الأوامر ذلك بدءاً من 16 GiB). يحتفظ العامل بإيجار مدته 30 ثانية على المهمة ويجدده كل 2 ثانية. عندما ينهار العامل، ينتهي الإيجار خلال 30 ثانية، ويأخذ العامل الذي أُعيد تشغيله المهمة مجدداً. تُشغّل المهمة 5 مرات كحد أقصى. بعد الفشل تنتظر 2 ثانية، مع مضاعفة المدة حتى 60 ثانية. تنهي هذه الأخطاء المهمة فوراً: `forbidden` و`invalid_input` و`integrity_mismatch` و`not_found`. تحصل المهمة التي استنفدت كل المحاولات على السجل `completion.attempts_exhausted`. يؤدي طلب إكمال عملية الرفع نفسها مجدداً إلى وضع المهمة في الطابور مرة أخرى. يفحص الإكمال البايتات المخزنة، لذلك يمكن تكراره بأمان.

ينتظر عامل ثانٍ على قاعدة البيانات نفسها في وضع الاستعداد (`worker.standby`)، ويفحص كل 5 ثوانٍ ما إذا كان العامل الأول قد غاب.

**وكيل النسخ الاحتياطي.** يحتفظ الوكيل بإيجار مدته 60 ثانية (`ARKVORY_BACKUP_LEASE_SECONDS`) ويجدده كل 20 ثانية. بعد الانهيار، يأخذ وكيل آخر أو الوكيل المعاد تشغيله الإيجار عند انتهائه، لذلك ينتظر النسخ الاحتياطي حتى دقيقة. تُشغّل المهمة المنقطعة مجدداً بالمفتاح نفسه، حتى 5 مرات. وتحرر عملية التقاط نسخة جديدة أقفال العملية المتوقفة. يظهر التحذير `agent_offline` بعد 2 دقيقة دون نبضة حياة. أثناء التحديث، يوقف برنامج التثبيت الوكيل أولاً، وتنتهي النسخة الاحتياطية الجارية بالحالة `interrupted` وتُعاد إلى الطابور.

**حدود المعدل.** توجد عدّادات تسجيل الدخول لكل عنوان داخل العملية وتُصفّر عند إعادة التشغيل. أما التأخير المتزايد للحساب ففي قاعدة البيانات ويظل محفوظاً.

## الفحوص عند بدء التشغيل {#startup-checks}

تفحص كل عملية بيئتها قبل تقديم الخدمة. ينهي الفحص الفاشل العملية برمز الخروج 1 وبسطر واحد `startup.failed` (واجهة API) أو `worker.unavailable` (العامل). يحدد `reason` السبب دون أسرار.

| العملية              | ما يُفحص                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| واجهة API            | لكل إعداد قيمة صالحة؛ تسمي الرسالة المتغير ولا تعرض قيمته أبداً. يُقرأ ملف المفاتيح بصيغة JSON حتى 1 MiB. في TLS المدمج: يمكن قراءة الشهادة والمفتاح، وهما متطابقان ولم تنته صلاحيتهما؛ ولا يوجد رجوع إلى HTTP. دليل التخزين قابل للكتابة. تستجيب قاعدة البيانات وتتضمن كل ترحيلات هذا الإصدار ولا تتضمن أي ترحيل من إصدار أحدث. يطابق الملف `storage-id` في دليل التخزين الهوية المحفوظة في قاعدة البيانات. لا يحتفظ أي كاتب آخر بقفل قاعدة البيانات |
| العامل               | الإعدادات نفسها وقاعدة البيانات وهوية التخزين وقفل العامل الوحيد. ينتظر عامل ثانٍ في وضع الاستعداد                                                                                                                                                                                                                                                                                                                                                   |
| وكيل النسخ الاحتياطي | هوية التخزين ورقم المخطط وعدم تداخل مخزن النسخ الاحتياطية مع دليل التخزين. المخزن المفقود أو غير المرتبط ليس خطأً قاتلاً. يُبلغ الوكيل عنه بتحذير                                                                                                                                                                                                                                                                                                      |

بعد التحديث، ينتظر برنامج التثبيت ثلاث استجابات جاهزية ناجحة متتالية وعاملاً يعمل. ثم ينتظر نحو 90 ثانية لنبضة حياة وكيل النسخ الاحتياطي. غياب الوكيل مجرد تحذير ولا يؤدي أبداً إلى التراجع عن تحديث.

## ما لا يزال يحتاج إلى تدخلك {#operator}

يغطي الإصلاح الذاتي أعطال العملية. وتحتاج الحالات التالية إلى مشغّل:

- **عطل دائم.** يجعل إعداد خاطئ أو قاعدة بيانات لا يمكن الوصول إليها أو قرص ممتلئ أو أذونات خاطئة الخدمة تعيد التشغيل كل 10 ثوانٍ دون نجاح. اقرأ `startup.failed` وأصلح السبب. انظر [استكشاف الأخطاء وإصلاحها](./troubleshooting).
- **تحديث فاشل.** يحتفظ التحديث المنقطع بقفله ودفتر عملياته حتى تشغّل `recover`.
- **نسخ احتياطية تالفة.** يحتاج `verify_failed` و`vault_unavailable` إلى شخص. يبقي الوكيل المخزن دون تغيير.
- **الشهادات.** يقرأ Arkvory ملفات الشهادات المجددة دون إعادة تشغيل (كل 300 ثانية افتراضياً)، لكن يجب أن تجددها أدواتك.
- **خدمة متوقفة.** تبقى الخدمة التي أوقفتها متوقفة.
- **المنصة.** يجب أن يبدأ Docker عند الإقلاع. تحدّث أنت إصدارات PostgreSQL الرئيسية وNode.js ونظام التشغيل.
- **فقدان خادم أو قرص.** لا يوفّر التثبيت المستقل تجاوزًا للفشل؛ استعد من نسخة احتياطية. يمكن لعنقود عالي التوافر الانتقال إلى خادم بيانات آخر وفق قواعد النسخ المتماثل والعزل. انظر [النسخ الاحتياطية](./backups) و[العنقود عالي التوافر](./cluster).
