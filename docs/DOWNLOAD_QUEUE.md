# Управляемые скачивания

Реализовано 2026-09-24. Клиентская очередь в portable SDK и web-консоли дополняет серверные admission/bandwidth механизмы. Legacy HTTP не меняется; миграция БД не требуется. Решение: [ADR 0022](adr/0022-client-download-queue.md).

## Что может пользователь

Экран «Скачивания / Downloads» показывает реальные задания текущей вкладки: ожидание, скачивание, задержку перед сетевым повтором, сохранение частичной копии, паузу, финальное сохранение, отмену, успех или ошибку. Счётчик байтов отражает записи во временную копию, а не подтверждение готовности итогового файла.

- «Пауза» прерывает fetch/ожидание retry, закрывает временную запись и сохраняет завершённые блоки. Слот освобождается после окончания этих операций.
- «Продолжить / повторить» перечитывает и хеширует сохранённый префикс, затем скачивает суффикс через Range/If-Range. Задание становится в конец очереди. Ошибка не создаёт бесконечных автоматических перезапусков.
- «Отменить» останавливает выбранное задание и удаляет его временную копию. Готовый пользовательский файл не удаляется. Ошибка очистки видна, отменённое задание больше не возобновляется; очистку можно повторить.
- «Отменить ожидающие» обрабатывает снимок queued/paused заданий; активные скачивания продолжаются. «Отменить все» включает активные сетевые передачи. Операции удаления завершённых записей освобождают место в истории очереди.
- Финальное сохранение начинается только после проверки SHA-256 и закрытия временной записи. В этой фазе пауза/отмена недоступны; закрытие очереди ждёт результат commit. Это не обещание пережить принудительное завершение браузера.
- Выход, смена токена или пользовательской сессии отменяют старые задания. Каждый job использует зафиксированные credentials в памяти, а не случайно подхватывает новый токен из формы. Смена темы, языка или просматриваемого репозитория не меняет скачиваемый объект.

## Параллелизм и задержки

| Параметр SDK    | По умолчанию | Диапазон и смысл                               |
| --------------- | ------------ | ---------------------------------------------- |
| concurrency     | 2            | 1–8 заданий, включая retries, запись и commit  |
| maxEntries      | 64           | 1–256 записей, включая историю, ошибки и паузы |
| startIntervalMs | 250          | 0–60 000 мс между запусками заданий            |
| queueTimeoutMs  | 300 000      | 1–1 800 000 мс ожидания queued задания         |

В UI настраиваются concurrency, startIntervalMs и queueTimeoutMs (последний в секундах, 1–1800). Снижение concurrency не обрывает активные задания, но задерживает запуск следующих. Paused задания не истекают; явное продолжение задаёт новое окно ожидания. Переполнение очереди отклоняется до начала передачи. Историю нужно очищать; отмена сама по себе сохраняет строку результата.

Это три разных уровня задержек: интервал запуска файлов; ограниченный backoff/Retry-After отдельных HTTP-запросов; серверное ожидание допуска и доступной полосы. Клиентская настройка не может увеличить серверную квоту. Retry policy по-прежнему передаётся в DepotClient; её границы и timeout каждого Range описаны в [TRANSFER_RECOVERY](TRANSFER_RECOVERY.md).

## Временное хранилище браузера

BrowserDownloadStorage пишет в приватное OPFS-хранилище origin. Выбранный пользователем файл назначения открывается для записи только после проверки исходного потока. Частичный файл не сохраняется под видом готового результата. После успешного commit временная копия удаляется; ошибка удаления не превращает успешно сохранённый файл в неудачное скачивание и показывается отдельно.

Снимок prefix полностью хешируется до открытия нового writer: изменение файла может инвалидировать ранее полученный File. На паузе сохраняются только завершённые записи; ошибка записи откатывает текущий writer к предыдущему закрытому checkpoint. При ошибке целостности временная копия удаляется, и следующий явный повтор начинает скачивание заново. В памяти не накапливается целый файл: сетевой блок ограничен 8 MiB, обработка prefix — 1 MiB, конечная копия потоковая.

Нужны Chromium/Edge с File System Access, OPFS и Web Locks и разрешение на выбранный файл. Квота OPFS и свободное место устройства должны вмещать временные данные; commit дополнительно создаёт запись назначения. Размер 5 GiB на сервере не гарантирует наличие такой браузерной квоты. Токены и журнал заданий в OPFS/localStorage не записываются.

Очередь живёт в памяти вкладки. Закрытие/reload теряет задания; автоматическое восстановление очереди после перезапуска браузера в этот инкремент не входит. Beforeunload предупреждает о незавершённой работе, но не является гарантией сохранения процесса. Временные каталоги принадлежат отдельным случайным session IDs; живые вкладки удерживают Web Lock. При следующем создании workspace очищаются только оставленные сессии, для которых удалось получить lock. Данные работающей соседней вкладки и пользовательские файлы не затрагиваются.

## SDK и адаптеры

```typescript
import { DownloadQueue, checkpointedDownload } from '@proanima/depot-sdk';

const queue = new DownloadQueue({ concurrency: 2, startIntervalMs: 250 });
queue.enqueue(checkpointedDownload(client, jobId, repository, artifactId, storage));
const unsubscribe = queue.subscribe(() => render(queue.snapshot));
queue.pause(jobId);
queue.resume(jobId);
await queue.clearWaiting();
await queue.cancel(jobId);
await queue.clearFinished();
await queue.close();
unsubscribe();
```

DownloadStorage — узкий клиентский интерфейс: prefix, append, commit, discard. Адаптер должен изолировать staging каждого задания, возвращать стабильный Blob prefix, записывать строго с заданного offset, поддерживать abort writer без порчи предыдущего checkpoint и атомарно публиковать конечный файл. Для Node-приложения нужен файловый адаптер с временным файлом и rename; браузерная реализация находится в web, а SDK не зависит от DOM-элементов или OPFS. Commit/discard не повторяются автоматически. Нельзя подставлять необратимый поток deployment вместо staging.

DownloadQueue управляет состояниями и расписанием, checkpointedDownload — проверяемым переносом в клиентский storage, DepotClient — HTTP/Range/retry, BrowserDownloadStorage — браузерным диском. Сервер продолжает авторизовывать каждый запрос и применять общие/per-principal ограничения. Новых серверных маршрутов и прав доступа не добавлено.

## Серверная очередь

Дополнены параметры запуска для обоих направлений, с отдельным состоянием upload/download:

| Environment                        | Default       | Граница                          |
| ---------------------------------- | ------------- | -------------------------------- |
| DEPOT_TRANSFER_QUEUE_LIMIT         | 64            | 1–1024 ожидающих на направление  |
| DEPOT_TRANSFER_QUEUE_PER_PRINCIPAL | min(8, limit) | 1–limit ожидающих одного клиента |
| DEPOT_TRANSFER_QUEUE_TIMEOUT_MS    | 20000         | 1–120000 мс                      |

Существующие maxUploads/maxDownloads, per-principal active caps и bytes/s сохраняются. Настройки применяются при запуске; общий HTTP admission в 128 запросов также продолжает действовать, поэтому увеличение waiting limit не создаёт гарантированную дополнительную ёмкость. Readiness показывает waitingCapacity, perPrincipalWaitingCapacity и timeoutMs. HTTP timeout/full queue сохраняют прежние 503/Retry-After. OpenAPI document 0.6.1, inventory по-прежнему 101 операция.

Это очередь клиента и допуски конкретного шлюза. Durable cluster-wide download jobs, динамическое перераспределение полосы, server-side operator cancellation чужих передач и HA остаются отдельными задачами; app/scheduler не объявляется реализованным благодаря клиентской очереди.

## Проверки

- Unit: пределы, интервалы, timeout, снижение concurrency, pause/abort/checkpoint, повторный запуск, очистка ожидающих, сбои очистки, запрет отмены commit и обработка ошибок наблюдателя.
- PostgreSQL + HTTP + диск: pause после 8 MiB, сохранение прежнего destination, Range с точного offset, проверенная публикация и удаление staging, серверный timeout и диагностика очереди.
- Browser: `tests/browser/downloads.mjs`, отдельная тестовая БД и установленный Playwright Chromium/Edge. Обходит только нативный диалог выбора: вместо него выдаёт реальные OPFS FileSystemFileHandle. Проверяет HTTP/OPFS/хеш, pause/resume, очистку, RU/EN, светлую/тёмную темы и ширины 390/1440 px. Нативный диалог ОС и квоты на 5 GiB этим тестом не проверяются.

Запуск после build: `node --env-file=.cache/test-db.env tests/browser/downloads.mjs`. При внешней установке Playwright задать DEPOT_PLAYWRIGHT_MODULE абсолютным путём к index.mjs; DEPOT_BROWSER_CHANNEL=msedge выбирает установленный Edge. Browser suite требует эксклюзивной тестовой БД, не запускается одновременно с integration suite.

Локальный прогон 2026-09-24: Windows, Node.js 24.13.0, PostgreSQL 18.4 — check/сборка, 76 unit tests и 83 integration tests прошли. Browser suite прошёл в headless Edge с 17 MiB, паузой после 8 MiB, проверкой итогового SHA-256 и очисткой abandoned sessions при сохранении живой соседней вкладки. Проверены обе темы/RU/EN/390–1440 px. Это не проверка браузерной квоты 5 GiB и не стендовая приёмка двух серверов.
