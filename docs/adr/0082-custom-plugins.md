# 0082. Самописные плагины: уровни доверия, изоляция и SDK

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-17. Решение **заменяет часть [ADR 0078](0078-open-core-modules-and-licenses.md)**: п. 7 («загружается только код, подписанный ProAnimaStudio; модули третьих сторон не поддерживаются») и п. 3.2 в части «доверяются только встроенные ключи» — для уровня 3 этого ADR. Альтернатива ADR 0078 «загрузка модулей без подписи» остаётся отклонённой для рабочих установок и разрешается только в режиме разработки (уровень 4). Уточняет [ADR 0079](0079-extension-modules.md) (п. 1 «источники модулей», `ModuleSource`) и [ADR 0081](0081-mcp-and-agent-skill.md) (п. 3.1). Остальное в ADR 0078 и 0079 не меняется: уровень 2, инварианты I1–I4, лицензии. Решение меняет границу доверия, модель прав, долговечность (данные плагинов в резервных копиях) и публичный контракт (аддитивно). До решения владельца код не пишется. Решения владельца 2026-10-17 (в конце ADR) разрешают экосистему сторонних плагинов, уточняют обработку ответов хуков и вводят пределы ресурсов на Windows. Связано с [ADR 0008](0008-gateway-bandwidth-budgets.md), [ADR 0009](0009-leased-read-gateways.md), [ADR 0017](0017-managed-service-keys.md), [ADR 0054](0054-built-in-backup-vault.md), [ADR 0059](0059-schema-updates-behind-verified-backup.md), [ADR 0060](0060-proanima-hub.md), [ADR 0061](0061-free-source-available-license.md), [ADR 0067](0067-self-healing-services.md), [ADR 0069](0069-webhooks-over-change-feed.md), [ADR 0072](0072-single-site-ha.md), [ADR 0077](0077-fleet-console.md), [ADR 0080](0080-event-integrations.md).

## Контекст

Владелец добавил требование (2026-10-17): качественная архитектура для платных **и** бесплатных модулей, **включая самописные плагины** оператора или заказчика. ADR 0078 это прямо запрещает: «изоляции нет», подписанный модуль — доверенный код в процессе ядра с доступом к БД, ключам и файловой системе, поэтому загружается только код ProAnimaStudio.

Факты кода и решений:

- **API расширений** (ветка `feat/extension-api`, первая часть этапа X1 ADR 0079). `@proanima/arkvory-extension-api` 0.1.0: `parseModuleManifest` с полями `format`, `id` (`[a-z][a-z0-9-]{1,31}`), `version`, `extensionApi` (caret-диапазон), `kind` (`protocol | storage-backend | backup-vault | identity-provider | event-sink | transfer`), `core`, `roles` (`api | reader | worker | backup`), `requires`, `provides`, `routePrefixes`, `metricPrefix`, `tablePrefix`. `ModuleSource = 'builtin' | 'signed'`. `planModules` закрепляет пространства внешних модулей: маршруты `/api/ext/<id>/v<major>/`, таблицы `arkvory_x_<id>_`. Отпечаток плана сравнивается всеми процессами.
- **Подпись** — minisign/Ed25519 (ADR 0060); ключи модулей и лицензий ProAnimaStudio встроены в ядро (ADR 0078, п. 3.2, 6.1).
- **Сервисные учётные записи** (ADR 0017): 24 точных действия над репозиторием (`serviceActions` в `packages/domain/src/service-policy.ts`: `artifact.read`, `content.read`, `annotation.write`, `artifact.promote` и другие), привязки только к конкретным репозиториям, не больше 64, ключ может только сузить права учётной записи, повторная проверка прав перед фиксацией изменения.
- **Службы.** Linux — systemd от системного пользователя `arkvory` (`deploy/register-linux.sh`); Windows — WinSW от `LocalService`, БД — от `NetworkService` (`deploy/register-windows.ps1`, `database-windows.ps1`); Compose — контейнеры. Перезапуск при падении и зависании — ADR 0067.
- **HA** (ADR 0072) держит весь корень установки на одном томе DRBD; службы — в группе Pacemaker на активном узле. Шлюзы чтения (ADR 0009) — отдельные процессы с той же БД.
- **Секреты в БД** шифруются ключом установки из файла вне БД и копии: `fleet.key` (ADR 0077), `events.key` (ADR 0080).
- **Исходящие запросы** — `createEgressPolicy` (ADR 0069): разрешение имени до соединения, запрет внутренних диапазонов, HTTPS с проверкой сертификата, частные сети только списком на хосте.
- **События** (ADR 0080): курсор `GET /api/v1/events` с ACL на каждый запрос.
- **Лицензия ядра** (LICENSE §1–2): изменения и изменённые версии можно использовать внутри своей организации; распространять программу или её части вне организации нельзя.

## Решение

### 1. Уровни доверия

| Уровень                   | Кто подписывает                    | Откуда доверие                                       | Где выполняется                                                                           |
| ------------------------- | ---------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 1. Встроенные модули ядра | Релиз ядра (ADR 0060)              | Входят в релиз                                       | В процессе ядра                                                                           |
| 2. Модули ProAnimaStudio  | Ключ модулей ProAnimaStudio (0078) | Встроенные в ядро ключи                              | В процессе; может и вне процесса (п. 5), если модулю это подходит                         |
| 3. Плагины оператора      | Ключ автора плагина                | Список доверия на хосте, который ведёт root-оператор | **Вне процесса** по умолчанию; в процессе — только по явному разрешению на хосте (п. 5.3) |
| 4. Плагины разработки     | Без подписи                        | Профиль установки `development`                      | Вне процесса; в процессе — с тем же флагом хоста, что для уровня 3                        |

**Что может и чего не может каждый уровень:**

- **Уровень 1** — все точки расширения ADR 0079. Свои шаги в общей последовательности миграций ядра.
- **Уровень 2** — все точки ADR 0079, `licenseFeature`, порт `LicenseView`, раздача хабом, список отзыва ProAnimaStudio, миграции `arkvory_x_<id>_*`. Обязан выполнять I1–I4 ADR 0078. Не может использовать id с префиксом `op-`.
- **Уровень 3** — возможности п. 7 в пределах, которые утвердил оператор: события, вызов разрешённых операций `/api/v1`, свои маршруты под `/api/ext/op-<name>/v<major>/`, проверки публикации и продвижения, своё состояние, секреты, исходящие запросы через ядро. В процессе (по разрешению хоста) — точки из матрицы п. 5.4. Не может: `publisher: "proanimastudio"`, id без префикса `op-`, `licenseFeature` и `requires: ["license"]`, корневые префиксы маршрутов, права администратора или делегирования, участие в хабе и его списке отзыва, вызов операций из запретного списка п. 7.2.
- **Уровень 4** — то же, что уровень 3, но только в установке с профилем `development` (п. 15). Рабочая установка такие пакеты не принимает и не запускает.

Уровень определяется ключом, которым подписан манифест, а не полем манифеста: поле `publisher` только проверяется на соответствие ключу. Ключ ProAnimaStudio подписывает только уровень 2; ключ из списка доверия — только уровень 3 и только id `op-*`. Пакет, подписанный ключом релизов ядра, отклоняется на всех уровнях (как в ADR 0078, п. 3.2).

### 2. Инварианты плагинов уровней 3 и 4

Это жёсткие требования к ядру. Тест, нарушающий любой из них, — дефект ядра, а не плагина.

- **P1. Чтение не зависит от плагинов.** Чтение, скачивание, Range, экспорт, резервное копирование, восстановление, проверка целостности, очистка и обновление ядра никогда не ждут плагин вне процесса и не вызывают его. Падение плагина не делает данные нечитаемыми. Для плагина уровня 3 в процессе с `dataClass: layout` действуют L1–L7 ADR 0078 (п. 5.3).
- **P2. Плагин не расширяет права.** Плагин действует как сервисный принципал со своими явными привязками (п. 9) или как пересечение своих прав с правами запросившего пользователя. Объединения прав нет. Прав администратора, делегирования (ADR 0019) и системных действий нет никогда.
- **P3. Целостность — за ядром.** Байты попадают в хранилище только через путь публикации ядра с проверкой размера и SHA-256. Плагин вне процесса не получает доступа к БД, каталогу blob, staging, ключам и конфигурации ядра.
- **P4. Всё ограничено.** У каждого вызова между ядром и плагином есть срок, размер сообщения, предел параллелизма и бюджет байтов (п. 11). Отказ плагина вне процесса не роняет процессы ядра.
- **P5. Всё записывается.** Установка, доверие, права, включение, решения проверок, обход проверки при `fail-open`, исходящие запросы и действия плагина в каталоге попадают в журналы с субъектом `plugin:<id>` (п. 17).
- **P6. Удаление плагина не теряет данные ядра.** Данные плагина удаляются только явной командой `--purge`.
- **P7. Доверие к коду — решение хоста.** Добавить ключ в список доверия, разрешить выполнение в процессе, публичные маршруты и частные сети можно только командой на хосте. HTTP API и консоль этого не умеют, поэтому захват учётной записи администратора не даёт выполнения кода на сервере.

### 3. Доверие к ключам оператора

**Ключ автора.** `arkvoryctl plugin keygen` создаёт пару Ed25519 в формате minisign: закрытый ключ под паролем на рабочей станции автора, открытый — файл `.pub`. Совместимость с `minisign` позволяет подписывать и проверять сторонним инструментом.

**Список доверия** — файл `config/plugin-trust.json` в каталоге конфигурации установки:

```json
{
  "format": 1,
  "keys": [
    {
      "keyId": "<16 hex>",
      "publicKey": "<base64>",
      "label": "Acme platform team",
      "plugins": ["op-*"],
      "allowInProcess": false,
      "addedAt": "2026-10-17T10:00:00Z",
      "addedBy": "root@host-a",
      "expiresAt": null
    }
  ]
}
```

- Ведётся только командами `apps/deploy` от root или администратора хоста: `arkvory module trust add <file.pub | строка> --label <текст> [--plugins <шаблон,…>] [--allow-in-process] [--expires <дата>]`, `trust list`, `trust remove <keyId>`. Команда показывает id ключа и отпечаток и требует подтверждения (`--yes` для сценариев).
- **Права файла:** владелец root (Windows — `Administrators`/`SYSTEM`), учётная запись службы ядра только читает. Скомпрометированный процесс ядра не может добавить ключ.
- Шаблон `plugins` ограничивает id, которые ключ может подписывать (`op-*` по умолчанию, например `op-acme-*`). Ключ с истёкшим `expiresAt` не принимается для новых установок; уже установленные пакеты продолжают работать с предупреждением `plugin_signer_expired`, пока оператор не решит иначе.
- **Отзыв.** `trust remove` запрещает новые установки и запуск плагинов этого ключа: при следующей сверке (не позже 10 с) службы плагинов вне процесса останавливаются, хуки этих плагинов переходят в отказ по своей политике (п. 8.3), плагин в процессе не загружается при следующем запуске процесса. Отдельно `arkvory plugin revoke <id>@<version> | --sha256 <hash>` пишет локальный список отзыва пакетов `config/plugin-revocations.json` (те же права файла).
- **Резервная копия.** Снимок списка доверия и списка отзыва (только открытые ключи) входит в манифест точки копии. Восстановление **не применяет** доверие автоматически: оно показывает ключи из точки и требует `arkvory module trust add` на целевом хосте или явного `--trust-plugin-signers-from-point`. Восстановление точки с данными плагина `layout` без доверия к его ключу отказывает до изменений (`plugin_signer_untrusted`).
- **HA.** Каталог конфигурации лежит на реплицируемом томе, поэтому список общий для узлов. Шлюзу чтения список нужен только для плагинов в процессе (п. 12); `arkvory module sync` на хосте шлюза не добавляет ключи сам и отказывает, если подписавший ключ не доверен этому хосту.

### 4. Пакет и манифест

Формат пакета — ADR 0078, п. 3.1 (`module.json`, `module.json.minisig`, `files/…`, полный список файлов с SHA-256), проверка до любого `import()` или запуска — п. 3.3. Манифест дополняется полями (имена — к реализованным в X1):

- `publisher` — для уровня 2 `"proanimastudio"`, для уровня 3 — строка автора `[a-z][a-z0-9-]{1,31}`, только для показа;
- `isolation` — `process` или `in-process`;
- `runtime` (для `process`): `{"kind": "node", "entry": "files/main.mjs"}` — запуск Node из релиза ядра; или `{"kind": "executable", "platforms": {"linux-x86_64": "files/linux/plugin", "windows-x86_64": "files/windows/plugin.exe"}}` — собственный исполняемый файл. Исполняемые файлы разрешены только вне процесса: их ограничивает ОС, а не процесс ядра. Пакет с `executable` ставится только на платформы из списка;
- `pluginProtocol` — caret-диапазон версий протокола (п. 6) для `process`; для `in-process` — прежний `extensionApi`;
- `capabilities` — запрошенные возможности п. 7 (`events.read`, `api.call`, `state`, `data`, `secrets`, `egress`, `routes`, `hooks`);
- `permissions` — запрошенный **потолок** прав: список действий `serviceActions`. Оператор выдаёт права в пределах потолка (п. 9);
- `events` — типы событий (`artifact.*` и т. п.), `egress` — список хостов `{host, port}` (точное имя или `*.example.com`), `secrets` — имена и описания;
- `routes` — `{method, path, operationId, auth, action, repositoryParam, bodyLimit, responseLimit, timeoutMs}`; `auth` — `principal` (по умолчанию) или `none` (п. 7.6);
- `hooks` — `{point, timeoutMs, reads}`: точка (`publish.validate`, `promote.validate`), срок и нужно ли чтение содержимого;
- `resources` — запрошенные пределы: `memoryMiB`, `cpuPercent`, `concurrency`, `stateMiB`, `dataMiB`.

Все поля разбираются как `unknown` с машинными кодами и JSON Pointer, как `parseModuleManifest`. Новые поля — необязательные для уровней 1–2 (minor-версия `extension-api`).

**Пространство имён.** Id уровня 3 — `op-[a-z][a-z0-9-]{1,20}`: ProAnimaStudio никогда не выпускает модули с префиксом `op-`, поэтому будущий модуль ProAnimaStudio не столкнётся с плагином заказчика. Маршруты — `/api/ext/op-<name>/v<major>/`, метрики — `arkvory_x_op_<name>_`, таблицы (только в процессе) — `arkvory_x_op_<name>_`. Проверку выполняет `planModules` по уровню источника.

**`ModuleSource`** расширяется аддитивно: `'builtin' | 'signed' | 'operator' | 'development'`. Отпечаток плана включает `keyId` подписавшего ключа.

#### 5.2. Решение

- **Уровень 3 по умолчанию — вне процесса**: отдельная служба ОС на плагин под своей учётной записью, связь с ядром по локальному сокету версионированным протоколом (п. 6), возможности по манифесту и разрешению оператора (п. 7), пределы ресурсов и перезапуски (п. 10).
- **В процессе** — уровень 2 (как в ADR 0078) и уровень 3 только при двух условиях: у ключа в списке доверия `allowInProcess: true` (`trust add --allow-in-process`) и плагин установлен с `arkvory plugin install --in-process`. Обе команды выводят предупреждение: код получает все права процесса ядра — БД, ключи, файлы, сеть — и может нарушить любые гарантии. В консоли и в `system/modules` такой плагин помечен «в процессе: полное доверие»; диагностика и обратная связь (ADR 0060) показывают его наличие.
- Уровень 2 может поставлять модуль вне процесса (например, интеграцию), тогда к нему применяется п. 6–11, но доверие — по ключу ProAnimaStudio.

#### 5.3. Плагины хранения оператора

Раскладка байтов (`storage-backend`, `dataClass: layout`) — горячий путь и часть гарантий чтения, поэтому **только в процессе**. Для уровня 3 это возможно лишь по разрешению хоста (п. 5.2) и с обязательствами ADR 0078: L1–L7, наборы `blob-store` и `readability` из `extension-testkit`. Ядро не может проверить, что плагин их проходит; это ответственность оператора, и `arkvory plugin install --in-process` для `layout` требует отдельного подтверждения `--accept-data-responsibility`. Отличия от уровня 2:

- хаб не раздаёт пакет, поэтому пакет **обязательно** лежит в каждой точке копии с данными плагина (L2 без хаба);
- восстановление требует доверия к ключу на целевом хосте (п. 3);
- `evacuate` (L3) — та же команда ядра, через порт хранения плагина.

Рекомендация в документации: для другого хранилища предпочитать встроенные хранилища ядра (S3 — по своему ADR), а плагин хранения писать только при измеренной необходимости.

### 6. Протокол плагинов вне процесса

**Транспорт.** Плагин — сервер на локальном сокете, ядро — клиент:

- Linux и контейнеры — Unix domain socket `run/plugins/<id>/plugin.sock` (каталог принадлежит учётной записи плагина, группе ядра даётся только подключение);
- Windows — именованный канал `\\.\pipe\arkvory-<installId8>-<id>`.

Все соединения открывает ядро, поэтому плагину не нужен доступ к сокетам ядра, а перезапуск плагина ядро видит как разрыв и переподключается с backoff (1 с → 30 с).

**Взаимная аутентификация.** Права на сокет — первая линия; вторая не зависит от ОС. `arkvory plugin install` создаёт 32-байтный ключ сессии `config/plugins/<id>/session.key`, доступный только учётной записи плагина и учётной записи ядра. Каждое соединение начинается обменом `hello`: ядро и плагин отправляют случайные nonce и доказывают знание ключа HMAC-SHA256 над `роль | nonce ядра | nonce плагина | id плагина`. Плагин, не доказавший ключ, отключается (`plugin_auth_failed`); подменивший канал процесс (захват имени канала на Windows) не проходит проверку. Ключ меняется при каждой установке, обновлении и `arkvory plugin rotate-key`.

**Сообщения.** JSON-RPC 2.0, по одному JSON-объекту на строку (UTF-8, как stdio-транспорт MCP), не больше 1 МиБ на сообщение. Соединение двунаправленное: ядро вызывает хуки и маршруты, плагин — возможности п. 7. Id запросов — строки. Каждый запрос несёт `meta.timeoutMs` (остаток бюджета); отмена — уведомление `$/cancel {id}`. Ошибки — объект JSON-RPC `error` с `data.code` из контракта ошибок ADR 0051. 64-битные значения — десятичные строки.

**Потоки байтов** не идут через JSON. Вызов, которому нужны байты (тело запроса маршрута, содержимое для проверки, ответ маршрута, загрузка через `api.call`, тело исходящего запроса), получает одноразовый `streamToken`. Ядро открывает к сокету **отдельное соединение**, проходит тот же `hello`, отправляет строку `{"stream": "<token>"}` и затем кадры `u32 длина | байты` (не больше 1 МиБ; кадр нулевой длины — конец; кадр ошибки — `0xFFFFFFFF` и JSON с кодом). Backpressure даёт сам сокет; отмена — закрытие соединения. Ядро сверяет объявленную длину и SHA-256 там, где они известны.

**Инициализация.** После `hello` ядро вызывает `initialize`: версия протокола, id и версия плагина из проверенного манифеста (плагин сверяет со своими), выданные возможности и пределы, обработчики, которые ядро ждёт. Плагин отвечает реализованными хуками и маршрутами; несоответствие манифесту — `plugin_contract_mismatch`, плагин не становится готовым. `health` вызывается каждые 10 с; три пропуска подряд — `failed`.

**Почему JSON-RPC 2.0 поверх сокета, а не HTTP/2 или gRPC:**

- нулевые зависимости в ядре (`node:net` и JSON) и простая реализация на любом языке: строка JSON и кадры байтов;
- тот же стиль, что у MCP и LSP, знакомый авторам;
- HTTP/2 без TLS поверх UDS и именованного канала поддерживается неравномерно (нужен h2c с prior knowledge, в части языков — сторонние библиотеки), а его мультиплексирование здесь заменяет отдельное соединение на поток;
- gRPC добавляет protobuf, генерацию кода и стороннюю зависимость в серверный процесс;
- потоки на отдельных соединениях не требуют своей схемы управления окном и не раздувают байты base64.

**Версии.** `ARKVORY_PLUGIN_PROTOCOL` — semver, независимый от релиза ядра и от `extension-api`. Новое необязательное поле или метод — minor; удаление или несовместимое изменение — major и ADR. Ядро поддерживает текущую major и предыдущую не меньше 12 месяцев после выхода новой. Схемы всех сообщений лежат в пакете `plugin-protocol` (п. 16) и публикуются как JSON Schema для авторов на других языках.

### 7. Возможности плагина

Каждая возможность выдаётся, только если она есть в манифесте **и** её утвердил оператор при установке (п. 9). Вызов невыданной возможности — `permission_missing`.

**7.1. События (`events.read`).** `events.read {after, limit, types, wait}` с семантикой `GET /api/v1/events` ADR 0080: курсор, эпоха, ограниченный просмотр, ACL по правам принципала плагина при каждом вызове. Доставка — at-least-once; плагин хранит курсор в `state` и дедуплицирует по `id`. Требует этапов E1–E2 ADR 0080.

**7.2. Вызов операций API (`api.call`).** `api.call {operationId, params, body?}` выполняет операцию публичного контракта `/api/v1` тем же обработчиком, с тем же ACL и контрактом ошибок, от имени принципала плагина (или пересечения, п. 9). Параллельного «API для плагинов» нет: OpenAPI ядра — описание возможностей. Разрешённые операции — список `pluginOperations` в `contracts` (как `fleetReadRoutes` ADR 0077). **Никогда не входят:** управление пользователями, группами, ключами, политиками и правами; `system/*` (модули, плагины, лицензия, обновления, площадки); резервные копии; ссылки `dtl_`; журнал безопасности. Удаление артефактов доступно, только если оператор выдал `artifact.delete`.

**7.3. Состояние (`state`).** Ключ–значение с ревизией: `state.get`, `state.put {key, value, expectedRevision}` (CAS), `state.delete`, `state.list {prefix, after, limit}`. Ключ — до 256 байт, значение — JSON до 256 КиБ, всего — до `stateMiB` (по умолчанию 64 МиБ). Таблица `arkvory_plugin_state` (expand-only миграция ядра) входит в реестр таблиц копии.

**7.4. Каталог данных (`data`).** `plugin-data/<id>/data/` — сохраняется в копии (до `dataMiB`, по умолчанию 1 ГиБ); `plugin-data/<id>/cache/` — не сохраняется и может быть очищен ядром. Доступ к каталогу только у учётной записи плагина. Размер ядро измеряет раз в 5 минут; превышение останавливает плагин (`plugin_quota_exceeded`). Жёсткую квоту в реальном времени ядро не обещает: это требует квот файловой системы.

**7.5. Секреты (`secrets`).** Манифест объявляет имена. Значения задаются командой `arkvory plugin secret set <id> <name> --from-file <f>` или в консоли глобальным администратором (только запись). Хранятся в БД, зашифрованные AES-256-GCM ключом `plugins.key` (каталог данных, 0600, вне БД и копии, по образцу `fleet.key`). Плагин читает `secrets.get {name}` только для объявленных и заданных имён; при изменении получает `secrets.changed`. Значения не попадают в журналы, ответы API, события и диагностику. После восстановления на хост без ключа секреты надо задать заново; до этого плагин `degraded` с `secret_unavailable`.

**7.6. Маршруты (`routes`).** Ядро регистрирует маршруты манифеста под `/api/ext/op-<name>/v<major>/` и проксирует их плагину:

- аутентификация, защита CSRF, допуск, бюджеты полосы (ADR 0008) и проверка `action` по ACL репозитория из `repositoryParam` — как у `/api/v1`, до вызова плагина;
- плагин получает субъект (id и вид), репозиторий, проверенное действие, `requestId` и `contextToken` (п. 9), но не заголовки авторизации и cookie;
- ответ: `Set-Cookie`, заголовки CORS и hop-by-hop удаляются; типы `text/html`, `application/xhtml+xml`, `image/svg+xml` и JavaScript отклоняются (`plugin_response_forbidden`); всегда `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox; default-src 'none'`. Так плагин не может выполнить скрипт в источнике консоли;
- `auth: none` (входящие вебхуки внешних систем) разрешается только командой хоста `arkvory plugin allow-public-routes <id>`; такие маршруты не получают `contextToken`, ограничены 10 запросами в секунду и телом 1 МиБ по умолчанию; проверка подписи отправителя — обязанность плагина;
- фрагмент OpenAPI маршрутов отдаёт `GET /api/v1/system/modules/{id}/openapi` (ADR 0078, п. 8). Публичный `/api/v1` от плагинов не меняется.

**7.7. Исходящие запросы (`egress`).** Плагин вне процесса не имеет сети (п. 10). `egress.fetch {method, url, headers, bodyStream?}` выполняет ядро:

- хост и порт — только из утверждённого списка манифеста; затем `createEgressPolicy` (SSRF-правила ADR 0069); частные сети и свои УЦ — только командой хоста `arkvory plugin egress <id> --allow-private <cidr> | --ca-file <pem>`;
- HTTPS с проверкой сертификата; перенаправления не выполняются, а возвращаются плагину и проверяются заново при следующем запросе;
- срок — до 60 с, ответ — до 16 МиБ по умолчанию, до 32 параллельных запросов на плагин;
- журнал: плагин, метод, хост, статус, байты; без пути с query, заголовков и тела.

**7.8. Журнал (`log`).** Уведомление `log {level, message, fields}` пишется в журнал ядра с полем `plugin`, не больше 100 строк в секунду и 8 КиБ на строку; сверх лимита считается в метрике потерь. stdout и stderr процесса собирает служба ОС (`arkvory plugin logs <id>`).

### 8. Проверки публикации и продвижения

Обработка ответов хуков (п. 8.3–8.4) уточнена «Решениями владельца 2026-10-17», Р2.

**8.1. Порты.** В `application` появляются порты потребителя `PublicationGate` и `PromotionGate`: `check(subject, signal) → allow | deny(code, message) | unavailable(code)`. Без плагинов реализация разрешает всё. Адаптер брокера плагинов в `infrastructure` реализует оба порта; сценарии о плагинах не знают (DIP).

**8.2. Где вызываются.**

- `publish.validate` — в каждом пути публикации **до** фиксации каталога и вне SQL-транзакции: в задании завершения загрузки (новая фаза `validating` после проверки размера и SHA-256) и в синхронных путях протоколов (raw, npm, манифест OCI, Git LFS) в запросе до транзакции. Policy-тест сверяет, что каждая фиксация публикации проходит через `PublicationGate`.
- `promote.validate` — в запросе продвижения до транзакции.
- Не вызываются: импорт зеркал (ADR 0058; источник уже проверил публикацию), восстановление из копии, внутренние переносы ядра (эвакуация, очистка).

Плагин получает дескриптор: репозиторий, вид, имя, версию или путь, размер, SHA-256, метки, metadata (только при `annotation.read`), субъект загрузки. При `reads: true` — поток содержимого ещё не опубликованного blob (бюджет байтов и срок хука). Ответ `deny` несёт код `[a-z][a-z0-9_]{0,63}` и сообщение до 256 символов, очищенное от управляющих символов; клиент получает `422 plugin_rejected` с id плагина, кодом и сообщением.

**8.3. Привязка и политика отказа.** Глобальный администратор (консоль, API) или команда хоста привязывает хук к репозиториям: `{point, repositories, failure: open | closed, required, timeoutMs}`. На репозиторий и точку — не больше 4 плагинов; они вызываются параллельно, публикация проходит, только если все ответили `allow`.

- **Срок** — по умолчанию 10 с для синхронных путей и 60 с для задания завершения, не больше 300 с.
- **`closed`** (по умолчанию): при сроке, недоступности или ошибке протокола синхронный путь отвечает `503 plugin_unavailable` с `Retry-After`, а задание завершения повторяет проверку с backoff до `maxPendingHours` (по умолчанию 24) и затем отклоняет загрузку с `plugin_unavailable`.
- **`open`**: публикация разрешается, пишется запись аудита `plugin.hook.skipped` и метрика.
- **`required: true`**: выключение, удаление или несовместимость плагина не снимают привязку — публикации в этих репозиториях отклоняются (`plugin_required_unavailable`), пока оператор явно не отвяжет хук. Так плагин соответствия нельзя молча «потерять» при обновлении.

**8.4. Идемпотентность.** Решение записывается в `arkvory_plugin_decisions` (плагин, версия, точка, субъект — id загрузки или артефакта со стадией, SHA-256, решение, код, время). Повтор задания после перезапуска или переключения HA берёт сохранённое решение той же версии плагина и не вызывает плагин снова. Хранение — 30 дней.

### 9. Права: плагин как сервисный принципал

- Установка создаёт сервисную учётную запись вида `plugin` (`plugin:<id>`, ADR 0017) **без ключей**: выпуск ключа для неё отклоняется. Аутентификация плагина — только ключ сессии сокета (п. 6), поэтому учётные данные плагина не покидают хост.
- **Права** — точные привязки `{repository, actions}` (до 64), как у сервисных ключей. Выдаёт их глобальный администратор (консоль, `PUT /api/v1/system/plugins/{id}/grants`) или команда хоста `arkvory plugin grant`. Выданное не может превышать потолок `permissions` манифеста. Новая версия плагина с более широким потолком ставится, но не включается до утверждения (`plugin_permissions_pending`); прежняя версия продолжает работать.
- **Шаблон `*` для репозиториев** в первой версии не поддерживается (ADR 0017 разрешает только точные привязки). Плагину на все репозитории привязки задаются списком; см. «Открытые вопросы».
- **От имени пользователя.** В вызове маршрута и хука ядро передаёт `contextToken`, действительный до конца вызова и привязанный к сессии плагина. `api.call` с ним проверяет права **дважды** — плагина и пользователя — и выполняется, только если разрешают оба. Аудит пишет обоих.
- Флага администратора, делегирования ADR 0019, чтения журнала безопасности и системных областей у плагина нет никогда; это проверяет `planModules` и разбор привязок.

### 10. Исполнение на хосте

`arkvory plugin install` (только хост, `apps/deploy`) создаёт службу плагина под отдельной учётной записью и записывает установку в журнал обновлений ADR 0059 (`plugins.before`/`plugins.after` с id, версией, SHA-256 пакета, ключом подписи), с теми же фазами и откатом.

- **Linux (systemd).** Пользователь `arkvp-<name>` (`useradd --system`, без оболочки), служба `arkvory-plugin-<name>.service`: `User=`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `PrivateDevices=yes`, `ReadWritePaths=` только каталог данных и сокета, `RestrictAddressFamilies=AF_UNIX`, `IPAddressDeny=any`, `SystemCallFilter=@system-service`, `MemoryMax=`, `CPUQuota=`, `TasksMax=64`, `LimitNOFILE=1024`. Пакет — только чтение, владелец root.
- **Windows (WinSW).** Служба `Arkvoryplugin-<name>` от виртуальной учётной записи `NT SERVICE\Arkvoryplugin-<name>` (проверяется на этапе P3), ACL каталога данных — только этот SID, правило брандмауэра Windows, запрещающее этой службе исходящие соединения. Жёсткие пределы памяти и CPU ОС в первой версии **не обеспечиваются**: ядро ограничивает кучу Node (`--max-old-space-size`), параллелизм, размеры сообщений и потоков. Это записано в документации (см. «Открытые вопросы»). Заменено 2026-10-17: пределы задаёт помощник с Job Objects («Решения владельца», Р3).
- **Docker Compose.** Сервис на плагин в `config/compose.plugins.yml`: образ Arkvory, `network_mode: none`, `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges`, `mem_limit`, `cpus`, `pids_limit`, свой uid; тома — пакет (только чтение), каталог сокета, каталог данных.
- **Перезапуски** (ADR 0067): служба ОС перезапускает упавший процесс с нарастающей паузой до 5 минут; больше 10 падений за 10 минут — служба остаётся остановленной, состояние `failed` до `arkvory plugin restart <id>`. SDK плагина содержит сторожевой поток: зависание цикла событий дольше 30 с завершает процесс.
- **Без перезапуска ядра.** Реестр плагинов вне процесса — таблица `arkvory_plugins` с ревизией. API и worker перечитывают её при изменении (опрос раз в 5 с) и подключаются или отключаются без перезапуска. Плагины вне процесса не входят в отпечаток плана ADR 0079: они не загружаются в процессы ядра и работают на одном хосте (п. 12). Плагины в процессе входят в отпечаток, их установка перезапускает службы, как у модулей.
- Брокер плагинов — адаптер `infrastructure`, его создают корни `apps/api` (маршруты, `promote.validate`, синхронные пути публикации) и `apps/worker` (`publish.validate` в задании завершения). Каждый процесс держит своё соединение с плагином; SDK плагина это скрывает.

| Состояние / данные                 | 64 МиБ / 1 ГиБ             | `resources`, утверждает оператор |
| Хуков на репозиторий и точку       | 4                          | нет                              |
| Исходящих запросов параллельно     | 32 на плагин               | команда хоста                    |

Превышение отклоняется машинным кодом (`rate_limited` с `Retry-After`, `plugin_quota_exceeded`), а не очередью без границы.

### 12. HA, шлюзы чтения, консоль площадок

- **HA (ADR 0072).** Пакеты, каталоги данных, сокеты, ключ сессии и `plugins.key` лежат в корне установки на томе DRBD. Службы плагинов — ресурсы группы Pacemaker после API на активном узле. Учётные записи плагинов создаются на каждом узле процедурой кластера с одинаковым uid. При переключении плагины стартуют на новом узле; незавершённые проверки повторяются по п. 8.4.
- **Шлюзы чтения (ADR 0009).** Плагины вне процесса работают только на хосте процесса записи. Шлюз не регистрирует `/api/ext/op-*/` и отвечает 404 `not_found`, как на маршрут выключенного модуля (ADR 0079, п. 5.7). Плагины в процессе с ролью `reader` требуют `module sync` и доверия на хосте шлюза (п. 3).
- **Консоль площадок (ADR 0077).** Обзор площадки показывает плагины: id, уровень, ключ, версию, состояние. Управлять плагинами удалённо нельзя; маршруты плагинов в `fleetReadRoutes` не входят.

### 13. Резервные копии, восстановление, удаление

- **Копия.** Точка содержит: `arkvory_plugin_state`, `arkvory_plugins`, привязки и решения — логическим экспортом по реестру таблиц; раздел каждого плагина с `plugin-data/<id>/data/` (файлы, размеры, SHA-256); пакет каждого установленного плагина (хаб их не раздаёт); снимок списка доверия и отзыва. Секреты и `plugins.key` в копию не входят.
- **Согласованность каталога данных.** Перед захватом ядро вызывает необязательный `backup.freeze {deadlineMs}` и после — `backup.thaw`. Плагин без этих методов копируется «как есть», раздел помечается `consistency: fuzzy`, и это видно в `verify` и консоли.
- **Восстановление.** Ядро восстанавливает разделы плагинов, но не запускает плагины, пока на целевом хосте нет доверия к ключу (п. 3) и не созданы службы: `arkvory plugin reinstall-from-point`. До этого плагины `unavailable`, хуки — по своей политике (`required` продолжают отклонять).
- **Удаление.** `arkvory plugin remove <id>` останавливает службу, отключает маршруты и хуки (привязки `required` — только с `--unbind-required`), отключает сервисную учётную запись (не удаляет: аудит ссылается на неё). Состояние, данные и секреты хранятся 30 дней; `--purge` удаляет их сразу. Плагин в процессе с `dataClass: layout` и данными не удаляется (`module_owns_data`): сначала `evacuate`.

### 14. Обновление ядра и совместимость

- Перед обновлением ядра updater сверяет каждый плагин: `pluginProtocol` (вне процесса) или `extensionApi` (в процессе) с новой версией. Политика `config/plugins.json` `onIncompatible`: `refuse` (по умолчанию) — обновление отклоняется до изменений с `plugin_incompatible` и списком плагинов; `disable` — несовместимые плагины выключаются одной записью журнала, хуки с `required: true` при этом продолжают отклонять публикации (п. 8.3). Флаг `--disable-incompatible-plugins` действует для одного обновления.
- Плагины вне процесса переживают обновления ядра лучше модулей в процессе: протокол меняется реже `extension-api`, а окно поддержки предыдущей major — 12 месяцев.
- Обновление плагина — `arkvory plugin install <file>` новой версии: та же проверка подписи и ключа, журнал, откат к предыдущей версии при неготовности за 60 с. Понижение — явной командой с файлом.

### 15. Режим разработки (уровень 4)

- Профиль установки `development` задаётся только при установке (`arkvory install --profile development`, `compose.dev.yml`, `npm run dev`) и записывается в `config/install-profile`. Рабочую установку перевести в `development` нельзя; обратный перевод возможен после удаления неподписанных плагинов.
- В профиле `development`: API слушает только loopback, HA не настраивается (`cluster-*` отказывает), консоль показывает постоянную плашку «режим разработки», `/health/status` и `capabilities` сообщают `developmentMode: true`.
- `arkvory plugin install --unsigned <dir | file>` и `arkvoryctl plugin dev` (подключение к локальной установке с перезапуском при изменении файлов) работают только в этом профиле. В рабочей установке неподписанный пакет отклоняется (`plugin_signature_required`) на установке и на каждом запуске.

### 17. Консоль, API, наблюдаемость

- **API (аддитивно).** `GET /api/v1/system/modules` получает `source: operator | development`, `signer: {keyId, label}`, `isolation`, `capabilities: {requested, granted}`, `hooks`, `restarts`, `lastError`. Новые маршруты глобального администратора: `GET /api/v1/system/plugins/{id}`, `PUT .../grants`, `PUT .../hooks`, `PUT .../secrets/{name}` (только запись), `POST .../enable|disable`. Установки, доверия, `--in-process`, публичных маршрутов и частных сетей в API нет (P7). OpenAPI, SDK (`client.system.plugins.*`) и CLI — в том же PR.
- **Консоль.** Страница «Модули и плагины» (расширение страницы ADR 0078, тексты через i18n, стили через токены): уровень с меткой ключа, изоляция, версия, состояние, перезапуски, последний код ошибки, запрошенные и выданные возможности и права, привязанные хуки с политикой, исходящие хосты, потребление ресурсов, последние 200 строк журнала плагина (только администратор). Ключи доверия видны только для чтения.
- **Журналы.** Действия плагина в каталоге пишутся в `arkvory_audit` с субъектом `plugin:<id>` (и пользователем при `contextToken`); установка, доверие, права, включение, секреты (без значений), `plugin.hook.skipped`, отклонения — в журнал безопасности.
- **События ADR 0080.** `module.health.changed` для плагинов; новые типы `plugin.hook.rejected` и `plugin.hook.skipped` (область `repository`).
- **Метрики.** `arkvory_plugin_up{plugin}`, `arkvory_plugin_restarts_total`, `arkvory_plugin_call_duration_seconds{plugin,method}`, `arkvory_plugin_hook_decisions_total{plugin,point,decision}`, `arkvory_plugin_egress_requests_total{plugin,result}`, `arkvory_plugin_rate_limited_total`, `arkvory_plugin_log_dropped_total`. Правила оповещения `ArkvoryPluginDown`, `ArkvoryPluginHookFailingOpen`, `ArkvoryPluginRequiredHookBlocking`.

### 18. Лицензирование

- Плагины уровня 3 — собственный код оператора или заказчика. LICENSE §1 разрешает использовать и менять программу внутри своей организации, поэтому самописный плагин для своей установки допустим без отдельного разрешения.
- **Ядро не требует лицензии ProAnimaStudio для плагинов уровня 3 и 4.** Ни одна функция п. 3–17 не проверяет `LicenseView`; I4 ADR 0078 распространяется и на механизм плагинов: он бесплатен и не станет платным.
- Платные модули остаются уровнем 2 и включаются лицензией по ADR 0078. Плагин уровня 3 не может объявить `licenseFeature`, получить `LicenseView` или занять пространство имён ProAnimaStudio.
- ProAnimaStudio не поддерживает код плагинов заказчика; диагностика и обратная связь показывают наличие плагинов (id, уровень, изоляция), чтобы отличать дефекты ядра.
- **Ограничение:** `extension-api`, `plugin-protocol`, `plugin-sdk` и `extension-testkit` сейчас под LICENSE ядра. Плагин, включающий их код, можно использовать внутри организации (подрядчики, работающие на неё, входят в «вашу организацию»), но нельзя передавать за её пределы (LICENSE §2). Экосистема сторонних плагинов, их продажа или публикация требуют решения правообладателя (см. «Открытые вопросы»). Этот ADR LICENSE не меняет. Решено 2026-10-17: экосистема разрешена через отдельные условия SDK, пока черновик («Решения владельца», Р1).

## Альтернативы

- **Только в процессе для всех уровней.** Самый быстрый путь, но код заказчика получает БД, ключи и файлы ядра, а его ошибка роняет хранилище. Ограничить его нельзя.
- **`vm`, worker threads, модель разрешений Node.** Не граница безопасности (документация Node); дают ложное ощущение изоляции.
- **WASM как основной вариант.** См. п. 5.1: асинхронность и потоки WASI ещё развиваются, для TypeScript нужен встроенный движок JS, отдельный рантайм — нативная зависимость. Возможен позже для маленьких чистых проверок.
- **HTTP/2 или gRPC поверх сокета.** См. п. 6: зависимости в ядре и неравномерная поддержка h2c на других языках при той же функциональности.
- **Ядро запускает плагины дочерними процессами.** Непривилегированная служба ядра не может сменить пользователя ОС, а дочерние процессы унаследуют её права. Служба ОС на плагин даёт свою учётную запись, пределы и перезапуск ADR 0067.
- **Только вебхуки и события ADR 0080.** Остаются рекомендуемым путём для интеграций без синхронных решений. Но они не умеют проверять публикацию до фиксации, добавлять маршруты и хранить состояние под гарантиями копии.
- **Доверие ключам через API или консоль.** Захват учётной записи администратора превращался бы в выполнение кода на хосте (P7).
- **Неподписанные плагины вне процесса в рабочей установке** (раз они изолированы). Плагин всё равно получает права, секреты и хуки. Подпись даёт целостность поставки и автора; стоимость для оператора — одна команда.
- **Контейнер на каждый плагин на всех платформах.** Нативные установки Windows и Linux не требуют Docker; Compose использует контейнеры (п. 10).
- **Шаблон `*` в правах плагина сразу.** Новое понятие ACL, которого нет у сервисных ключей; вынесено в открытые вопросы.

## Уточнения реализации (часть этапа P1)

Вместе с этапом O1 ADR 0078 сделаны список доверия и его команды; остальное P1 (поля манифеста п. 4, `plugin-revocations.json`, `plugin revoke`, источники `operator | development` у загрузчика) — нет. Подробности — ADR 0078, «Уточнения реализации (этап O1 и подготовка O2)».

- `config/plugin-trust.json` в формате п. 3, строгий разбор с JSON Pointer; шаблон `plugins` — точный id `op-…` или префикс `op-…*`; id плагина — `op-` и 2–21 символ без двойного и концевого дефиса, как в `extension-api`.
- `arkvory module trust add <file.pub | строка> --label … [--plugins …] [--allow-in-process] [--expires …] [--yes]`, `trust list`, `trust remove <keyId>`: только на хосте, под блокировкой установки; без `--yes` показывает id, отпечаток и ничего не пишет; файл получает владельца и группу `runtime.json` и права 0640 (Compose — 0644). Ключ с id встроенного ключа релизов, модулей или лицензий отклоняется.
- Уровень пакета определяет ключ: правила п. 1 (`op-`, `publisher`, `licenseFeature` и служба `license`, шаблон ключа, срок) проверяет `packages/signing`. `arkvory module install` пакеты уровня 3 не ставит до `arkvory plugin install` (P3).

## Последствия

- Новая граница доверия — ключи оператора. Она защищена правами файла списка доверия, командами только на хосте, взаимной аутентификацией сокета и изоляцией ОС, но не защищает от плагина в процессе, которому оператор сам разрешил полное доверие.
- Два новых workspace (`plugin-protocol`, `plugin-sdk`) и расширение `extension-testkit`; новые таблицы (`arkvory_plugins`, `arkvory_plugin_state`, `arkvory_plugin_decisions`, привязки и секреты) — expand-only миграции ядра, файл ключа `plugins.key`.
- Публичные обязательства: протокол плагинов (semver, окно 12 месяцев), `pluginOperations`, схемы сообщений.
- Публикация с привязанными хуками медленнее на время проверки; синхронные пути протоколов ждут плагин до срока хука. Чтение не меняется (P1).
- На Windows пределы ресурсов слабее, чем на Linux и в Compose; это документируется.
- Поддержка установок с плагинами в процессе сложнее: диагностика показывает их явно.
- Резервные копии больше на пакеты и данные плагинов; восстановление требует решения о доверии на целевом хосте.

## Проверка

- **Доверие и подписи.** Пакет уровня 3, подписанный недоверенным ключом, ключом релизов или ключом с шаблоном, не покрывающим id; id без `op-` у ключа оператора и `op-*` у ключа ProAnimaStudio; `publisher: "proanimastudio"` у ключа оператора; `licenseFeature` у уровня 3; неподписанный пакет в профиле `production` — на установке и при запуске после подмены файла. `trust remove` останавливает службу плагина за 10 с. Учётная запись службы ядра не может изменить `plugin-trust.json` (тест прав файла на Linux и Windows).
- **Протокол.** Набор `plugin-protocol` на эталонном плагине SDK и на минимальном плагине без SDK (тестовый сервер на Node без зависимостей, имитирующий другой язык). Неверный HMAC в `hello` с обеих сторон, подмена канала, сообщение больше 1 МиБ, кадр больше 1 МиБ, неполный поток, отмена `$/cancel` и закрытием соединения, несоответствие манифесту.
- **Изоляция (Linux, Compose).** Плагин не открывает TCP-соединение, не читает каталог данных ядра, `config/`, `fleet.key` и каталог blob; превышение `MemoryMax` и `TasksMax` перезапускает службу; 11 падений за 10 минут дают `failed`; зависание цикла событий завершает процесс сторожевым потоком.
- **P1.** При убитом, зависшем и медленном плагине: скачивание, Range, `verify`, резервная копия, восстановление и очистка идут без задержки; хуки ведут себя по политике.
- **Права.** Вызов операции вне `pluginOperations`; действие вне привязок; `contextToken` пользователя без права при правах плагина и наоборот — отказ в обоих случаях; выпуск ключа учётной записи `plugin` отклоняется; новая версия с широким потолком не включается до утверждения.
- **Маршруты.** ACL до вызова плагина; `text/html` и `Set-Cookie` не доходят до клиента; CSRF как у `/api/v1`; `auth: none` без команды хоста не регистрируется; шлюз чтения отвечает 404; OpenAPI `/api/v1` не меняется.
- **Проверки.** `deny` даёт `422 plugin_rejected` во всех путях публикации (загрузка, raw, npm, OCI, LFS); policy-тест находит путь фиксации без `PublicationGate`; `closed` при недоступности: 503 в синхронном пути и повтор с backoff в задании; `open`: публикация и аудит `plugin.hook.skipped`; `required` при выключенном плагине отклоняет; перезапуск worker после решения не вызывает плагин повторно; импорт зеркала хуки не вызывает.
- **Секреты и исходящие запросы.** Значение секрета не встречается в журналах, ответах и событиях всего сценария; хост вне списка, внутренний адрес и перенаправление на внутренний адрес отклоняются; частная сеть — только после команды хоста.
- **Копии и HA.** Точка содержит состояние, раздел данных, пакет и снимок доверия; восстановление без доверия не запускает плагин и отказывает для `layout`; `consistency: fuzzy` без `backup.freeze`; на стенде `deployment-ha` плагин стартует на новом узле, незавершённая проверка завершается один раз.
- **Обновление ядра.** Несовместимый плагин при `refuse` отклоняет обновление без изменений; при `disable` плагин выключен, а `required` хук продолжает отклонять.
- **Пределы.** Превышение частоты вызовов даёт `rate_limited` с `Retry-After`; переполнение `state` — `plugin_quota_exceeded`; журнал сверх 100 строк в секунду учитывается в метрике потерь.

## Решения владельца 2026-10-17

Владелец ответил на открытые вопросы 1, 4 и 6 и потребовал довести обработку ответов хуков и пределы ресурсов на Windows до уровня рабочих установок. Решения ниже дополняют ADR, а в местах из раздела «Что заменено» заменяют его текст.

### Р1. Экосистема сторонних плагинов

- **Да.** Авторы могут распространять плагины уровня 3, написанные по протоколу плагинов или с пакетами SDK, за пределами своей организации: публиковать и продавать на своих условиях. Это заменяет «Ограничение» п. 18 и отвечает на открытый вопрос 1.
- **Отдельные условия на материалы SDK.** Под материалами SDK понимаются пакеты `extension-api`, `plugin-protocol`, `plugin-sdk`, `extension-testkit` и спецификация протокола (документы и JSON Schema, п. 6). Черновик условий — [PLUGIN_SDK_LICENSE.draft.md](../legal/PLUGIN_SDK_LICENSE.draft.md). Он разрешает использовать материалы SDK для разработки плагинов и распространять их в составе плагина. Прав на ядро черновик не даёт: ядро остаётся под [LICENSE.md](../../LICENSE.md). На бренды он даёт только право указать совместимость. Плагин, который реализует протокол без кода Arkvory, частью программы не считается.
- **Черновик не действует.** Пока его не утвердил владелец и не проверил юрист, пакеты SDK остаются под LICENSE ядра, и п. 18 применяется как написан. LICENSE.md и LICENSE.ru.md этот ADR не меняет. Как ввести условия в действие (файл лицензии в каталоге каждого пакета, ссылка в NOTICE.md, возможно, уточнение LICENSE §2 или §11 об исключении для материалов SDK), решает юридическая проверка. Условия SDK — не открытая лицензия, «open source» их не называем.
- **Модель доверия не меняется.** Плагин стороннего автора — уровень 3: оператор добавляет ключ автора в список доверия хоста (п. 3), id плагина начинается с `op-`. Рекомендуемое соглашение — id `op-<автор>-<имя>` и шаблон ключа `op-<автор>-*`, чтобы плагины разных авторов не сталкивались. Хаб сторонние плагины не раздаёт; каталога плагинов ProAnimaStudio это решение не вводит. ProAnimaStudio не поддерживает и не проверяет сторонние плагины, а диагностика показывает их наличие (п. 18).
- **Публикация пакетов SDK** — tarball в релизах GitHub (ADR 0079); npm — открытый вопрос ADR 0078, п. 2.

### Р2. Обработка ответов хуков

Пункт уточняет п. 8.3–8.4 и заменяет их там, где они расходятся.

**Исходы.** Каждый вызов хука заканчивается одним исходом с машинным кодом. Исход записывается в аудит и метрики и попадает в ответ клиенту:

| Исход              | Когда                                                                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `allow`            | валидный ответ «разрешить»                                                                                                                                                     |
| `deny`             | валидный ответ «отклонить» с кодом плагина `[a-z][a-z0-9_]{0,63}` и сообщением до 256 символов                                                                                 |
| `timeout`          | ответа нет до срока; поздний ответ отбрасывается                                                                                                                               |
| `unavailable`      | вызов не состоялся; причина `cause`: `not_connected`, `disabled`, `incompatible`, `overloaded`, `circuit_open`, `transport` (после всех транспортных попыток), `auth_failed`   |
| `invalid_response` | ответ не проходит схему `HookResult` (разбор `unknown`), неверный код или длина сообщения, не совпало эхо `decisionId` или SHA-256 субъекта, ошибка JSON-RPC вместо результата |

`deny` — единственный исход, которым плагин решает против публикации. `timeout`, `unavailable` и `invalid_response` — отказы плагина; их обрабатывает политика привязки.

**Политика привязки** (`PUT /api/v1/system/plugins/{id}/hooks`, ревизия и CAS по `expectedRevision`):

```json
{
  "point": "publish.validate",
  "repositories": ["builds"],
  "failure": "closed",
  "required": false,
  "timeoutMs": 10000,
  "transportAttempts": 3,
  "maxPendingHours": 24,
  "circuit": { "minCalls": 10, "failureRatio": 0.5, "windowSeconds": 60, "openSeconds": 30 }
}
```

- `failure` по умолчанию `closed` для обеих точек (ответ на открытый вопрос 6). `open` задаётся только явно; изменение пишется в журнал безопасности с субъектом, и консоль помечает такую привязку.
- Пределы: `timeoutMs` — от 100 мс до 300 с (по умолчанию 10 с в синхронных путях и 60 с в задании завершения); `transportAttempts` — 1–3; `maxPendingHours` — 1–168; `circuit.openSeconds` — 5–300. Значение вне пределов отклоняется кодом `invalid_input` с JSON Pointer.

**Повторяются только транспортные ошибки.** Повторяется вызов, который не дошёл до плагина или оборвался до ответа: отказ подключения, разрыв соединения или потока байтов, сбой `hello`. Исключение — неверный HMAC: `plugin_auth_failed` не повторяется, сразу даёт `unavailable` с `cause: auth_failed` и оповещение. Попыток не больше `transportAttempts`, пауза — от 100 до 400 мс со случайным разбросом, и всё это в пределах оставшегося срока вызова: повторы срок не продлевают. `allow`, `deny`, `timeout` и `invalid_response` не повторяются: повтор медленного или неисправного плагина только умножил бы нагрузку. Повтор безопасен: каждая попытка несёт тот же `decisionId`, и плагин обязан отвечать на него одинаково (это проверяет набор `plugin-protocol`).

**Применение политики** к исходу одной привязки:

| Исход                                                     | `failure: closed`                                                                                                               | `failure: open`                                                      |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `allow`                                                   | проходит                                                                                                                        | проходит                                                             |
| `deny`                                                    | `422 plugin_rejected` с id плагина, кодом и сообщением                                                                          | то же                                                                |
| `timeout`, `unavailable`, `invalid_response`              | синхронный путь — `503 plugin_unavailable` с `Retry-After` и `details.outcome`; задание завершения — отложенная проверка (ниже) | публикация проходит, аудит `plugin.hook.skipped` с исходом и метрика |
| Плагин выключен, удалён или несовместим, `required: true` | `plugin_required_unavailable`                                                                                                   | `plugin_required_unavailable`: `required` сильнее `open`             |

Привязки одной точки вызываются параллельно, итог — самый строгий: `deny` (при нескольких — первый по id плагина, чтобы итог был детерминированным), затем отказ привязки `closed`, затем `allow` и пропуски `open`.

**Задание завершения** при отказе `closed` откладывает проверку (фаза `validating` остаётся) с паузой от 30 с до 15 минут со случайным разбросом и повторяет её до `maxPendingHours`. Затем загрузка отклоняется с `plugin_unavailable` и исходом последней попытки. Каждая отложенная проверка — новая попытка с тем же `decisionId`. Аренда и fencing задания — как сейчас.

**Автомат отключения** (circuit breaker) ведётся на пару «плагин, точка» в каждом процессе ядра. Его состояния названы иначе, чем политика отказа, чтобы их не путать: `normal`, `tripped`, `probing`.

- `normal` — вызовы идут. Переход в `tripped`, если за `windowSeconds` было не меньше `minCalls` вызовов и доля исходов `timeout`, `unavailable` (кроме `circuit_open`) и `invalid_response` не меньше `failureRatio`, или если `health` пропущен три раза подряд (п. 6). `deny` — ответ, а не отказ, и на автомат не влияет.
- `tripped` — плагин не вызывается. Исход сразу `unavailable` с `cause: circuit_open`, политика привязки применяется без ожидания срока, `Retry-After` — остаток времени. Через `openSeconds` автомат переходит в `probing`; при повторных срабатываниях время удваивается, но не больше 5 минут.
- `probing` — пропускается один вызов. Ответ (`allow` или `deny`) возвращает `normal` и сбрасывает удвоение, отказ — снова `tripped`. Остальные вызовы в это время получают `circuit_open`.
- **Состояние видно.** `GET /api/v1/system/plugins/{id}` показывает его по процессам и точкам с временем перехода и последним исходом. Метрика — `arkvory_plugin_hook_circuit_state{plugin,point,state}`, событие ADR 0080 — `plugin.hook.circuit.changed` (область `system`), каждый переход пишется в аудит. Оповещения: `ArkvoryPluginHookCircuitTripped` (дольше 1 минуты) и `ArkvoryPluginHookInvalidResponses` (хотя бы один `invalid_response` за 5 минут), вместе с прежними `ArkvoryPluginHookFailingOpen` и `ArkvoryPluginRequiredHookBlocking`.
- Состояние хранится в памяти процесса; после перезапуска — `normal`. Общего автомата для процессов нет: каждый процесс видит своё соединение с плагином (п. 10).

**Идемпотентные решения** (уточняет п. 8.4):

- `decisionId` — SHA-256 от id и версии плагина, точки, ревизии привязки, субъекта (id загрузки или артефакт с целевой стадией) и SHA-256 содержимого.
- В `arkvory_plugin_decisions` сохраняются только `allow` и `deny`: отдельной короткой транзакцией до фиксации публикации, а фиксация ссылается на `decisionId`. Повтор после перезапуска, переключения HA или транспортного повтора берёт сохранённое решение и плагин не вызывает.
- `timeout`, `unavailable` и `invalid_response` решениями не сохраняются, иначе временный сбой стал бы постоянным; они пишутся только в аудит попыток.
- Новая версия плагина или изменение привязки дают новый `decisionId`, то есть новую проверку. Хранение — 30 дней, как в п. 8.4.

**Аудит.** Для каждой попытки записываются плагин, версия, точка, привязка и её ревизия, субъект, `decisionId`, исход, `cause`, длительность и номер попытки. Итог публикации записывается вместе с политикой, по которой он получен. `plugin.hook.skipped` и перевод привязки в `open` попадают в журнал безопасности (п. 17). Метрика `arkvory_plugin_hook_decisions_total{plugin,point,decision}` использует исходы этого пункта.

### Р3. Пределы ресурсов на Windows: помощник с Job Objects

Пункт отвечает на открытый вопрос 4 и заменяет три места ADR: фразу п. 10 «жёсткие пределы памяти и CPU ОС в первой версии не обеспечиваются», строку «Память / CPU (Linux, Compose)» в п. 11 (теперь предел действует и на Windows) и последствие «на Windows пределы ресурсов слабее».

**Помощник** `arkvory-plugin-host.exe` — маленький нативный исполняемый файл в релизе для `windows-x86_64`. Он не ходит в сеть и не читает данных. Его единственная задача — запустить процесс плагина внутри объекта задания Windows (Job Object) с пределами и ждать завершения.

- Язык — без своей среды выполнения; предложены Rust с `windows-sys` и статическая сборка, окончательно — на этапе P3.
- Файл входит в подписанный манифест релиза (SHA-256 под подписью ADR 0060) и лежит в каталоге релиза, который учётные записи служб только читают. `arkvory plugin install` и `arkvoryctl doctor` сверяют его хеш с установленным манифестом.
- Подпись Authenticode появится вместе с подписью нативных пакетов, которой пока нет (ADR 0060, «Не сделано»).

**Интерфейс.**

- Запуск из WinSW: `arkvory-plugin-host.exe run --config run\plugins\<id>\job.json -- <команда плагина>`.
- `job.json` пишет `arkvory plugin install`; владелец — `Administrators`, плагин и ядро файл только читают. Помощник разбирает его как `unknown`:

  ```json
  {
    "format": 1,
    "pluginId": "op-acme-scan",
    "memoryBytes": "268435456",
    "cpuPercentOfCore": 50,
    "activeProcesses": 16,
    "statusFile": "run\\plugins\\op-acme-scan\\host-status.json"
  }
  ```

  `memoryBytes` — десятичная строка, чтобы 64-битное значение не теряло точность.

- **Пределы задания:**
  - `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` с `JOB_OBJECT_LIMIT_JOB_MEMORY` (память всего задания), `JOB_OBJECT_LIMIT_ACTIVE_PROCESS`, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION` и без `BREAKAWAY_OK`, поэтому потомки не выходят из задания;
  - `JOBOBJECT_CPU_RATE_CONTROL_INFORMATION` с `ENABLE` и `HARD_CAP`. Доля в манифесте задана в процентах одного ядра, а задание принимает долю всей машины, поэтому она пересчитывается: `cpuPercentOfCore × 100 / число логических процессоров` в единицах 1/100 %, не меньше 1;
  - UI-ограничения `JOB_OBJECT_UILIMIT_*`: рабочий стол, буфер обмена, глобальные атомы.
- **Порядок запуска:**
  1. создать задание и установить пределы;
  2. прочитать их обратно `QueryInformationJobObject` и сверить;
  3. создать процесс плагина приостановленным сразу внутри задания (`PROC_THREAD_ATTRIBUTE_JOB_LIST`; поддерживаемые Windows 10 и Server 2019+ это умеют), поэтому процесс не успевает поработать вне задания;
  4. возобновить процесс и ждать.

  Сообщения порта завершения задания (`JOB_OBJECT_MSG_JOB_MEMORY_LIMIT`, `JOB_OBJECT_MSG_ACTIVE_PROCESS_LIMIT`, `JOB_OBJECT_MSG_ABNORMAL_EXIT_PROCESS`) помощник пишет строкой JSON в stderr (журнал WinSW) и в `statusFile` вместе с применёнными пределами.

- **Остановка.** WinSW останавливает помощника, закрывается последний дескриптор задания, и `KILL_ON_JOB_CLOSE` завершает процесс плагина со всеми потомками. Падение помощника приводит к тому же.
- **Коды выхода.** Помощник возвращает код плагина; коды 90–99 зарезервированы за ним самим:
  - 90 — неверный `job.json`;
  - 91 — не удалось создать или настроить задание;
  - 92 — пределы не подтвердились чтением;
  - 93 — не удалось запустить плагин;
  - 94 — плагин завершён по пределу памяти;
  - 95 — плагин завершён по пределу числа процессов.

  Супервизор ядра переводит их в состояние плагина `failed` с кодом `plugin_limits_unavailable`, `plugin_memory_limit` или `plugin_process_limit`; перезапуски — по п. 10 (ADR 0067).

- **Самопроверка** `arkvory-plugin-host.exe check --config <file>` создаёт задание с теми же пределами, запускает в нём пробный процесс (сам помощник в режиме пробы), проверяет применение пределов и выходит. Её вызывают `plugin install`, `doctor` и гейт.
- Кучу Node плагина (`--max-old-space-size`) ядро ставит примерно на 75 % от `memoryBytes`. Тогда обычная нехватка памяти заканчивается ошибкой Node с понятной записью в журнале раньше, чем сработает жёсткий предел задания.

**При отказе плагин не запускается.** Если помощника нет, хеш не совпал, `check` не прошёл (например, среда не поддерживает задания) или пределы не подтвердились, плагин не запускается (`plugin_limits_unavailable`), и это видно в консоли и `system/plugins`. Запустить его со слабыми пределами первой версии (куча Node, параллелизм и размеры сообщений) оператор может только командой хоста `arkvory plugin limits <id> --allow-unenforced`. Решение пишется в журнал безопасности, консоль помечает плагин «пределы ОС не применяются». Вернуть строгий режим — `arkvory plugin limits <id> --enforce`.

**Проверка.**

- Гейт `deployment-services` на Windows с правами администратора:
  - превышение памяти завершает плагин с `plugin_memory_limit`;
  - процессы сверх предела не создаются;
  - доля CPU под нагрузкой не выше предела с допуском;
  - остановка службы и аварийное завершение помощника завершают все процессы плагина;
  - без помощника и с подменённым файлом плагин не запускается;
  - `--allow-unenforced` запускает плагин и помечает его.
- Unit-тесты: разбор `job.json`, пересчёт доли CPU, отображение кодов выхода.
- Сборка помощника и его хеш в манифесте релиза — гейты `native-package` и `native-install`.
