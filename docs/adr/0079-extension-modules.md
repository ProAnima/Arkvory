# 0079. API расширений и модули

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-17. Решение меняет границы пакетов ([AGENTS.md](../../AGENTS.md), «Обязательные границы», п. 8), способ сборки composition roots ([ADR 0030](0030-api-server-composition.md)) и вводит публичный semver-контракт для модулей вне репозитория. Модель поставки, подписи и лицензии задаёт [ADR 0078](0078-open-core-modules-and-licenses.md). До решения владельца код не пишется. Связано с [ADR 0018](0018-executable-api-inventory.md), [ADR 0027](0027-executable-engineering-gates.md), [ADR 0035](0035-online-cleanup.md), [ADR 0054](0054-built-in-backup-vault.md), [ADR 0058](0058-pull-mirrors.md), [ADR 0059](0059-schema-updates-behind-verified-backup.md), [ADR 0071](0071-s3-backup-vault.md), [ADR 0080](0080-event-integrations.md), [ADR 0081](0081-mcp-and-agent-skill.md).

## Контекст

По ADR 0078 ядро загружает подписанные модули ProAnimaStudio из отдельного приватного репозитория. Им нужен стабильный контракт, который не ломается от рефакторинга внутренних портов. Параллельно новые хранилища, протоколы, провайдеры входа и цели резервных копий в самом ядре подключаются правкой нескольких composition roots. Факты кода:

- **API.** `ApiRuntime` (`apps/api/src/api-runtime.ts`) сам создаёт `LocalBlobStore` и `PostgresCatalog`. `createProtocolServices` (`apps/api/src/protocol-services.ts`) связывает raw, Git LFS, npm и OCI с конкретным `LocalBlobStore` (`blobs.root` для staging, `blobs.checkSpace`), а не с портом. `registerProtocolRoutes` (`protocol-routes.ts`) регистрирует все протоколы безусловно: выключить неиспользуемый протокол нельзя.
- **Worker.** `apps/worker/src/runtime.ts` ещё раз создаёт `LocalBlobStore` и читает `process.env` сам, мимо типизированной конфигурации.
- **Резервные копии.** `FileVault.open` вызывается в `apps/backup/src/agent.ts`, `source.ts`, `vault-commands.ts` и `packages/infrastructure/src/vault-setup.ts`. Содержимое попадает в точку целыми blob через `BlobStore` с проверкой SHA-256 ([ADR 0054](0054-built-in-backup-vault.md)).
- **Маршрутизация хранилищ.** Порт `BlobStore` (`packages/application/src/ports.ts`) уже несёт необязательный `backendId`, а `RoutedBlobStore` (`packages/infrastructure/src/routed-blobs.ts`) — список `StorageTarget`, но приложения его не используют (только `tests/storage-routing.test.mjs`). Жизненный цикл хранилища он узнаёт утиной типизацией (`hasLifecycle`, `isCollectable`).
- **Инвентаризация маршрутов.** `apps/api/src/contract-guard.ts` вручную перечисляет исключения для `/v2/*`, `/lfs/:repository/...` и `/npm/:repository/*`. Флаги `GET /api/v1/capabilities` (`service-routes.ts`) заданы руками.
- **Вход.** `IdentityStore` (`packages/application/src/identity.ts`) объединяет пароль, пользователей, группы и токены; `AccountOrigin` — только `'administrator' | 'self-registration'`.
- **Схема.** Одна линейная последовательность миграций (`SCHEMA_VERSION = 41`, `packages/infrastructure/src/schema-version.ts`, таблица `arkvory_migrations`). На ней держатся проверка схемы ADR 0059 и реестр таблиц копии `backup-tables.ts`. Таблицы протоколов имеют префиксы `arkvory_oci_*`, `arkvory_lfs_*`, `arkvory_npm_*`.
- **Контрактные тесты.** Общего набора для реализаций `BlobStore` нет: `tests/local-blobs.test.mjs` проверяет только локальную реализацию. Принцип LSP из AGENTS.md ничем не проверяется.
- **Подпись.** Проверка minisign есть только в `apps/deploy/src/release-signature.ts`; `apps/deploy` зависит лишь от `packages/contracts`.
- **Границы.** Пакеты и связи задаёт `config/architecture.json`, `.dependency-cruiser.cjs` строит правила из него, `scripts/policy/inventory.mjs` отклоняет незарегистрированные workspace.

## Решение

### 1. Что такое модуль

Модуль — описание (`ModuleDescriptor`) и код, связанный с портами ядра через это описание. Источников два:

- **встроенный** — код в слоях репозитория, описание перечислено в явном списке корня (`apps/<root>/src/modules.ts`);
- **внешний** — подписанный пакет ProAnimaStudio, установленный по ADR 0078 и загруженный загрузчиком ядра после проверки подписи и хешей.

Инварианты:

- **Нет загрузки произвольного кода.** Конфигурация выбирает модули из встроенных и установленных подписанных и задаёт их параметры. `import()` с вычисляемым аргументом разрешён только в загрузчике ADR 0078 (п. 3.3); остальное проверяет policy-тест.
- **Нет service locator.** Модуль получает только зависимости, объявленные в `requires`, явным параметром `create`. Полную композицию модулю не передают (как обработчикам по ADR 0030).
- **`domain` и `application` о модулях не знают.** Порты остаются у потребителя (DIP). Адаптеры `infrastructure` связывают внутренние порты с типами API расширений.
- **Внутренние типы не публикуются.** Внешний модуль видит только типы `extension-api`. Рефакторинг `application` и `infrastructure` не меняет контракт модулей; меняется только адаптер.

### 2. Пакеты

**`packages/extension-api`** (`@proanima/arkvory-extension-api`) — стабильный публичный контракт модулей. Переносимый: без Node и сторонних пакетов, `allowed: []`, входит в правила `pure-core-no-external-runtime` и `portable-layers-no-node`. Содержимое:

- `EXTENSION_API_VERSION` (semver) и разбор манифеста `parseModuleManifest(input: unknown)` с машинными кодами ошибок;
- `ModuleDescriptor<Point, Config, Context, Instance>`: `manifest`, `parseConfig(input: unknown): Config` (ошибка `ModuleConfigError` с кодом и JSON-путём, без значений), `create(context, config)`. До `start` модуль не выполняет сетевого и дискового I/O;
- `ModuleLifecycle`: `start(signal)`, `drain(deadlineMs)`, `stop()` (идемпотентен, вызывается и после неудачного `start`), `health()` (`ok | degraded | failed` и код);
- чистая `planModules(descriptors, selection, hostVersion)` (п. 3);
- интерфейсы точек расширения (п. 5) и порт `LicenseView` (ADR 0078, п. 6.5). Потоки байтов — `AsyncIterable<Uint8Array>` и `AbortSignal`; размеры и смещения — `number` с проверкой `Number.isSafeInteger` на границе, 64-битные значения в wire — десятичные строки;
- клиентские интерфейсы: `TransferExtension` (п. 5.2) и `McpToolContribution` (ADR 0081).

**`packages/extension-testkit`** (`@proanima/arkvory-extension-testkit`) — контрактные наборы (п. 7). Node разрешён, `allowed: ["packages/extension-api"]`. Код продукта его не импортирует; только тесты ядра и тесты внешних модулей.

**`packages/signing`** (`@proanima/arkvory-signing`) — проверка minisign и встроенные открытые ключи модулей и лицензий (ADR 0078). `allowed: []`, использует `node:crypto`. Проверка подписи релизов переезжает сюда из `apps/deploy/src/release-signature.ts`; ключи релизов остаются в `apps/deploy/src/release-keys.ts`.

Новые связи в `config/architecture.json`:

| Потребитель                                                | Добавляется                              |
| ---------------------------------------------------------- | ---------------------------------------- |
| `packages/infrastructure`                                  | `extension-api`, `signing`               |
| `apps/api`, `apps/worker`, `apps/scheduler`, `apps/backup` | `extension-api`                          |
| `packages/sdk`                                             | `extension-api` (только клиентские типы) |
| `apps/cli`                                                 | `extension-api`, `signing`               |
| `apps/deploy`                                              | `extension-api` (манифест), `signing`    |

`domain`, `application`, `contracts` и `web` новых связей не получают.

**Версии.** `extension-api` и `extension-testkit` версионируются semver независимо от релиза ядра:

- удаление или несовместимое изменение экспорта — новая major-версия и ADR. Ядро поддерживает текущую major и предыдущую не меньше двух минорных релизов ядра после выхода новой;
- новый экспорт или необязательное поле — minor;
- снимок публичных деклараций (`packages/extension-api/api-report.d.ts`) хранится в репозитории. Policy-тест сравнивает его со сборкой и требует повышения версии нужного уровня.

**Публикация.** Оба пакета выпускаются tarball-файлами в релизе GitHub `ProAnima/Arkvory` — официальном источнике по LICENSE §2. `private: true` в манифестах остаётся (ADR 0061). Приватный репозиторий ставит точную версию по URL с `integrity`. Публикация в реестр npm — только отдельным решением владельца (ADR 0078, «Открытые вопросы», п. 2). Код пакетов остаётся под LICENSE ядра.

### 3. Реестр, конфигурация и план

- В каждом корне один явный список встроенных модулей: `apps/api/src/modules.ts`, `apps/worker/src/modules.ts`, `apps/backup/src/modules.ts`. Внешние модули добавляет загрузчик из `modules/<id>/<version>/` по набору, записанному `arkvory module install` (ADR 0078, п. 4).
- Выбор и параметры читаются из `ARKVORY_MODULES_FILE` (JSON `{"format": 1, "modules": {"<id>": {"enabled": true, "config": {...}}}}`) только в `loadConfig` корня. Неизвестный `id`, поле или нечитаемый файл останавливают запуск до захвата хранилища. Секреты в файле не хранятся, только пути к файлам секретов. Без файла поведение равно сегодняшнему: локальное хранилище, файловое хранилище копий, все протоколы включены, внешние модули выключены.
- `planModules` проверяет: уникальные `id`; известные точки расширения и `format`; совместимость `extensionApi` модуля с версией ядра; модули ядра с `core: true` включены; каждое `requires` закрыто `provides`; префиксы маршрутов, метрик и таблиц не пересекаются и принадлежат модулю. Результат — порядок запуска (топологический по `requires`, при равенстве по `id`), обратный порядок остановки и отпечаток плана: SHA-256 версии ядра, списка `(id, version, sha256 пакета, enabled)` и нормализованной конфигурации без путей к секретам. Хеш передаёт вызывающая сторона.
- **Один план на установку.** Процесс записи сохраняет отпечаток в `arkvory_module_plan` (одна строка, expand-only). Шлюз чтения, worker и агент копий с другим отпечатком не готовы (`module_plan_mismatch`); сравнивается отпечаток совместимости без версий встроенных модулей (см. «Уточнения реализации», «Два отпечатка плана»). Включение модуля нескольких ролей — перезапуск всех процессов, как смена `ARKVORY_MIRRORS_FILE`. `arkvory configure --module <id> [--module-disable] [--module-config <file>]` пишет файл и перезапускает службы с откатом по образцу `--webhook`.

### 4. Жизненный цикл

Порядок в корне: разбор конфигурации всех модулей (без I/O) → `planModules` → `create` → `start` в порядке плана с сигналом остановки процесса → регистрация маршрутов → готовность. Ошибка любого шага останавливает уже запущенные модули в обратном порядке; это расширение отката `ApiRuntime`. При остановке: прекращение приёма работы, `drain` с общим сроком, `stop` в обратном порядке, затем закрытие пулов.

Готовность: `failed` у модуля `core` или у модуля, нужного включённому модулю, снимает процесс с готовности. `failed` или `degraded` у необязательного модуля видны в метриках и `system/modules`, но процесс остаётся готовым. Модуль с `dataClass: layout`, который не загрузился, переводит процесс в `degraded`, а не в `failed`: данные ядра продолжают обслуживаться (ADR 0078, I1). Метрики `arkvory_module_info{module,kind,source}` и `arkvory_module_up{module}`; свои метрики модуль публикует только под `metricPrefix`, реестр отклоняет чужие имена.

### 5. Точки расширения

Каждая точка нейтральна: у неё есть реализация в ядре или тестовая реализация в `extension-testkit` (ADR 0078, п. 1.4).

**5.1. Хранилище (`storage-backend`).** Экземпляр — порт хранения в форме `BlobStore` (неизменяемая публикация, `putPart`/`readParts`, `put`, `verify`, `read` с Range, `exists`, `duplicate`), явный `StorageLifecycle` (`initialize`, `identity`, `ready`, `checkSpace`) и `StagingArea` вместо `blobs.root`. Утиная типизация `RoutedBlobStore` убирается.

- Каждый опубликованный blob помнит `backendId`; чтение всегда идёт в хранилище-владельца.
- Метод `acceptsWrites()` хранилища говорит, принимает ли оно новые данные. Маршрутизация новых записей выбирает хранилище по политике и при `false` возвращается к хранилищу ядра (ADR 0078, L4).
- Контекст сообщает режим: `full` или `read-only`. В `read-only` хранилище обязано обслуживать чтение, проверку и экспорт и отказывать в записи кодом `read_only`.
- Модуль объявляет `dataClass` (ADR 0078, п. 2). Для `layout` обязательны L1–L7 ADR 0078 и наборы `blob-store` и `readability`.

**5.2. Возможности передачи.** Сервер объявляет, клиент выбирает; обычная передача ядра всегда доступна.

- Модуль с точкой `transfer` объявляет возможность `{name, versions}` и маршруты под своим префиксом. `GET /api/v1/capabilities` получает необязательное поле `transfer: [{name, versions, module, prefix}]` (аддитивно, схема в `contracts`).
- Маршруты внешних модулей — только под `/api/ext/<id>/v<major>/`. Модуль описывает их нейтрально (`ModuleRoute`: метод, путь, `operationId`, действие ACL, лимит тела, потоковый обработчик с `AbortSignal`). Ядро само выполняет аутентификацию, проверку действия по ACL репозитория, допуск, бюджеты полосы ([ADR 0008](0008-gateway-bandwidth-budgets.md)) и контракт ошибок. Fastify модулю не виден.
- Контрактный guard сверяет зарегистрированные маршруты модуля с его манифестом; публичный контракт `/api/v1` от включения модуля не меняется. Модуль поставляет фрагмент OpenAPI своих маршрутов, его отдаёт `GET /api/v1/system/modules/{id}/openapi` (глобальный администратор).
- Клиент: SDK принимает в параметрах клиента список `TransferExtension` (`name`, `versions`, обёртки скачивания и загрузки). SDK пересекает список с `capabilities.transfer`, выбирает наибольшую общую версию и при отказе расширения возвращается к обычной передаче, кроме режима `strict`. Итоговые размер и SHA-256 дескриптора SDK проверяет сам, независимо от расширения. Бесплатный SDK и CLI не содержат реализаций расширений, только эту точку.

**5.3. Очистка и хранение.** `GcParticipant`: модуль получает уведомления о логическом удалении (правила хранения, ADR 0035) и удаляет свои объекты только через допуск удаления ядра (барьер 18471/18 и закрепления копий ADR 0054). Повтор `collect` идемпотентен. Пока модуль не загружен, очистка его хранилища остановлена (ADR 0078, L5).

**5.4. Резервные копии и восстановление.** По умолчанию модулю ничего не нужно: blob попадают в точку через путь чтения в форме ядра. `BackupParticipant` нужен, только если у модуля есть свои данные:

- `tables` — таблицы модуля в порядке, безопасном для внешних ключей, для логического экспорта; capture отказывает при таблице с префиксом модуля, не перечисленной в реестре;
- `section` — необязательный раздел точки: потоковый экспорт и импорт с манифестом раздела (файлы, размеры, SHA-256), проверка раздела для `verify --deep`;
- раздел добавляется, только если точка остаётся восстановимой ядром (ADR 0078, I2): манифест точки перечисляет модуль и SHA-256 пакета, пакет кладётся в точку, восстановление загружает модуль в режиме `restore` без лицензии.

**5.5. Зеркала.** Pull-зеркала ([ADR 0058](0058-pull-mirrors.md)) передают содержимое через SDK в worker. Серверный модуль с ролью `worker` может передать клиенту зеркала свой `TransferExtension`; базовая передача и проверка SHA-256 остаются за ядром. Если источник не объявил возможность, зеркало работает обычной передачей.

**5.6. Миграции.**

- Встроенные модули владеют шагами в общей последовательности ядра (`SCHEMA_VERSION`), таблицы `arkvory_<id>_*`. Миграции применяются независимо от включения модуля: схема одинакова у всех установок релиза.
- Внешние модули ведут свою последовательность в `arkvory_module_migrations(module_id, step, checksum, applied_at)`, таблицы только `arkvory_x_<id>__*` (дефисы id — `_`, см. «Уточнения реализации»). Шаги выполняет мигратор ядра под той же advisory-блокировкой. Состояние схемы установки — `SCHEMA_VERSION` и карта `{module: step}`. Его записывают журнал обновлений ADR 0059 и манифест точки копии; восстановление выполняет `migrate({upTo})` ядра и шаги модулей из пакетов в точке.
- Правила expand/contract те же. Выключение и удаление модуля схему не трогают. Удаление таблиц модуля — отдельная явная команда после удаления модуля, не в этом ADR.

**5.7. Протоколы.** Встроенные протоколы регистрируют маршруты внутренним регистратором `apps/api` с префиксами (`/v2`, `/lfs`, `/npm`). Исключения `contract-guard.ts` строятся из префиксов включённых модулей вместо ручного списка. Префиксы в корне адресного пространства есть только у встроенных модулей; внешние — только `/api/ext/<id>/` (п. 5.2). Операции встроенных модулей в `/api/v1` описаны в `contracts` статически; если модуль выключен, guard считает их ожидаемо отсутствующими, ответ — 404 `not_found`.

**5.8. Провайдеры входа.** Из `IdentityStore` выделяется узкий порт `ExternalAuthenticator` (учётные данные или код авторизации → внешний субъект и группы) и `AccountOrigin` `external:<provider>`. Вход по паролю — встроенный модуль `core`. Сессии и сервисные ключи проверяются локально, провайдер нужен только при входе: хранилище не зависит от внешних систем для авторизации. Каждый провайдер — свой ADR.

**5.9. Приёмники событий.** `EventSink.deliver(event, signal)` → `delivered | retry(after) | rejected(code)` (ADR 0080, п. 6).

**5.10. Метрики и состояние.** `metricPrefix` модуля, `health()`, событие `module.health.changed` (ADR 0080).

**5.11. Клиентские модули.** `arkvoryctl` загружает подписанные клиентские пакеты (`side: client`, ADR 0078) после той же проверки подписи и хешей. Клиентский модуль может дать `TransferExtension` (п. 5.2) и инструменты MCP через `McpToolContribution` (ADR 0081). Консоль внешний код не загружает.

**5.12. Сведения о лицензии.** Модуль, которому нужен `LicenseView`, объявляет `requires: ["license"]`. Порт только читает (ADR 0078, п. 6.5).

### 6. ACL и безопасность

- ACL проверяет сервер: маршрут модуля объявляет действие, ядро проверяет его по действующему `Principal`. Своей модели прав у модуля нет.
- Модуль с исходящими соединениями объявляет `egress` и получает только `createEgressPolicy` ядра (SSRF-правила ADR 0069). Расширить политику через API нельзя.
- Изоляции внутри процесса нет и не обещается (ADR 0078, п. 7).

### 7. Контрактные наборы (LSP)

`extension-testkit` содержит наборы — функции, принимающие фабрику реализации:

- `blob-store` — неизменяемость, проверка при повторе `put`, точная длина чтения с Range и частями, отмена через `Cancellation` и `AbortSignal`, поведение после `stop`, повтор `collect`, машинные коды ошибок, режим `read-only`;
- `readability` — сценарии L1–L7 ADR 0078;
- `vault` (`CaptureVault`, `ReadableVault`, `MaintainedVault`), `backup-participant`, `gc-participant`;
- `transfer-extension` — согласование версий, откат к обычной передаче, отказ при неверном SHA-256, отмена;
- `module-route` — ACL, лимит тела, отмена, коды ошибок;
- `event-sink`, `identity-provider`.

Реализации ядра подключают те же наборы тестовыми файлами из `config/gates.json`. Policy-тест сопоставляет каждую точку расширения с набором. Реализации, которым нужна внешняя инфраструктура, проверяются в гейте с контейнером; отсутствие контейнера — невыполненная проверка. Внешние модули проходят наборы в CI своего репозитория; это условие подписи пакета.

## Альтернативы

- **Только встроенные модули, без загрузки** (прежний черновик этого ADR). Не выполняет решение владельца ADR 0078: платный код не может жить в публичном репозитории.
- **Публиковать внутренние порты `application` как контракт модулей.** Каждый рефакторинг ядра ломал бы модули; контракт не был бы semver-стабильным.
- **Плагины с диска без подписи.** Выполнение непроверенного кода в процессе с ключами и БД.
- **DI-контейнер или service locator.** Запрещено AGENTS.md; связи становятся невидимыми для dependency-cruiser.
- **Отдельные сервисы на модуль.** Нет измеренной необходимости; появились бы сеть, авторизация между сервисами и восстановление.
- **Одна последовательность миграций и для внешних модулей.** Номера пришлось бы согласовывать между репозиториями, а релиз ядра зависел бы от релиза модуля.
- **Маршруты внешних модулей внутри `/api/v1`.** Публичный контракт менялся бы от установленного набора модулей; OpenAPI и SDK ядра перестали бы быть одинаковыми у всех установок.

Версия в `package.json` пакета равна константе.
- **Описание модуля** — `ModuleDescriptor<Context, Config, Instance>` без параметра `Point`: точка — `manifest.kind`, типы экземпляров точек появятся с их первыми реализациями (X2 и далее). `describeConfig(config)` даёт нормализованную конфигурацию для отпечатка; исключить из неё секреты и пути к ним — обязанность модуля. `drain(budgetMs)` получает оставшийся бюджет в миллисекундах.
- **`planModules(candidates, host)`.** Хост передаёт `coreVersion`, `extensionApi`, префиксы маршрутов ядра (`/api/v1/`, `/health/`, `/console/`) и функцию SHA-256. Результат — план или все найденные проблемы с машинными кодами: `invalid_manifest` (с JSON Pointer и причиной), `duplicate_id`, `incompatible_api`, `core_disabled`, `core_not_builtin`, `invalid_package`, `missing_requirement`, `duplicate_provider`, `requirement_role_mismatch`, `requirement_cycle`, `route|metric|table_prefix_overlap`, `route|metric|table_prefix_not_owned`. Сверх п. 3: у capability один поставщик; поставщик работает во всех ролях потребителя; несовместимый `extensionApi` отклоняется и у выключенного модуля; префиксы таблиц сравниваются у всех модулей (миграции встроенных не зависят от включения), маршрутов и метрик — только у включённых. Подписанный модуль (и любой будущий источник, кроме `builtin`) использует только `/api/ext/<id>/v<major>/` и `arkvory_x_<id>__` (дефис → `_`), встроенные модули в эти пространства не заходят. Двойное `_` завершает id, а id не содержит двойного и концевого дефиса (`MODULE_ID_PATTERN` строже `[a-z][a-z0-9-]{1,31}` ADR 0078, п. 3.1): так имена `foo` (`arkvory_x_foo__`) и `foo-bar` (`arkvory_x_foo_bar__`) не начинают друг друга, оба модуля ставятся вместе, а по имени таблицы виден владелец. Манифест, который не читается, но называет корректный id и диапазон `extensionApi`, не совместимый с ядром, даёт `incompatible_api`, а не `invalid_manifest`: новая minor-версия контракта может добавить поля и точки, и updater ADR 0078, п. 4 должен отличить несовместимый модуль от испорченного. `format` проверяется первым: манифест другого формата — `unsupported_format`, а не `unknown_field`. `requirement_cycle` называет только модули на цикле; модули, ждущие за ним, не упорядочиваются и не называются. Проверка «хотя бы одно `storage-backend` и `backup-vault`» не включена, пока нет описаний `local-storage` и `file-vault`.
- **Отпечаток** — SHA-256 канонического JSON (ключи по кодовым единицам UTF-16, как в RFC 8785) `{format, core, extensionApi, modules: [{id, version, source, kind, sha256, enabled, config}]}` в порядке `id` (`kind` добавлен во второй части X1). Встроенные модули несут версию релиза ядра; сборка разработчика (`dev`) — `0.0.0-dev`. Процессы установки сравнивают не его, а отпечаток совместимости (вторая часть X1, «Два отпечатка плана»).
- **Хост** (`apps/api/src/module-host.ts`, владелец — `ApiRuntime`). Разбор настроек и план — в конструкторе `ApiRuntime`, до пулов, хранилища и аренды; модули стартуют последним шагом `start()`, `stop()` отменяет старт. Неудачный или отменённый старт останавливает созданные модули, включая упавший, в обратном порядке; ошибки этих `stop` выбрасываются вместе с причиной (`AggregateError`, `cause` — ошибка старта). Старт, завершившийся после отмены, откатывается, а не возвращается. При закрытии — отмена старта и ожидание его завершения, затем `drain` с общим бюджетом 10 с, `stop` каждого модуля в обратном порядке и только потом пулы БД. `health()` читается как unknown: исключение или ответ вне контракта — `failed` (`health_unavailable`, `health_invalid`); отклонённый промис асинхронного `health()` перехватывается. Встроенные протоколы своих ресурсов пока не держат: маршруты регистрирует `registerProtocolRoutes`, сервисы — `createApiServices`, жизненный цикл модуля пуст, состояние `ok`.
- **`GET /api/v1/system/modules`** — `{extensionApi, fingerprint, modules: [{id, version, kind, source, core, enabled, roles, running, health}]}`, `health` — в ответившем процессе, `null` там, где модуль не работает. `kind`, `source` и `health.status` в схеме — открытые строки (известные значения в описании), чтобы новые точки и состояния ADR 0078 (`revoked`, `unavailable`) добавлялись аддитивно. `dataClass`, id ключа подписи и состояние лицензии появятся в O1–O4. Тег `System`: раздел справочника `system`, поверхность `discovery`, видимость `administrator`.
- **Снимок деклараций** `packages/extension-api/api-report.d.ts` — все собранные `.d.ts` пакета подряд, отформатированные Prettier (`node scripts/extension-api-report.mjs --write`). Тест сверяет снимок со сборкой и версию манифеста с `EXTENSION_API_VERSION`; уровень повышения версии оценивает review, автоматического сравнения уровней нет. Снимок исключён из ESLint и dependency-cruiser как собранный вывод.

Ядро пока не реализует ни одной службы (`PROVIDED_HOST_SERVICES = []`), поэтому любой `uses` у включённого модуля отклоняется `service_unavailable`, а `context.services` — пустой объект.

Хост строит контекст на каждый модуль непосредственно перед `create`: `mode` — `full` у процесса записи и `read-only` у шлюза, `signal` — отмена старта и остановка процесса. `ModuleLog.write(level, {code, subject?, durationMs?, count?})`: код `[a-z][a-z0-9_.]{0,63}` пишется как `module.<code>` с полем `module`, `subject` — идентификатор без `/` и `:` (не путь и не URL), неверная запись, в том числе с уровнем вне `debug`, `info`, `warning`, `error`, заменяется `module.log_invalid`; не больше 50 записей за 10 с на модуль, первая отброшенная даёт `module.log_suppressed`. `ModuleMetrics` — `counter`/`gauge` без меток, только под `metricPrefix`, до 32 рядов на модуль, имя занимается один раз; модуль без префикса метрик получает `TypeError`. `ApiModuleContext = ModuleContext<ApiServices>`.

Тест копирует сборку, меняет внутренние декларации и проверяет, что снимок не изменился, а изменение публичной его меняет.
- **Список встроенных модулей — в `packages/infrastructure`** (`builtin-modules.ts`, план с выбором оператора — `module-plan.ts`), а не в `apps/api/src/modules.ts`: план и отпечаток — одни на установку, и worker должен посчитать тот же отпечаток, что API, а приложения не импортируют друг друга. `infrastructure` получила связь с `extension-api` (п. 2), `apps/worker` её не получила: он вызывает только функции `infrastructure`. В `apps/api/src/modules.ts` остался контекст модулей API.
- **`ARKVORY_MODULES_FILE`** — `{"format": 1, "modules": {"<id>": {"enabled": true|false, "config": {...}}}}`; `modules` и `config` необязательны, `enabled` обязателен. Читают `loadConfig` API и запуск worker до захвата хранилища и блокировки worker. Неизвестное поле, id вне `MODULE_ID_PATTERN`, больше 256 модулей, файл больше 1 МиБ, нечитаемый файл или JSON, модуль, которого нет в релизе, ошибка `parseConfig` модуля и отказ плана (например, выключение `upack` или `raw` — `core_disabled`) останавливают запуск. Путь к файлу абсолютный: службы стартуют в каталоге текущего релиза, и относительный путь потерялся бы при следующем обновлении. Файл читается не дальше 1 МиБ + 1 байт. Сообщения называют JSON Pointer поля и id, совпадающие с `MODULE_ID_PATTERN`, но не значения; проблема стоит перед указателем, а не после двоеточия, потому что `startupReason` скрывает слово после `token:` или `key:`. Отказ плана (`ModulePlanError`) попадает в `startup.failed` и `worker.unavailable` с кодами и id модулей.
- **Выключенный протокол.** `registerProtocolRoutes` не регистрирует маршруты выключенных `lfs`, `npm`, `oci`; их пути отвечают общим 404 `not_found` (`route_not_found`) обработчика неизвестных путей. Таблицы, данные, обслуживание (`registry.expireUploads`) и работа worker с зеркалами образов и пакетов не меняются: выключение убирает поверхность, а не данные. Guard контракта больше не держит ручной список `/v2/*`, `/lfs/...`, `/npm/...`: маршрут под префиксом включённого модуля процесса исключается из инвентаризации `/api/v1`, маршрут вне префиксов проверяется как раньше (поэтому маршрут выключенного протокола был бы «undocumented»), а префикс включённого модуля без единого маршрута — ошибка `API route drift`. Точные исключения `/console/*` остались.
- **`capabilities.modules`** — `[{id, kind}]` включённых модулей роли ответившего процесса в порядке `id`; необязательное поле схемы `getCapabilities`, SDK возвращает его, только если сервер его прислал.
- **Один план на установку.** Миграция 43 (`SCHEMA_VERSION = 43`, expand-only) создаёт `arkvory_module_plan(singleton, compatibility_fingerprint, fingerprint, recorded_at)`; таблица вне копий (`excludedTables`): процесс записи восстановленной установки записывает свой план при старте. Процесс записи пишет оба отпечатка после захвата хранилища и аренды, до старта модулей. Шлюз чтения сравнивает отпечаток совместимости в каждой проверке готовности (`/health/status` с кэшем 1 с, `/health/ready`) и при отличии или отсутствии строки отвечает 503 `unavailable` с причиной `module_plan_mismatch`. Worker сверяет план, захватив блокировку worker; при отличии он отпускает блокировку, чтобы резервный worker с планом процесса записи взял работу, и смотрит снова раз в 5 с (`worker.module_plan_mismatch` один раз, работу не берёт), а во время работы сверяет план раз в 30 с: при смене плана процессом записи пишет `worker.module_plan_changed` и останавливается с кодом 1, чтобы служба перезапустила его с новым файлом. Worker тоже сравнивает только отпечаток совместимости. Шлюзы и worker релизов до этого не проверяют план.
- **Два отпечатка плана.** Первая версия сравнивала полный отпечаток, а встроенные модули несут версию релиза ядра. Тогда любое обновление ядра, даже исправление без миграции, делало шлюзы чтения и worker прежнего релиза неготовыми до их перезапуска, хотя раньше при таком обновлении процесса записи они продолжали обслуживать. Версия встроенного модуля здесь лишняя: встроенные модули меняются только вместе с ядром, а обновление, меняющее схему БД, и так останавливает прежние процессы точной проверкой версии схемы (`ready()` требует ровно `SCHEMA_VERSION` своего релиза, ADR 0059). Поэтому `planModules` считает два отпечатка:
  - `compatibilityFingerprint` — в чём процессы установки должны совпадать: SHA-256 `{format, scope: "compatibility", modules: [{id, source, kind, enabled, config, line}]}` в порядке `id`. `line` у встроенного модуля — `null`, у остальных — линия совместимости версии модуля по правилам caret: major с 1.0.0, `0.minor` ниже, `0.0.patch` у 0.0.z. Версий ядра и API расширений, SHA-256 пакета в нём нет: каждый процесс проверяет совместимость модулей со своим хостом сам, а версии одной линии обещают работать с теми же данными и настройками. Поля `compat` в манифесте нет и не заводим: линии версии достаточно, пока у модулей нет своих миграций; уровень миграций модуля появится с загрузчиком (этап X4) и будет проверяться, как схема ядра, картой шагов модулей (п. 3, «Последствия»). Версии возможностей `provides` (ADR 0083, п. 15) войдут сюда так же, своей линией.
  - `fingerprint` — полный, как раньше, плюс `kind`: версии ядра, API расширений и модулей, SHA-256 пакета. Справочный: точная сборка плана, меняется с каждым релизом; готовность его не сравнивает.
  - Готовность шлюза чтения и worker сравнивает только `compatibilityFingerprint`. Обновление без миграции снова идёт без остановки шлюзов: процесс записи нового релиза записывает тот же отпечаток совместимости, шлюзы и worker прежнего релиза остаются готовыми, их перезапускают из нового релиза позже. Выключенный или включённый модуль, другие настройки, источник или линия версии внешнего модуля дают `module_plan_mismatch` в любом релизе. Обязанность встроенного модуля — не менять `describeConfig` для тех же настроек между релизами без миграции, иначе шлюзы прежнего релиза станут неготовыми до перезапуска.
  - `GET /api/v1/system/modules` отдаёт оба: `fingerprint` сохранил имя и смысл (полный отпечаток), `compatibilityFingerprint` добавлен аддитивно; SDK возвращает его, только если сервер его прислал. `ModulePlan.compatibilityFingerprint` — аддитивное поле `extension-api` 0.2.0, ещё не выпущенной. Миграция 43 не выпускалась ни в одном релизе, поэтому столбцы таблицы изменены в ней, а не новой миграцией.
  - Проверки: unit — оба отпечатка устойчивы к порядку; смена только версии ядра и встроенных модулей сохраняет отпечаток совместимости и меняет полный; выключение модуля, другие настройки, источник и точка расширения меняют оба; у внешнего модуля отпечаток совместимости держится в пределах линии caret и не зависит от SHA-256 пакета. Integration — процесс записи релиза 1.6.1 и шлюз 1.6.0 с тем же планом: шлюз готов, полные отпечатки разные; шлюз 1.6.0 с другим набором модулей — 503 `module_plan_mismatch`; worker сборки `dev` при процессе записи 1.6.1 с тем же планом берёт работу.
- **Готовность по модулям.** `failed` у работающего модуля ядра или у поставщика capability, которую требует включённый модуль, даёт 503 с причиной `module_failed`; `degraded` и отказ необязательного модуля готовность не снимают. Причины `module_failed` и `module_plan_mismatch` добавлены в контракт ошибок `unavailable` (домен, `contracts`, консоль показывает общее «недоступно»).
- **Метрики** — `arkvory_module_info{module,kind,source}` (всегда 1) и `arkvory_module_up{module}` (1 при `ok`, 0 при `degraded` и `failed`) для модулей, которые выполняет процесс; у выключенного модуля рядов нет. Ряды самих модулей публикуются в том же `/health/metrics`.
- **Отложено:** `packages/signing` (вместе с O1; сделан, см. ниже), `arkvoryctl doctor`, `arkvory configure --module` с перезапуском и откатом (сейчас файл задаётся в `config/runtime.json` вручную), проверка плана агентом копий (у `apps/backup` нет модулей до X3), реализации служб хоста (этапы Y2–Y11 ADR 0083).
- **`packages/signing` сделан в этапе O1 ADR 0078** (его «Уточнения реализации (этап O1 и подготовка O2)»): проверка minisign, классы ключей, список отзыва, формат пакета и проверка установленного каталога. В отличие от п. 2 пакет зависит от `extension-api`: манифест пакета читается тем же `parseModuleManifest`. Связь со `signing` пока есть только у `apps/deploy`; `infrastructure` и `apps/cli` получат её с загрузчиком (X4) и клиентскими модулями (X5).

## Уточнения реализации (этап X2, вместе с Y3 ADR 0083)

- `local-storage` — встроенный модуль `storage-backend` с ролями `api`, `reader`, `worker`, `backup`; его настройки в `ARKVORY_MODULES_FILE` (`instances`) задают хранилища помимо `default`. Процессы строят экземпляры сами (`localStorageBackends`), `create` модуля ресурсов не держит, как у протоколов X1. Модуль `core: true`, пока он единственное хранилище ядра (отступление от таблицы п. 8, подробно — ADR 0083, «Y3»).
- `RoutedBlobStore` и его утиная типизация удалены: `StorageBackends` получает `StorageInstance` с явными `BlobStore`, `StorageLifecycle`, `mode` (`full | read-only`) и `acceptsWrites`; режим `read-only` отказывает в записи кодом `read_only`. Возврат новых записей в хранилище ядра — ADR 0083, N11.
- Наборы `blob-store` и `readability` пока не в `extension-testkit`: набор хранилища — `tests/contracts/storage-backend.mjs` с тестовым хранилищем `tests/contracts/directory-backend.mjs`; переносимых типов `storage-backend` в `extension-api` этот этап не добавляет. Типизированная конфигурация worker — только для хранилищ (`resources` читает `ARKVORY_MODULES_FILE`), остальной `process.env` worker — отдельно.

## Последствия

- Три новых workspace и новые связи в `config/architecture.json` (п. 2). Allowlist остальных пакетов не меняется.
- `extension-api` — публичное обязательство: снимок деклараций, semver, поддержка предыдущей major.
- Неиспользуемые протоколы можно выключить; поверхность атаки уменьшается.
- Схема зависит от набора внешних модулей; проверка схемы ADR 0059 и копии учитывают карту шагов модулей.
- Модули не изолированы в процессе; гарантии дают подпись, review, контрактные наборы и границы импортов.

## Проверка

- Unit `planModules`: дубли, неизвестная точка или формат, несовместимый `extensionApi`, незакрытое `requires`, пересечения префиксов маршрутов, метрик и таблиц, выключение `core`, порядок запуска и остановки, устойчивость отпечатка.
- Unit загрузчика конфигурации: неизвестные поля, `id` и типы отклоняются до I/O; сообщения без значений.
- Integration: выключенный `npm` отвечает 404 и отсутствует в `capabilities.modules`, guard проходит; шлюз чтения с другим отпечатком не готов; откат при неудачном `start` второго модуля останавливает первый; маршрут тестового внешнего модуля проверяет ACL ядром и не появляется в OpenAPI `/api/v1`; тестовое хранилище с `acceptsWrites() = false` переводит новые записи в `local-storage`, а старые читаются из своего хранилища.
- Контрактные наборы для `LocalBlobStore` и `FileVault`; намеренно сломанная реализация (неточная длина Range, запись в режиме `read-only`) набор не проходит.
- SDK: тестовое `TransferExtension` выбирается по пересечению версий, при отказе SDK переходит к обычной передаче, подмена байта даёт `checksum_mismatch` в обоих путях.
- Policy: `import()` с вычисляемым аргументом только в загрузчике; соответствие описаний и корней, таблиц модулей и реестра копии, точек расширения и наборов; снимок деклараций `extension-api` совпадает со сборкой; dependency-cruiser отклоняет импорт `extension-api` из `domain`, `application`, `contracts` и `web`.
