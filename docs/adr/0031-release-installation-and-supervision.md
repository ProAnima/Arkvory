# ADR 0031: автономная установка и обновление стабильными релизами

Статус: accepted. Owner: Ian Panaev. Дата: 2026-09-25.

Дополнение 2026-09-26: [ADR 0038](0038-update-notifications-and-control.md) добавляет зависимость deploy → contracts и ограниченный mailbox для удалённого управления, сохраняя привилегированный supervisor вне HTTP API.

Дополнение 2026-10-18: [разрешение модулей внутри каталога релиза](#confinement) — каждая поставляемая точка входа загружает код только из своего релиза и встроенных модулей Node.js.

Дополнение 2026-10-18: [целостность установки Windows](#windows-installation) — установщики запускают только проверенный runtime, каталоги кода принадлежат Administrators, существующий каталог релиза и этап Remote Setup используются только после проверки.

## Решение

`apps/deploy` — отдельная точка сборки управления установкой, без импортов других workspaces. Она не входит в HTTP API и не принимает удалённые команды от клиентов. Узкий UpdatePort отделяет порядок переключения от GitHub, файловой системы и менеджера служб. API/worker запускаются как отдельные процессы; их предметная архитектура не меняется.

В релиз включаются скомпилированные приложения, статический UI и production-зависимости из lockfile. Сборка на сервере и git pull в работающий каталог не выполняются. Runtime ZIP переносим между поддерживаемыми ОС: workspace links материализуются обычными файлами. Новая нативная зависимость потребует отдельных platform artifacts и пересмотра этого решения.

Код находится в releases/version; конфигурация, секреты и данные — за пределами releases. Служба не может менять код и GitHub credential. Привилегии обновления принадлежат локальному администратору/планировщику. systemd и WinSW обеспечивают перезапуск API/worker; контейнерами управляет restart policy движка.

Обновления opt-in, только опубликованные stable GitHub Releases. Pin блокирует плановые обновления. Подмена уже установленной версии и downgrade запрещены. SHA-256 защищает от повреждения/несовпадения опубликованных файлов, но не заменяет подпись: доверенная граница — права публикации в репозитории и TLS GitHub. Токен чтения приватного репозитория хранится отдельно; при перенаправлениях не передаётся CDN.

## Переходы и отказ

Download → checksum → ограниченное безопасное извлечение → подготовка образа → journal/prepared → остановка → переключение installation.json → старт → несколько readiness probes и проверка процесса worker → committed. Один lock запрещает параллельные операции. Журнал и указатель записываются через fsync и rename; на POSIX синхронизируется родительский каталог. Windows не предоставляет эквивалент directory fsync через Node, поэтому после отключения питания требуется проверить журнал.

При той же схеме БД обновление не запускает миграции, что позволяет вернуть предыдущий код. При ошибке rollback пишется recovery-required. После аварии stale lock не захватывается автоматически: оператор проверяет процессы и журнал, затем запускает recover. Данные и старые релизы автоматически не удаляются.

Ошибка записи журнала после остановки служб не отменяет попытку rollback: сохранённая фаза prepared/stopped уже содержит предыдущую версию. Откат повторно останавливает службы, восстанавливает указатель и проверяет запуск. Если итоговый журнал записать не удалось, команда сообщает об этом как об ошибке и требует проверки перед повтором; успешный rollback не выдаётся за успешное обновление. При ошибках самого отката сохранение recovery-required выполняется по возможности, исходный отказ восстановления не подменяется ошибкой журналирования.

Команда развёртывания имеет deadline 15 минут. При превышении завершается дерево процессов: отдельная process group на POSIX, `taskkill /T /F` на Windows. Runner ждёт завершения дочернего процесса и подтверждения остановки дерева не более 10 секунд. Если подтверждения нет, автоматический rollback не продолжается, `operation.lock` сохраняется, а recovery-required пишется по возможности. Оператор проверяет оставшиеся процессы, состояние служб и журнал перед удалением lock и ручным восстановлением. На POSIX неубранные zombie-процессы также могут привести к такому консервативному результату. Остановка CLI не отменяет уже принятые задания Docker daemon или systemd: после timeout их состояние нужно отдельно сверить, даже если локальное дерево успешно остановлено.

Изменение схемы выполняет отдельный maintenance upgrade с явной ссылкой на запись о backup. Это подтверждение оператора, не автоматическая проверка качества копии. После начала миграции автоматический возврат старых бинарников запрещён: требуется завершить обслуживание либо восстановить согласованные БД/файлы.

Проверка readiness повторяет обычный отказ worker probe, но немедленно передаёт ошибку неподтверждённой остановки (включая цепочку cause) вызывающему updater. Успешный следующий probe не доказывает завершение предыдущего процесса и не разрешает снимать installation lock.

## Ограничения

Профиль один writer + один completion worker. Обновление имеет окно недоступности: активные потоки получают штатную остановку, затем могут потребовать resume со стороны клиента. Это не rolling update и не HA. Healthcheck не превращается в автоматический restart при любой ошибке БД/диска: restart policy относится к завершению процесса, мониторинг доступности остаётся отдельным.

ОС без systemd используют Compose или внешнего supervisor. Windows installer — x64; Linux glibc — x64/arm64. Для Podman нужен совместимый compose provider; его наличие не доказывает приёмку каждой реализации. TLS, backup и двухсерверное fencing требуют эксплуатационной настройки и проверки стенда.

## Дополнение 2026-10-18: разрешение модулей внутри каталога релиза {#confinement}

**Контекст.** Голое имя Node.js ищет в `node_modules` каждого родительского каталога до корня диска, затем в `~/.node_modules`, `~/.node_libraries` и `NODE_PATH`. Библиотеки поставки пробуют необязательные зависимости (`try { require(...) } catch {}`), которых в релизе может не быть, и найденный так файл выполнился бы в процессе службы или администратора. Каталоги поиска не обязаны принадлежать администратору: на Windows корень по умолчанию лежит под `%ProgramData%`, где любой пользователь создаёт папки; домашний каталог учётной записи службы на Linux — `data/`, доступный ей на запись. Правило «код в releases/version, служба не может менять код» без ограничения поиска не выполнялось.

**Решение.**

- Пакет `packages/resolution` (Node.js, без зависимостей) регистрирует хук `module.registerHooks` потока. Разрешено только `node:` и файлы под заданными корнями: реальный путь файла, на Windows без учёта регистра, корень в обеих формах пути (короткое имя 8.3 остаётся в JavaScript-форме). Остальное отклоняется до загрузки с кодом отсутствующего модуля (`MODULE_NOT_FOUND` для `require`, `ERR_MODULE_NOT_FOUND` для `import`): необязательная зависимость ведёт себя как неустановленная, сообщение называет отклонённый файл. Хуки — состояние потока, поэтому хук и корни одни на поток и общие для копий пакета в одном процессе (бандл `launcher.mjs` и точка входа релиза) под символом реестра.
- Каждая поставляемая точка входа первым импортом подключает `confine.js` своего приложения, до кода любой библиотеки: `apps/api` (`main`, `migrate`), `apps/worker` (`main`, `gc`, `scrub`), `apps/backup`, `apps/deploy` (`main` — `arkvory` и `arkvory-setup.mjs`, `launch` — `launcher.mjs`, `manage` — `manage.mjs`, `container`, `probe`, `remote-main` — Remote Setup), `apps/cli` (`arkvoryctl`). Несобранная точка входа (`<релиз>/apps/<app>/dist/<файл>.js`) разрешает свой релиз. Бандл разрешает только встроенные модули, пока его код явно не назовёт релиз: `launcher.mjs` и `container.js` — релиз роли (`runRole` без ограничения отказывает), `manage.mjs` — текущий релиз установки. Скрипты Remote Setup, выполняемые на сервере через `node -e`, сначала импортируют `confine.js` установленного релиза; релиз старше этого решения его не имеет и работает как раньше. Переменные окружения корней не добавляют. Каталог подписанного пакета добавляет загрузчик этапа X4 [ADR 0079](0079-extension-modules.md) — после всех проверок, перед импортом, по одному пакету (реальный путь `modules/<id>/<version>/`), а не весь `modules/`; его собственное, более строгое ограничение (только файлы того же пакета) сохраняется.
- Новый пакет разрешён `apps/api`, `apps/worker`, `apps/backup`, `apps/deploy` и `apps/cli`. Для `cli` это сознательное расширение правила «cli использует sdk и contracts»: пакет без зависимостей, не серверный код, а клиентские файлы запускают и администраторы. Файл пакета внесён в `COMPUTED_IMPORTS` политики: он импортирует `node:module`, но ничего не загружает.
- Определения служб очищают `NODE_PATH`: `UnsetEnvironment=NODE_PATH` (systemd: службы, база, программа обновления, юниты HA), `<env name="NODE_PATH" value=""/>` (WinSW), `ENV NODE_PATH=` (образ). `HOME` службы не меняется: `~/.node_modules` закрывает хук.
- Windows: `register-windows.ps1` при установке и восстановлении служб (не `-ServicesOnly`, правила — в `protect-windows.ps1`) передаёт группе Administrators (`takeown /A`) сам корень установки — владелец каталога всегда может переписать его DACL, а корень мог создать другой пользователь до установки; дерево данных не обходится. `%ProgramData%\ProAnima` над корнем по умолчанию тоже переходит Administrators и получает защищённый наследуемый DACL: SYSTEM и Administrators — полный доступ, Users — чтение. Если это ссылка (точка повторной обработки), скрипт отказывает до любых изменений: цель ссылки осталась бы у её владельца. Распространение наследуемых записей останавливается на защищённых дочерних каталогах, в том числе на корне: их ACL и дерево данных не затрагиваются. Другой родитель — выбор оператора, его права не меняются. От каталогов `node_modules` выше установки, доступных пользователям на запись, защищает только хук. На Linux корень `root:arkvory 0750` и `/opt` службе на запись недоступны, изменений нет.

**Почему здесь.** Это решение определяет `launcher.mjs`, `manage.mjs`, каталог `releases` и службы — границу, которую закрывает дополнение. [ADR 0060](0060-proanima-hub.md) отвечает за подпись и источник релиза, но не за то, что релиз загружает при запуске; [ADR 0078](0078-open-core-modules-and-licenses.md) и [ADR 0079](0079-extension-modules.md) — за модули. Ограничение кода подписанных модулей (X4) остаётся отдельным и более строгим.

**Ограничения.** `require.resolve` в Node.js 24 хуки не проходит: путь вне релиза он вернёт, но загрузка этого пути отклоняется. Хуки действуют в своём потоке: worker threads не ограничены; продукт запускает только поток watchdog, который ничего не разрешает, транспорты pino не используются. Код, выполняемый до точки входа (`NODE_OPTIONS` с `--require`/`--import`), задаёт администратор окружения службы. Статический граф ES-модулей несобранной точки входа Node.js разрешает и загружает до вычисления первого из них, то есть до регистрации хука; вычисляются они после `confine.js`, а CommonJS-модули графа загружаются при вычислении и проходят хук. Статический ES-импорт, который разрешился бы вне релиза, хук не остановил бы; такие импорты называют только пакеты, поставляемые в релизе, и gate `deployment` проверяет разрешение production-зависимостей упакованного релиза. Службы, `arkvory` и `manage.mjs` запускают точку входа релиза из бандла через `import()`, и весь её граф проходит хук. Каталоги кода внутри корня закрывает [дополнение о целостности установки Windows](#windows-installation); каталоги данных, созданные другим пользователем до первой установки, не перехватываются. Установки получают новые `launcher.mjs` и `manage.mjs` с обновлением; определения служб и права `%ProgramData%\ProAnima` меняются при установке или восстановлении служб.

**Проверки.** Unit `tests/resolution-confinement.test.mjs`: код, подложенный в родительский `node_modules`, домашний каталог и `NODE_PATH`, выполняется в неограниченном процессе и отклоняется в ограниченном (`require`, `import`, `import.meta.resolve`, загрузка пути из `require.resolve`); ссылка из релиза наружу, регистр на Windows, две копии пакета, корни; launcher и `manage` с подложенным кодом над установкой; каждая точка входа импортирует ограничение первой. Gate `deployment` (`tests/deployment/confinement.mjs`): в упакованном релизе без необязательной зависимости его библиотека без ограничения выполняет подложенный код, а `arkvory-remote.mjs`, `arkvoryctl.mjs`, `remote-main.js` релиза, `launcher.mjs`, `manage.mjs` и `arkvory-setup.mjs` работают, и подложенный код не выполняется. Gate `deployment-services` (Windows): ссылка на месте `%ProgramData%\ProAnima` отклоняется до изменений, корень другого владельца после регистрации принадлежит Administrators.

## Дополнение 2026-10-18: целостность установки Windows {#windows-installation}

**Контекст.** Правило «код в releases/version, служба не может менять код» опирается на то, что код установки принадлежит администраторам и запускается только проверенным. До установки корень и его дочерние записи может создать любой пользователь `%ProgramData%`. Требования: установщики запускают только Node.js, совпадающий с закреплённым; каталоги кода и файлы с учётными данными после установки принадлежат Administrators независимо от того, кто их создал; существующий `releases/<version>` используется только после сверки с проверенным архивом; этап Remote Setup ни в один момент не доступен на запись не-администраторам.

**Решение.**

- **Проверенный runtime.** `install.ps1` запускает Node.js только после проверки `runtime\node-v24.21.0-win-x64`: `node.exe` имеет SHA-256 из закреплённого архива (`scripts/native-dependencies.mjs` закрепляет тот же архив), каталог и `node.exe` — не ссылки, рядом только записи архива (Windows загружает библиотеки сначала из каталога исполняемого файла). Иначе скрипт скачивает архив, проверяет его SHA-256, распаковывает в новый каталог внутри защищённого `runtime`, проверяет его, переносит прежний каталог в `runtime\unverified-<id>` (он не запускается) и переключается на проверенный. Непроверенный runtime не запускается никогда. Каталог распаковки удаляется и после отказа; каталоги `runtime\fresh-*`, оставшиеся от прерванного запуска, удаляются перед новой распаковкой (без перехода по ссылкам). Закреплённый SHA-256 `node.exe` и список записей `$nodeEntries` берутся из того же архива, что закрепляет `scripts/native-dependencies.mjs`; обновление Node.js меняет их вместе, а упаковка нативного установщика (gate `native-package`) останавливается, если `node.exe` архива имеет другой SHA-256 или в архиве есть запись вне `$nodeEntries`.
- **Каталоги кода.** При установке и восстановлении служб (`register-windows.ps1`) и в нативном Setup до запуска кода из корня (`native/prepare.ps1`, затем `apply.ps1`) `protect-windows.ps1` оставляет `runtime`, `releases`, `config` и `modules` корня группе Administrators с защищённым DACL: SYSTEM и Administrators — полный доступ, LocalService — чтение и выполнение, NetworkService — чтение и выполнение `runtime`, если есть управляемая база (как выдаёт `database-windows.ps1`). Каталог, который ещё не в этом состоянии, передаётся Administrators целиком (`takeown /R`), записи внутри получают только наследуемые права; ссылки проверяются до и после обхода, поэтому `takeown` и `icacls` не выходят за каталог. Уже защищённый каталог Administrators не обходится: добавлять в него могли только они. Ссылка (junction или символическая ссылка) на месте каталога кода или внутри непроверенного каталога останавливает установку с понятной ошибкой; для самих каталогов — до изменения корня. Файлы с учётными данными защищаются после каталогов кода: Administrators сначала забирают каждый файл (`takeown /A`), потому что `github-token.txt` и `bootstrap.owner` в корне могли существовать до установки, а ссылка на их месте останавливает установку. Новая нативная установка удаляет существовавший до неё `bootstrap.owner` до того, как Setup запишет в него учётные данные владельца: дескриптор, открытый на прежний файл, их не прочитает. `install.ps1` поставляется отдельно и содержит идентичную копию этих правил (unit-тест сравнивает копии); он защищает `runtime` и `releases` в режиме служб, Compose сохраняет права корня ([ADR 0050](0050-windows-compose-engine-user.md)) и проверяет только ссылки. Новая нативная установка копирует runtime в защищённый каталог и останавливается, если там есть записи, которых Setup не поставляет.
- **Повторное использование релиза.** `stage()` использует существующий `releases/<version>` только если он совпадает с проверенным архивом релиза: архив читается снова, его SHA-256 проверяется, архив распаковывается в новый каталог сравнения, и деревья сравниваются по записям и байтам (кроме `release.json`). Ссылки и специальные файлы не совпадают никогда; на POSIX каждая запись принадлежит пользователю установки и доступна на запись только ему. Отличающийся каталог остаётся нетронутым, операция останавливается с ошибкой.
- **Этап Remote Setup.** На Windows каталог этапа создаётся вызовом `[IO.Directory]::CreateDirectory` с владельцем Administrators и защищённым DACL (SYSTEM и Administrators) в том же вызове, поэтому ни в один момент не доступен на запись другим; существующий путь останавливает шаг, результат проверяется после создания. Команда установки снова проверяет этап, копирует загруженный установщик в новый файл этапа, считает SHA-256 через дескриптор, который держит открытым только для чтения, и запускает эту копию. Копия удаляется на всех путях; удаление этапа убирает и копию, оставшуюся после разрыва соединения. Принимаются только пути этапа, который назвал `makeRemoteStage`. На Linux этап по-прежнему создаётся `mkdir` с `umask 077`, существующий путь — ошибка.

**Ограничения.** Обход каталога кода и проверка ссылок не атомарны относительно учётной записи, которой каталог ещё принадлежал: ссылка, созданная во время обхода, обнаруживается повторной проверкой и останавливает установку. Каталог, который Administrators не могут прочитать, останавливает установку: его нужно передать Administrators вручную. Существующие нативные установки сохраняют свой runtime; его защищают права каталога, сверка хеша с другой версией Setup невозможна. `service\`, `database\`, `launcher.mjs` и `manage.mjs` наследуют права корня, как раньше. Первое восстановление служб после обновления обходит каталоги кода один раз; дерево данных не обходится. Повторное использование релиза требует повторной загрузки архива.

**Проверки.** Unit `tests/windows-installation.test.mjs`: копии правил в `install.ps1` и `protect-windows.ps1` идентичны, порядок проверки runtime и защиты корня в `install.ps1`, `register-windows.ps1`, `native/prepare.ps1`, `protect-windows.ps1` в нативном пакете, архив `install.ps1` совпадает с закреплённым для упаковки, упаковка сверяет с ним SHA-256 `node.exe` и `$nodeEntries`. Unit `tests/release-staging.test.mjs`: повторное использование только совпадающего каталога; изменённый, лишний и отсутствующий файл, ссылка, чужие права на POSIX и каталог с подходящим `release.json` отклоняются. Unit `tests/remote-deployment.test.mjs`: создание этапа с защищённым дескриптором в одном вызове после проверки существования, порядок проверки этапа, копии, хеша и запуска, удаление только своих файлов. Gate `deployment-services` (только CI windows-2022/2025, от администратора): каталоги кода другого владельца после регистрации принадлежат Administrators с защищённым DACL, записи внутри только наследуют, файлы с учётными данными закрыты и принадлежат Administrators, владельцы в дереве данных не меняются; ссылка на месте каталога кода и внутри него останавливает регистрацию, цель не меняется; `install.ps1` заменяет непроверенный runtime, удаляет оставшийся каталог распаковки и запускает только проверенный `node.exe`; этап Remote Setup — защищённый каталог Administrators, повторное создание отклоняется, неверный хеш ничего не запускает, запускается проверенная копия, после удаления ничего не остаётся. Gate `native-install` (CI) выполняет новый `prepare.ps1` в настоящем Setup.
