# 0088. Лимит логических байтов хранилища

Хранилище может задать `logicalByteLimit(): string | null`: канонический uint64
или отсутствие предела. Это общая политика приёма, не механизм лицензирования.
Предел применяется ко всей установке и одному backend, независимо от репозитория.
Считается полный размер всех ещё не reclaimed загрузок, включая pending и
cancelled до очистки. Дедупликация не уменьшает логический размер.

Создание upload уже удерживает общий lockReservations до COMMIT. После проверки
идемпотентности ядро сравнивает счётчик backend + заявленный размер с текущим
пределом. Превышение выбирает default в той же транзакции; заранее выбранный
backend не является резервированием. Существующая загрузка сохраняет выбранное
хранилище и не учитывается повторно при повторе запроса или публикации.
Ранее принятые загрузки и чтение не отменяются при уменьшении предела.

Expand-миграция 51 добавляет счётчик и триггер INSERT/UPDATE/DELETE, включая
storage_backend и reclaimed. Удаление возвращает ёмкость только после очистки.
Пересчёт начального состояния исключает конкурентные записи в каталог; старые
writers поддерживают счётчик триггером, но не применяют новый предел. Поэтому
модуль, требующий ограничения, требует API 0.12 на всех writer-процессах.
Изменение SQL-схемы аддитивно; destructive cleanup не требуется.

Проверки: граница и нулевой предел, uint64 без Number, конкурентные создания
через разные подключения, разные репозитории, идемпотентность, уменьшение
лимита, публикация, отмена/очистка и счётчик после миграции.
