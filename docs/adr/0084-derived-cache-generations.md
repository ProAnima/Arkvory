# 0084. Поколения производного кеша модулей

Статус: proposed; реализация в отдельном PR, принятие и результаты проверок
фиксируются перед merge. Дата: 2026-10-19. Owner: Ian Panaev.

## Контекст

ModuleFiles 0.8 атомарно публикует один файл, но не группу. Локальные mutex,
LRU и счётчики не координируют API/worker/reader. Lock-файл с TTL не отличает
приостановленного владельца от мёртвого. Нужен нейтральный сервис для
восстанавливаемых производных данных, без зависимости ядра от форматов модулей.

## Контракт и границы

Extension-api 0.9.0 добавляет `derived-cache` и типы DerivedCache, CacheBuild,
CacheRead. Служба доступна только signed-модулям, объявившим uses: API/worker
строят и читают, reader только читает, backup её не получает. Плагины и builtin
не получают эту службу. Исходные данные и авторизация в кеше не хранятся.
Модуль проверяет текущие права перед каждым запросом; cache handle не даёт прав.

`begin(key, {bytes, files}, signal)` резервирует поколение, возвращает builder
либо null при занятом ключе/нехватке бюджета. Reader получает read_only.
Ключ — 1..256 UTF-8 байт; bytes — неотрицательный safe integer,
files — safe integer от 3 до 4096. Builder даёт create(name), commit(signal), abort(); имя
соответствует ModuleFiles, файлы эксклюзивны. Commit при открытых sinks — conflict.
`open(key, signal)` даёт pinned reader либо null. Reader: stat, read(range),
list(after, limit 1..1000), release. Никакого raw path, rename или remove наружу.
Отмена/закрытие/потеря владения терминальны для handle. Повтор release/abort
безопасен, abort не удаляет опубликованное поколение.

## Публикация и fencing

Каждое поколение имеет уникальные UUID namespace и owner, fence,
состояние building/ready/retired/deleting. Namespace не переиспользуется.
Fence монотонен только в пределах жизни строки entry: после удаления пустой
entry новый begin для того же ключа начинает с 1. Защита от старого builder
проверяет также уникальный UUID поколения, owner и building_id, а не один fence.
Метаданные и current_generation принадлежат PostgreSQL. Короткая транзакция
begin резервирует место и владельца, затем заканчивается до файлового I/O.
До первого mkdir БД фиксирует полный резерв поколения. Ядро записывает файлы
потоково и manifest; только после завершения и проверки файлов короткая
транзакция commit проверяет owner/fence, сохраняет manifestHash и переключает current.
Повтор после неопределённого результата commit проверяет то же поколение.
Общей транзакции PG/FS нет: orphan возможен, указатель на незавершённую группу — нет.

В `module-derived-cache/<module>` находится отдельное приватное пространство
ядра, недоступное через ModuleFiles. Новый builder не наследует retired namespace.
Запоздалый syscall старого владельца может оставить только недоступную сироту,
но не изменить новое поколение или опубликовать старое в PG. PG session loss
сам по себе не является физическим fencing файловой системы.

Общая module-data advisory lock используется только для коротких операций
admission/accounting. Нельзя держать её или PG-транзакцию вокруг callback модуля,
compute, потока, вложенного вызова ModuleFiles либо всего lifetime build.
Вложенный вход в тот же coordinator недопустим. Общий порядок блокировок
accounting → entry → generation задаётся адаптером и проверяется тестами.

## Формат и ограничение I/O в v1

SQL хранит состояние и полный резерв поколения, current pointer, owner/fence,
manifestHash и read_refs. Отдельных SQL-строк на каждый файл не требуется.
Физический корень — `module-derived-cache/<moduleId>`; внутри уникального
namespace поколения имена файлов плоские, вычислены хешированием имён модуля.
Никакое имя из ModuleFiles не открывает этот корень. Manifest связывает логические
имена с внутренними именами, размерами и хешами содержимого; ядро не знает
прикладных форматов модулей.

На builder допускается один открытый FileSink одновременно. Имя — не более
512 UTF-8 байт с правилами ModuleFiles. Manifest ограничен 4 MiB и 4093 записями;
оба предела проверяются независимо, до публикации. Он записывается во временный
файл, проходит fsync и атомарный rename с необходимой синхронизацией каталога.
Только затем PG commit сохраняет его хеш. Pending-группа никогда не видна reader.

В запросе резерва учитывается полный peak: содержимое всех файлов, manifest
и временные файлы. Для CacheFileSink в v1 принят запас T = 2 файловых слота;
бюджет слотов — `entries + 1 manifest + 2`, поэтому при лимите 4096 остаётся
не более 4093 entries. Это верхний предел, а не гарантированная вместимость:
меньший утверждённый бюджет или предел 4 MiB manifest уменьшает число entries.
Байтовый резерв также покрывает одновременно существующие временные и итоговые
копии, включая временный manifest; одних двух свободных файловых слотов мало.
Превышение резерва/лимита прерывает build, частичной публикации нет.

Reader загружает только bounded manifest и проверяет его по manifestHash из БД,
проверяет имена, размеры, хеши и число entries. Перед выдачей запрошенного range
он потоково проверяет полный хеш соответствующего файла, сохраняя pin/read_ref
на всё время проверки и выдачи. Большой файл целиком в память не загружается;
отмена действует и во время проверки. Это требует полного чтения файла даже
для малого range, но не требует знания формата его содержимого.

Сироты удаляются целыми поколениями; один проход cleanup обрабатывает не более
1000 файлов. Незавершённая очистка сохраняет состояние и полный charge до
подтверждённого удаления поколения. Перечисление физического каталога ограничено
страницей; не читать все orphan filenames в память одним вызовом.

## Общий бюджет

resources.dataMiB/dataFiles — один бюджет для legacy data/cache и derived cache,
не две независимые квоты. ModuleDataAccounting под существующей per-module PG
lock добавляет derived reservations из БД через reservedUsage. Derived begin
под той же lock читает legacy ledger и SQL reservations перед admission.
Физические поколения лежат отдельно и не учитываются второй раз как legacy.
При ошибке чтения общего бюджета запись запрещена, нулевой резерв не подставляется.

Reservation включает peak temporary + committed + manifest, а не только payload;
files включает служебные и временные файлы. Если публикация копирует файл,
одновременные копии обе учитываются. Oversized build отказывает до публикации;
ошибка не делает часть группы ready. Lost-owner reservation сохраняется до
подтверждения quiescence и завершения очистки. Reserve тома действует отдельно.
Очереди, sinks, readers, параллелизм, SQL-время, retries и страницы reconciliation
ограничены. Не сканировать весь каталог в память; перечисление не более 1000
файлов за страницу, поколения обрабатывать ограниченными порциями.
Остальные числовые runtime-лимиты (очереди, handles, параллелизм и таймауты)
фиксируются реализацией и проверками до merge.

## Readers и удаление

Open атомарно выбирает ready generation и закрепляет её: PG pin плюс persisted
read_refs исключают щель между выбором поколения и eviction. Handle читает
одну неизменяемую группу. Release прекращает потоки, дожидается I/O, закрывает
дескрипторы и лишь затем снимает persisted ref/pin. Нормальный close хоста
дренирует все операции и дескрипторы, затем отмечает owner quiescent.

**Потеря PG advisory pin не освобождает persisted read_refs, reservation или
физическое место.** Нельзя удалять файлы остановленного/неопределённого reader,
считая отсутствующий lock доказательством закрытия OS handles. После сбоя
неопределённые owner остаются quarantined до доверенного восстановления.
Eviction скрывает запись в PG, затем удаляет retired generation постранично;
charge снимается после подтверждённого удаления. Повтор безопасен. Windows
sharing violation не считается успешным unlink. Между HTTP-запросами pin нет:
следующий запрос снова проверяет ACL и идентичность контента, miss даёт fallback.

## Операторское восстановление

Это доверенная операция на хосте, не API модуля и не команда удалённого CLI.
Сначала применить миграции версии ядра и использовать её собранные пакеты.
Получить точный UUID uncertain owner из диагностики/метаданных. Записать
доказательство остановки и инкарнацию хоста/процесса в журнал работ оператора.

1. Остановить **все** хосты, которые могут обслуживать данное пространство,
   и подтвердить прекращение их процессов и файлового I/O; либо достоверно
   доказать завершение точной инкарнации owner и невозможность её возобновления.
   При недоступном узле выполнить и подтвердить инфраструктурное host fencing.
2. Удаление PG session, PID timeout и возраст строки доказательством не являются.
   Если доказательства нет, не запускать recovery: квота остаётся занятой.
3. С привилегиями оператора и уже настроенным ARKVORY_DATABASE_URL выполнить:

```sh
node scripts/recover-derived-cache.mjs --owner UUID --confirm-owner-stopped
```

Wrapper не выводит строку подключения, не угадывает PID, не запускает миграции
и не повторяет операцию автоматически. Без обоих аргументов отказывает.
Он вызывает внутренний `recoverDerivedCacheOwner(pool, ownerId,
{confirmedStopped: true})`. Функция проверяет UUID/состояние и должна неблокирующе
захватить owner lock, подтверждая отсутствие активного владельца, прежде чем
записать quiescence. Наличие lock означает отказ даже с флагом оператора.
Флаг — утверждение оператора о физической остановке, не замена этой проверки.

4. Возобновить reconciliation на новом хосте. Он освобождает подтверждённые
   read refs, дочищает namespace и возвращает quota только после удаления.
   Подтверждение owner не обещает немедленного освобождения места. Проверить
   итоговый статус/учёт и отсутствие старого процесса перед возвратом нагрузки.

Путь recovery и его отказные случаи обязательны для закрытия замечания о shared
cache eviction. Одних PG pins недостаточно; автоматическое освобождение
неопределённых owner не заявляется. Ошибка очистки сохраняет учёт и допускает
ограниченный retry; повтор подтверждения quiescent owner идемпотентен.

## Rolling update

Expand-миграция добавляет таблицы/индексы; ModuleFiles не меняет форму.
Сначала остановить все прежние хосты с дренированием I/O, затем применить
миграцию 49, обновить все участвующие хосты до extension-api 0.9 и активировать
совместимый подписанный модуль с новым uses. Смешанная работа старых и новых
хостов при этом переходе не поддерживается. Старые хосты не предоставляют службу, никакой
локальной имитации нет. Старые cache namespace не импортируются и не удаляются
при старте. Их чистят отдельно после остановки всех прежних участников.
Откат модуля сохраняет ядро с extension-api 0.9, схему 49 и новые namespace;
downgrade БД не выполняется. Возврат к прежней логике ModuleFiles допустим
только подписанным пакетом, явно поддерживающим API 0.9: диапазон `^0.8`
не совместим с 0.9. Старое ядро со SCHEMA_VERSION=48 откажет на БД версии 49;
перезапуск старого бинарника не является поддерживаемым откатом. Иначе требуется
контролируемое восстановление по отдельной проверенной процедуре.
Тест миграции 48→49 и reopen legacy-порта доказывает изоляцию namespace и общий
учёт квоты, но не downgrade или запуск старого бинарника на новой схеме.
Contract-удаление отдельно. Производный кеш не входит в backup;
restore не возобновляет owners прежней инкарнации установки.

## Приёмка

Контрактные и реальные multi-process проверки входят в зарегистрированные гейты;
отсутствие PostgreSQL не является успешным skip. До merge обязательны:

- конкурирующие builders, одинаковые/разные key, атомарная видимость группы;
- смерть до/после каждого файлового и PG шага, неопределённый commit;
- session loss, пауза и возобновление старого процесса: старый fence не публикует;
- reader против eviction, отмена и early exit, OS handles и Windows unlink;
- сохранение read_refs/reservation при потере PG pin; recovery отказывает живому
  owner, подтверждённая остановка позволяет reconciliation освободить место;
- общая legacy/derived квота при конкурентных admission, рестарте и cleanup;
- peak temporary/manifest, границы list/queue/handles, bounded memory и retries;
- rolling update/rollback и реальные модули поверх API/worker/reader, без подмены
  службы host-sim; независимая проверка результата и освобождения ресурсов.

Документ и контракт не подтверждают прохождение этих проверок. Результаты
фиксируются в PR; merge требует отдельного одобрения владельца.
