# 0080. События для внешних систем

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-17. Решение меняет публичный контракт (`/api/v1`, OpenAPI, SDK, CLI), добавляет таблицу событий с собственной политикой хранения и расширяет исходящую границу доверия [ADR 0069](0069-webhooks-over-change-feed.md). До решения владельца код не пишется. Связано с [ADR 0058](0058-pull-mirrors.md), [ADR 0077](0077-fleet-console.md), [ADR 0079](0079-extension-modules.md), планом этапа D [API_EVOLUTION](../API_EVOLUTION.md).

## Контекст

Внешним системам (CI/CD, агентам развёртывания, каталогам, оповещениям, ИИ-агентам по [ADR 0081](0081-mcp-and-agent-skill.md)) нужен один устойчивый поток «что изменилось» по всей установке, а не по одному репозиторию. Факты кода:

- **Журнал каталога.** Все изменения каталога пишутся единственной функцией `appendCatalogAudit` (`packages/infrastructure/src/catalog-audit.ts`): только в ней есть `INSERT INTO arkvory_audit`. Её вызывают `catalog-change.ts`, `upload-transition.ts`, `promotion-store.ts`, `stage-events.ts`, `retention.ts`, `attachments.ts`, `oci-index.ts`, `npm-store.ts`, `lfs-store.ts` в транзакции изменения. Таблица `arkvory_audit` содержит `sequence bigint GENERATED ALWAYS AS IDENTITY`, `repository`, `actor`, `action`, `artifact_id`, `occurred_at` и `detail` (схема 27).
- **Порядок есть только внутри репозитория.** `readCatalogChanges` отдаёт ленту репозитория (`GET R/changes`): записи одного репозитория идут под его блокировкой, поэтому их порядок по `sequence` совпадает с порядком фиксации. Между репозиториями это не так. Значение `IDENTITY` выделяется при вставке, а не при фиксации: строка репозитория A с меньшим `sequence` может зафиксироваться позже строки репозитория B с большим. Глобальный курсор `sequence > after` по `arkvory_audit` поэтому **может пропустить событие**.
- **Вебхуки ADR 0069** — файл оператора, до 16 подписок, у каждой один репозиторий. События уходят по одному в строгом порядке; тело — поля ленты без времени. «Мёртвых писем» нет: неудача блокирует подписку. Секрет хранится в файле, API подписок отложено до выбора хранилища секретов.
- **Состояние вне ленты.** Зеркала — `arkvory_mirror_state`; резервные копии — `arkvory_backup_jobs`; обновления — файлы статуса почтового ящика ADR 0038; безопасность — `arkvory_security_audit` (`GET /api/v1/security/audit`); хранение — `GET R/storage/events`. Подписаться на них нельзя.
- **Секреты.** Шифрование ключом установки уже есть: `FleetSeal` (`packages/infrastructure/src/fleet-seal.ts`, AES-256-GCM, файл ключа вне БД и резервной копии, ADR 0077).
- **Защита исходящих запросов.** `createEgressPolicy`, `HttpWebhookSender` и `verifyWebhook` (`webhook-egress.ts`, `webhook-sender.ts`, `webhook-signature.ts`) уже проверены тестами `webhook-egress`, `webhook-sender` и `webhook-signature`.
- `GET /api/v1/capabilities` сообщает `webhooks: false` (`apps/api/src/service-routes.ts`).

## Решение

### 1. Каталог событий в `contracts`

`packages/contracts/src/events/` описывает каждый тип: имя, `schemaVersion` (целое), JSON Schema поля `data`, область (`repository` или `system`), право на чтение и ключ раздела. Каталог входит в OpenAPI (`components.schemas`) и отдаётся `GET /api/v1/events/types`. Изменения каталога только аддитивные: новое необязательное поле не меняет `schemaVersion`, несовместимое изменение — новый `schemaVersion`, и сервер выпускает обе версии на период, объявленный в ADR изменения.

Типы первой версии:

| Область    | Тип                                                                                     | Источник                                           |
| ---------- | --------------------------------------------------------------------------------------- | -------------------------------------------------- |
| repository | `artifact.published`, `artifact.deleted`, `artifact.restored`                           | `upload-transition`, `retention`                   |
| repository | `asset.revision.created`, `asset.restored`                                              | `catalog-change`                                   |
| repository | `package.registered`, `annotation.updated`, `attachment.added`                          | `catalog-change`, `attachments`                    |
| repository | `stage.added`, `stage.removed`, `artifact.promoted`, `artifact.received`                | `promotion-store`, `stage-events`                  |
| repository | `oci.manifest.pushed`, `oci.tag.updated`, `oci.tag.deleted`                             | `oci-index`                                        |
| repository | `npm.version.published`, `npm.tag.updated`, `lfs.object.stored`                         | `npm-store`, `lfs-store`                           |
| repository | `mirror.state.changed` (`following`, `failing`, `recovered`)                            | состояние зеркала в worker                         |
| system     | `backup.completed`, `backup.failed`, `backup.verified`                                  | `arkvory_backup_jobs`                              |
| system     | `update.available`, `update.applied`, `update.failed`                                   | наблюдение статуса почтового ящика                 |
| system     | `module.health.changed`                                                                 | ADR 0079                                           |
| security   | `security.credential.created`, `security.credential.revoked`, `security.account.locked` | `arkvory_security_audit`, только по явной подписке |

Что входит в `data`:

- `data` содержит идентификаторы и факты дескриптора: `artifactId`, имя, версию, размер (десятичной строкой), `sha256`, метки и стадию на момент события, путь файла.
- Значения metadata в `data` не входят (для них нужно `annotation.read`); их перечитывают маршрутами чтения.
- Автор события, IP, секреты, токены и байты в `data` не попадают никогда.
- Размер `data` — не больше 8 КиБ, проверяется при записи.

### 2. Конверт CloudEvents 1.0

Используется структурированный режим JSON (`application/cloudevents+json`):

- `specversion: "1.0"`;
- `id` — `<epoch>:<position>`;
- `source` — `/arkvory/<site>/repositories/<repository>` или `/arkvory/<site>/system`;
- `type` — `arkvory.<имя>.v<schemaVersion>`;
- `subject` — id артефакта или путь;
- `time` — `occurred_at` из часов БД;
- `datacontenttype: "application/json"`;
- `dataschema` — `urn:arkvory:event:<имя>:<schemaVersion>`;
- `data`.

Расширения: `partitionkey` (стандартное расширение Partitioning), `arkvoryposition` (десятичная строка, 64 бита) и `arkvoryepoch`. Выбор CloudEvents даёт готовые SDK и маршрутизаторы у потребителей. Схемы данных остаются нашими, в `contracts`.

### 3. Хранение: outbox и единственный секвенсор

Таблица `arkvory_events` (expand-only миграция): `id bigint identity`, `position bigint NULL UNIQUE`, `type`, `schema_version`, `scope`, `repository NULL`, `partition_key`, `subject`, `labels text[]`, `occurred_at`, `data jsonb`.

- **Запись в той же транзакции.** `appendCatalogAudit` вместе со строкой журнала пишет строку события. Это одна точка, поэтому журнал и события не расходятся: событие фиксируется тогда и только тогда, когда фиксируется изменение. Системные источники пишут событие в транзакции, меняющей их состояние (задание копии, состояние зеркала). Для состояний вне БД (статус обновлений в файлах) событие пишет worker, заметивший изменение, и оно повторяется после перезапуска, пока не записано (at-least-once «наблюдения»).
- **Позицию присваивает только секвенсор** — цикл единственного worker (`WorkerSingletonBusy`, владение хранилищем по ADR 0042). Он работает так: в одной транзакции под `pg_advisory_xact_lock` берёт строки `position IS NULL` в порядке `id` (до 1000) и присваивает им `nextval` по возрастанию; перед каждой транзакцией проверяет `catalog.active`. Инвариант: позиции выдаются последовательными зафиксированными транзакциями, поэтому читатель, увидевший позицию P, никогда потом не увидит новую строку с позицией меньше P. Строка, зафиксированная позже, получает большую позицию. Позиции уникальны и монотонны, но могут иметь пропуски: потребитель не считает их подряд идущими.
- **Порядок по разделу.** Внутри репозитория изменения фиксируются по очереди под его блокировкой, а секвенсор идёт по `id`. Поэтому порядок позиций в разделе `repository:<r>` совпадает с порядком фиксации. У системных событий раздел — `system:<источник>`. Глобальный порядок позиций — это порядок публикации, а не причинность между разделами.
- **Задержка.** Такт секвенсора — 500 мс, с пробуждением после записи в том же процессе. Метрика `arkvory_events_unsequenced_age_seconds` и правило `ArkvoryEventSequencerStalled` (дольше 2 минут).
- **Эпоха** (`epoch`, UUID) создаётся при первой миграции и при восстановлении из резервной копии. Таблица событий в копию не входит: это окно, а не история. После восстановления курсоры потребителей относятся к прежней эпохе, и сервер отвечает 409 `events_epoch_changed` с новой эпохой и `oldest`. Потребитель пересинхронизируется обычными маршрутами чтения.
- **Хранение.** `ARKVORY_EVENTS_RETENTION_HOURS` (по умолчанию 168) и `ARKVORY_EVENTS_MAX_ROWS` (по умолчанию 5 000 000). Процесс записи удаляет старые строки порциями. Курсор старше `oldest` — 410 `events_cursor_expired` с `oldest` и `head`. Хранение `arkvory_audit` от этого не зависит: журнал остаётся историей, аудитом и лентой зеркал ADR 0058.

### 4. Чтение с курсора

`GET /api/v1/events?after=<position>&limit=<1..500>&types=<список или префикс.*>&repository=<r>&wait=<0..30>` возвращает `{epoch, items, next, head, oldest}`. Позиции — десятичные строки.

- **ACL на сервере.** События репозитория видит тот, у кого есть `artifact.list` в этом репозитории (как для `R/changes`). Системные события доступны глобальному администратору; события безопасности — глобальному администратору и только при явном `scope=security`. Права проверяются при каждом запросе по действующему `Principal`, поэтому отзыв доступа действует сразу.
- **Ограниченный просмотр.** Один запрос просматривает не больше 5000 строк. `next` продвигается и за невидимые строки, чтобы потребитель с узкими правами не стоял на месте. Так раскрывается только факт «в этих позициях были недоступные события»; пропуски позиций нормальны и без этого. Это записано в документации.
- **Длинный опрос.** `wait` держит запрос до появления видимого события или до срока. Таких запросов не больше 64 на процесс; сверх лимита ответ сразу пустой (`waited: false`). Ожидание опрашивает БД раз в секунду, без LISTEN/NOTIFY. Это отдельный этап.
- Лента `R/changes` и вебхуки ADR 0069 остаются без изменений и поддерживаются.

### 5. Подписки и доставка

**API.** `GET|POST /api/v1/event-subscriptions` и `GET|PATCH|DELETE /api/v1/event-subscriptions/{id}`, а также `POST .../{id}/rotate-secret`, `POST .../{id}/rewind` (`{after}` не меньше `oldest`), `GET .../{id}/dead-letters` и `POST .../{id}/dead-letters/replay`. Изменения идут по ревизии (CAS), создание — с `Idempotency-Key`. Управляет подписками глобальный администратор.

**Секрет.** Секрет подписи создаёт сервер и показывает один раз (при создании и ротации). В БД он хранится зашифрованным `FleetSeal`-подобным ключом событий (`ARKVORY_EVENTS_KEY_FILE`, по умолчанию `events.key` в каталоге данных, 0600, вне БД и резервной копии). Без файла подписки не доставляются (`secret_unavailable`), а после восстановления требуют ротации. Это закрывает отложенный вопрос ADR 0069 о хранилище секретов. Подписки из файла оператора продолжают работать как прежде.

**Владелец и права.** У подписки есть владелец-принципал. Перед каждой отправкой права владельца проверяются заново по тем же правилам, что у чтения с курсора: отозванный доступ останавливает доставку (`owner_forbidden`), а не раскрывает события.

**Фильтры:**

- `types` — список или префикс `artifact.*`;
- `repositories` — до 64, или `*` (все, видимые владельцу);
- `labels` — любая из меток в `labels` события;
- `stages`.

Новая подписка начинает с `head`, если `after` не указан явно (не меньше `oldest`).

**Доставка** — цикл worker на подписку, развитие `WebhookDelivery`:

- Курсор — позиция. Порядок строгий по позициям, как в ADR 0069: событие N+1 не уходит, пока не доставлено N. Порядок разделов от этого только сильнее. Параллельная доставка по разделам — возможное развитие с отдельным решением.
- Тело — одно CloudEvent; подпись — схема ADR 0069 (`X-Arkvory-Delivery` = `id`, `X-Arkvory-Timestamp`, `X-Arkvory-Signature: sha256=…`, две подписи при ротации), то есть одна эталонная проверка `verifyWebhook` и её порт в SDK.
- Добавляется `X-Arkvory-Attempt`.
- Повторы — как в ADR 0069: 12 с с удвоением до 1 часа, ±20%.

**«Мёртвые письма» — только явно.** Подписка с `deadLetter: {maxAgeHours}` (1–168) переносит событие, не доставленное за этот срок, в `arkvory_event_dead_letters` (подписка, позиция, попытки, последний код ошибки) и идёт дальше. Без этого поля действует правило ADR 0069: событие не пропускается никогда. Повтор переносит письма обратно в очередь подписки в порядке позиций. Пока событие в таблице писем, его строка в `arkvory_events` не удаляется по сроку хранения; число писем ограничено 10 000 на подписку, при переполнении подписка останавливается с `dead_letters_full`.

**Защита исходящих запросов** — без изменений ADR 0069: разрешение имени до соединения, соединение на проверенный IP, запрещённые диапазоны, HTTPS с проверкой сертификата, без перенаправлений, 10 с на попытку, ответ до 4 KiB не сохраняется. **Через API расширить политику нельзя.** Частные сети (`ARKVORY_WEBHOOKS_ALLOW_PRIVATE`) и УЦ (`ARKVORY_WEBHOOKS_CA_FILE`) задаются только на хосте. API проверяет URL до сохранения и отклоняет адрес, который политика не пропустит (`egress_forbidden`).

**Пределы.**

- До 64 подписок на установку (`ARKVORY_EVENT_SUBSCRIPTIONS_MAX`).
- Не больше 10 запросов в секунду на подписку.
- Не больше 16 одновременных отправок на процесс.
- Получатель, отвечающий 429 или 503 с `Retry-After`, получает паузу не меньше указанной, но не больше часа.

**Идемпотентность у потребителя.** Получатель дедуплицирует по `id`. Событие — подсказка: актуальное состояние перечитывается маршрутами чтения. Повтор события не должен повторять бизнес-операцию.

### 6. Приёмники как модули

По ADR 0079 HTTP-вебхук — первый модуль вида `event-sink`. Порт `EventSink.deliver(event, signal)` возвращает `delivered`, `retry` (с паузой) или `rejected` (с кодом); его проверяет общий контрактный набор. Приёмники Kafka, NATS и AMQP — будущие модули, каждый по своему ADR. Брокер в ядро не вводится.

### 7. Наблюдаемость

Метрики:

- `arkvory_events_head_position`, `arkvory_events_oldest_position`, `arkvory_events_unsequenced_age_seconds`, `arkvory_events_pruned_total`;
- `arkvory_event_subscription_failing{subscription}`, `arkvory_event_subscription_lag_events{subscription}`, `arkvory_event_subscription_last_success_timestamp_seconds{subscription}`, `arkvory_event_dead_letters{subscription}`.

Правила оповещения: `ArkvoryEventSequencerStalled`, `ArkvoryEventSubscriptionFailing`, `ArkvoryEventDeadLetters`. В журналах только id подписки и код ошибки, без URL, тела и секрета.

### 8. SDK и CLI

- **SDK.** `client.events.list(params)`, `client.events.follow({after, signal})` — асинхронный итератор, который сохраняет курсор через переданную функцию и переживает `events_cursor_expired` только явной ошибкой; `client.events.types()`; `client.eventSubscriptions.*`; переносимая `verifyEventDelivery` (HMAC через уже используемый `@noble/hashes`).
- **CLI.**
  - `arkvoryctl events tail [--after] [--types] [--repository] [--follow]` выводит JSON-строки и пишет курсор в `--cursor-file`.
  - `arkvoryctl events subscriptions list|add|update|remove|rotate|rewind|dead-letters`.
  - Секрет выводится один раз и только в файл `--secret-out` (0600), не в stdout.
- **`capabilities`.** `features.events: true` и `features.eventSubscriptions: true`. Значение `webhooks` остаётся за подписками ADR 0069 и не меняется.

## Альтернативы

- **Глобальный курсор по `arkvory_audit.sequence`.** Пропускает события при параллельной фиксации разных репозиториев (см. контекст).
- **Составной курсор «репозиторий → sequence».** Корректен, но размер курсора растёт с числом репозиториев, и в нём нет системных событий.
- **Логическая репликация или Debezium.** Внешняя инфраструктура и привязка к внутренней схеме таблиц.
- **Брокер в ядре.** Новая служба без измеренной необходимости; брокеры подключаются как `event-sink`.
- **Свой конверт по API_EVOLUTION.** Поля почти совпадают с CloudEvents. Стандарт даёт инструменты потребителю, а схемы остаются нашими.
- **Подпись Standard Webhooks** (`webhook-id`, `webhook-signature`). Совместима с готовыми библиотеками, но расходится со схемой ADR 0069; см. открытый вопрос.
- **Отсутствие «мёртвых писем»** (как в ADR 0069). Остаётся поведением по умолчанию; письма включаются явно, потому что события — подсказки, и потерянное восстанавливается чтением.

## Последствия

- Каждое изменение каталога пишет ещё одну строку в той же транзакции: небольшая стоимость записи, без лишнего сетевого I/O. Секвенсор и удаление по сроку — нагрузка процесса записи, ограниченная порциями.
- Публичный контракт растёт аддитивно: `/api/v1/events`, `/api/v1/events/types`, `/api/v1/event-subscriptions*`, схемы событий, флаги `capabilities`.
- Новый файл ключа событий; при его потере подписки нужно перевыпустить.
- `arkvory_audit` и `R/changes` не меняются; зеркала от событий не зависят.

## Этапы (каждый — отдельный PR)

1. **E1. Outbox и секвенсор.** Миграция `arkvory_events`, запись в `appendCatalogAudit`, секвенсор в worker, эпоха, удаление по сроку, метрики. Гейты: `quick`, `integration`.
2. **E2. Чтение с курсора.** `GET /api/v1/events` и `GET /api/v1/events/types`, каталог в `contracts` и OpenAPI, SDK `events.list` и `follow`, CLI `events tail`, страница wiki с переводами. Гейты: `quick`, `integration`.
3. **E3. Системные источники.** Резервные копии, зеркала, обновления, `module.health.changed`; события безопасности — с `scope=security`. Гейты: `quick`, `integration`.
4. **E4. Подписки через API.** Ключ событий, шифрование секрета, CAS, проверка прав владельца при отправке, фильтры, `rewind`, CLI и SDK. Гейты: `quick`, `integration`, `deployment`.
5. **E5. «Мёртвые письма», длинный опрос, `event-sink` по ADR 0079.** Гейты: `quick`, `integration`.

## Проверка

- **Unit.** Валидация каталога (каждый тип имеет схему, право и раздел; имена уникальны); построение CloudEvent; фильтры; ограниченный просмотр и `next` за невидимыми строками; ACL по областям.
- **Integration на PostgreSQL:**
  - две параллельные транзакции разных репозиториев, где меньший `id` фиксируется позже, — читатель с курсором не теряет ни одного события;
  - откат изменения не оставляет события;
  - перезапуск worker во время присвоения позиций не создаёт дублей и не меняет порядок;
  - курсор старше `oldest` даёт 410, после восстановления — 409 с новой эпохой;
  - отзыв `artifact.list` скрывает события сразу, а подписка владельца останавливается с `owner_forbidden`.
- **Доставка** (на настоящих HTTP/HTTPS-серверах, как `webhook-sender`):
  - порядок, повтор под тем же `id` после падения между ответом и записью курсора;
  - `Retry-After`, перенос в «мёртвые письма» только при `deadLetter` и их повтор;
  - отказ сохранить URL, запрещённый политикой;
  - секрет и URL не попадают в журнал;
  - секрет недоступен без файла ключа.
- **SDK и CLI.** Строгий потребитель TypeScript, `follow` с сохранением курсора, проверка подписи совпадает с `verifyWebhook` на одних векторах.
- **Правила оповещения** ссылаются на существующие метрики; секвенсор, остановленный в тесте, поднимает `ArkvoryEventSequencerStalled`.
