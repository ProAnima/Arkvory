# 0078. Открытое ядро: бесплатное ядро, подписанные модули и лицензии

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-17. Решение меняет модель поставки (появляются отдельно устанавливаемые модули), границу доверия (загрузка подписанного кода во время работы), долговечность (данные модуля) и публичный контракт (`/api/v1/system/modules`, `/api/v1/system/license`). Условия [LICENSE.md](../../LICENSE.md) и [ADR 0061](0061-free-source-available-license.md) не меняются. До решения владельца код не пишется. Решения владельца 2026-10-17 (в конце ADR) заменяют I3 для платных модулей, таблицу состояний п. 2 и часть п. 6. Связано с [ADR 0009](0009-leased-read-gateways.md), [ADR 0054](0054-built-in-backup-vault.md), [ADR 0059](0059-schema-updates-behind-verified-backup.md), [ADR 0060](0060-proanima-hub.md), [ADR 0072](0072-single-site-ha.md), [ADR 0079](0079-extension-modules.md), [ADR 0080](0080-event-integrations.md), [ADR 0081](0081-mcp-and-agent-skill.md).

## Контекст

Владелец решил (2026-10-17) перейти к модели открытого ядра:

- публичный репозиторий `ProAnima/Arkvory` — **бесплатное ядро**. Его функции нельзя выключить лицензией, и они бесплатны;
- платные функции живут в отдельном **приватном** репозитории `ProAnima/Arkvory-Pro` и продаются. Первые из них — платный модуль хранения и модуль дельта-передачи. Публичный репозиторий не содержит их проектирования и кода и называет их только обобщённо;
- установка одна и бесплатная. Платный модуль — отдельный пакет, подписанный ProAnimaStudio. Он ставится командой, обновляется тем же каналом хаба и включается лицензией;
- ядро загружает во время работы **только подписанные** модули с совместимой версией API расширений. Произвольный и неподписанный код не загружается, service locator не появляется.

Факты кода и решений:

- **Подпись релизов** ([ADR 0060](0060-proanima-hub.md)): Ed25519 в формате minisign, проверка в `apps/deploy/src/release-signature.ts`, открытые ключи — `apps/deploy/src/release-keys.ts`, ротация через релиз с двумя ключами. Закрытый ключ — файл на рабочей станции выпуска.
- **Хаб** решает, какую версию получит установка, раздаёт файлы и принимает статистику. Случайный id установки (`config/install-id`) уходит в хаб только при включённой статистике. Состав передаваемых данных закреплён в §7 LICENSE.md.
- **Обновление со сменой схемы** ([ADR 0059](0059-schema-updates-behind-verified-backup.md)) идёт только после свежей проверенной резервной копии; журнал `apps/deploy/src/migration-update.ts` проходит фазы `prepared` → `committed` и умеет откат и `recover`.
- **HA** ([ADR 0072](0072-single-site-ha.md)) держит весь корень установки (релизы, конфигурацию, данные) на одном реплицируемом томе. **Шлюзы чтения** ([ADR 0009](0009-leased-read-gateways.md)) — отдельные процессы с той же БД.
- **Резервная копия** ([ADR 0054](0054-built-in-backup-vault.md)) хранит каталог логическим экспортом по реестру таблиц, а содержимое — целыми blob по неизменяемому id upload с проверкой SHA-256 при копировании. Восстановление — только в пустую цель.
- Сегодня в процессах ядра нет загрузки кода по пути из конфигурации; черновик ADR 0079 запрещал её полностью.
- [ADR 0061](0061-free-source-available-license.md): пакеты не публикуются в npm (`private: true`); LICENSE §2 перечисляет официальные источники копий.

## Решение

### 1. Граница ядра

**1.1. Ядро — всё, что входит в публичный репозиторий.** Оно бесплатно, работает без лицензии, и ни одна его функция не проверяет лицензию. В ядро входят:

- хранение и выдача UPack и обычных файлов: загрузка с возобновлением, проверенное скачивание, история файлов, вложения, стадии и продвижение, удаление и восстановление по правилам хранения;
- протоколы: UPack и raw (не выключаются), OCI, Git LFS, npm (выключаются оператором, ADR 0079);
- каталог, поиск, метки и metadata; общий поиск, пакетное чтение и список модулей (ADR 0081, A1–A4);
- учётные записи, группы, сервисные ключи, делегирование, ACL, журнал безопасности;
- резервные копии (агент, vault, шифрование, проверка, восстановление), обновления, хаб, обратная связь;
- зеркала, шлюзы чтения, HA ADR 0072, консоль площадок ADR 0077, планировщик скачиваний, ссылки, TLS, наблюдаемость;
- события, подписки и вебхуки (ADR 0069, ADR 0080);
- MCP-сервер в `arkvoryctl` и навык для агентов (ADR 0081);
- консоль, SDK и CLI, включая обычную (не дельта) передачу и общую точку согласования возможностей передачи (ADR 0079);
- API расширений и встроенные модули ядра (ADR 0079).

**1.2. Что может быть платным.** Необязательное улучшение поверх работающего ядра: экономия места, ускорение передачи, дополнительные интеграции. Платный модуль добавляет поведение, но не забирает и не ухудшает поведение ядра. Конкретные платные модули описываются в приватном репозитории; здесь они называются обобщённо («платный модуль хранения», «модуль дельта-передачи»).

**1.3. Что не бывает платным никогда:** доступ к своим данным (чтение, скачивание, экспорт), резервное копирование и восстановление, проверка целостности, ACL и исправления безопасности, механизм обновлений, публичный API к функциям ядра.

**1.4. Публичный репозиторий не содержит проектирования и кода платных функций.** Точки расширения ядра нейтральны: у каждой есть реализация в ядре (например, обычное хранилище, обычная передача) или тестовая реализация в наборе контрактных тестов. Точка расширения не добавляется «под» конкретный платный модуль без сценария ядра, который она обслуживает.

### 2. Инварианты защиты пользователей бесплатного ядра

Это жёсткие требования. Модуль, который их не выполняет, не подписывается.

**I1. Данные остаются читаемыми и восстановимыми.** Отсутствие модуля, истечение или отзыв лицензии **никогда** не делает сохранённые данные нечитаемыми или невосстановимыми.

Модуль объявляет в манифесте класс данных `dataClass`:

- `none` — модуль не хранит данных;
- `auxiliary` — хранит вспомогательные данные (индексы, кеши, свою статистику), а байты и метаданные артефактов остаются в форме, которую читает ядро;
- `layout` — меняет представление байтов опубликованных blob в хранилище (модуль хранения).

Для `layout` обязательны:

- **L1. Чтение без лицензии.** Путь чтения модуля работает в режиме «только чтение» без действующей лицензии: чтение и Range, `verify`, `exists`, чтение для резервной копии, экспорт. Лицензия ограничивает только запись новых данных в режиме модуля.
- **L2. Пакет хранится, пока есть данные.** Пакет каждой версии модуля, которой записаны данные, хранится в установке (`modules/<id>/<version>/`) и не удаляется, пока у модуля есть данные. Пакет входит в каждую точку резервной копии, содержащую данные модуля. Хаб раздаёт пакеты модулей без лицензии: сам по себе пакет без лицензии даёт только чтение.
- **L3. Эвакуация в форму ядра.** `arkvory module evacuate <id> [--repository <r>]` переписывает данные модуля в обычное хранилище ядра через порт хранения. Операция ограничена по ресурсам, возобновляема и идемпотентна, проходит под барьерами резервной копии и очистки (ADR 0035, ADR 0054), проверяет SHA-256 каждого blob и работает без лицензии. Перед запуском она оценивает нужное место и честно сообщает, что форме ядра может понадобиться больше места, чем занимали данные модуля.
- **L4. Запись не падает из-за лицензии.** Когда запись в режиме модуля прекращается, новые данные пишутся в форме ядра (конфигурация откатывается к хранилищу ядра). Пользователь теряет экономию или ускорение, но не возможность публиковать.
- **L5. Ядро не удаляет чужое.** Очистка ядра (ADR 0035) не удаляет объекты, которыми владеет незагруженный модуль. Если модуль не загружен, очистка его хранилища приостанавливается, и это видно в состоянии модуля.
- **L6. Целостность не ослабляется.** Контракт порта хранения (точная длина, неизменяемость, SHA-256 дескриптора) одинаков для ядра и модуля. Клиенты ядра проверяют итоговый SHA-256 независимо от модуля.
- **L7. Доказательство.** Модуль проходит набор контрактных тестов `readability` из тестового пакета расширений (ADR 0079): истечение лицензии, отзыв лицензии, чужая установка, отсутствие модуля с пакетом в точке копии, восстановление ядром, эвакуация.

Поведение по состояниям (для `layout`; для `auxiliary` и `none` пропадает только функция модуля):

| Состояние                                                            | Чтение, скачивание, экспорт                                         | Резервная копия и восстановление                                        | Новая запись                    | Конфигурация                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------- |
| Лицензия действует                                                   | да                                                                  | да                                                                      | в режиме модуля                 | как задана                                               |
| Срок истёк, идёт льготный период                                     | да                                                                  | да                                                                      | в режиме модуля, предупреждения | как задана                                               |
| Лицензии нет, истекла после льготного периода, отозвана или чужой id | да, через путь чтения модуля                                        | да                                                                      | в форме ядра                    | откат к хранилищу ядра для новых данных                  |
| Версия модуля отозвана ключом подписи (п. 3.4)                       | см. п. 3.4                                                          | прежние точки — да; новая — как чтение                                  | в форме ядра                    | откат к хранилищу ядра                                   |
| Пакет модуля удалён с диска вопреки L2                               | `503 module_unavailable` с id и версией пакета; данные не трогаются | прежние точки содержат пакет; новая копия отказывает до возврата пакета | в форме ядра                    | процесс `degraded`, очистка хранилища модуля остановлена |

Таблица заменена таблицей Р3 из «Решений владельца 2026-10-17» (пробный период, токен активации, офлайн-окно). Последняя строка — единственный случай временной недоступности. Он возникает, только если удалить файлы, которые ядро запрещает удалять. Данные при этом остаются восстановимыми: пакет есть в точке копии и раздаётся хабом без лицензии.

**I2. Резервные копии восстанавливает ядро.** Формат точки задаёт ядро (ADR 0054, ADR 0070). По умолчанию содержимое попадает в точку целыми blob через путь чтения, то есть в форме ядра, и восстанавливается без модуля. Модуль может добавить в точку свой раздел (свои таблицы и объекты) только по контракту ядра (ADR 0079, п. 5.4): манифест точки перечисляет модули с id, версией, SHA-256 пакета и классом данных, а пакет модуля лежит в точке. Восстановление такой точки инструментами ядра той же или более новой версии проверяет подпись пакета и загружает модуль в режиме восстановления без лицензии. Глубокая проверка точки (`verify --deep`) вызывает проверку раздела модуля.

**I3. Нет телеметрии сверх ADR 0060.** Лицензия проверяется офлайн, активации и обращений «домой» нет. Модули обновляются через хаб по правилам ADR 0060: id установки уходит только при включённой статистике, id лицензии и имя владельца лицензии не уходят никогда. Модуль не открывает собственных соединений к сервисам ProAnimaStudio. Исходящие соединения к целям, которые настроил оператор, идут только через политику исходящих запросов ядра (ADR 0069). Для платных модулей I3 заменён онлайн-активацией через хаб: «Решения владельца 2026-10-17», Р2.

**I4. Бесплатное остаётся бесплатным.** Функция, вышедшая в ядре, не переносится в платный модуль и не начинает требовать лицензию.

### 3. Пакет модуля

**3.1. Формат.** Один файл `arkvory-module-<id>-<version>.tgz`:

- `module.json` — манифест;
- `module.json.minisig` — подпись манифеста;
- `files/…` — код модуля (собранный ES-модуль) и ресурсы.

Манифест:

- `format: 1`, `id` (`[a-z][a-z0-9-]{1,31}`, не совпадает с id встроенных модулей ядра), `version` (semver), `publisher: "proanimastudio"`;
- `extensionApi` — диапазон semver версий API расширений, например `^1.3.0`;
- `core` — необязательный диапазон версий релиза ядра;
- `side` — `server` или `client`; для `server` — `roles` (`api`, `reader`, `worker`, `backup`) и `entry` по ролям, для `client` — `entry` для `arkvoryctl` (ADR 0079, п. 6);
- `extensionPoints`, `requires`, `provides`, `routes.prefix`, `metricPrefix`, `schema.tablePrefix` — по ADR 0079;
- `dataClass` — `none | auxiliary | layout`;
- `licenseFeature` — имя функции в лицензии, которую проверяет сам модуль (п. 6), или `null`;
- `files` — список `{path, size, sha256}` всех файлов. Других файлов в архиве нет.

Нативные дополнения Node (`.node`), скрипты установки и файлы вне `files/` в первой версии формата запрещены: так пакет одинаков для Linux и Windows и не выполняет кода при распаковке.

**3.2. Подпись.** Отдельный **ключ подписи модулей** Ed25519 в формате minisign, не совпадающий с ключами релизов ADR 0060. Закрытый ключ хранится только на рабочей станции выпуска модулей (`~/.proanima/arkvory-module-signing.key`). Открытые ключи встроены в ядро. Ротация — как у релизов: релиз ядра N несёт старый и новый ключ. Модуль, подписанный ключом релизов, отклоняется: компрометация одного ключа не даёт права на другое.

**3.3. Проверка до любого `import`.**

1. При установке: подпись манифеста встроенным ключом модулей → разбор манифеста как `unknown` с проверкой схемы → SHA-256 и размер каждого файла → отказ при лишнем файле, ссылке, устройстве, пути с `..` или абсолютном пути → распаковка во временный каталог и атомарное переименование в `modules/<id>/<version>/` с правами только на чтение для учётной записи службы.
2. При каждом запуске процесса: загрузчик ядра повторно проверяет подпись и SHA-256 каждого файла и только после этого вызывает `import()` точки входа по `file:`-URL внутри проверенного каталога.

Загрузчик — единственное место в `apps/*` и `packages/*`, где разрешён `import()` с вычисляемым аргументом; это проверяет policy-тест (ADR 0079).

**3.4. Отзыв.** Хаб отдаёт подписанный ключом модулей **список отзыва**: номер (монотонный), время выпуска и записи `{id, versions, reason, readOnly, replacement}`. Ядро:

- получает список вместе с проверкой обновлений и не принимает список с меньшим номером, чем сохранённый (`config/module-revocations.json`);
- получает свежий список также в каждом релизе ядра и каждом пакете модуля, поэтому отзыв доходит и до установок без доступа к хабу;
- не загружает отозванную версию для записи. Если у записи `readOnly: true`, путь чтения версии загружается для чтения, экспорта и эвакуации;
- для `readOnly: false` (опасен сам путь чтения) выпуск обязан сначала опубликовать `replacement` с исправленным путём чтения. Пока замена не установлена, чтение данных модуля отвечает `503 module_revoked`, данные не трогаются, `arkvory module install` предлагает замену.

**3.5. Версии и закрепление.** Модуль обновляется вместе с проверкой обновлений ядра, в том же окне и канале (`stable`/`beta`). `arkvory module pin <id> <version>` закрепляет версию, `--unpin` снимает. Понижение версии — только явной командой с файлом и только если у модуля нет миграций новее целевой версии.

### 4. Установка, обновление, откат и удаление

Команды `apps/deploy`:

- `arkvory module install <file | id[@version]>` — файл или пакет с хаба;
- `arkvory module list | update [<id>] | pin | remove <id> | evacuate <id> | sync`.

Правила:

- **Журнал.** Изменение набора модулей — запись журнала обновлений ADR 0059 с полями `modules.before` и `modules.after` (id, версия, SHA-256 пакета). Фазы, откат и `recover` — те же. Предыдущая версия пакета хранится до следующего успешного изменения.
- **Миграции модуля** (ADR 0079, п. 5.6) ставятся только после свежей проверенной копии, как смена схемы ядра. Без новых миграций копия не требуется.
- **Запуск после изменения.** Службы перезапускаются. Если новый набор не стал готов, возвращается прежний набор; после применённой миграции модуля — `maintenance-required` и `recover` вперёд, как в ADR 0059.
- **Обновление ядра проверяет модули.** Перед обновлением ядра каждый установленный модуль сверяется с версией API расширений нового релиза. Если модуль несовместим, updater ищет на хабе совместимую версию и ставит ядро и модули одной записью журнала. Если совместимой версии нет, обновление отклоняется (`maintenance_required`, `module_incompatible`). Отключить несовместимый модуль можно только явно: `--disable-incompatible-modules`; для `dataClass: layout` с данными это означает только чтение, если путь чтения совместим, иначе отказ.
- **Удаление.** `remove` выключает модуль и оставляет схему (п. 5.6 ADR 0079). Модуль `layout` с данными не удаляется (`module_owns_data`): сначала `evacuate`.

### 5. Один набор модулей во всех процессах

Отпечаток плана сборки (ADR 0079, п. 3) включает версию релиза ядра и для каждого модуля id, версию, SHA-256 пакета и признак включения. Процесс записи хранит отпечаток в БД. API, worker, агент резервных копий и шлюзы чтения с другим отпечатком не становятся готовыми (`module_plan_mismatch`). Уточнено при реализации (ADR 0079, «Уточнения реализации», «Два отпечатка плана»): готовность сравнивает отпечаток совместимости — без версий ядра и встроенных модулей, с линией caret версии внешнего модуля, — а полный отпечаток с версиями справочный; обновление ядра без миграции не делает прежние процессы неготовыми, со сменой схемы их останавливает проверка версии схемы.

- В HA ADR 0072 каталог `modules/` лежит на реплицируемом томе вместе с релизами, поэтому набор на узлах совпадает сам. Модули ставятся на активном узле процедурой обновления кластера.
- На хосте шлюза чтения `arkvory module sync` ставит набор, записанный в БД процессом записи, с хаба или из указанного каталога файлов. Проверка подписи та же.
- Консоль площадок (ADR 0077) показывает модули и состояние лицензии каждой площадки; у каждой площадки своя лицензия.

### 6. Лицензия

Пункты 6.1–6.3 и 6.5 дополнены и частично заменены «Решениями владельца 2026-10-17» (Р1, Р2).

**6.1. Формат.** Файл `arkvory-license-<licenseId>.json`: `{"format": 1, "payload": "<base64url>", "signature": "<minisign>"}`. Подпись покрывает точные байты `payload`, поэтому канонизация JSON не нужна. Отдельный **ключ подписи лицензий** Ed25519, не совпадающий с ключами релизов и модулей; открытые ключи встроены в ядро.

Поля `payload` (проверяются как `unknown`):

- `format: 1`, `licenseId`, `product: "arkvory"`, `licensee` (название организации для показа в консоли);
- `installations` — список id установок (`config/install-id`), к которым привязана лицензия;
- `features` — имена функций, `limits` — `{имя: десятичная строка}` (64-битные значения без потери точности);
- `issuedAt`, `notBefore`, `notAfter` (или `null` для бессрочной), `graceDays` (по умолчанию 30, не больше 90).

**6.2. Привязка.** Id установки — значение `config/install-id` процесса записи. В HA корень общий (ADR 0072), поэтому id у узлов один. Процесс записи записывает id в БД при запуске, и шлюзы чтения сверяют лицензию с ним. Чтобы получить лицензию, администратор копирует id из консоли или `arkvory license id` и передаёт его продавцу сам; ядро для этого в сеть не ходит. Восстановление на новую установку даёт новый id: лицензия переходит в состояние `mismatch` с льготным периодом от момента обнаружения, чтобы восстановление после аварии не останавливало запись сразу.

**6.3. Хранение и установка.** `arkvory license install <file>` на хосте процесса записи, позже `PUT /api/v1/system/license` для глобального администратора. Лицензия хранится в таблице `arkvory_licenses` (expand-only миграция ядра) и поэтому одинакова для всех процессов и входит в резервную копию. Файл лицензии не секрет: он подписан и привязан к установке. Удаление — `arkvory license remove <licenseId>`.

**6.4. Время.** Срок считается по «эффективному времени»: максимум из текущего времени БД и сохранённой отметки максимального наблюдённого времени (`arkvory_license_clock`, процесс записи обновляет её раз в час). Перевод часов назад не продлевает лицензию; расхождение больше суток даёт предупреждение `clock_rollback_detected`. Отметка может только приблизить истечение, но не отменить его; ошибка часов вперёд исправляется новой лицензией, а не правкой отметки.

**6.5. Кто что проверяет.**

- **Ядро** проверяет подписи пакетов модулей, списка отзыва и файла лицензии, формат лицензии и привязку к установке. Оно предоставляет модулям только порт чтения `LicenseView` (ADR 0079): состояние (`none | valid | grace | expired | mismatch | invalid`), `licenseId`, `features`, `limits`, `notAfter`, `graceUntil`, эффективное время. Решений о функциях ядро не принимает, и никакая функция ядра от лицензии не зависит.
- **Платный модуль** сам решает, что разрешено при данном состоянии и лимитах, и выполняет I1/L4 при отказе.
- Это коммерческий и правовой механизм, а не защита от копирования. Код ядра открыт для чтения и может меняться внутри организации (LICENSE §1), поэтому проверки в ядре обходятся; условия использования модуля задаёт его коммерческая лицензия.

### 7. Безопасность

- **Цепочка поставки модуля** — приватный репозиторий с теми же гейтами (`security`, lockfile, точные версии, review), отдельная подпись модулей и список отзыва. Хаб раздаёт только подписанные пакеты; ядро проверяет подпись само и хабу не доверяет.
- **Изоляции нет.** Подписанный модуль — доверенный код в процессе ядра с доступом к БД, ключам и файловой системе. Узкие порты защищают от случайной связанности, но не от злонамеренного кода. Worker threads, `vm` и права Node это не меняют, и ядро изоляцию не обещает. Поэтому загружается только код, подписанный ProAnimaStudio; модули третьих сторон не поддерживаются, внешние интеграции подключаются через API и события (ADR 0080).
- **Сеть.** Модуль объявляет `egress` (ADR 0079) и получает только политику исходящих запросов ядра. Технически запретить модулю `node:net` нельзя; соблюдение I3 проверяется review и policy-тестами приватного репозитория.
- **Секреты** модуля — только пути к файлам секретов в конфигурации, как у зеркал и вебхуков. В журналы и ответы API они не попадают.

### 8. Публичный контракт (аддитивно)

- `GET /api/v1/system/modules` (глобальный администратор): id, версия, источник (`builtin | signed`), точки расширения, `enabled`, `dataClass`, состояние (`ok | degraded | failed | revoked | unavailable`) с кодом, id ключа подписи, состояние лицензии с точки зрения модуля (`licensed | grace | unlicensed | not-required`), отпечаток плана. Без конфигурации и путей.
- `GET /api/v1/system/license` (глобальный администратор): id установки, список лицензий с `licenseId`, `licensee`, `features`, `limits`, сроками, `graceUntil`, состоянием и кодом причины. Без байтов подписи.
- `GET /api/v1/system/modules/{id}/openapi` (глобальный администратор): фрагмент OpenAPI маршрутов модуля под `/api/ext/<id>/` (ADR 0079, п. 5.2).
- `PUT /api/v1/system/license` и `DELETE /api/v1/system/license/{licenseId}` — отдельным этапом.
- Коды ошибок по ADR 0051: `module_unavailable`, `module_revoked`, `module_incompatible`, `module_owns_data`, `module_plan_mismatch`, `license_invalid`, `license_installation_mismatch`.
- Консоль: страница «Модули и лицензия» в администрировании (тексты через i18n, стили через токены), предупреждение о льготном периоде и истечении. Страница wiki на английском с переводами в том же коммите.
- `GET /api/v1/capabilities` сообщает включённые модули с публичной поверхностью (ADR 0079, п. 7). OpenAPI, SDK (`client.system.modules()`, `client.system.license()`) и `arkvoryctl doctor` обновляются в том же PR.

### 9. Правовое

- LICENSE.md и LICENSE.ru.md не меняются: ядро остаётся бесплатным, код открыт для чтения, это не open source.
- Платные модули распространяются по отдельным коммерческим условиям (LICENSE §11: другие права — отдельным письменным договором). Условия модуля лежат в его пакете (`files/LICENSE.md`) и показываются при `arkvory module install` до установки.
- Коммерческие условия модуля должны прямо сказать, что модуль не входит в «программу» по LICENSE ядра и что I1–I4 — обязательства продавца.

## Альтернативы

- **Платные функции в том же репозитории, включаемые ключом.** Отклонено решением владельца: код платных функций был бы открыт для чтения и изменения внутри организации, проверка ключа в открытом коде бессмысленна.
- **Отдельная платная сборка ядра.** Две линии релизов, два набора гейтов, миграция между сборками. Пользователь бесплатной версии не может просто добавить модуль.
- **Загрузка модулей без подписи (каталог `plugins/`).** Выполнение непроверенного кода в процессе с ключами и БД.
- **Онлайн-активация лицензии.** Противоречит I3 и работе в закрытых сетях. Пересмотрено 2026-10-17: для платных модулей принята с офлайн-окном и офлайн-активацией (Р2).
- **Проверка прав на функции в ядре.** Ядро открыто и изменяемо; решение о функции принадлежит модулю, ядро только проверяет подлинность лицензии.
- **Платный формат хранения без гарантии чтения.** Отклонено I1: пользователь не должен становиться заложником лицензии.

## Уточнения реализации

- `GET /api/v1/system/modules` и `client.system.modules()` сделаны раньше O4, в первой части X1 ADR 0079: id, версия, точка расширения (`kind`), источник, `core`, `enabled`, роли, работает ли модуль в ответившем процессе, состояние там и отпечаток плана. Без id ключа подписи, состояния лицензии и `dataClass`: они появятся вместе с O1–O4 аддитивно. Подробности — ADR 0079, «Уточнения реализации (этап X1, первая часть)».
- `id` модуля (п. 3.1) не содержит двойного и концевого дефиса: таблицы и метрики внешнего модуля называются `arkvory_x_<id>__` (ADR 0079), и только так имена разных модулей не начинают друг друга.

## Уточнения реализации (этап O1 и подготовка O2)

Сделано: пакет `packages/signing`, формат пакета модуля с проверкой при установке и перед использованием, классы ключей, список отзыва, хранилище установленных пакетов и команды хоста `arkvory module install|list|remove|pin|revocations` и `arkvory module trust add|list|remove` (часть этапа P1 [ADR 0082](0082-custom-plugins.md)). Службы внешний код пока не загружают: загрузчик — этап X4 ADR 0079. Лицензии (O3) не реализованы, есть только класс ключа лицензий.

- **Схема подписи — minisign/Ed25519, как у релизов.** Одна проверенная реализация вместо двух; совместимость с утилитой `minisign` нужна ключам авторов плагинов (ADR 0082, п. 3); стойкость держится на открытом ключе, а не на скрытии кода (Р5). Проверка релизов `apps/deploy/src/release-signature.ts` теперь вызывает `verifyMinisign` из `signing` с прежними сообщениями (`release-signing.test.mjs` не менялся); ключи релизов остаются в `apps/deploy/src/release-keys.ts`.
- **Классы ключей** `release | module | license | operator`. `keyRing` запрещает один id ключа в двух классах (подпись называет только id) и один открытый ключ под двумя id или в двух классах: id ключа minisign не подписан, подпись можно переназначить на другой id, и, например, ключ релизов, добавленный оператором под новым id, дал бы владельцу ключа релизов права ключа оператора (`duplicate_key`, в том числе в `trust add`). `verifyClassified` сначала проверяет подпись, затем класс (`wrong_key_class`), затем **назначение**: доверенный комментарий minisign должен содержать поле `file:<имя>` (`file:module.json` у манифеста, `file:module-revocations.json` у списка отзыва, `signature_purpose`). Ключ модулей подписывает и манифесты, и списки отзыва, и подпись одного не годится для другого. Модуль, подписанный ключом релизов или лицензий, отклоняется (`wrong_key_class`); неизвестным ключом — `unknown_key`. `verifyClassified` принимает только алгоритм `ED` (BLAKE2b-512 и Ed25519, по умолчанию в текущем minisign; `signature_algorithm`): если принимать и устаревший `Ed`, каждая подпись `ED` файла X была бы и действительной подписью `Ed` 64 байтов BLAKE2b(X). Манифест релиза (ADR 0060) по-прежнему проверяется `verifyMinisign` и принимает оба алгоритма. Строки base64 подписи и `payload` конверта отзыва принимаются только в канонической записи (`signature_malformed`, `revocations_invalid`): декодер Node пропускает лишние символы и биты заполнения, и один список одного номера иначе выглядел бы как конфликтующий.
- **Встроенные ключи модулей и лицензий пусты.** Закрытый ключ создаёт владелец на рабочей станции выпуска (`node scripts/module-signing.mjs keygen module|license`, файл `~/.proanima/arkvory-<class>-signing.key`, `wx`, 0600) и добавляет открытый в `packages/signing/src/keys.ts`. До этого любой пакет отклоняется с `unknown_key`; это проверяет тест через `arkvory` с встроенными ключами. Тесты подписывают одноразовыми ключами, созданными при запуске; закрытых ключей в репозитории нет, поэтому `tests/fixtures` не понадобились.
- **`signing` зависит от `extension-api`** (ADR 0079, п. 2 предлагал `allowed: []`). Манифест пакета читается тем же `parseModuleManifest`, что и встроенный модуль, а проверка совместимости — тем же `satisfiesCaret`; иначе правила id, версий и диапазонов пришлось бы повторить. `extension-api` переносимый и без зависимостей, цикла нет. `apps/deploy` получил `extension-api` и `signing`; `infrastructure` и `apps/cli` получат `signing` вместе с загрузчиком (X4) и клиентскими модулями (X5).
- **Поля пакета в `module.json`** сверх полей `parseModuleManifest`: `side` (в этой версии только `server`; клиентские пакеты — с X5), `entry` — объект «роль → путь», ровно по ролям манифеста, путь из `files` с расширением `.mjs`; `dataClass` (`none | auxiliary | layout`); `licenseFeature` (`[a-z][a-z0-9-]{1,63}` или `null`); `coreRelease` — необязательный caret-диапазон релиза ядра (имя по ADR 0079, «Уточнения реализации», вместо `core` п. 3.1); `files` — `{path, size, sha256}`. Неизвестное поле — `manifest_invalid` с кодом и указателем `parseModuleManifest`. `version` пакета без заглавных букв (`manifest_invalid`, `/version`): `modules/<id>/<version>/` — имя каталога, и на Windows и macOS `1.0.0-Beta` и `1.0.0-beta` были бы одним пакетом. Скриптов установки в формате 1 нет: нет и поля для них.
- **Архив** — gzip и POSIX ustar. Разрешены: `module.json` (до 1 МиБ), `module.json.minisig` (до 4 КиБ), необязательный `module-revocations.json` (до 1 МиБ, см. отзыв), каталог `files/` и файлы под ним. Отклоняются: жёсткие и символические ссылки (`link_entry`), устройства и FIFO (`special_entry`), расширенные заголовки pax и GNU (`extended_header`, длинные имена не нужны), размер в base-256, неверная контрольная сумма и магия, данные после конца архива tar и после конца потока gzip (`archive_invalid`; zlib молча останавливается на нулевом байте после члена gzip, поэтому каждый байт файла должен принадлежать потоку), пути с `..`, `.`, абсолютные, с буквой диска, `\`, пробелами, управляющими и не-ASCII символами, имена устройств Windows и имена с точкой в конце (`unsafe_path`), повтор имени (`duplicate_entry`), имена, равные без учёта регистра, и файл, который одновременно родитель другого пути (`case_collision`), `.node` (`native_addon`), любые другие записи (`unexpected_entry`). Пределы: архив 1 ГиБ, распакованный архив 1 ГиБ, файл 256 МиБ, 4096 файлов, 8192 записи, путь 240 символов и 16 уровней. Размер записи проверяется по заголовку до чтения данных; память под запись не выделяется (`entry_too_large`, `too_many_entries`, `archive_too_large`). Ошибки хоста при проходе (`ENOSPC`, `EACCES` при распаковке) передаются как есть: `archive_invalid` — только отказ читателя и испорченный поток (`Z_…`, `ABORT_ERR` zlib).
- **Порядок проверки** — п. 3.3: подпись манифеста → разбор манифеста и правила подписавшего (ниже) → размер и SHA-256 каждого файла, лишние и недостающие файлы → совместимость `extensionApi` с `EXTENSION_API_VERSION` и `coreRelease` с версией релиза (`module_incompatible`; у сборки разработчика без версии релиза проверяется только API). Совместимость проверяется после файлов, чтобы испорченный пакет не выглядел несовместимым. `inspectModulePackage` проходит архив один раз и ничего не пишет; `extractModulePackage` читает его второй раз, распаковывает в новый каталог и сверяет каждую запись и SHA-256 архива с первой проверкой (`package_changed`, каталог удаляется).
- **Правила подписавшего** (ADR 0082, п. 1): ключ модулей ProAnimaStudio — только `publisher: "proanimastudio"` и id без `op-`; ключ оператора — только id `op-…` под его шаблонами (`signer_scope`), не `proanimastudio`, без `licenseFeature` и службы `license` (`license_feature_forbidden`); истёкший ключ оператора не принимается для установки (`signer_expired`), а при проверке установленного пакета даёт признак `expired`.
- **Проверка перед использованием** — `verifyInstalledModule`: в каталоге ровно `module.json`, подпись и `files/`; ссылки и junction (`link_entry`), лишние, изменённые и недостающие файлы отклоняются; подпись, манифест, правила подписавшего и хеши проверяются заново, файлы открываются с `O_NOFOLLOW` (POSIX). Её вызывает `arkvory module list`, загрузчик X4 вызовет её перед `import()`. Policy-тест: `import()` и `require()` с вычисляемым аргументом, `node:module` (`createRequire`, `register`) и текст `import(` в строковых литералах (код для другого процесса) в `apps/*/src` и `packages/*/src` разрешены только файлам `COMPUTED_IMPORTS` в `scripts/policy/source.mjs`. AST не видит код, собранный из частей строк, `process.dlopen` и код, выполняемый через `eval`, `new Function` и Worker с `eval: true`; это остаётся за review. Уточнение п. 3.3 «единственное место»: кроме будущего загрузчика там уже были запускающие файлы ядра `apps/deploy/src/runtime.ts` и `manage.ts` — они импортируют установленный релиз ядра, проверенный подписью релиза при подготовке, — и `apps/deploy/src/remote-workflow.ts`, чьи скрипты для `node -e` на удалённом хосте импортируют установленный там релиз ядра.
- **SHA-256 пакета** — хеш файла архива: им отпечаток плана (`ModuleCandidate.packageSha256`, X4), журнал и точка копии называют пакет, и он совпадает с тем, что раздаёт хаб. Установка: `modules/<id>/<version>/` (распакованный пакет), `modules/.packages/<id>@<version>.tgz` (архив, L2), `modules/installed.json` (набор), `modules/.staging/` (временные файлы; очищается следующей командой). Имена с точкой не бывают id модуля. Каталоги 0755, файлы 0644 (и архив `.packages`: `copyFile` сохранил бы режим файла оператора, например 0666 из `/tmp`), владелец — администратор хоста. **Windows:** `modules\` наследует ACL корня (SYSTEM и Administrators); чтение для `LocalService` добавит загрузчик X4.
- **`arkvory module install <file>`**: копия файла в `.staging` (проверяется то, что будет установлено) → проверка → отзыв → показ модуля, ключа, SHA-256 и `files/LICENSE.md` (первые 64 КиБ, управляющие символы убраны, п. 9) → без `--yes` ничего не меняется. Одна версия — один пакет: та же версия с другими байтами отклоняется. Закреплённый модуль не меняет версию до `pin --unpin`; понижение — только с `--downgrade` (миграций модулей ещё нет, п. 3.5); версии сравниваются по п. 11 semver (`beta.10` новее `beta.9`), а у удалённого модуля — с его сохранённым пакетом, так что `remove` и установка старой версии тоже требуют `--downgrade`. Установка с хаба (`id[@version]`), `update`, `sync`, `evacuate` и проверка модулей при обновлении ядра — не сделаны (O2, O5, O6, Р4).
- **Журнал.** Изменение набора — запись `journal.json` с прежним релизом в `previous` и `next`, `modules.before/after` (id, версия, SHA-256 пакета, ключ, `dataClass`) и `modules.retained` (что хранил прежний набор): `prepared` → атомарная замена `installed.json` → `committed`. Если замена не удалась, прежний набор записывается заново и только тогда журнал получает `rolled-back`; иначе он остаётся `prepared` (переименование могло пройти, а синхронизация каталога — нет) и ждёт `recover`. После `committed` удаляются все пакеты (`<id>/<version>/`, `.packages/<id>@<version>.tgz`), которые набор не называет: сохранённые прежним изменением и остатки прерванных команд (пакет, размещённый до записи журнала, недоделанное удаление). Каждая изменяющая команда модулей, включая `revocations` и `trust add|remove`, сначала проверяет журнал. Службы не перезапускаются: модули ещё не загружаются; перезапуск и откат по готовности появятся с загрузчиком. `recover` после прерванной записи возвращает прежний набор (`recovered`), его `retained` и пакеты прерванного изменения остаются «сохранёнными». Прежняя версия пакета хранится до следующего успешного изменения. Команды модулей отмечены в `JOURNALED` блокировки установки.
- **`remove`** выводит модуль из набора и сохраняет пакет до следующего изменения; модуль `dataClass: layout` не удаляется (`module_owns_data`) — без загрузчика ядро не знает, есть ли у него данные, а `evacuate` появится в O5. **`pin <id> <version>`** закрепляет только установленную версию; `--unpin` снимает.
- **Отзыв.** Конверт как у лицензии п. 6.1: `{"format": 1, "payload": "<base64url>", "signature": "<minisign>"}`, подпись точных байтов, ключ модулей, назначение `file:module-revocations.json`. Полезная нагрузка: `format: 1`, `sequence` (целое ≥ 1), `issuedAt`, `entries` (до 4096) `{id, versions (точные semver, до 256), reason ([a-z][a-z0-9_]{0,63}), readOnly, replacement}`. Сохраняется как есть в `config/module-revocations.json` и проверяется при каждом чтении. Меньший номер — `revocation_rollback`, тот же номер с другим содержимым — `revocation_conflict`. Источники в этой версии: `arkvory module revocations <file>` (для закрытых сетей) и список в пакете (`module-revocations.json`, «каждом пакете модуля» п. 3.4) — он сохраняется, только если новее, даже если установку не подтвердили; старый список из старого пакета просто не применяется. Список в релизе ядра и с хаба — не сделаны (O6). `module list` показывает `revoked` и `read path only`; установка отозванной версии отклоняется с заменой.
- **Список доверия оператора** `config/plugin-trust.json` — формат ADR 0082, п. 3, строгий разбор (`trust_invalid` с JSON Pointer). Пишут только `arkvory module trust add|remove` на хосте: владелец и группа `runtime.json`, 0640 (Compose — 0644); службы только читают. `add` показывает id ключа, отпечаток (SHA-256 открытого ключа), шаблоны и срок и без `--yes` ничего не пишет; ключ с id встроенного ключа любого класса отклоняется (`duplicate_key`). `module install` пакеты уровня 3 не ставит: это `arkvory plugin install` этапа P3. Не сделаны `plugin-revocations.json`, `plugin revoke` и проверка прав файла службой.
- **Инструмент** `scripts/module-signing.mjs`: `keygen module|license`, `pack <dir> <out.tgz> [--revocations <file>]` (список файлов с SHA-256, подпись `file:module.json`, проверка подписи до записи, `wx`), `revocations <payload.json> <out.json>`.
- **Проверки:** `tests/signing.test.mjs` (подмена байта, комментария, неизвестный ключ, классы и назначение, устаревший алгоритм `Ed`, `.pub`, список доверия, отзыв: подпись, класс, назначение, откат номера, конфликт, поля), `tests/module-package.test.mjs` (zip-slip, абсолютные пути и диски, ссылки, устройства, pax, дубли, регистр, файл-родитель, `.node`, лишние записи, заявленный размер 300 МиБ без данных, 4097 файлов, испорченный gzip и tar, хвост после конца, совместимость, правила подписавшего и истёкший ключ, подмена архива между проходами, изменённый, лишний и связанный файл установленного пакета), `tests/module-commands.test.mjs` (установка без `--yes`, журнал, обновление, сохранённые пакеты, закрепление, понижение, `layout`, ключи релизов и операторов, отзыв, `recover`, `trust`, разбор команд, запуск `arkvory module` со встроенными ключами), `tests/module-loader-policy.test.mjs`. После независимого review: переназначенный id ключа, устаревший `Ed` для новых форматов, неканонический base64, байты после gzip, ошибки ввода-вывода хоста, заглавные буквы версии, режим архива, порядок pre-release, понижение после `remove`, `retained` при `recover`, удаление остатков, журнал перед `trust` и `revocations`, вычисляемая загрузка через `require` и `node:module`.

## Последствия

- Ядро получает загрузчик подписанного кода. Это новая граница доверия; она защищена подписью, повторной проверкой хешей при запуске и списком отзыва, но не изоляцией.
- Два новых ключа подписи (модули, лицензии) с резервными копиями у владельца. Потеря ключа модулей означает, что новые модули ставятся только после релиза ядра с новым ключом.
- Хаб ([pas-Hub](https://github.com/ProAnima/pas-Hub)) получает маршруты пакетов модулей и списка отзыва; это изменение хаба по его процессу.
- Модуль `layout` дороже в разработке: путь чтения без лицензии, эвакуация и набор `readability` обязательны.
- Резервные копии с разделами модулей больше на размер пакета модуля.
- Версия API расширений становится публичным обязательством (semver, ADR 0079).

## Проверка

- **Подписи.** Подмена байта манифеста, файла или комментария; лишний файл, ссылка, путь с `..`; модуль, подписанный ключом релизов; неизвестный ключ; повторная проверка при запуске после подмены файла в `modules/`; список отзыва с меньшим номером отклоняется.
- **Policy.** Единственный `import()` с вычисляемым аргументом — в загрузчике; загрузчик вызывает `import()` только после проверки (тест с подменённым файлом не доходит до выполнения кода).
- **Лицензия.** Подпись и формат; чужой id установки; `notBefore` в будущем; истечение и льготный период; перевод часов назад не продлевает; лимиты 64-битными строками; восстановление на новую установку даёт `mismatch` с льготным периодом.
- **Инварианты I1/I2** на тестовом модуле `layout` из тестового пакета расширений: истечение лицензии оставляет чтение и переводит запись в форму ядра; удалённый пакет даёт `module_unavailable` без изменения данных и без очистки; точка с разделом модуля восстанавливается ядром без лицензии; `evacuate` переносит данные и проверяет SHA-256; `remove` модуля с данными отклоняется.
- **I3.** Интеграционный сценарий с поддельным хабом: без статистики запросы модулей не содержат id установки; ни один запрос не содержит `licenseId` и `licensee`; проверка лицензии не делает сетевых запросов.
- **HA и шлюзы.** Шлюз с другим набором модулей не готов; `module sync` выравнивает набор; на стенде `deployment-ha` набор совпадает после переключения узла.
- **Обновление.** Несовместимый модуль отклоняет обновление ядра без изменений; совместимая версия ставится вместе с ядром одной записью журнала; откат возвращает прежний набор.

## Открытые вопросы владельцу

1. **I4.** Принять обязательство «функция, вышедшая в ядре, не становится платной» или оставить его вне ADR.
2. **Публикация `@proanima/arkvory-extension-api`.** Предложено: tarball в релизах GitHub `ProAnima/Arkvory`. Реестр npm не входит в официальные источники LICENSE §2; публикация туда потребует решения владельца и, возможно, уточнения документации об официальных источниках.
3. **Определение «программы» в LICENSE.** Оно включает «обновления, опубликованные лицензиаром»; через хаб модуль приходит тем же каналом. Нужна проверка юристом, что коммерческие условия модуля однозначно выводят его из-под LICENSE ядра, а запросы модулей к хабу укладываются в перечень данных LICENSE §7 («установленные обновления»). Текст LICENSE этот ADR не меняет.
4. **Отзыв с `readOnly: false`.** Достаточно ли обязательства выпускать замену до отзыва, или нужна явная команда оператора «загрузить отозванную версию только для чтения» с подтверждением.
5. **Сроки.** Льготный период по умолчанию 30 дней (не больше 90) после `notAfter` и после `mismatch` при восстановлении на новую установку. **Решено 2026-10-17** (Р1, Р2).
6. **Лицензия для нескольких площадок.** Одна лицензия со списком `installations` или отдельная на площадку (ADR 0077). **Решено 2026-10-17:** одна лицензия, активация на каждую установку (Р1).
7. **Установка лицензии через API** (`PUT /api/v1/system/license`) или только командой на хосте.
8. **Скачивание пакетов модулей с хаба без лицензии.** Нужно для L2 (восстановление чтения на новой установке); альтернатива — выдача по `licenseId`, но тогда пакет обязан лежать в каждой точке копии.
9. **Нативные дополнения Node** в пакетах модулей запрещены в первой версии формата.
10. **Окно поддержки предыдущей major** API расширений (предложено: два минорных релиза ядра).

## Решения владельца 2026-10-17

Владелец принял решения о типах лицензий, проверке лицензий через хаб, согласованных обновлениях ядра и модулей и защите кода. Они дополняют ADR, а в местах, перечисленных в разделе «Что заменено», заменяют его текст; остальное действует как написано выше. Коммерческий набор лицензий, цены и условия продажи определяет владелец вне репозитория. Проектирование платных модулей и их собственная защита логики лицензии здесь не описываются (п. 1.4): ниже — только то, что делает и гарантирует ядро, и условия, которые модуль выполняет, чтобы его подписали.

### Р1. Типы лицензий и пробный период

- **Где получают лицензию.** Пробный период и покупку оформляют на сайте ProAnimaStudio: личный кабинет, оплата и выдача — сервисы студии вне этого репозитория, они появятся позже. Сайт выдаёт **ключ лицензии** (секрет для онлайн-активации, Р2) и **токен активации** для указанной установки. В ядре нет платёжного кода, и с сайтом ядро не связывается.
- **Пробный период — 30 дней** от выдачи, один раз на установку и учётную запись сайта (правило сайта и хаба, а не ядра). Это лицензия типа `trial` без льготного периода продления (`graceDays: 0`): после окончания платные функции деградируют сразу по таблице Р3. Предупреждения появляются за 7, 3 и 1 день. Переход на купленную лицензию не требует переустановки: новый токен заменяет пробный при следующем обновлении или командой `arkvory license activate`.
- **Тип лицензии** — поле `licenseType` подписанного документа. Известные значения этой версии:
  - `trial` — пробный период;
  - `standard` — одна установка;
  - `multi-site` — несколько установок одной организации (ADR 0077);
  - `enterprise` — по договору, разрешает офлайн-активацию и длинное офлайн-окно.

  Формат значения — `[a-z][a-z0-9-]{1,31}`. Неизвестное значение не делает документ недействительным (его может знать модуль новой версии), консоль показывает его как есть. Тип только описывает лицензию: права задают `features`, `limits` и сроки документа, а решение о функции принимает модуль (п. 6.5). Окончательный перечень типов и их состав — коммерческое решение владельца; ядро и `LicenseView` от него не зависят.

- **Несколько площадок** (открытый вопрос 6). Одна лицензия (`licenseId`) с лимитом `limits.installations` и отдельной активацией на каждую установку. Список `installations` в одном документе (п. 6.1) заменяется полем `installationId` в каждом документе активации.

### Р2. Проверка через хаб: онлайн-активация, офлайн-окно, офлайн-активация

**Замена I3 для платных модулей.** Для платных модулей этот пункт заменяет три утверждения I3: «лицензия проверяется офлайн, активации и обращений «домой» нет», «id лицензии … не уходят никогда» и «модуль не открывает собственных соединений к сервисам ProAnimaStudio». Альтернатива «Онлайн-активация лицензии» больше не отклонена: оба возражения (I3 и закрытые сети) закрывают офлайн-окно и офлайн-активация ниже. Дух I3 сохраняется:

- **Бесплатное ядро никогда не обращается к хабу за лицензией и не зависит от него.** Установка без платных модулей не делает ни одного запроса о лицензии, и ни одна функция ядра не ждёт хаб. Команды `arkvory license …` в `apps/deploy` в сеть не ходят.
- **Сверх активации — ничего.** Запрос активации содержит только id установки, `licenseId`, id и версии установленных платных модулей и версию релиза ядра. Ключ лицензии идёт заголовком авторизации по TLS с проверкой сертификата и в журналы не попадает. `licensee`, имена, адреса, содержимое, metadata и статистика использования не отправляются. Тело запроса собирает ядро (служба `license`, ниже), а не модуль, поэтому набор полей задан публичным кодом и проверяется тестом.
- **Активация не зависит от статистики ADR 0060.** Выключенная статистика её не выключает и не меняет, а хаб не использует данные активации как статистику (требование к хабу). Адрес хаба тот же — `config/hub.json`. При `--hub-off` онлайн-активации нет, остаётся офлайн-активация.
- Состав данных описывают коммерческие условия модуля (п. 9) и страница wiki о лицензиях. LICENSE §7 описывает ядро и не меняется (новый открытый вопрос 3 ниже).

**Документы.** Конверт п. 6.1 (`{"format": 1, "payload", "signature"}`, ключ подписи лицензий) сохраняется. Полезная нагрузка получает `format: 2`; формат 1 не выпускался (этап O3 не реализован), поэтому совместимость с ним не нужна. Поля (разбираются как `unknown`):

- `kind` — `activation` или `refusal`;
- `licenseId`, `product: "arkvory"`, `licensee`, `licenseType`, `installationId`;
- `activation` — `online` или `offline`;
- `modules` — id модулей и диапазоны версий, которые покрывает документ; `features`, `limits` — как в п. 6.1;
- `issuedAt`, `notBefore`, `expiresAt` — срок самого документа; `licenseNotAfter` (или `null`) и `graceDays` — льготный период продления по п. 6.1, не больше 90, у `trial` — 0;
- только для `online`: `refreshAfter` и `offlineGraceDays` (7–90, по умолчанию 30; для офлайн-активации файлом enterprise — до 365);
- `sequence` — монотонный номер для пары `licenseId` и `installationId`;
- только для `refusal`: `reason` — `revoked`, `expired` или `installation_replaced`.

Ядро отклоняет документ, у которого `sequence` не больше сохранённого. Так после смены плана или отзыва нельзя подложить старый токен с прежним набором функций.

**Онлайн-активация.** Сетевой обмен выполняет платный модуль, ядро хранит и проверяет документы.

1. `arkvory license activate --license-id <id> --key-file <file> [--token <file>]` на хосте процесса записи кладёт ключ в `config/licenses/<licenseId>.key` (права 0600, владелец — учётная запись службы). Ключ не попадает в БД, журналы и резервные копии. Начальный токен сайта, если передан, устанавливается сразу; без него состояние — `pending`.
2. Экземпляр модуля **в активном worker** (владение ADR 0042) получает от службы `license` тело запроса, адрес хаба и ключ, обращается к хабу и передаёт ответ ядру (`submit`). Ядро проверяет подпись, формат, `installationId`, `sequence` и время (п. 6.4) и записывает документ в `arkvory_license_activations` (expand-only миграция ядра, входит в копию). API, шлюзы чтения и остальные процессы читают состояние из БД. К хабу обращается один процесс установки; шлюзам чтения доступ к хабу не нужен.
3. **Обновление** — после `refreshAfter` (хаб ставит около суток), при запуске модуля и командой `arkvory license refresh`. Неудача повторяется с нарастающей паузой от 5 минут до 6 часов со случайным разбросом, не больше 48 попыток в сутки. Хаб ставит `expiresAt` онлайн-токена не дальше 7 дней; ядро не принимает онлайн-токен, живущий дольше 31 дня от `issuedAt`.
4. **Отзыв и смена плана вступают в силу при обновлении.** Новый документ `activation` меняет `features` и `limits`. Подписанный документ `refusal` сразу переводит лицензию в `revoked` или `expired`. Ответ без действительной подписи (4xx без документа, подмена посредником) ничего не отзывает: это неудачное обновление, и дальше действует офлайн-окно. Сократить срок может только подписанный отказ.
5. **Офлайн-окно.** Если токен не обновился (сеть, тайм-аут, 5xx, ответ без подписи), функции работают до `expiresAt`. Затем лицензия в состоянии `offline-grace` до момента «последнее успешное обновление + `offlineGraceDays`», по умолчанию 30 дней. Окно задаёт подписанный документ в пределах 1–30 дней, значение для каждого типа лицензии выбирает владелец. Оператор окно не продлевает, а документ со значением вне пределов ядро отклоняет (`license_invalid`). Отсчёт идёт по эффективному времени п. 6.4, поэтому перевод часов назад окно не продлевает.
6. **Предупреждения.** Консоль, `arkvoryctl doctor` и событие `module.health.changed` предупреждают через 24 часа без успешного обновления и за 7, 3 и 1 день до конца окна. Метрики: `arkvory_license_state{license,state}`, `arkvory_license_refresh_failures_total{license,reason}`, `arkvory_license_offline_grace_remaining_seconds{license}`. Правило оповещения — `ArkvoryLicenseOfflineGrace`.
7. **Восстановление на новую установку** (п. 6.2). Лицензия, как и раньше, переходит в `mismatch` с льготным периодом, а модуль сразу запрашивает активацию для нового id. Перенос активации между установками — правило хаба и типа лицензии. Явно освободить место можно командой `arkvory license deactivate <licenseId>` (её тоже выполняет модуль). Прежняя установка узнаёт о переносе из подписанного отказа `installation_replaced` при своём обновлении.

**Офлайн-активация** — для закрытых сетей и `--hub-off`:

1. `arkvory license request --license-id <id> --out <file>` пишет файл запроса: поля онлайн-запроса, время и случайный nonce. Секретов в файле нет, ядро в сеть не ходит.
2. Администратор переносит файл на машину с доступом к сайту, загружает его в личном кабинете и получает файл активации с `activation: offline`.
3. `arkvory license install <file>` проверяет файл так же, как онлайн-токен. У офлайн-активации нет `refreshAfter` и офлайн-окна: она действует до своего `expiresAt`, но не дольше `licenseNotAfter`. Верхнюю границу срока задаёт тип лицензии. Отзыв для такой установки вступает в силу только при истечении файла или установке нового; это явное свойство офлайн-активации, его показывают консоль и условия модуля.

**Служба `license`** (ADR 0083, п. 2.4) для модулей с `licenseFeature`:

- `view()` — `LicenseView`. Он получает поля `licenseType`, `activation`, `lastRefreshAt`, `refreshFailing`, `offlineGraceUntil` и `reason`; состояния — `none`, `pending`, `valid`, `offline-grace`, `grace`, `expired`, `revoked`, `mismatch`, `invalid`;
- `activationRequest(licenseId)` — тело запроса активации;
- `hubEndpoint()` — адрес хаба из `config/hub.json` или `null`;
- `licenseKey(licenseId)` — чтение ключа лицензии;
- `submit(document)` — проверка и сохранение документа с машинным результатом: `accepted`, `stale_sequence`, `invalid_signature`, `installation_mismatch`, `out_of_bounds`;
- `pendingRequests()` — команды `refresh` и `deactivate`, которые записал хост.

Клиентские модули (`side: client`) лицензию не активируют: состояние сервера они видят через `capabilities` и `system/license`.

**Вне ядра.** Платный модуль может дополнительно защищать свою логику лицензии. Как именно — его дело: это вне ядра и в публичном репозитории не описывается (Р5). Ядро от таких проверок не зависит, а модуль при любом их исходе обязан выполнять I1 и L1–L7.

### Р3. I1 без исключений; обновлённая таблица состояний

I1 остаётся абсолютным и распространяется на все новые состояния. Отсутствие, истечение и отзыв лицензии, конец пробного периода, истёкший токен и недоступность хаба **никогда** не делают данные нечитаемыми или невосстановимыми и не выключают функции бесплатного ядра. Хаб не стоит на пути чтения, скачивания, резервного копирования, восстановления, проверки, экспорта и `evacuate`: всё это работает без сети и без лицензии. Деградируют только платные функции.

### Р4. Хаб согласует обновления ядра и платных модулей

- **Матрица совместимости.** Подписанный манифест релиза (`arkvory-release.json`, ADR 0060) получает поля `extensionApi` (версия API расширений релиза) и `extensionApiSupported` (поддерживаемые major по ADR 0079). Подписанный манифест модуля уже содержит `extensionApi` и `core` (п. 3.1). Из них хаб строит матрицу «релиз ядра ↔ версии модулей ↔ диапазон API расширений» и показывает её в своей консоли.
- **Согласованный набор.** Человек одобряет для канала (`stable`, `beta`) не отдельные файлы, а **набор**: версию ядра и совместимые с ней версии модулей. Набор, в котором модуль несовместим с ядром, хаб одобрить не даёт. Доля раскатки и пауза — как в ADR 0060. Обновление одного модуля — тоже набор: прежнее ядро и новая версия модуля.
- **Ответ хаба** на проверку обновлений несёт весь одобренный набор: ядро и все модули набора со ссылками, SHA-256 и подписями. Установка не сообщает хабу, какие модули у неё стоят: updater берёт из набора только установленные. Поэтому проверка обновлений не передаёт новых данных сверх ADR 0060.
- **Ядро хабу не доверяет** (п. 7). Updater сам проверяет подписи релиза и каждого пакета и заново сверяет совместимость по подписанным манифестам. Расхождение с матрицей хаба — отказ `module_incompatible`, а не повод поставить набор.
- **Одна транзакция.** Ядро и модули ставятся одной записью журнала ADR 0059 с полями `release.before/after` и `modules.before/after` (id, версия, SHA-256 пакета):
  1. до фазы `prepared` скачиваются и проверяются все файлы набора;
  2. если меняется схема ядра или хотя бы у одного модуля есть новые миграции, нужна свежая проверенная копия;
  3. переключение, перезапуск служб и проверка готовности всех процессов с новым отпечатком плана (п. 5);
  4. если набор не стал готов, откат возвращает **и** прежний релиз, **и** прежний набор модулей (их пакеты хранятся до следующего успешного изменения, п. 4); после применённой миграции — `maintenance-required` и `recover`, как в ADR 0059.
- **Отказ без изменений.** Если в наборе нет совместимой версии установленного модуля, закреплённая версия (`module pin`) несовместима с новым ядром или пакет не прошёл проверку, обновление отклоняется до любых изменений с `module_incompatible` и списком модулей. `--disable-incompatible-modules` работает как в п. 4.
- **Без хаба.** Обход через GitHub (ADR 0060) даёт только релиз ядра. Updater ставит его, только если все установленные модули совместимы с ним по своим манифестам, иначе — `module_incompatible`. В закрытой сети набор ставится из локального каталога (`arkvory update --artifact <dir>` с релизом и пакетами модулей) с той же проверкой и той же записью журнала.
- Маршруты наборов, матрицы и одобрения в хабе — изменение pas-Hub по его процессу (этап O6).

### Р5. Защита от анализа кода — только у платных модулей

**Ядро не обфусцируется** и не получает защиты от анализа:

- код ядра открыт для чтения и изменения внутри организации (LICENSE §1, ADR 0061). Запутывание противоречило бы обещанию лицензии и мешало бы аудиту безопасности, ради которого код открыт;
- безопасность ядра держится на подписях с открытым ключом. Релизы, модули, список отзыва и документы лицензий проверяются встроенными открытыми ключами Ed25519, а закрытые ключи не попадают в репозиторий и сборки. Знание кода проверки не помогает подделать подпись, поэтому скрывать его незачем (принцип Керкгоффса);
- лицензия в ядре — не защита от копирования (п. 6.5). Ядро не принимает решений о функциях, поэтому обход его проверок ничего не открывает: платных функций в ядре нет.

**Платные модули** могут защищать свой код и свою логику лицензии. Это их ответственность и вне ядра; методы в публичном репозитории не описываются. Ядро ставит только внешние условия, без которых модуль не подписывается: формат пакета п. 3.1 (в версии 1 — без нативных дополнений и скриптов установки, хеши всех файлов в манифесте), I1–I4 и L1–L7, набор `readability`, никаких сетевых запросов сверх Р2, машинные коды ошибок вместо стеков (ADR 0051), пределы цикла событий и памяти (ADR 0083, п. 12). Защита модуля, которая мешает этим условиям, — дефект модуля.

### Что заменено

- **I3** — для платных модулей заменён Р2; для ядра не меняется.
- **Таблица состояний п. 2** — заменена таблицей Р3.
- **П. 6.1** — полезная нагрузка формата 2 (Р2): `installationId` вместо списка `installations`, `licenseType`, `activation`, сроки документа, `sequence`.
- **П. 6.2** — ручная передача id установки остаётся для офлайн-активации; при онлайн-активации id отправляет модуль.
- **П. 6.3** — к `install` и `remove` добавлены `activate`, `refresh`, `request`, `deactivate`; ключ лицензии — файл в `config/licenses/`, вне БД и копий.
- **П. 6.5** — состояния `LicenseView` дополнены (`pending`, `offline-grace`, `revoked`), служба `license` получила методы активации.
- **П. 8** — `GET /api/v1/system/license` добавляет `licenseType`, `activation`, `lastRefreshAt`, `offlineGraceUntil` и `reason` (аддитивно); новые коды ошибок `license_revoked` и `license_activation_required`.
- **Альтернатива «Онлайн-активация лицензии»** — для платных модулей принята (Р2).
- **Проверка I3** заменяется:
  - установка без платных модулей не делает запросов о лицензии (поддельный хаб не получает ни одного);
  - тело запроса активации содержит ровно поля Р2 и не содержит `licensee`; выключенная статистика не добавляет и не убирает полей;
  - отказ без подписи не отзывает лицензию; документ с прежним `sequence` отклоняется;
  - перевод часов назад не продлевает офлайн-окно;
  - при недоступном хабе чтение, копия и восстановление идут без задержки; запись после конца окна переходит в форму ядра и после обновления возвращается в режим модуля;
  - набор «ядро и модуль» ставится и откатывается одной записью журнала; несовместимый набор отклоняется до изменений.
- **Открытые вопросы владельцу.** Вопрос 5 решён: пробный период — 30 дней без льготного периода; льготный период продления остаётся 30 дней (до 90); офлайн-окно — 14 дней (1–30). Вопрос 6 решён: одна лицензия с активацией на каждую установку. Остальные вопросы остаются открытыми.

### Новые открытые вопросы

1. Срок онлайн-токена (до 7 дней) и интервал обновления (около суток) предложены; окончательные значения по типам лицензий владелец выбирает в пределах Р2.
2. Число одновременных активаций и правило переноса между установками для `standard` и `multi-site` (правило сайта и хаба).
3. LICENSE §7 перечисляет данные, которые отправляет ядро. Активацию выполняет платный модуль по своим коммерческим условиям; юрист должен проверить, достаточно ли этого или в LICENSE §7 нужна ссылка на условия модулей. Этот ADR текст LICENSE не меняет.
4. Наибольший срок офлайн-активации для `enterprise` (предложено: не больше года и не позже `licenseNotAfter`).
