# 0083. Точки расширения ядра: хранение, копии, каталог, лента, данные, маршруты, деревья каталогов

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-17. Решение дополняет [ADR 0079](0079-extension-modules.md) (п. 5 «Точки расширения», п. 2 «Пакеты»), уточняет первую часть этапа X1 (`packages/extension-api` 0.1.0) и опирается на модель поставки [ADR 0078](0078-open-core-modules-and-licenses.md) и уровни доверия ADR 0082 ([ADR 0082](0082-custom-plugins.md), PR #29, на момент написания не влит). Оно меняет публичный контракт модулей (`extension-api`, аддитивно до 1.0.0), долговечность (перенос blob между хранилищами, разделы точки копии с содержимым, каталог данных модуля), границу прав (чтение каталога модулями) и публичный контракт `/api/v1` (аддитивно). До решения владельца код не пишется. Решение владельца 2026-10-17 о базовой реализации деревьев (N8) — в конце ADR. Связано с [ADR 0004](0004-native-standalone-core.md), [ADR 0008](0008-gateway-bandwidth-budgets.md), [ADR 0009](0009-leased-read-gateways.md), [ADR 0035](0035-online-cleanup.md), [ADR 0042](0042-bounded-storage-ownership.md), [ADR 0051](0051-error-contract.md), [ADR 0054](0054-built-in-backup-vault.md), [ADR 0058](0058-pull-mirrors.md), [ADR 0064](0064-raw-files-by-path.md), [ADR 0070](0070-encrypted-backup-vault.md), [ADR 0071](0071-s3-backup-vault.md), [ADR 0072](0072-single-site-ha.md), [ADR 0073](0073-capacity-counters-and-pools.md), [ADR 0074](0074-staged-file-adoption.md), [ADR 0075](0075-catalog-query-bounds.md), [ADR 0076](0076-download-scheduling.md), [ADR 0080](0080-event-integrations.md), [ADR 0081](0081-mcp-and-agent-skill.md).

## Контекст

ADR 0079 перечисляет точки расширения на уровне «что есть», но для модулей ядра и модулей вне репозитория не хватает контрактов там, где модуль встречается с механизмами долговечности ядра: завершением загрузки, очисткой, барьером копии, восстановлением, шлюзами чтения. Общие потребности, которые не закрыты:

- **другие раскладки и хранилища** — второй локальный том, будущее S3-хранилище ядра, хранилища заказчика. Им нужны выбор хранилища для новых данных, перенос опубликованного blob, завершение загрузки из частей, которые хранилище уже приняло, и чтение без физического пути;
- **оптимизации передачи** — модулю нужны маршруты с теми же Range, ETag, очередью и бюджетами полосы, что у ядра, и чтение каталога с ACL;
- **клиенты синхронизации каталогов** — сегодня каждая команда CLI работает с одним файлом;
- **собственные сервисы** — модулю нужны лента изменений, своё место на томе данных, ограниченные вычисления вне цикла событий и обмен значениями с другими модулями.

Факты кода (ветка `origin/main` после PR #26):

- **Порт `BlobStore`** (`packages/application/src/ports.ts`) — `putPart`, `readParts`, `put`, `verify`, `read` с Range, `exists`, `duplicate`, необязательный `collect`; у каждого метода необязательный `backendId`. Единственная реализация — `LocalBlobStore` (`packages/infrastructure/src/local-blobs.ts`): `blobs/<uploadId>`, `parts/<uploadId>/<index>-<sha256>`, `staging/<uploadId>/<uuid>`. Точка долговечности — `fsync` временного файла → `link` → синхронизация каталога; повтор `put` при существующем файле проверяет его хешем.
- **Маршрутизация хранилищ не подключена.** `RoutedBlobStore` (`routed-blobs.ts`) и правила `resolveStorageBackend` (`packages/domain/src/storage-routing.ts`) есть, но приложения их не создают; `StorageService` без `StorageRouter` пишет `storage_backend = 'default'` в `arkvory_uploads` (`varchar(64)`). Политика хранения репозитория (`storage-policy-routes.ts`) управляет только сроками хранения и квотой. Переноса blob между хранилищами нет.
- **Завершение multipart** (`StorageService.complete`, `packages/application/src/storage.ts`) читает все части и пишет объект заново через `put`: SHA-256 целого нельзя получить из хешей частей (ADR 0074). Большие объекты завершает задание worker (`apps/worker/src/completion.ts`) с арендой, fencing по generation и повтором. Перенос готового файла без копии (`StagedFile`, `adoptStagedFile`) работает только для одного объекта на том же томе.
- **Удаление содержимого** идёт в порядке `upload lock → content lock → try 18471/18 shared → барьер открыт и нет pins → unlink → unlock` (`unlink-admission.ts`, ADR 0035, ADR 0054). Скачивания и разбор ZIP держат разделяемую блокировку содержимого (`PostgresContentPins`); очистка только пробует исключительную и при занятости откладывает объект. Свободные номера рекомендательных блокировок пространства 18471 начинаются с 22.
- **Резервная копия** закрепляет `(upload_id, job_id)` по неизменяемому id upload и копирует каждый blob целиком в `blobs/<2 hex>/<id>` vault с проверкой SHA-256 (`backup-capture.ts`, `file-vault.ts`). Строка инвентаря — `{id, size, sha256}` без хранилища. `LocalContentSource` получает конкретный `LocalBlobStore` и распознаёт пропажу по `ENOENT`.
- **Физические пути вне хранилища:** `ZipManifestReader` (`packages/infrastructure/src/upack.ts`) открывает `blobs.contentPath(id)` через yauzl и игнорирует `storageBackend`; он же используется зеркалами (`apps/worker/src/mirror-target.ts`). `protocol-services.ts` создаёт временные области raw и OCI в `blobs.root`; `restore-storage.ts` проверяет пустоту чтением `blobs.root`.
- **Проверка места** — `statfs` по байтам (`ARKVORY_STORAGE_RESERVE_BYTES`, 1 ГиБ); свободные inode не проверяет никто.
- **Выдача содержимого** — `createContentSender` (`apps/api/src/download-routes.ts`): pin → ACL `content.read` → ETag `"sha256:<hex>"`, 304, `If-Range`, один диапазон (`range.ts`), HEAD → допуск ADR 0076 (`download-admission.ts`) → бюджет полосы → поток. `Cache-Control: private, no-store` ставит глобальный хук. Общее тело Fastify — 64 КиБ; потоковые маршруты снимают разбор тела.
- **Шлюз чтения** — тот же `apps/api` с ролью `reader`; запросы кроме GET и HEAD получают `read_only` в общем хуке.
- **Каталог.** ACL проверяют сценарии `application` до обращения к хранилищу каталога; хранилища (`PostgresBrowse`) прав не проверяют. В доступном репозитории отсутствующий и неопубликованный артефакт одинаково дают `not_found`.
- **Лента.** `arkvory_events` ADR 0080 ещё не реализована; есть лента репозитория `readCatalogChanges` и курсоры вебхуков `arkvory_webhook_state`.
- **Вычисления.** `node:worker_threads` используется только сторожевым потоком цикла событий; хеширование потоковое в основном потоке, zlib уже работает вне цикла событий.
- **Клиент.** SDK проверяет SHA-256 скачивания (`verified-download.ts`), загрузка — частями с чекпойнтом. Ни SDK, ни CLI не работают с каталогами и ZIP. UPack — ZIP с `upack.json`; сервер читает только центральный каталог и `upack.json`, содержимое записей не проверяет. Список путей (`R/assets/page`) не отдаёт размер и SHA-256.
- **`extension-api` 0.1.0.** `ModuleSource = 'builtin' | 'signed'` (и копия этого объединения в `plan-rules.ts`); `kind` — закрытый список, неизвестное значение делает манифест нечитаемым; поля `publisher` нет; контекст модуля (`ApiModuleContext`) объявлен в `apps/api/src/modules.ts`; `NAME_PREFIX` допускает префикс таблиц до 48 символов, а внешний префикс `arkvory_x_<id>__` при id из 32 символов занимает 44 из 63 байт имени PostgreSQL; снимок `api-report.d.ts` склеивает все `.d.ts`, включая внутренние `plan-rules` и `plan-order`.

## Решение

### 1. Общие правила точек расширения

Правила действуют для каждой точки п. 3–15.

- **Базовая реализация обязательна.** У каждой точки есть реализация в ядре или тестовая реализация в `extension-testkit` (ADR 0078, п. 1.4) и контрактный набор. Точка без набора не попадает в `EXTENSION_API_VERSION`; policy-тест сопоставляет точки и наборы (ADR 0079, п. 7).
- **Узкие службы хоста.** Модуль объявляет нужные службы ядра в новом необязательном поле манифеста `uses` (список имён, п. 2.4). `create(context, config)` получает в `context.services` только объявленные службы. `requires`/`provides` остаются связями между модулями (п. 15).
- **Типы — в `extension-api`, реализации — в `infrastructure`.** Интерфейсы ниже переносимые: без Node, потоки — `AsyncIterable<Uint8Array>`, отмена — `ModuleSignal`, размеры — `number` с `Number.isSafeInteger` на границе, 64-битные значения в wire — десятичные строки. Адаптеры связывают их с внутренними портами; `domain` и `application` о модулях не знают.
- **Ядро остаётся владельцем гарантий.** SHA-256 и размер проверяет ядро, ACL проверяет ядро, удаление содержимого идёт только через допуск удаления ядра, долговечность публикации не ослабляется. Модуль может сделать путь быстрее, но не может сделать его менее проверенным.
- **Всё ограничено.** У каждой службы есть срок, предел параллелизма, размер страницы или сообщения; превышение даёт машинный код (`rate_limited`, `module_quota_exceeded`, `busy` с `Retry-After`), а не очередь без границы.
- **Ошибки** — коды контракта ADR 0051. Модуль возвращает свои коды только в форме `[a-z][a-z0-9_]{0,63}`; ядро не передаёт клиенту стеки и пути.

### 2. Уточнения формы API (по ревью PR #26)

**2.1. Открытый `ModuleSource`.** `MODULE_SOURCES = ['builtin', 'signed', 'operator', 'development'] as const`, `ModuleSource = (typeof MODULE_SOURCES)[number]`. `ReadModule.source` в `plan-rules.ts` использует этот тип, а не свою копию. Правила владения уже трактуют любой источник, кроме `builtin`, как внешний; так остаётся. Wire-поле `source` в `system/modules` уже открытая строка.

**2.2. Открытый `kind`.** Манифест принимает `kind` по шаблону `[a-z][a-z0-9-]{1,31}`; `MODULE_KINDS` — известные этой версии значения. Неизвестный `kind` больше не делает манифест нечитаемым: `planModules` даёт `unknown_kind` для **включённого** модуля, а выключенный модуль с неизвестной точкой остаётся в плане и в `system/modules`. Так updater ADR 0078, п. 4 отличает модуль новой точки от испорченного. Новые значения этого ADR: `service` (модуль без своей точки ядра, пользуется только службами `uses`: маршруты, лента, данные) и клиентский `tree-transfer` (п. 10).

**2.3. `publisher` и пространство id.** Поле `publisher` (`[a-z][a-z0-9-]{1,31}`). Встроенные модули — `proanimastudio`. Правило id по источнику проверяет `planModules` (`id_namespace_mismatch`): `operator` и `development` — только `op-[a-z][a-z0-9-]{1,20}`; `builtin` и `signed` — никогда не `op-`. Соответствие `publisher` ключу подписи проверяет загрузчик (ADR 0082, п. 1), а не план.

**2.4. Контекст модуля в `extension-api`.**

```ts
export interface ModuleContext<Services> {
  readonly role: ModuleRole;
  readonly source: ModuleSource;
  readonly mode: 'full' | 'read-only' | 'restore';
  readonly signal: ModuleSignal; // остановка процесса
  readonly log: ModuleLog; // уровни, поля без секретов, ограничение частоты
  readonly metrics: ModuleMetrics; // только под metricPrefix
  readonly services: Services; // только объявленные в `uses`
}
export const HOST_SERVICES = [
  'blob-store',
  'staged-completion',
  'catalog-read',
  'content-read',
  'change-feed',
  'data-directory',
  'routes',
  'compute',
  'license',
] as const;
```

`ApiModuleContext` в `apps/api` становится `ModuleContext<ApiServices>`. `planModules` проверяет, что каждое имя `uses` известно и доступно ролям и источнику модуля по матрице п. 16 (`service_unavailable`).

**2.5. Бюджет длины префикса таблиц.** PostgreSQL молча усекает идентификаторы длиннее 63 байт; усечённое имя таблицы, индекса или ограничения могло бы совпасть с чужим. Поэтому:

- `tablePrefix` — не длиннее 36 символов (`table_prefix_too_long`), и у модуля с таблицами id не длиннее 24 символов. Внешний префикс `arkvory_x_<id>__` тогда занимает не больше 36 и оставляет 27 символов на имя и суффиксы (`_pkey`, `_<столбец>_idx`). Для `op-` id ADR 0082 это совпадает с пределом `op-` + 21 символ; префикс таблиц плагина пишется с двойным `_`, как у остальных внешних модулей (`arkvory_x_op_<name>__`);
- мигратор модулей до выполнения шага сверяет каждое создаваемое имя (таблица, индекс, ограничение, последовательность, триггер) с префиксом модуля и длиной 63 байт и отказывает (`identifier_too_long`, `identifier_not_owned`), а не полагается на усечение.

**2.6. Снимок только публичных деклараций.** `scripts/extension-api-report.mjs` строит снимок из `index.d.ts` по экспортируемым символам и тому, на что они ссылаются, а не склейкой всех `.d.ts`. `checkModules`, `checkOwnership`, `startOrder`, `ReadModule` не входят в снимок; `RuleCode` экспортируется как `ModulePlanRuleCode`, потому что входит в публичный `ModulePlanProblemCode`. Тест: каждая декларация снимка достижима из `index.ts`; изменение внутреннего модуля не меняет снимок.

### 3. N1. Завершение загрузки из частей, принятых хранилищем

**Зачем.** Хранилище, которое само умеет собрать объект из уже принятых частей (например, объектное хранилище с составлением частей на своей стороне), не должно получать объект второй раз через ядро. Сегодня завершение читает части и пишет объект заново.

**Контракт** (необязательная возможность экземпляра `storage-backend`, служба `staged-completion`):

```ts
export interface StagedCompletion {
  /** Собирает ещё не видимый объект из принятых частей; повтор для того же id идемпотентен. */
  compose(id: string, parts: readonly PartRef[], signal: ModuleSignal): Promise<StagedObject>;
}
export interface StagedObject {
  readonly size: number;
  read(range?: ByteRange): AsyncIterable<Uint8Array>; // байты будущего объекта
  /** Делает объект опубликованным и долговечным; повтор после успеха — успех. */
  commit(expected: BlobDescriptor, signal: ModuleSignal): Promise<void>;
  discard(): Promise<void>; // идемпотентно
}
```

**Порядок завершения** (`StorageService.complete` и задание worker, если хранилище upload даёт `StagedCompletion`):

1. под `Catalog.exclusive(id)` (как сегодня) проверка частей `checkParts`;
2. `compose` → ядро само читает `staged.read()` потоком и считает размер и SHA-256 (в задании worker для объектов больше порога синхронного завершения); при несовпадении — `discard`, `integrity_mismatch`, upload остаётся по прежним правилам;
3. `commit(expected)` — точка долговечности хранилища: объект неизменяем и переживает заявленный класс отказов;
4. `mutation.publish` — фиксация каталога. Порядок «blob долговечен → каталог» не меняется.

**Инварианты и отказы.** Ядро не принимает размер или хеш, измеренные хранилищем: одно полное чтение остаётся ценой проверки (ADR 0078, L6). Падение между `commit` и `publish` повторяется: `compose` для опубликованного id возвращает объект, ядро проверяет его снова и публикует. Части не удаляются до `publish`; затем их убирает очистка ядра через `collect`. Отмена между шагами вызывает `discard`, кроме шага 4. Хранилище в режиме `read-only` отвечает `read_only` на `compose`; тогда ядро идёт обычным путём п. 13 (чтение частей и запись в хранилище ядра).

**Базовая реализация.** `LocalBlobStore` возможности не объявляет: обычный путь (чтение частей → `put`) остаётся базовым. `extension-testkit` содержит тестовое хранилище `directory-backend`, у которого `compose` возвращает объект, читающий файлы частей подряд, а `commit` записывает долговечную ссылку на них; набор `staged-completion` проверяет повтор после падения на каждом шаге, подмену байта части после `compose` (ядро отклоняет), `discard` и отказ `read_only`.

**Где.** Процессы `api` (синхронное завершение) и `worker`. Только в процессе (п. 16).

### 4. N2. Перенос опубликованного blob между хранилищами

**Зачем.** Второй том, вывод хранилища из работы, эвакуация данных модуля в форму ядра (ADR 0078, L3) — это один механизм: переписать байты опубликованного blob в другое хранилище и переключить `storage_backend`, не нарушая чтений, закреплений копии и очистки. Сегодня переноса нет.

**Операция ядра.** `arkvory storage rehome --from <backend> --to <backend> [--repository <r>] [--limit <n>]` на хосте и `POST /api/v1/system/storage/moves` (глобальный администратор, этап позже). `arkvory module evacuate` ADR 0078 вызывает ту же операцию с целью «хранилище ядра».

**Состояние.** Таблица `arkvory_blob_moves` (expand-only миграция ядра): `id`, `upload_id`, `from_backend`, `to_backend`, `state`, `generation`, `lease_until`, `attempts`, `error_code`. Состояния: `planned → copied → switched → released`, а также `skipped` (upload больше не опубликован) и `failed` (после 5 попыток). Таблица входит в исключённые реестра копии: перенос — свойство источника.

**Шаги одного blob** (worker, singleton `18471/22`, по умолчанию 2 переноса параллельно, бюджет полосы `ARKVORY_REHOME_BYTES_PER_SECOND`):

1. **Копия.** Разделяемая блокировка содержимого upload (как у скачивания) на время копии. `to.put(id, descriptor, from.read(id))`: цель проверяет размер и SHA-256 и делает объект долговечным; существующий объект цели проверяется хешем (повтор идемпотентен). `checkSpace` цели — до начала. → `copied`.
2. **Переключение.** Короткая транзакция под блокировкой upload: `UPDATE arkvory_uploads SET storage_backend = $to WHERE id = $1 AND storage_backend = $from AND status = 'available'`. Ноль строк: если уже `$to` — шаг выполнен; иначе (upload отменён или удалён) — `skipped`, и копия в цели удаляется шагом 3 с обратными ролями. Никакой ввод-вывод под транзакцией не идёт. → `switched`.
3. **Освобождение источника** — обычное физическое удаление ядра: `upload lock → content lock (try exclusive) → try 18471/18 shared → барьер открыт и нет pins upload → from.collect(id, true) → unlock`. Занятость любой блокировки откладывает шаг, ожидания нет. → `released`.

**Читатели и копии.** Чтение разрешает хранилище по строке upload при каждом запросе. Скачивание, начатое до переключения, держит разделяемую блокировку содержимого и дочитывает источник: шаг 3 его ждёт. Точка копии закрепляет upload по id; пока pin есть, источник не освобождается, поэтому захват, прочитавший старое хранилище в инвентаре, дочитает его. Инвентарь точки получает необязательное поле `backend` (п. 11) и не зависит от переноса: байты одинаковы.

**Очистка и счётчики.** Если очистка ADR 0035 удаляет upload во время переноса, она удаляет копию в текущем `storage_backend`; копию в другом хранилище освобождает задание переноса (оно знает обе стороны). `arkvory_upload_bytes` не меняется: это логический учёт. Метрики `arkvory_blob_moves{state}`, `arkvory_blob_move_bytes_total`.

**Отказы.** Цель не принимает записи (`acceptsWrites() = false`) — перенос не начинается (`backend_read_only`). Источник в режиме `read-only` (модуль без лицензии) — разрешён: это эвакуация. Потеря аренды — fencing по generation, как у заданий завершения. Сбой на любом шаге повторяет только этот шаг.

**Базовая реализация.** Два экземпляра `LocalBlobStore` на разных томах (п. 13) и `directory-backend` из testkit. Набор `rehome`: падение после каждого шага, гонка с удалением и online GC, активное скачивание во время переключения, точка копии во время переноса, повтор всего задания.

**Где.** Только `worker` и хост; модули переносы не выполняют сами.

### 5. N3. Раздел точки копии, покрывающий содержимое

**Зачем.** Хранилище со своей раскладкой или с собственными средствами копирования (например, серверное копирование между корзинами будущего S3-хранилища ядра) может выгрузить свои объекты в точку дешевле, чем ядро прочитает каждый blob целиком. Ядро разрешает это только если точка остаётся восстановимой и проверяемой ядром без лицензии (ADR 0078, I1, I2).

**Контракт** (расширение `BackupParticipant` ADR 0079, п. 5.4, только `dataClass: layout`):

```ts
export interface ContentSection {
  /** Какие blob из порции инвентаря модуль выгрузит сам; остальные ядро копирует целиком. */
  cover(entries: readonly InventoryEntry[], signal: ModuleSignal): Promise<readonly string[]>;
  export(ids: readonly string[], out: SectionWriter, signal: ModuleSignal): Promise<void>;
  /** Байты одного blob прямо из раздела точки, без восстановления. */
  open(section: SectionReader, id: string, range?: ByteRange): AsyncIterable<Uint8Array>;
  import(section: SectionReader, target: RestoreTarget, signal: ModuleSignal): Promise<void>;
}
```

**Инварианты:**

- манифест точки перечисляет модуль (id, версия, SHA-256 пакета, `dataClass`), а строка инвентаря покрытого blob получает `section: "<module>"` вместо копии в `blobs/` vault (аддитивное поле формата точки);
- пакет модуля лежит в точке (ADR 0078, L2); восстановление и проверка загружают его в режиме `restore` без лицензии;
- `SectionWriter` и `SectionReader` — порты vault ядра: шифрование ADR 0070, будущий S3-vault ADR 0071, атомарная публикация точки и удаление по сроку хранения работают как для остальных файлов. Модуль не пишет файлы vault сам;
- `verify --deep` для каждого покрытого blob читает `open(...)` из раздела и сверяет размер и SHA-256 с инвентарём — та же сила проверки, что у blob в форме ядра;
- восстановление после `import` читает каждый покрытый blob через путь чтения модуля и сверяет размер и SHA-256 до загрузки таблиц; несовпадение — отказ восстановления (цель пуста, ADR 0054, ничего не портится);
- `arkvory-backup convert <point> --core-form` пишет новую точку, где покрытые blob лежат целиком; работает инструментами ядра с пакетом из точки и без лицензии. Это запасной путь, если модуль отозван с `readOnly: false` (ADR 0078, п. 3.4);
- pins и барьер не меняются: покрытые blob закреплены, пока `export` их читает.

**Отказы.** Ошибка `cover` или `export`, недоступный модуль — ядро копирует эти blob целиком, точка остаётся полной (предупреждение `section_fallback`). Отказ при `commit` точки — как у всей точки.

**Базовая реализация.** У ядра раздела нет: `local-storage` не объявляет `ContentSection`, и это поведение по умолчанию. `extension-testkit` содержит тестовую раскладку `wrapped-layout` (каждый blob — файл со своим заголовком и другим именем) с разделом, который копирует свои файлы. Набор `content-section`: восстановление ядром без лицензии, подмена байта в разделе ловится `verify --deep` и восстановлением, `convert --core-form`, отказ модуля во время `export`, шифрованный vault.

**Где.** Агент копий (`backup`) и `arkvory-backup`. Только в процессе, уровни 1–2.

### 6. N4. Чтение каталога модулями без утечки существования

**Зачем.** Маршрутам модулей и фоновым модулям нужно читать артефакты, пакеты, пути и поиск с теми же правами, что у пользователя или у сервисного принципала модуля.

**Контракт** (службы `catalog-read` и `content-read`):

```ts
export interface CatalogRead {
  artifact(scope: AccessScope, repository: string, id: string): Promise<ArtifactView | null>;
  artifacts(scope: AccessScope, repository: string, page: PageRequest): Promise<Page<ArtifactView>>;
  batch(scope: AccessScope, repository: string, ids: readonly string[]): Promise<BatchView>;
  resolvePackage(
    scope: AccessScope,
    repository: string,
    query: PackageQuery,
  ): Promise<PackageView | null>;
  asset(scope: AccessScope, repository: string, path: string): Promise<AssetView | null>;
  search(scope: AccessScope, query: SearchQuery): Promise<Page<ArtifactView>>;
}
export interface ContentRead {
  open(scope: AccessScope, ref: ContentRef, range?: ByteRange): Promise<ContentHandle | null>;
}
```

- `AccessScope` — непрозрачный объект ядра: принципал запроса маршрута (п. 9), сервисный принципал модуля (ADR 0082, п. 9) или их пересечение. Модуль не может создать его из id и не может расширить.
- **Нет оракула существования.** `null` означает одинаково «нет», «не опубликован», «нет права» и «нет репозитория»; `batch` возвращает недоступные id в `missing` вместе с отсутствующими. Время ответа не зависит от причины сильнее, чем у маршрутов ядра.
- Права проверяют сценарии `application` (`authorizeAction`, `StorageService.artifact`) — тот же код, что у `/api/v1`; адаптер в `infrastructure` вызывает их, SQL модулю не виден. Значения metadata в `ArtifactView` только при `annotation.read`.
- `ContentRead.open` берёт разделяемую блокировку содержимого (ADR 0035), проверяет `content.read` и даёт `ContentHandle` с `descriptor`, `read(range)` и `release()`; обработчик маршрута не держит его дольше ответа (ядро освобождает при закрытии ответа).
- **Пределы** — правила ADR 0075: страница до 100, `batch` до 100 id, поиск по репозиториям с `artifact.list` (не больше 1000), курсоры непрозрачны.

**Базовая реализация** — сами сценарии ядра; набор `catalog-read` в testkit проверяет одинаковый ответ для отсутствующего, неопубликованного и запрещённого объекта, сужение пересечением и пределы.

**Где.** `api`, `reader`, `worker`. Плагины вне процесса читают каталог тем же кодом через `api.call` (ADR 0082, п. 7.2).

### 7. N5. Внутренняя лента изменений для фоновых модулей

**Зачем.** Модули индексов, кешей и интеграций реагируют на публикации и удаления. Опрос каталога дорог и пропускает удаления.

**Контракт** (служба `change-feed`, роль `worker`):

```ts
export interface ChangeFeed {
  subscribe(spec: {
    readonly consumer: string; // [a-z][a-z0-9-]{0,31}, уникально в модуле
    readonly types: readonly string[]; // имена каталога событий ADR 0080 или префикс `artifact.*`
    readonly batch: number; // 1..500
    handle(events: readonly ChangeEvent[], signal: ModuleSignal): Promise<void>;
    resync(reason: 'epoch_changed' | 'cursor_expired', signal: ModuleSignal): Promise<void>;
  }): FeedSubscription;
}
```

- **Источник** — строки `arkvory_events` ADR 0080 с теми же позициями, эпохой и разделами. Публичная лента `GET /api/v1/events` и подписки от этой службы не меняются; внутренняя служба не создаёт второй очереди.
- **At-least-once.** Ядро вызывает `handle` и только после успешного завершения сохраняет курсор. Курсор — в состоянии модуля, которое ведёт ядро: `arkvory_module_cursors(module_id, consumer, epoch, position, revision)` с CAS по ревизии (expand-only миграция ядра, входит в реестр копии). Падение между `handle` и сохранением повторяет пачку; модуль узнаёт повтор по `id` события и обрабатывает его идемпотентно.
- **Смена эпохи и истёкший курсор** вызывают `resync`; после него курсор ставится на `head`. Модуль восстанавливает состояние чтением каталога (п. 6).
- **Видимость.** Модуль уровня 1–2 в процессе читает все события с областью `repository` и `system` своего типа; события безопасности — никогда. Данные, которые модуль затем отдаёт пользователям, проходят ACL п. 6.
- **Один потребитель.** Цикл работает только в активном worker (владение ADR 0042); в HA курсор переживает переключение вместе с БД.
- **Пределы и отказы.** `handle` ограничен сроком (по умолчанию 60 с); ошибка — повтор с нарастающей паузой до 5 минут, без пропуска событий. Метрики `arkvory_module_feed_lag_events{module,consumer}` и `arkvory_module_feed_failing{module,consumer}`.

**Базовая реализация** — доставка вебхуков ADR 0080, этап E5, переводится на ту же службу; testkit содержит набор `change-feed`: повтор после падения, смена эпохи, истёкший курсор, CAS курсора двумя процессами.

**Где.** `worker`. Плагины вне процесса — `events.read` ADR 0082, п. 7.1 с правами своего принципала. Зависит от этапов E1–E2 ADR 0080.

### 8. N6. Каталог данных модуля на томе данных

**Зачем.** Индексам, кешам и состоянию модуля, которое не помещается в таблицы, нужно место на томе данных с учётом квот, свободного места и inode, с HA и резервной копией.

**Расположение.** `<ARKVORY_DATA_DIR>/module-data/<id>/data/` (входит в копию) и `.../cache/` (не входит, ядро может очистить). Предлагается то же имя для плагинов ADR 0082 вместо `plugin-data/` (открытый вопрос 5).

**Контракт** (служба `data-directory`):

```ts
export interface ModuleFiles {
  create(name: string, options: { durable: boolean; exclusive: boolean }): Promise<FileSink>;
  read(name: string, range?: ByteRange): AsyncIterable<Uint8Array>;
  stat(name: string): Promise<{ size: number } | null>;
  rename(from: string, to: string): Promise<void>; // атомарно в пределах каталога
  remove(name: string): Promise<void>;
  list(prefix: string, after: string | null, limit: number): Promise<Page<string>>;
  usage(): { bytes: number; files: number; quotaBytes: number; quotaFiles: number };
}
```

- Имена — правила путей assets (без `..`, абсолютных путей, обратной косой, ссылок); файл создаётся с `wx` и правами 0600. Модуль получает порт, а не путь, поэтому ядро учитывает каждую запись.
- **Квоты** — байты и число файлов (`resources.dataMiB`, `resources.dataFiles` манифеста, утверждает оператор в `ARKVORY_MODULES_FILE`). Порт учитывает их при каждой записи; сверка с диском — ограниченный обход раз в 10 минут. Превышение отклоняет запись (`module_quota_exceeded`) и не останавливает процесс.
- **Место и inode.** Перед созданием файла и каждые 64 МиБ записи: свободные байты не меньше резерва ядра (`ARKVORY_STORAGE_RESERVE_BYTES`) плюс записываемое, свободные inode не меньше `ARKVORY_STORAGE_RESERVE_INODES` (новое, по умолчанию 100 000). Та же проверка inode добавляется в `LocalBlobStore.checkSpace`: ядро пишет файл на каждый blob и часть, и том может кончиться по inode раньше, чем по байтам. На файловых системах без счётчика inode (NTFS, часть сетевых) проверка inode не выполняется, остаётся квота файлов.
- **Долговечность.** `durable: true` — `fsync` файла при закрытии и каталога после `rename` (на Windows каталог не синхронизируется, ADR 0004).
- **HA.** Каталог — на реплицируемом томе (ADR 0072) вместе с blob. На шлюзе чтения порт только читает (`read_only` на запись): шлюзы видят тот же корень хранения (ADR 0009).
- **Копии.** `data/` попадает в точку разделом модуля (ADR 0079, п. 5.4) через порты vault; перед захватом ядро вызывает необязательный `freeze(deadlineMs)` модуля и после — `thaw()`; без них раздел помечается `consistency: fuzzy` (как ADR 0082, п. 13). Восстановление пишет `data/` в пустую цель.
- **Удаление модуля** не удаляет каталог; удаление — только явной командой ADR 0078/0082.
- Метрики `arkvory_module_data_bytes{module}`, `arkvory_module_data_files{module}`. В `arkvory_upload_bytes` данные модулей не входят.

**Базовая реализация** — адаптер ядра на локальном томе; набор `data-directory`: квоты байтов и файлов, нехватка inode (тест на маленьком томе с малым числом inode в контейнерном гейте), `fuzzy` без `freeze`, только чтение на шлюзе, отказ путей с `..` и ссылок.

**Где.** `api`, `worker`, `backup` (чтение для раздела); `reader` — только чтение. Плагины вне процесса — свой каталог ОС с той же раскладкой (ADR 0082, п. 7.4), но без учёта в реальном времени.

### 9. N7. Маршруты модулей с механизмами выдачи ядра

**Зачем.** Модулю передачи или интеграции нужны маршруты с той же выдачей содержимого, что у `/api/v1`: Range, ETag, 304, очередь ADR 0076, бюджеты полосы, лимиты тела, ACL — без копии этого кода в модуле.

**Контракт.** `ModuleRoute` ADR 0079, п. 5.2 дополняется:

```ts
export interface ModuleRoute {
  readonly method: 'GET' | 'HEAD' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
  readonly path: string; // под /api/ext/<id>/v<major>/
  readonly operationId: string; // `<id>.<имя>`
  readonly effect: 'read' | 'write';
  readonly access: 'principal' | 'administrator';
  readonly action: ServiceActionName | null; // проверяется по repositoryParam
  readonly repositoryParam: string | null;
  readonly body:
    { kind: 'none' } | { kind: 'json'; limit: number } | { kind: 'stream'; limit: number };
  readonly responseLimit: number; // байты ответа `json` и `stream`
  readonly timeoutMs: number; // срок обработчика до первого байта ответа
  handle(request: ModuleRequest, signal: ModuleSignal): Promise<ModuleResponse>;
}
export type ModuleResponse =
  | { kind: 'json'; status: number; body: ModuleJson }
  | { kind: 'content'; ref: ContentRef; disposition?: string } // выдача ядром
  | {
      kind: 'stream';
      status: number;
      contentType: string;
      length: number | null;
      etag: string | null;
      body: AsyncIterable<Uint8Array>;
    };
```

- **До обработчика** ядро выполняет аутентификацию, CSRF, проверку `access` и `action` по ACL репозитория, допуск записи (`createUploadAdmission`) для `effect: 'write'` и контракт ошибок ADR 0051. Обработчик получает `AccessScope` запроса (п. 6), но не заголовки авторизации и cookie.
- **`content`** проходит через `createContentSender` ядра: pin, `content.read`, ETag `"sha256:<hex>"`, `If-None-Match`/304, `If-Range`, один диапазон, HEAD, `Content-Disposition`, сессия и очередь ADR 0076 (`Arkvory-Download-Id`, талоны, классы), `BandwidthGovernor` ADR 0008. Модуль только называет объект.
- **`stream`** — содержимое, которое модуль строит сам: ядро ставит `Content-Length` при известной длине, считает отданные байты, применяет бюджет полосы и допуск по запросу (`AdmissionQueue`), Range не поддерживает (`Accept-Ranges: none`), а `etag` модуля обязан быть сильным и в кавычках. Предел ответа — `responseLimit` маршрута.
- **`Cache-Control`.** По умолчанию глобальное `private, no-store`. Для `content` опубликованного blob модуль может выбрать `private, max-age=<до 31536000>, immutable`: байты неизменяемы, а ETag — их SHA-256.
- **Тело запроса.** `json` — до 1 МиБ, `stream` — до предела объекта ядра (`MAX_OBJECT_BYTES`), с таймаутами простоя и общего срока загрузки (`ARKVORY_UPLOAD_IDLE_TIMEOUT_MS`, `ARKVORY_UPLOAD_DEADLINE_MS`) и бюджетом полосы загрузки. Байты в хранилище модуль кладёт только через путь публикации ядра (служба `blob-store` с проверкой размера и SHA-256), не в обход.
- **Шлюзы чтения.** Маршруты с `effect: 'read'` (только GET и HEAD) регистрируются на `reader`, если у модуля есть роль `reader`; маршруты записи там не регистрируются, общий хук отвечает `read_only`. Валидация манифеста отклоняет `effect: 'read'` с другими методами (`route_effect_mismatch`).
- **Ответы** очищаются как у плагинов ADR 0082, п. 7.6 для всех источников, кроме `builtin`: без `Set-Cookie`, CORS и hop-by-hop; `nosniff`; HTML, SVG и JavaScript отклоняются.

**Базовая реализация.** Встроенный модуль не нужен: testkit содержит модуль `echo-routes` (JSON, `content` по id, `stream`, загрузка `stream`), набор `module-route` ADR 0079 расширяется Range/304/очередью/бюджетом на `content`, лимитами тела, регистрацией на `reader` и отказом записи там.

**Где.** `api` и `reader`. Плагины вне процесса — через прокси ядра (ADR 0082, п. 7.6); ответ `content` разрешается и им, потому что выдачу выполняет ядро с пересечением прав.

### 10. N8. Клиентская точка «дерево каталогов»

**Зачем.** Агентам развёртывания и CI нужно положить каталог, получить каталог, проверить его и починить расхождения. Сегодня это делает каждый потребитель сам поверх одиночных файлов.

**Контракт** (клиентская точка `tree-transfer`, `side: client`, ADR 0079, п. 5.11):

```ts
export interface TreeTransfer {
  readonly name: string;
  readonly versions: readonly number[];
  push(tree: LocalTreeReader, target: TreeTarget, signal: ModuleSignal): Promise<TreeReceipt>;
  pull(source: TreeSource, tree: LocalTreeWriter, signal: ModuleSignal): Promise<TreeReport>;
  verify(source: TreeSource, tree: LocalTreeReader, signal: ModuleSignal): Promise<TreeReport>;
  repair(source: TreeSource, tree: LocalTreeWriter, signal: ModuleSignal): Promise<TreeReport>;
}
```

- **Дерево хранится в форме ядра.** Результат `push` — обычный ZIP-артефакт (raw по пути или UPack с координатами пакета), который ядро читает, скачивает и восстанавливает без модулей. Расширение может ускорить передачу, но не меняет формы хранения (ADR 0078, I1).
- **Файлы пишет ядро.** `LocalTreeWriter` CLI пишет каждый файл во временный рядом с целью, считает SHA-256 и размер, сверяет с ожидаемыми из оглавления архива ядра и атомарно переименовывает; несовпадение — `checksum_mismatch`, цель не меняется. Так расширение не может записать файл, который не совпадает с опубликованным деревом. Пути — внутри корня, правила ADR 0081, п. 1 (`path_outside_root`, ссылки, устройства, FIFO).
- **Выбор.** SDK пересекает расширения клиента с `capabilities.tree` сервера (аддитивно, как `capabilities.transfer`) и при отказе расширения возвращается к базовой реализации, кроме `strict`.

**Варианты базовой реализации (бесплатное ядро).**

| Вариант                                                                                                                                                                                | `pull` и `repair`                                                                  | `verify`                                                                        | Цена                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| А. Целый архив: `push` пакует каталог в ZIP и загружает частями с чекпойнтом; `pull` — проверенное скачивание целиком и безопасная распаковка во временный каталог с атомарной заменой | всегда весь архив                                                                  | только CRC32 центрального каталога (не криптографическая) или полное скачивание | простая; любой починке нужен весь объём                                                                 |
| Б. Файл на путь (raw ADR 0064 под общим префиксом)                                                                                                                                     | только изменившиеся файлы                                                          | по SHA-256 каждого пути                                                         | нет атомарной версии дерева, тысячи объектов, список путей сейчас без размера и SHA-256                 |
| В. Архив и пофайловая сверка по оглавлению: архив как в А; сервер при регистрации строит оглавление (путь, размер, SHA-256 содержимого, смещение и длина данных записи)                | пустой каталог — как А; иначе только записи, у которых не совпал SHA-256, по Range | по SHA-256 каждой записи из оглавления                                          | один проход сервера по архиву при регистрации (worker, п. 12) и таблица записей; клиент — Range-запросы |

**Рекомендация — В, в два этапа.** Сначала А (`T1`): полезна сразу и не требует сервера. Затем оглавление и пофайловая сверка (`T2`):

- оглавление строит worker после публикации архива: потоковый проход через `BlobStore.read` (п. 13) с теми же пределами, что у разбора UPack (100 000 записей, 100 ГиБ, без ссылок, шифрования и `..`), распаковка записей `deflate` — в пуле вычислений (п. 12);
- оглавление хранится в `arkvory_tree_entries(upload_id, ordinal, path, size, sha256, method, data_offset, data_length)` (expand-only, входит в копию) и отдаётся `GET /api/v1/repositories/{r}/artifacts/{id}/tree?after=&limit=` с `content.read`, страницами до 1000;
- доверие идёт от сервера: SHA-256 записей посчитал сервер из байтов, чей SHA-256 проверен при публикации; клиент сверяет и каждый полученный файл;
- запросы записей — обычные диапазоны `…/content` одной сессии ADR 0076 (`Arkvory-Download-Id`), поэтому очередь, бюджеты и шлюзы чтения работают без изменений;
- `push` по умолчанию сохраняет записи без сжатия (`stored`): тогда диапазон записи — ровно байты файла; `--compress` включает `deflate`.

Обоснование: гранулярность «целый файл» — то, что пользователь и так сделает `curl` с Range и `unzip`; она не экономит байты внутри файла, работает со стандартным ZIP и стандартными диапазонами и не вводит своего формата. Граница бесплатного ядра — решение владельца (открытый вопрос 1). Решено 2026-10-17: в ядре и T1, и T2 («Решения владельца», Р1).

**Базовая реализация** — `zip-tree` версии 1 в SDK и CLI: `arkvoryctl tree push|pull|verify|repair <dir> …`. Набор `tree-transfer` в testkit: подмена байта на сервере и в канале, лишний и пропавший локальный файл, путь вне корня, отмена, возврат к базовой реализации, совпадение результатов расширения и базовой реализации на одном дереве.

**Где.** SDK и `arkvoryctl`; сервер — оглавление (worker) и маршрут чтения (`api`, `reader`). Клиентские модули — уровень 2 (ADR 0082, п. 5.4, этап P10 для уровня 3). Консоль внешний код не загружает.

### 11. N9. Все потребители байтов — через `BlobStore.read(range)`

**Зачем.** Хранилище без локальных файлов (другой том, объектное хранилище, раскладка модуля) должно работать везде, где ядро читает байты.

**Решение:**

- `ZipManifestReader` открывает архив через yauzl `fromRandomAccessReader`: `RandomAccessReader._readStreamForRange(start, end)` вызывает `blobs.read(id, size, {start, end - 1}, upload.storageBackend)` под той же блокировкой содержимого. Чтение центрального каталога — несколько небольших диапазонов; конструктор получает порт `BlobStore`, а не `LocalBlobStore`. Это же исправляет зеркала (`mirror-target.ts`).
- `contentPath` удаляется из публичной поверхности `LocalBlobStore` и `RoutedBlobStore`.
- `LocalContentSource` копии и `LocalRestoreStorage` получают порт и `backendId` из строки инвентаря (новое необязательное поле `backend`; отсутствие — `default`). Пропажа распознаётся кодом порта `unavailable`, а не `ENOENT`. Проверка пустоты цели — `StorageLifecycle.requireEmpty()` вместо `readdir(blobs.root)`.
- Временные области raw, OCI и зеркал получают `StagingArea` ядра (ADR 0079, п. 5.1) на томе данных вместо `blobs.root`. Перенос без копии ADR 0074 остаётся оптимизацией `LocalBlobStore` на том же томе; для других хранилищ — обычная запись потоком.
- `duplicate` остаётся внутри одного хранилища; копия продвижения между репозиториями с разным размещением получает хранилище источника: политика размещения п. 13 к копиям продвижения не применяется.
- **Policy-тест:** вне `local-blobs.ts`, `blob-files.ts` и временных областей нет обращений к путям blob (`contentPath`, `.root` хранилища, `blobs/`); каждый вызов `read`, `verify`, `exists` и `collect` с опубликованным upload передаёт его `storageBackend`.

**Базовая реализация** — `LocalBlobStore`; проверка — наборы `blob-store` и сценарии разбора UPack, зеркала, копии и восстановления на `directory-backend` testkit, у которого нет путей.

**Где.** `api`, `reader`, `worker`, `backup`.

### 12. N10. Вычисления вне цикла событий: пул ядра

**Зачем.** Распаковка, хеширование и разбор больших структур не должны блокировать цикл событий процесса ядра (AGENTS.md).

**Сравнение.**

- **Модуль сам создаёт `Worker`.** `new Worker(url)` — загрузка кода по вычисляемому адресу мимо загрузчика ADR 0078, п. 3.3: модуль мог бы указать на файл вне проверенного пакета. Число потоков, память и время ничем не ограничены. Изоляции это не даёт (ADR 0078, п. 7; ADR 0082, п. 5.1).
- **Пул ядра** (выбрано). Модуль объявляет точки входа вычислений в манифесте, загрузчик проверяет их вместе с остальными файлами пакета, пул запускает только их и ограничивает ресурсы. Policy-тест «вычисляемая загрузка кода только в загрузчике» расширяется на `new Worker` и остаётся простым.

**Контракт** (служба `compute`):

```ts
// манифест: "compute": [{ "name": "index", "entry": "files/compute/index.mjs" }]
export interface ComputePool {
  run(task: string, input: ComputeMessage, signal: ModuleSignal): Promise<ComputeMessage>;
}
```

- `ComputeMessage` — структурно клонируемые данные и передаваемые `ArrayBuffer`; общей памяти (`SharedArrayBuffer`) нет.
- Пределы на модуль: потоков — 1 по умолчанию, не больше `min(4, cpus - 1)`; очередь — 64 задачи; срок задачи — 60 с по умолчанию, затем `worker.terminate()` и `compute_timeout`; `resourceLimits.maxOldGenerationSizeMb` — 256 по умолчанию. Переполнение очереди — `busy`.
- Поток получает только вход задачи: ни контекста модуля, ни соединений, ни служб. Это граница сопряжения, а не безопасности: поток выполняется с правами процесса.
- Упавший поток перезапускается при следующей задаче; три падения подряд за минуту — модуль `degraded` (`compute_failing`).

**Базовая реализация** — первый потребитель пула — ядро: оглавление дерева (п. 10) и распаковка записей. Набор `compute`: срок, память, очередь, отмена, отказ точки входа, не указанной в манифесте.

**Где.** `api`, `worker`, `backup`; только в процессе (плагины вне процесса — свой процесс ОС).

### 13. N11. Политика размещения новых записей и возврат к хранилищу ядра

**Зачем.** Оператор выбирает, где хранить новые данные репозитория: на другом томе, в хранилище модуля, в будущем S3-хранилище ядра. Отсутствие модуля или лицензии не должно мешать публикации (ADR 0078, L4).

**Решение:**

- `ARKVORY_MODULES_FILE` и конфигурация `local-storage` позволяют несколько экземпляров хранилищ с id `[a-z][a-z0-9-]{0,63}` (`default` — хранилище ядра по умолчанию, например `default` и `volume-2` на разных томах); модуль хранения регистрирует экземпляры с id `<moduleId>` или `<moduleId>.<имя>`.
- **Политика размещения** — таблица `arkvory_storage_placement(repository, revision, rules jsonb, updated_by, updated_at)` (expand-only, входит в копию), правила — существующие `StorageRoutingRule` (`repository`, `packageGroup`, `minSizeBytes` → `backendId`). `GET|PUT /api/v1/repositories/{r}/storage/placement` с `expectedRevision` (CAS) и правом `storage.manage`; `arkvoryctl storage placement`. Сохранение отклоняет неизвестное хранилище (`backend_unknown`).
- Хранилище выбирает `StorageService.create` через `StorageRouter` при создании upload и записывает в `storage_backend`. Части и объект пишутся туда же.
- **Возврат к ядру.** Если выбранное хранилище не включено, не загружено, в режиме `read-only` или `acceptsWrites()` — `false`, upload создаётся в `default`; это видно в ответе (`storageBackend`), в метрике `arkvory_storage_placement_fallback_total{backend,reason}` и в событии `module.health.changed`. Публикация из-за этого не отказывает.
- **Смена во время загрузки.** Если хранилище upload перестало принимать записи до завершения, ядро не переносит незавершённый upload молча. Новые части отклоняются кодом `backend_read_only`, и клиент создаёт загрузку заново (она получит `default`). Уже принятые части остаются читаемыми (L1): если все части есть, завершение читает их и пишет объект в `default`, обновляя `storage_backend` в той же транзакции публикации (CAS по прежнему значению).
- Изменение политики не переносит существующие данные; для этого — п. 4.
- **Квоты и ёмкость** остаются логическими (ADR 0073) и не зависят от размещения; `checkSpace` вызывается у выбранного хранилища.

**Базовая реализация** — два экземпляра `local-storage` на двух томах; это самостоятельная ценность ядра (добавить диск без LVM). Набор `placement`: правила, возврат к ядру по каждой причине, завершение upload, чьё хранилище перестало принимать записи, CAS политики.

**Где.** `api` (создание, политика), `worker` (завершение); шлюзы чтения читают по `storage_backend` строки.

### 14. N12. Маршруты администрирования и фрагменты OpenAPI модулей

**Решение:**

- Маршрут с `access: 'administrator'` (п. 9) доступен только глобальному администратору; проверку выполняет общий помощник ядра, который заменяет локальные копии `administrator()` в маршрутах `system/*`. Пути администрирования модуля — под `/api/ext/<id>/v<major>/admin/`. Плагин уровня 3 может объявить такой маршрут, но сам прав администратора не получает (ADR 0082, P2): вызывает его администратор, а `api.call` плагина ограничен `pluginOperations`.
- **Фрагмент OpenAPI** модуля (`openapi` в пакете, OpenAPI 3.1): пути относительно префикса модуля, `operationId` — `<id>.<имя>`, компоненты — `ext_<id_>_*`, ссылки только на свои компоненты и общие компоненты ядра (`ErrorResponse` ADR 0051, схемы дескриптора). Схемы безопасности задаёт ядро. Загрузчик проверяет фрагмент как `unknown` до регистрации маршрутов (`openapi_invalid` с JSON Pointer).
- **Контрактный guard** сверяет маршруты модуля и фрагмент в обе стороны: каждая операция зарегистрирована, у каждого маршрута есть операция с тем же методом, путём, телом и `access` (`openapi_route_mismatch`).
- **Публикация.** `GET /api/v1/system/modules/{id}/openapi` (ADR 0078, п. 8) отдаёт фрагмент; `GET /api/ext/openapi.json` (аутентифицированный) — сводный документ включённых модулей, видимых по правам вызывающего, с `info.version` = отпечаток плана. `/api/v1/openapi.json` и SDK ядра от модулей не меняются.

**Базовая реализация** — `echo-routes` testkit с фрагментом; набор `openapi-fragment`: лишняя операция, маршрут без операции, ссылка на чужой компонент, конфликт `operationId`.

**Где.** `api`, `reader` (только операции `effect: 'read'`).

### 15. N13. Значения возможностей между модулями

**Зачем.** Модуль, который даёт возможность другим (например, общий индекс или клиент внешней системы), должен передать типизированное значение, а не только закрыть строку `requires`.

**Контракт:**

```ts
export interface CapabilityToken<T> {
  readonly name: string; // как в provides/requires
  readonly version: string; // semver контракта значения
  check(value: unknown): value is T; // проверка формы на границе
}
// поставщик: instance.capability(name) после успешного start
// потребитель: context.capabilities.get(token) → T
```

- Манифест: `provides: ["name@1.4.0"]`, `requires: ["name@^1.2.0"]`; строка без версии означает `@0.0.0` и допустима только у `builtin`. `planModules` проверяет caret-совместимость (`requirement_version_mismatch`); версии входят в отпечаток плана.
- Значение запрашивается у поставщика после его `start` в порядке плана и проверяется `check` токена потребителя (`capability_invalid`). Оно действительно до `stop` поставщика; потребители останавливаются раньше (обратный порядок плана).
- Доступ: значение уровня 2 по умолчанию видно только модулям того же `publisher`; поставщик открывает его другим полем `exposeTo: ["builtin", "operator"]`. Плагин вне процесса значений не получает.
- Необязательная возможность — новое поле манифеста `optional: ["name@^1.0.0"]`: без поставщика план проходит, а `context.capabilities.get(token)` возвращает `null`. Лицензию поставщик проверяет сам и может отдавать значение, чьи операции отказывают кодом `capability_unavailable`; потребитель обрабатывает это как отсутствие возможности.
- Токены публикуются пакетом поставщика (тип и `check`), а не `extension-api`; `extension-api` даёт только `CapabilityToken` и помощник `defineCapability`.

**Базовая реализация** — testkit: поставщик `counter-provider` и потребитель; набор `capability`: несовместимая версия, неверная форма значения, порядок остановки, необязательная возможность без поставщика.

**Где.** Все серверные роли и `arkvoryctl` (клиентские модули), только в процессе.

## Альтернативы

- **Расширять внутренние порты `application` напрямую.** Модули ломались бы от каждого рефакторинга, а гарантии (проверка SHA-256, допуск удаления) оказались бы на стороне модуля.
- **Доверять размеру и хешу, измеренным хранилищем, при завершении (N1).** Экономит полное чтение, но перекладывает проверку целостности на модуль и противоречит L6 ADR 0078. Сохранение состояния хеша между частями не подходит: части приходят параллельно и не по порядку.
- **Перенос blob как копия под новым id (N2).** Ломает ссылки, пути, стадии и закрепления копии по id upload; переключение `storage_backend` сохраняет id.
- **Перенос внутри одной транзакции с удалением источника.** Нет общей транзакции БД и хранилища (AGENTS.md); удаление вне допуска ADR 0035/0054 нарушило бы чтения и копии.
- **Раздел точки без проверки ядром (N3).** Точка была бы восстановима только кодом модуля; I2 ADR 0078 требует проверку и восстановление ядром.
- **Модуль читает таблицы каталога SQL-запросами (N4).** Нет ACL на уровне хранилища каталога; права остались бы на совести модуля.
- **Своя очередь событий для модулей (N5).** Вторая лента с другим порядком и хранением; лента ADR 0080 уже даёт позиции, эпохи и разделы.
- **Модулю — путь к каталогу данных (N6).** Проще, но квоты и проверки inode стали бы обходом раз в несколько минут; порт учитывает запись сразу. Модуль в процессе всё равно может обойти порт (изоляции нет), это фиксируется в документации.
- **Модуль сам выдаёт содержимое (N7).** Каждый модуль повторял бы Range, ETag, очередь и бюджеты и расходился бы с ядром.
- **Дерево как свой формат хранения (N8).** Данные стали бы зависеть от модуля или нового формата ядра; ZIP читают все инструменты.
- **`new Worker` в модулях (N10).** См. п. 12: загрузка кода мимо загрузчика и неограниченные ресурсы.
- **Глобальный реестр значений вместо `requires`/`provides` (N13).** Это service locator, запрещённый AGENTS.md.

## Уточнения реализации (этап Y1)

Этап Y1 сделан вместе со второй частью этапа X1 [ADR 0079](0079-extension-modules.md) (выбор встроенных модулей, один план на установку); те же уточнения записаны в его разделе «Уточнения реализации». Остальные этапы не начаты.

- **`extension-api` 0.2.0.** Изменения формы несовместимы для потребителей 0.1.0 (обязательный `publisher`, открытый `kind`, новое поле хоста), поэтому minor-версия повышена; модуль с `^0.1.0` получает `incompatible_api`. `MODULE_SOURCES` и `ModuleSource` объявлены один раз (`context.ts`), `ReadModule.source` использует их. `kind` — `[a-z][a-z0-9-]{1,31}`, `MODULE_KINDS` — известные точки, `unknown_kind` только у включённого модуля. Новые точки `service` и `tree-transfer` (п. 2.2) в `MODULE_KINDS` не добавлены: по п. 1 точка входит в контракт вместе с базовой реализацией и набором, а их этапы (Y6 и далее, Y13) ещё не начаты.
- **`publisher` и пространство id.** `publisher` обязателен (`[a-z][a-z0-9-]{1,31}`), у встроенных модулей — `proanimastudio`; план его не проверяет, соответствие ключу — задача загрузчика. `id_namespace_mismatch`: `operator` и `development` — только `op-[a-z][a-z0-9-]{1,20}`, `builtin` и `signed` — никогда не `op-`. Пространства маршрутов, метрик и таблиц плагинов — те же внешние (`/api/ext/op-<name>/v<major>/`, `arkvory_x_op_<name>__`), пакет с SHA-256 обязателен для всех источников, кроме `builtin`.
- **`uses` и службы.** `uses` необязателен (нет поля — пустой список), имена — `[a-z][a-z0-9-]{1,31}`, до 32, без повторов. `planModules` для включённых модулей проверяет: имя есть в `HOST_SERVICES`, хост его реализует (новое обязательное поле `ModuleHost.services`), служба есть во всех ролях модуля и открыта его источнику. Матрица п. 16: `blob-store`, `license` — все серверные роли; `staged-completion` — api и worker; `catalog-read`, `content-read` — api, reader, worker; `change-feed` — worker; `data-directory` — все серверные (на шлюзе только чтение); `routes` — api и reader; `compute` — api, worker, backup. Плагинам `operator`/`development` закрыты `blob-store`, `staged-completion` (нужен `dataClass: layout`, которого в манифесте ещё нет) и `license` (ADR 0082, п. 18). Ядро пока не реализует ни одной службы (`PROVIDED_HOST_SERVICES = []`), поэтому любой `uses` у включённого модуля отклоняется `service_unavailable`, а `context.services` — пустой объект.
- **`ModuleContext<Services>`** (`role`, `source`, `mode`, `signal`, `log`, `metrics`, `services`). Хост строит контекст на каждый модуль непосредственно перед `create`: `mode` — `full` у процесса записи и `read-only` у шлюза, `signal` — отмена старта и остановка процесса. `ModuleLog.write(level, {code, subject?, durationMs?, count?})`: код `[a-z][a-z0-9_.]{0,63}` пишется как `module.<code>` с полем `module`, `subject` — идентификатор без `/` и `:` (не путь и не URL), неверная запись, в том числе с уровнем вне `debug`, `info`, `warning`, `error`, заменяется `module.log_invalid`; не больше 50 записей за 10 с на модуль, первая отброшенная даёт `module.log_suppressed`. `ModuleMetrics` — `counter`/`gauge` без меток, только под `metricPrefix`, до 32 рядов на модуль, имя занимается один раз; модуль без префикса метрик получает `TypeError`. `ApiModuleContext = ModuleContext<ApiServices>`.
- **Бюджет префикса таблиц.** `table_prefix_too_long`: `tablePrefix` длиннее 36 символов или id длиннее 24 у модуля с таблицами; проверяются все модули, включённые и нет. Проверку мигратора модулей (`identifier_too_long`, `identifier_not_owned`) делает этап X4: мигратора модулей ещё нет, встроенные таблицы создают миграции ядра.
- **Снимок деклараций** строит `scripts/extension-api-report.mjs` через TypeScript: `index.d.ts` и каждая декларация, достижимая из его экспортов (с импортами и реэкспортами), по файлам в порядке исходника. `checkModules`, `checkOwnership`, `checkServices`, `startOrder`, `ReadModule`, `RuleProblem` в снимок не входят; коды правил экспортируются как `ModulePlanRuleCode`. Тест копирует сборку, меняет внутренние декларации и проверяет, что снимок не изменился, а изменение публичной его меняет.

## Последствия

- `extension-api` растёт: контекст, службы хоста, интерфейсы точек; до 1.0.0 — minor-версии, затем semver и окно поддержки ADR 0079. Снимок деклараций становится точнее и меньше.
- Новые таблицы ядра (expand-only): `arkvory_blob_moves`, `arkvory_module_cursors`, `arkvory_storage_placement`, `arkvory_tree_entries`. Поле `backend` в инвентаре и `section` в строке инвентаря точки — аддитивные поля формата точки; старые инструменты восстановления отклоняют точку с разделами по версии формата, а не молча.
- Новый номер рекомендательной блокировки `18471/22` (перенос blob).
- Новый параметр `ARKVORY_STORAGE_RESERVE_INODES`; проверка inode в `LocalBlobStore.checkSpace` может впервые отказать в записи на томе с исчерпанными inode — это раньше заканчивалось ошибкой файловой системы.
- Разбор UPack и копии через порт добавляют несколько диапазонных чтений вместо одного открытия файла; на локальном томе это измеряется гейтом `large`.
- Публичный `/api/v1` растёт аддитивно: `storage/placement`, `system/storage/moves`, `artifacts/{id}/tree`, `capabilities.tree`, `/api/ext/openapi.json`. OpenAPI, SDK и CLI — в тех же PR; wiki с переводами — в PR, меняющих поведение для пользователя.
- Модуль в процессе по-прежнему может обойти любой порт: границы защищают от случайной связанности, гарантии — подпись, review и контрактные наборы (ADR 0078, п. 7).

## Проверка

- **Unit `planModules`:** `unknown_kind` только у включённых модулей; `id_namespace_mismatch` по каждому источнику; `table_prefix_too_long`; `service_unavailable` по матрице п. 16; `requirement_version_mismatch`; устойчивость отпечатка с версиями возможностей.
- **Снимок деклараций** не содержит `checkModules`, `ReadModule`, `startOrder`; изменение внутреннего файла снимок не меняет.
- **Мигратор модулей** отклоняет имя длиннее 63 байт и имя вне префикса до выполнения шага.
- **N1:** подмена байта части после `compose` даёт `integrity_mismatch`, объект не публикуется; падение после `commit` до `publish` завершается одной публикацией.
- **N2 (PostgreSQL, два тома):** падение после каждого шага; активное скачивание при переключении дочитывается без ошибки; точка копии во время переноса восстанавливается; online GC удаляет перенесённый upload без потери копии в другом хранилище; `skipped` убирает копию цели.
- **N3:** точка с разделом тестовой раскладки восстанавливается ядром без лицензии; `verify --deep` находит подменённый байт в разделе; `convert --core-form` даёт точку без разделов с теми же SHA-256.
- **N4:** одинаковый `null` для отсутствующего, неопубликованного, запрещённого объекта и чужого репозитория; пересечение прав сужает доступ.
- **N5:** повтор пачки после падения; `resync` при смене эпохи и истёкшем курсоре; два процесса с одним курсором — CAS.
- **N6:** квота файлов при свободных байтах; отказ по inode на маленьком томе (контейнер); `fuzzy` без `freeze`; запись на шлюзе — `read_only`.
- **N7, N12:** `content` модуля даёт тот же Range, 304, `If-Range` и очередь, что `/api/v1`; `stream` без Range; маршрут чтения на шлюзе, маршрут записи там — `read_only`; HTML в ответе отклоняется; фрагмент OpenAPI и маршруты сверяются в обе стороны; `/api/v1/openapi.json` не меняется.
- **N8:** подмена байта в архиве на сервере и в канале — `checksum_mismatch` без изменения цели; `repair` скачивает только записи с несовпавшим SHA-256 (подсчёт байтов прокси); путь вне корня отклоняется; базовая реализация и тестовое расширение дают одинаковое дерево.
- **N9:** разбор UPack, зеркало, копия и восстановление на `directory-backend` без путей; policy-тест находит обращение к пути blob вне хранилища.
- **N10:** задача дольше срока завершает поток; точка входа вне манифеста не запускается; policy-тест находит `new Worker` вне пула.
- **N11:** выключенный модуль хранения переводит новые upload в `default` без отказа публикации; незавершённый upload в хранилище, переставшем принимать записи, завершается в `default`.
- **N13:** несовместимая версия возможности отклоняет план; неверная форма значения — `capability_invalid`; потребитель останавливается до поставщика.

## Реализация

### Y2. Чтение через порт (N9)

Ветка `refactor/blob-read-port`.

- **Разбор UPack.** `BlobRangeReader` (`packages/infrastructure/src/blob-range-reader.ts`) — `RandomAccessReader` yauzl поверх `BlobStore.read(id, size, range, storageBackend)`; `ZipManifestReader` открывает архив через `fromRandomAccessReader` под той же разделяемой блокировкой содержимого. Чтения заголовков (конечные записи, центральный каталог, локальные заголовки) отдаются из одного окна до 1 МиБ, которое читается одним диапазоном через порт: центральный каталог читается вперёд, и одно окно покрывает тысячи записей. Окно, которое вышло бы за конец blob, начинается раньше, поэтому первое чтение конечных записей небольшого архива обычно захватывает и весь каталог. Одно чтение yauzl не длиннее 192 КиБ (имя, extra и комментарий записи); больше — отказ до обращения к порту. Данные записи (`upack.json`) идут потоком `Readable.from` с обратным давлением. Память — одно окно; весь blob в память не читается.
- **Цикл событий.** Каждый обратный вызов чтения доставляется через `setImmediate`: yauzl читает следующую запись из обратного вызова предыдущей, и синхронная доставка разобрала бы весь каталог за один оборот цикла с растущим стеком. Число записей ограничено как раньше (100 000). Сжатая запись `upack.json` длиннее 128 КиБ отклоняется до чтения её данных: несжатый манифест не больше 64 КиБ, а запись из пустых блоков deflate разбор иначе читал бы целиком через порт.
- **Отмена и отказы.** `AbortSignal` прерывает и ещё не отвеченное портом чтение (итератор порта закрывается через `return`), `check` перед каждым диапазоном прекращает разбор при потере блокировки содержимого. Короткий и длинный диапазон — `integrity_mismatch`. Первая ошибка порта сохраняется, и `ZipManifestReader` возвращает её код: пропавший blob — `unavailable` (503), а не `invalid_input` (400), как было при открытии файла. `invalid_input` остаётся только для дефектов самого архива.
- **ZIP64 и больше 4 ГиБ.** Смещения и размеры — безопасные целые `number`; 32-битных операций нет. Тест разбирает виртуальный архив 5 ГиБ с `upack.json` после записи 5 ГиБ: все диапазоны лежат дальше 4 ГиБ, прочитано не больше 2 МиБ.
- **Порт.** `ManifestReader.inspect({ id, size, storageBackend })` вместо `inspect(id)`; `ArtifactCatalog.register` берёт их из строки upload. `ServiceMirrorTarget` и `MirrorLoopOptions` получают `BlobStore`, а не `LocalBlobStore`. `contentPath` удалён из `LocalBlobStore` и `RoutedBlobStore`; `LocalBlobStore.read` сообщает об отсутствующем файле кодом `unavailable`, как `exists`.
- **`StorageLifecycle`** (`storage-lifecycle.ts`): `initialize`, `identity`, `ready`, `checkSpace`, `requireEmpty`; реализует `LocalBlobStore`. Утиная типизация `RoutedBlobStore` остаётся до X2 ADR 0079.
- **Копия.** `InventoryEntry.backend` — необязательное поле строки инвентаря; захват читает `storage_backend` в том же снимке, что и строку upload. Строка хранилища `default` поле не пишет, поэтому точки установки с одним хранилищем побайтно прежние и читаются прежними инструментами; строку другого хранилища прежний инструмент отклоняет как `invalid_manifest` (строгий набор полей), а не теряет поле молча. `LocalContentSource` читает через порт с этим хранилищем и распознаёт пропажу по `unavailable` (`blob_missing`), а не по `ENOENT`.
- **Восстановление.** `LocalRestoreStorage` получает `BlobStore & StorageLifecycle`, проверяет пустоту цели `requireEmpty()` (`conflict` → `target_not_empty`) и пишет каждый blob в хранилище своей строки инвентаря. Корень цели по-прежнему создаётся с правами 0700 (параметр `rootMode` у `LocalBlobStore` в составлении `apps/backup`). Цель CLI — один `LocalBlobStore`, который хранилище в вызовах не различает: blob любой строки ложится в его каталог, а строка upload сохраняет своё `storage_backend`; так же его читает и API с одним `LocalBlobStore`. Восстановление в несколько хранилищ появится вместе с их составлением (Y3, N11).
- **Временные области.** `StagingArea` (`staging-area.ts`, `dataVolumeStaging`) — каталоги `raw-staging`, `oci-uploads`, `mirror-staging` тома данных; их получают `FileRawStaging`, `FileOciStaging` и зеркала из `ApiRuntime` и `main` worker вместо `blobs.root`. Пути и проверка места прежние; перенос без копии ADR 0074 работает как раньше на том же томе.
- **Хранилище в остальных вызовах.** `scrub` (`verify`) и очистка (`GarbageCollector`, `PostgresOnlineCleanup` → `collect`) передают `storage_backend` upload.
- **Policy.** `scripts/policy/blob-paths.mjs` (вызывается из `check-policy.mjs`): вне `local-blobs.ts`, `blob-files.ts` и раскладки vault (`file-vault.ts`, `vault-blobs.ts`, `vault-maintenance.ts`) нет `contentPath`, `.root` у хранилища (`blobs`, `store`, `storage`, `target`), `join`/`resolve` с сегментом `blobs` и вызовов `blobs.read|verify|exists|collect` без хранилища. Проверка синтаксическая (работает до сборки) и опирается на соглашение об имени `blobs` для порта. Она видит псевдонимы в файле (`const s = this.blobs`, `{ blobs: s }`, цепочки, `as`), имена в скобках (`blobs['root']`, `blobs['read'](…)`), разбор `{ root }` и `{ contentPath }` из хранилища и сегмент `blobs` в шаблонах и сцеплениях строк у `join`/`resolve`; порт, полученный под другим именем (параметр, поле), и вызов со spread-аргументами она не проверяет. Регрессия — `tests/blob-path-policy.test.mjs`.
- **Отступление: `directory-backend`.** Тестовое хранилище testkit появляется на этапе Y3. Вместо него тесты Y2 используют `MemoryBlobStore` и `portOnly` (`tests/memory-blobs.mjs`) — порт без путей и без `root`: разбор UPack (`tests/blob-range-reader.test.mjs`), зеркало (`pair` в `tests/integration/mirror-fixture.mjs` через `portOnly(LocalBlobStore)`), копия и восстановление (`tests/integration/blob-read-port.test.mjs`: источник через порт, цель — `MemoryBlobStore`, хранилище `volume-2` проходит через точку и строку upload).

### Y3. Размещение (N11) и хранилище (X2 ADR 0079)

Ветка `feat/storage-placement`, миграция 44.

- **Экземпляры `local-storage`.** Встроенный модуль `local-storage` (`kind: storage-backend`, роли `api`, `reader`, `worker`, `backup`) — хранилище ядра: `default` в `ARKVORY_DATA_DIR` и экземпляры из его настроек в `ARKVORY_MODULES_FILE`: `{"format": 1, "modules": {"local-storage": {"enabled": true, "config": {"instances": {"volume-2": {"directory": "/srv/arkvory-2", "enabled": true, "mode": "full", "acceptsWrites": true, "reserveBytes": 1073741824}}}}}}`. Id экземпляра — `[a-z][a-z0-9-]{0,63}` без точки (`<module>.<name>` остаётся модулям хранения), не `default`, не больше 16; каталог абсолютный и не пересекается с каталогом данных и другими экземплярами (`localStorageSettings`). Ошибка — `ModuleConfigError` с JSON Pointer, без значения. В отпечаток плана входят id, `enabled`, `mode`, `acceptsWrites` (процессы установки должны видеть одинаковый набор хранилищ), но не каталоги и резервы — это точки монтирования хоста. Без экземпляров `describeConfig` даёт `{}`.
- **Отступление: `local-storage` — `core: true`.** Таблица п. 8 ADR 0079 называет его необязательным, но пока это единственное хранилище ядра и цель возврата новых записей, выключить его нельзя: план отклоняет `enabled: false` (`core_disabled`). Когда появится второе хранилище ядра (S3), признак пересматривается вместе с проверкой «хотя бы одно `storage-backend`».
- **`StorageBackends`** (`storage-backends.ts`) заменяет `RoutedBlobStore` и его утиную типизацию: `StorageInstance` — порт `BlobStore` с обязательным `collect`, явный `StorageLifecycle`, `mode` (`full | read-only`), `acceptsWrites`, `enabled`. Вызов идёт ровно в хранилище, которое названо (отсутствие — `default`): перебора хранилищ в `exists` и возврата к `default` для неизвестного id больше нет. Неизвестное, выключенное или недоступное хранилище отвечает `unavailable`, для `collect` — `busy` (очистка откладывает объект, L5); `read-only` отказывает в записи кодом `read_only`, в `collect` — `busy`, чтение и проверку обслуживает. `acceptsWrites: false` хранилище не ограничивает: решение о новых данных принимают размещение и `StorageService`, а то, что уже начато, хранилище завершает. Чтения ленивые: неработающее хранилище отказывает на первом `next`, как ошибка чтения.
- **Открытие и проверка.** Хранилище, кроме `default`, открывается после `claimStorage` (`probeStorageBackends`) и перепроверяется каждые 30 с (API — фоновая задача на всех ролях, worker — `watchStorageBackends`). Его `storage-id` должен совпадать с записью `arkvory_storage_backends`; запись в БД делает только писатель API при первом открытии; файл `storage-id` тома не создаёт ни один процесс (см. «Инициализация тома»). Worker, шлюз чтения, обслуживание и агент копий хранилище без записи не открывают (`identity_unknown`). Нет файла идентичности у нового тома (`not_initialized`), несовпадение (`identity_mismatch`), отсутствие разметки или файла у записанного (`probe_failed`) и ошибка открытия (`open_failed`) делают хранилище `unavailable`, процесс продолжает работу; ошибка БД состояние не меняет. Так незамонтированный том или чужой том по тому же пути никогда не получает записи. Готовность и `writable` в `/health/ready` следуют только за `default`. **Исправление ревью PR #37:** между проверками каждые 30 с отмонтированный том принимал записи — `putPart` и `put` создавали `parts/` и `staging/` под пустой точкой монтирования на корневой файловой системе, а очистка считала удалёнными файлы, которых не видела (на Windows, где каталоги не синхронизируются, upload помечался `reclaimed`, файлы тома оставались навсегда). Теперь `StorageBackends` хранит идентичность, доказанную при открытии, и читает `storage-id` тома снова до и после каждой записи (`put`, `putPart`, `duplicate`) и удаления (`collect`): другая или отсутствующая идентичность — `unavailable` (для `collect` — `busy`), часть или объект на чужой файловой системе не считаются сохранёнными; состояние меняет следующая проверка. Хранилище тома (`VolumeLayout`) создаёт папки разметки только в `initialize` и только внутри существующего каталога (каталог создаёт лишь цель восстановления, `createVolumeRoots`): первый старт с несмонтированным томом — `not_initialized` (нет файла `storage-id`), а не разметка на корневом диске. Повторная проверка тома с записанной идентичностью не создаёт `storage-id`; идентичность, которая уже есть у другого хранилища процесса (два id на один каталог через ссылку), отклоняется до записи (`identity_mismatch`). Worker журналирует состояние своих томов так же, как API (`storage.backend_unavailable` / `storage.backend_available`); метрик у worker нет.
- **Инициализация тома (доработка ревью, решение координатора).** Том никогда не размечается неявно при старте службы: файл `storage-id` пишет только команда хоста `arkvory volume-init --directory DIR [--expect-mount | --no-expect-mount]` (`apps/deploy`, без `--root`). Она требует существующий пустой каталог (допускается только `lost+found`), не заменяет существующий файл (временный файл, `fsync`, `link`, `fsync` каталога), отдаёт файл владельцу каталога. Правило монтирования: при `--expect-mount` каталог должен быть точкой монтирования своей файловой системы — `stat.dev` каталога отличается от `stat.dev` родителя; по умолчанию включено на Linux, выключено на Windows; для каталога внутри смонтированного тома — `--no-expect-mount`. Службы файл только читают: настроенный том без него — `not_initialized` (`unavailable`), без разметки и без записи в `arkvory_storage_backends`; писатель при первом открытии размечает (`initialize`) только каталог с файлом. Поэтому пустая точка монтирования несмонтированного тома не размечается никогда. Явный путь восстановления (`createVolumeRoots`, `prepare` пишет новый `storage-id`) остаётся.
- **Политика** — `arkvory_storage_placement(repository, revision, rules jsonb, updated_by, updated_at)`, в копии (`since: 44`). Правила хранятся в форме wire: `{id, backendId, packageGroup | null, minSizeBytes: "<decimal>" | null}`, не больше 32, `repository` у правила нет — это репозиторий политики. `GET|PUT /api/v1/repositories/{r}/storage/placement` (`getStoragePlacement` — `storage.read`, `setStoragePlacement` — `storage.manage`, CAS по `expectedRevision`, `revision_mismatch`), как у политики хранения: учётные записи с паролем прав `storage.*` не имеют, нужен сервисный ключ. Ответ — `revision`, `rules`, `updatedAt` и `backends: [{id, state}]` ответившего процесса; кто сохранил, не отдаётся. Сохранение отклоняет ненастроенное хранилище (`invalid_input`, reason `backend_unknown`, деталь `/rules/<i>/backendId`), но не хранилище, которое сейчас не принимает данные. Событие хранилища `storage.placement_updated`. SDK: `storagePlacement`, `setStoragePlacement` и `repository.storage.placement|configurePlacement`; CLI: `arkvoryctl storage placement [--revision N --file RULES.json]`.
- **Решение** — чистая `decidePlacement` домена: первое подходящее правило, иначе `default`; выбранное хранилище в состоянии, отличном от `accepting` (`not_loaded`, `disabled`, `unavailable`, `read_only`, `not_accepting`), заменяется на `default` с этой причиной. `default` не спрашивается и не возвращается. `PolicyPlacement` (application) читает политику при каждом создании upload (один запрос по ключу; кэша нет — его пришлось бы инвалидировать между процессами). Ответ upload-маршрутов получает аддитивное `storageBackend`; ответ артефактов — нет. Возврат виден в метрике `arkvory_storage_placement_fallback_total{backend,reason}` и в журнале `storage.placement_fallback` (раз в минуту на пару хранилище—причина).
- **Отступление: событие `module.health.changed`** не публикуется: событий модулей в ленте ADR 0080 ещё нет. Вместо него — журнал `storage.backend_unavailable` / `storage.backend_available` и метрики `arkvory_storage_backend_up{backend}`, `arkvory_storage_backend_accepting{backend}`.
- **Смена во время загрузки.** Хранилище «отказывает надолго», если оно `not_loaded`, `disabled`, `read_only` или `not_accepting`; `unavailable` — нет: запись в него отказывает `unavailable` (503) и повторяется, а не переключает хранилище из-за короткого сбоя. Новая часть upload такого хранилища — `conflict`, reason `backend_read_only`. Завершение upload с частями переключает его в `default` **до** записи объекта: `UploadMutation.relocate` (короткая транзакция под блокировкой upload, только `pending`) пишет `storage_backend = 'default'` и `parts_backend` = прежнее хранилище частей, затем части читаются оттуда, объект пишется в `default`, публикация — как раньше. Это **отступление** от «в той же транзакции публикации»: при записи переключения вместе с публикацией повтор после падения между записью объекта и публикацией мог бы, если хранилище снова начало принимать данные, записать объект во второе хранилище и оставить первый объект в `default` без владельца. Порядок «сначала имя хранилища, потом байты» делает повтор детерминированным; байты не переносятся. Загрузка целым телом в такое хранилище ещё ничего не хранит и так же переключается до первого байта (`parts_backend` не пишется). Части одного upload всегда в одном хранилище: `partsBackendOf(upload)`. Переключения нет, если хранилище upload уже держит весь объект (`exists`): попытка записала его и остановилась до публикации. Иначе повтор записал бы второй объект в `default`, а первый остался бы в томе без строки, за которой идёт очистка (в `parts_backend` очистка удаляет только временные файлы). Такой объект проверяется (`verify`, части) или пишется туда же снова (целое тело) и публикуется в своём хранилище.
- **Очистка** (исправление сужения после Y2). `collectEverywhere` (application) сначала собирает части в `parts_backend`, если оно отличается, затем временные файлы и содержимое в `storage_backend`; так делают `GarbageCollector` и `PostgresOnlineCleanup`. Хранилище, которое недоступно или `read-only`, отвечает `busy`: онлайн-очистка считает объект отложенным, офлайн — тоже; квота освобождается только после удаления.
- **Копии и восстановление.** Агент копий и `capture` собирают те же хранилища из `ARKVORY_MODULES_FILE` (только чтение идентичности) и читают каждый blob из хранилища строки инвентаря; недоступное хранилище даёт `blob_missing`, а не пропуск. `restore --modules-file <file>` берёт экземпляры `local-storage` из файла модулей целевой установки: каждый каталог должен быть пустым и не пересекаться с vault и источником, корни создаются с правами 0700. До записи первого байта `RestoreToEmptyTarget` читает инвентарь и отказывает (`invalid_argument`), если точка содержит blob хранилища, которого у цели нет (`RestoreStorage.supports`), — в том числе в предварительной проверке без `--yes`. Таблица `arkvory_storage_backends` в копию не входит: восстановленная установка записывает идентичности своих томов при первом старте писателя. Восстановление в один каталог для точки с несколькими хранилищами больше не делается молча: так строки upload указывали бы на хранилище, которого у установки нет. Восстановленный том получает новый `storage-id` при `prepare`; установка записывает его при первом старте писателя. **Решение владельца (2026-10-17):** vault не может лежать внутри каталога данных или тома и не может их содержать — агент, `capture` и `vault init` отказывают `unsafe_path` до первой записи, как restore для своих целей; restore на хосте источника отделяет цели и от томов источника (`ARKVORY_MODULES_FILE` окружения).
- **Миграция 44** (expand-only): `arkvory_storage_placement`, `arkvory_storage_backends(backend_id, storage_id, recorded_at)`, `arkvory_uploads.parts_backend varchar(64) NULL`. Номер 43 — план модулей Y1.
- **Ёмкость.** Квоты и `ARKVORY_CAPACITY_BYTES` остаются логическими (ADR 0073); `checkSpace` и резерв — у хранилища, куда идёт запись (`reserveBytes` экземпляра или `ARKVORY_STORAGE_RESERVE_BYTES`). Временные области raw, OCI и зеркал остаются на томе данных `default`. Проверка inode — этап Y9, не здесь.
- **Кластер (ADR 0072).** Реплицируется одна файловая система DRBD; том на другом диске остался бы на отказавшем сервере. При `ARKVORY_REPLICA_SOCKET` API не стартует, если каталог тома отсутствует или лежит не на файловой системе `ARKVORY_DATA_DIR` (`requireReplicatedVolumes`, сравнение `stat.dev`).
- **Том, удалённый из конфигурации.** `arkvory_storage_backends` помнит каждый том, на который писатель когда-либо писал. Каждая проверка (при старте и каждые 30 с, теперь и без настроенных томов) сравнивает этот список с конфигурацией процесса; отсутствующие — `StorageBackends.unconfigured()`: журнал `storage.backend_unconfigured` (один раз на появление), метрика `arkvory_storage_backend_unconfigured{backend}` (1), оповещение `ArkvoryStorageVolumeUnconfigured` (critical, 10 мин), ответ `GET …/storage/placement` перечисляет их с состоянием `not_loaded` (аддитивно, не больше 64 строк). Чтение — 503, очистка откладывает, копия завершается `blob_missing`, как и раньше, но больше не молча. Минимальный безопасный вариант: команды «забыть том» или переназначения нет — без переноса (Y4) это означало бы потерю содержимого; выводить том из работы — `acceptsWrites: false`. Готовность не меняется: она следует только за `default`.
- **Контрактный набор.** `extension-testkit` ещё нет, поэтому набор `blob-store` лежит в `tests/contracts/storage-backend.mjs` (функция от фабрики хранилища: жизненный цикл, неизменяемый проверяемый `put`, точные Range, отклонённое объявление не видно, `unavailable` для отсутствующего, отмена, читатель, остановившийся рано, части и идемпотентный `collect`, `duplicate`). Его проходят `LocalBlobStore`, тестовое хранилище `tests/contracts/directory-backend.mjs` (своя раскладка по SHA-256, без путей на поверхности) и оба как `volume-2` за `StorageBackends`. Перенос набора в `packages/extension-testkit` — вместе с переносимыми типами `storage-backend` в `extension-api` (вне этого этапа: экземпляр модуля пока строит ядро, `create` модуля ресурсов не держит).
- **Не вошло:** `arkvory configure --storage-volume` и тома в Compose (оператор добавляет bind mount и файл модулей сам), раздел консоли, гейт `deployment` для нескольких томов, перенос blob (Y4).

**Y5. Завершение из частей (N1).** Порт `application` `StagedParts`/`PartComposer`/`ComposedObject`; `StorageService.complete` (API и задание worker) спрашивает компоновщик хранилища upload, если части лежат в нём и оно принимает записи. Порядок: под `Catalog.exclusive` `checkParts` → `compose` → ядро читает весь объект и само считает размер и SHA-256 (`staged-composer.ts`; размер от хранилища — только первая проверка) → `commit` внутри проверки идентичности тома `StorageBackends` → публикация. Несовпадение — `discard` и `integrity_mismatch`, upload остаётся `pending`; ошибка до или во время `commit` — тоже `discard` (части остаются, повтор компонует заново). Повтор после падения между `commit` и публикацией получает от `compose` закоммиченный объект, проверяет его и публикует один раз. `read_only` от `compose` — `relocate` в `default` до записи и обычный путь (как у хранилища, переставшего принимать данные, Y3). Ошибки модуля переводятся в коды ядра (`module-errors.ts`), переносимая отмена ядра — в сигнал (опрос раз в 250 мс). `LocalBlobStore` компоновщика не объявляет. Отступления: (1) служба `staged-completion` не входит в `PROVIDED_HOST_SERVICES`: возможность принадлежит экземпляру хранилища, а экземпляры строит ядро (`StorageInstance.staged`); модулю её предложить нечем, пока нет экземпляров хранилищ модулей (переносимые типы `storage-backend`, X2); (2) тестовое хранилище `directory-backend` с `compose` осталось в `tests/contracts/` (зависит от `domain`), его `commit` делает жёсткие ссылки на файлы частей в `composed/<id>/` и пишет запись последней; набор — в testkit; (3) зеркала завершают загрузки прежним путём; (4) гейт `large-multipart` в этой ветке не запускался.

**Y4. Перенос (N2).** Таблица `arkvory_blob_moves` (миграция 45, expand-only, без внешнего ключа на upload; исключена из копии), одна активная запись на upload (частичный уникальный индекс). Состояния и шаги — `domain/blob-moves.ts`, сценарий `RehomeBlobs` (`application`), адаптеры PostgreSQL — `blob-moves-store.ts`, `blob-moves-steps.ts`. Шаги как в п. 4: копия под разделяемой блокировкой содержимого (`to.put(from.read)` с проверкой размера и SHA-256, существующая копия проверяется хешем); переключение — короткая транзакция с `pg_try_advisory_xact_lock` ключа upload, без ввода-вывода (`switched` и для уже переключённого upload, иначе `skipped`); освобождение — порядок удаления ядра на отдельном соединении, которое затем уничтожается (блокировки не переживают удаление), потеря сессии прекращает удаление между фазами. `skipped` удаляет копию в цели тем же порядком. Цель, не принимающая данных, — `failed` с `backend_read_only` сразу; занятая блокировка откладывает шаг на 5 с, недоступное хранилище (цель или источник копии) и хранилище, которое сейчас не удаляет файлы (только чтение — источник эвакуации, недоступное), — на 300 с, без счёта попытки и без блокировок и соединений; ошибка шага — попытка с паузой `5·2^n` с (не больше 300 с), пятая — `failed`, кроме состояния `switched`: upload уже в цели, копию источника больше никто не освободит, поэтому шаг освобождения только отступает. Переносы берутся по сроку (`lease_until`: время планирования или конец отсрочки), поэтому ожидающие не задерживают запланированные за ними. Аренда 60 с, продление каждые 20 с с текущим состоянием, запись прогресса — с fencing по generation; переключение и удаление копии проверяют аренду (generation и состояние) под блокировкой upload в той же транзакции или сессии, поэтому держатель, потерявший аренду, ничего не переключает и не удаляет, а копию, из которой upload читается сейчас, удаление не трогает никогда (`conflict`). Worker: цикл `runRehome` под `18471/22`, 2 переноса параллельно, бюджет `ARKVORY_REHOME_BYTES_PER_SECOND` (0 или нет — без предела). **Решение владельца: сначала хост.** `arkvory storage rehome --root R --from A --to B [--repository r] [--limit n]` (по умолчанию 10 000, не больше 100 000) и `arkvory storage moves --root R` запускают точку входа планирования worker того же релиза (`apps/worker/dist/rehome.js`, роль запускателя `storage-rehome`; в Compose — разовый контейнер worker; для разработки `npm run rehome`); планирование не берёт владения хранилищем и не останавливает службы. План требует оба хранилища в конфигурации и цель, принимающую данные (не открытая в процессе планирования цель допускается, worker проверит её перед копией). `arkvory_upload_bytes` не меняется. Отступления: (1) метрик `arkvory_blob_moves{state}` и `arkvory_blob_move_bytes_total` нет — у worker нет метрик; вместо них журнал `storage.move_completed|skipped|failed|interrupted` и `arkvory storage moves`; (2) копия в цели после `failed` до переключения не удаляется: следующий перенос проверяет её хешем и использует; (3) `POST /api/v1/system/storage/moves` — отдельным этапом (открытый вопрос 3 решён); (4) сценарий «online GC удаляет перенесённый upload» проверен частично: отмена до переключения (`skipped`), ожидание удаления источника при закреплении; гейты `large` и `deployment-ha` в этой ветке не запускались.

**Y7. Чтение каталога (N4).** Сценарий `ScopedCatalog` (`application`) проверяет каждого принципала области теми же сценариями, что `/api/v1` (`StorageService.artifact|list|download`, `ArtifactCatalog.resolvePackage|asset`, `GlobalSearch.searchAll` — репозитории, которые может перечислить каждый принципал). `not_found` и `forbidden` — `null`; неверный формат (id, репозиторий, путь) — `invalid_input` при любых правах, до проверки прав. Страница до 100, пачка до 100 id, недоступные id — в `missing`; курсор страницы — последний id полной страницы (страница после последней полной может быть пустой). `AccessScopes` (`infrastructure`) — пустые замороженные объекты в `WeakMap`, отдельной для каждого модуля (`ModuleHostServices.scopes(id)`): область, переданная другому модулю (например, через значение возможности), там прав не имеет; принципалы хранятся замороженной копией; поддельный объект прав не имеет; `intersect` объединяет принципалов (пустая сторона — без прав). `moduleCatalog` переводит результаты в `ArtifactView`/`SearchHit`/`ContentHandle`, ошибки ядра — в коды модуля. Неверный по форме диапазон `open` — `invalid_input` до прав и до закрепления; диапазон за концом blob — `invalid_input` с освобождением закрепления; `read()` без диапазона читает диапазон `open`, любой диапазон проверяется по размеру до обращения к хранилищу. Содержимое: сначала право `content.read`, потом закрепление (отказ `busy` видит только имеющий право), под закреплением артефакт читается снова; закрепление проверяется между фрагментами, `release` идемпотентен, чтение после него — `unavailable`. Отступления: (1) `search` возвращает `Page<SearchHit>` (без SHA-256 и metadata; подробности — `artifact`), а не `Page<ArtifactView>`; (2) добавлен метод `CatalogRead.intersect`; (3) порядок `content-read` — права до закрепления (см. выше); (4) областей пока создаёт только хост (`ModuleHostServices.scopes`): маршрутам модулей (этап Y6) — из принципала запроса, фоновым модулям нужен сервисный принципал модуля (ADR 0082, п. 9), которого ещё нет.

**Y8. Значения возможностей (N13).** Манифест: `provides: ["name@1.4.0"]`, `requires` и новое необязательное `optional: ["name@^1.2.0"]`, `exposeTo` (источники), имя без версии — только у `builtin`. План: `requirement_version_mismatch` (caret по версии поставщика), новые коды `capability_unversioned` и `capability_not_exposed` (тот же `publisher` или источник потребителя в `exposeTo`), необязательная возможность без поставщика проходит, с поставщиком — проверяется и упорядочивает старт (роль поставщика может отличаться: потребитель там получает `null`). Списки возможностей входят в оба отпечатка только у модуля, у которого они есть (в отпечаток совместимости — линией caret): планы без возможностей сохранили прежние отпечатки. Хост: `CapabilityRegistry` спрашивает `capability(name)` у поставщика сразу после успешного `start`, отзывает перед его `stop`; `context.capabilities.get(token)` проверяет совместимость версии токена с версией поставщика и форму значения (`capability_invalid`), обязательная без работающего поставщика — `capability_unavailable`, необязательная без поставщика в этом процессе — `null`, необъявленная — `TypeError`. Отказ поставщика каскадно отклоняет потребителей (`requirement_failed`) по имени возможности.

**Y9. Каталог данных (N6).** `<ARKVORY_DATA_DIR>/module-data/<id>/{data,cache,tmp}` (каталоги 0700, файлы 0600), `openModuleData`: запись во временный файл и атомарная публикация (`exclusive` — `link`, иначе `rename` с заменой), `durable` — `fsync` файла и каталога, точные диапазоны чтения, список по порядку имён. Имена — правила путей assets и без имён устройств Windows и завершающих точки и пробела; имя через ссылку отклоняется (`invalid_input`). Одна квота байтов и файлов на обе области, учёт при каждой записи (замена засчитывает прежний размер): резерв файла и байтов берётся до первого `await`, публикация (`close`, `rename`, `remove`) и `reconcile` идут по очереди под блокировкой каталога, `close` проверяет квоту снова по тому, что имя содержит сейчас (`module_quota_exceeded`), переименование в тот же файл (то же имя, другой регистр, имя 8.3) счётчики не меняет; на Windows публикация поверх файла, открытого другим дескриптором, повторяется ограниченно, затем `unavailable`; чтение открывает файл один раз и проверяет диапазон по открытому файлу. Остатки `tmp/` удаляет следующий писатель, `reconcile` пересчитывает с диска (хост — каждые 10 минут). Квота: `resources` манифеста, оператор заменяет её в `ARKVORY_MODULES_FILE` (`modules.<id>.resources`); без размера модуль только читает. На шлюзе — только чтение (`read_only`). `ARKVORY_STORAGE_RESERVE_INODES` (по умолчанию 100 000, открытый вопрос 6 — как предложено) проверяется в `LocalBlobStore.checkSpace` и перед каждым файлом каталога данных и каждые 64 МиБ записи; ФС без счётчика inode (`statfs.files = 0`: NTFS, часть сетевых) проверяют только байты. Имя `module-data/` принято и для будущих плагинов (открытый вопрос 5 — как предложено). `freeze`/`thaw` — необязательные методы `ModuleLifecycle`; `ModuleRuntime.freezeData(deadlineMs)` даёт каждому модулю с `data-directory` `consistent` или `fuzzy` (нет `freeze`, ошибка или срок) и `thaw` для всех, кого спрашивали. Отступления: (1) раздел `data/` в точке копии не пишется — это разделы модулей O5 ADR 0078 (агент копий модули не выполняет); `freezeData` — сторона хоста для него; (2) проверка нехватки inode на маленьком томе в контейнерном гейте заменена проверкой с подставленным `statfs` и проверкой на томе платформы (`deployment-containers` не запускался); (3) метрик `arkvory_module_data_bytes|files` нет (данные — в `usage()`).

**Службы в процессе API.** `ModuleHostServices` даёт модулю только службы его `uses`: службы каталога строятся один раз на процесс при первом модуле, который их использует (`module-services.ts` — те же сценарии, что `/api/v1`), каталоги данных открываются лениво, сверка останавливается вместе с процессом. `PROVIDED_HOST_SERVICES = ['catalog-read', 'content-read', 'data-directory']`. Worker модули не выполняет (X4), его план те же службы видит.

### Y6. Маршруты и OpenAPI (N7, N12)

Ветка `feat/module-routes`, вместе с серверной частью этапа X5 [ADR 0079](0079-extension-modules.md) (его «Уточнения реализации (этап X5, серверная часть)»). `extension-api` 0.3.0.

- **Служба `routes`.** `PROVIDED_HOST_SERVICES = ['routes']`: план принимает `uses: ["routes"]` у модулей ролей `api` и `reader` (матрица п. 16 не менялась). Модуль получает в `context.services.routes` регистратор `ModuleRoutes` (`add(route)`, `document(fragment)`, `offerTransfer(offer)`), открытый только на время `create`; поздний вызов — `TypeError`. Сразу после `create` хост вызывает новый необязательный шаг `ModuleProcess.created` (`apps/api/src/module-host.ts`): `ModuleRouteRegistry.seal` (`extension-registry.ts`) читает маршруты, фрагмент и предложения передачи как `unknown` и хранит проверенную копию. Отказ — `ModuleSetupError` с кодом и JSON Pointer: подписанный модуль падает один (`routes_invalid`, `openapi_invalid`, `openapi_route_mismatch`, `transfer_invalid`, `running: false`, созданный экземпляр останавливается с тем же сроком 30 с, что и после неудачного старта), встроенный останавливает запуск процесса. Маршруты обслуживаются только у модулей, которые работают после старта (`ApiRuntime.extensions()`): модуль, не загрузившийся или не стартовавший в этом процессе, маршрутов не оставляет, его пути — общий 404 `route_not_found`.
- **Форма `ModuleRoute`** (`extension-route-check.ts`). Методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`; `GET` отвечает и на `HEAD` (отступление от п. 9: `HEAD` отдельным маршрутом не объявляется). `path` — полный путь под одним из `routePrefixes` модуля (у подписанного это всегда `/api/ext/<id>/v<major>/`, правило владения X1): сегменты `[a-z0-9][a-z0-9._-]{0,63}` и параметры `:name`, до 16 сегментов, без `..` и пустых сегментов. `operationId` — `<id>.<имя>`, уникален в модуле; одинаковая форма пути (параметры отличаются только именем) отклоняется, как её отклонил бы маршрутизатор. `GET` ⇔ `effect: 'read'` (`route_effect_mismatch` п. 9 стал частью `routes_invalid`). `access` — `authenticated` или `administrator` (отступление: `principal` п. 9 назван `authenticated`, как в правилах операций `/api/v1`). `action` из `MODULE_ROUTE_ACTIONS` (действия с ясным правилом для учётных записей: семь читающих с правом `read` и `upload.create`, `package.publish`, `asset.write`, `annotation.write` с правом `write`) и `repositoryParam` — оба или ни одного; читающий маршрут называет только читающее действие, а пишущий маршрут с `access: 'authenticated'` обязан назвать пишущее действие на репозиторий: запись модуля не открыта любому вошедшему. Тело `json` до 1 МиБ, `stream` до `MAX_OBJECT_BYTES` (на запросе ещё и до `maxObjectBytes` сервера), у `GET` тела нет. `timeoutMs` до 1 ч, `responseLimit` — безопасное целое ≥ 1, до 64 маршрутов на модуль. Каждый префикс модуля обязан иметь маршрут, иначе guard контракта остановил бы процесс.
- **До обработчика** (`extension-routes.ts`): аутентификация и контракт ошибок — общий хук ядра, как у `/api/v1`; `access: 'administrator'` — общий помощник `requireAdministrator` (`domain`), он же заменил одинаковые локальные копии в `system/modules`, `system/updates`, `system/downloads/settings`, `system/site-changes`, `system/topology` и вложениях отзыва (маршруты парка оставили свою проверку «только человек», которая отклоняет и ключ парка); действие — `authorizeAction` с правилами `/api/v1` (сервисный ключ — по правам, учётная запись — по праву чтения или записи, изменения в зеркальном репозитории запрещены). Повтор параметра запроса и больше 32 параметров — 400. Запись — через допуск загрузок (`createUploadAdmission`). Тело `stream` читается `UploadReceiver` ядра (таймаут простоя, общий срок, полоса загрузки), `Content-Length` больше предела — 413 до первого байта модуля, поток длиннее — 413 на пересечении. CSRF не проверяется: API принимает только `Authorization`, cookie нет. Обработчик получает параметры, запрос, тело, `requestId` и сигнал (запрос, срок `timeoutMs`, остановка), но не заголовки и учётные данные. `AccessScope` п. 6 в `ModuleRequest` нет: он появится вместе с `CatalogRead`/`ContentRead` (этап Y7).
- **Ответы** (`extension-responses.ts`), читаются как `unknown`:
  - `json` — статус 200, 201 или 202, только JSON-значения, не больше `responseLimit` и 16 МиБ;
  - `content` — `repository` и `artifact` (без отдельного типа `ContentRef`: его вводит Y7), выдача — `createContentSender` ядра целиком: pin, `content.read`, ETag `"sha256:<hex>"`, 304, `If-Range`, один диапазон, 416, `HEAD`, `Content-Disposition: attachment` (поле `disposition` п. 9 не введено), очередь и сессии ADR 0076, `BandwidthGovernor`. `cache: 'immutable'` даёт `Cache-Control: private, max-age=31536000, immutable` (открытый вопрос 7: только `private`, общие прокси не кэшируют) — только у 200, 206 и 304; отказ, 503 очереди, 404 и 416 получают `private, no-store`: статус решает хук `onSend` маршрута (`immutableCaching`), потому что 416 отправитель содержимого отвечает без исключения;
  - `stream` — статус всегда 200, `Accept-Ranges: none`, `Content-Length` при известной длине, сильный ETag в кавычках и 304 по `If-None-Match`, допуск на запрос (`downloadGate`), полоса скачивания; байт больше `length`/`responseLimit` или меньше заявленного обрывает ответ (журнал `download.read_failed`), клиент не получает короткий файл как целый;
  - `error` — код из `MODULE_ROUTE_ERRORS` (`invalid_input`, `not_found`, `conflict`, `forbidden`, `busy`, `unavailable`, `capacity_exceeded`, `integrity_mismatch`) с фиксированным сообщением; своих кодов и причин у модуля нет (дополнение к п. 9: без вида `error` модулю пришлось бы бросать исключения, а `instanceof` между копией `extension-api` в пакете модуля и ядром не работает).
  - Исключение обработчика — 500 `internal` и журнал `module.route_failed`; ответ вне контракта — 500 и `module.response_invalid`; срок — 503 `unavailable`, сигнал обработчика отменяется, поздний ответ закрывается непрочитанным (`return()` у тела). Чтение ответа как `unknown` не бросает наружу: геттер или прокси модуля, который бросает, — тоже ответ вне контракта, а закрытие тела (`closeBody`) поглощает любую ошибку, иначе поздний ответ дал бы необработанное отклонение и остановку процесса (политика crash-only). Тело, которое ядро не отправляет (`HEAD`, 304, отказ, отмена), закрывается так же.
  - Очистка ответов п. 9 для всех источников: заголовков модуль не задаёт вовсе (`Set-Cookie`, CORS и hop-by-hop невозможны), CORS ядра действует только для `/api/v1`, `nosniff` — общий хук, плюс `Content-Security-Policy: default-src 'none'; sandbox` у каждого ответа модуля; типы с `html`, `xml`, `svg`, `javascript`, `ecmascript`, `jscript`, `livescript` (все типы JavaScript стандарта WHATWG MIME Sniffing) отклоняются как ответ вне контракта.
- **Шлюзы чтения** обслуживают маршруты чтения. Отступление от п. 9: маршруты записи на шлюзе тоже зарегистрированы, а общий хук отвечает на них `read_only` после аутентификации, как маршрутам записи `/api/v1`; иначе путь без маршрута чтения отвечал бы 404. Обработчик записи на шлюзе дополнительно отказывает `read_only` до кода модуля. Режим контекста модуля на шлюзе — `read-only`.
- **Фрагмент OpenAPI** (`extension-openapi.ts`) — отступление от п. 14: его передаёт код модуля (`routes.document`, подписан вместе с кодом), а не файл `openapi` пакета; поля пакета не добавлялись. Поэтому фрагмент есть только у модуля, который обслуживает маршруты в ответившем процессе. Проверка: копия как чистый JSON (глубина до 32, до 256 КиБ), верхний уровень только `openapi` (`3.1.x`), `paths`, `components`; пути — полные пути с `{name}` (отступление: не относительные, у модуля может быть несколько префиксов, и сводный документ собирается без переписывания); операции — `operationId`, `summary` (1–1024), `responses`, `x-arkvory-access`, необязательные `description`, `tags`, `parameters`, `requestBody` (ровно один тип: `application/json` или `application/octet-stream`), `deprecated`; `security`, `servers` и другие поля отклоняются; `components` — только `schemas` с именами `ext_<id_>_*`; каждая `$ref` — своя схема или `NativeError` ядра, а ключевые слова, разрешаемые относительно другого документа (`$id`, `$schema`, `$dynamicRef`, `$recursiveRef`), отклоняются: иначе ссылка ушла бы из фрагмента в обход проверки `$ref`. JSON Pointer проблемы экранирован по RFC 6901. Сверка в обе стороны: у каждого маршрута есть операция с тем же методом, путём, `operationId`, `access` и телом, у каждой операции — маршрут (`openapi_route_mismatch`, предмет — `METHOD path`).
- **Публикация** (`extension-documents.ts`). `GET /api/ext/openapi.json` — любой аутентифицированный: OpenAPI 3.1 модулей, работающих в процессе, операции маршрутов `administrator` — только глобальному администратору, на шлюзе — только чтение; у каждой операции `security` ядра и `x-arkvory-module`, `x-arkvory-effect`, `x-arkvory-action`, `x-arkvory-repository-param`; `components.schemas` — `NativeError` и только те схемы модулей, до которых доходят показанные операции (прямо или через другие схемы): формы операций, недоступных вызывающему, не раскрываются и через компоненты; `info.version` — полный `fingerprint` плана. `GET /api/v1/system/modules/{id}/openapi` (`getSystemModuleOpenApi`, глобальный администратор, аддитивно в `contracts`, OpenAPI и SDK `client.system.moduleOpenApi(id)`) — тот же документ одного модуля, иначе 404 `not_found`. `/api/v1/openapi.json` от модулей не меняется.
- **Guard контракта** (`contract-guard.ts`): `GET|HEAD /api/ext/openapi.json` — точное исключение; для модуля со службой `routes` маршруты под его префиксами сверяются с объявленными в обе стороны (`API route drift: module routes [undocumented …, unregistered …]`), `GET` ожидает и `HEAD`; правило «префикс без маршрутов» осталось для встроенных протоколов. Guard получает только работающие модули процесса, а не все включённые.
- **`capabilities.transfer`** — см. ADR 0079, X5: `[{name, versions, module, prefix}]` предложений работающих модулей вида `transfer`; имя уникально в процессе (первый запечатанный модуль держит имя, даже если потом не стартовал). SDK возвращает поле, только если сервер его прислал.
- **Базовая реализация вместо testkit.** Пакета `extension-testkit` ещё нет (как в Y3), поэтому модуль `echo-routes` п. 9 — подписанный тестовый модуль `echo` (`tests/module-route-fixtures.mjs`, вид `transfer`): JSON, `content`, `stream`, загрузка `stream`, JSON администратора, исключение, срок, отказ `error`, HTML; варианты с нарушениями фрагмента и маршрутов. Наборы `module-route` и `openapi-fragment` — `tests/module-routes.test.mjs` (правила маршрутов и фрагмента, регистратор, отказ при `created`, drift guard, очередь ADR 0076 у ответа `content`, обрыв короткого `stream`, закрытие позднего ответа, `read_only` на шлюзе) и `tests/integration/module-routes.test.mjs` (установленный командой хоста пакет; Range, ETag, `If-Range`, 304, 416, `HEAD` с теми же заголовками, что у `/api/v1`; ACL до кода модуля; пределы тел; ошибки; документы, `capabilities.transfer`, SDK; шлюз чтения; модули с нарушениями падают по одному). Перенос в testkit — вместе с пакетом.

## Открытые вопросы владельцу

1. **Решено 2026-10-17 (Р1).** **Граница бесплатного ядра для деревьев (N8).** Предложено: в ядре и целый архив (T1), и оглавление с пофайловой сверкой и починкой (T2). Альтернатива — в ядре только T1, а пофайловая сверка остаётся точкой расширения без базовой реализации; тогда контракт `repair` в ядре сводится к повторному скачиванию архива.
2. **Хранение дерева.** Raw-путь или UPack по умолчанию для `tree push`; сжатие по умолчанию (`stored` предложено ради точных диапазонов записей).
3. **Решено: сначала хост.** **Перенос blob через API** (`POST /api/v1/system/storage/moves`) или только командой на хосте; предложено и принято: сначала хост (`arkvory storage rehome`, этап Y4), API — отдельным этапом.
4. **Уровень 3 в процессе и N3.** Разрешить ли плагинам оператора с `dataClass: layout` разделы с содержимым; предложено — нет в первой версии.
5. **Одно имя каталога данных** `module-data/<id>/` для модулей и плагинов вместо `plugin-data/<id>/` ADR 0082.
6. **Резерв inode по умолчанию** (`ARKVORY_STORAGE_RESERVE_INODES = 100000`) и поведение на файловых системах без счётчика inode.
7. **`Cache-Control` для неизменяемого содержимого** модулей (`immutable` до года) — допустимо ли для установок за общими прокси; ядро сегодня везде отдаёт `private, no-store`.
8. **Значения возможностей между издателями (N13).** Разрешать ли модулям уровня 2 открывать значения плагинам оператора (`exposeTo: ["operator"]`) или запретить совсем.
9. **Пределы пула вычислений** по умолчанию: 1 поток на модуль, 256 МиБ, 60 с.

## Решения владельца 2026-10-17

### Р1. Базовая реализация деревьев (N8): T1 и T2 в бесплатном ядре

Владелец принял предложение открытого вопроса 1: бесплатное ядро содержит оба этапа базовой реализации N8 (вариант В п. 10).

- **T1 — целый архив** (этап Y13): `push` упаковывает каталог в ZIP и загружает его частями с чекпойнтом; `pull` скачивает архив с проверкой и распаковывает его во временный каталог с атомарной заменой.
- **T2 — оглавление и пофайловая сверка** (этап Y14). Сервер строит оглавление архива (`arkvory_tree_entries`), отдаёт его маршрутом `GET /api/v1/repositories/{r}/artifacts/{id}/tree` и объявляет `capabilities.tree`. `verify` сверяет каждую запись по SHA-256, а `repair` докачивает диапазонами только записи, которые не совпали.

Что из этого следует:

- контракт `repair` в ядре — пофайловая починка, а не повторное скачивание архива. Альтернатива «в ядре только T1» отклонена;
- T1 и T2 — функции ядра по ADR 0078, п. 1.1. По I4 они не переносятся в платный модуль и не требуют лицензии. Маршрут оглавления и `capabilities.tree` — публичный контракт `/api/v1`, изменения аддитивные;
- точка `tree-transfer` остаётся. Расширение может предложить другой способ передачи, но не меняет форму хранения (обычный ZIP), проверку каждого файла ядром (`LocalTreeWriter`) и возврат к базовой реализации (п. 10);
- этап Y14 больше не ждёт решения владельца. Он идёт после Y13 и после Y10: записи `deflate` распаковываются в пуле вычислений (п. 12);
- открытый вопрос 2 (raw-путь или UPack, сжатие по умолчанию) остаётся открытым.
