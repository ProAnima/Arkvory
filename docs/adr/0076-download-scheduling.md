# 0076. Планировщик скачиваний: сессии, очередь, приоритеты и окна

Статус: proposed. Owner: Ian Panaev. Дата: 2026-10-14.

## Контекст

Массовое обновление: 1000 клиентов одновременно скачивают по 4–20 ГБ через канал 1 Гбит/с. Это 4–20 ТБ, то есть 9–45 часов передачи при любом коде. Задача планировщика — не ускорить канал, а сделать так, чтобы ни один клиент не отвалился, каждый знал, когда начнётся его скачивание, и первые закончили через минуты, а не все разом в конце.

Что сейчас (ADR 0004, 0007, 0008, 0009, 0022):

- Допуск выдаётся на HTTP-запрос. SDK и `arkvoryctl` читают файл диапазонами по 8 МиБ, и каждый диапазон заново проходит `AdmissionQueue`: 20 ГБ — около 2500 допусков. 1000 клиентов делят канал поровну, и все заканчивают одновременно.
- Очередь сервера в памяти: 16 активных, 64 ждущих (8 на principal), ожидание до 20 с. Переполнение — сразу 503 `busy` с фиксированным `Retry-After: 2`. Ни места в очереди, ни срока клиент не узнаёт.
- Бюджет повторов SDK — 20 на всю операцию и 5 на запрос, ожидание дольше 60 с считается отказом. При тысяче клиентов бюджет кончается за минуты: обновление падает. `arkvoryctl` сохраняет префикс, но продолжит только при повторном запуске.
- Под одним ключом (частый случай для парка агентов) активны не больше 4 скачиваний, остальные получают отказ.
- Сторонние клиенты (docker/oras, git-lfs, npm/Unity, curl/wget по ссылкам и путям) видят только статус и `Retry-After`; их повторами мы не управляем.

При одинаковых файлах среднее время завершения минимально, когда файлы обслуживаются по очереди целиком, и максимально при делении поровну. Поэтому единица планирования — **сессия скачивания**, а не запрос.

## Решение

### 1. Клиент никогда не сдаётся из-за занятости

Ответ 503 `busy` или 429 с `Retry-After` — это «приходи позже», а не сбой. В SDK такие ожидания не расходуют бюджет повторов (`maxRetries`, `maxAttempts`) и не ограничены `maxDelayMs`: клиент ждёт указанное время плюс случайную добавку, пока не истечёт общий срок операции, заданный вызывающим (`waitLimitMs`, по умолчанию без срока), или не сработает отмена. Бюджет повторов остаётся для настоящих сбоев: обрыв сети, 502/504, таймаут попытки. `arkvoryctl download` по умолчанию ждёт без срока (`--wait-limit` задаёт срок) и печатает, сколько ещё ждать.

### 2. Сессия скачивания

Сессия — допуск на всё скачивание одного объекта (артефакт, путь, пакет, слой OCI, объект LFS, tarball npm) одним клиентом. Пока сессия активна, её диапазоны идут без повторного допуска; полоса по-прежнему делится `BandwidthGovernor` (ADR 0008).

- **Явная сессия.** SDK, CLI и консоль просят талон: `POST /api/v1/downloads` с `Idempotency-Key` и объектом. Ответ — состояние `queued` или `active`, место в очереди, оценка начала `startsAt` с интервалом, `checkAt` (когда спросить снова) и срок жизни. Диапазоны активной сессии несут заголовок `Arkvory-Download: <id>`.
- **Неявная сессия.** Запрос без талона (сторонние инструменты, ссылки, старые клиенты) встаёт в ту же очередь под ключом «principal + объект + адрес клиента». Пока сессия ждёт, ответ — 503 `busy` с `Retry-After` до `checkAt` и заголовками `Arkvory-Queue-Position` и `Arkvory-Starts-At`. Клиенты за одним NAT с одним ключом делят одну сессию; это описано в документации.
- Активная сессия держит место, пока идут байты. Пауза между диапазонами дольше `idleSeconds` (30 с), выдача всех байтов объекта или отмена освобождают место.
- Ждущая сессия, которую клиент не подтвердил вовремя (не пришёл к `checkAt` плюс запас), удаляется — «неявка». Неявка не наказывается: новый запрос встаёт в конец очереди своего класса.

### 3. Стратегии

Оператор выбирает стратегию во время работы, без перезапуска:

- `ordered` (по умолчанию) — классы приоритета с весами, внутри класса FIFO, между principal класса — по кругу. Ждущий дольше `agingMinutes` поднимается на класс выше: никто не голодает.
- `smallest-first` — внутри класса первыми идут меньшие объекты (минимум среднего времени при разных размерах), со старением, чтобы большие не ждали вечно.
- `shared` — прежнее поведение: допуск на запрос, канал делится поровну. Для тех, кому важнее равномерность, чем раннее завершение.

Смена стратегии действует на следующие решения о допуске. Активные сессии не прерываются.

### 4. Классы приоритета

Встроенные классы: `interactive` (люди в консоли и CLI), `release` (CI и развёртывания), `bulk` (массовые обновления), `background` (синхронизация зеркал и прочее фоновое).

- **Безопасные умолчания.** Люди — `interactive`, сервисные аккаунты — `release`, ссылки — класс выпустившего. Веса 8/4/2/1. Для `interactive` резервируется одно место: консоль работает даже при полной очереди обновлений.
- **Настройка.** Оператор меняет веса, резерв и класс каждого сервисного аккаунта; класс входит в сервисную политику с её ревизией и аудитом. Клиент может только понизить свой класс в запросе талона (например, агент обновления просит `bulk`), но не повысить.

### 5. Окна

- **Окна клиента.** Талон принимает `notBefore` и `notAfter`. Планировщик не начинает сессию раньше `notBefore` и сразу говорит, если с текущей очередью к `notAfter` не успеть (`startsAt` позже срока; клиент решает сам).
- **Окна оператора.** У класса могут быть окна по расписанию (дни недели, часы, часовой пояс): например, `bulk` — только 22:00–06:00. Вне окна класс получает `outsideShare` полосы (по умолчанию 0: только в окне). Начатая в окне сессия доводится до конца. Оценки начала учитывают окна.

### 6. Оценка начала

Планировщик знает размер каждого объекта, остаток активных сессий и измеренную скорость выдачи (скользящее среднее за последнюю минуту, не меньше настроенной полосы, если она задана). Начало ждущей сессии — момент, когда перед ней освободится место, с учётом классов, резерва и окон; клиенту отдаются точка и интервал. Оценка пересчитывается при каждом обращении. `checkAt` — середина до начала, но не позже 5 минут и не раньше 5 секунд, с разбросом по талону: опросы не приходят толпой. Точность оценок видна в метриках.

### 7. Ресурсы и утечки

- Все структуры ограничены: сессий всего (по умолчанию 65 536), на principal (4096 — парк агентов под одним ключом), длина неявного ключа. Сверх лимита — 503 `busy` с `Retry-After`, а не рост памяти.
- Нет таймера на сессию: один такт планировщика (500 мс) пересчитывает очередь и удаляет просроченное; поиск — по индексам (класс → principal → FIFO), без сканирования всей очереди на каждый запрос.
- Сессия освобождается при закрытии ответа, отмене, ошибке и на такте при простое: каждый путь проверяется тестом на счётчики (`active`, `waiting` возвращаются к нулю).
- Остановка сервиса: ждущие получают 503 `busy` с `Retry-After`, активные доводятся по ADR 0048.

### 8. Хранение и несколько процессов

Этап 2 держит очередь в памяти процесса записи за портом `DownloadScheduler` (application). Талон — подписанный токен с id, классом и временем постановки: после перезапуска клиент приходит с тем же талоном и встаёт на своё прежнее место, а не в конец. Этап 4 добавляет реализацию порта на PostgreSQL (выдача мест с арендой и fencing, как `arkvory_jobs`), общую для процесса записи и шлюзов чтения (ADR 0009); её таблицы исключаются из резервной копии.

### 9. Видимость

- `arkvoryctl download`: «в очереди, 312-й, начало ≈ 14:05 (через 47 мин)», затем прогресс. Консоль показывает это же на странице «Скачивания».
- Оператор: страница настроек скачиваний (стратегия, классы, веса, резерв, окна) и состояние очереди — длина по классам, ожидание, прогноз опустошения.
- Метрики: сессии по классам и состояниям, время ожидания, неявки, отклонение оценки от факта. Readiness — агрегаты без id.

### 10. Этапы (каждый — отдельный PR)

1. Устойчивый клиент (п. 1) и `Retry-After` по фактической очереди вместо фиксированных 2 с.
2. Планировщик в памяти: сессии (явные и неявные), стратегии, классы, окна клиента, оценки, `POST /api/v1/downloads`, SDK и CLI.
3. Настройки оператора: стратегия, веса, резерв, классы сервисных аккаунтов, окна классов; страница консоли.
4. Очередь в PostgreSQL для шлюзов чтения и HA.
5. Нагрузочный гейт: масштабированная модель (например, 500 клиентов по 40 МБ на канале 40 МБ/с) проверяет, что все докачали без ошибок, оценка начала отклоняется не больше заданного, первые заканчивают за время одного файла.

## Последствия

- Правило ADR 0007 «Retry-After дольше `maxDelayMs` — отказ» заменено п. 1: для ответов `busy` и `rate_limited` клиент ждёт, сколько просит сервер, в пределах `waitLimitMs`. Остальные повторы ADR 0007 не меняются.
- Публичный контракт расширяется аддитивно: ресурс `/api/v1/downloads`, заголовки `Arkvory-Download`, `Arkvory-Queue-Position`, `Arkvory-Starts-At`, поле класса в сервисной политике. Существующие клиенты работают без изменений: без талона они получают неявную сессию.
- Смысл `ARKVORY_MAX_DOWNLOADS` меняется с «одновременных запросов» на «одновременных сессий» (при `shared` — по-прежнему запросов).
- Сторонние клиенты получают честный `Retry-After`, но их повторы остаются на их совести; для массовых раздач через них рекомендуются ссылки и окна.
- Очередь не увеличивает пропускную способность канала. Для 20 ТБ через 1 Гбит/с по-прежнему нужны зеркала и шлюзы на площадках, волны через хаб и, позже, дельты между версиями.
