# 0072. HA на одной площадке: active/passive на синхронной реплике тома

Статус: accepted. Owner: Ian Panaev. Дата: 2026-10-10.

## Контекст

Владелец выбрал первый профиль отказоустойчивости (обсуждение 2026-10-10):

- **цель** — быстрое восстановление без потери данных на одной площадке; потеря площадки по-прежнему закрывается зеркалами (ADR 0058) и резервными копиями;
- **подтверждение записи** — только после двух устойчивых копий; при потере второй копии запись останавливается (RPO = 0 для подтверждённого);
- **арбитраж и fencing** — доступны управление питанием (IPMI/iDRAC/iLO, PDU), API гипервизора и отдельный узел-свидетель;
- **уровень** — production: каждое поведение при отказе описано, проверено на стенде и видно оператору.

Сейчас Arkvory — один писатель на одной PostgreSQL. Владение хранилищем подтверждается раз в 2 секунды и теряется необратимо (ADR 0042), службы перезапускаются после падения и зависания (ADR 0067). Блокеры HA из [аудита](../CLUSTER_AUDIT_2026-09-26.md): синхронная копия байтов и каталога, fencing при переключении, HA PostgreSQL, защита от очистки ещё не скопированного. [TWO_NODE_PLAN](../TWO_NODE_PLAN.md) предлагал active/passive на DRBD, но без принятого решения.

## Решение

### Топология

Только Linux. Узлы с данными держат одинаковую копию **одного блочного тома** (DRBD 9, protocol C). На томе — весь корень установки: PGDATA, хранилище, конфигурация, релизы, журналы. Каталог и байты физически не расходятся, PostgreSQL и писатель Arkvory остаются в единственном экземпляре: код блокировок, поколений и владения не меняется.

| Профиль | Узлы с данными | Свидетель                                                            | Запись при отказе одного узла с данными                 |
| ------- | -------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| `ha-2`  | 2              | обязателен (без данных, `corosync-qnetd` + DRBD diskless tiebreaker) | останавливается до возврата копии или решения оператора |
| `ha-3`  | 3              | не нужен                                                             | продолжается: две копии остаются                        |

Требуемое число актуальных копий для подтверждения записи — 2 в обоих профилях (`required_copies`). `ha-3` — рекомендуемый production-профиль; `ha-2` дешевле и честно останавливает запись.

Решение об активном узле принимает **Pacemaker + Corosync** с кворумом, а не Arkvory. Своего leader election нет (ADR 0042). Группа ресурсов, по порядку: fencing прежнего активного → DRBD Promoted → файловая система → PostgreSQL → `arkvory-api`, `arkvory-worker`, `arkvory-backup` → плавающий IP. Таймер обновлений и вебхуки работают только на активном узле, потому что их состояние на томе.

**Fencing обязателен** (`stonith-enabled=true`, `fencing resource-and-stonith` в DRBD): агент питания (`fence_ipmilan`, `fence_redfish`, PDU) или гипервизора (`fence_pve`, `fence_vmware_rest`, `fence_xvm`/`fence_virsh`). Без проверенного fencing кластер не запускается: `arkvory cluster-check` это проверяет. SSH-команда остановки fencing'ом не считается.

### Как запись узнаёт о числе копий

Источник правды — состояние ядра DRBD в момент проверки, а не журнал событий: события приходят с задержкой, и проверка по ним могла бы пропустить только что случившуюся потерю копии.

**Актуальная копия** — локальный диск `UpToDate` и каждый сосед, у которого соединение установлено (`Established`), а диск `UpToDate`. Protocol C завершает запись только после записи на всех подключённых актуальных соседей; сосед, пропустивший хоть одну запись, перестаёт быть `UpToDate` до окончания ресинхронизации. Отсюда ключевое свойство: **если сразу после завершения записи актуальных копий не меньше двух, эта запись есть минимум в двух копиях**.

Состояние ядра читает служба `arkvory-replica` (root, только на узлах кластера): `drbdsetup status --json` по запросу через Unix-сокет `/run/arkvory/replica.sock` (группа `arkvory`, только чтение). Одновременные запросы объединяются, но ответ выдаётся только из чтения, **начатого после** запроса: устаревший снимок не может подтвердить запись. Служба также применяет разрешение оператора на одну копию (ниже) и отдаёт `{ copies, required, singleCopyUntil }`.

Arkvory применяет правило подтверждения ко всем изменяющим запросам (`/api/v1`, реестр OCI, Git LFS, npm):

- **до** обработки — по снимку не старше секунды: если `copies < required`, сразу `503 unavailable`, reason `replication_degraded`, `Retry-After`;
- **после** фиксации в PostgreSQL и `fsync` байтов, перед ответом 2xx — новый запрос к службе. Если копий меньше требуемых или служба не ответила за 2 секунды, клиент получает `503 replication_degraded`, а не 2xx. Операция могла остаться в одной копии, но не подтверждена; изменяющие операции идемпотентны или сверяются (ADR 0051), и повтор после восстановления безопасен.
- **Статус задачи завершения** (`GET /api/v1/jobs/{id}`) — единственное чтение, которое по контракту является подтверждением: клиент узнаёт из него, что большая загрузка опубликована. Оно проверяется так же, как ответ на запись.

Без настроенного сокета (standalone) правило не действует: одна копия — это и есть standalone.

Исключения, перечисленные в коде: вход и выход (сессия — не данные), отзыв в хаб (нужен именно во время инцидента), пакетный запрос Git LFS (по нему же идёт скачивание; сама загрузка объекта проверяется).

Подтверждённое (2xx) поэтому всегда лежит минимум в двух копиях: RPO = 0 для того, что клиент получил как успешное. Чтение — скачивание, каталог, консоль — продолжается, пока активный узел жив.

Fencing и кворум остаются за Pacemaker и штатным `crm-fence-peer`: правило подтверждения защищает от потери данных, fencing — от двух писателей.

### Деградация, решения оператора и возврат

- `ha-2`, отказал резервный: активный продолжает отдавать файлы, запись — 503 до окончания ресинхронизации вернувшегося узла, затем возобновляется сама.
- `ha-2`, отказал активный: fencing → переход на второй узел → чтение восстанавливается; запись остановлена до возврата второй копии.
- Оператор может явно разрешить запись в одну копию: `arkvory cluster-single-copy --until <срок> --reason "<текст>"`, только пока копий не хватает. Решение (срок, причина, время) хранится на томе в `config/single-copy.json` и попадает в журнал systemd; пока оно действует, `required` = 1, это видно баннером в консоли, метрикой и алертом. По истечении срока или при возврате копии решение снимается само: следующая потеря снова останавливает запись.
- `ha-3`: отказ одного узла запись не останавливает; второй отказ — как `ha-2`.
- Сетевой разрыв: кворум решает свидетель или большинство; проигравший узел выключается fencing'ом. Две стороны одновременно не пишут.
- Автоматического возврата активной роли (failback) нет.

### Установка, обновление, резервные копии

- `arkvory cluster-plan` формирует конфигурацию DRBD и команды Pacemaker (`pcs`: fencing, кворум-устройство, группа ресурсов) для проверки и применения оператором; параметры агента fencing заполняет площадка.
- `arkvory configure --cluster <ha-2|ha-3>` на основном узле: проверяет, что корень — смонтированный том DRBD с двумя полными копиями, включает правило подтверждения и снимает автозапуск юнитов; при сбое возвращает standalone. `arkvory cluster-node` готовит остальные узлы: те же UID/GID служебных пользователей и юниты с тома, без автозапуска.
- `arkvory cluster-status|cluster-check|cluster-fence-test|cluster-switchover|cluster-single-copy`: состояние копий, проверка кворума, fencing каждого узла и настроек DRBD, fencing резервного узла, плановое переключение (только с двумя полными копиями), решение об одной копии.
- Обновление идёт на активном узле: релиз и миграция на томе, поэтому бинарные файлы следуют за томом. Перед обновлением ресурсы переводятся в maintenance, после проверки готовности возвращаются под Pacemaker; автоматическое переключение во время обновления запрещено. Миграции и так должны совместимо откатываться (ADR 0059).
- Агент резервных копий работает только на активном узле; хранилище копий — вне кластерного тома.
- Проверка ресурса для Pacemaker — `/health/ready` с ключом (уже есть), с отдельными кодами для «не готов» и «готов, запись остановлена»: остановленная запись не повод для переключения.

### Наблюдаемость

Метрики `arkvory_replication_copies`, `arkvory_replication_required_copies`, `arkvory_replication_writes_refused_total`, `arkvory_replication_check_failures_total`; алерты на деградацию, на действующее разрешение одной копии и на сбой чтения состояния копий; кворум и свидетель проверяет `cluster-check`. Баннер администратора в консоли и поле `replication` в `/health/ready`.

## Альтернативы

- **PostgreSQL streaming (Patroni) + отдельная репликация хранилища.** Две независимые реплики требуют общего барьера публикации и переключения; без него каталог и байты расходятся. Это дольше и рискованнее, чем один том.
- **Репликация на уровне приложения (outbox/ACK, [REPLICATION](../REPLICATION.md)).** Переносима и работает на Windows, но это месяцы работы и собственная реализация консенсуса. Остаётся направлением для асинхронных зеркал.
- **Общее хранилище (SAN/NFS) + один активный узел.** Хранилище остаётся единственной точкой отказа; NFS к тому же не даёт нужных гарантий `fsync` для PostgreSQL.
- **Ceph/объектное хранилище.** Отдельный кластер, который нужно эксплуатировать; для 4 ТБ на одной площадке избыточно. Может стать вторым backend после ADR 0071.
- **Своё переключение в Arkvory по heartbeat.** Отвергнуто ADR 0042: нет fencing, есть split brain.

## Последствия

- Windows и Docker Compose не поддерживаются в HA-профиле; они остаются standalone + зеркала + резервные копии.
- Каждому узлу с данными нужен диск на весь объём, сеть между узлами с измеренной задержкой: protocol C добавляет RTT к каждому `fsync`. Цели по задержке записи измеряются на стенде.
- Новая поверхность: служба `arkvory-replica` от root и команда `arkvory cluster`. Сокет службы доступен Arkvory только на чтение состояния; разрешение одной копии меняет только `arkvory cluster` от root.
- Публичный контракт расширяется аддитивно: reason `replication_degraded`, поле `replication` в готовности, метрики.
- Стенд требует Linux-хост с KVM: модуль DRBD и fencing не проверяются в контейнерах Docker Desktop.

## Проверка

Отдельный гейт `deployment-ha` на стенде из виртуальных машин (KVM, `fence_virsh`), профили `ha-2` и `ha-3`:

1. Выключение питания активного узла во время 5 GiB загрузки и потока мелких загрузок: ни одна подтверждённая (2xx) загрузка не потеряна; неподтверждённые завершаются повтором; время до восстановления чтения измерено.
2. Отказ резервного: `ha-2` — запись 503 `replication_degraded`, чтение работает, после возврата запись возобновляется сама; `ha-3` — запись продолжается.
3. Разрыв сети между узлами с данными: ровно один активный, проигравший выключен fencing'ом, без split brain.
4. Сбой fencing: переключение не происходит, состояние видно оператору.
5. Отказ во время коммита: соседа выключают между `fsync` и ответом; загрузка, оставшаяся в одной копии, не получает 2xx, а повтор после возврата узла её подтверждает.
6. Плановое переключение и обновление релиза в кластере, включая миграцию схемы.
7. `cluster-single-copy`: запись идёт, баннер и алерт есть, решение снимается по сроку.
8. Возврат узла и полная ресинхронизация под нагрузкой чтения; затем повтор сценария 1 в обратную сторону.
