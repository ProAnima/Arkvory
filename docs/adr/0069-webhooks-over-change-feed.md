# 0069. Вебхуки поверх ленты изменений

Статус: proposed. Требуется решение Ian Panaev: решение добавляет исходящую границу доверия ([AGENTS.md](../../AGENTS.md), «Обязательные границы»; [SECURITY.md](../../SECURITY.md): «при появлении webhook защита от SSRF обязательна»). Дата: 2026-10-07.

## Контекст

CI/CD, агенты развёртывания и игровые студии узнают о новой сборке опросом. План этапа D ([API_EVOLUTION](../API_EVOLUTION.md), [API_MAP](../API_MAP.md)) описывает `R/events`, `R/webhooks`, transactional outbox, повторную доставку и подпись; ничего из этого не реализовано.

Факты текущего кода, на которые опирается решение:

- `GET /api/v1/repositories/{r}/changes?after=&limit=` (`listCatalogChanges`, право `artifact.list`, [ADR 0058](0058-pull-mirrors.md)) уже отдаёт упорядоченную ленту репозитория: `{items: [{sequence, action, artifactId, detail}], head, next}`, до 100 событий. События пишутся в `arkvory_audit` под блокировкой репозитория в той же транзакции, что и изменение каталога, поэтому курсор по `sequence` не теряет событий и порядок внутри репозитория определён. Событие — подсказка «изменилось вот это»; потребитель перечитывает состояние через обычные маршруты чтения.
- Первая половина плана («events cursor») этой лентой фактически закрыта. Не закрыто: уведомление получателя без опроса.
- Исходящие запросы сервера сейчас идут только на адреса, заданные администратором в `ARKVORY_MIRRORS_FILE`, и на фиксированные адреса продукта. Цикл зеркал в worker (`apps/worker/src/mirror-loop.ts`) — готовый образец: курсор, повторы, состояние в БД, метрики `arkvory_mirror_*`.
- Секрет подписи сервер обязан знать (в отличие от токенов, которые хранятся хешем). Хранилища секретов, кроме файлов службы (ключ зеркала, `ARKVORY_KEYS_FILE`), нет.
- Усечения `arkvory_audit` в коде нет; усечение появится только вместе с политикой хранения журнала, и тогда окно ленты станет окном воспроизведения.

## Решение (предлагается)

1. **Источник — существующая лента.** Отдельный outbox или журнал событий не вводится: он дублировал бы `arkvory_audit`. Доставка — потребитель ленты со своим курсором, как зеркало.
2. **Подписки задаёт оператор файлом** `ARKVORY_WEBHOOKS_FILE` (JSON, как `ARKVORY_MIRRORS_FILE`): `{id, repository, url, secretFile, actions?}`. API управления подписками и хранение секрета в БД не вводятся: секрет лежит в файле с правами учётной записи службы, как ключ зеркала. Это не требует нового хранилища секретов и не расширяет права ключей.
3. **Состояние доставки в БД** — одна таблица `arkvory_webhook_state` (`subscription_id`, `cursor`, `last_success`, `failing`, `error_code`): независимый жизненный цикл, как `mirror-state`. Расширение схемы только аддитивное ([ADR 0059](0059-schema-updates-behind-verified-backup.md)).
4. **Доставка — цикл в существующем worker.** Для каждой подписки: читать ленту после курсора пачкой до 100, отправлять события по одному в порядке `sequence`, сдвигать курсор только после ответа 2xx. Гарантия — at-least-once; порядок внутри репозитория сохраняется, потому что событие N+1 не уходит, пока N не доставлено. Получатель дедуплицирует по `id = <repository>:<sequence>`.
5. **Тело** — JSON: `{id, repository, sequence, action, artifactId, detail}`: те же поля, что у ленты, плюс репозиторий. В теле нет байтов, автора события, секретов и метаданных пользователей.
6. **Подпись**: заголовки `X-Arkvory-Delivery` (то же `id`), `X-Arkvory-Timestamp` (UTC, секунды) и `X-Arkvory-Signature: sha256=<hex HMAC-SHA256(secret, timestamp + "." + body)>`. Получатель проверяет подпись и отвергает метку времени старше 5 минут. Ротация — второй `secretFile` на переходный период.
7. **Повторы.** Экспоненциальная пауза с jitter от 5 с до 1 часа. Недоступный получатель не задерживает загрузки, скачивания и других подписок: цикл подписки изолирован. Состояние `failing` публикуется метрикой `arkvory_webhook_failing` и правилом `ArkvoryWebhookFailing`.
8. **Защита от SSRF** (обязательна по SECURITY.md): только HTTPS с проверкой сертификата (HTTP — лишь для loopback); адрес разрешается до соединения, соединение идёт на проверенный IP (повторное разрешение имени не обходит политику); по умолчанию запрещены loopback, link-local, private, metadata-адреса; private-сети включаются явным списком CIDR `ARKVORY_WEBHOOKS_ALLOW_PRIVATE`; редиректы не выполняются; таймаут 10 с; ответ читается не более 4 KiB и не логируется.
9. **Границы** (значения предлагаются, подтвердить): не более 16 подписок на установку, один URL на подписку, 5 попыток в минуту на подписку максимум.
10. **Не входит:** события identity, UI управления, SSE и long-poll, доставка бинарных данных.

## Альтернативы

- **Только опрос ленты и документация.** Уже работает, но требует цикла у каждого потребителя и держит задержку. Остаётся поддерживаемым способом.
- **API `R/webhooks` из плана D.** Удобно для самообслуживания, но секрет должен храниться в БД зашифрованным: нужен ключ шифрования и выбранный secret store ([API_EVOLUTION](../API_EVOLUTION.md) прямо выносит это в отдельный контракт). Откладывается до решения о хранилище секретов.
- **Отдельный outbox.** Дублирует `arkvory_audit` и добавляет вторую точку расхождения; без измеренной нужды не вводится.
- **SSE или long-poll.** Не требует исходящих соединений сервера, но держит соединение на каждого получателя; возможен следующим шагом.

## Последствия

- Новая граница доверия: сервер отправляет запросы по адресам из файла оператора. Риск ограничен HTTPS-проверкой, SSRF-политикой и тем, что адрес задаёт только администратор.
- Права подписки — оператора, а не пользователя: подписка видит поля ленты своего репозитория. Отзыв доступа отдельного пользователя на неё не действует; об этом говорит документация.
- Стоимость — один цикл в worker и одна небольшая таблица; нагрузка на загрузки нулевая.
- Мониторинг: метрика и правило оповещения; запись `webhook.step_failed` без URL и тела.
- Совместимость: вся схема аддитивна; без `ARKVORY_WEBHOOKS_FILE` поведение не меняется.

## Проверка

Тесты обязаны показать: падение процесса после commit не теряет событие (курсор сдвигается только после 2xx); повтор доставки не повторяет бизнес-операцию и дедуплицируется по `id`; недоступный получатель не задерживает загрузку байтов; порядок внутри репозитория сохраняется при повторах; запрещённые адреса (loopback, link-local, metadata, private, смена DNS между проверкой и соединением, редирект) отклоняются; неверная и просроченная подпись не принимается эталонным проверяющим кодом; секрет и тело не попадают в журнал. Интеграционная проверка идёт на реальном PostgreSQL через `npm run gate`.

## Вопросы к владельцу

1. Подписки файлом оператора (предлагается) или API с шифрованным секретом в БД?
2. Допускать ли private-сети по CIDR-списку или только публичные адреса?
3. Подтвердить предложенные лимиты (16 подписок, 10 с, 4 KiB, окно подписи 5 минут).
4. Формат тела: поля ленты (предлагается) или envelope из [API_EVOLUTION](../API_EVOLUTION.md) (`type`, `schemaVersion`, `occurredAt`)? Для `occurredAt` лента времени не отдаёт.
