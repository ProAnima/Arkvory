# 0058. Зеркала репозиториев: свой каталог, забор по публичному API

Статус: accepted. Owner: Ian Panaev. Дата: 2026-10-02. Заменяет mirror-профиль [ADR 0044](0044-replication-profiles-and-control.md) (синхронный HA-профиль ADR 0044 остаётся отдельной темой).

## Контекст

Потребители (CI/CD, агенты развёртывания) работают в разных сетях и на разных площадках. Им нужна копия выбранных репозиториев рядом: скачивание без дальнего канала и чтение, когда главный сервер недоступен. Проект ADR 0044 держал каталог и права только на главном: каждое чтение с зеркала авторизовалось у главного (гранты по 5 с), узлы регистрировались по mTLS, нужен был отдельный протокол и журнал. Такое зеркало не раздаёт без главного, а объём работы несоразмерен задаче. Владелец выбрал (2026-10-02): у зеркала свой каталог и свои ключи, копирование забирает само зеркало.

Факты текущего кода, на которые опирается решение:

- изменения каталога одного репозитория выполняются под транзакционной блокировкой `18472/hashtext(repository)` и пишут `arkvory_audit`; публикация файла блокировку не брала и в журнал не писалась;
- изменения стадий выполняются под той же блокировкой и пишутся в `arkvory_promotion_events`;
- UUID артефакта выдаёт сервер; загрузка частями (`uploads` + `parts` + `complete`) уже переживает обрывы;
- отдельной таблицы репозиториев нет: репозиторий существует через права.

## Решение

**Зеркало — обычная установка Arkvory.** В ней отдельные репозитории объявлены зеркалами репозитория другого (главного) сервера. Остальные репозитории той же установки работают как обычно. Зеркало раздаёт свой каталог своими ключами и учётными записями; пользователи, ключи и права с главного не переносятся. Отзыв ключа на главном на зеркало не действует.

**Что копируется.** Опубликованные артефакты с их байтами и **теми же ID**, аннотации (метки, метаданные, коллекции), регистрация UPack, стадии, текущие пути файлов (assets) и удаления. Номера ревизий аннотаций и путей на зеркале свои: история зеркала начинается с первой синхронизации. Не копируются незавершённые загрузки, ссылки удержания (references), вложения (attachments), история путей, которой зеркало не видело, журналы аудита и политики хранения. Скачивание по ID, по пакету (версия, диапазон, стадия) и по пути файла на зеркале отвечает так же, как на главном на момент последней синхронизации.

**Лента изменений на главном.** Журнал `arkvory_audit` становится полной упорядоченной лентой репозитория:

- публикация (`artifact.publish`) берёт блокировку репозитория в той же короткой транзакции, что меняет статус, и пишет событие; порядок блокировок тот же, что у остальных изменений каталога (доступ сервиса → репозиторий);
- изменения стадий пишут `stage.add` / `stage.remove`, изменения путей — `asset.replace` / `asset.restore` с путём;
- новая колонка `detail` (путь или стадия), миграция 27, аддитивно.

Под блокировкой номер события выдаётся в порядке commit внутри репозитория, поэтому курсор по `sequence` не теряет событий. Новый маршрут `GET /api/v1/repositories/{r}/changes?after=&limit=` с правом `artifact.list` (ключ только для чтения) отдаёт `{items: [{sequence, action, artifactId, detail}], head, next}` без автора события. Событие — подсказка «у этого артефакта изменилось это»: зеркало перечитывает текущее состояние через существующие маршруты чтения, поэтому повтор и пропущенные промежуточные состояния безопасны.

**Синхронизация на зеркале** — цикл в существующем worker, новой службы нет. Для каждого зеркального репозитория:

1. Первое заполнение: запомнить `head` ленты, затем пройти `GET R/artifacts` и `GET R/assets/page` постранично и привести каталог к ним; потом следовать ленте от запомненного `head`. Порядок «сначала head, потом список» не теряет удалений, случившихся во время заполнения.
2. Следование ленте: события применяются по порядку, курсор сохраняется только после применения события. Удаление на главном удаляет артефакт на зеркале обычным путём удаления (tombstone, затем GC).
3. Байты копируются загрузкой частями в локальное хранилище под тем же ID (`StorageService` с источником ID, равным ID главного, и служебным субъектом зеркала): часть скачивается с главного по Range, проверяется её SHA-256, записывается; после перезапуска копирование продолжается с первой отсутствующей части. Итоговые размер и SHA-256 сверяются с главным при `complete`. Другой SHA-256 для того же ID — ошибка `mirror_mismatch`, существующий файл не перезаписывается.
4. Пакет UPack регистрируется на зеркале из тех же байтов тем же валидатором, поэтому его идентичность совпадает с главным.

**Только чтение.** Запись в зеркальный репозиторий отклоняется для всех, кроме синхронизации: загрузки, аннотации, пути, стадии, удаление, продвижение в него и политики очистки получают 409 с причиной `mirror_read_only`. Продвижение копией из зеркала в обычный репозиторий разрешено.

**Настройка** — файл `ARKVORY_MIRRORS_FILE` (JSON, как `ARKVORY_KEYS_FILE`): `{repository, upstream, sourceRepository, tokenFile}`. Ключ главного лежит в отдельном файле с правами только для учётной записи службы и в БД, журналы и копии не попадает. TLS проверяется всегда; корпоративный УЦ главного добавляется worker через стандартную `NODE_EXTRA_CA_CERTS`. Изменение — `arkvory configure --mirror <repository> --mirror-upstream <origin> [--mirror-source <repository>] --mirror-token-file <file>` и `--mirror-detach <repository>`. До изменений команда проверяет главный этим ключом: `capabilities.features.mirrorFeed` и ответ ленты для исходного репозитория. Затем она пишет ключ и `mirrors.json` в `config/mirrors/` с правами `runtime.json`; в Compose каталог монтирует только на время зеркал файл-дополнение `config/compose.mirrors.yml`. После этого API и worker перезапускаются с проверкой готовности, при сбое прежние файлы возвращаются. API читает файл для запрета записи и показа состояния, worker — для синхронизации. Состояние (курсор, фаза, отставание, ошибка, объём) хранится в таблице `arkvory_mirror_state` и видно в `GET /api/v1/mirrors`, консоли и метриках `arkvory_mirror_*`.

**Отсоединение.** Запись репозитория удаляется из `ARKVORY_MIRRORS_FILE` (в установках — `arkvory configure --mirror-detach <repository>`), API и worker перезапускаются. Репозиторий становится обычным: синхронизация прекращается, запись разрешается, ID и данные остаются. Это ручной переход на копию при потере главного (RPO равен отставанию зеркала). Обратного присоединения в этом решении нет.

## Альтернативы

- Каталог и права только на главном (ADR 0044): зеркало не раздаёт без главного, нужны регистрация узлов, mTLS и протокол грантов. Отклонено владельцем.
- Главный отправляет на зеркала: нужен входящий доступ к каждому зеркалу и ключ записи на главном. Отклонено.
- Новые ID на зеркале: ссылки и скачивание по ID с главного не работали бы на зеркале.
- Периодическая полная сверка вместо ленты: тысячи запросов на каждом цикле и отставание на минуты. Полная сверка остаётся только как первое заполнение и ручной `resync`.
- Отдельная служба зеркала: регистрация в установщиках, как у агента копий, без выигрыша — у worker уже есть БД, хранилище и супервизор.

## Последствия

- Публикации одного репозитория сериализуются на время короткой транзакции смены статуса; проверка байтов идёт до неё.
- Worker получает исходящий HTTPS к главному и зависимость от SDK (allowlist `apps/worker` → `packages/sdk`): зеркало — клиент публичного API главного.
- Зеркало не является резервной копией установки (нет пользователей и ключей) и не становится главным автоматически.
- Главный и зеркало обновляются независимо; зеркало требует на главном версию с лентой изменений (capability `mirrorFeed`).

**Состояние** — `GET /api/v1/repositories/{r}/mirror` с правом `repository.read` (404 для обычного репозитория): фаза, `caughtUp`, время последней проверки и синхронизации, код последней ошибки, число и объём скопированного. Номера ленты глобальные, поэтому их разность не равна числу изменений и в ответ не выводится.

Удаление на зеркале идёт через хранилище удалений, а не через сценарий клиента: клиентам удаление разрешено только управляемым ключом, а синхронизация — системный субъект. Перед удалением зеркало снимает свои стадии, иначе они защищали бы копию.

## Проверка

- `tests/integration/mirror.test.mjs` — два экземпляра, каждый со своей БД и каталогом хранения:
  - первое заполнение и следование ленте: артефакты с теми же ID и байтами, файл из нескольких частей, аннотации, пакет, стадия, путь, удаление, перенос пути;
  - запрет записи клиентам (409 `mirror_read_only`) и состояние зеркала;
  - обрыв копирования и продолжение только с недостающих частей;
  - недоступный главный: зеркало продолжает раздавать, ошибка записана в состоянии.
- `tests/integration/mirror-feed.test.mjs` — лента: состав и порядок событий, страницы, доступ ключом чтения без авторов, ошибки курсора, числовой порядок при десятках событий (`ORDER BY` текстовой колонки сортировал «10» раньше «9» и в `R/audit`; исправлено там же и в журнале сервисных ключей).
- `tests/mirror-sync.test.mjs` — порядок первого заполнения, применение событий с перечитыванием, курсор при сбое, отказ продолжать чужой источник.
- `tests/mirror-policy.test.mjs` — разбор настройки (только HTTPS, без учётных данных в URL), запрет записи для файловых и управляемых ключей при сохранении чтения.
- `tests/mirror-setup.test.mjs` — команда установщика: проверка главного до изменений, файлы и переменная для systemd и Compose, замена ключа, откат при сбое перезапуска, отсоединение, проверка главного без ключа в тексте ошибки.
- `tests/browser/mirror.mjs` — значок по состоянию синхронизации, источник в подсказке, нет действий загрузки, RU/EN. Интеграционный тест проверяет, что обнаружение операций скрывает изменения зеркала и оставляет чтение и продвижение из него.
