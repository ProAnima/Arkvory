# Перенос данных и откат

Текущий инструмент переносит **подготовленный файловый каталог**, не подключается к ProGet и не переносит его ACL автоматически. Экспорт с ProGet и полная миграция 4 ТБ не выполнены. Исходники не удаляются, production hostname не меняется.

## Инструмент

```sh
npm run import -- /path/to/export
```

По умолчанию dry run: потоково вычисляет SHA-256 и печатает JSONL-опись `{path,size,sha256,kind}`. Отказывает для symlinks, нештатных файлов, более 100 000 файлов, объектов больше 5 GiB и небезопасных путей. На время переноса исходный каталог должен быть неизменяемым. Имена каталогов/файлов не следует использовать для секретов: пути попадают в опись/журнал оператора.

Для применения задать `ARKVORY_BASE_URL` (HTTPS либо loopback), `ARKVORY_TOKEN_FILE`, `ARKVORY_REPOSITORY` и `ARKVORY_IMPORT_JOURNAL` (путь вне импортируемого каталога):

```sh
npm run import -- /path/to/export --apply
```

Порядок для файла: hash → deterministic Idempotency-Key → native multipart/resume → complete → UPack registration или asset pointer → полный download → проверка hash/size → fsync строки журнала. Повтор идентичного source path/hash/repository использует прежнюю сессию. Журнал является отчётом; не используется как основание пропустить проверку. Истёкшая cancelled-сессия требует новой операции с осознанно изменённой идентичностью импорта, не подмены descriptor.

`.upack` регистрируется как пакет; прочие файлы привязываются к относительному asset path. По умолчанию существующий другой asset не перезаписывается. `--replace-assets` разрешает атомарную замену только с проверкой текущей ревизии; старый blob остаётся. Изменённую версию UPack перезаписать нельзя.

Инструмент добавляет label `imported`, не выдумывает метаданные ProGet. Последние следует экспортировать отдельно и применить через annotation API с проверкой ревизий. Секреты передаются из файла, не через argv и не выводятся. Передачи последовательны, память bounded; автоматического расписания/ограничения суммарной полосы нет. Проверка скачиванием удваивает сетевой трафик — учесть это в окне миграции.

## Пилот и переключение (ожидают стенда)

1. Снять read-only инвентаризацию feeds, UPack identities, asset paths, revisions, metadata, scopes и пользователей. Зафиксировать точную сборку ProGet и версии клиентов.
2. Подготовить export без перепаковки и подписанную/контролируемую опись исходных хешей. Файловые URL и имена проверить на коллизии регистра и ограничения Arkvory.
3. Прогнать малый пилот: обычные, пустые, большие файлы, prerelease/build metadata, nested groups, нестандартные пользовательские поля. Сопоставить исходные и целевые permissions. Прерывать процессы и повторять перенос.
4. Перенести основной объём вне пиков, сверить журнал и независимую опись. До завершения совместимости только native тестовые клиенты.
5. Приостановить запись в ProGet, перенести финальную дельту, сверить byte counts/hash, метаданные, scopes и выбранные рабочие клиентские сценарии.
6. Сохранить конфигурацию hostname/TLS и rollback-маршрута. Переключать только после стендовых HA/restore/client проверок и согласованного окна.
7. При откате сначала остановить запись в Arkvory, инвентаризировать появившуюся дельту и перенести её обратно. Простое возвращение DNS без дельты теряет новые публикации. ProGet не удалять до завершения периода наблюдения.

## Резервное копирование до реализации online backup

Остановить API/worker и отключить автоматический перезапуск. Снять согласованный PostgreSQL dump и полную копию storage root вместе со storage-id, parts и staging. Не копировать только blobs, теряя БД. Секреты/конфигурацию хранить отдельно с ограниченными правами. Зафиксировать версии сервиса, PostgreSQL и схему 3.

Восстанавливать сначала в изолированную чистую среду: БД, соответствующий storage root, конфигурация; затем offline `npm run scrub`, проверки pending/available и sample downloads. Реплика не заменяет независимый backup: ошибки/удаления также реплицируются. Автоматический backup/restore runner и испытание восстановления 4 ТБ остаются открытыми задачами.
