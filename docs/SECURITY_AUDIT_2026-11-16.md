# Проверка безопасности и инфраструктуры — 2026-11-16

Область: исходники и история Git `ProAnima/Arkvory` и `ProAnima/Arkvory-Pro`,
зависимости npm, поставляемые runtime, Docker/Compose, GitHub Actions и локальные
одноразовые стенды. Рабочие серверы, внешние развёртывания и другие проекты на
этой машине не проверялись. Проверка не доказывает отсутствие неизвестных ошибок
и не является полной независимой экспертизой исходного кода.

Связанный результат: [документация и переводы](DOCS_TRANSLATIONS_AUDIT_2026-11-16.md).
Историческая приёмка обновления npm сохранена отдельно в
[отчёте обслуживания](MAINTENANCE_2026-11-16.md).

## Исправления

### Поставляемые runtime отставали от security releases

Node.js 24.21.0 заменён на **24.22.3** в Windows/Linux-установщиках,
нативной упаковке, Dockerfile, CI-образе и защищённой сборке Pro. Обновлены
SHA-256 Windows ZIP, Linux x64/arm64 и `node.exe`, проверки установщика,
инструкции и все 11 языков wiki. Минимум Node в manifests/lockfiles обоих
репозиториев и `.nvmrc` теперь 24.22.3. CI читает `.nvmrc`.

Это [security release Node.js от 11 ноября](https://nodejs.org/en/blog/release/v24.22.3/),
в том числе исправления HTTP/TLS. Применимость каждого upstream CVE к Arkvory
отдельно не доказана; например, приложение не использует серверный `node:http2`.

PostgreSQL 18.4 заменён на **18.7** в Compose, тестовых сервисах CI и
нативном Windows-пакете; digest Linux-стенда обновлён. Вендор выпустил
[исправления безопасности 12 ноября](https://www.postgresql.org/about/news/postgresql-187-1712-1616-1520-1425-and-19-rc-2-released-3442/).
В частности, [CVE-2026-6460](https://www.postgresql.org/support/security/CVE-2026-6460/)
позволяет владельцу SQL-объекта исполнить код сервера. Наличие работающего
Arkvory-эксплойта этой ошибки не утверждается.

Архивы Node проверены по официальному `SHASUMS256.txt`; подпись Windows
`node.exe` действительна, издатель OpenJS Foundation. Windows ZIP PostgreSQL
получен по HTTPS с `get.enterprisedb.com`; версия `postgres.exe` — 18.7,
Authenticode действителен, издатель EnterpriseDB Corporation. Это проверка
конкретного исполняемого файла, а не подпись всего ZIP.
SHA-256 архива `ead0bbc27fb678fa24dcf86b738981323042abd073c744103bf7f3aed23f9a33`
измерен локально и закреплён в `scripts/native-dependencies.mjs`.
**Независимый опубликованный checksum EDB не найден**: это ограничение
проверки происхождения, а не подтверждение подписи поставщика. При каждом
использовании упаковщик проверяет закреплённый хеш.

### Аудит npm отсутствовал в обязательной приёмке Pro

В Pro добавлен гейт `security` с `npm audit --audit-level=moderate`,
включённый в `verify` и `release`. Отдельное задание CI выполняет
`quick security`, чтобы формат, типы, unit/HTTP/recovery и аудит зависимостей
проверялись независимо от ресурсоёмкой физической приёмки. Сетевой отказ
аудита считается ошибкой. Полный `verify` и его требования не ослаблены.

### Конфигурация и доступ

Trivy сообщил `DS-0026` (LOW: нет `HEALTHCHECK`) в production Dockerfile:
фактический healthcheck API определён в `deploy/compose.yml` и вызывает
`apps/deploy/dist/probe.js`. Для запуска вне Compose отдельный probe должен
назначить оператор.

В `scripts/ci/linux.Dockerfile` найдены `DS-0002` (HIGH: root) и `DS-0026`
(LOW). Это одноразовый инструментальный образ для системных служб, упаковки
и стендов, не production runtime. Нужные привилегии CI не перенесены в продукт.
Срабатывания оставлены в отчёте; успешный exit сканера без порога severity
не означает отсутствия таких находок.

Ручная проверка Compose/Actions подтвердила:

- API/worker работают как `node`, с `read_only`, `cap_drop: ALL`,
  `no-new-privileges`, ограниченным tmpfs и ротацией логов; опубликованный
  API-порт привязан к loopback, production PostgreSQL не публикует порт хоста.
- Root у `initialize`/`vault-owner` нужен для одноразовой подготовки владельца
  volumes. `vault-owner` не имеет сети и запускается через maintenance profile.
- Подготовка Pro передаёт manifests/lockfile в сетевую фазу; защищённая сборка
  выполняется без сети, с readonly mounts, снятыми capabilities и отдельными
  лимитами ресурсов. Образы выбираются по immutable ID.
- Actions закреплены по SHA, checkout не сохраняет credentials, доступ по
  умолчанию `contents: read`. Release admission Core требует полный merge gate
  для точного коммита на main. Публикация релиза в рамках этой проверки не запускалась.

**Dependabot alerts отключены в обоих GitHub-репозиториях**: API ответил 403
с явным сообщением об отключённой функции. Доступ текущей учётной записи не
позволяет включить её; это открытая задача владельца репозиториев. `npm audit`
в CI остаётся действующим контролем, но не заменяет уведомления GitHub.

Серверный SAST-отчёт GitHub недоступен: для Pro API явно сообщил, что code
scanning выключен; для Core вернул `no analysis found` с требованием
дополнительного scope. Отсутствие доступного отчёта не считается нулём
находок. Включение сервиса и условия доступа требуют действий владельца.

Полный Pro CI ранее останавливался на preflight: 8 978 329 600 свободных байт
при требовании 60 GiB, ещё до `verify`. Нужен runner с достаточным диском,
числом inodes и KVM. Требования к 4 млн физическим файлам, 12 млн ссылкам и
виртуализации сохранены; отсутствие полной приёмки нельзя считать PASS.

## Воспроизведение и свидетельства

Приёмочные проверки выполняются через `npm run gate`. Для ручного аудита:

```text
npm audit --json
gitleaks git --log-opts=--all --redact=100 --ignore-gitleaks-allow --report-format=json --report-path=<history.json> .
gitleaks dir --redact=100 --ignore-gitleaks-allow --report-format=json --report-path=<worktree.json> <VCS-source-snapshot>
trivy fs --scanners vuln,misconfig --include-dev-deps --format json --output <repository.json> <VCS-source-snapshot>
trivy image --scanners vuln --format json --output <image.json> <image>
```

Локальные исходные отчёты сохранены в игнорируемых `test-results/security-*`:
версии и checksum инструментов, официальные Node SHASUMS, provenance EDB,
Gitleaks, Trivy, registry manifests и вывод гейтов. Они не содержат раскрытых
значений секретов и не являются автоматически опубликованными CI artifacts.
Сканирование истории охватывает полученные локально refs, а не скрытые
удалённые объекты, удалённые репозитории или серверные secret stores.
