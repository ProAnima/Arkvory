# Надёжность и управление передачами

## Граница обещаний

Реализованное клиентское восстановление при обрывах описано отдельно: [TRANSFER_RECOVERY](TRANSFER_RECOVERY.md). Оно дополняет сохранение multipart-частей на сервере, но не заменяет резервирование узлов.

Реализованные профили и их границы перечислены в следующем разделе; разделы после него — проектные требования, по которым эти профили построены и проверяются.

Standalone: один узел с backup, без доступности при его потере. HA одной площадки ([ADR 0072](adr/0072-single-site-ha.md)): весь корень установки (PostgreSQL, содержимое, конфигурация, релизы) на одном синхронно реплицируемом томе, переключение решает Pacemaker с fencing. Внешний NAS, БД или балансировщик, вынесенные из такого тома, остаются единственной точкой отказа. Потерю площадки закрывают зеркала с ручным переходом ([ADR 0058](adr/0058-pull-mirrors.md), [SECOND_SITE](SECOND_SITE.md)) и резервные копии.

## Границы реализованных профилей {#profiles}

**Standalone** (Windows, Linux, Docker Compose).

- Один сервер: его отказ или обновление — перерыв; клиенты продолжают передачи через resume/retry.
- На Windows Node.js не даёт переносимого fsync каталога ([ADR 0004](adr/0004-native-standalone-core.md)): `LocalBlobStore` синхронизирует сам файл, но не запись каталога (hard link в `blobs/`, переименование). Внезапная потеря питания вскоре после публикации может оставить в каталоге БД артефакт без файла; заметит это `scrub`, восстановление — из резервной копии или зеркала. Проверяется перезапуск и убийство процесса, а не аппаратная потеря питания. На Linux гарантия зависит от файловой системы, диска и включённых `fsync`/`synchronous_commit` PostgreSQL.
- Содержимое и vault — локальные каталоги; S3 не реализован ни для содержимого, ни для vault ([ADR 0071](adr/0071-s3-backup-vault.md) — предложение).
- Несколько томов содержимого ([ADR 0083](adr/0083-core-extension-points.md), N11): каждый том — отдельный экземпляр `local-storage` с теми же гарантиями записи, что у `default`; тома не дублируют друг друга, потеря тома — потеря его содержимого (восстановление из копии). Том, который не открылся или не прошёл проверку идентичности, не останавливает процесс: его upload отвечают 503 `unavailable`, новые загрузки идут в `default` (метрика `arkvory_storage_placement_fallback_total`), очистка его файлов ждёт его возвращения. Идентичность тома проверяется заново перед каждой записью и удалением и после записи, поэтому несмонтированный или подменённый между проверками том не получает данных, а его файлы не считаются удалёнными; каталог тома и его файл `storage-id` службы не создают: том помечает только команда хоста `arkvory volume-init` (проверка точки монтирования). Том с данными, удалённый из конфигурации, видно по метрике `arkvory_storage_backend_unconfigured` и оповещению. В кластере каждый том должен лежать на реплицируемой файловой системе каталога данных, иначе API не стартует. Готовность и `writable` следуют только за `default`. Переноса опубликованного содержимого между томами нет (Y4).

**HA одной площадки** ([ADR 0072](adr/0072-single-site-ha.md), эксплуатация — wiki «High availability cluster»).

- Только Linux с нативными пакетами: DRBD 9 (protocol C), Pacemaker + Corosync. Windows и Docker Compose остаются standalone.
- Fencing обязателен: `stonith-enabled=true`, `fencing resource-and-stonith` в DRBD, агент питания или гипервизора для каждого узла с данными; без него `cluster-check` не проходит, а переключение не происходит. SSH-остановка fencing'ом не считается.
- Профиль `ha-2` (два узла с данными) требует отдельного свидетеля без данных (`corosync-qnetd` и diskless tiebreaker DRBD) на машине, которая не делит питание и хост с узлами данных: иначе одиночный отказ лишает кворума. `ha-3` свидетеля не требует.
- Стенды CI (`deployment-ha*`) проверяют сценарии на гостевых ВМ KVM с `fence_virsh`. Агент fencing площадки (IPMI, Redfish, PDU, гипервизор) этим не проверен: его доказывает на месте `arkvory cluster-fence-test` для каждого узла до ввода в работу и после замены узла.
- 2xx на изменение означает минимум две полные копии (RPO = 0 для подтверждённого). При нехватке копий запись получает 503 `replication_degraded`, чтение продолжается; явное решение `cluster-single-copy` на срок снимает это правило, и потеря активного узла в это время теряет записи после решения.
- Потеря двух узлов из трёх участников кворума останавливает Arkvory целиком. Автоматического failback нет. Потеря площадки не покрывается.

**Зеркала и импорт** ([ADR 0058](adr/0058-pull-mirrors.md), эксплуатация — wiki «Mirrors and a second site»).

- Асинхронный забор по публичному API: RPO при потере источника равен отставанию зеркала (`syncedAt`). Переход — ручное отсоединение, без fencing старого источника и без обратной синхронизации.
- Не копируются учётные записи, ключи и права, ссылки удержания (references), вложения (attachments), журналы аудита, политики хранения и история путей до первой синхронизации. Зеркало — не резервная копия.
- Засев только добавляет и обновляет: после восстановления источника из копии артефакты, которых на источнике больше нет, на зеркале остаются, а удалённое зеркалом не возвращается.
- Конфликт версии пакета или занятый ID откладывается (`conflicts`, метрика `arkvory_mirror_conflicts`) и не останавливает ленту; конфликт в записях реестров (образы, Git LFS, npm) и повреждённые байты источника останавливают синхронизацию.
- Импорт по стадиям не переносит образы, Git LFS и npm.

## Запись

Временное содержимое → проверка → устойчивый blob → фиксация доступной версии. Между blob-store и БД нет общей транзакции. Reconciliation восстанавливает промежуточные состояния; cleanup удаляет только проверенные осиротевшие объекты после grace period.

Подтверждённая часть и публикация должны переживать заявленный класс отказа. Local staging на единственном шлюзе не выполняет HA-гарантию. При асинхронной репликации нельзя обещать нулевую потерю подтверждённых записей.

При потере безопасного кворума новые публикации приостанавливаются. Автоматическое снижение долговечности запрещено без явной политики. Failover БД и storage реализуется проверенными инфраструктурными средствами с fencing, а не собственным голосованием приложения.

## Очереди

Реализованная локальная часть: [TRAFFIC_CONTROL](TRAFFIC_CONTROL.md) — общий и per-principal payload budget, bounded admission, отмена и preClose, агрегаты readiness. Фиксированные доли download-бюджета и конечные leases уже реализованы для общего storage: [READ_GATEWAYS](READ_GATEWAYS.md). Очередь скачиваний с сессиями, классами, оценкой начала и подписанными талонами реализована в памяти процесса записи ([ADR 0076](adr/0076-download-scheduling.md), этапы 1–2 и часть 3); у шлюзов чтения очередь своя на процесс, общая очередь в PostgreSQL для шлюзов и HA (этап 4) не реализована. Динамическое перераспределение полосы между процессами остаётся целевым.

Раздельные upload/download/background очереди. PostgreSQL сохраняет задания, попытки, резервы и leases; короткие транзакции захвата, TTL, heartbeat, fencing generation и повторяемые операции. Фактическая передача не удерживает SQL-транзакцию.

Планировщик учитывает полосу площадки/шлюза/клиента, чтение/запись дисков, staging и параллелизм. Справедливость — по принципалу, а не только по IP. Приоритеты имеют aging и минимальную долю ресурса, чтобы миграция или большие файлы не голодали бесконечно.

Очередь ограничена по размеру и времени. Неактивные резервы истекают. При сетевом разделении просроченный lease не должен позволять старому шлюзу работать безлимитно параллельно с новым владельцем.

## Сеть

Streams с backpressure/отменой и ограниченным буфером на поток. Раздача не проходит через внешние приложения. Least connections недостаточно для распределения байт/с; глобальный лимит нельзя заменить per-request лимитом Nginx.

Измеряемый первый алгоритм: допуски по параллелизму и консервативные бюджеты на узел/класс с перераспределением. Upload shaping и суммарные ограничения всех потоков одного клиента проверяются отдельным прототипом. Число шлюзов не увеличивает скорость общего uplink.

При падении узла TCP-поток обрывается; новый запрос может обслужить другой узел, а клиент продолжает через Range/If-Range. Не обещаем незаметный перенос соединения. API поддерживает задачи и resume; клиенты без Range/retry проверяются отдельно.

## Деградация и безопасность

Ранее выданные ограниченные допуски могут работать в пределах TTL при недоступности API/БД, если это разрешено профилем. Задержка отзыва прав должна быть явно принята. Новым запросам без допуска нельзя выдавать байты в обход ACL.

При недостатке места блокируем новые uploads до повреждения рабочей ёмкости. Чтение и управление должны сохранять резерв ресурсов. Метрики/аудит не требуют записи в БД каждого блока файла.

## Наблюдаемость и восстановление

Службы поднимаются сами после падения, незапрошенного выхода, потери владения хранилищем или аренды и зависания главного потока: systemd, службы Windows и Docker перезапускают процесс, а зависание превращает в выход сторожевой поток. Матрица по платформам — [ADR 0067](adr/0067-self-healing-services.md).

Нужны live/ready health, глубина и возраст очередей, p95/p99 управления, throughput, память на поток, свободное место/staging, отказы допуска, checksum errors, лаг репликации, возраст backup и результат restore.

Backup БД и содержимого согласован по точке восстановления; cleanup не уничтожает нужные старые blob. Backup хранится вне основного домена отказа. Регулярно восстанавливаемся на чистую среду: репликация не защищает от логического удаления.

Испытания: остановка процессов в каждой фазе upload; потеря ответа после commit; отказ узла БД/storage; сетевое разделение; заполненный staging; повтор части; конфликт перезаписи; отзыв доступа; удаление во время download; работа при отключённых внешних приложениях.

Last-N автоочистка фиксирует только tombstones и audit под repository gate; physical bytes остаются до успешного online GC; [блокировки читателей и гарантии](ONLINE_CLEANUP.md). Квоты сериализуют upload reservations с policy update и учитывают retired bytes. Scheduler bounded, с live key recheck; диагностика best-effort с ограничением памяти, не блокирует transfer на ожидании записи логов. [Гарантии и ограничения](STORAGE_POLICIES.md).
