## Сохранённые инварианты

Блокировки не снимаются на другом соединении и не захватываются повторно, чтобы «починить» живую операцию. Одно соединение удерживается на загрузку/GC-операцию, а не на каждый chunk. Content pins по-прежнему используют одну сессию с reference counts на gateway. Передачи не удерживают длинные SQL-транзакции; потоковый SHA и границы памяти сохранены. На потерянной сессии нет fallback-записи через общий pool для публикации частей/blob.

SQL jobs уже проверяли generation, status и срок lease при heartbeat/finish — это подтверждено чтением operations.ts и прежними интеграционными тестами. Проблема была в локальном поведении worker, а не в отсутствии CAS.

## Дополнительная проверка передачи

- Защита content pin теперь повторно проверяется после bandwidth wait: ранее уже прочитанный блок мог уйти после потери сессии. Детерминированный HTTP-тест удерживает блок в pacing, теряет pin и проверяет обрыв без следующего блока для скачивания по ID и путей, адресующих пакет или файл; источник, pin и слот освобождаются.
- После metadata lookup проверяются отмена и pin до HEAD/304/416. Просроченная защита больше не возвращает успешный короткий ответ. Проверки не требуют SQL-запроса на каждый блок.
- Закрытый BandwidthGovernor больше не выдаёт блок, допуск которому был подтверждён непосредственно перед close; проверяются также пустой источник и EOF после потери доступности/отмены.
- Интеграционный тест завершает именно PostgreSQL-сессию shared content pin при здоровом writer: текущая раздача прерывается, readiness остаётся доступной, новое защищённое Range-чтение проходит без restart API.
- Справка TRANSFER_RECOVERY согласована с реализованными OPFS recovery и CLI staging/checkpoints; прежние утверждения об отсутствии восстановления удалены.
- Повторная проверка обнаружила отказ до первого байта: Fastify уже переносил binary headers на raw response, поэтому JSON-ошибка давала 500 вместо 503. Общий error handler снимает заголовки представления из обоих хранилищ; JSON получает собственные тип/длину без ETag, диапазона или имени файла. Регрессионный тест с настоящим production error handler воспроизвёл 500 до исправления; проверяет 503, Retry-After, тело и освобождение ресурсов. Ошибка после начала отправки по-прежнему обрывает поток.

Проверки добавлены в существующие quick/integration gates и обнаруживаются реестром автоматически. SQL-схема, публичные API и права доступа не меняются. Подробности: [ADR 0043](adr/0043-operation-session-protection.md).

## Исследование инфраструктурных вариантов

Для двух Linux-серверов первый кандидат остаётся active/passive с согласованной репликацией тома PostgreSQL + storage. DRBD protocol C сам по себе не задаёт политику при потере peer: отдельно нужны ограничения деградированной записи и fencing/quorum. [Руководство LINBIT](https://linbit.com/drbd-user-guide/drbd-guide-9_0-en/).

Третий полноценный сервер данных не обязателен во всех схемах. Надёжное внешнее отключение питания/доступа к storage может обеспечить fencing двух узлов. SSH-команда stop на потенциально зависшем узле не является достаточным production fencing; управляющий канал не должен зависеть от той же отказавшей сети. [Pacemaker: Fencing](https://clusterlabs.org/projects/pacemaker/doc/3.0/Pacemaker_Explained/html/fencing.html).

Альтернатива — отдельно HA PostgreSQL и проверенный replicated backend. Для PostgreSQL синхронный режим и запрет деградации записи задаются явно: Patroni различает synchronous_mode и synchronous_mode_strict. Это покрывает SQL, но не внешние файлы Arkvory. [Patroni: Replication modes](https://patroni.readthedocs.io/en/latest/replication_modes.html).

Рекомендация для проектирования: строгий ACK обеих копий, при потере требуемой копии запись приостанавливается; асинхронное зеркало — отдельный режим с явным возможным отставанием и без автоматического повышения до writer. Это рекомендация, не уже выбранная пользователем или включённая политика. Выбор допустимого арбитража/fencing и политики ACK остаётся открытым в [TWO_NODE_PLAN](TWO_NODE_PLAN.md). До него конфигурация работающего продукта остаётся standalone/shared-storage readers.
