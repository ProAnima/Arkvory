# Безопасность

Сервис не готов к публичному размещению. Сервисные ключи, пользовательские учётные записи и repository ACL реализованы; внешняя проверка угроз, эксплуатационные процедуры и полный аудит доступа ещё требуются перед production.

Учётные записи создаёт администратор. Сессии хранятся в PostgreSQL в виде хеша токена и отзываются при выходе, отключении аккаунта или смене пароля. Проверка membership и repository grants выполняется на каждом запросе. Пароли хешируются scrypt; пять неверных входов блокируют аккаунт на 15 минут. См. [ADR 0011](docs/adr/0011-users-groups-and-package-browser.md).

## Обязательные свойства

Управляемые machine credentials проверяются через PostgreSQL на каждом запросе, без положительного auth cache. Эффективные права — пересечение account policy и key bindings. Перед фиксацией изменения проверка повторяется под короткими row locks; revoke/disable/policy update упорядочены с публикацией. Уже начатое скачивание не прерывается только из-за revoke. Создание аккаунтов и назначение grants требует отдельного локального `serviceAdministrator`, не обычного `administrator`. Управление существующим аккаунтом допускается делегированному managed key с точной целью/actions/ceiling; самоуправление и цепочки запрещены. Отзыв grant блокирует pending activation, но не отзывает уже активированные ключи потребителя: для них требуется явный revoke/disable. Control mutation повторно проверяет authority после общей транзакционной блокировки; начатое snapshot-чтение может завершиться по прежнему grant. [Контракт делегирования](docs/SERVICE_DELEGATION.md). Подробнее: [эксплуатация и границы](docs/SERVICE_KEYS.md), [ADR 0017](docs/adr/0017-managed-service-keys.md).

- TLS с проверкой сертификатов; сервисные аккаунты с минимальными правами и возможностью ротации/отзыва.
- Авторизация на уровне репозитория и операции; фильтрация поиска и счётчиков по тем же правам.
- Ограниченные по объекту, действию, допуску и сроку токены передачи. Их нельзя логировать.
- Недоступность внешнего сервиса не включает анонимный режим доступа.
- Валидация путей, имен, архивов, metadata и размеров. Не использовать пользовательский путь напрямую как путь blob на сервере.
- Ограничения распаковки, количества частей/записей, очередей, staging и параллелизма.
- Защита от SSRF в импорте по URL и webhook; адреса задаются доверенными администраторами и ограничиваются сетевой политикой.
- Безопасный вывод метаданных в UI; отделение права загрузки от права approve/promote.
- Защита от CSRF для cookie-сессий web UI; серверные ключи не сохраняются в браузерном коде.

## Секреты и сообщения об ошибках

Используйте переменные окружения или выбранный secret store. Примеры не содержат рабочих ключей. В журналах остаются request ID, код ошибки и разрешённый контекст, но не Authorization, query key, signed URL или тело с секретами.

При обнаружении уязвимости не публикуйте credentials и эксплуатационные детали в общедоступном issue. Ответственный правообладатель — Ian Panaev, GitHub-аккаунт ProAnima. Выделенный закрытый канал раскрытия должен быть определён до внешнего выпуска; вымышленные email-адреса в каркасе не задаются.

Перед production: threat model, проверка прав и отзыва токенов, скан зависимостей, тесты путей/архивов, проверенный backup/restore и назначенный владелец обновлений.
